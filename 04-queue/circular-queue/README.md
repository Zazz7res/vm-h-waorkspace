# 循环队列 circular-queue

> 上一节 `04-queue/array-queue` 留了个烂摊子：`front` 和 `rear` 只会往右走、从不回头，于是 `rear` 顶到墙时
> 前面明明空着一堆格子，程序却报「满」—— 假满。本节的解法只有**一行代码**，但它是整章最重要的技巧：**取模**。
> 顺带还得解决取模带来的新麻烦：环上「空」和「满」长得一模一样。
> 本节主推**方案 A**（多带一个 `size` 计数器），同时把**方案 B**（老教材的「牺牲一个格子」）也完整实现了一遍
> （`CQueueWaste` / `cqueue_w_*`），让你能现场撞一次墙。

## 一句话是什么

循环队列 = 一整排格子 + `front`/`rear` 两个下标 + **每走一步都取模**：

```c
rear  = (rear  + 1) % capacity;   /* 到墙了不报错，绕回第 0 格 */
front = (front + 1) % capacity;   /* 队头也一样绕圈 */
```

数组在内存里**仍然是那条直线**，没有任何东西真的弯成了圈 —— 是我们把它**当成一个环来走**。
于是 `front` 走过的格子，`rear` 绕回来之后还能继续用：上一节的假满被彻底消灭，两头仍然是 O(1)。

## 为什么需要它（不用它会怎样）

**不用循环会怎样。** 上一节已经演到底了：`capacity=6` 的队列只剩 1 个人，`rear` 却站在第 6 格（墙外），`enqueue` 只能拒绝；
最后 `front = rear = 6`，队列**一个人也没有**却什么都塞不进去。线性数组队列只有两条路，都不好：搬数据（`compact`）
→ 假满消失但出队退化成 `O(n)`；不搬数据 → 出队 O(1) 保住了，但下标回不了头，空间越用越少。

**取模为什么就是绕圈。** 把下标想成**时钟的指针**：`capacity = 6` 就是一个只有 6 个刻度的钟
`0 → 1 → 2 → 3 → 4 → 5 → 又回到 0`。普通下标走到 6 就出界，但 `6 % 6 == 0`、`7 % 6 == 1`……
取模天生就是「绕回开头」的操作，指针永远在 `0..capacity-1` 里循环，既不越界也不留回不去的前缀。
`front` 和 `rear` 沿同一个圆周跑，`rear` 追着 `front`，两者之间「弧长」没满一圈就能塞人。

**环带来的新麻烦（本节真正的难点）。** 上一节判空是 `front == rear`、判满看右墙，两件事互不干扰；现在判空还是
`front == rear`，可**装满时 `rear` 沿环正好走一整圈，又回到 `front`，还是 `front == rear`**！光看两个下标的信息量
不足以区分这两种状态，必须再引入一个信息，于是有两条路：

| | 判空 | 判满 | 得到什么 | 付出什么 |
|---|---|---|---|---|
| A（`CQueue`，主推） | `size == 0` | `size == capacity` | 格子一个不浪费，判据是一眼能看懂的整数比较 | 多一个 `int` 字段；`size++`/`size--` 必须成对 |
| B（`CQueueWaste`） | `front == rear` | `(rear+1) % capacity == front` | 不用额外字段，纯靠两个下标 | 永久浪费 1 格；式子忘 `+1` 或忘取模就是灾难 |

**为什么队列非得两头都 O(1)。** BFS、消息队列这类场景是「进一次、出一次」高频交替的，一头不是 O(1) 整体就退化成
每任务 O(n)。循环队列的全部技术含量就是：**在不搬数据的前提下让空间能反复复用** —— 取模负责复用，
`size`（或路标格）负责不认错状态。

## 图解：直线 + 一根回指的箭头

### 绕圈之后的内存布局（`capacity = 4`，方案 A）

入队 10、20、30、40 时 `rear` 从第 3 格绕回 0；再继续进出，就会出现下面这类「下标顺序 ≠ 排队顺序」的状态：

```
  下标      0       1       2       3
        ┌───────┬───────┬───────┬───────┐
   data │  30   │  40   │   ·   │  10   │   ← 内存里仍然是一条直线
        └───────┴───────┴───────┴───────┘
          ▲                       ▲
          └────── 首尾相接 ────────┘  front=3（队头是 10）, rear=2（新人站 data[2]）, size=3

  逻辑顺序（谁先谁后）＝ 从 front 出发沿环走到 rear，跟下标大小【无关】：
        data[3]=10 → data[0]=30 → data[1]=40 →（data[2] 空，该站新人）
```

★ 记住这句：**环上「先后」= 沿环走，不是比下标大小。** 这一条比取模本身更容易让人翻车。

### 「空」和「满」为什么会撞车（`capacity = 4`）

```
  空队列（0 人）      front == rear == 0，弧长 0
      [  ·  ][  ·  ][  ·  ][  ·  ]        F,R 重合在第 0 格
  装满（4 人，方案 A） rear 沿环走了整整 4 步，又落回 front，还是 front == rear
      [ 10  ][ 20  ][ 30  ][ 40  ]        F,R 又重合在第 0 格
```

两种状态下两个下标的数值**完全相同** —— 程序只看它们分不出「一圈都没用」还是「一圈全用满」。
所以必须补一个信息：`size` 字段（方案 A 里 0 对 4，立判），或者「不许站人」的路标格（方案 B 让装满时差一格）。

### 方案 B 为什么非得浪费一格（`capacity = 4`，可用只有 3 格）

```
  装 3 个之后：front=0, rear=3
      [ 10  ][ 20  ][ 30  ][  ·  ]   第 3 格（R 站的）就是路标，谁也不许放人
        F                        R   判满：(rear+1)%4 = (3+1)%4 = 0 == front ✓ → 到此为止
  硬放第 4 个：写 data[3]=40，rear 变成 (3+1)%4 = 0 == front
      → 状态和「空队列」一模一样，程序会以为队列是空的，整环数据全丢
```

所以这不是抠门，是**两个下标的信息量不够**。`cqueue_w_init` 干脆拒绝 `capacity <= 1` —— 只有 1 格时
`front == rear` 与 `(rear+1)%capacity == front` 会同时成立，方案 B 根本不成立。这条就是最硬的证据。

### 「哪些格子还活着」怎么判断

`rear` 绕圈之后会比 `front` 小（比如 `front=3`、`rear=1`），朴素的大小比较会把整段弧切错：
`front <= i && i < rear` 在这种状态下区间为空，可队里明明有人。唯一正确的式子是

```
  (i - front + capacity) % capacity < size     例 front=3, size=4, cap=6 → 活着的是 3、4、5、0（断成两段）
```

所以遍历环必须写 `for (k = 0; k < size; k++) idx = (front + k) % capacity;`，绝不能写 `for (i = front; i < rear; i++)`。
`cqueue.c` 里那个静态小工具 `cq_alive` 就是这一行式子。

## 逐个操作拆解

### `cqueue_init(CQueue *q, int capacity)` —— 建环，O(capacity)

`malloc` 出 `capacity` 个格子，`front = rear = size = 0`，统计字段归零。为什么强调「三个字段一起归零」？因为
`front == rear` 和 `size == 0` 是**两套判据**，必须同时成立；如果留下 `size = 0` 却 `front != rear` 的鬼状态，
就成了「既说不空、又说不满」的 bug 温床。`capacity <= 0` 或 `malloc` 失败就建空壳（`data=NULL`、`capacity=0`），
后续所有操作安全失败、绝不解引用空指针。注意方案 A 的**可用容量 = capacity**，一格都不浪费。

### `cqueue_destroy(CQueue *q)` —— 销毁，O(1)

`free` + `data` 置 `NULL` + 其余字段全部复位。置 `NULL` 让误用当场崩而不是悄悄读垃圾，也让重复 `destroy` 安全
（`free(NULL)` 是合法空操作）。谁 `malloc` 谁 `free`，否则 ASan 报泄漏。

### `cqueue_enqueue(CQueue *q, int value)` —— 入队，O(1)

```c
if (q->size == q->capacity) { /* 真满，reject_full++ */ return false; }   /* ② 判【人数】 */
q->data[q->rear] = value;                                                  /* ③ 先放 */
q->rear = (q->rear + 1) % q->capacity;                                     /* ④ ★ 到墙就绕回 0 ★ */
q->size += 1;                                                              /* ⑤ 人数 +1 */
```

第 ② 步就是本节对上一节的**本质修正**：判的是 `size == capacity`，不是「`rear` 有没有顶到墙」—— `rear` 顶到最后一格
根本不算满，因为它下一步就绕回 0 了，就这一句改动假满彻底消失。第 ⑤ 步是方案 A 的命根子：漏写一次 `size++`，
判空判满从此全乱。代码用 `rear < old_rear` 识别「刚刚发生了一次绕圈」并累计 `wrap_count`，每绕一次就省下一次上节
那种「明明有空位却报错」。

### `cqueue_dequeue(CQueue *q, int *out_value)` —— 出队，O(1)

```c
if (q->size == 0) return false;                    /* ① 判空，且【不写】out_value */
int v = q->data[q->front];                         /* ② 先取值（挪指针之前）*/
q->front = (q->front + 1) % q->capacity;           /* ③ ★ 队头也绕圈 ★ */
q->size -= 1;                                      /* ④ 与 size++ 成对 */
if (out_value != NULL) { *out_value = v; }
```

对比上一节：这里 `front` 同样往前挪、同样不搬数据，但它挪到的是**环上的下一格**，而不是「往右一格直到撞墙」。
同一个动作加了取模就不再产生作废格子 —— 被 `front` 走过的格子 `rear` 绕回来还能继续用。这就是循环队列不需要
`compact` 的原因：空间不靠搬数据回收，而是靠下标绕圈自然复用。

### `cqueue_peek_front` / `cqueue_peek_rear` —— O(1)

队头在 `data[front]`，很简单；**队尾在 `rear` 的前一格**，这里藏着 C 语言经典坑：`rear == 0` 时 `rear - 1 == -1`，
`data[-1]` 直接越界（ASan 立刻报警）。正确写法：

```c
int tail = (q->rear - 1 + q->capacity) % q->capacity;
/* rear=0,cap=4 → (0-1+4)%4 = 3 ✓   rear=2,cap=4 → (2-1+4)%4 = 5%4 = 1 ✓ */
```

为什么写「先 `+capacity` 再取模」而不是 `if (rear == 0)` 特判？因为前者对**所有**情况都成立、一个分支都不用写
（这个技巧在 `04-queue/deque` 里每天都要用）。根子上的原因是：**C 的 `%` 是向零取整的余数，不是数学上的同余** ——
`-1 % 4` 等于 `-1`，不是 `3`。

### 查询组 `is_empty` / `is_full` / `size` / `capacity` 与静态工具 `cq_alive` —— 全 O(1)

```c
is_empty → size == 0
is_full  → size == capacity   /* ⚠ 千万别写成 rear == capacity，也别写成 front == rear */
size     → 直接读字段
cq_alive → (i - front + capacity) % capacity < size   /* i 换算成「从 front 沿环走几步」，步数 < size 就在弧上 */
```

方案 A 的好处在这里体现：判空判满都是一次整数比较，一眼看穿，不用记 `(rear+1)%capacity == front` 这种脆式子。
`cq_alive` 则是打印函数决定「这格显示数值还是显示 `·`」的依据。

### `cqueue_print` / `cqueue_ring` —— 教学打印

`cqueue_print` 打三行：① 所有格子的「下标 : 值」，不在弧上的打 `·`（注意**不是**上一节那种 `x` —— 环上没有永久作废
的格子）；② 标 `F`/`R`/`FR`，用与第一行相同的循环、相同格宽（` [%2d:%3s]`），免得中文把标记顶歪；③ **环上顺序
（队头→队尾）**，按 `(front + k) % capacity` 走 —— 这一行最能治「下标顺序 = 排队顺序」的误解。`cqueue_ring` 只画
一条数组 + 一根从最后一格回到第 0 格的箭头；不画真圆圈是因为①内存本来就是直线，两者一起展示最诚实，
②真圆圈按 `capacity` 排版，容量一大就画不下。

### 方案 B 全家：`cqueue_w_init` / `w_enqueue` / `w_dequeue` / `w_is_empty` / `w_is_full` / `w_size` / `w_print`

操作和方案 A **一模一样**（写 `data[rear]`、`rear` 取模；读 `data[front]`、`front` 取模），唯一区别是**不维护 `size`**，
靠判满式子挡人：

```c
w_is_empty → front == rear                          /* 弧长 0 */
w_is_full  → (rear + 1) % capacity == front         /* ★ 经典判满式：rear 再走一步就撞上 front */
w_size     → (rear - front + capacity) % capacity   /* 现算，不是读字段 */
```

`w_size` 同样有负数坑：`rear` 绕到 `front` 左边时 `rear - front` 是负数，要 `+ capacity` 把被除数抬正
（`rear=1, front=3, cap=4 → (1-3+4)%4 = 2`，环上活的正是 `data[3]`、`data[0]`）。
`w_enqueue` 拒绝时把式子整个展开打印给你看；`w_print` 额外用 `!` 标出那个「空着却不许放人」的路标格。

## 复杂度一览

| 操作 | 时间 | 空间 | 备注 |
|---|---|---|---|
| `init` | O(capacity) | O(capacity) | A 可用满 capacity；B 只有 capacity-1 |
| `enqueue` | **O(1)** | — | 判满看 `size==capacity`（A）/ 路标式（B），一次取模 |
| `dequeue` | **O(1)** | — | 一次取模，不搬数据 |
| `peek_front` / `peek_rear` | O(1) | — | 后者 `(rear-1+cap)%cap` |
| `is_empty` / `is_full` / `size` | O(1) | — | A 读 size；B 比较下标 / 现算 |
| `destroy` | O(1) | — | free + 置 NULL |
| `print` / `ring` / 遍历整条队 | O(capacity) / O(size) | — | 教学用；遍历必须 `(front+k)%cap` |

对比上一节：**假满没了**（`capacity` 格真能装 `capacity` 个），两头仍然都是 O(1)；新增成本是每次多一个取模，
以及判满式子必须想清楚。

剩下共 261 行输出，一句话带过：第 1 幕打印 `(i+1)%4` 的循环表和「直线 + 回指箭头」的环示意图；第 3 幕把 array-queue 那出戏原样重演且**全程没报假满**；空队 `dequeue`/`peek` 安全返回 `false` 且不写脏；方案 B 的 `capacity=1` 被直接拒绝；最后五个队列全部 `destroy`，`q` 打印出 `data=(nil), front=0, rear=0, size=0`。

## 常见的坑

**坑 1：把上一节的判满式搬过来，写成 `rear == capacity`。** 错法：`if (q->rear == q->capacity) return false;` —— 循环队列里 `rear` 取模过了，永远不等于 `capacity`，这条件永远为假，于是队满后照样往 `data[rear]` 写，**把队头那个人覆盖掉**，数据静默损坏。对法：A 用 `size == capacity`，B 用 `(rear+1) % capacity == front` —— 判满问的是「弧长」，不是「下标位置」。

**坑 2：`peek_rear` 直接写 `data[rear - 1]`。** 错法：`rear == 0` 时算出 `data[-1]`，数组越界。对法：`data[(rear - 1 + capacity) % capacity]`。根因是 C 的 `%` 向零取整：`(0-1)%6 == -1` 而不是 5。

**坑 3：忘写 `size++` 或 `size--`（两处不成对）。** 错法：入队只写 `data[rear]=v; rear=(rear+1)%cap;`，出队只挪 `front`。后果是 `size` 越走越偏，判空判满同时错，还会出现「明明有 3 个人却报空」。对法：`size` 的增减必须紧跟指针移动成对出现；或者改用方案 B（不存 `size`），但要接受浪费一格。

**坑 4：用下标大小比较来判断先后或遍历。** 错法：`for (int i = q->front; i < q->rear; i++)` —— `rear` 绕到左边时 `rear < front`，循环一次都不执行，队里的人全被当空气；`front <= i && i < rear` 判「活着」同样错。对法：`for (k = 0; k < size; k++) idx = (front + k) % capacity;`，判活着用 `(i - front + capacity) % capacity < size`。

**坑 5：方案 B 的判满式漏 `+1` 或漏取模。** 错法：写成 `rear == front` 判满 → 和判空撞车，队一满就报空，数据全丢；写成 `rear + 1 == front` → `rear` 在最后一格时 `rear+1 == capacity`，永远不等于 `front`，于是**判不出满并越界写**。对法：`(rear + 1) % capacity == front`，`+1` 和取模一个都不能少。

**坑 6：把方案 B 的 `capacity` 当成可用容量。** 错法：申请 `capacity = 10` 就以为能装 10 个 —— 实际只能装 9 个，第 10 次入队被拒。对法：接口上把两件事分开（本节的 `w_print` 就同时打印 `capacity` 和 `可用`）；要满容量就用方案 A。另外方案 B 要求 `capacity >= 2`，`cqueue_w_init` 直接拒绝更小的值。

**坑 7：在循环队列里也写 `compact`，或手动把 `front`/`rear` 归零。** 错法：把上一节的习惯搬过来「整理一下」写 `q->front = q->rear = 0;` —— 这是在结构体外破坏不变量，`size` 和实际数据立刻对不上。对法：什么都不用做，`rear` 绕回来自然复用那些格子；环本来就可以一直转下去。

## 自检问题

1. 为什么 `rear` 永远不会越界？—— 每次移动都是 `(rear + 1) % capacity`，结果恒在 `0..capacity-1`。
2. 空和满在两个下标上为什么区分不开？—— 装满时 `rear` 沿环走了整整 `capacity` 步又落回 `front`，和空队列的 `front == rear` 数值完全相同；必须再引入 `size` 或留一格当路标。
3. 方案 A 和方案 B 各自拿什么换什么？—— A 用一个 `int` 字段 + 两处成对的 `size` 增减，换到「格子不浪费、判据简单」；B 不要字段，代价是永久少用一格，且判满式子更脆。
4. `capacity = 4` 的方案 B 最多装几个人？第 4 次入队会怎样？—— 3 个；报满，`rear` 站的那格是路标，空着也不许用。
5. `peek_rear` 为什么写 `+ capacity` 而不是特判 `rear == 0`？—— 前者对所有取值都成立、不用分支；C 的 `%` 向零取整，`(0-1)%4` 得 `-1` 而不是 3。
6. `front=3, rear=1, capacity=6, size=4`：队头是谁？活着的是哪几格？—— 队头 `data[3]`；活着的是 3、4、5、0（断成两段），判据 `(i-3+6)%6 < 4`。
7. 本节的出队和上一节几乎一样，差别在哪？—— 都是「只挪 `front`、不搬数据」；差别在挪法：本节挪到环上下一个格子，格子会被 `rear` 绕回来复用，所以没有永久作废的前缀。
8. `size == 0` 与 `front == rear` 两套判据为什么要保持一致？—— 不一致就是「鬼状态」：程序一边说空一边说不空，多半是初始化漏了字段或某处 `size` 增减没成对，是 bug 的温床。
