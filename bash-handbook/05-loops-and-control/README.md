# 循环、`select` 与作业控制：谁在跑、跑几轮、跑完归谁

> 这一章只管三件事：**循环的词表是什么时候定下来的**、**循环体在哪个进程里跑**、
> **后台作业跑完之后这笔账记在谁头上**。
> 下面每一段输出都是这台机器（bash 5.3.9(1)-release，`seq`/`sleep`/`wc` 是 uutils Rust 版 coreutils 0.8.0，
> `ss` 有、`shellcheck` 没有，umask 钉在 0022，语言环境在 demo 里强制 `LC_ALL=C.UTF-8`）上真实跑出来的，
> 出自同一次 `bash demo.sh > ~/.cache/handbook-captures/bash05.txt`（957 行、22 节，
> 69 条带 `$` 的命令里只有第 5 节 `failglob` 那一条真实拿到退出码 1，其余全是 0）。
> 每次重跑只有这几类值会变：**进程号、毫秒数、轮询次数、并发完成顺序**；
> 本章把这类值全部换成「相等吗 / 谁比谁大 / 几个」的形式，所以正文里的数字都能复现。

## 你会遇到的场景

先对上号。下面每一条都在本章里真跑过，而且**都给出了原文**：

1. `for f in *.log` 里删掉当前文件、新建一个文件 —— 删的那个照样被处理一轮，新的这一轮**根本看不见**。
2. `for f in nosuch*.txt` 匹配不到文件时不但不跳过，还把字面图案交给你，接着 `rm "$f"` 一脸认真地报错。
3. `{1..$N}` 一个字都没展开，循环只跑一轮，`i` 的值是字符串 `{1..5}`。
4. `for ((i=1;i<=n;i++))` 出了循环，`i` 还挂在那儿；下一段代码复用同一个名字，接着上一个值往下跑。
5. 最后一行没有换行符的文件，`while read` 就是少跑一轮 —— 两份文件只差 1 个字节。
6. `while read host; do ...; done < hosts.txt` 里放一句会读标准输入的命令（真实场景是 `ssh`，本章不联网，
   用一句裸 `cat` 复现了同一个形状）：4 行名单只跑了 1 轮，剩下 3 行被它端走了。
7. 循环外面看 `n=0`，可循环体明明加了 3 次 —— 那一段是**管道里的另一个进程**。
8. `shopt -s lastpipe` 让计数回来了，但它**只救管道的最后一段**，而且要求作业控制是关着的
   （非交互 bash 默认就关着）；中间段的赋值照样丢。
9. `select` 在脚本里一声不响：没人喂输入时它一次都不跑，退出码还不是 0；菜单和 `PS3` 提示符走的是 **stderr**。
10. `read -t` 超时返回 **142**，读到结尾返回 **1**；把两者当同一件事的重试环会提前放弃。
11. `mapfile` 不加 `-t`，每个元素尾巴上都挂着一个 `\r`，后面比字符串全都不相等。
12. `cmd &` 之后不 `wait`：它失败了你永远不知道；`wait` 返回 0 又有三种完全不同的成因。
13. `disown` 之后 `jobs`、`wait`、`%1` 全都看不见它了，但进程**照样活着**。
14. 一把全扔到后台：6 个任务什么毛病都看不出来，危险在「任务数不由你定」的那一天（本章没有真跑一千个去撞 `ulimit -u`，那句只当推理）。
15. `wait -n` 和「数 `jobs -rp` 的个数」两把闸门，前者不轮询、后者好读；混用时失败的账容易漏记。
16. `break 2` / `continue 2` 的层数数错，或者 `break 9` 把所有循环一次跳光 —— 而 bash **没有循环标签**。
17. `kill -0` 探活：返回 1 有两种含义（没这个进程 / 有但轮不到你），只看码会提前收工。
18. 循环里放了 `grep`/`cat` 这类外部命令，一百万轮就是百万次 fork —— 而 `printf` 一百万轮一次都不 fork。

## 本章在讲什么，以及为什么是这三件事

前两章的读者已经拿到两条规矩：**词是被 IFS 切开再展开的**（第 02 章）、
**每句话只有一个退出码，管道则是一段一个**（第 03、04 章）。
把这两条塞进循环，就会长出本章的三个「看不见的手」：

> **一、词表在进入循环之前就被摊平。** `for` 的名单是展开出来的**快照**，
> 之后循环体里再 `rm`、再 `touch`、再改变量，都改不到这一轮的名单。
> 想让处理跟着目录走，只能换结构（每轮重新取，或者 `find -print0 | while read -d ''`）。
>
> **二、循环体可能在另一个进程里。** 只要循环进了管道，它就是管道的一段，
> 里面的赋值、数组、`cd` 全部留在原地 —— 这一条是第 04 章那条规矩在循环里的影子。
>
> **三、后台作业的收尾权在你手上。** `&` 之后唯一能拿到退出码的通道是 `wait`；
> `disown` 是放弃收尾权，不是让进程更安全。

这三条各自成套，所以本章的排版也是三条线：
第 3~7 节走**词表**这条线（`for` 的三形态、快照、通配三态、算术循环、不加引号的展开）；
第 8~16 节走**读输入**这条线（`while`/`until`、`read` 的语义与开关、最后一行、偷吃 stdin、
管道里的循环、`mapfile`、`select`）；
第 17~21 节走**进程与账**这条线（`break N`、作业控制、重试环、限并发、循环的成本）；
第 22 节是自证。

| 你想搞清楚的东西 | 本章用哪一节回答 | 一句话答案 |
|---|---|---|
| 循环里新建/删掉的文件为什么「看不见」 | 第 4 节 | 词表是进循环前摊开的快照，改磁盘不改快照 |
| 通配符没匹配到文件时循环会怎样 | 第 5 节 | 默认把**图案本身**当文件；`nullglob` 变空、`failglob` 当场炸 |
| `for (( ))` 和 `for in` 该用哪个 | 第 6、21 节 | 只要整数序列就用 `for (( ))`：没有词表、不占内存；`{1..$N}` 是废写法 |
| 最后一行为什么被吞 | 第 9、12 节 | `read` 的退出码问的是「撞到分隔符没有」，补 `\|\| [ -n "$x" ]` |
| 循环只跑一轮 | 第 13 节 | 循环体里的命令读了你的 stdin：喂 `/dev/null`、或名单挂 fd 3 |
| 循环里的计数出了循环就没了 | 第 14 节 | 那一段在子进程里；`lastpipe` 只救最后一段，重定向进循环最稳 |
| 要不要用 `mapfile` | 第 15、21 节 | 几千行随便用（一次消掉三个坑）；日志级大小回到流式读 |
| `select` 为什么不能用在脚本里 | 第 16 节 | 它读的是 stdin：没人喂就 0 轮且非 0，菜单和提示符走 stderr |
| 怎么从三层循环里跳出去 | 第 17 节 | `break N` 数得清层数时用；数不清就把内层包成函数用 `return` |
| 后台任务失败了怎么知道 | 第 18、20 节 | 只有 `wait` 能拿到；不 `wait` 等于把失败咽下去 |
| 怎么限并发 | 第 20 节 | 两把闸门：`jobs -rp \| wc -l` 数着放、`wait -n` 等一个走一个 |
| 循环慢在哪里 | 第 2、21 节 | 用 `type -t` 问循环体：`builtin` 不 fork，`file` 每轮 fork 一次 |
| `kill -0` 能不能当探活 | 第 18 节 | 能，但返回 1 有两种含义，真要用它当循环条件就把原文留着 |

## 1. 先把这台机器的发言权确认一遍

这一章要用的开关（`lastpipe`、`nullglob`、`failglob`、`wait -n`、`mapfile -d`、`break N`）都是 bash 4.x 时代陆续加进来的，
换个版本行为就不一样；报错文本还另外跟着**语言环境**走。所以第一步不是讲道理，是把这两件事钉死，
后面每一行原文才谈得上「你也能复现」。

```
$ bash --version | head -1
GNU bash, version 5.3.9(1)-release (x86_64-pc-linux-gnu)
[退出码 0]

$ echo "demo 已把自己改成：LC_ALL=[$LC_ALL] LANG=[$LANG]（你原来的终端是 LANG=$ORIG_LANG，LC_ALL=$ORIG_LC_ALL）"
demo 已把自己改成：LC_ALL=[C.UTF-8] LANG=[C.UTF-8]（你原来的终端是 LANG=zh_CN.UTF-8，LC_ALL=（未设））
[退出码 0]
```

↑ 第二格那条不是走过场：本机终端原本是 `zh_CN.UTF-8`，demo 一进来就把自己改成 `LC_ALL=C.UTF-8 LANG=C.UTF-8`（外加 `LANGUAGE=C`），
而且改只发生在这个脚本和它 fork 出的子进程里。为什么必须改：`rm`、`cat` 找不到文件时报的是
`No such file or directory` 还是「没有那个文件或目录」，全看这一档；bash 自己的报错同理。
**换语言环境等于换一本报错词典**，README 里能逐字核对的前提就是这一格被钉住。

然后是本章真正会碰的六个开关，出厂位置一个比一个容易猜错：

```
# 六个本章会碰的开关，此刻的默认位置（on=开）：

$ for o in lastpipe nullglob failglob globstar extglob nocaseglob; do printf "  %-12s %s\n" "$o" "$(shopt -q "$o" && echo on || echo off)"; done
  lastpipe     off
  nullglob     off
  failglob     off
  globstar     off
  extglob      off
  nocaseglob   off
[退出码 0]
# ★ 为什么 lastpipe 值得单独看一眼：它默认是 off，而 off 的代价是「管道最后一段里的赋值带不出来」。
#   第 14 节整节就在处理这一件事。
```

读法：六个**全是 off**。这一章后面每一节都在动这里面的一两个 ——
`nullglob`/`failglob` 决定「通配没匹配到」时循环怎么活（第 5 节），`lastpipe` 决定「管道最后一段里的赋值能不能带出来」（第 14 节），
`globstar` 关着的时候 `**` 就退化成一个普通的 `*`，`for f in **/*.txt` 看着像递归、其实只往下一层走。
默认位是 off 就意味着：**你什么都不做的时候，bash 走的是最危险那一档**，这一点第 5 节有现场。

第二个天花板是并发数，第 20 节限并发要靠它：

```
# 后台并发的天花板（第 20 节限并发时为什么不能一把全扔）：

$ echo "ulimit -u（最大用户进程数）= $(ulimit -u) ｜ /proc/sys/kernel/pid_max = $(cat /proc/sys/kernel/pid_max)"; echo "屏幕上不印真实 pid，pid_max 是个固定的内核参数，不是本机进程号"
ulimit -u（最大用户进程数）= 50372 ｜ /proc/sys/kernel/pid_max = 4194304
屏幕上不印真实 pid，pid_max 是个固定的内核参数，不是本机进程号
[退出码 0]
```

`ulimit -u` 这个 50372 是**你这个用户当前所有进程**的总数上限（不是单脚本上限），`pid_max` 只是号码循环的上限，
两个数量级差着 80 倍，所以真会先撞上的是前面那个。第 20 节「一把全扔后台」翻车就翻在这里。

最后一格决定本章的取证方式：

```
$ command -v shellcheck >/dev/null 2>&1 && echo "shellcheck 在：$(shellcheck --version | grep version: | head -1)" || echo "shellcheck 本机没有 —— 本章不装东西，脚本只能靠逐条真跑来验"
shellcheck 本机没有 —— 本章不装东西，脚本只能靠逐条真跑来验
[退出码 0]
```

这台机器没装 `shellcheck`，本章也不装东西 —— 所有结论只能靠**逐条真跑**，跑一条记一条。

先把本章的读数规矩立清楚（后面每节都按这个来）：

- 每格都是**一个全新的非交互 `bash -c`** 在跑，所以上一格 `shopt -s` 开的开关不会串到下一格；
  第 5 节那三档能各演各的，靠的就是这个。
- 围栏最后一行的 `[退出码 N]` 是 demo 自己打的总结行，**不是 shell 的输出**；它记的是这一整串命令跑完之后那个
  `bash -c` 的状态，而 `bash -c` 的状态 = 它**最后一条命令**的状态 —— 这决定了第 5、6 节里几个「看着矛盾」的读数。
- 子进程的 stderr 被并进 stdout 了，所以报错原文和正常输出混在同一格里，顺序就是屏幕上真实的顺序。

**这一节带走：**

- 本章的每个结论都挂在 bash 5.3.9 + `LC_ALL=C.UTF-8` 上；换机器、换 `LANG`，报错原文那一列就得重新取一遍证。
- 六个本章会碰的 shopt 默认**全是 off**：默认位不是「安全的位」，是「把没匹配到伪装成有文件」的那一档。
- `ulimit -u` = 50372 是用户级进程总数上限，比 `pid_max` 先撞；后台并发不是想开多少开多少。
- 没有 `shellcheck`：这一章的判断全部来自实跑，不来自静态检查器。
- `[退出码 N]` 是 demo 的总结行，等于「最后一条命令的退出码」，不是循环自己的成败。

## 2. 循环体里的东西是内建还是外部命令：一次 fork 都不许猜

「这个循环为什么这么慢」的第一反应通常是「bash 的循环本来就慢」，
但真正吃掉时间的几乎都不是循环本身，而是循环体里那一句**到底是内建还是外部命令**。
这件事不用猜，`type -t` 一个个问就行。

```
$ for c in : true echo printf read mapfile for while jobs wait kill test seq grep cat; do printf "  %-8s type -t → %s\n" "$c" "$(type -t "$c")"; done
  :        type -t → builtin
  true     type -t → builtin
  echo     type -t → builtin
  printf   type -t → builtin
  read     type -t → builtin
  mapfile  type -t → builtin
  for      type -t → keyword
  while    type -t → keyword
  jobs     type -t → builtin
  wait     type -t → builtin
  kill     type -t → builtin
  test     type -t → builtin
  seq      type -t → file
  grep     type -t → file
  cat      type -t → file
[退出码 0]
```

三种答案要分清：

- `builtin` —— `:`、`true`、`echo`、`printf`、`read`、`mapfile`、`jobs`、`wait`、`kill`、`test` 都跑在**当前这个 bash 进程**里，
  一百万轮也不 fork。
- `keyword` —— `for`、`while` 不是命令，是语法结构，所以它连「可执行文件」都不是，谈不上 fork。
- `file` —— `seq`、`grep`、`cat` 是磁盘上的程序：写进循环体就是**每轮一次 fork + exec**。

顺带两条容易看漏的：`kill` 和 `test` 在这里是内建（所以你 `kill` 的是 bash 自己实现的版本，行为跟 `/bin/kill` 不必完全一样），
而 `[ ]` 走的就是 `test`。

同一条命令，怎么写决定它是不是外部进程：

```
# type -t 给 builtin 的（read/mapfile/jobs/wait/[ ]）跑在**当前进程**里；给 file 的（seq/grep/cat）
#   每一轮都要 fork+exec 一个进程。慢的脚本几乎都是这个原因，而不是「循环本身慢」。

$ printf "seq 的真身：%s\n" "$(command -v seq)"; printf "/bin/true 的真身：%s ｜ type -t → %s\n" "$(command -v /bin/true)" "$(type -t /bin/true)"
seq 的真身：/usr/bin/seq
/bin/true 的真身：/bin/true ｜ type -t → file
[退出码 0]
```

`seq` 的真身是 `/usr/bin/seq`，这个没悬念。有意思的是第二行：bash 明明有内建 `true`（上面 `type -t → builtin`），
但你把路径写全成 `/bin/true`，`type -t` 立刻改口给 `file` —— **带路径的命令名绕过内建查找**，直接 exec 磁盘那个。
所以在循环里写 `/usr/bin/printf` 和写 `printf`，一轮的差别是「起不起进程」。

最后把两种「数到 5」放一起对照，这就是本章第 21 节成本账的缩影：

```
$ n=0; for i in $(seq 1 5); do n=$((n + 1)); done; echo "for i in \$(seq 1 5) 跑了 $n 轮；seq 自己是一个外部进程"
for i in $(seq 1 5) 跑了 5 轮；seq 自己是一个外部进程
[退出码 0]

$ n=0; for ((i = 1; i <= 5; i++)); do n=$((n + 1)); done; echo "for ((i=1;i<=5;i++)) 跑了 $n 轮；一个进程都没起，也没有词表"
for ((i=1;i<=5;i++)) 跑了 5 轮；一个进程都没起，也没有词表
[退出码 0]
```

两格都跑了 5 轮，账完全不同：

- `for i in $(seq 1 5)`：`$( )` 起 **1 个** `seq` 进程，它把 `1\n2\n3\n4\n5` 打到 stdout，bash 收回来再按 IFS 切成 5 个词。
  所以这里的 fork 是「一次」而不是「每轮一次」，代价是**名单先整个摊在内存里**（词表第 4 节讲）。
  如果你写的是 `for i in $(seq 1 "$n")` 且循环体里再去改 `n`，那也不会影响已经摊好的名单。
- `for ((i = 1; i <= 5; i++))`：**一个进程都没起，也没有词表**。它只是三次算术表达式，每轮判一次条件、加一次。

真正的百万次 fork 长这样：循环体里放 `grep`/`cat`/`sed`，或者放上面那个带路径的 `/bin/true`。
所以调循环的第一步不是加 `time`，是 `type -t` 问一遍循环体里每一个名字。

**这一节带走：**

- `type -t` 是零成本的探针：`builtin` 不 fork，`keyword` 不是命令，`file` 每轮 fork+exec 一次。
- `echo`/`printf`/`read`/`mapfile`/`test`/`kill`/`wait`/`jobs` 全是内建；`seq`/`grep`/`cat` 全是外部程序。
- 写绝对路径（`/bin/true`）会绕过内建，从 `builtin` 掉回 `file`。
- `$(seq 1 N)` 只 fork 一次（生成名单），`for (( ))` fork 零次且没有名单 —— 两者的慢都不是「循环慢」。
- 循环慢的元凶是**循环体里的外部命令**，逐个 `type -t` 才是可执行的优化步骤。

## 3. for 的三种形态，和「循环变量出了循环还活着」

`for` 有三种写法，但很多人身上的问题是另一件事：循环跑完之后，那个循环变量还挂在 shell 里，
下一段代码复用了同一个名字，就接着上一个值往下走。

```
$ for x in a b c; do printf "  拿到 [%s]\n" "$x"; done; echo "循环结束后 x=[$x]（★ 它不是块内变量，bash 没有块作用域）"
  拿到 [a]
  拿到 [b]
  拿到 [c]
循环结束后 x=[c]（★ 它不是块内变量，bash 没有块作用域）
[退出码 0]

$ for ((i = 0; i < 3; i++)); do printf "  i=%s\n" "$i"; done; echo "循环结束后 i=$i（所以复用同一个变量名的两层循环会互相踩）"
  i=0
  i=1
  i=2
循环结束后 i=3（所以复用同一个变量名的两层循环会互相踩）
[退出码 0]
```

两格的形状很像，收尾却不一样，这个差别值得记住：

- `for x in a b c`：`x` 是**逐个接住词表里的词**，循环结束后它停在**最后一个词** `c`。
- `for ((i = 0; i < 3; i++))`：打印到 `2` 就没了，但 `i` 出来是 `3` —— 因为循环是**先把 `i` 加到 3、再判 `3 < 3` 失败**才退出的。
  也就是说算术循环留下的值是「那个让条件终于不成立的值」，比最后一轮多用了一次。

`bash` 没有块作用域：`for` / `while` / `if` 的 `{ }` 都不开新作用域，所以循环变量就是**普通 shell 变量**。
它带着上一个循环留下的值**进来**，带着最后一个值**出去**。两层循环复用 `i`，内层一跑完外层的 `i` 就被改写了，
这不是「有时候」，是每次。

再看两格「一轮都没跑」的：

```
$ echo "空词表：for x in ; do echo 不该出现; done"; for x in ; do echo "不该出现"; done; echo "  一次都没跑，退出码=$?"
空词表：for x in ; do echo 不该出现; done
  一次都没跑，退出码=0
[退出码 0]

$ echo "没有位置参数时："; for a in "$@"; do echo "  不该出现"; done; echo "  退出码=$? ｜ 注意它和上面那条都不报错 —— 空循环在 bash 里是 0 不是失败"
没有位置参数时：
  退出码=0 ｜ 注意它和上面那条都不报错 —— 空循环在 bash 里是 0 不是失败
[退出码 0]
```

两格都是 0 轮，都是**退出码 0**。这里有个很多人会猜反的点：

- `for x in ;` 是空词表 —— 名单是空的，循环体一次都不执行，但 bash 不认为这是失败。
- `for a in "$@"` 在没有任何位置参数时，`"$@"` 展开成**零个词**（这是它在引号里的特殊待遇；
  换成 `"$*"` 就会展开成**一个空字符串**，循环照样跑一轮，拿到一个空值 —— 差别就在这儿）。

所以「循环没跑」和「循环失败」在 bash 里是两件事，靠退出码分不开。

★ 最阴的一条是这个：

```
# ★ 带走第一条：循环变量是**普通 shell 变量**。它带着上一个循环留下的值进来，
#   带着最后一个值出去。所以下面这条「看起来在数个数」的写法是坏的：

$ n=0; for f in x y z; do :; done; echo "n=$n ← 全程没碰过 n，但它没报错，看着像跑了 3 次"
n=0 ← 全程没碰过 n，但它没报错，看着像跑了 3 次
[退出码 0]
#   数个数请用 "${#arr[@]}"（第 15 节）或干脆计数：for f in ...; do n=$((n+1)); done。
```

`n` 全程没被碰过，循环也老老实实跑了 3 轮，`echo` 打出 `n=0`，
看起来像「我数了，结果是 0 个」，实际上你数的是**变量**而不是**轮数**。
要数轮数就自己在循环体里 `n=$((n + 1))`；要数元素就用 `${#arr[@]}`（第 15 节）。

**这一节带走：**

- `for in` 出来是「最后一个词」，`for (( ))` 出来是「让条件失败的那个值」（比最后一轮多 1）。
- bash 没有块作用域：循环变量是普通变量，带旧值进来、带最后值出去，两层循环同名必互相踩。
- 空词表、`"$@"` 无参数都是 0 轮且**退出码 0** —— 空循环不等于失败，别用 `$?` 判断「有没有东西可处理」。
- `"$@"` 无参时给 0 个词，`"$*"` 给 1 个空词，这是「循环莫名多跑一轮」的常见来源。
- 循环跑了没跑、跑了几轮，只有自己在循环体里计数才可信；`退出码` 和「变量还在」都证明不了。

## 4. 词表快照：循环里新建/删掉的文件，本轮根本看不见

这条是本章最值钱的一条，因为它一次解释了两件看起来相反的事：
「新放进去的文件循环看不见」和「已经删掉的文件循环还在处理它」。
四小段都在辅助脚本 `loopsnap.sh` 里，它只在沙箱的 `snap/` 子目录里造三个 `.txt`，跑完自删。

```
$ bash loopsnap.sh
=== 1. 词表快照：循环里新建的文件，本轮看不见 ===
  进循环前 ls 一下：a.txt b.txt c.txt 
  正在处理 snap/a.txt
  正在处理 snap/b.txt
  正在处理 snap/c.txt
  → 循环体跑了 3 次，可磁盘上现在有 4 个文件：a.txt b.txt c.txt zz_new.txt 
  → 为什么 zz_new.txt 没被处理：*.txt 只在**进 for 之前**展开了一次，
    展开结果（三个词）就是这一轮 for 的全部行程；循环体里再改磁盘改不动它。

  再开一个 for，同一个glob 现在展开成几个？
  → 第二轮的 n = 4（★ 同一个通配，两轮展开结果不同 —— 因为中间有人改了磁盘）
```

第一段说的事：`for f in snap/*.txt` 进了循环以后，循环体里 `: > snap/zz_new.txt` 造出来的文件**本轮就是看不见**，
而磁盘上明明已经有 4 个文件。原因不是「bash 缓存了目录」，而是：

> 通配展开是**进入 for 之前的一次性动作**。展开出来那三个词（`snap/a.txt snap/b.txt snap/c.txt`）
> 就是这一轮 `for` 的全部行程，之后循环体里怎么改磁盘，都改不到这排已经摊开的词。

第二行那个「第二轮的 n = 4」是同一件事的另一面：**快照的生命周期只有一轮 `for`**。
你再开一个 `for`，同一个通配重新展开一次，这次就是 4 个词 —— 磁盘改了，所以下一次展开的结果改了，仅此而已。

快照的另一面更疼：删掉的文件照样迭代到它。

```
=== 2. 词表快照的另一面：循环里删掉的文件，本轮照样迭代到它 ===
  轮到 snap/a.txt；它现在还在吗 → 在
cat: snap/a.txt: No such file or directory
  轮到 snap/b.txt；它现在还在吗 → 在
cat: snap/b.txt: No such file or directory
  轮到 snap/c.txt；它现在还在吗 → 在
cat: snap/c.txt: No such file or directory
  → 上面每一轮都报了 No such file or directory：词表是**名字**的快照，不是**存在性**的快照。
    「先收集名字、再逐个动手」的循环，动手前都得再 test 一次。
```

看清楚顺序：每一轮**开头**测 `[ -e "$f" ]` 都回答「在」（此时还没删），
紧接着循环体自己 `rm` 掉它，再 `cat` 就必然报 `No such file or directory`。
三轮全是这个形状，而且三条报错原文一条不少（`loopsnap.sh` 故意没加 `set -e`，就是要让你看见它们）。

结论是这句话：**词表是「名字」的快照，不是「存在性」的快照**。
`for f in *.log; do 处理 $f; rm $f; done` 这种「先收集名字、再逐个动手」的写法，
动手那一刻文件在不在，快照不担保 —— 所以 body 里第一步永远是再 `test` 一次。

第三种情况是「改名单的变量」，很多人以为这样就能动态加名单：

```
=== 3. 改「装着列表的变量」也晚了：for 要的是展开后的词，不是那个变量 ===
  word=one ｜ 现在我把 list 改成 (x y)
        改完之后 list 的实际内容 = x y（但循环还在按 old 走）
  word=two ｜ 现在我把 list 改成 (x y)
        改完之后 list 的实际内容 = x y（但循环还在按 old 走）
  word=three ｜ 现在我把 list 改成 (x y)
        改完之后 list 的实际内容 = x y（但循环还在按 old 走）
  → 循环里一共打了 3 个 word（one two three），一个 x/y 都没出现。
    循环结束后 list 的长度 = 2、内容 = x y，
    说明**变量确实被改了**，只是这一轮 for 早就跟它没关系了。
```

`for word in "${list[@]}"` 在进循环那一刻就把 `"${list[@]}"` 展开成了 `one two three` 三个词，
之后循环体里 `list=(x y)` 改的只是**变量本身**：变量确实被改了（长度 2、内容 `x y`），
但这一轮 `for` 早就跟它没关系了。一个 `x`、一个 `y` 都不会被处理。

最后一段是收口，直接给三种需求各自的写法；末了 demo 自己把前面四段总结了一遍（`↑` 那三行）：

```
=== 4. 收口：什么时候「快照」会变成 bug，什么时候它正是你要的 ===
  ① 想「本轮新产生的文件也一起处理」→ 别硬塞进同一个 for，外面套 while 反复跑，
     或者干脆用 find（它是边走边吐，见下面 ③ 那条区别）。
  ② 想「动手前确认它还在」→ for 的词表只保证名字、不保证存在；body 里先 [ -e "$f" ] 再说。
  ③ 与本章第 13 节直接相关：find … | while read 里的 while 是**另一个进程**，
     它拿到的是「管道里当下流过来的东西」，所以边生成边消费；
     而 for 的词表是**同一个进程在开始前**算完的。两者的可见性差别是结构性的，不是快慢问题。
[退出码 0]
↑ 四段全是同一件事的两面：`for` 的词表在进入循环**之前**就摊成了一排固定的词。
  所以「跑一遍目录里的文件，处理完就删掉它」这种写法，删掉的永远是上一轮的、看不见的永远是新出现的。
  要跟着目录走只能换结构：while + 每轮重新 ls，或者 find -print0 | while read -d（第 15 节）。
```

第 ③ 条是这节和后面几节的接口，值得单独拎出来：`find … | while read` 里的 `while`
拿到的是「管道里当下流过来的东西」，所以能边生成边消费；`for` 拿到的是「同一个进程在开始之前算完的一排词」。
这两个不是快慢差别，是**结构差别** —— 一个是过程（process），一个是名单（list）。
名单要跟着目录走只有两条路：每轮重新取（外面套 `while`），或者换成 `find -print0 | while read -d ''`（第 15 节）。

**这一节带走：**

- `for` 的词表在进入循环之前一次摊平，之后循环体里 `touch`/`rm`/改变量都改不到本轮名单。
- 新文件本轮看不见（下一轮 `for` 才看见）；已删文件本轮照样迭代到它，body 里必须自己 `[ -e ]`。
- 词表是名字的快照，不是存在性的快照；「收集完再动手」的循环，动手前重新确认一次。
- `for … | while read` 与 `for x in 名单` 的可见性差别是结构性的：一个消费过程，一个消费名单。
- 想让处理跟着目录走：外面套 `while` 每轮重取，或者 `find -print0 | while read -d ''`。

## 5. 通配符匹配到 0 个文件时，循环里有三种人生

`for f in nosuch*.txt` 匹配不到文件的时候，你猜 bash 怎么办？
答案分三档，而**默认那一档最危险**：它不但不跳过，还把图案本身当成一个文件交给你。

沙箱里此刻有什么、以及下面要用的那个图案：

```
# 沙箱里现在有什么、故意点一个不存在的名：

$ ls; echo "----- 下面全部用 nosuch*.txt 这个匹配不到任何东西的图案 -----" 
demo.sh
jobwait.sh
loopsnap.sh
loopspeed.sh
mapfill.sh
parlimit.sh
readlast.sh
readsteal.sh
selectmenu.sh
untilretry.sh
----- 下面全部用 nosuch*.txt 这个匹配不到任何东西的图案 -----
[退出码 0]
```

（沙箱里只有复制进去的辅助脚本，所以 `nosuch*.txt` 注定匹配不到 —— 这正是这一节要的场景。）

### ① 默认档：图案原样进循环

```
# ① 默认（nullglob/failglob 都关）：图案**原样**当词交给循环，循环照跑一轮。

$ for f in nosuch*.txt; do echo "  拿到的是 [$f] ← 这不是文件，是图案本身"; done; echo "  跑了 1 轮"
  拿到的是 [nosuch*.txt] ← 这不是文件，是图案本身
  跑了 1 轮
[退出码 0]
```

`*.txt` 匹配不到东西时，bash 默认**保留这个字面词**交给循环，于是循环跑了一轮，`$f` 的值就是 `nosuch*.txt` 这串字符本身。
「没文件」被伪装成了「有一个名字叫 `nosuch*.txt` 的文件」。

灾难现场通常长这样：

```
#   灾难现场是 rm / cp 这类拿到字面图案的写法：它不会删你的文件，但会让脚本一脸认真地报错。

$ for f in nosuch*.txt; do rm "$f"; done; echo "  退出码=$?"
rm: cannot remove 'nosuch*.txt': No such file or directory
  退出码=1
[退出码 0]
```

`rm` 拿到那个字面图案，报了 `No such file or directory` —— 它没有删掉任何你的文件（这点可以放心），
但脚本一脸认真地报错，而且只报一次。注意两个退出码是分层的：

- `rm` 失败 → 那个 `for` 循环的退出码就是它循环体里最后一条命令的状态，也就是 `1`；紧跟的 `echo "$?"` 于是打出 `退出码=1`。
- 但整格最后的 `[退出码 0]` 是 demo 那条 `bash -c` 的状态 —— 它最后是那个成功的 `echo`。
  这就是第 1 节立的规矩：**`[退出码 N]` 只看最后一条命令**，中间某条炸了它不知道。

### ② nullglob：匹配不到就变空

```
# ② nullglob：匹配不到就展开成**空**，循环一次都不进。这是「按文件列表干活」最该有的开关。

$ shopt -s nullglob; n=0; for f in nosuch*.txt; do n=$((n + 1)); done; echo "  进了 $n 轮 ← 循环体压根没执行"; shopt -u nullglob
  进了 0 轮 ← 循环体压根没执行
[退出码 0]
```

`shopt -s nullglob` 之后，匹配不到的图案展开成**零个词** —— 于是这一格和前一格的区别就是「0 轮 vs 1 轮」，
`for` 拿到空词表，循环体压根不执行（这正好接上第 3 节：空词表 0 轮、退出码 0，不报错）。
这一格末尾把 `shopt -u nullglob` 关回去，是因为开关会留着影响同一条命令行后面的写法。

### ③ failglob：匹配不到就当场炸

```
# ③ failglob：匹配不到就**当场报错、整条命令不执行**，脚本类工具里想「宁可炸不能静默」时用它。

$ shopt -s failglob; for f in nosuch*.txt; do echo 不该出现; done; echo "  退出码=$?"
bash: line 1: no match: nosuch*.txt
[退出码 1]
```

这一格值得逐行读，因为它**少了一行**：命令里明明还挂着 `echo "  退出码=$?"`，屏幕上却没有它。
`bash: line 1: no match: nosuch*.txt` 是 failglob 的报错原文（`line 1` 指的是 `bash -c` 里那一行），
它发生在**展开阶段**，命令根本还没开始执行，所以整条命令作废、后面的 `echo` 也没机会跑，
`[退出码 1]` 是那个 `bash -c` 的最终状态。这一格和 ② 的 `[退出码 0]` 摆在一起，就是「静默跳过」与「宁可炸」的真实账单。

三种怎么选，只看一个问题：**「没匹配到」在你的业务里算不算正常**。
算正常（清理临时目录、批量转换）→ `nullglob`；
不算正常、静默跳过会让故障咽下去（发布脚本、迁移工具）→ `failglob`；
两者都不开（默认档）→ 你必须在循环体里自己判断 `[ -e "$f" ]`，
而这正是最容易忘的一步。第 22 节会回头自证：本章所有辅助脚本都不依赖默认档那个字面图案。

**这一节带走：**

- 默认档下「0 个匹配」= 图案本身变成一个词进循环，`rm`/`cp` 会一脸认真地报错，但不会误删你的文件。
- `nullglob`：匹配不到展开成空 → 循环 0 轮、退出码 0；这是「按文件列表干活」最该有的开关。
- `failglob`：匹配不到 → 报错原文 `bash: line 1: no match: …`，整条命令不执行，`[退出码 1]`。
- 展开阶段的错误（failglob）发生在命令执行之前，所以连同一命令行里的后续命令一起作废。
- 选哪一档取决于「没匹配到」算不算正常；三档都不开时，循环体第一步必须是 `[ -e "$f" ]`。

## 6. for (( )) 只吃整数，以及无限循环怎么被掐掉

`for (( ))` 看着像「把 C 的 for 抄进 bash」，但它真正的身份是**三段算术上下文**。
认清这一条，能一次解释四件事：不用写 `$(( ))`、能直接写变量、`{1..$N}` 为什么是废写法、小数为什么当场炸。

```
$ for ((i = 1; i <= 3; i++)); do printf "%s " "$i"; done; echo "  ← 三段都是算术上下文，不需要 \$(( ))"
1 2 3   ← 三段都是算术上下文，不需要 $(( ))
[退出码 0]

$ N=3; for ((i = 1; i <= N; i++)); do printf "%s " "$i"; done; echo "  ← 这里能写变量，因为它本来就是算术上下文"
1 2 3   ← 这里能写变量，因为它本来就是算术上下文
[退出码 0]
```

两格都是 `1 2 3`。第一格想说：三段里**已经是**算术上下文了，再套一层 `$(( ))` 是多余的。
第二格想说：既然是算术上下文，`i <= N` 里的 `N` 就是按变量名去查值，不需要写成 `$N`（写了也对，但没必要）。
顺带一条实用价值：`for (( ))` 不生成名单，所以 `for ((i = 1; i <= 1000000; i++))` 的内存是平的，
而 `for i in $(seq 1 1000000)` 要先把一百万个词摊在内存里（第 2 节、第 21 节）。

接下来这格是全章被引用最多的一条坑（前言场景清单第 3 条就是它）—— 花括号展开不归算术管：

```
# 但**花括号展开**不是算术上下文：它发生在变量替换之前。这一条和第 02 章直接相关：

$ N=3; echo "  {1..\$N} 展开成：[{1..$N}] ← 一个字都没动"; echo "  \$(seq 1 \$N) 展开成：[$(seq 1 $N)] ← 这条才是对的写法"
  {1..$N} 展开成：[{1..3}] ← 一个字都没动
  $(seq 1 $N) 展开成：[1
2
3] ← 这条才是对的写法
[退出码 0]
```

这一格最关键的是方括号里的东西：`$N` 被换成了 `3`（变量替换照常发生），
但整串 `{1..3}` 仍然是**一个字符串**，没有变成 `1 2 3` 三个词。原因就在顺序里：
bash 的展开次序是固定的 —— **花括号展开 → 波浪号 `~` → 变量替换 / 命令替换 / 算术展开（从左到右）→ 词分割 → 通配展开**。
轮到花括号展开那一步时，这个词还是 `{1..$N}`，`$N` 不是数字，花括号展开直接放弃；等变量替换把 `3` 填进去，
那一步已经过去了。于是 `for i in {1..$N}` 只跑一轮，`i` 拿到的是字符串 `{1..3}`。
一句话：**排在变量替换之前的那几步，永远看不到变量的值。**
（这格用 `echo` 把词放在双引号里，而引号本身就挡住花括号展开 —— 它演示的是同一个终点：得到字符串，得不到序列；
demo 那句「一个字都没动」指的也是**序列没生成**，那两个点始终还是字面文本。）
想按变量生成序列只有两条路：`$(seq 1 "$N")`（第 2 节：那是个外部进程，但只起一次），
或者干脆用 `for ((i = 1; i <= N; i++))`（本节开头那格，零进程）。

右边那格顺带留下一个细节：`$(seq 1 $N)` 塞进 `[ ]` 里，打出来是跨了三行的
`1`、`2`、`3`。命令替换把内部的换行**原样保留**了，是后面词分割那一步（默认 IFS 里含换行）才把它们切成三个词 ——
这正是第 7 节要单独算账的地方。

非数字在算术上下文里也不会报错，这是第三种坑：

```
$ for ((i = 0; i < abc; i++)); do echo "  不该出现"; done; echo "  非数字在算术上下文里当变量名查，查不到就是 0 → 条件 0<0 假 → 一轮都没跑，退出码=$?"
  非数字在算术上下文里当变量名查，查不到就是 0 → 条件 0<0 假 → 一轮都没跑，退出码=0
[退出码 0]

$ for ((i = 0; i < 1.5; i++)); do echo "  第 $i 轮"; done; echo "  退出码=$? ← ★ for (( )) 不接受小数，直接语法错误"
bash: line 1: ((: i < 1.5: arithmetic syntax error: invalid arithmetic operator (error token is ".5")
  退出码=1 ← ★ for (( )) 不接受小数，直接语法错误
[退出码 0]
```

第一格：`i < abc` 里的 `abc` 不是数字，bash 把它**当变量名去查**，`abc` 没定义 → 按 0 算 → 条件 `0 < 0` 假 → 一轮都没跑，
而 `$?` 还是 `0`。所以「循环莫名不跑」不一定是名单空，可能是你把一个字符串塞进了算术位置。
第二格：`i < 1.5` 就不给面子了 —— `arithmetic syntax error: invalid arithmetic operator (error token is ".5")`，
`for (( ))` 只认整数，小数是**语法错误**。
注意这一格末行又是 `[退出码 0]`：语法错误杀掉了这个循环（`$?` = 1，被那行 `echo` 打出来了），
但它是「一条命令失败」，不是「shell 退出」，后面那句 `echo` 照样跑，所以整串命令的最终状态还是 0。
想数小数只能换结构：整数计数再除（`for ((i = 0; i < 15; i++))` 然后用 `i/10`），或者交给 `awk`。

最后是无限循环。`for ((i = 1;; i++))` 是合法写法，中段缺省就等于恒真：

```
# 无限循环本身不是 bug，`for ((i=1;;i++))` 是合法的。真正的问题是它怎么停：

$ for ((i = 1;; i++)); do echo "$i"; done | head -3; echo "  ← head 读完 3 行就关门，循环收到 SIGPIPE 死掉（第 04 章第 17 节那条）"
1
2
3
  ← head 读完 3 行就关门，循环收到 SIGPIPE 死掉（第 04 章第 17 节那条）
[退出码 0]
```

这一格里循环真的在无限跑，被 `| head -3` 掐掉了：`head` 读满 3 行就退出并关掉读端，
循环那一段还在往已经关闭的管道里写，内核给它发 SIGPIPE，默认动作就是终止 —— 于是屏幕上是整齐的 `1 2 3`。
两个要点：

- 循环是管道的左段，所以它跑在**另一个进程**里（第 14 节会把这条放大成「计数带不出来」）。
- 主 shell 活着，所以后面那句 `← head 读完 3 行就关门…` 照样打印，`[退出码 0]`。
  想看被 SIGPIPE 杀掉那一段的退出码得读 `PIPESTATUS`（第 04 章第 5、17 节：`141 = 128 + 13`）。

真正的教训不是「别写无限循环」，而是：**写无限循环的同时必须写清它靠什么停** ——
`head`、`break`、超时、或者外面那个 `kill`。三者都没有，它就是 bug。

**这一节带走：**

- `for (( ))` 三段都是算术上下文：不用 `$(( ))`、变量直接写名字、不生成名单所以内存平。
- 花括号展开排在变量替换**前面**，所以 `{1..$N}` 永远是字面量；要按变量生成序列用 `seq` 或 `for (( ))`。
- 非整数在算术位置上当变量名查，查不到就是 0 → 条件假 → 0 轮且退出码 0（静默不跑）。
- 小数是语法错误 `arithmetic syntax error`，只杀掉那个循环，不杀掉整个 shell。
- 无限循环靠管道下游（`head`）收 SIGPIPE 停：那一段是子进程，主 shell 的 `[退出码]` 照旧是 0。

## 7. 不加引号的展开会把词表切成几份

第 4 节说「词表在进循环之前摊平」，这一节回答摊平时**先按什么切**。
答案：不带引号的展开会按 `IFS` 做词分割，切完之后还会**再做一次通配展开**。名单里有空格就会在这里出事。

```
$ v="a b  c"; echo "带引号："; for x in "$v"; do echo "  [$x]"; done; echo "不带引号："; for x in $v; do echo "  [$x]"; done
带引号：
  [a b  c]
不带引号：
  [a]
  [b]
  [c]
[退出码 0]
```

同一个 `"$v"`，带引号是 1 个词，不带引号是 3 个词。
注意是 3 个而不是 4 个：默认 `IFS` 里的**空白字符**（空格、制表、换行）作为分隔符时，
连续的空白算**一个**分隔符，多余的空格不会产生空词。所以 `a b  c` 切成 `a`、`b`、`c`。
这也意味着「靠空格数量对齐」在 bash 里根本不存在。

数组更疼，因为它的元素本来就是为了装空格才存在的：

```
$ arr=("a b" c d); echo "数组 \${arr[@]} 带引号："; for x in "${arr[@]}"; do echo "  [$x]"; done; echo "不带引号（★ 空格被二次切开，元素数从 3 变 4）："; for x in ${arr[@]}; do echo "  [$x]"; done
数组 ${arr[@]} 带引号：
  [a b]
  [c]
  [d]
不带引号（★ 空格被二次切开，元素数从 3 变 4）：
  [a]
  [b]
  [c]
  [d]
[退出码 0]
```

`arr=("a b" c d)` 是 3 个元素，第一个元素自己带空格。

- `"${arr[@]}"`：bash 对这个写法有特殊照顾 —— **每个元素各成一个词**，引号保住元素内部的空格，出来还是 3 个词。
- `${arr[@]}`：不带引号时，元素先取出来、再走一遍词分割，`a b` 被劈成 `a` 和 `b` → 4 个词。
  元素数量从 3 变 4，而且**没有任何警告**。

这就是「名单里有空格就炸」的标准现场：文件名、用户输入、`find` 的结果全都可能带空格。
唯一写法是 `"${arr[@]}"`。对照一下另外两种：`"${arr[*]}"` 是把所有元素用 IFS 的第一个字符（默认就是空格）
拼成**一个**词，适合打印，不适合遍历；`${#arr[@]}` 数的是元素个数（上面那格就是 3），
它不受引号影响 —— 所以「元素 3 个、词 4 个」这件事只能靠遍历本身暴露。

`IFS` 一改，切法立刻跟着变：

```
$ IFS=":"; v="a b:c"; for x in $v; do echo "  [$x]"; done; unset IFS
  [a b]
  [c]
[退出码 0]
# ★ 循环头里的展开和命令行上任何位置的展开是同一条规矩（第 02 章）：
#   不带引号的 $var / ${arr[@]} 会按 IFS 拆词，还会再做一次通配展开。
#   名单里可能有空格（真实文件名、用户输入）时，唯一的写法是 "${arr[@]}"。
```

这格把 `IFS` 设成单个冒号，于是 `a b:c` 切成 `a b` 和 `c` 两个词 —— 空格**不再是分隔符**了，
因为现在的 `IFS` 里只有冒号。这也说明上一节 `$(seq 1 $N)` 里的换行为什么会被切开：默认 `IFS` 含换行。
末尾 `unset IFS` 是把 `IFS` 恢复成 bash 的默认值（空格 + 制表 + 换行），不是把它变成空字符串。

最后一条是这一节和第 5 节的接口：不带引号的展开在切完词之后**还会做一次通配展开**。
所以如果你的名单里可能含有 `*`、`?`、`[abc]` 这样的内容（用户输入的文件名、从文件里读出来的一行），
`for x in $list` 会拿它们去匹配磁盘，名单被**悄悄换成了别的文件**。第 5 节那个「图案原样进循环」的坑，
在这里会以「名单被替换」的形式重演一次。带引号就两件事都不发生。

**这一节带走：**

- 不带引号 = 先按 IFS 词分割、再做一次通配展开；带引号 = 原样一个词。循环头里的展开没有例外。
- 默认 IFS 下连续空白算一个分隔符，所以 `a b  c` 出 3 个词，不是 4 个。
- `"${arr[@]}"` 保住每个元素（3 个词），`${arr[@]}` 会被二次切开（4 个词）且无警告 —— 遍历数组只写前者。
- `IFS` 换成分隔符集合：`IFS=":"` 时空格不再算分隔符；`unset IFS` 恢复默认值而不是空。
- 名单可能带空格或通配字符时，除了加引号，还要记得第 5 节：`nullglob` 或 `[ -e ]` 兜住通配那一半。

## 8. while / until 是镜像：先看形状，再看第 19 节的重试环

`for` 数的是「一串已经摊好的词」，而 bash 里另外两类活——「读到没读头」和「等一件事发生」——都归 `while` 和 `until`。
先把一件事立住：它们不是两种循环，是同一条判断的一正一反。

```
$ n=0; while [ "$n" -lt 3 ]; do n=$((n + 1)); done; echo "while [ n -lt 3 ] → n=$n"
while [ n -lt 3 ] → n=3
[退出码 0]

$ n=0; until [ "$n" -ge 3 ]; do n=$((n + 1)); done; echo "until [ n -ge 3 ] → n=$n ← 条件正好反过来，轮数一样"
until [ n -ge 3 ] → n=3 ← 条件正好反过来，轮数一样
[退出码 0]
```

条件取反、轮数一样，这就是「镜像」的全部内容。决定进不进循环体的，永远是条件命令那一次的**退出码**：
`while` 是「退 0 才进」，`until` 是「退 0 就停」。别把 `[ ]` 当成循环的一部分——它只是个恰好返回 0/1 的普通命令，
所以下一节那个「退出码另有含义」的 `read` 直接塞进条件里，坑就是这么埋下的。

真正容易想当然的是「一次都不跑」那一档，两个方向的空循环长得一模一样，而且都不报错：

```
# 最容易想当然的是「一次都不跑」那一档：

$ n=9; while [ "$n" -lt 3 ]; do echo 不该出现; done; echo "while 一进来就假 → 0 轮，退出码=$?"
while 一进来就假 → 0 轮，退出码=0
[退出码 0]

$ n=9; until [ "$n" -ge 3 ]; do echo 不该出现; done; echo "until 一进来就真 → 0 轮，退出码=$?"
until 一进来就真 → 0 轮，退出码=0
[退出码 0]
```

↑ 注意那两行末尾的「退出码=0」：**循环一轮没跑，在 bash 里不算失败**。这和第 3 节末尾那条空 `for` 是同一条规矩。
脚本如果靠「循环有没有干活」来判断成败，这一档会直接把错误咽下去——第 19 节的重试环就必须自己带上「等到了吗」的判据。

再加一格把两个方向钉死：

```
$ while false; do echo 不该出现; done; echo "while false → 0 轮，退出码=$? ｜ 反过来说 until false 就是无限循环，见第 6 节最后一条"
while false → 0 轮，退出码=0 ｜ 反过来说 until false 就是无限循环，见第 6 节最后一条
[退出码 0]
# ★ 停止条件写反一次，后果是「一次都不干」或「永远干不完」。第 19 节把这两档都演成现场，
#   并且给「必须停下来」的那一支补上界。
```

`while false` 是 0 轮，`until false` 就是永不停——所以本章凡是「必须自己停下来」的循环，第 19 节都给它补了一个上界。

**这一节带走：**

- `until C` 与 `while ! C` 是一件事：选哪个只看你想让条件读起来是「等到什么就算了」还是「什么才继续」。
- 循环进不进体，只看条件命令那一次的退出码；`[ ]`、`grep -q`、`read` 都只是恰好会返回码的普通命令。
- 「一进来就假」和「一进来就真」都是 **0 轮 + 退出码 0**，不报错；想区分「跑完了」和「压根没跑」，得自己数轮数。
- 停止条件写反一次的后果只有两种：一次都不干，或者永远干不完。第 19 节把这两档都演成现场。

## 9. read 的最小语义：它的退出码问的不是「读到字了吗」

`read` 是 bash 里少数「给你的东西」和「告诉你的码」不是一回事的命令。先把最小用法摆出来，包括那个很多人不知道存在的保留变量：

```
$ printf "hello\n" | { read x; echo "read x → x=[$x] ｜ 退出码=$? ← 内容给了点名的变量"; }
read x → x=[hello] ｜ 退出码=0 ← 内容给了点名的变量
[退出码 0]

$ printf "hello\n" | { read; echo "裸 read → REPLY=[$REPLY] ｜ 退出码=$? ← 没点变量名时整行进 REPLY 这个 bash 保留变量（第 16 节 select 也用它）"; }
裸 read → REPLY=[hello] ｜ 退出码=0 ← 没点变量名时整行进 REPLY 这个 bash 保留变量（第 16 节 select 也用它）
[退出码 0]
```

两种写法的分工在这里：点名了变量就填那个变量，一个都没点则整行进 `REPLY`——`REPLY` 是 bash 留给 `read` 的保留名字，
所以第 16 节的 `select` 也拿它装你敲进去的原始字符。

然后是这一节真正要盯住的一屏——同一段内容，`read` 给两种码：

```
$ printf "没有结尾换行" | { read x; rc=$?; echo "read 退出码=$rc ← ★ 撞 EOF 没读到换行，算失败"; echo "但 x=[$x] ← 内容已经拿到了"; }
read 退出码=1 ← ★ 撞 EOF 没读到换行，算失败
但 x=[没有结尾换行] ← 内容已经拿到了
[退出码 0]
```

↑ **变量里明明白白装着内容，退出码却是 1**。因为 `read` 的返回值回答的是另一个问题：
「这次有没有撞到分隔符（默认换行，或 `-d` 指定的那个）」，而不是「有没有拿到字符」。
撞到 EOF 就是没撞到，于是判失败——**可它照样把已经读到的东西赋给了你**。

两个边界把「成功」和「失败」的界线补全：

```
$ printf "\n" | { read x; echo "空行：read 退出码=$? ｜ x=[$x]"; }
空行：read 退出码=0 ｜ x=[]
[退出码 0]

$ read x < /dev/null; echo "立刻 EOF：退出码=$?（不是超时，超时是第 11 节那个 142）"
立刻 EOF：退出码=1（不是超时，超时是第 11 节那个 142）
[退出码 0]
# 这一节立的规矩，第 12 节（最后一行被吞）和第 13 节（循环体偷吃 stdin）都是从它长出来的：
#   read 的退出码 = 「有没有撞到分隔符」，不是「有没有拿到字符」。
```

空行是「撞到了换行」，所以退 0、变量为空；`/dev/null` 是「一上来就到结尾」，所以退 1。
而真正的**超时**不是 1，是另一个数（`142`），第 11 节单独演——把两者混为一谈，重试环就会提前放弃。

这一节立的规矩后面立刻要用两次：第 12 节「最后一行被吞」是它的直接后果，第 13 节「循环只跑一轮」也是从它长出来的。

**这一节带走：**

- `read` 退出码 = 「撞没撞到分隔符」，与「有没有拿到内容」无关；内容和返回值要分开看。
- 不点变量名时整行进 `REPLY`；点了变量名时内容只进你点的那一个。第 12 节问「手里还有货吗」，问的就是你实际用的那个。
- 空行退 0、EOF 退 1、超时退 142：三种「没读到东西」是三件不同的事。
- 把 `read` 放进 `while` 的条件里，就等于让「有没有换行」来决定循环跑不跑——第 12 节整节讲这一件事。

## 10. 一行拆成多个字段：末变量拿剩余，IFS 说了算

把一行按分隔符切成几个字段是 `read` 最常见的用法，坑一次摆出来：

```
$ printf "a b c d\n" | { read p q r; echo "read p q r → p=[$p] q=[$q] r=[$r] ← ★ 最后一个变量拿走剩下的全部"; }
read p q r → p=[a] q=[b] r=[c d] ← ★ 最后一个变量拿走剩下的全部
[退出码 0]

$ printf "x,,y,z\n" | { IFS=, read a b c d; echo "IFS=, 切 x,,y,z → a=[$a] b=[$b] c=[$c] d=[$d] ← 连续逗号不折叠，中间那个空是真的空"; }
IFS=, 切 x,,y,z → a=[x] b=[] c=[y] d=[z] ← 连续逗号不折叠，中间那个空是真的空
[退出码 0]
```

两格的机制不一样，但都归第 02 章那套 IFS 规矩：

1. **变量比字段少**：最后一个变量拿走剩下的全部（`[c d]`，中间那个空格原样留着）。
2. **`IFS=,` 这种非空白分隔符**：逐字符切，连续的逗号**不折叠**，所以 `x,,y,z` 中间那个字段是真的空。

这第 2 条和默认的「空白分隔符」待遇正好相反：空格、tab、换行属于空白类，连续的会折叠成一刀，
首尾的还会被直接剥掉；`,`、`:`、`@` 这类非空白字符一人一票，谁也不折叠谁。

想要「整行原样」，只有一条写法：

```
$ printf "  前后空白都要  \n" | { IFS= read -r line; echo "IFS= read -r → [$line] ← 不拆词、不处理反斜杠，整行原样"; }
IFS= read -r → [  前后空白都要  ] ← 不拆词、不处理反斜杠，整行原样
[退出码 0]
```

`IFS=` 把分隔符集换成空（于是一个词都不拆，首尾空白也不再被剥），`-r` 让反斜杠不再被当转义（第 11 节有现场），
两个都得写。这种写在 `read` 前面的赋值只对这一条命令生效，不会把你后面的 `IFS` 改掉。

最后确认一件事：默认的 `IFS` 连制表符也算空白。

```
$ printf "one\\ttab\ttwo\n" | { read a b c; echo "默认 IFS 也吃制表符：a=[$a] b=[$b] c=[$c]"; }
默认 IFS 也吃制表符：a=[one] b=[tab] c=[two]
[退出码 0]
# ★ 两条常错：① 想「整行原样」必须 IFS= read -r，只写 read 会把首尾空白和连续空白吃掉；
#   ② read 的字段数是写死的，源里的列数变了不会报错，只会让最后一个变量默默变长。
```

**这一节带走：**

- 最后一个变量拿剩余全部；想让每列各归各的，变量数得自己对齐列数。
- `IFS=,` 之类的单字符分隔符**不折叠**连续分隔符，空字段是数据；只有空白类分隔符才折叠、才剥首尾。
- 「整行原样」的唯一写法是 `IFS= read -r`，少写哪个字符都会改形状。
- `read` 的字段数是写死的：源里列数变了不会报错，只会让最后一个变量默默变长——拿它解析 CSV 之类要先数清列。

## 11. read 的开关柜：-t 的超时码、-p 在非终端为什么不显示

`read` 的选项不多，但每一个都在改「什么时候算读到」。先看两个最容易误判的：超时和提示。

```
$ sleep 2 | { read -t 0.3 x; echo "read -t 0.3 但没人喂 → 退出码=$? ← ★ 超时是 128+14=142，和 EOF 的 1 是两回事"; }
read -t 0.3 但没人喂 → 退出码=142 ← ★ 超时是 128+14=142，和 EOF 的 1 是两回事
[退出码 0]

$ read -p "这个提示你看得见吗？" x < /dev/null; echo "read -p 在非终端 stdin 下：退出码=$? ｜ 屏幕上一行提示都没有 ← 提示只在 stdin 是终端时才印"
read -p 在非终端 stdin 下：退出码=1 ｜ 屏幕上一行提示都没有 ← 提示只在 stdin 是终端时才印
[退出码 0]
```

`-t` 到点没等到输入，`read` 带着 **142** 回来——这是第 04 章那套信号记账：128 + 14（SIGALRM，`read -t` 内部上的那个闹钟）。
所以「超时」不是「读到结尾」：一个是「还没好，等等可能就有」，一个是「没有了」。
把两者都当失败的重试环会提前收工，第 19 节就是按这两个码分派的。
`-p` 那一条更值得记住：**提示只在 stdin 是终端时才印**。CI、cron、管道里跑带 `-p` 的脚本，屏幕上一个字都不会有——
你以为「没打印提示 = 没走到这段代码」，其实是它压根不打算打。

`-n` 和 `-d` 换的是「读到什么算停」：

```
$ printf "abcdef\n" | { read -n 3 x; echo "read -n 3 → x=[$x] ｜ 剩下的 [def] 还挂在输入里，下一个 read 拿走它"; }
read -n 3 → x=[abc] ｜ 剩下的 [def] 还挂在输入里，下一个 read 拿走它
[退出码 0]
```

`-n 3` 把停的条件从「撞到换行」换成「读满 3 个字符」，于是 `abc` 到手、`def` **还挂在那份输入里**，
下一个 `read` 拿走它。也就是说：改了停的条件，就改了「剩下多少留给别人」——这句话在第 13 节会以最坏的样子出现。

```
$ printf "a\\0b\\n" | { read -d "" x; echo "  第一句：退出码=$? ｜ x=[$x] ← -d 空串 = 拿 NUL 当分隔符，只吃到那个 NUL 就停"; read -d "" y; echo "  第二句：退出码=$? ｜ y=[$y] ← NUL 之后的 b 还挂在输入里；这句撞到 EOF（没等到分隔符）所以退 1"; }
  第一句：退出码=0 ｜ x=[a] ← -d 空串 = 拿 NUL 当分隔符，只吃到那个 NUL 就停
  第二句：退出码=1 ｜ y=[b] ← NUL 之后的 b 还挂在输入里；这句撞到 EOF（没等到分隔符）所以退 1
[退出码 0]
```

`-d ""` 是「拿 NUL 当分隔符」的专用写法（空串被 bash 特殊照顾成 NUL），配套的正是 `find -print0`——
名字里带空格、带换行都不会散架。第二句又是第 9 节那条规矩的翻版：`y` 里明明白白装着内容，退出码却是 1，
因为它这次撞到的是 EOF 而不是 NUL。

最后一对是本章所有读行写法都带 `-r` 的原因：

```
$ printf "路径： a\\\\b\\n" | { read x; echo "普通 read 把 \\\\ 当转义吃掉 → x=[$x]"; }
普通 read 把 \\ 当转义吃掉 → x=[路径： ab]
[退出码 0]

$ printf "路径： a\\\\b\\n" | { read -r y; echo "read -r 原样保留 → y=[$y]"; }
read -r 原样保留 → y=[路径： a\b]
[退出码 0]
# ★ -t 的 142 和 EOF 的 1 必须分开处理：等不到输入是「还没好」，读到结尾是「没有了」，
#   把两者都当失败的重试环会提前放弃。第 19 节的重试写法就靠这条分类。
```

默认那个 `read` 会把反斜杠当**转义符**消费掉：吃掉一个 `\`，只留下它后面那个字符（`\` 加换行甚至被当成续行）。
于是同一份输入，两格的变量值差着一个字节——而少掉的那个字节不会报错，
只会让你后面那条 `rm` / `cp` 动到一个根本不存在（更糟：恰好存在）的名字。
文件名、用户输入、任何你不知道里面有没有反斜杠的东西，都必须 `-r`。

**这一节带走：**

- `read -t` 超时给 **142**（128+SIGALRM），EOF 给 **1**：两种失败要分开处理，重试环靠这条分类。
- `read -p` 的提示在 stdin 不是终端时**一个字都不印**；别拿「有没有提示」判断代码执行到哪。
- `-n` 按字数停、`-d` 按指定字符停、默认按换行停；停在哪个位置，决定剩下的内容留给谁。
- `-d ""` = NUL 分隔，专配 `find -print0`；它的数组版就是第 15 节的 `mapfile -d`。
- 读行统一写 `IFS= read -r`：少一个 `-r`，反斜杠就被吃掉，你的路径悄悄变了形状。

## 12. 最后一行没有换行符就被吞掉：readlast.sh

这是本章命中率最高的一个 bug，而且它**不报错**。先把两份文件的形状钉死——它们只差 1 个字节：

```
$ bash readlast.sh
=== 1. 先把两份文件的形状钉死：只差 1 个字节 ===
  last/with_nl.txt     字节数=20  wc -l 行数=3  最后一字节=\n
  last/no_nl.txt       字节数=19  wc -l 行数=2  最后一字节=y
  → 注意 wc -l 说 no_nl.txt 只有 2 行：wc -l 数的是**换行符的个数**，不是「有几段文本」。
    可这两份文件的**内容**都是三种水果。后面所有「数一数跑了几轮」的地方，都以这个差值为源头。
```

↑ `wc -l` 的账和内容的账不是一回事：它只数换行符，所以那个没有换行收尾的 `cherry` 在它的账上压根不存在。
先接受这个「看不见末行」的口径——下一格的 `while read` 用的正是同一个口径，那才是它变成 bug 的地方。

事故现场：同一个 `while read`，两份文件少跑一轮。

```
=== 2. 事故现场：同一个 while read，两份文件少跑一轮 ===
    第 1 轮读到：apple
    第 2 轮读到：banana
    第 3 轮读到：cherry
  last/with_nl.txt     循环跑了 3 轮
    第 1 轮读到：apple
    第 2 轮读到：banana
  last/no_nl.txt       循环跑了 2 轮
  → 第二份文件里那个 cherry **一个字都没被读到**，而且循环正常结束、退出码 0。
    这就是它危险的地方：不报错，只是安静地少干一件活。
```

↑ 第 9 节那条规矩在这里咬人：读 `cherry` 的那一次**内容确实拿到了**，可它撞到的是 EOF 不是换行，于是退 1，
`while` 连门都不进。屏幕上少了一行，退出码却还是 0——少干活这件事一点痕迹都没留。

为什么？把同一次读取的「变量里有什么」和「返回值是什么」并排看：

```
=== 3. 为什么：read 的返回值问的是「读到分隔符了吗」，不是「读到字了吗」 ===
  输入没有换行：read 退出码=1 ｜ 变量 v=[cherry]
  输入有换行：  read 退出码=0 ｜ 变量 v=[cherry]
  → ★ 关键就在这两行：**赋值成功了，返回值仍是 1**。
    while 只看返回值决定「进不进循环体」，所以那次成功的赋值被条件判断丢掉了。
    记住这句：read 的退出码 = 「这次有没有撞上换行（或 -d 指定的分隔符）」，与「有没有拿到内容」无关。
```

两行的差别只在有没有那个换行，变量里的内容一模一样。而 `while` 只读返回值、不读变量——
**它拿一个「撞没撞到分隔符」的答案，去决定一次成功的赋值到底要不要用**。

推荐的修法只有一行，条件里补一句「手里还有货就再进一次」：

```
=== 4. 修法一（推荐，一行）：条件里补一句「手里还有货就再进一次」 ===
    第 1 轮读到：apple
    第 2 轮读到：banana
    第 3 轮读到：cherry
  → 现在 no_nl.txt 也是 3 轮。为什么用 [ -n "$fruit" ] 就够：EOF 且手里空 → 条件假，退出。
    ★ 别写成 while read -r fruit; do ... 之后再在循环外补一次 —— 有换行的文件会被多处理一遍。
    拿两份文件各跑一次对账（这才是这条修法合格的判据）：
      last/with_nl.txt     跑了 3 轮（两份现在都是 3 → 是）
      last/no_nl.txt       跑了 3 轮（两份现在都是 3 → 是）
```

↑ 补进去的那一半问的是**变量**而不是返回值，于是「有内容」这条路也进得来；只有 EOF 且手里空才让条件假、循环退出。
这条修法的合格判据不是「跑起来了」，是屏幕上那两行对账：**两份文件都得是 3 轮**。
至于捕获点出来的那个反写法——把补的那一次写在循环外面——有换行的文件会把最后一行**多处理一遍**：
少一轮不对，少一轮之后再补一轮也不对。

不想动循环条件的话还有两条路：

```
=== 5. 修法二/三：不改循环条件的那两条路 ===
  修法二：把「补一个换行」交给数据管道，循环体一个字不动
      用 <(cat 文件; echo) 喂进去 → 3 轮（代价：多起一个进程，且路径要能 cat）
  修法三：一次读进数组，压根不用 read 做循环条件
      mapfile -t 读到 3 个元素：apple banana cherry（末行不需要换行也能拿到）
      ★ 但 mapfile 是把**整份文件留在内存里**，大文件要回头用第 2 节的流式写法。
```

两条都不碰循环条件：修法二把「补一个换行」推给数据管道（代价：多起一个进程，而且路径得能 `cat`）；
修法三干脆不逐行读，一次读进数组——`mapfile` 判成功不看换行，所以末行有没有都拿得到，
它的代价在另一头（整份文件进内存，第 15 节专门量）。

顺手把 `wc -l` 的账结掉，看看谁会被这个坑骗、谁不会：

```
=== 6. 顺手把 wc -l 的账也结掉：谁会被这个坑骗 ===
  awk / sed / cut / grep 是按「记录」切行的，末行没有换行照样算一行：
    awk 数到的行数 = 3 ｜ grep -c "" 数到的行数 = 3
  → 只有 while read 这一族（bash 的 read、以及任何「以换行判成功」的读法）会漏。
    所以「脚本里数出来的行数」和「awk 数出来的行数」不等时，先怀疑末行换行，再怀疑逻辑。
```

↑ 差别的根在「一行」的定义：那些工具按记录切，读到字符就算一条；bash 的 `read` 按换行判成功。
所以两边数出来的不等时，**先怀疑末行有没有换行，再怀疑你的循环逻辑**——顺序反了就会去改一段本来没错的代码。

收口三条：

```
=== 7. 收口：三条能带走的话 ===
  ① 见到 while read 就条件反射地问一句：最后一行有换行吗？修法只有 || [ -n "$REPLY" ] 这一条最省。
  ② read 的退出码语义是「撞到分隔符没有」，不是「读到东西没有」—— 这一条也解释了
     read -t 超时（>128）和 read 到 EOF（1）为什么都算失败，见第 11 节。
  ③ 判断「两份文件一样吗」别用 wc -l：它数的是换行符。要比内容就用 cmp / wc -c。
[退出码 0]
↑ 两份文件只差 1 个字节（最后一个换行符），坏写法就少跑一轮 —— 这是本章命中率最高的一个 bug。
  修法只有一条值得背：while read -r x || [ -n "$x" ]。其余两条（补换行、mapfile）在第 15 节。
```

**这一节带走：**

- 见到 `while read` 就条件反射地问一句：最后一行有换行吗？
- 唯一值得背的修法：`while read -r x || [ -n "$x" ]`（补在条件里，别补在循环外）。
- 判断「两份文件一样吗」别用 `wc -l`：它数换行符。比内容用 `cmp`，比大小用 `wc -c`。
- 这个 bug 全程退出码 0、不报错——凡是「应该处理 N 件」的循环，就把 N 打在屏幕上数。

## 13. 循环体偷吃 stdin：readsteal.sh

`while read host; do ssh "$host" uptime; done < hosts.txt`——4 台机器只连了 1 台，剩下 3 台无声消失。
本机用裸 `cat` 复现同一条事故（真实肇事者最常见的是 `ssh`）：

```
$ bash readsteal.sh
=== 1. 现场：4 行名单，体里有一句会读 stdin 的命令（这里用裸 cat 模拟 ssh） ===
  名单内容：node-1 node-2 node-3 node-4 
  裸 cat 不带参数 = 从 stdin 读。它和 while read 用的是同一个 fd，这就是事故的全部原因。
```

↑ 事故的全部原因就是那句「同一个 fd」：`cat` 不带参数就是从标准输入一路读到底，
而你的名单也正是从标准输入进来的——两条读同一条流，谁先动手谁全拿走。

```
=== 2. 事故：循环只跑 1 轮，剩下 3 行被 cat 端走 ===
  第 1 轮：host=[node-1]，现在跑一句裸 cat（它会从 stdin 读）
node-2
node-3
node-4
  → 循环跑了 1 轮（名单有 4 行），退出码 0 —— 不报错、不警告。
  → 上面那 3 行 node-2/node-3/node-4 是被 cat 打印出来的：它们**作为输入**被吃掉了，
    所以 read 下次去拿的时候已经到 EOF，循环自然结束。
```

`node-2` 往后那三行不是被 `cat`「跳过」的，是被它**读走了**（所以才原样打印出来）：等 `read` 下一轮再去拿，
手上已经是 EOF，条件直接假、循环结束。**跑 1 轮、退出码 0，不报错也不警告**——和第 12 节同一款病形。

调试这类问题不要靠看输出长度，把它变成能数的东西：

```
=== 3. 判据：把「谁读了 stdin」变成能数的东西 ===
  名单总行数 = 4
  坏写法跑到的轮数 = 1   ← 少了 3 轮，这就是这条 bug 的「可数」形态
  → 以后调试这类问题就问一句：**轮数对不对**？对不上就是有人吃了 stdin。
```

↑ 为什么非把这两个行数出来不可：屏幕上「少打了 3 行」是看不出门道的（也许名单本来就这么短），
而「名单 4 行 / 循环 1 轮」这个不等式一眼就扎眼。**能数的判据才是判据**。

三条修法，按侵入性从小到大。第一条：

```
=== 4. 修法一：给循环体喂 /dev/null（改动最小，最常用） ===
  轮数 = 4 ｜ cat 这次读到 0 字节，名单保住了
  → ssh 有专门的开关（-n 就是把 stdin 接 /dev/null），比事后补 < /dev/null 更显眼。
```

喂 `/dev/null` 改动最小：那个命令照样跑，只是读不到你的名单。捕获里还点出 `ssh` 有专门的开关 `-n`
（就是把它的 stdin 接到 `/dev/null`），写在命令行上比事后补一句 `< /dev/null` 更显眼，不容易被下一个改脚本的人删掉。

第二条：

```
=== 5. 修法二：名单挂到 fd 3，read 从 3 读，stdin 留给循环体 ===
  第 1 轮：host=[node-1] ｜ 体内的 cat 从 stdin 拿到 [这份文件是正文，跟名单无关。]
  第 2 轮：host=[node-2] ｜ 体内的 cat 从 stdin 拿到 []
  第 3 轮：host=[node-3] ｜ 体内的 cat 从 stdin 拿到 []
  第 4 轮：host=[node-4] ｜ 体内的 cat 从 stdin 拿到 []
  轮数 = 4 ｜ 这就是第 04 章第 23 节 exec 3< / read -u 3 那一招的循环版
  → 什么时候必须用它：你**真的**要在循环体里读别的 stdin（比如喂密码给 gpg）。
    否则修法一更简单：一个 fd 干一件事，别让人共读。
```

这一招是把「共读」拆成两条道：名单走 fd 3（`read -u 3`），stdin 整个留给循环体。
屏幕上那四行就是证据——第 1 轮 `cat` 读到的是正文，后面三轮读到的是空，而 `host` 一路拿到 `node-4`、
**名单一个字都没少**。什么时候值得多写这两行：你真的要在循环体里读 stdin（喂密码给 `gpg` 之类）；
否则用第一条，一个 fd 干一件事，别让人共读。

第三条：

```
=== 6. 修法三：先把名单读进数组，循环就再也不碰 stdin 了 ===
  轮数 = 4 ｜ mapfile 一次读完，for 走数组 —— 顺便把第 12 节末行漏读的问题也一起解决了
  → 注意这里 for 的词表是**展开好的数组**（第 4 节讲的快照），所以体里改 stdin、改磁盘都不影响轮数。
```

这条换掉的是「谁在提供名单」，于是共读从根上没了：`for` 的词表是进循环之前就展开好的数组（第 4 节讲的快照），
之后循环体再怎么吃 stdin、怎么改磁盘，都动不了这一轮的轮数。而 `mapfile` 又不靠换行判成功，
所以第 12 节那个末行漏读也一起没了——一条写法还了两节的债（代价在内存那一头，第 15 节最后一屏量给你看）。

收口：

```
=== 7. 收口：三条能带走的话 ===
  ① 症状识别：while read 的循环**跑不满**、又不报错 → 先怀疑循环体吃了 stdin；
     肇事名单：ssh / scp / mplayer / ffmpeg / gpg / mysql / cat / read（体里再 read 一次也是）。
  ② 三档修法按侵入性排：< /dev/null（最省事）< fd 3 分离（要真读 stdin 时）< mapfile+for（最干净，但吃内存）。
  ③ 判据要能数：轮数、字节数、行数——任何「应该跑 N 次」的循环，都在屏幕上把 N 打出来，
     别靠肉眼看输出长度；这一章后面第 18、21 节的后台作业对账用的是同一招。
[退出码 0]
↑ 4 行名单只跑了 1 轮：循环体里那句会读标准输入的命令（这里用裸 cat 模拟 ssh）把剩下的 3 行端走了。
  三条修法各有适用面：喂 /dev/null 最省事；名单挂 fd 3 最干净；先读进数组则和第 15 节同源。
```

**这一节带走：**

- 症状识别：`while read` 的循环**跑不满**又不报错 → 先怀疑循环体吃了 stdin。
- 常见肇事名单：`ssh` / `scp` / `ffmpeg` / `gpg` / `mysql` / 裸 `cat`，以及循环体里再 `read` 一次。
- 三档修法：`< /dev/null` 最省事；fd 3 分离留给「体里真要塞 stdin」；`mapfile` + `for` 最干净但吃内存。
- 轮数、字节数、行数——凡是「应该跑 N 次」的循环就把 N 打出来；肉眼看输出长度是数不出少了几轮的。

## 14. 管道里的 while 是另一个进程：lastpipe 与三种接回办法

第 04 章那条「管道每一段都是自己的进程」落到循环上，事故比裸赋值更隐蔽——因为这次**循环真的跑了、计数也真的加了**。

```
# 这一节和第 04 章第 3 节是同一件事，但发生在循环里，坑得更隐蔽：计数器在循环体里明明加了。

$ n=0; printf "a\nb\nc\n" | while read l; do n=$((n + 1)); done; echo "循环里加了 3 次，外面看 n=$n ← ★ 最后一段是子进程，它的赋值带不回来"
循环里加了 3 次，外面看 n=0 ← ★ 最后一段是子进程，它的赋值带不回来
[退出码 0]
```

↑ 循环确实跑了 3 轮，`n` 也确实加了 3 次——只是那些加法发生在本 shell 看不见的进程里。
子进程拿的是父进程内存的**复印件**，写复印件改不到原件；外面那个 `n=0` 就是原件原本的值。

三种接回办法。第一种是开关：

```
# ① lastpipe：让**最后一段**回到当前 shell（要求作业控制关着，非交互 bash 默认就是关的）。

$ shopt -s lastpipe; n=0; printf "a\nb\nc\n" | while read l; do n=$((n + 1)); done; echo "shopt -s lastpipe 之后 n=$n"
shopt -s lastpipe 之后 n=3
[退出码 0]
```

`lastpipe` 把**最后一段**搬回当前 shell 跑，所以那个 `n` 就是在本进程里加的。但它有两个前提，
缺一个就是「加了等于没加」：作业控制必须**关着**（非交互 bash 默认关着，你的交互终端里默认开着——
这就是第 04 章那句「只在脚本里有用」的来处），而且**只救最后一段**，中间段里的赋值照样丢。

第二种不靠开关，把要带出来的东西变成**输出**：

```
# ② 把要带出来的东西变成「输出」，用命令替换接住：

$ n=$(printf "a\nb\nc\n" | while read l; do echo x; done | wc -l); echo "用 wc -l 数出来 n=$n"
用 wc -l 数出来 n=3
[退出码 0]
```

第三种干脆不让循环进管道，输入用重定向交给当前 shell 里的循环：

```
# ③ 干脆不走管道：把输入用重定向交给当前 shell 的循环（第 15 节的 mapfile 是它的加强版）。

$ n=0; while read l; do n=$((n + 1)); done < <(printf "a\nb\nc\n"); echo "while ... < <(...) → n=$n ← 循环留在当前进程里，赋值保住了"
while ... < <(...) → n=3 ← 循环留在当前进程里，赋值保住了
[退出码 0]
# ★ 三条里最该背的是最后一条的判断依据：**需要把循环体里的状态带出来，就别让循环进管道**。
#   lastpipe 只救最后一段，且要求 set +m；中间段的赋值照样丢。
```

第二、三种比 `lastpipe` 稳，因为它们不要求任何开关先处于某个位置：命令替换让要带出来的东西走 stdout，
从左边的门进来；`< <(...)` 干脆连管道都没有，循环和本进程是同一个，赋值自然保住。
真正该背的也不是这三种写法，而是捕获末尾那两行给的判断依据——
**需要把循环体里的状态带出来，就别让循环进管道**。

**这一节带走：**

- 循环一进管道就是管道的一段 = 另一个进程；里面的赋值、数组、`cd` 全都带不出来。
- 先问「我需要把循环体里的状态带出来吗」：需要，就别让循环进管道。
- `lastpipe` 只救最后一段，且要求作业控制关着（`set +m`）——它是脚本里的写法，不是终端里的万能药。
- 命令替换接住（走 stdout）和 `while ... < <(...)`（不走管道）都不依赖开关，比 `lastpipe` 稳。
- 第 15 节 `mapfile` 读 `find -print0` 用的就是 `< <(...)` 这一招；同一条规矩在两节里各兑现一次。

## 15. 一次读全：mapfile 的全部开关和它的适用边界

`mapfile`（别名 `readarray`）是「一次读全」：它把整份输入读成一个数组，而且判成功不靠换行——
第 12 节那个坑在它身上不存在，代价则要换到内存那一头（最后一屏量）。先把它的开关逐个看清楚：

```
$ bash mapfill.sh
=== 1. 一次读全：mapfile 拿到什么、和 while read 的分工差别在哪 ===
  数组长度 = 3 ｜ 元素 = [alpha beta gamma] ｜ 第一个 = [alpha] ｜ 最后一个 = [gamma]
  ★ 注意末行：map/plain.txt 末尾**有**换行；有没有都无所谓，mapfile 不靠它判成功（对比第 12 段）。
  不加 -t 时元素带不带行尾？ [alpha
]（-t 的意思就是「把行尾那个分隔符去掉」）
```

↑ 这一格里有两件事：末行那个换行**有没有都无所谓**（第 12 节那个坑在这里压根不存在），
以及不加 `-t` 时行尾分隔符是留在元素里的——`-t` 没有别的作用，它只负责去掉它。
第二件事看起来无害，下一格就变成这一节最难查的那个 bug。

来源有三种，第三种最容易写错：

```
=== 2. 三种来源：< 文件 ｜ <<< 一个串 ｜ < <(命令) —— 第三种最容易写错 ===
  < 文件      → alpha beta gamma（3 个元素）
  <<< 一个串  → x y z（1 个元素 ★ 整个串只有 1 行 → 就是 1 个元素，不会按空格拆）
  < <(命令)   → one two three（3 个元素）
  → 想把命令的输出按空格拆成多个元素，mapfile 帮不了你（它是**按行**的），
    那属于第 02 章的词与 IFS；mapfile 的定位是「一份行数组」。
```

`<<<` 那一格看着反直觉（只有 1 个元素），其实正是它的定位：here string 给的是**一行**，
`mapfile` 就只收一格。它永远按行切，不会替你把空格拆成词——想拆词是第 02 章 `IFS` 那一套，
对号的工具是第 10 节的 `read a b c`。

下一个开关是这一节最容易咬人的：CRLF。

```
=== 3. ★ 不加 -t 时 \r 会留在元素里：CRLF 文件的隐形后果 ===
  带 -t 的第 1 个元素字节数 = 5 ｜ 不带 -t 的 = 6（多的那 1 个字节就是 \r）
  拿它去比字符串 → [win1
] = "win1" 吗：不相等
  → 这就是「脚本在 Windows 生成的 CSV 上莫名对不上」的一种形状：差别看不见，比较却全错。
    注意 -t 去掉的是**行尾分隔符**（\n），它不管 \r；要连 \r 一起去掉只有两条路：
    ① 整份先过一遍 tr -d '\r' 再 mapfile；② 读完之后把行尾那个 CR 当后缀剪掉，本机当场剪了一刀：
    ★ 剪的是 mapfile -t **之后**的那个元素：不带 -t 时元素结尾是 \n（6 字节 = win1+CR+LF），
      那时候剪 CR 会一刀剪空（我上一版就剪错了对象，屏幕上 6 字节剪完还是 6 字节）。
      现场剪一刀：带 -t 的元素=5 字节 ｜ 剪掉行尾 CR 后=4 字节 ｜ 剪完和 "win1" 相等吗 → 是
```

↑ 5 字节对 6 字节，差的那一个肉眼看不见：`win1` 后面还挂着 CR，于是字符串比较当场判不相等——
这就是「同一份脚本换一台机器、换一份 Windows 生成的 CSV 就对不上」的形状。
`-t` 救不了你：它只负责去掉行尾那个**分隔符**（`\n`），CR 不归它管。要连 CR 一起去掉只有两条路：
整份先过一遍 `tr -d '\r'`，或者读完之后把行尾那个 CR 当后缀剪掉。

这里捕获留了一段自白，值得照实讲：剪 CR 这一刀必须剪在 **`mapfile -t` 之后**的那个元素上。
不带 `-t` 时元素结尾是 `\n`（`win1` + CR + LF = 6 字节），那时候去剪 CR 会一刀剪空——
上一版就是剪错了对象，屏幕上量到「6 字节剪完还是 6 字节」。改成剪带 `-t` 的元素（5 字节），
剪完是 4 字节，和 `"win1"` 才相等。所以这一段真正的教训不是「怎么剪」，
而是**剪之前先问清楚：我手里这个元素几个字节、尾巴上是什么**。

数字开关三个：`-s` 跳过、`-n` 限量、`-O` 从数组第几格开始写。

```
=== 4. 三个数字开关：-s 跳过 / -n 限量 / -O 从数组第几格开始写 ===
  全读        → L1 L2 L3 L4 L5（5 个）
  -s 2 跳两行 → L3 L4 L5（3 个）
  -n 2 只取两条 → L1 L2（2 个）
  -O 3 从第 3 格开始写 → 下标 0,1,2 = [][][]，3,4 = [L1][L2]
  → 想要「第 3 到第 5 行」这种切片，bash 里没有 while 计数器优雅的做法，
    要么 -s + -n 组合，要么读全再用 ${arr[@]:2:3} 切（第 02 章的数组切片）。
```

↑ 三个开关各管一件事，别混：`-s` 是「收之前先丢几条」、`-n` 是「最多收几条」、
`-O` 是「从数组的第几格**开始写**」。最后这个最容易被当成「跳过输入行」，它跳的其实是数组下标——
所以屏幕上 0、1、2 三格是空的，数据从第 3 格才落下来。想要「第 3 到第 5 行」，
要么 `-s` + `-n` 组合，要么读全再用 `${arr[@]:2:3}` 切。

`-d` 能把「按行」改成按任意单字符（bash 4.4+）：

```
=== 5. 换分隔符：mapfile -d 能把「按行」改成按任意单字符（bash 4.4+） ===
  按 ; 切 → 3 个元素：[k1=v1 k2=v2 k3=v3] ｜ 末尾那个空段被留着了吗 → 长度=3
  -d "" = 读到 EOF 为止 → 1 个元素（整份文件成了 1 格，含原来的换行）
  → -d 的用处：把「以 NUL 分隔的 find -print0」安全读进数组（第 04 章 xargs 那两节的循环版解法）：
    本机读到 4 个文件名： semi.txt five.txt crlf.txt plain.txt（NUL 分隔，名字里有空格/换行也不会散）
    ★ 这里刻意用 < <(...) 而不是 find ... | mapfile：管道会让 mapfile 跑到子进程里，
      数组读完了也带不回来（第 14 节那条规矩在第 15 节同样生效）。上一版就是写成管道的，
      屏幕上量到 0 个 —— 那 0 不是「没有找到文件」，是「找到的东西留在了别的进程里」。
```

↑ 这一格有两处要停下来。第一处是写法：那 4 个文件名是用 `mapfile ... < <(find -print0)` 读的，
**不是** `find ... | mapfile`——管道会让 `mapfile` 跑到子进程里，数组读完了也带不回来，
这正是第 14 节那条规矩在第 15 节的兑现。捕获里留着上一版的教训：那次写成管道，屏幕上量到 **0 个**文件名。
这个 0 特别容易读错：它**不是「没有找到文件」，是「找到的东西留在了别的进程里」**——
两种解释差着一个 bug 的性质，改法也完全不同。
第二处是 `-d ""` 在这里的读法：分隔符还是 NUL，而那份文件里一个 NUL 都没有，
于是这条记录一路延伸到 EOF，整份文件压成 1 格（原来的换行也留在里面）。

两种失败的原文：

```
=== 6. 两种失败原文：文件不存在 ／ set -u 下的空数组 ===
mapfill.sh: line 92: map/根本没有.txt: No such file or directory
  读不存在的文件：mapfile 退出码=1（重定向在**进 mapfile 之前**就失败了）
  空输入：数组长度=0 ｜ 这个数组存在吗 → 存在
  set -u 下问长度：长度=0 ｜ 退出码=0 ← 问长度不炸
  set -u 下展开它：[] ｜ 退出码=0 ← 5.x 这里也不炸，只给你一个空串
  → ★ 本机（bash 5.3）两条都安静地给空值。老 bash（4.3 及更早）里第二条会报 unbound variable，
    这条差别**本机未验证**（这里没有旧版本可跑），只当作「别在 5.x 上依赖它报错」来记。
```

↑ 第一条的报错行号是 `mapfill.sh: line 92`，可它不是 `mapfile` 失败：文件打不开这件事发生在**进 `mapfile` 之前**，
那个 `1` 是重定向留下的，`mapfile` 压根没被执行。
第二条才是真正要留意的：`set -u` 底下问空数组的长度、展开空数组，本机两条都安静地给空值、都不炸。
所以别把「空数组会报错」当成 bash 的通用行为——这条差别捕获里照实标了**本机未验证**（这里没有旧版本可跑），
真要依赖它，就得挂到你 CI 那个 bash 上验一次。

最后一屏是它的边界和收口：什么时候**别**用 `mapfile`。

```
=== 7. 什么时候别用 mapfile：它是整份进内存（这里只报方向，不报字节数） ===
  同一个文件，两种读法各自「手里同时握着多少」：
    mapfile -t：文件的全部行 → 一个数组（行数=5，**一次性**都在内存里）
    while read ：任意时刻只有一行在变量里（流式，多大都读得动）
  → 判据：行数和单行大小都能预估 → mapfile（干净）；可能是几百 MB 的日志 → 老老实实 while read，
    并且把第 12、13 段的两个修法一起带上。

=== 8. 收口：三句话 ===
  ① mapfile 是「按行」的读取器：-t 去行尾、-s 跳、-n 限量、-O 偏移、-d 换分隔符，readarray 是同一条命令的别名。
  ② 它是第 12/13 两段事故的整片解法：先 mapfile 进数组，再 for 走数组 —— 循环不再碰 stdin，也不再漏末行。
  ③ 代价是内存：它把整份输入握在数组里。大文件回到 while read + || [ -n "$REPLY" ] + < /dev/null 那套。
[退出码 0]
↑ mapfile 把「逐行 read」的三件麻烦（最后一行没换行、循环体偷 stdin、管道里丢状态）一次性消掉，
  代价是整份输入进内存 —— 第 7 小段专门量了这个边界，第 21 节把它和流式读对比。
```

↑ 选谁不看哪段代码短，看**规模**：这两格的形状不一样——一个数组把 5 行**同时**握在手里，
另一个任意时刻只有一行在变量里。行数和单行大小都能预估 → `mapfile`（第 13 节那条修法三的完整版）；
可能是几百 MB 的日志 → 回到流式读，但别只带流式：`mapfile` 顺手消掉的那三件麻烦
（末行没换行、循环体偷 stdin、管道里丢状态）会一件一件回来，所以第 12 段的 `|| [ -n "$REPLY" ]`
和第 13 段的 `< /dev/null` 必须一起带上。

**这一节带走：**

- `mapfile` 是**按行**的读取器：`-t` 去行尾、`-s` 跳、`-n` 限量、`-O` 偏移、`-d` 换分隔符；`readarray` 是同一条命令的别名。
- 它不靠换行判成功，所以第 12 节那个「最后一行被吞」在它身上不存在。
- CRLF 文件里 `-t` 只吃 `\n`、不吃 `\r`；剪 CR 之前先量清楚元素几个字节、尾巴是什么。
- 数组要带回当前 shell，来源就得写 `mapfile ... < <(...)`；写成 `cmd | mapfile` 数组落在子进程里（量到 0 个的那种 0）。
- 代价是内存：它整份进数组。大文件回到 `while read` + `|| [ -n "$REPLY" ]` + `< /dev/null` 那三件套。

## 16. select：它是菜单，不是「遍历」

你大概率是在搜「bash 怎么遍历数组」的时候撞见 `select` 的，看两眼示例会觉得它是 `for` 换了层皮。它不是。
`for` 的名单是进循环前自己算完的；`select` 的名单只是**候选**，每轮干什么由**从 stdin 读进来的那一行**决定 ——
没人输入，它就一次都不跑。这一节所有反直觉都长在「输入」这一侧。

先把最小可用的一版跑给你看（`selectmenu.sh` 里每个 `select` 都自带输入，这点最后说）：

```
$ bash selectmenu.sh
=== 1. 最小可用：菜单、编号从 1 开始、变量里进的是「内容」不是编号 ===
1) 备份
2) 归档
3) 清理
挑一个 >   循环体：item=[归档] ｜ REPLY=[2]（你按的那个数字原样留在这里）
挑一个 >   循环体：item=[备份] ｜ REPLY=[1]（你按的那个数字原样留在这里）
挑一个 > 1) 备份
2) 归档
3) 清理
挑一个 > 
  → 菜单三项对应编号 1 备份 / 2 归档 / 3 清理，select 把**名字**赋给 item；
    输入喂完（EOF）循环就结束，一共跑了 2 轮 —— 喂几个合法编号就跑几轮。
```

三行菜单先出来，编号从 **1** 开始（不是 0），然后提示符读一行。这一份喂了 `2` 和 `1`，于是屏幕上把两件事分得很清楚：

- **`item` 里进的是「归档」「备份」这两个名字**，不是你按的数字；
- **你按的那个原始字符留在 `REPLY` 里**（`REPLY=[2]`）。

要内容就读变量，要编号就读 `REPLY`。第一现场搞反的人通常是拿 `item` 去做数值判断，结果永远为空。
末尾菜单又被打了一遍然后循环结束 —— **喂几个合法编号就跑几轮**，喂完（EOF）就走，不问你是谁。

非法输入这一支是最反直觉的：

```
=== 2. 非法输入：不报错、不退出，只把 item 变成空字符串 ===
1) fast
2) safe
挑一个 >   ★ 输入 [9] 不在菜单里：mode 为空、循环没结束、也没任何报错
挑一个 >   ★ 输入 [zzz] 不在菜单里：mode 为空、循环没结束、也没任何报错
挑一个 >   ★ 输入 [fast] 不在菜单里：mode 为空、循环没结束、也没任何报错
挑一个 >   合法：mode=[fast]（REPLY=[1]）
挑一个 > 1) fast
2) safe
挑一个 > 
  → 判据只有一条：**变量为空 = 刚才那下没选上**。别指望它抛错、也别指望它自己退出。
    注意 'fast' 是菜单里的**名字**，按名字输入同样算非法（REPLY=[fast] → mode 为空）：只认编号。
    ★ 顺便看一眼提示符：这一段还是「挑一个 > 」—— PS3 是**全局变量**，第 1 段设的会一直跟着后面的
    每一个 select（默认值是 '#? '）。想换就得每次自己设，别以为它跟着菜单走。
```

`9`、`zzz`、`fast` 三个都不在菜单里，bash **一个字都没抱怨**，也不退出，只是把 `mode` 赋成空串。
所以判据只有一条：**变量为空 = 刚才那下没选上**。别指望它报错，也别指望它自己退出。

- `fast` 那一条命中率最高：它是菜单里的**名字**，可 `select` **只认编号**，按名字输入和按 `zzz` 完全等价。
- 注意提示符：这一段根本没设 `PS3`，屏幕上却还是「挑一个 > 」。因为 **`PS3` 是全局变量**，第 1 段设的那次会一直跟着后面每一个 `select`（默认值是 `#? `）。想换就得每次自己设，别以为它跟着菜单走。

再往 stdin 这一侧看一眼，这次是空行和「谁在哪个流里」：

```
=== 3. 空行 = 重打菜单、循环体不进；stderr 里才是菜单和提示符 ===
  先数一下：这一段的 stdout 有几行？（下面这条 printf 走 stdout）
1) a
2) b
挑一个 > 1) a
2) b
挑一个 > 1) a
2) b
挑一个 >     进了循环体：x=[a] REPLY=[1]
挑一个 > 1) a
2) b
挑一个 > 
  → 两个空行让菜单重打了两遍，可循环体只进了一次：空行 = 「重显菜单」，不是「选了个空值」。
```

这一段的小标题把归属说死了：**菜单和 `PS3` 提示符走 stderr，循环体的输出走 stdout**。
捕获里是一份混排（demo 把两个流合起来才录得到），所以看着像一坨；但数一下就清楚了：这段属于 stdout 的只有两句 ——
「先数一下：这一段的 stdout 有几行？」和那句「进了循环体：x=[a]」。剩下的菜单、提示符全是 stderr。
于是 `2>/dev/null` 那一下就等于把整个菜单抹掉：屏幕上一个字都不剩，看着像程序卡死。

形状上的另一条规矩：**空行 = 重打菜单，循环体根本不进**；它不是「选中了一个空值」。上面这段菜单打了一遍又一遍，循环体只进了一次。

把「变量为空」当校验、再自己带上重试上界，才是 `select` 在生产里唯一正确的写法：

```
=== 4. 拿「变量为空」做校验 + 重试上界：select 在生产里唯一的正确姿势 ===
1) 保留最近3份
2) 保留最近7份
3) 全部删除
挑一个 >   第 1 次非法输入（REPLY=[7]），再问一次
挑一个 >   第 2 次非法输入（REPLY=[9]），再问一次
挑一个 >   最终选择=[保留最近7份] ｜ 非法次数=2 ｜ 有没有落进「全部删除」→ 没有
```

`[ -z "$pick" ]` 当校验，`attempts` 当上界：`7`、`9` 两次非法输入只是「再问一次」，第三次 `2` 选中就 `break`。
最后那行「有没有落进「全部删除」→ 没有」是它在自证 —— **没确认之前，绝不走进那个破坏性分支**。

最要紧的是这一支，非交互场景全在这里翻车：

```
=== 5. ★ 输入不够 / 立刻 EOF：循环安静地一次都不跑，还返回非 0 ===
1) p
2) q
挑一个 > 1) p
2) q
挑一个 > 
  喂一个空行：循环体跑了 0 轮
1) p
2) q
挑一个 > 
  直接 EOF（< /dev/null）：循环退出码 = 1
  → ★ 这一条是给非交互场景准备的：CI / cron / 管道里跑 select 脚本，stdin 不是终端，
    循环会因为 EOF 结束而不是因为用户选完了；退出码 1 会被 set -e 当成失败。
    所以「脚本里有 select」和「脚本会被自动跑」这两件事不能同时想当然。
```

`<<< ""` 只喂到一个空行 → 循环体跑了 **0 轮**；`< /dev/null` 直接 EOF → **循环退出码 1**。
CI / cron / 管道里跑带 `select` 的脚本，stdin 不是终端，循环是**因为 EOF 结束**的，不是因为用户选完了；
那个 `1` 会被 `set -e` 当成失败收走。所以「脚本里有 `select`」和「脚本会被自动跑」这两件事不能同时想当然。

收口那四条 + demo 自己的复盘：

```
=== 6. 收口：select 的四条规矩 ===
  ① 菜单 + PS3 提示 → stderr；循环体输出 → stdout。想只留一个就得分别重定向，
     而随手写 2>/dev/null 会把整个菜单抹掉（屏幕上什么都不剩，看着像卡死）。
  ② item 是名字、REPLY 是你按的原始字符；非法输入（包括按名字）→ item 为空、不报错、不退出，
     校验代码必须自己写（第 4 段那个 attempts 上界就是最小实现）。
  ③ 编号固定从 1 开始，菜单项顺序一变，「按 2」的含义就跟着变 —— 别把编号写进文档或配置。
  ④ 非交互喂 stdin 完全可行，但要管好 EOF 与退出码；真正需要「选择」的场合，
     更稳的做法是把它做成参数（getopts，第 08 章），select 只当交互糖衣。
[退出码 0]
↑ 每一条 select 都自带输入（done <<< "..."），因为 select 的语义就是「读用户输入」——
  在非交互脚本里它必须有人喂，喂不到就一次都不跑、还返回非 0。
  三条反直觉的：REPLY 装编号、item 装内容；非法输入不报错只给空串；菜单和提示符走 stderr。
```

最后三行里有一句是这一节的技术核心：**每一条 `select` 都自带输入**（`done <<< "..."`），不共用脚本的 stdin。
因为 `select` 的语义就是「读用户输入」，同一个 stdin 会被上一个 `select` 吃到 EOF，后面的 `select` 一轮都起不来 ——
那正是第 5 段演过的事故，所以前面几段必须先各自把输入管够。

**这一节带走：**

1. `select` = 打菜单 + 读一行 + 按编号取内容：**变量装名字，`REPLY` 装原始输入**；它不是遍历。
2. 非法输入（包括按名字输入）→ 变量变空串，**不报错、不退出**；校验和重试上界必须自己写。
3. 空行只重打菜单、循环体不进；编号固定从 1 开始，菜单顺序一变「按 2」的含义就跟着变。
4. `PS3` 是**全局变量**，设一次跟着后面所有 `select`（默认 `#? `）；菜单和提示符走 **stderr**，`2>/dev/null` 会把菜单整个抹掉。
5. 每条 `select` 都得自带输入；喂不到就 0 轮且**退出码 1**，`set -e` 当场算失败。

## 17. break / continue 的层数，和 bash 根本没有循环标签

你在别处用过 `break outer:` 这种东西。**bash 没有循环标签**，`break` 后面只能跟一个整数（层数），默认 1。
于是所有「从第三层跳回最外层」的需求，都变成了一次数层数的作业 —— 数错不报错，只是少干活。

```
$ for i in 1 2; do for j in 1 2 3; do [ "$j" = 2 ] && break; printf "  i=%s j=%s\n" "$i" "$j"; done; done; echo "  ← 裸 break 只出内层，外层照跑（第 02 轮 j=1 又打了一次）"
  i=1 j=1
  i=2 j=1
  ← 裸 break 只出内层，外层照跑（第 02 轮 j=1 又打了一次）
[退出码 0]
```

裸 `break` 就是 `break 1`，只出**最里面那层**：外层照旧往下走，所以第二遍 `j=1` 又打了一次。屏幕上只有两行，这就是证据。

```
$ for i in 1 2; do for j in 1 2 3; do [ "$j" = 2 ] && break 2; printf "  i=%s j=%s\n" "$i" "$j"; done; done; echo "  ← break 2 一次出两层，整个嵌套当场结束"
  i=1 j=1
  ← break 2 一次出两层，整个嵌套当场结束
[退出码 0]
```

`break 2` 一次出两层，整个嵌套当场结束 —— 只剩 `i=1 j=1` 一行。

`continue` 的层数比 `break` 更容易读错，因为它的语义不是「往上跳」而是「往前推」：

```
$ for i in 1 2 3; do for j in a b c; do if [ "$j" = b ]; then continue 2; fi; printf "  i=%s j=%s\n" "$i" "$j"; done; done; echo "  ← continue 2 不是「跳过内层剩下的」，是「直接进外层下一轮」"
  i=1 j=a
  i=2 j=a
  i=3 j=a
  ← continue 2 不是「跳过内层剩下的」，是「直接进外层下一轮」
[退出码 0]
```

`continue 2` **不是**「跳过内层剩下的」，而是「**直接进外层的下一轮**」。三行输出每行都只有 `j=a`：
内层的 `b`、`c` 一次都没出现过，因为每次撞见 `b` 就把外层推进到下一轮了。想只丢下内层剩下的，写不带数的 `continue`。

层数写超了会怎样？这一条最阴：

```
$ for i in a b; do break 9; done; echo "  break 9 超出层数：退出码=$? ｜ 上面一行都没打 ← ★ 它把所有循环都跳掉了，脚本继续"
  break 9 超出层数：退出码=0 ｜ 上面一行都没打 ← ★ 它把所有循环都跳掉了，脚本继续
[退出码 0]
# ★ bash 没有 C/Java 那种 label。要「从第三层跳回最外层」只有三条路：break N（数得清层数时）、
#   把内层包进函数用 return（最稳）、或者置一个 flag 让外层条件去查。
```

只有两层循环，`break 9` **不报错**：退出码 0（`[退出码 0]` 也在那儿），上面一行都没打 ——
它把**所有**循环一次性跳光，脚本继续往下跑。所以「层数写多」不是崩溃，是**悄悄少干活**，这类 bug 最难查。
底下那两行 `#` 是 demo 给的三条出路：`break N`（数得清时）、包成函数用 `return`（最稳）、置 flag 让外层条件去查。

第三条路长这样：

```
$ lookup() { local n=0; for a in 1 2; do for b in 3 4; do for c in 5 6; do n=$((n + 1)); [ "$c" = 6 ] && { echo "  命中：第 $n 次内层迭代，在这里 return"; return 0; }; done; done; done; echo "  走不到这行（$n）"; return 1; }; lookup; echo "  ← 三层循环里的 return 一次跳到底；函数的退出码=$?"
  命中：第 2 次内层迭代，在这里 return
  ← 三层循环里的 return 一次跳到底；函数的退出码=0
[退出码 0]
```

`return` 退出的是**函数**，函数里那三层循环跟着一起没了，所以它一次就跳到底，而且**层数以后变了也不用改代码** ——
这就是「数不清层数」时首选它的原因。最后一行「函数的退出码=0」是配套的记账：`return 0` 就是函数的返回值，
调用方能直接拿它当判据，比在循环外面猜「到底有没有命中」干净得多。

**这一节带走：**

- `break` / `continue` 只能带**整数**层数，bash 没有循环标签；不带数 = 只动最内层。
- `break N` 是往上跳穿 N 层；`continue N` 是把第 N 层**推进到下一轮**，不是「跳过内层剩下的」。
- 层数超出实际循环数**不报错**：退出码 0、所有循环一次跳光、脚本继续 —— 静默少干活的典型形状。
- `return` 只能出现在函数里（或者 source 进来的脚本里）：顶层循环想一次跳到底，就先把那几层包成函数，像上面那样。
- 跳出来落在哪儿要自己证明：像在 `break 9` 那条里一样，循环后面 `echo` 一句「有没有走到这里」，比事后数层数可靠。

## 18. 作业控制：& / $! / jobs / wait / disown / kill -0

脚本里写 `cmd &` 的人，一半以为「不等」就是它的全部语义。其实是三件事叠在一起：
**多了一个进程**、**它进了本 shell 的作业表**、**这笔账只有 `wait` 能结**。
`bash jobwait.sh` 七小段，就是把这三条分开演 —— 这一节所有 pid 都折成 `<pid>`，因为那个数字每跑必变，
而「它和谁相等、退出码是几」这类关系每次都一样。

```
$ bash jobwait.sh
=== 1. & 起来的到底是什么：一个新进程，还是同一个 shell 里的「另一条线」？ ===
  本 shell 的 pid 与后台 sleep 的 pid 相等吗 → 不相等（不相等 = 真的多起了一个进程）
  后台进程的**父进程 pid** 等于本 shell 的 $$ 吗 → 是 ｜ 所以它只是「不等」，不是「换了爹」
  → & 之后子进程仍挂在本 shell 下：本 shell exit，它就变成孤儿（第 5 段 disown 演的就是这个）。
```

两个读数：`$$` 与后台 `sleep` 的 pid **不相等**（真的多起了一个进程）；那个进程的**爹还是本 shell**（`/proc/<pid>/stat` 第 4 列等于 `$$`）。
所以 `&` 不是「开了条线」，它只是一个仍挂在你下面的子进程 —— 本 shell 一 `exit`，它就成孤儿。这一条是后面 `disown` 的地基。

同一张作业表，四种问法，输出形状完全不同：

```
=== 2. jobs 的几种问法：同一份作业表，不同的输出形状 ===
  jobs 默认（带 [+]/[-] 与命令行原文）：
      [1]   Running                    sleep 0.5 &
      [2]-  Running                    sleep 0.5 &
      [3]+  Running                    sleep 0.5 &
  jobs -l（比默认多一列 pid；只折 pid 那一列，[1]/[2]/[3] 和命令行原文都留着）：
      [1] <pid> Running                    sleep 0.5 &
      [2]- <pid> Running                    sleep 0.5 &
      [3]+ <pid> Running                    sleep 0.5 &
  jobs -p（只有 pid）行数=3 ｜ jobs -rp（只有 running 的 pid）行数=3 ｜ jobs -sp（stopped）行数=0
  → 数并发为什么一律用 jobs -rp | wc -l：-r 滤掉已结束的、-p 只吐 pid，
    行数就是「还在跑的个数」，跟命令行文本、跟 [+]/[-] 的排版都没关系。
    （还有个 jobs -n 只报「自上次问以来状态变过的」，答案取决于你什么时候问 —— 本机不拿它当证据。）
```

默认那版带 `[1]`、`[2]-`、`[3]+` 和**命令行原文**；`-l` 比默认只多一列 pid（捕获里这一列一律折成 `<pid>`，作业号和命令行原文都留着）；
`-p` 只有 pid；`-rp` 只有**还在跑**的 pid；`-sp` 是 stopped，这里 0。
★ 数并发为什么一律 `jobs -rp | wc -l`：`-r` 滤掉已经结束但还没被回收的（僵尸会把数顶高），`-p` 保证一行一个 pid，
于是**行数就是「还在跑的个数」**，跟 `[+]/[-]` 的排版、跟命令行里有没有空格全都无关。
`jobs -n` 那句是提醒：它只报「自上次问以来状态变过的」，答案取决于你什么时候问 —— 本机不拿它当证据。

`wait` 的三种结局，一个数一种：

```
=== 3. wait 的三种结局：成功 0 ｜ 作业自己失败了 ｜ 被信号杀了 ===
  正常跑完的后台：wait 退出码=0
  子进程自己 exit 7：wait 退出码=7 ← ★ 脚本里拿到后台退出码的**唯一**办法
  被 SIGTERM 杀掉：wait 退出码=143 ｜ kill -l 15 的名字=[TERM] ｜ 143 = 128 + 15 → 是
  → 对照：& 之后不 wait，$? 是「起作业这条命令自己」的退出码（永远 0）；
    作业干了什么、死得多惨，全在 wait 的返回值里 —— 这一条和第 04 章的 141/143 是同一套记账。
```

正常跑完 → **0**；子进程自己 `exit 7` → **7**；被 `SIGTERM` 杀掉 → **143**，旁边 `kill -l 15` 给的名字是 `TERM`，`143 = 128 + 15` 对得上。
★ 「`&` 之后不 `wait`」的真实代价是：`$?` 是**起作业那条命令自己**的退出码（永远 0），作业干了什么、死得多惨，全在 `wait` 的返回值里。
这和第 04 章那笔 141/143 的账是同一套记法。

两种「什么都没等到」的退出码不一样，还有一种「等到 0」是假的：

```
=== 4. wait 的两次「什么都没等到」：重复 wait 与 wait 一个不是自己孩子的 pid ===
  第一次 wait=0，第二次 wait=0（★ 同一个 pid 再 wait 一次仍返回 0，不报错 —— 它在翻旧账）
  wait 一个**不是自己孩子**的 pid（这里用 $PPID：只是问一句，不碰它）：退出码=127 ｜ 原文=[jobwait.sh: line 56: wait: pid <pid> is not a child of this shell]
  wait 一个大得离谱的数：退出码=1 ｜ 原文=[jobwait.sh: line 59: wait: `4294967000': not a pid or valid job spec]
  → ★ 两条都是「没等到」，但 bash 给的退出码不一样：127 是「它确实是个 pid，只是不是我的孩子」，
    1 是「这个数根本不构成一个合法作业号」。写脚本时想拿这个码做分支的话，先分清这两层。
  → 三种「返回 0」要分清：真成功、翻旧账（已经 wait 过）、以及作业表空时 wait 不带参数。
    「重复 wait 得 0」特别容易被当成「等到了一次成功」，其实它什么都没等。
```

- `wait $PPID`（它确实是个 pid，但不是这个 shell 的孩子）→ **127**，原文里那句是 `is not a child of this shell`；
- `wait 4294967000`（这个数连合法作业号都不算）→ **1**，原文里那句是 `not a pid or valid job spec`。

想拿这个码做分支，先分清这两层：**127 = 不是我的孩子，1 = 你给的数根本不成话**。
而最阴的是第一行：同一个 pid **再 `wait` 一次还是 0** —— 它什么都没等，只是在翻旧账。
所以「`wait` 返回 0」有三种成因：真成功 / 翻旧账 / 作业表空时不带参数的 `wait`。
要把 0 当「活干成功了」，只有两条路：显式检查你 `wait` 的那个 pid，或者让作业自己把结果写进文件。

`disown` 是把上面这张表撕掉一行：

```
=== 5. disown：从作业表里摘掉，但进程照跑（等于把收尾权交了出去） ===
  disown 之后 jobs -rp 行数=0（表里已经没它了）｜ kill -0 探它 → 还活着
  wait（无参数）返回后再探一次 → 还在跑（★ 这是 30 秒的 sleep，wait 一回来它当然还在跑 = wait 压根没等它）
  → ★ disown 只动 bash 的作业表，不动进程表。之后 wait / jobs / %1 都再也看不见它，
    但脚本退出时它照样活着（被 init 收养）。这就是本手册要求「后台作业必须当场收尾」的原因。
```

`disown` 之后 `jobs -rp` 行数 0（表里已经没它了），可 `kill -0` 一探 → **还活着**；
无参数 `wait` 返回后再探一次 → **还在跑**。这一句就是铁证：**那是 30 秒的 `sleep`，`wait` 一回来它当然还在跑 = `wait` 压根没等它**。
`disown` 只动 bash 的作业表，不动内核进程表；之后 `jobs` / `wait` / `%1` 再也看不见它，脚本退出时它被 init 收养、照样活着。
这就是本手册要求「后台作业必须当场收尾」的原因 —— 第 7 段会把它 kill 掉再自证。

`kill -0`：不投递信号的那次调用，是最好的探活。

```
=== 6. kill -0：不投递信号的那次调用，是最好的探活（第 20 节循环等进程就靠它） ===
  活着时 kill -0（信号 0 只是查一下，不投递任何东西）：退出码=0 ｜ 原文=[]
  自己家的进程已结束并被回收后：退出码=1 ｜ 原文=[jobwait.sh: line 85: kill: (<pid>) - No such process]
  别人的进程（pid 1，本脚本既不动它也发不到它）：退出码=1 ｜ 原文=[jobwait.sh: line 85: kill: (<pid>) - Operation not permitted]
  → ★ 后两条的退出码都是 1，但含义**不一样**：一条是「没这个进程」，一条是「有，但轮不到你」。
    循环等进程结束时如果只看 rc≠0 就判定「它退出了」，遇到权限类情况会提前收工 ——
    所以真要用它当循环条件，得把报错原文一起留着，或者干脆 wait 你自己的 pid（第 3 段）。
  → kill -0 答的是**内核视角**：进程刚死、还没被父进程回收时它是个僵尸，kill -0 仍然说「在」。
```

三行读数：活着 → **0**、原文为空；自己家的进程已结束并被回收 → **1**、原文 `No such process`；
pid 1（别人的）→ **也是 1**、原文 `Operation not permitted`（原文里的 pid 同样折成了 `(<pid>)`）。
★ 同一个 `rc=1`，**两种含义**。你要是写 `while kill -0 "$p" 2>/dev/null; do ...; done` 当循环条件，
碰到权限类那一次就当场判「它退出了」，提前收工。真要用它，就把报错原文一起留着，或者干脆 `wait` 自己的 pid（第 3 段）。
最后一行补了个视角差：进程刚死、还没被父进程回收时它是**僵尸**，`kill -0` 仍然说「在」—— 它答的是内核视角，不是「还在干活」。

收口之前，先把「一个都没留下」自证掉：

```
=== 7. 收口：先自证一个进程都没留下，再给判据 ===
  本脚本经手过的 pid 共 6 个 ｜ 此刻还活着的 = 0（必须是 0）
  作业表里剩下的行数 = 0 ｜ jobs 输出 =[]
  ① 后台作业的退出码**只有 wait 能拿到**；不 wait 就等于把失败咽下去了。
  ② wait 返回 0 有三种成因（真成功 / 翻旧账 / 没孩子可等），所以别拿「wait 0」当「活干成功了」的唯一证据，
     要么显式检查你 wait 的那个 pid，要么让作业自己把结果写进文件。
  ③ disown 是「放弃收尾权」，不是「让进程更安全」；要留长命进程就得自己写 trap EXIT。
  ④ 数并发、探存活，只用 jobs -rp 与 kill -0 这两把尺，别 grep jobs 的文本。
[退出码 0]
↑ 这一节把「后台作业的失败去哪了」问到底：wait 是拿到后台退出码的唯一办法，
  而 wait 返回 0 有三种成因（真成功 / 翻旧账 / 没孩子可等）。
  所有 pid 都折成 <pid> 或换成「相等吗」，因为这个数字每跑必变，而关系每次都一样。
```

经手 **6** 个 pid、此刻还活着 **0** 个、作业表剩 **0** 行、`jobs` 输出为空 ——
这一节起过的每个后台都在当场 `wait` 或 `kill` 收尾，第 22 节那句 `jobs -p | wc -l` = 0 靠的就是这张干净的表。
底下四条判据和那三行 `↑` 一起给出：`pid` 为什么全部折掉、以及「数并发 / 探存活」只用 `jobs -rp` 与 `kill -0` 这两把尺。

**这一节带走：**

1. `&` = 多一个进程（爹还是本 shell）+ 进本 shell 的作业表 + 这笔账**只有 `wait` 能结**。
2. 后台退出码只有 `wait` 拿得到：作业自己的码（7）、被信号杀的 `128+信号号`（143）；`&` 之后的 `$?` 永远是 0。
3. `wait` 返回 0 有三种成因（真成功 / 翻旧账 / 没孩子可等）；「没等到」有两种码：不是自己孩子 **127**、号码不合法 **1**。
4. `disown` 是**放弃收尾权**，不是让进程更安全：`jobs`/`wait`/`%1` 都看不见它，进程照跑。
5. `kill -0` 的 `rc=1` 有两种含义（没这个进程 / 有但轮不到你）；它答的是内核视角，僵尸也算「在」。
6. 数并发只用 `jobs -rp | wc -l`，探存活只用 `kill -0`，别去 `grep` `jobs` 的文本。

## 19. 重试环：until 的正解，和它必须带的上界

「等它就绪」这种循环谁都写过，死循环也谁都踩过。`until` 的本体只是 `while not`，
它值钱的地方是把**意图**写在条件里；真正救你命的是另一半 —— **上界**。

```
$ bash untilretry.sh
=== 1. until 和 while 是镜像：条件互为反面，轮数才一样 ===
  while [ i -lt 3 ]（条件真才进）：跑了 3 轮，i=3
  until  [ j -ge 3 ]（条件假才进）：跑了 3 轮，j=3
  ★ 反面写法 until [ w -lt 3 ]：只跑了 0 轮就停了（0 -lt 3 一进来就真 → 立刻满足停止条件）
  → 一句话：until = while not。它俩的语法差别只是「第一次判断用哪个真假」，
    读代码时的差别是**意图**：until 后面跟的是「我等到什么就算了」的停止条件 —— 写反一次就是
    上面第三行那种「一次都不干就收工」，或者第 2 段那种停不下来的死循环。
```

`while [ i -lt 3 ]`（条件真才进）和 `until [ j -ge 3 ]`（条件假才进）各跑 3 轮，互为镜像。
第三行才是重点：`until [ w -lt 3 ]` 一进来条件就为真 → **0 轮**。
`until` 后面跟的是「我等到什么就算了」的**停止条件**，写反一次就是上面那种「一次都不干就收工」，
或者反过来一个停不下来的死循环。读别人的重试循环，先看这一行是「等」还是「不等」。

```
=== 2. 一次都不跑的情形，和它的退出码（这条最容易被想当然） ===
  停止条件一进来就成立（0 -ge 0 为真）：跑了 0 轮，循环整体退出码=0
  → 循环体一轮都没跑，退出码仍是 0：bash 的循环**不会**因为「什么都没干」而报错。
    所以重试类循环必须自己带上「等到了吗」的判据（看第 4 段拿文件存在性判断，而不是拿退出码）。
```

停止条件一进来就成立 → **跑了 0 轮，退出码 0**。bash 的循环**不会**因为「什么都没干」而报错，
这条直接否掉了「拿循环的退出码判断有没有等到」这条路 —— 判据必须自己造（第 4 段拿文件存在性，不是拿 `$?`）。

确定性的一版（用计数模拟「第 3 轮才 ready」，所以每次跑逐字一样）：

```
=== 3. 确定性的重试环：第 3 轮才 ready（用计数模拟，保证每次跑逐字一样） ===
  第 1 轮：ready.flag 在吗 → 不在
  第 2 轮：ready.flag 在吗 → 不在
  第 3 轮：ready.flag 在吗 → 在
  收工：tries=3 ｜ 等到了吗 → 是 ｜ 有没有撞上上界 → 没撞
  → 注意循环条件里的两半：**等的是什么** + **最多等多久**。少了后半句就是一个死循环。
```

条件里是两半：**等的是什么**（`[ -e ready.flag ]`）+ **最多等多久**（`tries` 的上界），用 `||` 拼在 `until` 后面。
少了后半句就是死循环。收工那行打了三个读数：`tries=3`、等到了 → **是**、撞界 → **没撞**。
「等到了吗」和「撞没撞上界」是**两个独立判据**，都得打出来；只打前者，失败时你分不清是超时还是压根没开始等。

永远不 ready 那一支，必须存在：

```
=== 4. 撞上界的那一支：东西永远不 ready，循环必须自己认输 ===
  ★ 到上界还是没等到：轮询了 4 轮，按失败处理（下面把退出码交出去）
  这一支的判定结果 = 超时（4 轮 × 上界 4）
```

轮询到上界（4 轮 × 上界 4）→ 判定结果 **超时**，并且「下面把退出码交出去」。
生产里这一支就是「重试耗尽 → 报警 / 非零退出」的落点。只写了「等什么」、没写「等多久」的循环，
等于把「服务没起来」写成「还在起」，而且这句话永远不会被推翻。

真异步的一版（后台进程 0.2 秒后立 flag）：

```
=== 5. 真·异步版：后台进程 0.2 秒后立 flag，循环带 sleep 轮询 ===
  等到了吗 → 是 ｜ 轮询了 <每跑必变> 次（这个数字每次跑都可能不一样，★ 所以本机只当过程看，不印进 README 的证据里）
  → 屏幕上不打轮询次数（它取决于调度），只打「等到了 = 是」这种每次都成立的事实。
```

屏幕上只留了一句「等到了吗 → **是**」，轮询次数那一格直接打成 `<每跑必变>` —— 它取决于调度，本机故意不把它印进证据。
这是本章反复用的手法：**能复现的写成人能核对的布尔，不能复现的明说它是变量**。

忙等和带 sleep 的轮询，差在哪：

```
=== 6. 忙等 vs 带 sleep 的轮询：代价是能用数字看出来的（这里打的是可复现的量） ===
  忙等写法（条件里不放 sleep）：循环体每轮都只做一次 [ -e ]，但 CPU 一直被占满 —— 本机用 0.2 秒的时间窗测一下轮询次数：
    忙等这一支在这 0.2 秒里空转了 <很多> 次（次数巨大且每跑必变 → ★ 本机不印具体数字）
    带 sleep 0.05 的这一支：轮询次数是「耗时 / 0.05」量级（同样每跑必变，不印数字）
  → 这一段的结论不靠数字：**忙等 = 用一整个核换一个不确定的延迟**；
    只要循环体里有 sleep，你的轮询就变成了「最多晚半秒知道」，代价可控。
    真要知道「进程结束」这件事，压根不用轮询：wait 它（第 18 节），或者用 inotifywait（不在本章范围）。
```

demo 明说这两支的**次数**都不印（一支在 0.2 秒窗口里空转「很多」次，另一支是「耗时 / 0.05」的量级，都每跑必变）。
结论不靠数字：**忙等 = 用一整个核换一个不确定的延迟**；循环体里放了 `sleep`，代价就变成「最多晚半秒知道」，可控。
而真要知道「进程结束了」这件事，压根不用轮询 —— `wait` 它（第 18 节）。

```
=== 7. 收口：三条能带走的话 ===
  ① until 用来写「等到 X 为止」，读起来比 while [ ! -e X ] 顺，仅此而已 —— 语义上和 while not 等价。
  ② 任何重试环都必须**两个条件一起写**：等什么 + 最多等多久（第 3、4 段那对 4 / 4）。
     只有前一半的 until 是本机见过的最常见死循环；循环退出码是 0，不会替你报错。
  ③ 每跑必变的数字（耗时、轮询次数、pid）不要印成证据；改成「等到了吗」「撞没撞上界」这类布尔，
     它们才是能逐字核对、也是换台机器还成立的东西。
[退出码 0]
↑ 前四段用计数模拟出「第 3 轮才 ready」，所以逐字可复现；第 5 段是真异步轮询，
  那一段的轮询次数每次跑都可能不同 —— 脚本里只报「等到了吗」这个布尔值。
```

**这一节带走：**

- `until` = `while not`，条件里写的是**停止条件**；写反一次就是 0 轮或者死循环。
- 跑 0 轮的循环退出码仍是 **0**，bash 不替你报错：判据要自己带（存在性、布尔），别用 `$?`。
- 重试环**两个条件一起写**：等什么 + 最多等多久；「等到了」和「撞界了」两条读数都要打出来。
- 撞上界那一支必须有自己的出口（非零退出 / 报警），否则「没起来」和「还在等」在屏幕上长得一样。
- 耗时、轮询次数、pid 这类每跑必变的数不要当证据，换成「等到了吗」这种换台机器还成立的布尔。
- 真需要「知道进程结束」就 `wait`，别用 `sleep` 轮询换 CPU。

## 20. 限并发：一把全扔 vs 数闸门 vs wait -n

「把 N 个任务全扔后台」是最顺手的写法，也是唯一一种在**别人看不见的地方**出事的写法：它不会报错，它只是把压力全部转给下游。
对账的基准永远是串行 —— 并发改法如果连文件数都对不上，那不是快，是写坏了。

```
$ bash parlimit.sh
=== 1. 先把「串行」作为基准：跑完几个、用了几个进程位 ===
  串行跑完 → 结果文件数=6（六个任务，6 个成功）
  → 串行是**正确性**的基准线：后面两种并发改法都必须得到同样这 6 个文件，否则就是并发写坏了。
```

串行跑完 6 个任务、6 个结果文件。这一行是**正确性**的基准线：后面两种并发写法都必须得到同样这 6 个文件。

最常用也最危险的一版：

```
=== 2. 最常用（也最危险）的一版：一把全扔到后台 ===
  全部 & 起来 → 观察到的并发峰值=6 ｜ 结果文件数=6
  → 6 个任务就 6 个并发；60 个就 60 个。数据库连接、磁盘 IO、被限流的 API 都会在这里爆炸，
    而脚本一声不响 —— 因为它确实「跑完了」。这就是为什么第 3 段那个闸门必须写。
```

6 个任务就 6 个并发，60 个就 60 个 —— 数据库连接池、磁盘 IO、会被限流的 API 都在这个位置炸，
而脚本**一声不响**，因为它确实「跑完了」。这就是下一段那个闸门必须存在的理由。

正解：起新任务**之前**先数闸门。

```
=== 3. ★ 正解：起新任务之前先数闸门（jobs -rp | wc -l 就是那个闸） ===
  限并发 2 → 观察到的峰值=2 ｜ 结果文件数=6 ｜ 前 3 个结果=alpha bravo charlie 
  → 三处细节，错一处整套就废：① 用 -r（只数还在跑的，否则已完成的僵尸会把闸门顶死）；
    ② 循环条件用命令替换**重新数一次**，不能把 running 存成变量再用（那是上一轮的数）；
    ③ 闸门里必须有 sleep 0.05，见第 6 段。
  三版结果对不对得上（串行=全并=限流）：一致 ｜ 有没有超过上限 2：没有（闸门有效）
```

限并发 2 → 观察到的峰值就是 2，结果文件数还是 6。三处细节错一处整套就废，捕获里也逐条点了：

1. 用 **`-r`**：只数还在跑的。已结束的进程在被回收前仍会出现在 `jobs` 里，闸门会被僵尸顶死（这就是「脚本卡住不动」的常见原因）。
2. 循环条件里用命令替换**每轮重新数一次**，不能把 `running` 存进变量再拿它比 —— 那是上一轮的数。
3. 闸门里必须有那一下 `sleep`（第 6 段算这笔账）。

再补一句闸门的位置：**在 `&` 起新任务之前数**，不是起完之后；起完之后才数，峰值已经先冲上去了。
最后一行是对账：串行 = 全并 = 限流，三版一致，且没超过上限 2。

另一把闸门：`wait -n`（bash 4.3+）。

```
=== 4. 另一把闸门：wait -n（bash 4.3+，等到「任意一个」结束就走，不用轮询） ===
  wait -n 版 → 峰值=2 ｜ 结果文件数=6 ｜ 和 sleep 轮询版数量一致吗 → 是
  → 差别不在快慢，在**谁在等**：sleep 0.05 版是你每 0.05 秒问一次；wait -n 是内核结束那一刻推你一下。
    闸门里的 wait -n 还有个副作用：它顺手把结束的作业**回收**了并返回它的退出码（第 5 段要用）。
```

峰值同样是 2，和 `sleep` 轮询版数量一致。差别**不在快慢，在谁在等**：`sleep 0.05` 版是你每 0.05 秒问一次，
`wait -n` 是内核在作业结束那一刻推你一下。它还有个顺手的好处：把结束的那个作业**回收**掉并返回它的退出码 —— 下一段就靠它记账。

失败的账记在哪儿：

```
=== 5. ★ 记账：并发时谁失败了？（不 wait 就等于把失败咽下去） ===
  ★ 任务 charlie 故意失败
  故意让 1 个任务失败 → 结果文件数=5 ｜ wait -n 抓到的失败数=1
  → 两条都要看清：文件数少 1（**证据在磁盘上**），计数靠 wait -n 的返回值。
    如果这里写成裸 wait（不带 -n、不接返回值），失败就永远看不见 —— 脚本还是退 0。
```

故意让 `charlie` 失败 → 结果文件数掉到 **5**（证据在磁盘上），`wait -n` 抓到的失败数 **1**（证据在返回值里）。
两条都要看：只看文件数你分不清是「没跑」还是「跑失败了」；只看计数你分不清文件是不是被谁删了。
★ 而这里如果写成**裸 `wait`**（不带 `-n`、不接返回值），失败就永远看不见 —— 脚本照样退 0，这就是「不 wait 等于把失败咽下去」。

三种等待方式各自的形状（本机不掐表）：

```
=== 6. 忙等 vs sleep 轮询 vs wait -n：本机不打耗时，只打能复现的东西 ===
  三种闸门各自的「等待方式」：
    A 无 sleep 的 while [ jobs -rp ... ]  → 每轮都重新起一次 jobs 和 wc，CPU 空转
    B 有 sleep 0.05                       → 最多晚 0.05 秒知道，代价可控
    C wait -n                             → 不轮询，被结束的那个作业直接唤醒
  闸门检查这件事，B 版每轮要起几个外部进程？jobs 是内建（0 个进程），wc 是外部（1 个）：
    jobs is a shell builtin
    wc is /usr/bin/wc
    wait is a shell builtin
  → 所以「A 版忙等」的真实形状是：**每轮 fork 一个 wc**。这是第 22 节要算的那笔账的一个预告。
```

屏幕上 A 那句写的是「每轮都重新起一次 `jobs` 和 `wc`」，下面 `type -t` 一问才发现这句话**只对了一半**：`jobs` 是内建（0 个进程）、
`wc` 是外部（1 个）、`wait` 是内建。所以「A 版忙等」的真实形状是**每轮 fork 一个 `wc`** —— 睡一下的那版也一样，只是次数少。
B（`sleep 0.05`）最多晚 0.05 秒知道；C（`wait -n`）压根不数。这笔账在下一节（循环贵在哪里）会用「不同 pid 个数」量给你看。

```
=== 7. 收口：四条能带走的话 ===

     闸门必须在**起新任务之前**数，不是起完之后；每轮重新数，别把上一次的数存进变量。
  ② 一定要 -r：已结束的进程在被回收前仍会出现在 jobs 里，闸门会被僵尸顶死（这就是「卡住不动」的常见原因）。
  ③ 有 wait -n 就别轮询：它同时解决「等得晚」和「失败没人记账」两件事（第 4、5 段）。
  ④ 并发版的合格判据永远和串行版**同一份对账**：结果文件数、失败数。别只看「跑完了」。
     第 08 章的锁与幂等讲的是同一件事的另一半：多个 writer 抢同一个文件时怎么办。
[退出码 0]
↑ 第 2 小段「一把全扔」这里只有 6 个任务，什么毛病都看不出来 —— 它危险在「任务数不由你定」的那一天。
  本章没有真跑一千个任务去撞 ulimit -u（第 1 节那个 50372 是这台机器的上限），所以「放大就会撞」只当推理给出，不当证据；两把闸门里 wait -n 那把更省：不用轮询，但它「等任意一个结束」的语义要求你只 wait 自己起过的。
```

**这一节带走：**

- 限并发的最小正确写法就三行：**数闸门（`jobs -rp | wc -l`）→ 超了就睡一下 → 再 `&` 起下一个**；闸门在起之前数，每轮重新数。
- 一定要 `-r`，否则没回收的僵尸把闸门顶死；也一定要有那一下 `sleep`，否则每轮白 fork 一个 `wc`。
- 有 `wait -n` 就别轮询：它一次解决「等得晚」和「失败没人记账」两件事，代价是要求你只 `wait` 自己起过的作业。
- 并发版的合格判据永远和串行版**同一份对账**：结果文件数、失败数。「跑完了」不是判据。

## 21. 循环贵在哪里：词表形状与一次 fork

「这个循环慢」这句话没有信息量。能问的只有两件：**词表被摊成了几个元素**、**循环体里出现了几个不同的 pid**。
这一节全程不掐表 —— 毫秒每次跑都不一样，印进书里就永远对不上。

```
$ bash loopspeed.sh
=== 1. 三种 for：词表是被「摊开成一排」还是「每轮现算」 ===
  for i in {1..2000}     → 进循环前就摊开成 2000 个词（数组长度实测，不是估算）
  ★ 但 {1..2000} 写成 {1..$N} 就废了：摊开成 1 个词，第一个词是 [{1..2000}]（花括号展开发生在变量替换**之前**，    它压根不认识 $N）→ 这一条是第 02 章「展开有固定顺序」在循环里的现场。
  for i in $(seq 1 2000)   → 先起一个 seq 进程，再把它 2000 行输出摊成 2000 个词
  for ((i=1;i<=2000;i++))  → 没有词表这回事，每轮现算一个数（所以它给不出上面那种数组长度）
  C 风格那一支实测跑了 2000 轮，最后一轮 x=2001（★ 循环变量出了循环还活着，见第 3 节）
  → 为什么要紧：前两种写法把 N 个元素**同时**握在内存里（N=2000 无所谓，
    N=2000000 或者元素是长路径时就很难看）；for (( )) 一个都不存。
```

三种 `for` 的内存形状一目了然：`{1..2000}` 进循环前就摊成 2000 个词（这里打的是实测数组长度）；
`$(seq 1 2000)` 先起一个 `seq` 进程、再把它的 2000 行输出摊成 2000 个词；`for (( ))` 根本没有词表，每轮现算一个数。
中间那行 ★ 是本章反复引用的那条展开顺序：`{1..$N}` **一个字都不展开**，摊成 1 个词、词面就是 `{1..2000}`，
因为花括号展开发生在变量替换**之前**，它压根不认识 `$N`。
C 风格那一支还顺手量到 `x=2001` —— 循环变量出了循环照样活着（第 3 节那条），所以复用变量名的两层循环会互相踩。
为什么要紧：前两种把 N 个元素**同时**握在内存里，N=2000 无所谓，N=2000000 或者元素是长路径时就很难看；`for (( ))` 一个都不存。

循环体贵不贵，取决于它是内建还是外部命令 —— 这个直接问，不用测：

```
=== 2. 循环体贵不贵，取决于它是内建还是外部命令（这里不掐表，直接问） ===
    :        type -t → builtin
    true     type -t → builtin
    echo     type -t → builtin
    printf   type -t → builtin
    cd       type -t → builtin
    wait     type -t → builtin
    mapfile  type -t → builtin
  /bin/true 这种带路径的：command -v → /bin/true ｜ type -t → file
  → 判据一句话：**type -t 给出 builtin 的，循环一百万轮也不 fork；给出 file 的，每一轮都 fork+exec 一次。**
```

判据一句话：**`type -t` 给出 `builtin` 的，循环一百万轮也不 fork；给出 `file` 的，每一轮都 fork+exec 一次。**

这个数是可以现场量出来的，办法是让循环体自己报告 pid：

```
  现场量一下 fork 的次数（办法：让循环体自己报告 pid，用 BASHPID 而不是 $$）：
    循环体全是内建（printf）  → 出现的不同 pid 个数=1
    循环体每轮起一个外部 bash → 出现的不同 pid 个数=50（★ 每个 pid 就是一次 fork+exec）
```

同样 50 轮：循环体全是内建（`printf`）→ 出现的**不同 pid 个数 = 1**；循环体每轮起一个外部 `bash` → **50 个**，每个 pid 就是一次 fork+exec。
不用掐表，50 次进程创建已经摆在屏幕上。

管道版为什么慢一整截，还有本章自己踩过的一个坑：

```
=== 3. 管道版为什么慢一整截：它把循环体放进了另一个进程 ===
  判据用 $BASHPID（本进程真实 pid），不要用 $$（它在子 shell 里仍然等于父进程的 pid）。
    写法 A：for i in $(seq 1 50)　→ 循环体里 [ "$BASHPID" = "$$" ] 成立，循环体就在**本进程**里跑
    写法 B：seq 1 50 | while read i　→ 循环体里 [ "$BASHPID" = "$$" ] **不成立**，它在另一个进程里
    ★ 自己踩过的坑：pa=$(BASHPID) 想拿主 shell 的 pid，结果命令替换**本身就 fork 了一个子进程**，
      量到的是那个 subprocess 的 pid（和 $$ 永远不等）。凡是用 $() 去问「我在哪个进程」，问的都是别人。
  → 这条和第 04 章「管道每一段都是自己的进程」是同一条规矩，代价在这里加了一层：进程之间只能通过那根管道说话。
    循环体里赋值、开数组、cd，主 shell 一个都收不到 —— 第 14 节的 lastpipe 三接回就是为了治这个。
```

写法 A（`for i in $(seq 1 50)`）里 `[ "$BASHPID" = "$$" ]` 成立 —— 循环体就在本进程里跑；
写法 B（`seq 1 50 | while read i`）里**不成立** —— 循环体在另一个进程里，于是里面的赋值、数组、`cd` 主 shell 一个都收不到（第 14 节 `lastpipe` 三接回治的就是这个）。
★ 中间那三行是本章自己踩过的坑：`pa=$(BASHPID)` 想拿主 shell 的 pid，结果**命令替换本身就 fork 了一个子进程**，

逐行读文件 vs 一次读全，两种「循环」的内存形状：


`while read` 流式 → 循环跑了 3000 轮，任意时刻内存里只有 **1 行**。

九个辅助脚本，`pgrep -c -f` 数出来是 **0**。这里有两个必须照抄的细节：

- **每个词都写成 `[x]xxx`**（`[l]oopsnap`、`[r]eadlast`……）是**防自捕**：`-f` 匹配的是整条命令行，照直写 `loopsnap`
  就把正在执行这条命令的 bash 自己也数了进去（它的 argv 里就有那个字符串），于是量出一个**永远不为 0 的假数**。
- 结尾那句 `|| true` 不是装饰：`pgrep` 找不到匹配时**自己退 1**，不挂就压根印不出这个 0（开了 `set -e` 更会当场把脚本杀了）。

最后一条是「为什么这里没有 `ss`」：

```
# 本章没起过监听端口、没调用过任何网络命令，这是本章的设计约束；不贴 ss 的监听表，
#   因为那几行是本机其它服务的端口号，每跑必变，贴进书里就永远复现不了（本机端口归属怎么看是另一件事，
#   在 ssh 手册第 05 章《端口转发》那条线上；本章只需要它证明「这里没有本章的贡献」）。
```

最后三行是 demo 提前把话说明白：**这张表不是本章的证据来源**。真要贴 `ss`，那几行全是本机其它服务的端口号和进程号，
每跑必变，而且和「本章有没有留下东西」毫无因果关系 —— 一句设计约束（没起监听端口、没调用过网络命令）比一张会变的表管用得多。
端口归属怎么查是另一条线（ssh 手册第 05 章《端口转发》那条）。

**这一节带走：**

- 跑过东西的脚本要自证两件事：**落了什么文件**（`ls | wc -l` + 非产物计数）、**留了什么进程**（作业表行数 + `pgrep`）。
- 自证要给「数」也给「确实没有」的形态：`grep -vc` 配一句 `|| echo "  （无）"`，别只留一个孤零零的 0。
- 问「我这张作业表干净吗」必须在**起后台的那个进程自己**里问；换个 `bash -c` 子进程去问，那里天生是空表，那个 0 是假的。
- `pgrep -f` 的模式一律写成 `[x]xxx` 防自捕，后面挂 `|| true` 防它自己退 1。
- 每跑必变的东西（pid、毫秒、端口表）不进证据：本章把它们全换成「相等吗 / 几个 / 有没有」这类每次都成立的关系。

## 一页纸（考前扫这半页）

```text
词表：for 的名单进循环前摊平一次；体里 rm/touch/改变量都改不到本轮。已删的照样轮到，新出的看不见 → body 第一步 [ -e ]。
通配：0 匹配 → 默认档图案原样进循环（1 轮）；nullglob → 0 轮；failglob → 展开阶段炸且整条命令行作废。按名单干活先开 nullglob。
引号：不带引号 = 先按 IFS 词分割、再做一次通配展开。遍历数组只有 "${arr[@]}" 这一种写法。
序列：{1..$N} 一个字都不展开（花括号早于变量替换）。要序列：for (( )) 零进程零名单，或 $(seq) 起一个外部进程但只起一次。
算术：for (( )) 三段都是算术上下文，直接写变量名；非数字当变量名查 → 0 → 0 轮不报错；小数 = 语法错误。
变量：bash 没有块作用域。for in 出来是最后一个词，for (( )) 出来是那个让条件失败的数（比最后一轮多 1）。
空循环：0 轮 = 退出码 0。「跑完了」和「压根没跑」靠 $? 分不开，只能在体里数轮数。
read：退出码问「撞没撞到分隔符」，不问「拿到字没有」。空行 0、EOF 1、超时 142 —— 三件不同的事。
末行：while read 少跑一轮且不报错。唯一值得背的修法写在条件里：|| [ -n "$x" ]。判据是两份文件都得 3 轮。
收尾变量：循环外别拿那个循环变量当证据 —— 最后一次失败的 read 会把它清空（第 21 节那格打的就是 []）。
原样读行：IFS= read -r。少 = 就吃首尾空白和连续空白，少 r 就吃反斜杠。
偷吃：体里任何读 stdin 的命令（ssh/cat/gpg/mysql/再 read 一次）都跟 read 抢同一条流 → 只剩第一轮。
      三档：< /dev/null（ssh 用 -n）< fd 3 分离（体里真要塞东西）< mapfile 进数组再 for。
管道：循环一进管道就是另一个进程，里面的赋值、数组、cd 全留在原地。
lastpipe：只救最后一段，且要求作业控制关着（set +m；非交互 bash 默认关着，交互终端默认开着）。
接回：要带状态出来就别让循环进管道。while ... done < <(...) 最稳，n=$(...) 走 stdout，mapfile 是前者的加强版。
mapfile：按行的读取器。-t 去行尾、-s 跳、-n 限量、-O 偏移、-d 换分隔（-d "" = NUL，配 find -print0）。readarray 是别名。
CRLF：-t 只吃 \n 不管 \r。要连 \r 一起走：tr -d '\r' 先过一遍，或读完剪后缀 —— 剪之前先量元素几个字节、尾巴是什么。
select：是菜单不是遍历。item 装名字、REPLY 装原始输入；非法输入（包括按名字）给空串、不报错、不退出；
        空行只重打菜单；编号从 1 开始；PS3 是全局变量；菜单走 stderr；喂不到输入 → 0 轮 + 退出码 1。
跳出：break N 往上穿 N 层；continue N 是把第 N 层推进下一轮（不是「跳过内层剩下的」）。
      层数写超不报错、只是悄悄少干活；数不清就把内层包成函数用 return。没有循环标签。
后台：& = 多一个进程（爹还是本 shell）+ 进本 shell 的作业表 + 这笔账只有 wait 能结。
      wait 0 有三种成因；127 = 不是我的孩子，1 = 号码不成话。disown = 放弃收尾权，进程照跑。
探活：kill -0 的 rc=1 有两种含义（没这个进程 / 有但轮不到你）；它答内核视角，僵尸也算「在」。
尺子：数并发只用 jobs -rp | wc -l，别 grep jobs 的文本；轮数、字节数、行数都要打在屏幕上。
重试：until = while not，条件里写的是「等到什么就算了」；必须同时写「最多等多久」。
      撞上界那一支要有自己的出口（非零退出／报警），否则「没起来」和「还在等」长得一样。
限流：三行：数闸门（起新任务**之前**、每轮重新数）→ 超了就 sleep 一下 → 再 & 起下一个。
      一定要 -r；一定要接住 wait -n 的返回值，否则失败的账没人记。对账永远拿串行版比。
成本：type -t 问循环体 —— builtin 一百万轮不 fork，file 每轮 fork+exec，keyword 不是命令；带路径就绕开内建。
进程：认自己用 $BASHPID，别用 $$；但 $(BASHPID) 量到的是命令替换自己 fork 出来的那个子进程。
证据：能复现的是计数、排序、布尔、退出码。pid、毫秒、轮询次数、并发完成顺序每跑必变 → 一律不上屏。
```

## 这章的坑（按代价从大到小）

1. **循环体偷吃 stdin**（第 13 节）。**症状**：4 行名单只跑 1 轮，退出码 0，不报错不警告；被吃掉的那几行常常从循环体那个命令的输出里冒出来。
   **根因**：`done < 名单` 这个重定向作用在**整个 while 语句**上，循环体继承同一个 stdin fd，体里任何会读标准输入的命令（`ssh`/`cat`/`gpg`/`mysql`/再 `read` 一次）都跟 `read` 抢同一份数据，而且**它先拿走**。
   **写法**：`cat` 后面补 `< /dev/null`（`ssh` 有自己的 `-n`）；体里真要塞 stdin 就用 fd 3（`exec 3<名单` + `read -u 3`）；最干净是 `mapfile` 进数组再 `for`。判据：把轮数打出来 —— 名单 4 行就该 4 轮。
2. **管道里的循环丢状态**（第 14、21 节）。**症状**：循环体明明加了 3 次，外面看 `n=0`；数组、`cd` 同理消失。
   **根因**：循环一进管道就是管道的一段 = 另一个进程，它写的是父进程内存的复印件。
   **写法**：先问「我需要把循环体里的状态带出来吗」，需要就别让它进管道 —— `while ...; done < <(命令)` 最稳；
   其次把结果变成输出用 `n=$(...)` 接住。`shopt -s lastpipe` 只救最后一段、还要求作业控制关着（非交互 bash 默认关着，交互终端默认开着），中间段照样丢。
3. **最后一行没换行被吞**（第 9、12 节）。**症状**：两份内容一样的文件，一份 3 轮一份 2 轮，`cherry` 一个字没被读到，退出码仍是 0。
   **根因**：`read` 的退出码问「撞没撞到分隔符」，那次内容到手了但撞到的是 EOF → 条件假 → 循环连门都不进。
   **写法**：`while IFS= read -r x || [ -n "$x" ]; do ...; done` —— 补在**条件里**，别补在循环外（补外面有换行的文件会多处理一遍）。
   合格判据：`last/with_nl.txt` 和 `last/no_nl.txt` 两份都得 3 轮。
4. **通配符没匹配到，把图案当文件**（第 5 节）。**症状**：`for f in nosuch*.txt; do rm "$f"; done` 一脸认真地报 `rm: cannot remove 'nosuch*.txt': No such file or directory`，循环跑了 1 轮。
   **根因**：默认档下 0 匹配 = **图案本身**变成一个词，「没文件」被伪装成「有个叫 `nosuch*.txt` 的文件」；而默认位是 off，等于什么都不做时走最危险那一档。
   **写法**：按文件名单干活就 `shopt -s nullglob`（→ 0 轮）；静默不可接受就 `failglob`（→ 展开阶段炸、整条命令行作废）；两个都不开就 body 第一步 `[ -e "$f" ]`。
5. **`&` 之后不 `wait`**（第 18、20 节）。**症状**：后台任务失败了，脚本照样退 0，你永远不知道。
   **根因**：`&` 之后那个 `$?` 是「起作业这条命令自己」的退出码（永远 0）；作业的码只有 `wait` 能拿到，不 `wait` 就是把失败咽下去。
   **写法**：`p=$!` 存下来、`wait "$p"` 接返回值（0／7／143 都是它的读数）；并发用 `wait -n || fails=$((fails + 1))`；
   再不然让作业自己把结果写进文件，外面数文件数（本章失败那一版：结果文件 5、抓到失败 1）。
6. **`{1..$N}` 一个字都不展开**（第 6、21 节）。**症状**：循环只跑 1 轮，`i` 是字符串 `{1..2000}`；`arr=({1..$N})` 的数组长度实测就是 1。
   **根因**：展开有固定顺序，花括号展开排在变量替换**前面**，轮到它时那个词还是 `{1..$N}`。
   **写法**：`for ((i = 1; i <= N; i++))`（零进程、零名单），或 `for i in $(seq 1 "$N")`（一个外部进程，但只起一次）。
7. **`for (( ))` 的变量出了循环还活着**（第 3、21 节）。**症状**：下一段复用同一个名字，接着上一个值往下跑；两层循环同名互踩。
   **根因**：bash 没有块作用域，循环变量就是普通 shell 变量 —— 带旧值进来、带最后值出去；算术循环出去的是「那个让条件终于不成立的值」（`i=3`、`x=2001`）。
   **写法**：不同循环用不同名字，或者把循环包进函数、`local i`；别拿「变量还在」当「循环跑了」的证据。
8. **`mapfile` 不带 `-t`，CRLF 的 `\r` 谁都不管**（第 15 节）。**症状**：元素尾巴上多一个看不见的字节（5 vs 6），后面比字符串全不相等 —— 「脚本在 Windows 生成的 CSV 上莫名对不上」。
   **根因**：`-t` 去掉的是**行尾分隔符**（`\n`），`\r` 不归它管。
   **写法**：`mapfile -t` + 整份先过一遍 `tr -d '\r'`，或者读完把行尾 CR 当后缀剪掉；
   剪之前先问清楚「我手里这个元素几个字节、尾巴上是什么」—— 本章自己剪错过一次（6 字节剪完还是 6 字节）。
9. **层数数错、`break 9`**（第 17 节）。**症状**：该跳出去的没跳出去，或者一批活静默没干；`break 9` 退出码 0、一行都没打。
   **根因**：bash 没有循环标签，`break N` 数的是层数；层数超出实际循环数不报错，只是把所有循环一次跳光。
   **写法**：数得清用 `break N`；数不清就把内层包成函数用 `return`（层数以后变了也不用改代码），或者置一个 flag 让外层条件去查。
   跳出来落在哪儿要自己证明：循环后面 `echo` 一句「有没有走到这里」。
10. **把 `wait` 返回 0 当「活干成功了」**（第 18 节）。**症状**：翻旧账那次也给你 0。
    **根因**：0 有三种成因 —— 真成功 ／ 已经 `wait` 过同一个 pid（它什么都没等）／ 作业表空时不带参数的 `wait`。
    **写法**：要么显式检查你 `wait` 的那个 pid，要么让作业自己写结果文件。顺带分清两种「没等到」：`127` = 不是我的孩子，`1` = 号码根本不成话。
11. **拿 `kill -0` 当唯一探活**（第 18 节）。**症状**：`rc=1` 就当「它退出了」，遇到权限类情况提前收工。
    **根因**：同一个 1 两种含义（没这个进程 ／ 有但轮不到你）；而且它答的是内核视角，僵尸也算「在」。
    **写法**：拿它当循环条件就把报错原文一起留着；能 `wait` 自己的 pid 就别轮询。
12. **把 `disown` 当「让进程更安全」**（第 18 节）。**症状**：`jobs`、`wait`、`%1` 全都看不见它了，进程照样活着。
    **根因**：`disown` 只动 bash 的作业表，不动内核进程表 —— 它是**放弃收尾权**。
    **写法**：要留长命进程就自己写 `trap EXIT` 交代清楚，别靠 `disown`；本手册的规矩是后台作业当场收尾。
13. **限并发闸门的三处细节**（第 20 节）。**症状**：并发压不下去、或者脚本卡住不动、或者失败的账没记上。
    **根因**：① 不用 `-r` → 已结束未回收的进程仍出现在 `jobs` 里，闸门被顶死；② 把 `running` 存进变量再比 → 那是上一轮的数；
    ③ 闸门里没有那一下 `sleep` → 每轮白 fork 一个 `wc`（`jobs` 是内建 0 个进程，`wc` 是外部 1 个），CPU 空轮换 0 点几秒的延迟。
    **写法**：数闸门（起新任务**之前**、每轮重新数）→ 超了就 `sleep` → 再 `&`；有 `wait -n` 就别轮询。对账永远拿串行版比。
14. **把 `select` 放进会被自动跑的脚本**（第 16 节）。**症状**：CI／cron／管道里跑，循环一次都不跑，退出码还是 1（`set -e` 当场算失败）。
    **根因**：`select` 读的就是 stdin，没人喂就撞 EOF；菜单和 `PS3` 走 stderr，随手一句 `2>/dev/null` 会把整个菜单抹光，看着像卡死。
    **写法**：每条 `select` 自带输入；判据自己写（变量为空 = 没选上）+ 重试上界；真正的选择做成参数，`select` 只当交互糖衣。
15. **把 `read -t` 的 142 和 EOF 的 1 当同一件事**（第 11、19 节）。**症状**：重试环提前放弃。
    **根因**：142 = 128 + SIGALRM 是「还没好」，1 是「没有了」，`while read` 只看这一个码决定进不进。
    **写法**：按这两个码分派；重试环两半（等什么 + 最多等多久）一起写，撞上界那一支要有自己的出口。
16. **`read` 少写 `IFS=` 或少写 `-r`**（第 10、11 节）。**症状**：首尾空白和连续空白没了；`a\\b` 变成 `a\b` 少一个字节，后面 `rm`／`cp` 动到一个根本不存在（更糟：恰好存在）的名字。
    **根因**：默认 `read` 按 IFS 拆词并把反斜杠当转义符消费掉。
    **写法**：读行统一 `IFS= read -r`；想拿整行只这一条。字段数还要自己对齐列数 —— 源里列数变了不报错，只会让最后一个变量默默变长。
17. **不带引号地遍历数组**（第 7 节）。**症状**：元素数量从 3 变 4，没有任何警告；带通配字符的名单被悄悄换成别的文件。
    **根因**：`${arr[@]}` 先取元素再走一遍词分割，切完**还再做一次通配展开**。
    **写法**：`"${arr[@]}"` 是唯一写法；`${arr[*]}` 只适合打印；`${#arr[@]}` 数的是元素个数，不受引号影响 —— 所以「3 个元素、4 个词」只能靠遍历本身暴露。
18. **循环里放外部命令，或者用 `$(BASHPID)` 问自己在哪**（第 2、21 节）。**症状**：一百万轮就是百万次 fork+exec；或者「我在哪个进程」永远答「不是」。
    **根因**：`type -t` 给 `file` 的每轮起进程（写绝对路径 `/bin/true` 会从 `builtin` 掉回 `file`）；而命令替换**本身**就是一个子进程。
    **写法**：调循环第一步不是加 `time` 是 `type -t` 问一遍循环体；要问主 shell 的 pid 就在主 shell 里当场比。

## 自检问题

1. `for f in snap/*.txt` 的循环体里 `rm` 掉当前文件、又新建一个 `.txt`：新来的会被处理吗？已删的还会轮到吗？该在 body 里补哪一句？（答：新来的本轮看不见、下一轮 `for` 才看见；已删的照样轮到 —— 词表是名字的快照不是存在性的快照，body 第一步 `[ -e "$f" ]`；第 4 节）
2. 匹配不到文件时三档各是什么后果？哪一档真给了非零退出码？（答：默认 = 图案原样进循环跑 1 轮；`nullglob` = 0 轮退出码 0；`failglob` = 展开阶段炸、同一条命令行的后续 `echo` 也没机会跑，是 957 行捕获里唯一一格非零总结行；第 5 节）
3. `{1..$N}` 为什么只跑一轮？按变量生成序列的两条写法各起几个进程？（答：花括号展开排在变量替换之前；`for (( ))` 零进程且没有名单，`$(seq 1 "$N")` 起一个外部进程但只起一次；第 6、2、21 节）
4. `for ((i=0;i<3;i++))` 结束后 `i` 是几？`for x in a b c` 结束后 `x` 是什么？循环跑了 0 轮时退出码是几？（答：`i=3`（先加到 3 再判失败）、`x=[c]`；0 轮仍是退出码 0，`$?` 分不开「跑完」和「没跑」；第 3、8 节）
5. 19 字节那份文件 `while read` 为什么少跑一轮？唯一值得背的修法写在哪？合格判据是什么？为什么别在循环外拿那个变量收尾？（答：`read` 的码问撞没撞到分隔符；`|| [ -n "$x" ]` 补在**条件里**；两份文件都得 3 轮；最后一次失败的 `read` 会把变量清空，第 21 节那格就是 `[]`；第 9、12、21 节）
6. `wc -l` 为什么在这个场景骗人？哪一族工具不骗？（答：它数的是换行符个数；`awk`、`grep -c ""` 按记录切行，末行没换行照样算；比内容用 `cmp`、比大小用 `wc -c`；第 12 节）
7. `while read host; do ssh "$host" uptime; done < hosts.txt` 只连了 1 台的根因是什么？三条修法按侵入性排一遍，各用在什么场合？（答：`done <` 作用在整个 while 语句上，体里的命令跟 `read` 共用同一个 fd 且先拿走；`< /dev/null`（`ssh -n`）最省事、fd 3 分离留给体里真要塞 stdin、`mapfile` + `for` 最干净但吃内存；第 13 节）
8. 管道里的 `while` 为什么把 `n` 丢了？`lastpipe` 的两个前提是什么？哪两条接回办法不依赖开关？（答：那一段是另一个进程；`lastpipe` 只救最后一段且要求作业控制关着；`n=$(...)` 走 stdout、`while ... done < <(...)` 不走管道；第 14 节）
9. 怎么**亲眼**证明循环体在不在本进程？为什么 `pa=$(BASHPID)` 拿不到主 shell 的 pid？（答：在循环体里比 `[ "$BASHPID" = "$$" ]`；命令替换本身就 fork 一个子进程，量到的是它；第 21 节）
10. `mapfile` 的 `-t -s -n -O -d` 各管什么？为什么那 4 个文件名必须用 `< <( )` 读而不是 `find ... | mapfile`？CRLF 怎么办？（答：去行尾／跳／限量／偏移／换分隔（`-d ""` = NUL）；管道会让 `mapfile` 落在子进程里，上一版量到 0 个；`-t` 只吃 `\n` 不管 `\r`；第 15 节）
11. `select` 喂不到输入时跑几轮、退出码几？菜单和 `PS3` 走哪个流？非法输入（包括按名字）会报错吗？（答：0 轮、退出码 1；stderr；不报错，只把变量赋成空串 —— 判据只有「变量为空 = 没选上」；第 16 节）
12. `break 2` 和 `continue 2` 各做什么？`break 9` 只有两层循环时会报错吗？数不清层数怎么办？（答：穿两层／把外层推进下一轮；不报错，退出码 0、所有循环一次跳光；包成函数用 `return` 或置 flag；第 17 节）
13. 后台作业退出码的唯一通道是什么？`wait` 返回 0 的三种成因？`127` 和 `1` 分别说明什么？`143` 是怎么算出来的？（答：`wait`；真成功／翻旧账／作业表空；不是我的孩子／号码不合法；`128 + 15`（SIGTERM）；第 18 节）
14. `disown` 之后 `jobs`、`wait`、`kill -0` 各看到什么？数并发该用哪一把尺，为什么？（答：表里 0 行／无参 `wait` 回来它还在跑／还活着；`jobs -rp | wc -l` —— `-r` 滤掉已结束的、`-p` 一行一个 pid，跟排版无关；第 18、20 节）
15. 重试环的条件里必须一起写的两半是什么？为什么不能拿循环退出码当「等到了」？撞上界那一支必须有什么？（答：等什么 + 最多等多久；0 轮也退 0，bash 不替你报错；要有自己的出口（非零退出／报警）；第 19 节）
16. 限并发的最小正确写法是哪三行？并发版的合格判据是什么？本章能复现的成本读数是哪一个，为什么没有毫秒？跑过东西的脚本要自证哪两件事？（答：数闸门 → 超了就睡一下 → 再 `&`；和串行版同一份对账（结果文件数、失败数）；是「不同 pid 个数 1 vs 50」「数组元素个数」这类计数，毫秒每跑必变；落了什么文件 + 留了什么进程；第 20、21、22 节）

## 术语小抄

| 术语 | 一句话（本章的用法） |
| --- | --- |
| 词表 ／ 快照 | `for` 在进循环之前展开出来的那排词。它是**名字**的快照，不是存在性的快照，生命周期只有一轮 `for` |
| 通配三态 | 默认（图案原样）／`nullglob`（展开成空）／`failglob`（当场炸），区别就是「0 个匹配」在你的业务里算不算正常 |
| 花括号展开 | `{1..20}` 那一步，排在变量替换**前面**，所以永远看不到变量的值 |
| 算术上下文 | `for (( ))` 的三段：直接写变量名、不用 `$(( ))`、只认整数（小数是语法错误） |
| IFS ／ 词分割 | 不带引号的展开按它切词；空白类（空格 tab 换行）连续算一刀并剥首尾，非空白类逐个字符算、不折叠 |
| `"${arr[@]}"` | 每个元素各成一个词的唯一写法。`${arr[@]}` 会被二次切开，`${arr[*]}` 拼成一个词，`${#arr[@]}` 数元素个数 |
| 块作用域 | bash 没有。`for`／`while`／`if` 都不开新作用域，循环变量就是普通 shell 变量 |
| `read` 的退出码 | 「这次撞没撞到分隔符」。空行 0、EOF 1、超时 142 —— 与「有没有拿到内容」无关 |
| `REPLY` | `read` 不点变量名时的容器；`select` 也用它装你敲进去的那一行原始字符（编号在它那儿） |
| 流式读 ／ 一次读全 | `while read` 任意时刻只有一行在变量里；`mapfile` 把整份输入同时握在数组里 |
| 偷吃 stdin | 循环体里的命令和 `read` 共用同一个 fd，把名单剩下的部分端走 |
| fd 3 分离 | `exec 3<名单` + `read -u 3`：一个 fd 干一件事，stdin 留给循环体 |
| 管道最后一段 | `lastpipe` 只把那一段搬回当前 shell，且要求作业控制关着（`set +m`）；中间段的赋值照样丢 |
| `<( )` ／ `< <( )` | 前者给的是一个 `/dev/fd/N` **名字**，后者才真的接进 stdin。`mapfile`、`while read` 要的是后者 |
| `-d ""` | `read` ／ `mapfile` 的「分隔符 = NUL」写法，配套的是 `find -print0` |
| `PS3` | `select` 的提示符，**全局变量**，设一次跟着后面每一个菜单（默认 `#? `） |
| `break N` ／ `continue N` | 往上穿穿 N 层 ／ 把第 N 层推进下一轮。bash 没有循环标签，层数写超不报错 |
| 作业表 | bash 自己那张「我起了哪些后台」。`jobs`／`wait`／`%1` 都读它，`disown` 从它上面撕一行 |
| `$!` | 最后一个后台作业的 pid。不存下来，之后就再也指不到它 |
| `jobs -rp \| wc -l` | 「还在跑的个数」= 数并发唯一的尺：`-r` 滤掉已结束的，`-p` 一行一个 pid |
| `wait` ／ `wait -n` | 等指定的作业 ／ 等**任意一个**结束就走；`wait -n` 还顺手回收它并返回它的退出码 |
| `disown` | 放弃收尾权：作业表里没了，进程照跑。不等于「更安全」 |
| `kill -0` | 不投递信号的探活。`rc=1` 有两种含义；它答内核视角，僵尸也算「在」 |
| 僵尸（未回收） | 已退出、父进程还没 `wait` 的那段时间；它仍出现在 `jobs` 里，所以闸门必须带 `-r` |
| 闸门 ／ 并发峰值 | 起新任务**之前**数一次「还在跑几个」；峰值 = 你实际同时放出去的进程数 |
| 上界 | 重试环的后半句「最多等多久」。只写「等什么」就是死循环 |
| `type -t` → builtin／keyword／file | 内建在当前进程里跑（不 fork）；关键字不是命令；外部程序每轮一次 fork+exec |
| `$$` ／ `$BASHPID` | 前者在子 shell 里仍是父进程的 pid；后者才是本进程的真实 pid —— 但 `$(BASHPID)` 又绕回去了 |
| 每跑必变 | pid、毫秒、轮询次数、并发完成顺序、端口号 —— 本章一律不上屏，改写成「相等吗／几个／有没有」 |
| 沙箱 | `${TMPDIR:-/tmp}` 下 `bash05-XXXXXX` 那一个目录，`trap cleanup EXIT` 整份删；仓库目录全程只读 |

## 本章之后

- **下一章 `06 functions-and-returns`**：本章第 17 节给的那条出路 ——「数不清层数就把内层包成函数用 `return`」——
  它的账要到那里才结清：`return` 只能交出一个退出码（就是第 03 章那套 0~255），想把**数据**带出去只有两条路，
  走 stdout 再用命令替换接住，或者写一个全局变量（那就得先弄明白第 14 节那个「复印件」什么时候会变成原件）；
  再加上 `local` 到底把谁关在函数里、递归的深度、以及函数怎么接住信号。
  本章刻意把 `lookup()` 那一格停在「函数退出码=0」，那个 0 后面能装多少东西，是下一章的正题。
- **往后的那条健壮性线**（`set -euo pipefail`、`trap`、`mktemp`、`getopts`、锁与幂等）：本章欠了三句 ——
  第 16 节的「真正要选就用参数」、第 20 节的「多个 writer 抢同一个文件时怎么办」、第 22 节的「为什么生产脚本必须加 `set -e`」，都在那里结。
- **外部工具那一章**：第 21 节数到的 3000 行那份文件是 `awk` 生成的，而本机 `awk` 是 **mawk 1.3.4** 不是 gawk；
  「循环里放 `grep`／`sed`／`awk` 就是每轮一次 fork+exec」这笔账，到那一章才换成「什么时候该把整件事交给它一次做完」。

**本章回指**：第 02 章的「展开有固定顺序」在第 6、21 节的 `{1..$N}` 上兑现成一次都不展开；
第 03 章的「一句话只有一个退出码」在第 9、11、18 节长成三种数（1、142、143）；
第 04 章的「管道每一段都是自己的进程」「私有 fd 3」「SIGPIPE = 141」分别在第 14、13、6 节各兑现一次 ——
本章没有新添规矩，只是把那三条放进循环里，让它们**跑很多轮**之后才现形。
