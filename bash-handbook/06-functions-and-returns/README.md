> 这一章只管三件事：**函数能交回来的那个数是怎么算出来的**、**函数体里的名字归谁**、
> **这个名字在哪个进程里存在**。

> 这台机器的底细：bash 5.3.9(1)-release，`/bin/sh` 的真身是 `/usr/bin/dash`，没装 `shellcheck`，
> demo 一进来就把自己钉成 `LC_ALL=C.UTF-8`，所以 **bash 的报错全是英文原文**（第 1 节当场钉给你看）。

## 本章在讲什么，以及为什么是这三条

前两章的读者已经拿到两条规矩：**每句话只有一个退出码**（第 03 章）、
**展开与词表是看不见的手**（第 02、04 章）。把这两条塞进函数，就会长出三个反直觉：

> **一、函数没有「返回值」，只有 0~255 的退出码。** `return` 后面那个数只保留低 8 位，
> 写 300 得 44、写 256 得 0（★ 把失败伪装成成功）、写 -1 得 255。想带回**数据**只能走 stdout，
> 而命令替换会交出四刀：尾部换行全吃光、多值只剩一坨文本、诊断一句就污染、副作用出不了子 shell。
>
> **二、函数体里的名字是动态作用域。** 同一个 `x`，漏写 `local` 改的就是调用者那个变量；
> 被调用者读到什么、改掉谁的，取决于「谁调了它」，跟函数写在哪儿无关。
> 这是本章最容易长出线上事故的地方 —— 它不报错，它只是把你的结果送到别处去。
>
> **三、函数是当前 shell 名字表里的一个条目，不是磁盘上的文件。** 换个新进程（`bash -c`）就看不见它；
> `export -f` 传的是「导出那一刻的文本快照」，不是活引用。它还会排在内建和 PATH 前面 ——
> 一个同名函数能把 `ls`、`true` 整个换掉，而且一句报错都没有。

三条各成套，所以本章的排版也是三条线：第 2~10 节走**码与文本**（`return` 的规矩、命令替换的四刀、
三条通道怎么分、`return` 与 `exit` 在 trap 与 source 里的下场）；第 11~13 节走**作用域**；
第 14~20 节走**身份与可见性**（定义顺序、`type` 的分类、遮蔽与夺回、跨进程、参数从哪来）；
第 21~24 节把三条线拧成一个能抄的库、对账、自证。

| 你想搞清楚的东西 | 本章用哪一节回答 | 一句话答案 |
|---|---|---|
| 这些结论换台机器还成立吗 | 第 1 节 | 先钉 bash 版本与语言环境：报错原文和「数几个字符」都跟着它走 |
| 函数到底能「返回」什么 | 第 2 节 | 只有一个小整数；变量默认改外面那个；换个进程就不认识这个名字 |
| `return` 后面能写什么、写 300 会怎样 | 第 3 节 | 不报错，折成 44；写 `abc` 才报错且退 2；`return` 之后的句子一句都不跑 |
| 不写 `return` 的函数有没有码 | 第 3 节 | 有，等于体里**最后执行的那条命令**；中间挂掉的一步会被后面的 `echo` 洗掉 |
| `exit` 和 `return` 该用哪个 | 第 3、9 节 | `return` 结束这次调用、脚本继续；`exit` 结束整个 shell，连调用方一起没 |
| 调用完之后码还保得住吗 | 第 3、7 节 | `v=$(f)` 保得住（实测 3），`local v=$(f)` 当场被 `local` 吞成 0 |
| 退出码的上限是多少 | 第 4 节 | 只留低 8 位：256→0、511→255、512→0、-1→255、-2→254 |
| 命令替换会对我的输出做什么 | 第 5 节 | 四刀：尾换行全吃、多值只剩一坨文本、诊断污染、副作用出不了子 shell |
| 函数多打一个空行为什么拿到空串 | 第 6 节 | 一个尾换行和三个尾换行的捕获结果一模一样；只打空行就是长度 0 |
| 诊断该写 stdout 还是 stderr | 第 5、7 节 | 给人看的一律 `>&2`；漏一句，比较、算术、取首行、判空同时中招 |
| 想只捞 stderr 怎么写 | 第 7 节 | `err=$(f 2>&1 >/dev/null)`，顺序不能反（实测 17 字符对反写 0 字符） |
| 函数到底「返回了什么」 | 第 8 节 | 这句问法本身是错的：判成败看码，拿数据看文本，两套并行且互不解释 |
| 函数外面写 `return` 会怎样 | 第 9 节 | 报英文原文但不拦路：前后两句照打，脚本整体退 0 |
| `RETURN`/`DEBUG` trap 会不会替我盯函数 | 第 9 节 | `functrace` 默认不开：函数返回触发 0 次，source 结束反倒算 1 次 |
| 为什么这些脚本都不写 `set -e` | 第 10 节 | 第二条命令一失败整个脚本当场结束（实测退出码 1），而它在 `\|\|` 左边根本不管制 |
| `local` 挡的是谁 | 第 11 节 | 只在函数活着的那段时间挡全局；漏写的一句就把名字扔进公共命名空间 |
| 为什么下层函数改得到我的局部 | 第 11 节 | 作用域按调用栈找，不按定义位置找 —— 这就是动态作用域 |
| `if`/`for` 的花括号算不算一个作用域 | 第 12 节 | 不算：`t` 出了 `if` 还在、`u` 出了 `for` 还在；`local` 划的圈是这次函数调用 |
| 递归为什么必须把中间变量全 `local` | 第 13 节 | 漏一个，4! 实测算成 1；深度只能靠栈扛（不设 `FUNCNEST` 撞段错误 rc=139） |
| 递归有多贵 | 第 13 节 | 用计数不用耗时：`fib 10` 结果 55、函数被进入 177 次 |
| 函数定义在调用之后行不行 | 第 14 节 | 行：名字是调用那一刻才查的；同名重定义直接盖掉且不报错 |
| 我调的这个名字到底是谁 | 第 15 节 | 顺序是函数 > 内建 > PATH 里的文件；查身份只有 `type -a` 一次给全 |
| 被自己的函数遮蔽了怎么夺回来 | 第 16 节 | 三条急救：`command`、`builtin`、写绝对路径 |
| 函数能不能跨进程 | 第 17 节 | 默认不能；`export -f` 把文本塞进环境变量，键名 `BASH_FUNC_名字%%` |
| 「看不见」会不会是我守卫坏了 | 第 18 节 | 先弄响再报 0：不导出时同名条目数 0，导出后 1；孙子进程实测退 127 |
| 函数里的 `$1` 是从哪来的 | 第 19 节 | 位置参数是每次调用临时换上的一组，脚本级那组在函数里看不见 |
| 包装函数怎么转发参数 | 第 20 节 | 只有 `"$@"`：空串也占一格（实测 $#=3），`"$*"` 会粘成一坨 |
| 有没有一个能直接抄的库 | 第 21 节 | 有 `lib/fnlib.sh`：日志走 stderr、失败用 `return`、中间变量 `local`、转发用 `"$@"` |
| 同一份库换个 shell 会怎样 | 第 22 节 | dash 不认 `export -f`（`Illegal option -f`，退 2），也没有 `declare`（退 127） |
| 本章一共演了多少东西 | 第 23 节 | 九个辅助脚本合计 64 格、demo 自己 24 节、九脚本源码 1249 行 |

## 1. 先把这台机器的发言权确认一遍

这一节钉的是**后面 23 节每一行的落脚点**：这一章的结论有两个变量会要它的命 ——
bash 的版本（`export -f`、`declare -f`、`FUNCNEST`、RETURN trap 到底存在不存在、行为长什么样），
和语言环境（报错原文是英文还是中文、字符到底按什么数）。所以第一步不讲道理，先把这两件事钉死。

```
$ bash --version | head -1
GNU bash, version 5.3.9(1)-release (x86_64-pc-linux-gnu)
[退出码 0]

$ echo "demo 已把自己改成：LC_ALL=[$LC_ALL] LANG=[$LANG]（你原来的终端是 LANG=$ORIG_LANG，LC_ALL=$ORIG_LC_ALL）"
demo 已把自己改成：LC_ALL=[C.UTF-8] LANG=[C.UTF-8]（你原来的终端是 LANG=zh_CN.UTF-8，LC_ALL=（未设））
[退出码 0]
```

↑ 第二格不是走过场：你原来的终端是 `zh_CN.UTF-8`、`LC_ALL` 没设，demo 一进来就把自己和它
fork 出来的子进程全改成 `LC_ALL=C.UTF-8 LANG=C.UTF-8`。为什么要改：**换语言环境等于换一本报错词典**，
bash 找不到命令时报 `command not found` 还是报中文，全看这一档；本章后面那些英文原文
（`return: can only ...`、`local: can only be used in a function`、`maximum function nesting level exceeded`）
能逐字核对，前提就是这一格被钉住。

同一份文本，换 locale 连「有几个」都会变，所以先把读数口径钉下来：

```
$ f(){ echo 一二三; }; v=$(f); printf "  同一个函数返回值，本机数出来的字符数=%s（本章只报这一档）\n" "${#v}"
  同一个函数返回值，本机数出来的字符数=3（本章只报这一档）
[退出码 0]
```

**直觉以为「一个汉字算一个还是按字节算都行，反正固定」**：屏幕上这一档给的是 **3**，
`${#v}` 数的是**字符**，而它数得动字符靠的就是 locale 被钉在 UTF-8 上；换成按字节数是另一个数。
这就是为什么本章只报「本机数出来的这一档」—— 后面所有「字符数=19」「长度=4」都是这个口径。

然后是本章主线③的地基：函数在这张表里到底算什么。12 个名字挨个问一遍：

```
$ for c in echo printf local declare set jobs type true not-a-name grep sed awk; do printf "  %-9s type -t → %s\n" "$c" "$(type -t "$c" 2>/dev/null || echo 查无此名)"; done
  echo      type -t → builtin
  printf    type -t → builtin
  local     type -t → builtin
  declare   type -t → builtin
  set       type -t → builtin
  jobs      type -t → builtin
  type      type -t → builtin
  true      type -t → builtin
  not-a-name type -t → 查无此名
  grep      type -t → file
  sed       type -t → file
  awk       type -t → file
[退出码 0]
```

读法：`for` 里点了 12 个名字，屏幕就 12 行，分成三档 —— **8 个 `builtin`**
（`echo` `printf` `local` `declare` `set` `jobs` `type` `true`）、**3 个 `file`**（`grep` `sed` `awk`）、
**1 个查无此名**（`not-a-name`：`type -t` 查不到返回空，那一列的「查无此名」是脚本自己补的字）。

**直觉以为「函数是 shell 里的另一种东西」**：屏幕上它就跟 `echo`、`grep` 一样，是这张名字表里的一行，
`type -t` 给它那一档叫 `function`（第 15 节实测）。既然只是表里的一行，就长出两个后果：
这张表**每个进程各有一份**（第 17、18 节），以及**同名就能盖掉**（第 15、16 节）。

本章第 9 节要用三个「关」，先记下此刻的位置：

```
$ for o in errexit pipefunctrace functrace xtrace verbose; do printf "  %-12s %s\n" "$o" "$(set -o 2>/dev/null | awk "\$1==\"$o\"{print \$2}")"; done
  errexit      off
  pipefunctrace 
  functrace    off
  xtrace       off
  verbose      off
[退出码 0]
```

**直觉以为「函数返回时 bash 默认会用 RETURN trap 替我盯着」**：屏幕上 `errexit`、`functrace`、`xtrace`、
`verbose` 四个全是 `off`，而 `pipefunctrace` 那一格是**空的** —— 这台 bash 的 `set -o` 清单里就没有这个名字，
那一列是拿 `awk` 按第一列去匹配、没匹配到就打印空，所以「空」不等于「关」，是「查不到」。
`functrace` 默认 off 的代价第 9 节给了数：关着时**函数返回一次都不触发**（实测 0 次）。

再钉两个天花板，第 13 节的递归全压在这两行上：

```
$ printf "  FUNCNEST=[%s]（未设=只受栈限制，第 13 节会把它设成 10 看拦截）\n" "${FUNCNEST-未设}"
  FUNCNEST=[未设]（未设=只受栈限制，第 13 节会把它设成 10 看拦截）
[退出码 0]

$ printf "  ulimit -s（栈 KB）=%s ｜ 它是本机固定参数，不是每跑必变的量\n" "$(ulimit -s)"
  ulimit -s（栈 KB）=8192 ｜ 它是本机固定参数，不是每跑必变的量
[退出码 0]
```

**直觉以为「递归有个默认深度上限」**：屏幕上 `FUNCNEST` 是「未设」，也就是 bash 不拦你，
深度只由 8192 KB 这块栈扛 —— 第 13 节实测不设就往栈上撞，崩掉的那个进程退出码 **139**。

最后两格决定本章的取证方式，也决定第 22 节那堵墙：

```
$ printf "  /bin/sh 的真身=%s\n" "$(readlink -f /bin/sh)"; echo "  ★ 第 22 节要让同一个函数库去撞一下它"
  /bin/sh 的真身=/usr/bin/dash
  ★ 第 22 节要让同一个函数库去撞一下它
[退出码 0]
```

```
$ command -v shellcheck >/dev/null 2>&1 && echo "shellcheck 在" || echo "shellcheck 本机没有 —— 本章不装东西，脚本只能靠逐条真跑来验"
shellcheck 本机没有 —— 本章不装东西，脚本只能靠逐条真跑来验
[退出码 0]
```

`/bin/sh` 的真身是 `/usr/bin/dash`，这意味着本章里凡是「换个 shell 跑同一份定义」的实验，对手就是 dash；
`shellcheck` 没装，本章也不装东西，所以每条结论都是真跑出来的，不是静态检查器给的。

**这一节带走：**

- 本章每个结论都挂在 **bash 5.3.9 + `LC_ALL=C.UTF-8`** 上；换机器或换 locale，报错那一列得重新取证。
- 「数几个字符」是 locale 决定的读数，本机口径是**字符数**（`一二三` → 3）。
- 函数只是名字表里的一档（`type -t` 答案之一）：12 个名字问出 8 builtin / 3 file / 1 查无此名。
- `errexit`、`functrace`、`xtrace`、`verbose` 默认全 off；`FUNCNEST` 未设、栈 8192 KB、`/bin/sh` 是 dash。
- 围栏最后一行的 `[退出码 N]` 是 demo 给这一串命令的总结行，不是某一句输出自己的内容。

## 2. 一张地图：三条主线各一条最小证据

这一节钉的是**整章的形状**：三条主线各一条最短的证据，每条都是一行你能自己复现的命令。
后面 22 节做的事，就是把这里三行放大成「为什么屏幕上只有这个数」。

主线①，函数能交回来的只有一个小整数：

```
$ f(){ return 42; }; f; code=$?; printf "  只写 return 的函数，外面拿到的是数字 %s（它和 \$? 是同一条线）\n" "$code"
  只写 return 的函数，外面拿到的是数字 42（它和 $? 是同一条线）
[退出码 0]
```

屏幕上为什么是 42：函数体里只有 `return 42`，`f` 这次调用结束时 bash 把 42 交给 `$?`，
脚本紧接着用 `code=$?` 接住再打印 —— 全程没有第二个命令参与。所以那句「它和 `$?` 是同一条线」
不是比喻：**42 只能住在这一个字节宽的通道里**。而这一格外层的 `[退出码 0]` 是最后那句 `printf` 的 0，
不是 `f` 的 42 —— 两个数在同一格里和平共处，第 3 节整节就在算这笔账。

主线②，函数体里的赋值默认改的是外面那个变量：

```
$ x=外面; f(){ x=里面; }; f; printf "  调用一次之后，外面的 x=%s（函数没有把变量藏起来）\n" "$x"
  调用一次之后，外面的 x=里面（函数没有把变量藏起来）
[退出码 0]
```

**直觉以为「`f` 里的 `x` 是 `f` 自己的变量」**：屏幕上外面那个 `x` 直接变成了「里面」。
这一格没有任何看不见的手：`x=里面` 就是一条普通赋值，函数体不是一个隔离区。
要不要把名字留在函数里，只有一个开关能做（`local`，第 11 节整节）。

主线③，函数活在当前这个 shell 的表里，不在磁盘上：

```
$ f(){ echo 在里面; }; bash -c "f"; echo "  ★ 上面那句是 bash 自己的原话，同一个名字换个进程就不认识了"
bash: line 1: f: command not found
  ★ 上面那句是 bash 自己的原话，同一个名字换个进程就不认识了
[退出码 0]
```

**直觉以为「函数定义在这个脚本里，脚本起的子进程自然也能调它」**：屏幕上第二行就是 bash 自己的原话，
而且是**英文**的 —— 这正是第 1 节那格 `LC_ALL=C.UTF-8` 换来的东西。
`bash -c "f"` 起的是一个全新进程，那张函数表从零开始，`f` 不在里面，于是这个名字连「被当成函数」的
机会都没有，只能按命令去找、找不到。
这一格最容易误读的是它末尾的 `[退出码 0]`：那句报错自己是 127（第 17 节里同一个形状的调用实测就是 127），
只是最后那句 `echo` 成功了，demo 的总结行才显示 0 —— 屏幕上「有报错」和「这一串最后是 0」并不矛盾。

三格连起来读，就是本章要立起来的三句话：**码只有一个字节宽**、**函数体里的名字沿调用栈走**、
**函数只是一个进程的名字表里的条目**。三条各自的代价，下面三节开始一条一条付。

## 3. retcode.sh 完整跑：return 后面能写什么

这一节钉的是**退出码这条通道的全部规矩**：能写什么、越界怎么写、不写怎么办、`return` 与 `exit` 的分工、
以及「调用完之后码还在不在」。`retcode.sh` 一共 7 格（第 23 节对账时它的格数就是 7），一次跑完，逐格读。

第 1 格，`return` 后面能写什么，五个写法各跑一次：

```
$ bash retcode.sh
=== 1. return 后面能写什么：五个写法各跑一次（bash 原文照打） ===
  return 0     → $?=0    ｜ 是不是 0 → 是 ｜ 除了退出码还有什么：（一句报错都没有）
  return 42    → $?=42   ｜ 是不是 0 → 否 ｜ 除了退出码还有什么：（一句报错都没有）
  return 300   → $?=44   ｜ 是不是 0 → 否 ｜ 除了退出码还有什么：（一句报错都没有）
  return -1    → $?=255  ｜ 是不是 0 → 否 ｜ 除了退出码还有什么：（一句报错都没有）
  return abc   → $?=2    ｜ 是不是 0 → 否 ｜ 除了退出码还有什么：bash: line 1: return: abc: numeric argument required
  → 直觉以为「写 300 会报错」：实测一句报错都没有，它只是被折成了 44；
    真报错的只有 abc（需要数值参数）。而且 bash 一报错就把那次调用当场结束，
    函数体里剩下的句子一句都不跑，退出码停在 2 —— 这个 2 是「内建命令用法不对」的固定码，不是你写的那个数。
```

屏幕上为什么是这些数：`0` 和 `42` 是原样交回来的；`300` 变成 **44**、`-1` 变成 **255**，
因为它只保留低 8 位（300 减掉一个 256 就是 44）；`abc` 那一格给的 **2** 不是你写的数，
是 bash 那句「需要数值参数」的英文报错对应的**内建用法错误固定码**。

**直觉以为「写 300 这种越界的数会被 bash 拦下来报错」**：屏幕上五个写法里只有一句报错，就是 `abc` 那格；
`300` 和 `-1` 一句抱怨都没有，只是悄悄折了。更狠的是报错那一格的后半段：bash 一报错就把**这次调用当场结束**，
函数体里剩下的句子一句都不跑 —— 这件事你在第 9 节会再撞一次（`return` 写在函数外面报错时，反而是「报完照样往下跑」）。

第 2 格，把「只保留低 8 位」当场对账，7 个输入：

```
=== 2. ★ 退出码只保留低 8 位：256 和 258 当场对账 ===
  return 255    → $?=255  ｜ 和 255 % 256 = 255  相等吗 → 相等
  return 256    → $?=0    ｜ 和 256 % 256 = 0    相等吗 → 相等
  return 257    → $?=1    ｜ 和 257 % 256 = 1    相等吗 → 相等
  return 258    → $?=2    ｜ 和 258 % 256 = 2    相等吗 → 相等
  return 300    → $?=44   ｜ 和 300 % 256 = 44   相等吗 → 相等
  return 512    → $?=0    ｜ 和 512 % 256 = 0    相等吗 → 相等
  return 99999  → $?=159  ｜ 和 99999 % 256 = 159  相等吗 → 相等
  → 一句话：退出码是一个字节（0~255）。256 → 0、257 → 1、258 → 2、300 → 44、-1 → 255。
  ★ 256 那一格最阴：你本想「返回 256」表达某个状态，$? 却变成 0，
    调用方那句 if f; then 一路绿灯 —— 这不是无害的截断，是把失败伪装成了成功。
```

屏幕上为什么是这些数：右边那列 `N % 256` 是脚本自己算的期望值，左边是 bash 实测的 `$?`，
7 行全部「相等」—— 255→255、256→0、257→1、258→2、300→44、512→0、99999→159。
**直觉以为「返回 256 至少算『另一个状态』」**：屏幕上 256 那一格给的是 **0**，
调用方那句 `if f; then` 一路绿灯。这条线真正的危险不是截断，是**把失败伪装成成功** ——
而 0 恰好是「成功」的唯一写法。

第 3 格，`return` 的三个边角：

```
=== 3. return 的三个边角：它之后的句子、空的函数体、写在函数外面 ===
  f(){ return 7; echo 这句; } → 调用后收到的字符数=0（0 = return 之后的话压根轮不到说）
  函数体里只写一条 : （空操作）→ 退出码=0 ← 想「什么都不干」只能这么写
  函数体一个字符都不留（e(){ }）→ 退出码=2，原文：
    bash: -c: line 1: syntax error near unexpected token `}'
    bash: -c: line 1: `e(){ }'
  在函数**外面**写 return 3 → 退出码=2，原文：
    bash: line 1: return: can only `return' from a function or sourced script
  → 最后那条原文里的「被 source 的脚本」是关键：source 进来的脚本就是当前 shell 自己，
    所以那里能 return；用 bash 跑起来的脚本是一个独立进程，它没有「调用方的函数」可回，只能 exit。
```

四件事分开解释：
① `f(){ return 7; echo 这句; }` 捕获到的**字符数=0** —— 那个 0 不是「echo 打了行空白」，
是 `echo` 压根轮不到执行：`return` 一交码，这次调用就结束了。
② 函数体里只写一条 `:`（空操作）→ 退出码 **0**，因为 `:` 是内建、永远成功。
③ 函数体一个字符都不留（`e(){ }`）→ bash 连语法都不认，直接甩出 `syntax error near unexpected token` 那两行原文，
外层码 **2**：想「什么都不干」在 bash 里不是一个合法形状。
④ 最后一格最有用：**在函数外面**写 `return 3` → 码 **2** 加那句英文原文，原文里出现的词是
「被 source 的脚本」—— 那五个字是第 9 节的入口：`source` 进来的文件就是当前 shell 自己，那里能 `return`；
用 `bash` 跑起来的脚本是独立进程，它没有「调用方的函数」可回，只能 `exit`。

第 4 格，不写 `return` 的函数到底交回什么：

```
=== 4. 不写 return 的函数：退出码 = 最后执行的那条命令（下面用一条一定失败的 ls 当证据） ===
  下面紧跟着的那一行**没有缩进**：它是 ls 的 stderr 直接上屏，本脚本一个字都没改（原文照打）：
  〔第一条：干活，成功〕
ls: cannot access 'retcode-没有这个文件.txt': No such file or directory
  ↑ 上面那行 ls 的报错原文，就是函数体最后一条命令留下的状态 → 退出码=2
  〔第二条：把场子圆回来了〕
  中间那条失败、最后一条是 echo → 退出码=0 ← ★ echo 几乎永远返回 0，失败被洗掉了
  同一个 washed 放进 if 里走的是 then 分支 ← 「明明挂了一步，if 却认为成功」就是这么来的
  → 两条判据：① 想让函数表达失败，就自己 return 一个非 0，别把希望寄托在「最后一条刚好是失败的那条」；
    ② bash 只看最后一个状态，函数体里挂过几次都不算数。
```

围栏里那行**没有缩进**的是 `ls` 自己的 stderr 直接上屏，脚本一个字都没改。
屏幕上为什么是这些数：`ls` 读不到那个文件，它的 **2** 就是函数体里最后执行的那条命令的状态，于是函数整体退 2；
第二条是「中间挂了一步、最后一条是 `echo`」→ 退出码 **0** —— `echo` 几乎永远返回 0，前面那步失败被当场洗掉，
所以同一个函数放进 `if` 里走的是 **then** 分支。
**直觉以为「函数里失败过，`if` 就会知道」**：屏幕上它不知道，bash 只看**最后一个**状态，体里挂过几次都不算数。
想让函数表达失败，就只能自己 `return` 一个非 0。

第 5 格，`exit` 与 `return` 在函数里的差别：

```
=== 5. exit 和 return 在函数里的差别：谁结束、还剩多少话要说 ===
  先在**本脚本自己身上**演示 return 那一支：
  ★ 我还活着 —— 这一行是调用完 return 版函数之后才打出来的，脚本没被打断 ｜ 刚才的退出码=3
  exit 那一支不敢在本脚本里跑（一跑后面全没了），所以两支都放进 bash -c 的子进程里对照。
  子进程末尾统一写 `exit "$rc"`，好让屏幕上那个退出码是函数的 7、不是后面 echo 的 0：
  函数体里写 return → 子进程输出的字符数=21  ｜ 「我还活着」出现了吗 → 有 ｜ 子进程退出码=7
  函数体里写 exit   → 子进程输出的字符数=0   ｜ 「我还活着」出现了吗 → 没有 ｜ 子进程退出码=7
  顺带一问：exit 后面写 300 → 退出码=44 ← exit 也逃不出第 2 段那个取模规矩
  → 一句话：return 结束「这次调用」，脚本继续往下跑；exit 结束「这个 shell 进程」，
    函数后面所有话（包括调用方那一行）都不再存在。所以被复用的函数里默认写 return，
    exit 只留给脚本主干上那句「到此为止」。
```

屏幕上为什么是这些数：`return` 那一支是在脚本自己身上演的，所以「我还活着」印出来了、码 3；
`exit` 那一支不敢这么演（一跑后面全没了），两支都被放进 `bash -c` 的子进程里对照，而且子进程末尾统一补一句
`exit "$rc"`，好让屏幕上那个码是函数的 **7**、不是后面 `echo` 的 0。对照结果：`return` 版子进程输出
**21 个字符**、「我还活着」**有**、码 7；`exit` 版输出 **0 个字符**、「我还活着」**没有**、码 7。
两支的码一样、内容差着 21 个字符 —— 差别全在「这次调用之后还剩不剩代码」。
顺带那一格 `exit 300` → **44**，说明 `exit` 用的是同一套取模规矩。
**直觉以为「函数里写 exit 也一样，反正码能带出去」**：码确实带得出去，但「函数后面所有话，包括调用方那一行」
都不再存在 —— 被复用的函数默认写 `return`。

第 6 格，调用完之后码还保得住吗（函数一律 `return 3` + 一句 `echo 数据`）：

```
=== 6. 调用完之后退出码还保得住吗：四种写法实测（函数一律 return 3 + echo 数据） ===
  ① v=$(fcode)           → $?=3 ｜ v=[数据] ← 码和数据都留下了
  ② local x=$(fcode)     → $?=0 ← ★ 码被 local 吞掉了
  ③ local x; x=$(fcode)  → $?=3 ← 声明和赋值分成两句就保住了
  ④ if fcode; then/else  → 走 else 分支 ← 判断调用本身永远拿的是函数的码
  → 差别的成因：local/declare 自己也是一条命令，「声明 + 赋值」写在同一行时那句的退出码是
    local 的（成功就是 0），fcode 的 3 当场蒸发。要码就分成两句，或者直接 if f; then。
```

屏幕上为什么：① `v=$(fcode)` → **3**，同时 `v=[数据]`，码和数据都留下了；
② `local x=$(fcode)` → **0**，码当场蒸发，因为 `local` 自己也是一条命令，「声明 + 赋值」写在同一行时
这一句的状态是 `local` 的（成功就是 0）；③ `local x; x=$(fcode)` → **3**，把声明和赋值拆成两句就保住了；
④ `if fcode; then/else` → 走 **else**，判断调用本身永远拿函数的码。
**直觉以为「① 和 ② 只是差一个 `local`，写法口味而已」**：屏幕上差的是整条退出码通道，
而 `local x=$(...)` 恰恰是最顺手的那一种。第 7 节的对照版实测同样是 3 对 0。

第 7 格，收口四句 + 自证：

```
=== 7. 收口：四句能带走的话 + 自证 ===
  ① return 只能给一个 0~255 的整数：写 300 得 44、写 256 得 0（★ 伪装成成功）、写 -1 得 255、写 abc 直接报错退 2。
  ② 不写 return 不等于没有码：退出码 = 函数体里最后执行的那条命令的状态，中间挂掉的一步会被后面的 echo 洗掉。
  ③ 函数里默认写 return，exit 留给「整个脚本到此为止」；两者共用同一套 0~255 取模规矩。
  ④ 这条通道只有 8 位宽，装不下数据：想带回东西只能走 stdout（见 outcapture.sh、errmix.sh）
     或者全局变量/nameref（见 localscope.sh）。$? 只能回答「成没成」，别拿它传内容。
  自证：本脚本没写过任何文件/目录（以自己名字开头的条目数=0）｜ 自己的作业表行数=0 ｜ 退出码到这一行为止都是 0
[退出码 0]
```

自证那一行的两个 **0**（以自己名字开头的条目数、作业表行数）是脚本跑完自己回头问的：
这一节全程只在内存里玩 `return`，一个文件都没落，所以沙箱外面不该有任何痕迹。

## 4. 小证据：退出码只保留低 8 位（把整条数轴排一遍）

这一节钉的是第 3 节第 2 格的**形状**：那一格只用了 256 和 258 两个数，这里把整条数轴排开，
让「回绕」自己浮出来，顺便把负数也排进去。

```
$ f(){ return "$1"; }
for v in 0 1 7 42 255 256 257 511 512 -1 -2; do
  f "$v"; code=$?
  printf "  return %-4s → 外面拿到 %s\n" "$v" "$code"
done
echo "  ★ 256 与 0 同、257 与 1 同、512 与 0 同：低 8 位之外的全被丢掉；负数按补码回绕"
  return 0    → 外面拿到 0
  return 1    → 外面拿到 1
  return 7    → 外面拿到 7
  return 42   → 外面拿到 42
  return 255  → 外面拿到 255
  return 256  → 外面拿到 0
  return 257  → 外面拿到 1
  return 511  → 外面拿到 255
  return 512  → 外面拿到 0
  return -1   → 外面拿到 255
  return -2   → 外面拿到 254
  ★ 256 与 0 同、257 与 1 同、512 与 0 同：低 8 位之外的全被丢掉；负数按补码回绕
[退出码 0]
```

屏幕上为什么是这些数：脚本里 `f(){ return "$1"; }` 是个纯粹的中转，
11 个输入 `0 1 7 42 255 256 257 511 512 -1 -2` 一个个送进去，输出每一行都是「低 8 位留下的那部分」：
0→0、1→1、7→7、42→42、255→255、**256→0**、**257→1**、**511→255**、**512→0**、-1→**255**、-2→**254**。
两行要特别看一眼：**511→255** 说明它不是「超过 255 就夹在 255」那种饱和截断，而是真的取模；
**-1→255、-2→254** 说明负数是按补码绕回来的 —— `-1` 和「你写了 255」在屏幕上完全同形。

**直觉以为「越界要么报错、要么停在 255」**：屏幕上它既不报错也不停，它绕圈。
绕圈最阴的后果就是 256 那一格：它跟 0 撞了。脚本自己把这件事挑明了，直接对拍：

```
$ f(){ return 256; }; g(){ return 0; }; f; a=$?; g; b=$?; printf "  于是 return 256 和 return 0 分得开吗 → a=%s b=%s，%s\n" "$a" "$b" "$( [ "$a" = "$b" ] && echo 分不开 || echo 能分开 )"
  于是 return 256 和 return 0 分得开吗 → a=0 b=0，分不开
[退出码 0]
```

屏幕上 `a=0 b=0，分不开`：`return 256` 和 `return 0` 交回来的东西**在调用方看来是同一个**。
这条线的判据只有两句：想让函数报告「成没成」，只能在一个字节里编码，而且**别把 256 的倍数当状态号用**；
想让函数报告「多少、是什么」，`return` 这条路天生装不下 —— 第 5~8 节整节在讲另一条道。

## 5. outcapture.sh 完整跑：命令替换的四刀

这一节钉的是**第二条通道（stdout）的四刀**：尾部换行、多值、诊断污染、子 shell 副作用。
`outcapture.sh` 一共 6 格（第 23 节对账里它是 6 格），前四格就是那四刀。

第一刀，尾部换行被吃掉，而且吃的是「所有连续的尾部」：

```
$ bash outcapture.sh
=== 1. 第一刀：尾部换行被吃掉，吃的还是「所有连续的尾部」 ===
  printf 'a\nb\n'  原始 4 字节 / 2 个换行 → 捕获后 3 字符 / 1 个换行
  printf 'a\nb'    原始 3 字节 / 1 个换行 → 捕获后 3 字符 / 1 个换行
  printf 'a\nb\n\n' 原始 5 字节 / 3 个换行 → 捕获后 3 字符 / 1 个换行
  printf '\n'      原始 1 字节 / 1 个换行 → 捕获后 0 字符 / 0 个换行
  → 直觉以为「只吃一个换行、差一个字节返回值就差一个字节」：实测 4 字节、3 字节、5 字节三种写法
    捕获后都是 3 个字符 —— 它把结尾的换行**全**删光，中间的换行一个不动（前一行还剩 1 个）。
  ★ 最后一行最阴：函数只是多打了一个空行，捕获到的就是空字符串，[ -z "$v" ] 当场把「有结果」判成没结果。
```

屏幕上为什么是这些数：四行输入分别是 4 字节 / 3 字节 / 5 字节 / 1 字节，捕获后却全变成 **3 个字符**
（`a\nb\n`、`a\nb`、`a\nb\n\n` 三种写法一模一样），最后一行 `\n` 捕获后 **0 字符 0 换行**。
**直觉以为「命令替换只吃一个换行，差一个字节返回值就差一个字节」**：屏幕上它把结尾的换行**全**删光，
而中间的换行一个不动 —— 第一行捕获后还剩 **1 个**换行，因为那个换行不在尾部。
最后一格是这刀最疼的地方：函数只是**多打了一个空行**，捕获到的就是空字符串，
`[ -z "$v" ]` 当场把「有结果」判成「没结果」（第 6 节把这一刀单独放大）。

第二刀，想带两个值，只有「一坨文本」这一种写法，两种编码各付一种代价：

```
=== 2. 第二刀：想带两个值，只有「一坨文本」这一种写法，两种编码各付一种代价 ===
  甲·空格版 echo "$x $y" → 捕获到 [12 34] ｜ 行数=1 ｜ 词数=2 ｜ 拆出来 sx=[12] sy=[34]
  ★ 代价现场：两个值里有一个本身带空格 → 捕获到 [红 黄 蓝]（3 个词），拆出来 bx=[红] by=[黄 蓝]
  乙·换行版 echo -e "x\ny" → 捕获到 [12/34]（斜杠代表换行）｜ 字符数=5 ｜ 换行数=1 ← 没被吃，因为它不在尾部
    可 read -r 只读得到第一行：ly1=[12] ｜ ★ 第二个值压根没进任何变量（read 撞到换行就收工）
    要拿全两个值就只能逐行读（while read / mapfile）：这里读到 2 行
  → 一句话：空格版在赌「值里没有空格」，换行版在赌「你记得逐行读」。$( ) 交回来的从来不是两个变量，
    只是一段文本；真要稳稳带出多个值，得走全局变量或 nameref（见 localscope.sh）。
```

屏幕上为什么：空格版 `echo "$x $y"` 捕获到 `[12 34]`，**1 行 2 词**，靠拆词能还原成 `sx=[12] sy=[34]`；
可一旦两个值里有一个自带空格，捕获到的就是 `[红 黄 蓝]` —— **3 个词**，拆出来 `bx=[红] by=[黄 蓝]`，
边界当场错位。换行版看着更稳：`[12/34]`（斜杠代表换行）**字符数=5、换行数=1**，那个换行没被吃，
因为**它不在尾部**；但 `read -r` 只读到第一行 `ly1=[12]`，第二个值压根没进任何变量 ——
`read` 撞到换行就收工，要拿全两个值只能逐行读（这里读到 **2 行**）。
**直觉以为「echo 两个变量就等于带回两个变量」**：屏幕上 `$( )` 交回来的从来只是一段文本，
词边界和行边界都得你自己再切一次，而两种切法各赌一件事：空格版赌「值里没有空格」，换行版赌「你记得逐行读」。
真要稳稳带出多个值，得走全局变量或 nameref（第 11 节）。

第三刀，诊断写进 stdout，返回值就变成「一个词加一句废话」：

```
=== 3. 第三刀：诊断写进 stdout，返回值就变成「一个词加一句废话」 ===
  事故版 v=$(noisy) → v=[调试中…/结果]（斜杠=换行）｜ 行数=2 ｜ 首行=[调试中…] ← 首行是废话
  判定 [ "$v" = "结果" ] → 假 ｜ 判空 [ -z "$v" ] → 非空（明明没拿到值也说「有」）
  正解版：下一行就是 v=$(quiet) 的执行现场，屏幕上会先掉出那句诊断 ——
调试中…
  ★ 上面那行诊断**没有缩进**：它是函数的 2 号 fd 原路上屏，本脚本一个字都没加工；
    而 v=[结果]（字符数=2）里干干净净 —— 命令替换只接管 1 号 fd，2 号它根本接不着
  → 判据：函数里每一句 echo 先问一句「这是要带回的值，还是给人看的？」给人看的一律 >&2；
    漏一句，比较、判空、取首行同时中招（想把 stderr 也捞进变量得写 2>&1，顺序代价见 errmix.sh）。
```

屏幕上为什么：事故版 `v=$(noisy)` 拿到的是 `[调试中…/结果]`、**2 行**、首行是废话，
于是 `[ "$v" = "结果" ]` 判**假**、`[ -z "$v" ]` 判**非空**（明明没拿到值也说「有」）；
正解版把诊断写成 `>&2`，所以围栏里那行**没有缩进**的「调试中…」是函数的 2 号 fd 原路上屏、脚本没加工，
而 `v=[结果]` **字符数=2**，干干净净。
**直觉以为「少写一句 `>&2` 只是屏幕上多一行字」**：屏幕上它同时改掉了比较结果、判空结果和「首行是什么」。
命令替换只接管 1 号 fd，2 号它接不着 —— 这一句在第 7 节还会再撞一次。

第四刀，`$( )` 是个子 shell，里面的副作用一个都带不出来：

```
=== 4. 第四刀：$( ) 是个子 shell，里面的副作用一个都带不出来 ===
  ① 替换里 cd cap：里面的 pwd 等于「外层 PWD/cap」吗 → 是 ｜ 外层目录变了吗 → 没变
  ② 替换里给全局变量赋值：v=[值] ｜ 外面的 G=[外层] ｜ 和「里面」相等吗 → 否
  ③ 替换里 exit 3（前面还有一句 echo）：v=[hi] ｜ 外层 $?=3 ｜ ★ 脚本还活着，这一行就是证据
     只写 exit 1：v=[]（字符数=0）｜ 外层 $?=1 ｜ 外层脚本继续往下跑
  → ③ 那一格要说清：命令替换里的 exit 只杀掉**那个子 shell**，它把 3 交回给赋值语句当退出码，
    所以「码」传得出来（$? = 3），「终止」传不出来。想真结束整个脚本，只能在主干上 exit（见 trapreturn.sh）。
```

屏幕上为什么：① 替换里 `cd cap`，里面的 `pwd` 确实等于「外层 PWD/cap」（**是**），外层目录**没变**；
② 替换里给全局变量赋值，里面 `v=[值]`、外面 `G=[外层]`，两者**不相等**；
③ 替换里 `exit 3`（前面还有一句 `echo`），`v=[hi]`、外层 `$?` = **3**、而脚本**还活着**。
③ 那一格最容易被读反：命令替换里的 `exit` 只杀掉**那个子 shell**，它把 3 交给赋值语句当退出码 ——
所以「码」传得出来、「终止」传不出来；只写 `exit 1` 时 `v=[]`（**字符数=0**）而外层码是 **1**，
是同一个道理的第二遍。**直觉以为「函数里 `cd`、赋值、exit 影响的是我的脚本」**：屏幕上三件全部留在原地，
只有那段文本和一个码出来了。想留下副作用，只能走全局变量或 nameref（第 11 节）。

第 5 格，两条线别搅在一起：同一次调用里码和文本互不相干：

```
=== 5. 两条线别搅在一起：同一次调用里 return 的码和 stdout 的内容互不相干 ===
  原文：v=$(both) ｜ 函数里 echo 和 return 都执行了 → v=[hello]（5 字符）｜ $?=7
  ★ 内容判据说「有货」、码判据说「失败」：两句都没错，因为它们量的不是同一件事
  对照·布尔函数（本意只回答成没成，顺手 echo 了一句）：if is_bad >/dev/null → 走 then 分支
  同一个 is_bad 放进替换里 v2=[在的] ← 它「以为」自己在报布尔，实际交出去的是一坨文本
  → 一句话：$? 这条通道只有 8 位宽，只能回答「成没成」；stdout 那条只能回答「是什么」。
    一个函数可以两条都给，但调用方每次必须清楚自己伸手拿的是哪一条。
```

屏幕上为什么：`v=$(both)` 里函数既 `echo` 又 `return`，于是 `v=[hello]`（**5 字符**）而 `$?` = **7**。
内容判据说「有货」、码判据说「失败」，两句都没错，因为它们量的不是同一件事。
对照那一格更有意思：一个本意「只回答成没成」的布尔函数 `is_bad`，被 `if is_bad >/dev/null` 用时走 **then** 分支，
被 `v2=[在的]` 用时交出去的是一坨文本 —— 它自己「以为」在报布尔，实际走的是 stdout 那条道。

第 6 格，四刀收口 + 自证：

```
=== 6. 收口 + 自证 ===
  四刀背下来：① 尾部换行全吃光 ② 多值只能是一坨文本 ③ 漏一句 echo 就污染 ④ 副作用出不了子 shell。
  现场目录 cap/ 还在吗 → 在 ｜ 删之前里面的条目数=0 ｜ 本脚本自己的作业表行数=0
  现在 cap/ 还在吗 → 不在了 ｜ 当前目录里名为 cap 的条目数=0
[退出码 0]
```

自证那一行读的是目录：现场 `cap/` 删之前**条目数=0**、删之后**名为 cap 的条目数=0**，
外加本脚本自己的作业表**行数=0** —— 这一节全程没起过后台作业。

## 6. 小证据：尾部换行是「全吃光」，多一个空行返回值就成空串

这一节钉的是第一刀的**边界**：把「尾部换行有几个」单独排一遍，并且把「看着像空」和「真的是空」分开。

```
$ a(){ printf "x\n"; }
b(){ printf "x\n\n"; }
c(){ printf "\n"; }
d(){ printf "x\n\n\n"; }
for f in a b c d; do v=$($f); printf "  %s：捕获后长度=%s 内容=[%s]\n" "$f" "${#v}" "$v"; done
echo "  ★ 一个尾换行和三个尾换行，捕获结果一模一样；只打一个空行的函数，返回值是空串"
  a：捕获后长度=1 内容=[x]
  b：捕获后长度=1 内容=[x]
  c：捕获后长度=0 内容=[]
  d：捕获后长度=1 内容=[x]
  ★ 一个尾换行和三个尾换行，捕获结果一模一样；只打一个空行的函数，返回值是空串
[退出码 0]
```

屏幕上为什么是这些数：四个函数只差尾部换行的个数 —— `a` 打一个（长度 **1**）、`b` 打两个（长度 **1**）、
`d` 打三个（长度 **1**）、`c` 只打一个换行（长度 **0**、内容 `[]`）。
**直觉以为「一个尾换行和三个尾换行，捕获结果会差两个字符」**：屏幕上三行一模一样，
它不是「删掉一个换行」，是「删掉所有连续的尾部换行」。而 `c` 那一格说明另一件事：
函数从头到尾只往 1 号 fd 写了换行，删完就什么都不剩 —— 返回值是空串。

第二格把「真的是空」和「看着像空」摆在一起对拍：

```
$ ok(){ printf "done\n\n"; }
v=$(ok)
printf "  函数打的是 done + 一个空行：捕获到 [%s] 长度=%s（被吃掉的只有换行，done 还在）\n" "$v" "${#v}"
empty(){ printf "\n"; }
w=$(empty)
printf "  函数只打一个空行：捕获到 [%s] 长度=%s → 判空结果=%s\n" "$w" "${#w}" "$([ -z "$w" ] && echo 是空串 || echo 非空)"
  函数打的是 done + 一个空行：捕获到 [done] 长度=4（被吃掉的只有换行，done 还在）
  函数只打一个空行：捕获到 [] 长度=0 → 判空结果=是空串
[退出码 0]
```

屏幕上为什么：`ok` 打的是 `done` 加一个空行，捕获到 `[done]`、**长度=4** —— 被吃掉的只有换行；
`empty` 只打一个空行，捕获到 `[]`、**长度=0**，`[ -z "$w" ]` 判「**是空串**」。
**直觉以为「判空能告诉我函数有没有干活」**：`ok` 明明干完了活，长度却是 4 而不是 5；
`empty` 也一样「干完了活」（`printf` 成功），可它就是空串 —— 判空只看通道里剩了什么。
两种「看着像空」必须分开：**尾部换行被吃光**之后你的值还在；
**函数从来没往 1 号 fd 写过非换行字节**才是真的空。

## 7. errmix.sh 完整跑：三条通道怎么分

这一节钉的是**通道的分配权**：stdout、stderr、退出码三条，`$( )` 接哪条、重定向怎么写、
以及「码到底是谁的」。`errmix.sh` 一共 7 格（第 23 节对账里它是 7 格）。

第 1 格，现场：同一个函数，`out=$(f)` 到底兜住了什么：

```
$ bash errmix.sh
=== 1. 现场：同一个函数，out=$(f) 到底兜住了什么 ===
  原文：out=$(count_words mix/a.txt)
  下一条就是这个调用。注意屏幕上会先冒出诊断那行，它**不会**出现在 out 里：
诊断：正在统计 mix/a.txt
  out=[3] ｜ 字符数=1 ｜ 词数=1 ｜ 行数=1
  → ★ 命令替换只接管函数的 1 号 fd。stderr 没被接，所以原路走到屏幕上 —— 这正是想要的效果。
    但别忘了它是「碰巧没接」，不是你写的规矩；下一段把三种接法各跑一次。
```

屏幕上为什么：围栏里那行**没有缩进**的诊断是 stderr 原路上屏，`out=[3]` 里只有 1 号 fd 的东西 ——
**字符数=1、词数=1、行数=1**。但这一格的重点是它自己的提醒：stderr 出现在屏幕上是因为它
「**碰巧没被接**」，不是你写的规矩；下一格就把几种接法各跑一次。

第 2 格，三条分流的写法：原文与拿到的值：

```
=== 2. 三条分流的写法：原文与拿到的值 ===
  ① 只要 stdout：out=$(f 2>/dev/null)
     out=[3] 字符数=1 词数=1 行数=1 ｜ 这一条屏幕上没出现诊断
  ② 诊断也进来：out=$(f 2>&1)
     out=[诊断：正在统计 mix/a.txt/3] 字符数=19 词数=3 行数=2 ｜ ★ 结果那行被挤到了第 2 行
  ③ 只要 stderr：err=$(f 2>&1 >/dev/null)   ← 两个重定向的顺序**不能**换
     err=[诊断：正在统计 mix/a.txt] 字符数=17 行数=1 ｜ 结果（stdout）被丢进 /dev/null 了
  ④ 对照：写反成 out=$(f >/dev/null 2>&1)
     out=[] 字符数=0 ｜ 两手空空
  → ③ 就是第 04 章那条顺序事故在命令替换里重演：重定向从左往右生效，
    先执行 2>&1 时，2 号抄走的是「1 号那一刻的指向」= 命令替换的那根管道；
    随后 >/dev/null 才把 1 号改走。于是 stderr 留在了替换里、stdout 被扔掉。
    反过来写（④）就是两个流一起扔 —— 一个字符都拿不到。
```

屏幕上为什么：① `out=$(f 2>/dev/null)` → `[3]`，字符数 **1**，这次连诊断都看不见；
② `out=$(f 2>&1)` → `[诊断：正在统计 mix/a.txt/3]`，**字符数=19、词数=3、行数=2**，结果被挤到第 2 行；
③ `err=$(f 2>&1 >/dev/null)` → `err=[诊断：正在统计 mix/a.txt]`，**字符数=17、行数=1**，结果（stdout）被扔进 `/dev/null`；
④ 写反成 `out=$(f >/dev/null 2>&1)` → **字符数=0**，两手空空。
③ 和 ④ 这 **17 对 0** 的差就是顺序：重定向从左往右生效，先执行 `2>&1` 时 2 号抄走的是
「1 号那一刻的指向」= 命令替换那根管道；随后 `>/dev/null` 才把 1 号改走，于是 stderr 留在替换里、stdout 被扔掉。
**直觉以为「`2>&1` 和 `>/dev/null` 谁先谁后效果一样」**：屏幕上一个是 17 个字符、一个是 0 个字符。

第 3 格，★ 事故现场：函数里报错也 `echo` 到 stdout，比较当场假：

```
=== 3. ★ 事故现场：函数里报错也 echo 到 stdout，比较当场假 ===
  原文：out=$(bad_count_words mix/a.txt)，然后 if [ "$out" = "3" ]; then 认为是成功
  out=[诊断：正在统计 mix/a.txt/3]（两行）
  字符数=19 词数=3 行数=2 ｜ 判定 [ "$out" = "3" ] → 假
  拿它做整数比较会怎样（放到子进程里跑，报错前缀才是干净的 bash:）：
    bash: line 1: [: 诊断：正在统计 mix/a.txt
    3: integer expected
    退出码=2
  → ★ 同一段诊断：走 stderr 只是「屏幕上多一行字」，走 stdout 就把整条通道搅浑了 ——
    比字符串会假、做算术会报错、取首行取到的是「诊断：正在统计」那一行、判空（[ -z ]）也判错。
  正解只有一条：函数里凡不是「要带回的值」的输出，一律 >&2。
  兜底（改不动别人的函数时）：只取末行 [3] —— 但这等于在赌「诊断永远印在前面」。
  再狠一点：函数其实什么都没算出来，判空却说「有结果」（bash mix/empty.sh，故意不带 2>&1）：
     mix/empty.sh: line 3: mix/没有这个文件.txt: No such file or directory
     out=[诊断：这一趟什么也没算出来] ｜ 字符数=13 ｜ 判空 [ -z "$out" ] → 非空
  → 上面那行 wc 的报错原路走到了屏幕，而 out 里躺着的就是那句诊断 —— 通道里「非空」和「有结果」是两回事。
```

屏幕上为什么：`out=$(bad_count_words mix/a.txt)` 拿到的是**两行**（字符数 **19**、词数 **3**、行数 **2**），
于是 `[ "$out" = "3" ]` 判**假**；拿去当整数用，bash 直接甩出英文原文（`[: 诊断：…` / `integer expected`）
并给码 **2**。最下面那一格更狠：函数其实什么都没算出来，`wc` 的报错原路走到屏幕，
而 `out` 里躺着的就是那句诊断 —— **字符数=13**，`[ -z "$out" ]` 判「**非空**」。
**直觉以为「通道里有东西就说明函数算出了结果」**：屏幕上「非空」和「有结果」是两回事。
正解只有一条：函数里凡不是「要带回的值」的输出，一律 `>&2`；兜底「只取末行」等于在赌「诊断永远印在前面」。

第 4 格，`out=$(f)` 的退出码：赋值带得回码，披上 `local` 就没了：

```
=== 4. out=$(f) 的退出码：赋值带得回码，披上 local 就没了 ===
  原文：out=$(f3)   → 实测 $?=3 ｜ out=[数据] ← 简单赋值的退出码 = 命令替换里那条命令的
  原文：v=$(f3)（先 local 声明、再单独赋值）→ 实测 $?=3
  原文：local v=$(f3)（声明与赋值写同一行）→ 实测 $?=0 ← ★ 码被吞了
  对照：if f3; then A; else B; fi 走的是 else 分支（f3 说了 3）
  → ★ 三件事分开记：想拿码就判断调用本身，或者写成「先声明再赋值」；
    local v=$(f) 这个最顺手的写法，拿到的是 local 这个 builtin 自己的 0，f3 的 3 当场蒸发；
    脚本如果加了 set -e，这条坑更狠 —— 该炸的那一行根本不炸。
```

屏幕上为什么：`out=$(f3)` → **3**（简单赋值的退出码 = 命令替换里那条命令的）；
先 `local` 声明、再单独 `v=$(f3)` → 也是 **3**；`local v=$(f3)` 写同一行 → **0**，
因为这一句的状态是 `local` 这个 builtin 自己的。对照那行 `if f3; then A; else B; fi` 走 **else**：
判断调用本身永远拿函数的码。这和第 3 节第 6 格的 ①②③ 是同一个坑的两次实测（那边 3 对 0，这边还是 3 对 0）。
**直觉以为「加个 `local` 只是声明范围，不影响取值」**：屏幕上它把整条退出码通道改成了 0，
而最顺手的写法恰好就是它。

第 5 格，`if f; then` 的码是函数自己的，不是体里最后那句 `echo` 的：

```
=== 5. if f; then 的退出码是函数自己的，不是体里最后那句 echo 的 ===
  loose（体里 false 之后还有一句 echo）→ 退出码=0 ｜ if loose 走 then 分支
  strict（体里最后一条就是 false）→ 退出码=1 ｜ if strict 走 else 分支
  endsay（最后一条是 echo，但函数 return 9）→ 退出码=9 ｜ if endsay 走 else 分支
  → ★ 函数的退出码 = 体里**最后执行的那条命令**的状态，或者自己 return 的数。
    echo 几乎永远返回 0，所以「函数里挂了个 false / 挂了个读不到的文件」在 if f 面前等于没发生；
    反过来 endsay 说明另一半：码归函数说了算，最后一句 echo 的 0 拦不住 return 9。
```

屏幕上为什么：`loose`（`false` 之后还有一句 `echo`）→ **0**、走 **then**；
`strict`（最后一条就是 `false`）→ **1**、走 **else**；
`endsay`（最后一条是 `echo`，但函数 `return 9`）→ **9**、走 **else**。
**直觉以为「函数里失败过，`if` 总会察觉」**：`loose` 那一格它没察觉（`echo` 的 0 把 `false` 洗掉了）；
而 `endsay` 给出另一半：码归函数说了算，最后一句 `echo` 的 0 拦不住 `return 9`。
两半合起来才是完整判据：**要么自己 `return`，要么别指望最后那条命令替你不说话**。

第 6 格，走 stdout 这条通道的结构性代价：命令替换是个子 shell：

```
=== 6. 走 stdout 这条通道的结构性代价：命令替换是个子 shell ===
  原文：r6=$(bump) ｜ r6=[结果] ｜ 函数里明明 counter+1 了，外面的 counter=0
  原文：r6b=$(cd mix && pwd) ｜ 替换里的 pwd 和外面的 pwd 相等吗 → 不相等（不等 = 里面确实 cd 成了）
  外面这个 shell 的当前目录变了吗 → 没变（前一次 pwd 与后一次 pwd 相等吗：是）
  对照：直接 bump（不套命令替换）→ 外面的 counter=1 ｜ 这就是「全局变量」那条通道的来路
  → ★ 只要走 stdout，函数就在子 shell 里跑：它改的全局变量、它的 cd、它起的后台作业，
    全都传不出来。所以「既要带回值、又要留下副作用」这种需求 $(f) 天生做不到 —— 那是
    全局变量或 nameref（见 localscope.sh）的活；退出码则永远走 return，见 retcode.sh。
```

屏幕上为什么：`r6=$(bump)` 拿到 `r6=[结果]`，可函数里明明 `counter+1` 了，外面 `counter=0`；
`r6b=$(cd mix && pwd)` 里外两个 `pwd` **不相等**（说明里面确实 `cd` 成了），而外面这个 shell 的当前目录
**没变**（前一次 `pwd` 与后一次 `pwd` 相等）；不套命令替换、直接 `bump` → 外面 `counter=1`。
**直觉以为「全局变量通道和 stdout 通道只是写法不同」**：屏幕上同一句赋值，套上 `$( )` 就带不出来、
不套就带得出来 —— 差别不在函数，在「谁替它起了一个进程」。所以「既要带回值、又要留下副作用」
这种需求 `$(f)` 天生做不到，那是 nameref 或全局变量的活。

第 7 格，收口判据与自证：

```
=== 7. 收口：判据与自证 ===
  删之前 mix/ 里有 4 个文件 ｜ 现在执行 rm -rf mix（trap 里是同一句，这里提前跑一遍好自证）
  ① 现场目录 mix/ 还在吗 → 不在了 ｜ ls -A 里名为 mix 的条目数 = 0
  ② 后台进程：本脚本没起过后台作业，在**自己的进程里**复核 jobs -p 行数 = 0
  ③ 同一次调用、四种写法拿到的字符数：默认=1 ｜ ①=1 ｜ ②=19 ｜ ③=17 ｜ ④=0
  ④ 判据一：函数里每一句 printf/echo 先问一句「这是要带回的值，还是给人看的？」
     给人看的一律 >&2；漏一行进 stdout，比较、算术、取首行会同时中招。
  ⑤ 判据二：只想捞 stderr 就写 err=$(f 2>&1 >/dev/null)，顺序不能反；

  ⑥ 判据三：out=$(f) 带得回退出码（实测 3），local v=$(f) 带不回（实测 0）；
     $(f) 里改不动外面的变量、cd 也带不出来。三条通道各有代价：stdout 干净但要子 shell，
     全局变量留得住但要自己擦干净，nameref 只回填一个已有变量 —— 选哪条看你要带回什么。
[退出码 0]
```

屏幕上为什么自证那一串是「**4 个文件 → 0 个条目**、后台作业 **0**」：`mix/` 是这一支唯一的现场目录，
删之前数一遍、删之后当场再问一遍。
第 ③ 行是这一节的总结读数：**默认=1、①=1、②=19、③=17、④=0** —— 同一次调用、五种写法拿到的字符数，
全部差在「你把哪条通道交给了 `$( )`」。

## 8. 小证据：同一次调用，码走一条道、文本走另一条道

这一节钉的是本章的**分水岭**：一次函数调用同时交出两个东西，一个是码、一个是字节，
它们各自独立、互不解释。三格，越往后越短。

```
$ f(){ echo 给捕获的; echo 给屏幕的 >&2; return 3; }
v=$(f); code=$?
printf "  捕获到的 v=[%s] ｜ 退出码=%s\n" "$v" "$code"
echo "  ★ 屏幕上那句「给屏幕的」没进 v：命令替换只接管 1 号 fd，2 号它接不着"
给屏幕的
  捕获到的 v=[给捕获的] ｜ 退出码=3
  ★ 屏幕上那句「给屏幕的」没进 v：命令替换只接管 1 号 fd，2 号它接不着
[退出码 0]
```

屏幕上为什么：函数里三句都执行了 —— `echo 给捕获的`（1 号 fd）、`echo 给屏幕的 >&2`（2 号 fd）、`return 3`。
于是 `v=[给捕获的]`、`退出码=3`，而围栏里那行**没有缩进**的「给屏幕的」是 2 号 fd 原路上屏，
它**没有**进 `v`：命令替换只接管 1 号，2 号它接不着。这一格同时给了你「有内容」**和**「非 0 码」，两个都是真的。

第二格把命令替换整个拆掉，只留判断：

```
$ f(){ echo 给捕获的; echo 给屏幕的 >&2; return 3; }
if f; then echo "  走进 then（说明码是 0）"; else echo "  走进 else（说明码非 0，而且和 stdout 内容无关）"; fi
给捕获的
给屏幕的
  走进 else（说明码非 0，而且和 stdout 内容无关）
[退出码 0]
```

屏幕上为什么：不套 `$( )` 时 `echo 给捕获的` 也直接上屏了（所以围栏里有两行没缩进的字），
而 `if f` 走的是 **else** —— 因为 `f` 交回的码是 3。
**直觉以为「函数往 stdout 打了字，就说明它在『给出结果』」**：这一格里它照样打字，
可判断看的是那个 3，跟它打了几行字没有任何关系。

第三格把两种「单边为空」摆在一起：

```
$ f(){ return 0; }; v=$(f); printf "  函数一个字都不输出、只 return 0：v=[%s] 长度=%s 码=%s\n" "$v" "${#v}" "$?"
f2(){ echo 有内容; return 1; }; w=$(f2); printf "  函数有内容但 return 1：w=[%s] 码非 0 → %s\n" "$w" "$( [ "$?" -ne 0 ] && echo 是 || echo 否 )"
  函数一个字都不输出、只 return 0：v=[] 长度=0 码=0
  函数有内容但 return 1：w=[有内容] 码非 0 → 是
[退出码 0]
```

屏幕上为什么：`f(){ return 0; }` 什么都不输出 → `v=[]`、**长度=0**、码 **0**；
`f2(){ echo 有内容; return 1; }` → `w=[有内容]` 而「码非 0」判「**是**」。
**直觉以为「拿到空串就是函数失败了」**：第一格空串配的恰恰是成功（0）；
**直觉以为「拿到内容就是成功了」**：第二格内容齐全，码却是 1。

这两句同时成立，才叫「两套并行且互不解释」：**判成败看码，拿数据看文本**。
所以「函数返回了什么」这句问法本身是错的 —— 它要么返回一个码（0~255，第 3、4 节），
要么输出一些字节（第 5~7 节），不存在第三种东西。

## 9. trapreturn.sh 完整跑：return 与 exit 在 trap、在 source 里

第 3 节量的是「`return` 能交出什么」，这一节问的是另一件事：**它在什么场合才生效**。
同一句 `return`，写在函数里合法、写在函数外面报错、写在 EXIT 处理器里等于白写、写进被 `source` 的文件里
反倒管用了。`trapreturn.sh` 七格就是把这四种场合逐个摊开，每格都带 bash 自己的原文和退出码。
这一支只在沙箱里开一个 `traps/` 目录放临时文件，最后一格会当场把它删干净并自证。

**第 1 格：把 `return` 挪到函数外面。** 直觉是「写在不该写的地方，bash 总该把我拦下来」；
屏幕上是「它报了错，但没拦路」。

```
$ bash trapreturn.sh
=== 1. return 写在函数外面：bash 自己的原话（逐字照打，一个字没改） ===
  ① bash traps/top.sh（脚本顶层第 2 行是 return 5） ｜ 退出码=0
      〔脚本第 1 行〕
    traps/top.sh: line 2: return: can only `return' from a function or sourced script
      〔脚本最后一行〕
  ② bash -c "return 3"（连脚本文件这层皮都没有） ｜ 退出码=2
    bash: line 1: return: can only `return' from a function or sourced script
  → ★ 它报错，但它不拦路：第 1 行和最后一行都照打，脚本整体退 0 —— 那个 2 只属于 return 那一句自己。
    两句原文里都有「被 source 的脚本」五个字，那就是第 6 节的入口：换个加载方式，同一条 return 就合法。
```

↑ 两个退出码得掰开看：①那个脚本顶层写着 `return 5`，bash 在第 2 行报了原文错，可第 1 行和最后一行都照打了，
脚本整体退 **0**；②的 **2** 只属于 `return` 那一句自己，它没把 `bash -c` 的进程带走。
两句报错的正文一模一样，只是前缀不同：一个指到那个临时脚本的第 2 行，一个指到 `bash -c` 的第 1 行 ——
**报错原文里的路径取决于加载方式**，这也是本手册坚持用相对路径跑临时文件的原因。
原文末尾那五个字（说的是「函数或者被 source 的脚本」）就是第 6 格的入口：换个加载方式，同一条 `return` 立刻合法。

**第 2 格：EXIT 处理器里写 `exit` / 写 `return` / 什么都不写。** 直觉是「处理器里再 `exit` 会不会自己套自己」；
屏幕上是「只进场 1 次，但你的码被顶掉了」。

```
=== 2. EXIT 处理器里写 exit / 写 return / 什么都不写：三种下场 ===
  ① 处理器里 exit 3 ｜ 退出码=3
      主干：exit 9
      处理器进场：这是第 1 次；下一句我自己 exit 3
  ② 处理器里 return 4（此刻没有函数上下文） ｜ 退出码=9
      主干：exit 9
      处理器进场；下一句是 return 4
    traps/h.sh: line 1: return: can only `return' from a function or sourced script
      ★ return 之后这句居然也跑了
  ③ 处理器什么都不写 ｜ 退出码=9
      主干：exit 9
      处理器看到的退出码 = 9（主干写的也是 exit 9）
  → ★ ①只进场 1 次：EXIT 处理器里再 exit，bash 不让 EXIT trap 自己递归（真递归会印第 2 次），但它把最终
    码顶成了 3、主干那个 9 作废。②就是第 1 节那句原文错：报完照样跑，码还是 9。③是另一半：处理器里的 $?
    恰好等于主干交出来的码 —— 收尾时能知道自己是「因为什么」被叫起来的。
```

三版的主干都写的是 `exit 9`，差别全在处理器里那一句话：
①里写 `exit 3`，最终码成了 **3**，主干那个 9 作废，而「这是第 1 次」只出现一次 —— bash 不让 EXIT 处理器
再递归进 EXIT 处理器；②里写 `return 4`，此刻没有函数上下文，于是第 1 格那句原文错在这里又出现一次
（前缀换成了那个临时脚本的第 1 行），**报完错下一句照样跑**，码还是 9；③什么都不写，处理器里读到的
`$?` 恰好是 **9** —— 收尾的时候你是知道自己「因为什么被叫起来」的。

**第 3 格：DEBUG trap 一次函数调用加几次。** 直觉是「函数体里有几条命令，它就加几次」；
屏幕上是「关着 functrace 时，1 条和 3 条都是 +2」。

```
=== 3. DEBUG trap：一次函数调用让它加几次，全看 functrace 开不开 ===
  ① 关掉 functrace ｜ 退出码=0
      functrace=off ｜ 调一次函数让计数加了多少：体里 1 条 → +2 ｜ 2 条 → +2 ｜ 3 条 → +2
  ② 开着 functrace ｜ 退出码=0
      functrace=on ｜ 调一次函数让计数加了多少：体里 1 条 → +4 ｜ 2 条 → +5 ｜ 3 条 → +6
  → ★ 关着时恒等于 2（「调用那一行」+「紧接着那一行」），函数体里 1 条还是 3 条命令**都不算数**；
    开着时差值是「体里命令数 + 1」。多出来那 1 次是什么？把处理器改成会自报家门的，当场问它：
  ③ 体里 2 条命令的函数被调一次，逐次印出触发点 ｜ 退出码=0
        DEBUG 第 1 次 ← 即将执行 [b2] ｜ 此刻在函数 [不在函数里]
        DEBUG 第 2 次 ← 即将执行 [b2] ｜ 此刻在函数 [b2]
        DEBUG 第 3 次 ← 即将执行 [:] ｜ 此刻在函数 [b2]
        DEBUG 第 4 次 ← 即将执行 [:] ｜ 此刻在函数 [b2]
    ★ 第 1、2 次是同一句 [b2] 被追了两遍，第二遍的 FUNCNAME 已经是 b2 —— 多出的那次发生在**进函数的
      那一刻**，不是函数返回；而处理器自己的「赋值 + echo」没再触发自己（不然 4 次会变成十几次）。
  ④ DEBUG 会不会截胡函数的码 ｜ 退出码=0
      函数的码还是 7
```

关着 functrace：体里 1 条 → **+2**、2 条 → **+2**、3 条 → **+2**，恒等于 2（「调用那一行」+「紧接着那一行」），
体里写多少条都不算数。开着 functrace：**+4 / +5 / +6**，差值正好等于函数体里的命令条数再加 1。
多出来的那 1 次在哪？③把处理器换成会自报家门的（印出 `BASH_COMMAND` 和 `FUNCNAME[0]`），
屏幕上四次里前两次盯的是同一句函数调用，到第二次「此刻在函数」的名字才变成它自己 ——
**多的那次发生在进函数那一刻，不是函数返回**。④顺手结掉一个常见担心：处理器里放 `true`，
函数的码**还是 7**，DEBUG 不截胡返回值。

**第 4 格：RETURN trap 到底替不替你盯着函数。** 直觉是「挂了 RETURN trap，函数一返回就通知我」；
屏幕上是「默认一次都不触发」。

```
=== 4. RETURN trap：functrace 不开时函数返回一次都不触发，source 反倒触发 ===
  ① 关掉 functrace ｜ 退出码=0
      A｜三层嵌套 l1→l2→l3 跑完：触发 0 次
      B｜一个 j 把同一个 k 调了两次：触发 0 次
        第 1 次触发 ← 刚从 [不在函数里（source 结束了）] 返回
      C｜只 source 一个文件、不调任何函数：触发 1 次
  ② 开着 functrace ｜ 退出码=0
        第 1 次触发 ← 刚从 [l3] 返回
        第 2 次触发 ← 刚从 [l2] 返回
        第 3 次触发 ← 刚从 [l1] 返回
      A｜三层嵌套 l1→l2→l3 跑完：触发 3 次
        第 1 次触发 ← 刚从 [k] 返回
        第 2 次触发 ← 刚从 [k] 返回
        第 3 次触发 ← 刚从 [j] 返回
      B｜一个 j 把同一个 k 调了两次：触发 3 次
        第 1 次触发 ← 刚从 [不在函数里（source 结束了）] 返回
      C｜只 source 一个文件、不调任何函数：触发 1 次
  → ★ 关着：A、B 全是 0 —— 「挂了 RETURN trap 就替你盯着每个函数」是误解，默认它谁都不管；
    可 C 照样触发 1 次（source 结束算一次，这条不要 functrace）。开着：A=3，一层一次，顺序是
    l3→l2→l1（最里层先回）；B 也是 3 —— 它数的是**实际返回了几回**，不是代码里写了几个函数。
```

关掉 functrace：三层嵌套 l1→l2→l3 跑完触发 **0** 次，一个 j 把同一个 k 调两次也是 **0** 次；
可第三个小格（只 source 一个文件、一个函数都不调）照样触发 **1** 次 —— source 结束算一次，这条不要 functrace。
开着 functrace：A 是 **3** 次，顺序 l3→l2→l1（最里层先回）；B 也是 **3** 次，因为 j 自己也要返回一次，
它数的是**实际返回了几回**，不是代码里写了几个函数。C 前后都是 1 次。
「挂了 RETURN trap 就有人替你盯着每个函数」是这一章要清掉的误解：**默认它谁都不管**。

**第 5 格：裸 `return` 拿谁的码，以及 `return` 和 `exit` 的分界线。**
直觉是「`exit` 会跳过收尾」。屏幕上：两种写法 EXIT 处理器都进场 1 次。

```
=== 5. 裸 return 拿谁的码，以及 return / exit 的「最后一行出现没出现」 ===
  ① 体里一条 false 然后裸 return ｜ 退出码=0
      上一条是 false → 码=1
  ② 体里一条 true 然后裸 return ｜ 退出码=0
      上一条是 true → 码=0
  ③ 体里一条 false|true 然后裸 return ｜ 退出码=0
      上一条是这条管道 → 码=0（没开 pipefail，只看最后一段）
  函数里写 return → 外层跑到最后一行了吗 → 是 ｜ EXIT 处理器进场 1 次 ｜ 脚本退出码=0
  函数里写 exit   → 外层跑到最后一行了吗 → 否 ｜ EXIT 处理器进场 1 次 ｜ 脚本退出码=4
  → 用「最后一行有没有出现」这个二值就够判了：return 只结束这次调用、调用方还在；exit 连调用方一起结束。
    可两版的 EXIT 处理器都进场 1 次 —— ★ 别指望用 return 跳过收尾，也别以为 exit 会绕过 EXIT trap；
    分清它俩看的是「之后还有没有代码可跑」，不是「trap 跑没跑」。裸 return 交的就是上一条命令的码。
```

裸 `return` 交的就是上一条命令的码：体里放 `false` → **1**，放 `true` → **0**，
放 `false|true` 这条管道 → **0**（没开 pipefail，只看最后一段）。
下面两行才是 `return` / `exit` 的真分界：判据用的是「外层最后一行有没有出现」这个二值 ——
`return` 版出现（是）、脚本退 **0**；`exit` 版没出现（否）、脚本退 **4**。
但两版的 EXIT 处理器都进场 **1** 次。所以：**别指望用 `return` 跳过收尾，也别以为 `exit` 能绕过 EXIT trap**，
它俩的差别在之后还有没有代码可跑，不在 trap 到底跑没跑。

**第 6 格：被 source 的文件里，`return 5` 和 `exit 5` 的下场完全不同。**
这一格兑现第 1 格那句报错里对加载方式的那半句。

```
=== 6. 被 source 的文件里：return 5 与 exit 5 的下场完全不同 ===
  〔被 source 的文件：开头这句〕
  ① 外层跑 . traps/src_ret.sh（文件里 return 5）→ 外层还活着吗 → 是（这行就是外层打的）｜ 码=5
  ② 外层跑 . traps/src_exit.sh（文件里 exit 5）：这格不敢在本脚本里演，放进子进程：
      〔被 source 的文件：开头这句〕
  ★ 子进程屏幕上有「我还活着」吗 → 没有 ｜ 那个子进程的退出码=5
  → source 进来的文件就是当前 shell 自己：里面 return 是「这段结束」，外面接着活；里面 exit 是
    「这个 shell 没了」—— 写脚本的人最常在这里把整场跑批一起带走。同一条 return，加载方式不同
    就从第 1 节那句报错变成这里合法的「结束本段」，这就是报错原文里那五个字的分量。
```

`. traps/src_ret.sh` 里那句 `return 5` 让文件提前结束（文件里 return 之后的那句没印），
外层不但活着，还当场承认后面那行就是它自己打的，码 **5**；
`. traps/src_exit.sh` 里的 `exit 5` 就不敢在本脚本里演了 —— 它会把整场跑批一起带走，所以放进子进程：
那格屏幕上有「我还活着」吗 → **没有**，子进程退出码 **5**。
这就是第 1 格那五个字的分量：**同一条 `return`，加载方式不同，就从报错变成合法的「结束本段」**。

**第 7 格：收口 + 自证。** 四条判定 + 一次当场清理。

```
=== 7. 收口 + 自证 ===
  ① return 只能在函数里或被 source 的文件里用；在函数外面用就是第 1 节那句原文错，但脚本不会停。
  ② EXIT 处理器里 exit 不会递归（进场实测 1 次），却会顶掉最终退出码；处理器里写 return 等于白写。
  ③ RETURN trap 默认完全不跟函数返回（但跟 source 结束）；开了 functrace 才是「每返回一层算一次」。
  ④ DEBUG 的代价是「每条命令一次」，函数体里的命令归不归它管同样看 functrace（多的那次在进函数时）。
  删之前 traps/ 里的文件数=7 ｜ 现场目录还在吗 → 在
  现在 traps/ 还在吗 → 不在了 ｜ 当前目录里名为 traps 的条目数=0 ｜ 本脚本作业表行数=0
[退出码 0]
```

删之前 `traps/` 里有 **7** 个文件，`rm -rf traps` 之后当前目录里名为 traps 的条目数 **0**、作业表行数 **0**
（这一支全程没起过后台进程），区间末尾那行标记给出的脚本退出码是 **0**。

**这一节带走：**

- `return` 只在**函数体内**和**被 source 的文件里**有意义；在函数外面写它，bash 报原文错、脚本继续跑、整体码不变。
- EXIT 处理器里 `exit` 不会递归（实测进场 1 次），但会顶掉最终退出码；处理器里 `return` 等于白写。
- DEBUG / RETURN trap 默认**不跟函数体里的命令、也不跟函数返回**；要它们跟，得 `set -o functrace`（RETURN 对 source 结束那条例外）。
- 判 `return` 还是 `exit`，看的是之后还有没有代码可跑；两者都会让 EXIT 收尾跑一次。

## 10. 小证据：本章为什么不写 set -e

本章九个辅助脚本的头部都写着「故意不加 `set -e`」，理由是这一半内容全是失败现场：
一遇非 0 就停，后面的对照组一条都看不见。这里当场演四次，看它到底会掐掉什么。

**第一格：最典型的那一刀。** 直觉是「`set -e` 只杀掉失败的那条命令」；屏幕上是「整个脚本当场结束」。

```
$ set -e
f(){ false; }
g(){ f; }
g
echo "  这行印不出来：第 2 条命令一失败，整个脚本当场结束"
[退出码 1]
```

↑ 这一格值得盯的是**屏幕上没有任何输出行**：四条命令里 `g` 那一条失败（它调的 `f` 里只有 `false`），
后面那句 echo 压根没轮到，整段退出码 **1**。你想知道「失败之后还有哪几步会跑」，`set -e` 不给你看。

**第二格：那就给命令补一个 `|| true`。** 脚本活下来了，代价是另一回事。

```
$ set -e
f(){ false; }
g(){ f || true; }
g
echo "  加了 || true 就走到这里了 —— 但你的失败现场已经被自己咽掉了"
  加了 || true 就走到这里了 —— 但你的失败现场已经被自己咽掉了
[退出码 0]
```

走到这里靠的是把失败当场抹平成 0 —— **失败现场被自己咽掉了**，`$?` 拿回来永远是 0，
后面想判「到底有没有成功」就没料了。

**第三格：`set -e` 最有名的例外。** 直觉是「加了 `set -e`，任何失败都会停」。

```
$ set -e
f(){ false; }
f || echo "  在 || 左边时 set -e 根本不管制（这是它最有名的例外）"; echo "  所以 set -e 既不可靠、又会误伤"
  在 || 左边时 set -e 根本不管制（这是它最有名的例外）
  所以 set -e 既不可靠、又会误伤
[退出码 0]
```

同一个 `false`，写在 `||` 左边时 `set -e` 根本不管制：两句 echo 都印出来了，退出码 **0**。
所以它**既不可靠（该管的不管）又会误伤（不该杀的整场杀掉）** —— 这就是本章不写它的理由。

**第四格：函数里的 `return` 撞上 `set -e`。**

```
$ bash -c "set -e; f(){ return 7; }; f; echo 到不了"; printf "  子进程整体退出码=%s（demo 自己不受影响，因为每条 runc 都是新进程）\n" "$?"
  子进程整体退出码=7（demo 自己不受影响，因为每条 runc 都是新进程）
[退出码 0]
```

把 `set -e` 和一句 `return 7` 的函数一起关进 `bash -c` 起的新进程里，`echo` 那一条一个字都没印，
子进程整体退出码 **7** —— 函数交出的那个 7 就是整个进程的码。屏幕上能看见的只有外层那句 printf 打的这个 7
—— demo 自己不受影响，因为它的每一条命令都是新起一个进程跑的。

**这一节带走：**

- 本章的失败一律**显式判码**：`if f; then`、`code=$?`、`f || …`，不靠 `set -e` 兜。
- `set -e` 杀的是「整个脚本」，不是「那一条命令」；想留下的对照组长跑不完。
- `||` 左边的失败 `set -e` 不管制 —— 它既漏又误伤，别把它当安全网。
- 需要「一失败就停」时，把它关进一个子进程（`bash -c "set -e; …"`），别让它在主脚本里替你做决定。

## 11. localscope.sh 完整跑：动态作用域

主线②在这儿落地：**函数里的名字是按调用栈找的，不是按定义位置找的**。
`localscope.sh` 八格，前四格是 `local` 的正反面，第五格是把它写错地方的原文，
六、七格是 `local -n`（nameref）的正用和两个不报错的坑，第八格数一遍还剩下的全局。
它只在沙箱里开一个 `scope/` 目录，第七格那两次撞名都放在**子进程**里，本 shell 一个都不沾。

**第 1 格：`local` 的基本面。** 直觉是「函数里的变量当然是局部的」；
屏幕上是「不写 `local` 就全是全局，而且外面直接读得到」。

```
$ bash localscope.sh
=== 1. local 的基本面：里面写的外面看不见，函数里漏写的就是全局 ===
  原文：inside_only() { local only_here=只活在函数里的值; ... } ；然后 inside_only
    函数里读 only_here=[只活在函数里的值]
  函数返回后：only_here 还在吗 → 不在 ｜ g_demo 还在吗 → 在（值=[外面本来就有的全局]）
  ★ 代价：函数里赋值不写 local，它就是全局 —— leaky 跑完，外面直接读到 forgot_local=[函数里忘了写local]
  → 判据：local 不是代码风格，是「别往公共命名空间乱扔名字」唯一的开关；一个函数里有几行
    裸赋值，就有几个可能撞名的全局。第 4 段会看到这句话反过来也咬人（下层挡住不了上层，上层也拦不住下层）。
```

`inside_only` 里那个 `only_here` 在函数里读得到值、函数一返回就「不在」，
而同函数里另一个没写 `local` 的赋值（`g_demo`）返回后还在、值还是外面本来那个；
`leaky` 那一行更直白：忘写 `local` 的变量 `forgot_local` 在函数外被直接读了出来，屏幕上给的就是它的值。
这一格给的判据是：**`local` 不是代码风格问题，它是唯一能把名字挡在公共命名空间之外的开关**。

**第 2 格：遮蔽与恢复。** 直觉是「函数里的 `local x` 像盖了个盖子，把 `unset` 掉就露出下面那个全局」；
屏幕上是「`unset` 是把这一层整个抹掉」。

```
=== 2. 遮蔽与恢复：把这一层撤掉之后，外面看见的还是原来那个吗 ===
  调用前：外面 x=[外面原来的值]
    函数里 x=[函数内的新值]（同名的全局被挡在门外）
  返回后：外面 x=[外面原来的值] ｜ 和调用前一模一样吗 → 是
    函数里 unset 之后：x=[（空）] ｜ [[ -v x ]] → 无 ← ★ 没有「露出下面那个全局」这回事
  返回后：外面 x=[外面原来的值] ｜ 还在吗 → 在
  → 两句记牢：local 只在函数活着的那段时间挡全局；在函数里 unset 一个 local 是把这一层**整个抹掉**
    （当场读它是空的、-v 也说无），不是「揭开盖子露出全局」；函数一返回，被遮蔽的那个全局原封不动回来。
```

调用前外面那个 `x` 是它本来的值，函数里同名 `local` 读到的是新值（外面那个被挡在门外），
返回后又变回调用前那个，一模一样。中间那一行才是重点：函数里 `unset x` 之后
读它是**空**、`[[ -v x ]]` 也说**无** —— 不存在「把盖子揭开就露出下面那个全局」这回事，
`local` 只在函数活着的那段时间挡全局，函数一返回被遮蔽的那个全局原封不动回来。

**第 3 格（本章最要紧的一格）：动态作用域。**
`inner` 一个 `local` 都没写，`outer` 也一个都没传给它的 —— 直觉是「它们互不认识」；
屏幕上是「`outer` 的那个 `x` 被一个什么都没声明的函数改了」。

```
=== 3. ★ 动态作用域：inner 一个 local 都没写，却读得到、改得动 outer 的那个 x ===
  ① 先在顶层问一次 peek：
      现在 peek 读到的 x=[全局那个x]
  ② 同样这两个函数，这次是从 outer 里调下去的：
    outer 里 local x=[外层函数的那个x]，然后调用 peek、poke（它俩谁都不认识 outer）
      现在 peek 读到的 x=[外层函数的那个x]
      poke 把当下最近的 x 写成了 [被poke改掉]
    poke 回来之后，outer 自己的 x=[被poke改掉] ← ★ 被一个「什么都没声明」的函数改了
  ③ outer 返回后，最外面那个全局 x=[全局那个x] ｜ 一点没被改吗 → 是
  ④ 再把 poke 拿到顶层调一次（这次它手上没有别的 x 了）：
      poke 把当下最近的 x 写成了 [被poke改掉]
     全局 x=[被poke改掉] ← 同一个 poke，两次改的是两个不同的变量
  → ★ 判据（这一章最要紧的一句）：bash 的作用域是按**调用栈**找的，不是按函数的定义位置找的。
    outer 的 local x 对所有「被 outer 调下去的函数」都可见、可写 —— 这就叫动态作用域。
    代价：底层函数里一句随手赋值，改掉的可能是几十层之上某个函数正在用的变量；而它读到什么
    取决于「谁调了它」，同一个函数换个调用者行为就变 —— 这类 bug 盯着函数本身看是看不出来的。
```

四步是同一个 `poke` 的两种命运：① 顶层调它，它改的是全局那个 `x`；
② 从 `outer` 里调下去，`peek` 读到的是 outer 那一层的值，`poke` 写下去之后
`outer` 自己的 `x` 就变成了 poke 写进去的那个；③ `outer` 返回，最外面那个全局 `x` **一点没被改**；
④ 再把同一个 `poke` 拿到顶层调一次，这次它改的就是全局了（屏幕上那行的值就是它刚写的）。
**同一个函数，换个调用就换个结果** —— 因为作用域是按调用栈找的。
这类 bug 盯着函数本身看是看不出来的：`poke` 的代码一个字没变，变的只有「谁调了它」。

**第 4 格：反面 —— 被调用者自己写一句 `local`，这条链当场断掉。**

```
=== 4. 反面：被调用者自己写一句 local，这条链当场断掉 ===
    mid  的 x 初值=[中间层的x]
      leaf_shield 里刚写完 local x（还没赋值）：x=[（空）] ｜ [[ -v x ]] → 无
      → 读到的是空，不是上层的「中间层的x」：这一层已经存在了，只是没值
    leaf 回来之后 mid 的 x=[中间层的x] ← 没被动过
    mid2 的 x 初值=[中间层的x]
      leaf_open 里没有 local，读到 x=[中间层的x]
    leaf 回来之后 mid2 的 x=[leaf_open改的] ← 被下层的裸赋值改了
  对照（同名字、同结构，只差被调用者那一句 local）：
     挡了的那一层结束时 x=[中间层的x] ｜ 没挡的那一层结束时 x=[leaf_open改的] ｜ 两者相等吗 → 不相等
     顺带把两个变量本身也比一下：shielded=[中间层的x] 是 mid 自己的值吗 → 是 ｜ opened=[leaf_open改的] 是 leaf 写的吗 → 是
  → ★ 判据：被调用者挡不住上层传下来的同名变量，除非自己声明 local；反过来，上层也拦不住
    下层往全局里造名字（第 1 段的 leaky、第 3 段的 poke）。所以规矩只有一条：
    函数里每一个变量，进函数先 local，宁可写多不靠猜。
```

同名字、同结构，只差被调用者开头那一句 `local x`：
`leaf_shield` 挡了，刚 `local` 还没赋值时读到的是**空**、`[[ -v x ]]` 说无
（**这一层已经存在了，只是没值**，不是「往下找」），回来之后 `mid` 的 `x` 还是它自己那一层的值；
`leaf_open` 没挡，进去就读到了 mid2 传下来的那个值，它的裸赋值直接把上层那个改了，
回来 `mid2` 的 `x` 已经是 leaf 写的那个。最后那两行对照把结论钉死：两者**不相等**。
判据是双向的：被调用者不声明就挡不住上层传下来的同名变量，上层也拦不住下层往全局造名字
（第 1 格的 `leaky`、第 3 格的 `poke` 各演示了一遍）。所以规矩只有一条：**进函数先 `local`，宁可写多不靠猜**。

**第 5 格：把 `local` 写在函数外面。** 直觉是「非法用法总该让脚本停下来」。

```
=== 5. 函数外面写 local：报错原文，以及它为什么不中断脚本 ===
  现场文件 scope/notlocal.sh 第 2 行是一句裸的 local（下面这条是当前 locale 的原文）：
scope/notlocal.sh: line 2: local: can only be used in a function
    local 那句报错之后，这一行照样执行了：target=[外面本来就有这个全局]
    退出码=0 ← ★ 报的是错，但不致命：脚本继续跑，遮蔽也没发生，target 还是那个全局
  同一条命令的英文对照（只在这一步给子进程强制 LC_ALL=C.UTF-8；外层已经是 C.UTF-8 时两行会重合）：
scope/notlocal.sh: line 2: local: can only be used in a function
  → 判据：local / export / declare 这些 builtin 只在函数体内有意义，写在函数外面 bash 就报
    「只能在函数中使用」这一句，然后接着跑下一行 —— 所以「反正我加了 set -e」在这里救不了你：
    这一句根本不是让脚本停下来的错，遮蔽也没生效，代码却看起来是对的。
```

屏幕上两行报错**一字不差**（内容就是「`local` 只能在函数里用」这一句），
因为 demo 已经把语言环境钉成 `LC_ALL=C.UTF-8`（第 1 节），所以「本机 locale 那一行」和「强制英文那一行」撞成了同一句。
关键是它下面那两行：报错之后那句 printf **照样执行了**，`target` 还是外面本来就有那个全局，
遮蔽压根没生效，**退出码 = 0**。这就是「反正我加了 `set -e` 就安全」救不了你的现场 ——
这一句根本不是让脚本停下来的错，遮蔽也没生效，而代码看起来是对的。

**第 6 格：`local -n`（nameref）的正用：把值回填给调用方，不占用全局。**
直觉是「要回填就只能开全局或者抄 stdout」；屏幕上是「传**变量名本身**（不加 `$`）就行」。

```
=== 6. local -n（nameref）的正用：把值回填给调用方，不占用全局 ===
  原文：f() { local -n _out=$1; _out=计算结果; }   ← 调用方传的是**变量名本身**（不加 $）
  ① 回填一个调用方已有的全局：square_into box 7 → box=[49]
  ② 回填调用方的**局部**：user 里的 result=[算完了：42]
     函数自己的 _out 在外面存在吗 → 不在 ｜ _res 呢 → 不在 ← nameref 是 local，不泄漏
  ★ 代价：名字不存在时 nameref 不失败，它给你**凭空造一个全局**：
     slot_from_thin_air=[填进去的值] ｜ declare -p 的原文=[declare -- slot_from_thin_air="填进去的值"]
     顺便：名字写成非法变量名（比如中文）时，本机也只给一句就过 ——
       localscope.sh: line 143: local: `从没出现过的名字': invalid variable name for name reference
       filler 那句的退出码=0 ← 撞名、非法名都不拦，全靠你自己保证
  → 什么时候**才**该用 nameref：你要回填的就是调用方那一个变量，又不想为此开全局、
    也不想让调用方去抄 stdout。它比 stdout 通道干净在「不留子 shell」（errmix 第 6 段），
    比全局通道干净在「不白占名字」；但它仍然按**名字**找变量，而名字会在调用栈上重复 —— 下一段两个坑。
```

① `square_into box 7` 把 `box` 填成了 **49**；② 甚至能回填**调用方的局部**（`user` 里那个 `result`
拿到的是算完的值 **42**），而函数自己的 `_out`、`_res` 在外面都不存在 —— nameref 本身是 `local`，不泄漏。
代价那一行更要紧：名字不存在时 nameref **不失败**，它给你**凭空造一个全局**
（紧跟着那一行 `declare -p` 的原文，就是它被凭空造出来的凭据）；
名字写成非法变量名（这里塞了个中文名字）时，本机只留一行非法变量名的原文报错，
**而 filler 那句的退出码是 0**。撞名、非法名都不拦，全靠你自己保证。

**第 7 格（两个坑，全程不报错）：`local -n` 的自引用与悬空引用。**

```
=== 7. ★ local -n 的两个坑：自引用、指向已经返回的局部 ===
  坑① 自引用：函数里 nameref 自己的名字（caller_var）和要回填的名字（$1 传进来的 caller_var）撞了。
scope/circ.sh: line 2: local: warning: caller_var: circular name reference

- `local` 划的圈是「这次函数调用」，不是那对花括号（第 12 节）；函数里 `unset` 一个 `local` 是抹掉这层，不是露出全局。
- `local -n` 能干净地回填，但**撞名和悬空都不报错**：三行 warning 之后退出码 0、值去了别处。回填前先确认目标存在（`[[ -v $1 ]]`），nameref 的名字要避开一切可能传进来的名字。

## 12. 小证据：bash 没有块作用域，local 的范围是整个函数

第 05 章在循环里钉过一条「bash 没有块作用域」，这一节把它钉进函数里：
`local` 划的圈是**这次函数调用**，不是那对花括号。两格：第一格把 `local` 塞进 `if` 和 `for` 的块里，
第二格把它写在函数外面。

**第一格：把 `local` 写进 `if` 和 `for` 的块里，出了块再问它还在不在。**
直觉是「`}` 一闭，块里的东西就该没了」。

```
$ f(){ if true; then local t=1; fi
printf "  出了 if 的大括号，t 还在吗 → t=[%s]\n" "$t"
for i in 1 2 3; do local u=$i; done
printf "  出了 for 的大括号，u 还在吗 → u=[%s]\n" "$u"
printf "  循环变量 i 我没写 local，它现在=[%s]\n" "$i"; }
f
printf "  函数返回之后，外面的 t=[%s] i=[%s]（★ i 是全局的，它一路活到了函数外面）\n" "${t-未定义}" "${i-未定义}"
  出了 if 的大括号，t 还在吗 → t=[1]
  出了 for 的大括号，u 还在吗 → u=[3]
  循环变量 i 我没写 local，它现在=[3]
  函数返回之后，外面的 t=[未定义] i=[3]（★ i 是全局的，它一路活到了函数外面）
[退出码 0]
```

↑ 三行「还在吗」的答案全是「在」：`if` 的大括号外 `t` 还是 **1**，`for` 的大括号外 `u` 是最后一轮的 **3**，
连没写 `local` 的循环变量 `i` 也还是 **3**。真正有意思的是最后一行：函数返回之后
`t` 的位置打出来的是「未定义」（`local` 的圈到函数结束就收了），而 `i` **带着 3 一路活到了函数外面** ——
它压根不是局部的，它是个全局。同一个函数体里，两个变量两种命运，差别只在有没有那两个字。

**第二格：把 `local` 写在函数外面。**

```
$ local q=1
printf "  报完错这行照样印出来（q=[%s]）：非 0 不等于终止，第 10 节讲的正是它的另一面\n" "${q-没赋上值}"
bash: line 1: local: can only be used in a function
  报完错这行照样印出来（q=[没赋上值]）：非 0 不等于终止，第 10 节讲的正是它的另一面
[退出码 0]
```

英文原文就一句，说的还是「`local` 只能在函数里用」这一句（第 11 节第 5 格在脚本文件里撞的是同一句话，
只是前缀换成那个临时脚本的第 2 行）。它下面那行照样印出来了，`q` 是「没赋上值」，退出码 **0** ——
非 0 不等于终止，这正是第 10 节讲的另一面。

**这一节带走：**

- `local` 的作用范围是**整个函数体**，与 `if` / `for` / `{ }` 的块无关；块里写的 `local` 出了块照样读得到。
- 循环变量不写 `local` 就是全局，它会活到函数外面，下一层递归或下一次调用都可能撞上它。
- 函数外面写 `local`：报错原文 + 退出码 0 + 遮蔽没生效，三件事同时发生。
- `local` 的圈由「这次调用」划，所以递归每层一个圈 —— 下一节专门量这件事。

## 13. recursion.sh 完整跑：递归靠什么成立、代价怎么量

递归是动态作用域最贵的一次考试：**每一层共用同一张调用栈，中间变量只要漏一个 `local`，
内层回退时就把外层那个同名变量改了**。
七格：漏 `local` 的阶乘、`FUNCNEST` 拦截、不设上限的真爆栈、代价怎么数、三层同名 `x`、
递归撞命令替换、收口。这一支在沙箱里开 `rec/` 放两个「敢在子进程里炸」的脚本，本脚本自己始终活着。

**第 1 格：漏掉 `local` 的递归会炸。** 直觉是「`4*3*2*1` 怎么会算错」。

```
$ bash recursion.sh
=== 1. 漏掉 local 的递归会炸：回来时 n 被内层改掉 ===
  漏 local 版 bad_run 4 → res=1（正解应是 24）｜ 跑完外层那个全局 n=[1]
  正确版   good_run 4 → res=24
  → ★ 判据：漏 local 那版只有一个全局 n；递归到最底层时 n 被写成 1，回退路上每一层
    乘的都是那个被改剩的 1，于是 4*3*2*1 实际算成了 1*1*1*1=1。正确版每层有自己的 local n。
```

两版函数结构完全一样，唯一差别是 `n=$1` 前面有没有 `local`。漏了的那版 `bad_run 4` 给
`res=`**1**（正解是 24），而且跑完之后外层那个全局 `n` 停在 **1** ——
递归到最底层时 `n` 被写成 1，回退路上每一层乘的都是那个被改剩的 1，于是 4 层实际算的是 `1*1*1*1`。
正确版每层有自己的 `local n`，`res=`**24**。

**第 2 格：`FUNCNEST`。** 直觉是「设了深度上限，脚本就会被炸掉」。
屏幕上是「拦下那一次调用，脚本继续活」。

```
=== 2. FUNCNEST：本机不设 = 只受栈限制；设 10 会当场拦下这次调用（脚本继续活）===
  本脚本进程里 echo $FUNCNEST → []（空 = 没设上限，递归只能靠栈来扛）
  FUNCNEST 是普通 shell 变量、不 export，所以每个新起的 bash 里它都是空的。
  在一个子进程脚本里设 FUNCNEST=10 再往深里递归（只活在那条命令里）：
    rec/nest10.sh: line 1: deep: maximum function nesting level exceeded (10)
    deep 这次调用退出码=1
    被拦之后脚本还在跑：reach=after
  子进程整体退出码=0 ｜ 那句「超出最大函数嵌套层数」是 bash 的原文（这里强制取英文，好逐字复现）
  → FUNCNEST 拦下来时：那次超限的调用返回非 0（上面「deep 这次调用退出码=1」），但 bash 报一句就
    放过脚本继续跑，末尾那句 echo 成功 → 整个子进程退出码又是 0。拦你，不等于打死你。
```

本脚本进程里 `echo $FUNCNEST` 是**空**（第 1 节也确认过它是未设状态），意思是递归只能靠栈来扛；
它是普通 shell 变量、不 `export`，所以每个新起的 bash 里它都是空的。
在子进程脚本里把它设成 10 再往深里递归：bash 给了一句原文，说这次调用撞到了最大函数嵌套层数、
上限就是那个 10（这一格强制取英文，好逐字复现）；那次超限调用退出码 **1**，
被拦之后脚本还在跑（末尾的 reach 印出来了），**子进程整体退出码 0** —— 因为最后那句 echo 成功了。
拦你，不等于打死你。

**第 3 格：不设 `FUNCNEST`、真递归到爆。** 直觉最怕这一格：「栈爆了会不会把整场跑批带走」。

```
=== 3. 不设 FUNCNEST、真递归到爆：崩的是子进程，本脚本不受影响 ===
  让子 bash 无限递归（不设 FUNCNEST），捕获它的输出与退出码：
    崩溃前 bash 吐出的字符数=0（0 = bash 一个字都没说，直接撞栈）
    子进程退出码=139 ← ★ 139 = 128+11，11 是 SIGSEGV（段错误），是内核砍掉了那个孩子
  本脚本走到这一行还活着 → 是（爆栈只打死了 fork 出去的那个 bash，没打满整台机器的栈）
  → 拿「子进程退出码 139 + 崩前零输出」当证据就够了；递归深度计数每跑必变，不印上屏。
```

崩的那个 `bash rec/runaway.sh` 在崩溃前吐出的字符数 = **0**（bash 一个字都没说，直接撞栈），
子进程退出码 **139** = 128 + 11，11 是 SIGSEGV，是内核砍掉了那个孩子；
而本脚本走到下一行还活着。递归深度那个数每跑必变，所以没印上屏 ——
拿「子进程 139 + 崩前零输出 + 本进程照活」当证据就够了。

**第 4 格：代价怎么量 —— 用计数，不用耗时。**
直觉是「递归慢，掐个表就知道了」；屏幕上给的是「进了多少次函数」这种每次都一样的量。

```
=== 4. 递归的代价用计数：fib 进来了多少次函数 ===
  fib 5  → 结果=5 ｜ 函数被进入 15 次
  fib 10 → 结果=55 ｜ 函数被进入 177 次
  为什么计数器是全局不是 local：local calls 让每层各数各的、回退时清零，总数就丢了。
  为什么不用 v=$(fib ...)：命令替换在子 shell 里跑，里面 calls 怎么加都带不回父进程 —— 实测：
    g 里给 lost 加了一次，用 v=$(g) 调 → 外层 lost=0（加在子 shell 里，回不来）
```

`fib 5` 结果 **5**、函数被进入 **15** 次；`fib 10` 结果 **55**、进入 **177** 次 —— 输入翻一倍，
调用次数翻十几倍，这个数字每次都一样，比任何耗时都稳。
下面两行解释了这个计数器为什么**必须是全局**：`local calls` 会让每层各数各的、回退时清零；
而套在 `$( )` 里也不行 —— 那个 `lost` 的实验就在这一格里跑完了：`g` 里给 `lost` 加了一次，
用 `v=$(g)` 调，外层读到的 `lost=`**0**。第 5 节那条「命令替换是子 shell，副作用带不出来」
在递归里又演了一遍。

**第 5 格：三层同名 `x` 各是什么。** 这一格是第 11 节第 3 格（动态作用域）的正照：
每层都 `local`，所以每层互不干扰。

```
=== 5. local 的作用域由调用栈决定：三层同名 x 各是什么 ===
  下去 深度=1 本地 x=[层1的x]
  下去 深度=2 本地 x=[层2的x]
  下去 深度=3 本地 x=[层3的x]
  回来 深度=3 本地 x=[层3的x]
  回来 深度=2 本地 x=[层2的x]
  回来 深度=1 本地 x=[层1的x]
  → 下去印 1→2→3、回来印 3→2→1：每层的 local x 只在自己那一帧有效，深度=2 那层从头到尾没碰过层 3 的 x。
```

下去印深度 1→2→3、回来印 3→2→1，六行里每一层读到的 `x` 都是自己那一层的那个值，
深度=2 那一层从头到尾没碰过层 3 的 `x`。**调用栈上每一帧一个圈** —— 这就是递归能成立的机制。

**第 6 格：递归 + 命令替换。** 直觉是「`v=$(f 5)` 拿回来的就是最外层那个值」。

```
=== 6. 递归 + 命令替换：v=$(f 5) 把每一层的 echo 全拼进来 ===
  捕获到的行数=6（f6 5 一路 echo 到第 0 层，全被同一个 $( ) 接住）
    第 5 层的 echo
    第 4 层的 echo
    第 3 层的 echo
    第 2 层的 echo
    第 1 层的 echo
    第 0 层的 echo
  对比「每层自己捕获」的写法（内层被 local s=$(...) 截走，外层只剩自己那行）：
    捕获到的行数=1 ｜ 内容=[第 3 层]
  → 谁没被下一层的 $( ) 接走，谁的 echo 就一路冒到最外层那次捕获 —— 递归函数里 echo 要格外当心。
```

第一版每层只 echo 不接住，最外面那次捕获到的行数 = **6**（第 5 层到第 0 层的 echo 全被同一个 `$( )` 接走）；
第二版让每层自己 `local s=$( … )` 把内层截走，外层只剩自己那行 —— 行数 **1**。
谁没被下一层的 `$( )` 接走，谁的 echo 就一路冒到最外层那次捕获，所以递归函数里 echo 要格外当心。

**第 7 格：收口。**

```
=== 7. 收口 ===
  删之前 rec/ 里有 2 个文件 ｜ 现在 rm -rf rec ｜ 之后名为 rec 的条目数=0
  自证：本脚本作业表 jobs -p 行数=0（第 3 段那个是用 $( ) 起命令替换，跑完即收，没留后台）
  ① 递归必须把所有中间变量都 local：漏一个，内层回退时就把外层那个同名全局改了（第 1 段 4! 算成 1）。
  ② 深度由栈扛：FUNCNEST=10 会让那次超限调用返回 1（脚本继续、末尾 echo 让它整体退 0），
     不设就只能等段错误 rc=139，且崩的只是 fork 出去的那个 bash，本进程照活。
  ③ 代价用计数不用 time：fib(10) 进了 177 次函数；计数要放全局，且不能套在 $( ) 里，否则带不回来。
  ④ 递归函数里的 echo 会被最外层 $( ) 一路接走（第 6 段捕获 6 行）：想只拿最外层那个值就别让中间层 echo。
[退出码 0]
```

`rec/` 里有 **2** 个文件，`rm -rf rec` 之后名为 rec 的条目数 **0**；作业表行数 **0**
（那个爆栈是用命令替换起的，跑完即收，没留后台）。四条判据把这一节合上：
中间变量全 `local`、深度由栈扛（`FUNCNEST=10` 让那次调用返回 1，不设就等段错误 **139**）、
代价用计数（`fib(10)` = **177** 次）、别让中间层 echo。

**这一节带走：**

- 递归函数里**每一个**中间变量都要 `local`；漏一个，内层回退时就把外层那个同名全局改了，而且不报错、只算错。
- `FUNCNEST` 是「拦下这次调用」，不是「打死脚本」：超限那次返回非 0，脚本继续、整体可以退 0。
- 不设 `FUNCNEST` 的深递归撞的是真栈：崩的是 fork 出去的那个 bash（rc=139，崩前零输出），父进程照活。
- 代价用**函数进入次数**量（`fib 10` = 177 次），计数器要放全局、不能套在 `$( )` 里。

## 14. 小证据：定义顺序不重要，重定义立刻生效

bash 里函数不是「编译期的对象快照」，而是名字表里一条**可以随时替换的条目**，
查表发生在**调用那一刻**。三格把这句话钉死。

**第一格：先定义调用者，再定义被调用者。** 直觉（从别的语言带来的）是「`first` 定义时 `second` 还不存在，这说不通」。

```
$ first(){ second; }
second(){ echo "  first 定义时 second 还不存在，照样能调 —— 名字是**调用那一刻**才查的"; }
first
  first 定义时 second 还不存在，照样能调 —— 名字是**调用那一刻**才查的
[退出码 0]
```

它照样跑通了。定义函数时 bash 只把**函数体原文**存进表里，一个名字都没解析；
等到 `first` 被调用，才去表里找 `second` —— 那一刻它已经在了。

**第二格：同名重定义。** 直觉是「重复定义同名函数至少要警告一下吧」。

```
$ g(){ echo "  第一版"; }
g
g(){ echo "  第二版（同名重定义，bash 不报错，直接盖掉）"; }
g
  第一版
  第二版（同名重定义，bash 不报错，直接盖掉）
[退出码 0]
```

两次调用打出两个不同的版本：第二次定义直接把表里那条盖掉，**一句提示都没有**。
一个文件里前后两处定义同一个名字，跑的是**执行到的那一次**；
`source` 一个库文件两次，就等于把所有函数重新覆盖一遍。

**第三格：反过来说 —— 名字查不到时才报错，而那也不是终止。**

```
$ notyet; echo "  这行印不出来"
bash: line 1: notyet: command not found
  这行印不出来
[退出码 0]
```

`notyet` 从没定义过，bash 给的是那句「找不到命令」的原文，
可它后面那半句 echo **照样跑完了**（屏幕上多出来的那一行正是它自己那句自嘲），整条退出码 **0**
—— 因为这条复合命令最后是 echo 说了算。这一格和第 10 节互为对照：
**「找不到名字」是一次普通的命令失败，不是语法错误**；加了 `set -e` 它才会变成终止。

**这一节带走：**

- 定义顺序无所谓：函数体里的名字要到被调用的那一刻才去查表，先写调用者完全合法。
- 重定义立刻生效且无通知；`source` 同一个文件两次等于覆盖两次。
- 查不到的名字给的是那句「找不到命令」的原文 + 非 0，但脚本继续跑；判成败要自己看码。
- 想要「定义时就固定住」的语义，bash 不提供；能靠的只有命名前缀（第 15 节）和别覆盖（第 21 节的库）。

## 15. functype.sh 完整跑：一个名字有几种身份

主线③：`f(){ }`、`function g { }`、`function h(){ }` 三种写法进的是**同一张表**，写法本身不留痕；
而「我这么写，最后跑起来的到底是谁」由查找顺序决定 —— 函数压过文件、内建也压不过函数。
七格把这三件事逐个量出来，第六格还要把同一份定义文件拿去撞 `/bin/sh`（本机 `/bin/sh` 是 dash，第 1 节确认过）。
这一支的沙箱目录是 `funcs/`，PATH 前置只挂在单独一条命令上。

> 先说一句这一节的屏幕现状：`functype.sh` 在第 5、6、7 格里踩了 bash 的一个经典陷阱 ——
> 它在**双引号的 `echo` 里用反引号包代码**，而反引号在双引号里是命令替换，不是「引用代码」。
> 于是那三格的末尾混进了若干条语法错误的原文，判定句里被反引号包住的那几个字则当场空了。
> **捕获照原样收下了这些行**，我一条没改；这几行本身也是一课：**双引号里的反引号是「执行」**。

**第 1 格：三种声明写法进表后长得一模一样。** 直觉是「三种写法是三种东西」。

```

      d_one () 
      {

末尾那句 ★ 值得记：`command -v` 对函数只回名字、不回内容，它答的是「会不会被找到」，不是「它是谁」。

**第 2 格：一个名字有几种身份。** 直觉是「`type -t` 给我的那个词就是全部」。

```
=== 2. 一个名字有几种身份：type -t 给分类，type -a 给全部来源 ===

五行把工具的能力差摆出来了：函数 → `function`（来源行数 **1**）、内建 → `builtin`、

定义了同名 `date` 函数之后，`type -t` 说它是函数、`command -v` 只回名字，

## 16. 小证据：被函数遮蔽之后怎么夺回来

上一节证明了函数压过内建、内建压过 PATH 里的文件，这一节演另一头：**你已经有同名函数了，
怎么把原来那个命令要回来**。三条急救路，四条命令，每条都带退出码。

**第一格：事故本体 —— 定义一个 `ls` 函数，然后调 `ls`。**
直觉是「函数只吃它自己写的参数」。

```
$ ls(){ echo "  【函数版】我把真的 ls 挡掉了"; }
ls /nonexistent-x
printf "  → 屏幕上没有 ls 的结果，函数吃掉了参数（退出码 %s）\n" "$?"
  【函数版】我把真的 ls 挡掉了
  → 屏幕上没有 ls 的结果，函数吃掉了参数（退出码 0）
[退出码 0]
```

↑ 屏幕上没有 `ls` 的结果：`/nonexistent-x` 这个参数**原封不动交给了函数**，函数把它当垃圾忽略了，
于是既没报错也没列出任何东西，退出码 **0**。这就是遮蔽最阴的地方：
**被顶掉的那个命令连一句「我听不见你」都不会说**，而你的函数还稳稳退 0。

**第二格：第一条路 —— `command`。**

```
$ ls(){ echo "  【函数版】我把真的 ls 挡掉了"; }
command ls /nonexistent-x
printf "  → command 一挡在前面就绕过函数，拿到真 ls 的原文与码（退出码 %s）\n" "$?"
ls: cannot access '/nonexistent-x': No such file or directory
  → command 一挡在前面就绕过函数，拿到真 ls 的原文与码（退出码 2）
[退出码 0]
```

同一个函数还在表里，只是词前面多了 `command`：屏幕上立刻出现真 `ls` 的报错原文，
退出码 **2** —— 原文和码一起拿回来了。`command` 的作用是把「查函数表」这一步跳过去，
按普通命令走一遍（它也顺带绕过别名）。

**第三格：第二条路 —— `builtin`。**

```
$ true(){ echo "  我的 true 抢在内建前面"; }
true
builtin true
printf "  → builtin 强制走内建，退出码=%s\n" "$?"
  我的 true 抢在内建前面
  → builtin 强制走内建，退出码=0
[退出码 0]
```

`true` 被函数顶掉之后，裸 `true` 打的是函数那行，`builtin true` 什么也不打
（内建 `true` 本来就不输出），但它的退出码是 **0** —— 也就是说这次走的是内建，不是函数。
`builtin` 比 `command` 更窄：它**只**走内建，你要顶掉的是文件就得换第三条路。

**第四格：第三条路 —— 绕开名字表，走 PATH。**

```
$ true(){ echo "  我的 true"; }
/usr/bin/env true
printf "  → 第三条路：写出绝对路径/走 env，查的是 PATH 而不是名字表，退出码=%s\n" "$?"
  → 第三条路：写出绝对路径/走 env，查的是 PATH 而不是名字表，退出码=0
[退出码 0]
```

这一格的证据是**屏幕上少了什么**：明明定义了一个会 echo 的 `true` 函数，
`/usr/bin/env true` 跑完却一个函数版的字都没印，退出码 **0** ——
因为 `env` 自己是外部命令，它按 PATH 去找磁盘上那个 true，压根不看 bash 的函数表。

**这一节带走：**

- 三条夺回路：`command`（绕过函数与别名）、`builtin`（只走内建）、绝对路径 / `env`（绕名字表也绕 PATH）。
- 被遮蔽时**不会有任何提示**：参数被函数吃掉、退出码照抄函数自己的，所以要判成败就得自己看码。
- 既然函数排在最前面，包装函数里那句「我要调真的那个」就必须写 `command ls`，否则按第 15 节的顺序它又落回自己。
- 本手册第 21 节那个库里统一用 `command`。

## 17. exportfun.sh 完整跑：函数能不能跨进程

主线③的最后一支：**函数是那个 bash 进程里的对象，不是磁盘上的文件**。
`export -f` 传的是**文本快照**（写进环境变量），别名压根不在这张表里。
八格全在 `xpf_` 前缀的名字上做（这一段本身就示范了「起名带前缀」），沙箱目录是 `exp/`。

**第 1 格：同一个进程看得见，换个新进程就看不见。** 直觉是「我 `source` 过 / 定义过了，孩子也该有」。

```
$ bash exportfun.sh
=== 1. 同一个进程看得见，换个新进程就看不见 ===
  本进程里 type -t xpf_hello → function
  本进程里直接调用：
    〔xpf_hello 真的跑了〕
  换一个新的 bash 进程跑同一条命令（bash -c "xpf_hello"）：
    原文=[bash: line 1: xpf_hello: command not found] ｜ 退出码=127
  → ★ 函数没导出 = 只存在于当前这个 bash 进程的函数表里；bash -c 起的是新进程，那张表从零开始。
```

本进程里 `type -t xpf_hello` 说它是函数，直接调它真的跑了；
换一个 `bash -c "xpf_hello"`，屏幕上给的是那句「找不到命令」的原文、退出码 **127**。
注意这一格的 127 和上一节那种「被遮蔽」不同：这里是**新进程的函数表从零开始**，
`bash -c` 起的是 exec 出来的全新进程，不是当前进程的影子。

**第 2 格：`export -f` 之后，同一条命令的差别。**

```
=== 2. export -f 之后：同一条命令的输出差别（两处都是真实原文） ===
  export -f 之后再 bash -c "xpf_hello"：
    〔xpf_hello 真的跑了〕
    退出码=0
  对照组：新进程里先 unset -f 再调（等于没导出）：
    原文=[bash: line 1: xpf_hello: command not found] ｜ 退出码=127
  → export -f 不是「让函数更厉害」，是把它的**文本**写进环境变量，好让下一个 bash 进程读得到。
```

导出之后 `bash -c "xpf_hello"` 打出的是那个函数自己的输出，退出码 **0**；
对照组在**新进程里**先 `unset -f` 再调，回到 127。
`export -f` 不是「让函数更厉害」，是把它的文本写进环境变量，好让下一个 bash 进程读得到。

**第 3 格：导出之后 env 里那一行长什么样。**
直觉是「导出来的东西总该像个正常的变量」。

```
=== 3. 导出后 env 里的键名形状（用判定，不依赖本机具体函数集合） ===
  env 里和这个函数有关的那一行（整行原文）：
    BASH_FUNC_xpf_hello%%=() {  printf '    〔xpf_hello 真的跑了〕\n'
  键名 = [BASH_FUNC_xpf_hello%%]
    → 以 BASH_FUNC_ 开头吗：是 ｜ 名字两侧夹了双百分号吗：是
  值 = [() {  printf '    〔xpf_hello 真的跑了〕\n']
    → 以 "() {" 开头吗：是 ← 值就是函数体文本，不是一个路径
  printenv "BASH_FUNC_xpf_hello%" 单独取出来（注意它是跨行的）：
    () {  printf '    〔xpf_hello 真的跑了〕\n'
    }
  ★ 键名里那两个 % 不是笔误，是 bash 的固定包裹；正常环境变量名不允许有 %，所以这一行很扎眼。
```

三个判定都成立：键名以 `BASH_FUNC_` 开头、两侧夹了双百分号、值以 `() {` 开头 ——
**值的形状就是函数体本身，不是一个路径**。`printenv` 单独取出来那一行更是跨了两行
（第二行只剩一个 `}`），这正是末尾 ★ 说的：那两个 `%` 不是笔误，是 bash 的固定包裹，
而正常环境变量名不允许有 `%`，所以这一行在 `env` 输出里非常扎眼。
这一整套形状是 bash 自己的：第 22 节会让 `/bin/sh`（本机是 dash）来执行同一条导出，当场撞墙。

**第 4 格：别名不跟着 `export -f` 走。** 直觉是「别名和函数都是『一个词的缩写』，应该一起导」。

```
=== 4. 别名不会跟着 export -f 走（真实报错原文） ===
  先做一个别名，再看它进不进函数表（都在新进程里跑）：
    declare -F xpf_ll → []（空 = 别名压根不在函数表里）
    export -f 一个别名名字 → 原文=[bash: line 1: export: xpf_ll: not a function] ｜ 退出码=1
  → 别名是「读代码时的一次文字替换」，函数是「进程里一个真正的对象」；两条线，export -f 只认函数。
```

在新进程里做一个别名，`declare -F` 查它得到的是**空** —— 别名压根不在函数表里；
`export -f` 一个别名名字直接撞出原文报错，退出码 **1**。
别名是**读代码时的一次文字替换**，函数是**进程里一个真正的对象**，两条线不互通。

**第 5 格：`( )` 子 shell / `{ }` 分组 / `bash -c`，谁能看见函数。**
这是第 5 节那条「命令替换是子 shell」在函数表上的版本。

```
=== 5. ( ) 子 shell / { } 分组 / bash -c：谁看得见函数 ===
  定义 xpf_g 后，三种「换个写法调用」的结果：
    { xpf_g; } 分组      → [看见 xpf_g] ← 就是当前进程本身，当然看得见
    ( xpf_g )   子 shell → [看见 xpf_g] ← 当前进程 fork 的副本，函数表一起抄走
    bash -c xpf_g 新进程 → [bash: line 1: xpf_g: command not found]
  现在把同名函数导出，再走一次 bash -c：
    bash -c xpf_g（已导出）→ [看见 xpf_g]
  → ★ 判据：( ) 和 { } 都还是**同一个进程**（前者是它的 fork 副本，函数表跟着抄），所以看得见；
    bash -c 是 exec 一个全新进程，函数表从零开始，不 export 就看不见 —— 上面那个原文就是它说的。
```

`{ xpf_g; }` 看得见、`( xpf_g )` 也看得见、`bash -c xpf_g` 看不见（原文就是 127 那句），
把同名函数导出之后 `bash -c` 又看得见。判据是：`( )` 和 `{ }` 都还是**同一个进程**
（前者是它 fork 出来的副本，函数表跟着一起抄），所以看得见；
`bash -c` 是 exec 一个全新进程，那张表从零开始。
**「子 shell 里改的变量带不回来」和「子 shell 里能读到父进程的函数」是同一件事的两面：fork 抄表，exec 不抄。**

**第 6 格：导出的是「那一刻的文本」。** 直觉有两个，都不全对：
要么以为「导出之后就固定了，父进程再改孩子也不变」，要么以为「父进程改了孩子跟着变」。

```
=== 6. 导出的是「那一刻的文本」：已启动的孩子冻旧版，之后新起的孩子拿新版 ===
  在重新定义**之前**就 fork 出去的那个后台子进程，打印的是：[OLD_导出那一刻的文本]
  父进程自己现在打印的是：[NEW_父shell后来重新定义]
  重新定义**之后**才新起的 bash -c，打印的是：[NEW_父shell后来重新定义]
  → ★ 反直觉在中间和最后两行：子进程只认**它自己 exec 那一刻** env 里躺着的那份文本，冻住就不回头同步；
    所以「旧定义不变」说的是已经跑起来的那个孩子；bash 5.3 在父进程重新定义时会刷新 env，故之后新起的孩子看到新版。
```

三行把中间态钉死了：在重新定义**之前**就 fork 出去的那个后台子进程打印的是旧文本，
父进程自己现在打印的是新文本，重新定义**之后**才新起的 `bash -c` 打印的是新文本。
所以「旧定义不变」只适用于**已经跑起来的那个孩子**：它认的是自己 exec 那一刻 env 里躺着的那份文本，
冻住之后不回头同步。而父进程这一支是 bash 5.3，重新定义时它会把 env 里那份刷新一次，
所以之后新起的孩子看到的就是新版 —— 两个直觉各对一半，分界线是「孩子起于哪一刻」。

**第 7 格：真实代价。** 这一格只报实测到的量：差值和「能不能查到」，不报绝对计数。

```
=== 7. 真实代价（只写实测到的）：每一个子进程都被塞，env 输出变难读 ===
  同一个进程里多导出一个 3 行体的函数，env 行数净增 4 行（★ 只取差值：绝对值随启动环境变，不当证据）
  再确认它跟着进每一个 fork 出去的孩子（只报「孩子里能不能查到」，不报绝对计数）：
    孙子进程里能查到 xpf_child 这个 BASH_FUNC_ 条目吗 → 查到了
  → 实测到的风险：export -f 会把函数塞进**每一个**子进程的环境；函数体一带换行，env 输出里就冒出
    跨行、带空格和 () { 的怪条目，肉眼很难对齐 —— 所以生产脚本用「磁盘上的脚本 + 显式 source」传函数，而不是到处 export -f。
```

同一个进程里多导出一个 3 行体的函数，`env` 行数净增 **4** 行（只取差值，绝对值随启动环境变，不当证据）；
再往下一层确认：孙子进程里能查到那个 `BASH_FUNC_` 条目 —— **查到了**。
风险就在这两行连起来的地方：`export -f` 会把函数塞进**每一个**子进程的环境，
函数体一带换行，`env` 的输出里就冒出跨行、带空格和 `() {` 的怪条目，肉眼很难对齐。
所以生产脚本传函数的正解是「磁盘上的脚本 + 显式 `source`」，而不是到处 `export -f`。

**第 8 格：收口。**

```
=== 8. 收口 ===
  删之前 exp/ 里有 1 个文件 ｜ 现在执行 rm -rf exp（trap 里是同一句，这里提前跑一遍好自证）
  自证：现场目录 exp/ 还在吗 → 不在了 ｜ ls -A 里名为 exp 的条目数 = 0
  自证：本脚本自己的后台作业表 jobs -p 行数 = 0（第 6 段那个孩子已经 wait 收掉了）
  ① 函数是**进程里的对象**：type -t 说它在本进程存在，bash -c 起的下一个进程默认读不到它。
  ② export -f 走的是环境变量这条路：键名 BASH_FUNC_名字%%、值以 () { 开头 —— 传的是文本快照不是活引用。
  ③ 别名不在函数表里（declare -F 查为空），export -f 撞它会当场报「不是函数」rc=1。
  ④ 想跨进程传函数，正解是把函数写进磁盘上的脚本再 source，而不是到处 export -f。

`exp/` 里删之前有 **1** 个文件（就是第 6 格那个孩子的落盘输出），删完当前目录里名为 exp 的条目数 **0**；
本脚本自己的后台作业表行数 **0** —— 第 6 格那个孩子已经 `wait` 收掉了，不是漏在那儿。
四条判据合上主线③：函数是进程里的对象；`export -f` 走环境变量这条路、传的是文本快照不是活引用；
别名不在函数表里、撞它会当场 rc=1；想跨进程传函数就用「磁盘脚本 + source」。

**这一节带走：**

- 函数默认**不跨进程**：`bash -c` 起的下一个进程读不到它（rc=127），`( )` 和 `{ }` 能读到（同一个进程或它的 fork 副本）。
- `export -f` 的产物是环境变量里一条 `BASH_FUNC_名字%%` = 以 `() {` 开头的**文本快照**。
- 别名不在函数表里：`declare -F` 查为空，`export -f` 撞它 rc=1。
- 已启动的孩子冻在它 exec 那一刻的那份文本；之后新起的孩子才可能拿到新版。跨进程传函数，用磁盘脚本 + `source`。

## 18. 小证据：负对照 —— 什么都不做时，孙子进程就是看不见

第 17 节把 `export -f` 演通了，但「通了」这句话单独放着没有价值 ——
**没有负对照，你不知道是函数真的跨过去了，还是那条命令本来就不需要函数。**
这一节把对照组补齐：同一个 `have`，同一个 `bash -c`，只差 `export -f` 那一句。

先用最普通的写法（不导出）：

```
$ have(){ command -v "$1" >/dev/null 2>&1; }
bash -c "have bash"; printf "  没导出时，孙子进程里调用它的退出码=%s（上面是原文错）\n" "$?"
bash: line 1: have: command not found
  没导出时，孙子进程里调用它的退出码=127（上面是原文错）
[退出码 0]
```

屏幕上两行都是要看的：`bash: line 1: have: command not found` 是**孙子进程里的 bash 自己打的**
（`line 1` 指它读到的那条 `bash -c` 字符串的第一行），下面那行是我们把它兜下来的码：**127**。
回到第 03 章那张码表，127 的原文含义就是「命令名找不到」——
所以在孙子进程眼里，**一个没导出的函数和一个根本不存在的命令，下场逐字相同**：
同一个报错格式、同一个 127。函数不是文件，也不在 `$PATH` 上，名字表里没有它，bash 只能报「command not found」。

现在只加那一句：

```
$ have(){ command -v "$1" >/dev/null 2>&1; }
export -f have
bash -c "have bash"; printf "  export -f 之后，同一条命令的退出码=%s（0 = 找到了，函数活着）\n" "$?"
  export -f 之后，同一条命令的退出码=0（0 = 找到了，函数活着）
[退出码 0]
```

同一条 `bash -c "have bash"`，报错那一行**整行消失**，码变成 0。
两格摆在一起才叫证据：唯一的差别就是 `export -f have`，
它做的事是把函数定义序列化成环境变量，交给新起的 bash 在初始化时读回名字表。

然后是这一节真正想教的东西 —— **怎么让一道「恒 0 的守卫」不骗人**。
先数不导出时环境里有没有那个键：

```
$ have(){ command -v "$1" >/dev/null 2>&1; }
printf "  不导出时 env 里的同名条目数=%s（★ 恒 0 的守卫等于没守卫，下一条专门把它弄响）\n" "$(env | grep -c "^BASH_FUNC_have")"
  不导出时 env 里的同名条目数=0（★ 恒 0 的守卫等于没守卫，下一条专门把它弄响）
[退出码 0]
```

这个 0 本身**不能当证据**：任何 `grep -c` 在匹配不到时都印 0，
所以「印了 0」既可能是「真的干净」，也可能是「这道守卫根本找不到东西」。
于是紧接着把同一道守卫**故意弄响一次**：

```
$ have(){ command -v "$1" >/dev/null 2>&1; }; export -f have
printf "  导出之后同名条目数=%s（同一道守卫，非 0 —— 说明它真的能响）\n" "$(env | grep -c "^BASH_FUNC_have")"
  导出之后同名条目数=1（同一道守卫，非 0 —— 说明它真的能响）
[退出码 0]
```

同一个式子，导出之后数到 1 —— 说明这条 `env | grep -c "^BASH_FUNC_have"` 真的能看见目标，
那么上一条的 0 才是「确实没导出」，而不是「眼睛是瞎的」。
这条规矩本章用了三次（第 18 节的这道键名守卫、第 23 节的格数守卫、第 24 节的禁词守卫），
**形状都是同一个：先让它响，再让它 0**。

> 一句话判据：**「测出来是 0」要先回答「这道检查有没有能力测出非 0」。**
> 答不出来，这个 0 就只是屏幕上的一行字。

## 19. argpass.sh 完整跑：函数的参数从哪来

这一节把第 02 章（词与展开）的账在函数上收一次：**函数调用的括号，就是一次展开现场**。
七格：位置参数换层、`"$*"` 与 `"$@"`、IFS 只影响谁、`set --` 的边界、三种传参写法的真实后果、
词边界由谁决定、收口自证。

```
$ bash argpass.sh
=== 1. 函数一进来，看到的 $# 是传进来的个数，脚本级 $@ 不见了 ===
  脚本级：$#=3  $1=[脚本甲]  "$*"=[脚本甲 脚本乙 脚本丙]
  调用 show 传两个：
    函数里：$#=2  $1=[x]  $2=[y]
  调用 show 一个都不传（★ 函数里看到的是 0，不是脚本级那 3 个）：
    函数里：$#=0  $1=[（无）]  $2=[（无）]
  回到脚本级：$#=3  $1=[脚本甲]（一点没被 show 影响）
  → ★ 位置参数是「每次调用临时换上去的一组」：函数体里读到的 $1..$# 永远是这次的，脚本级那组进不来。
```

第一格先把最容易误会的一件事钉死：脚本级有 3 个参数（`脚本甲 脚本乙 脚本丙`），
把 `show` 叫起来**一个都不传**时，函数里看到的是 `$#=0`，不是那 3 个。
位置参数不是「全局的一个数组」，它是**每次调用临时换上的一组**，函数返回后 bash 再把外层那组还原回来
（最后一行 `回到脚本级：$#=3` 就是还原的证据）。这也解释了为什么 `f "$@"` 在函数里读到的永远是这一次的。

```
=== 2. "$*" 拼成一行 vs "$@" 分成多个词（默认 IFS，逐字贴）===
  用 f2 "p q" r s 调用（第一个词自带空格）：
    "$*"=[p q r s]（7 个字符，是 1 个词）
    "$@" 逐元素：[p q] [r] [s]   ← 共 3 个元素
  → "$*" 把所有参数用空格粘成 1 个词；"$@" 保持每个参数各自一个词（含它自带的空格）。
```

第二格是 `"$*"` 与 `"$@"` 的分水岭，用**自带空格的第一参数**才看得出来：
调用 `f2 "p q" r s`，`"$*"` 得到 `[p q r s]` —— 屏幕上标了「7 个字符，是 1 个词」，
因为 `p q`、`r`、`s` 被空格粘成一坨，**词边界信息没了**；
`"$@"` 得到 `[p q] [r] [s]` 三个元素，各自独立。
一句话记法：`"$*"` 是「把所有参数写成一句话」，`"$@"` 是「把所有参数原样搬过去」。

```
=== 3. IFS 改成 - 再各演一次（只有 "$*" 受影响）===
  IFS=- 后 f3 "p q" r s（在子 shell 里只改这一次的 IFS）：
    "$*"=[p q-r-s]   "$@" 元素数=3
      [p q]
      [r]
      [s]
  → ★ "$*" 用当前 IFS 的第一个字符当粘合剂（这里变成 -）；"$@" 不受 IFS 影响，元素照旧分开。
```

第三格把 IFS 改成 `-` 再演一次，这是分辨两者的最快实验：
`"$*"` 变成 `[p q-r-s]` —— 粘合剂换了，因为它用的就是**当前 IFS 的第一个字符**；
`"$@"` 的三个元素**一个字没变**。
所以「IFS 一改，行为跟着改的那个」是 `"$*"`，`"$@"` 对 IFS 免疫（它不做拼接，也就不需要粘合剂）。
顺带注意这格是在子 shell 里只改这一次的 IFS：`( IFS=- ; f3 ... )`，改完就散，不脏外面的环境。

```
=== 4. 函数里写 set -- 新值，会不会改写外层的位置参数？===
  外层调用前：$#=2  "$*"=[外层甲 外层乙]
    函数里 set -- 之后：$#=4  "$*"=[新1 新2 新3 新4]
  外层还剩几个 → $#=2  "$*"=[外层甲 外层乙]（★ 返回时 bash 把外层的还原回来了）
  → set -- 在函数里只动这一层的位置参数；返回后 bash 自动恢复调用前那组，外层不脏。
```

第四格回答一个很多人靠猜的问题：函数里写 `set -- 新1 新2 新3 新4`，会不会把外层的参数改掉？
屏幕上函数内 `$#=4`，函数返回后外层仍是 `$#=2`、`"$*"=[外层甲 外层乙]`。
`set --` 的作用范围是**这一层调用**的位置参数，返回时 bash 自己还原。
它是「在函数里重排自己的参数」的正经手段（配合 `shift` 做参数解析），不是污染外层的后门。

```
=== 5. 三种传参写法的真实后果（通配实验在 ap/ 里做）===
  造了 ap/one.txt ap/two.txt；令 v="ap/one.txt ap/two.txt ap/*.txt"
  ① 不带引号 collect $v（词分割 + 通配展开同时发生）：
    收到 4 个词：[ap/one.txt] [ap/two.txt] [ap/one.txt] [ap/two.txt] 
  ② 带引号 collect "$v"（正解：1 个词，星号原样不展开）：
    收到 1 个词：[ap/one.txt ap/two.txt ap/*.txt] 
  ③ 数组整个传 collect "${arr[@]}"（每个元素一个词，含空格那个不被切）：
    收到 3 个词：[两个 词] [单独] [又一个] 
     对照不带引号 collect ${arr[@]}（★ 空格又被二次切开，元素数变了）：
    收到 4 个词：[两个] [词] [单独] [又一个] 
  → 不带引号会先按 IFS 拆词、再对每段做通配展开：v 本是 3 个源词，第三段 ap/*.txt 被展成两个真文件，
    一个词顶替成两个，于是实测收到 4 个词（比你要传的还多）。传参默认就该 "$var"；传数组用 "${arr[@]}"。
```

第五格是本章最容易出线上事故的一格，通配实验放在 `ap/` 沙箱子目录里做。
先看 `v="ap/one.txt ap/two.txt ap/*.txt"` 这**一个变量**里塞了 3 段文本，其中第三段是通配。

| 写法 | 屏幕上收到 | 为什么 |
| --- | --- | --- |
| `collect $v`（不带引号） | **4 个词**：`[ap/one.txt] [ap/two.txt] [ap/one.txt] [ap/two.txt]` | 先按 IFS 拆成 3 段，再对每段做通配展开：第三段 `ap/*.txt` 命中两个真文件，**一个词顶替成两个** |
| `collect "$v"`（带引号，正解） | **1 个词**：`[ap/one.txt ap/two.txt ap/*.txt]` | 引号把拆词和通配同时关掉，星号原样传进去 |
| `collect "${arr[@]}"` | **3 个词**：`[两个 词] [单独] [又一个]` | 数组每个元素各自一个词，元素里的空格不被切 |
| `collect ${arr[@]}`（不带引号） | **4 个词**：`[两个] [词] [单独] [又一个]` | 二次拆词把「两个 词」这个元素劈成两半，**元素数变了** |

看第一行：**不带引号的后果不是「少一个参数」，而是「多一个参数」** —— 数字对不上你写的那个变量，
而它偏偏是最像「正常」的那种错（每个词都还在，只是凭空多了一个）。这就是第 02 章那条
「引号不是美化，是词边界」在函数调用点的账单。

```
=== 6. 名字接不住值：格数差别用 $# 计数 ===
  x="hello world there"（中间两个空格）
  count $x   →    收到 3 个参数
  count "$x" →    收到 1 个参数
  → 同一个名字、同一个值：不带引号被拆成 3 个，带引号还是 1 个。词边界不是「值」决定，是引号决定。
```

第六格把这件事压到最小：同一个 `x="hello world there"`，
`count $x` → 3 个参数，`count "$x"` → 1 个参数。
**词边界不是「值」决定的，是引号决定的。** 值里有没有空格，只决定「不加引号会不会出事」，
不决定「加了引号还出不出事」。

```
=== 7. 收口 ===
  删之前 ap/ 里有 2 个文件 ｜ 现在 rm -rf ap ｜ 之后名为 ap 的条目数=0
  自证：本脚本作业表 jobs -p 行数=0（全程没用过 &）
  ① 函数体里的 $1..$# 永远是这次调用传进来的一组；脚本级位置参数在函数里看不见，返回后原样回来。
  ② "$*" 粘成一行（受 IFS 影响）、"$@" 保持每参数一个词（不受 IFS 影响）—— 转发参数一律用 "$@"。
  ③ 传参带引号 "$var"、传数组 "${arr[@]}"；不带引号会同时触发拆词和通配展开，值里有空格或 * 就坏。
[退出码 0]
```

第七格是收口，同时也是这个脚本的自证：`ap/` 里造了 2 个文件，`rm -rf ap` 之后条目数 0，
`jobs -p` 行数 0（全程没用过 `&`）。三句能带走的话写在最后，
其中第②句「转发参数一律用 `"$@"`」下一节单独钉。

## 20. 小证据：转发参数只有一个姿势

写包装函数（`outer` 里调 `inner`）时，能传对的写法只有一种，其余写法都**在悄悄改变格数**。
先立「什么叫对的」：

```
$ show(){ printf "  收到 %s 个：\n" "$#"; for a in "$@"; do printf "    [%s]\n" "$a"; done; }
show "a b" "" c
  收到 3 个：
    [a b]
    []
    [c]
[退出码 0]
```

`show "a b" "" c` —— 一个带空格的、一个**空串**、一个普通词。屏幕上 `$#=3`，
三个元素分别打成 `[a b]`、`[]`、`[c]`。这里最值钱的是那个 `[]`：**空串也占一格**。
很多转发写法不会报错，只会把空串吞掉，于是第 3 格悄悄变成第 2 格。

再看同一条数据在三种写法下的格数：

```
$ count(){ printf "%s\n" "$#"; }
x="a b"
printf "  不加引号 f \$x      → %s 个\n" "$(count $x)"
printf "  加引号   f \"\$x\"    → %s 个\n" "$(count "$x")"
printf "  转发     f \"\$@\"    → 见下一条"
  不加引号 f $x      → 2 个
  加引号   f "$x"    → 1 个
  转发     f "$@"    → 见下一条[退出码 0]
```

`x="a b"`：不加引号 2 个、加引号 1 个。
注意屏幕上第三行是 `  转发     f "$@"    → 见下一条[退出码 0]` ——
这句 `printf` 结尾**没写 `\n`，所以 `[退出码 0]` 直接贴在了句子后面**。
这行原样保留，不美化：它就是「printf 少一个换行」在屏幕上的下场，
你在自己的脚本里迟早会撞见同一张脸（第 07 章数行数时会再撞上）。

最后是真·转发现场，三层名字都不重：

```
$ inner(){ printf "  inner 看到 %s 个：" "$#"; for v in "$@"; do printf "[%s] " "$v"; done; echo; }
outer(){ inner "$@"; }
outer "带 空格" "" 单个
  inner 看到 3 个：[带 空格] [] [单个] 
[退出码 0]
```

`outer "带 空格" "" 单个` → `inner "$@"` → `inner 看到 3 个：[带 空格] [] [单个]`。
`outer` 自己不碰参数，只是 `inner "$@"`，格数原样穿过两层。
把 `"$@"` 换成 `"$*"` 会怎样？第三格那种「一格长文本」的下场：`inner` 会只看到 1 个元素，
里面装着 `带 空格  单个`（空串粘进去后连分隔都变得含糊）。
换成 `$@`（不带引号）呢？带空格那个元素被拆成两半，格数变多 —— 和第 19 节第五格同一个机制。

> **判据**：包装函数里唯一正确的转发是 `"$@"`。
> 只要屏幕上 `$#` 不等于你传进去的项数，就先把转发写法换成 `"$@"` 再比。

## 21. 综合演练：一个能上线的小函数库

前面 20 节的规矩在这一节拼成一个可以直接抄进生产脚本的库。
它只有五个函数，每个都对应本章某一节的一条硬结论：
日志走 stderr（第 5、7 节）、失败用 `return` 不用 `exit`（第 3、9 节）、
中间变量一律 `local`（第 11、12、13 节）、转发只用 `"$@"`（第 19、20 节）、
查命令用 `command -v`（第 16 节）。

```
$ cat lib/fnlib.sh
# 本章的收尾件：一个可以直接抄进生产脚本的小函数库。
# 它没有一个 echo 走 stdout（除了「给出数据」的那一个），所以任何一句都能安全地被 $( ) 捕获。

log()  { printf 'log: %s\n' "$*" >&2; }            # 诊断：只上 stderr，永远不污染捕获
die()  { printf 'die: %s\n' "$*" >&2; return 1; }   # 报告并交出一个非 0，杀不杀由调用方决定
have() { command -v "$1" >/dev/null 2>&1; }         # 命令存在吗：答案在 $? 里，不在输出里

# retry <最多几次> <命令...>：靠退出码轮询。故意不 sleep —— 耗时每跑必变，本章不上屏。
retry() {
  local max="$1" i=1
  shift
  while [ "$i" -le "$max" ]; do
    if "$@"; then
      printf 'retry: 第 %s 次成功\n' "$i" >&2
      return 0
    fi
    printf 'retry: 第 %s 次失败\n' "$i" >&2
    i=$((i + 1))
  done
  return 1
}

# last_line：真正的「返回数据」——把 stdout 交出去，同时用 local 接住尾换行的后果。
last_line() {
  local all
  all="$("$@")"
  printf '%s\n' "${all##*$'\n'}"
}
[退出码 0]
```

逐句看这个库为什么这么写：

- `log()` 用 `printf 'log: %s\n' "$*" >&2`。这里**故意用 `"$*"`**：日志就是把一堆参数拼成一句话给人看，
  粘成一坨正是想要的效果；关键是 `>&2`，它保证 `$( )` 捕获时永远不会把日志当数据。
- `die()` 末尾是 `return 1` 而不是 `exit 1`。这一条决定了「报告失败」和「终止脚本」是两个人的事：
  `die` 只交出码，杀不杀由调用方决定 —— 库函数擅自 `exit` 会把上层脚本的清理逻辑整段跳过。
- `have()` 里 `command -v "$1" >/dev/null 2>&1`：**答案在 `$?` 里，不在输出里**。
  `command -v` 顺带绕开了第 16 节那条「函数名遮蔽同名命令」的坑（它查的是「这个名字能否执行」）。
- `retry()` 用 `local max="$1" i=1` + `shift`，然后 `while` 里 `if "$@"` ——
  被重试的命令是**原样转发的 `"$@"`**，所以带空格、带空串的参数都能穿过去。
  它**故意不 sleep**：睡眠时长、耗时这类数字每跑必变，进了捕获这份材料就不再可复现。
- `last_line()` 是全章唯一「返回数据」的写法：`all="$("$@")"` 先把 stdout 整坨接住，
  再用 `${all##*$'\n'}` 从前面贪心吃掉「最后一个换行之前的一切」，把最后一行交出去。
  这里必须用 `local all` —— 不 local 的话，任何一个调用方只要也有变量叫 `all`，就会被覆盖（第 11 节那条链）。

五个函数各自的实测：

```
$ cd lib || exit 1
source ./fnlib.sh
log 启动 "两个参数"
v=$(log 这条不会进 v; echo 真正的值)
printf "  捕获结果=[%s] 长度=%s ｜ ★ log 走 stderr，所以捕获干干净净\n" "$v" "${#v}"
log: 启动 两个参数
log: 这条不会进 v
  捕获结果=[真正的值] 长度=4 ｜ ★ log 走 stderr，所以捕获干干净净
[退出码 0]
```

`v=$(log 这条不会进 v; echo 真正的值)` → `捕获结果=[真正的值] 长度=4`。
屏幕上 `log:` 那两行是 stderr（它们照样出现在屏幕上，因为 2>&1 汇到同一个终端），
但 `v` 里干干净净只有 4 个字符。这就是第 5 节「第三刀：诊断写进 stdout 就污染返回值」的正解。

```
$ cd lib || exit 1
source ./fnlib.sh
have bash;      printf "  have bash（本机在）        → 码=%s\n" "$?"
have 没有这个命令; printf "  have 没有这个命令（不在）  → 码=%s\n" "$?"
  have bash（本机在）        → 码=0
  have 没有这个命令（不在）  → 码=1
[退出码 0]
```

`have bash` → 0，`have 没有这个命令` → 1。
两个词都是中文，`command -v` 找不到就是找不到，返回 1；**它没有打印任何东西**，
所以这个函数被 `$( )` 捕获也是安全的。

```
$ cd lib || exit 1
source ./fnlib.sh
n=0
flaky(){ n=$((n + 1)); [ "$n" -ge 3 ]; }
retry 5 flaky; printf "  前两次必失败、retry 5 次额度 → 最终码=%s（计数器 n=%s）\n" "$?" "$n"
retry 2 flaky; printf "  再给 2 次额度（此时 n 已 >=3）→ 最终码=%s\n" "$?"
retry: 第 1 次失败
retry: 第 2 次失败
retry: 第 3 次成功
  前两次必失败、retry 5 次额度 → 最终码=0（计数器 n=3）
retry: 第 1 次成功
  再给 2 次额度（此时 n 已 >=3）→ 最终码=0
[退出码 0]
```

`flaky(){ n=$((n + 1)); [ "$n" -ge 3 ]; }` —— 前三次必失败。
`retry 5 flaky` 的屏幕：`第 1 次失败`、`第 2 次失败`、`第 3 次成功`，最终码 0、计数器 n=3。
紧接着 `retry 2 flaky` 给出 2 次额度时 n 已经 ≥3，所以 `第 1 次成功`、码 0。
这两条合起来验的是「retry 真的按退出码轮询，且额度用完会 `return 1`」——
注意 `flaky` 没有 `local n`，它是**故意**用全局计数器的：这样重试次数能从外部观察得到。
（第 11 节讲的是「中间变量必须 local」，这里不是反例，是「要跟外部通话的变量」的另一类。）

```
$ cd lib || exit 1
source ./fnlib.sh
if die "这一步炸了"; then echo "  不该走到 then"; else echo "  die 交出一个码，但脚本还活着 → 这行印出来了"; fi
printf "  die 之后还能继续说话，说明它用的是 return 不是 exit\n"
die: 这一步炸了
  die 交出一个码，但脚本还活着 → 这行印出来了
  die 之后还能继续说话，说明它用的是 return 不是 exit
[退出码 0]
```

`if die "这一步炸了"; then ... else ... fi` → 走 else，然后 `die` 之后脚本**还能继续说话**。
这就是 `return` 和 `exit` 的分工：`die` 交出 1，`if` 拿到 1，进程还活着，后面的 printf 照常执行。
如果 `die` 里写的是 `exit 1`，屏幕上只会有一行 `die:`，后面两句都不会出现
（第 9 节把这条演成了「还剩多少话要说」）。

```
$ cd lib || exit 1
source ./fnlib.sh
printf "  last_line 拿数据：[%s]\n" "$(last_line printf "1\n2\n3\n")"
  last_line 拿数据：[3]
[退出码 0]
```

`last_line printf "1\n2\n3\n"` → `[3]`。
这格是「函数返回数据」的最短正解：数据走 stdout，被调用方用 `$( )` 接，
尾换行被吃光之后用 `${all##*$'\n'}` 定位最后一行（第 6 节那把「尾部换行全吃光」的账在这里付清）。

> 这个库没有一个函数同时干两件事：**码是码、文本是文本、名字是名字**。
> 抄的时候请记住第 22 节 —— 这个库怎么交给另一个进程，比它写得对不对还容易翻车。

## 22. 把这个库交给另一个进程：三条路，和 dash 的一堵墙

`source` 进来的函数只活在这一个进程里。要让「另一个进程」也拿到它，实测有三条路，
每条的边界都当场钉一遍，最后再撞一次 dash。

```
$ 〔在 lib 里〕 bash try_source.sh
  〔路①source〕本进程里 have 能用吗：
    能用（码 0）
  〔路①的边界〕同一个 have，孙子进程还是看不见：
bash: line 1: have: command not found
    ↑ 上面是原文错，退出码=127
[退出码 0]
```

路①：`source ./fnlib.sh` 之后，本进程里 `have` 能用（码 0）；
但同一个脚本里 `bash -c 'have bash'` 立刻打回原形 —— 报错 + 127，和第 18 节负对照逐字一样。
**source 的作用域是「当前进程的名字表」**，它不会自动往环境里塞任何东西。

```
$ 〔在 lib 里〕 bash try_export.sh
  〔路②export -f〕把定义塞进环境，交给新起的 bash：
    孙子进程能用 have（码 0）
  〔路②的代价〕env 里多了一个键名很怪的条目：
BASH_FUNC_have%%=<函数体，以 () { 开头>
[退出码 0]
```

路②：`export -f have` 之后，孙子进程的 `have bash` 码 0。
代价这一行现在是实打实的输出：`BASH_FUNC_have%%=<函数体，以 () { 开头>` ——
环境里多了一个键名长得就不正常的条目（bash 用 `%%` 来标记「这是函数」），
值是函数体的**文本**，初始化时被 `eval` 回名字表。所以「脏环境」不是修辞：
这个键会跟着**每一个**子进程，`env` 一屏都读不下去，而且键名里的函数名等于把实现公开了。

```
$ 〔在 lib 里〕 bash try_declare.sh
  〔路③declare -f〕把定义抄成纯文本，27 行：
  抄出来的第一行长这样：log () 
    新进程 source 这份文本就复活了（码 0）
[退出码 0]
```

路③：`declare -f log die have retry > funcs.inc` 把定义抄成纯文本，27 行，第一行长这样：`log () `。
新进程 `source ./funcs.inc` 之后 `have bash` 码 0 —— 复活成功。
这条路的要点是**它不依赖环境**：文本落到磁盘上就是普通文件，谁都能 source，
代价是要自己管版本（改了库得重新 dump）。

```
$ 〔在 lib 里〕 bash try_dash.sh
  本机 /bin/sh 的真身：/usr/bin/dash
  ① 同一个名字，让 dash 来执行 export -f：
sh: 1: export: Illegal option -f
    退出码=2（原文就在上面那行）
  ② 让 dash 执行 declare -f（本章第 22 节的路③靠它）：
sh: 1: declare: not found
    退出码=127
  ③ 让 dash 在函数外面写 local：
sh: 1: local: not in a function
    退出码=2
  ④ 把本章那个库文件整份交给 dash 读：
    退出码=0 ★ 库里那句 ANSI-C 转义（dollar-quote）dash 不认 —— 换 shell 就不是同一套语法
[退出码 0]
```

然后是墙。本机 `/bin/sh` 的真身是 `/usr/bin/dash`（第 1 节就钉过），四条全撞：

| 让 dash 干的事 | 屏幕上 bash 会说的话 | 码 |
| --- | --- | --- |
| `export -f have`（路②） | `sh: 1: export: Illegal option -f` | **2** |
| `declare -f`（路③） | `sh: 1: declare: not found` | **127** |
| 函数外面写 `local x=1` | `sh: 1: local: not in a function` | **2** |
| 直接 `sh ./fnlib.sh`（整份库） | 无报错 | **0** ★ |

前三行是「dash 没有这个能力」，报错格式还是第 03 章那套（`sh: 行号: 消息`）。
第四行最阴：**退出码 0 不代表能跑**。我们的 `last_line` 里用了 `$'\n'`（ANSI-C 转义），
dash 不认这个写法 —— 但脚本只被**读取**、那行没有被真正执行时，`sh ./fnlib.sh` 可以一路 0 走到尾。
所以「换个 shell 跑一遍看码」这种验收是假的：要验的是**功能**，不是退出码。
（对照第 15 节：同一份函数定义文件在 `/bin/sh` 里撞出来的原文不一样。）

> 三条路的分工，记这一句就够：
> **source 只管当前进程；`export -f` 能跨进程但把每个子进程的环境都弄脏，而且 dash/busybox 根本不认；
> `declare -f` 抄出来的纯文本是最 portable 的写法** —— 它落到磁盘上就成了「库文件」，
> 正好是第 15 节「函数不是磁盘上的文件」这句话的反面：把文本变成文件，它就可以了。

## 23. 对账：九个脚本各几格、合计几格、demo 自己几节

这一节不教新语法，只交付一件事：**这份材料有多少内容，是当场数出来的，不是作者报的**。
先看守卫能不能响 —— 故意用一个匹配不到任何东西的模式去数每个脚本的格数：

```
$ for f in retcode outcapture errmix trapreturn localscope recursion functype exportfun argpass; do
  printf "  %-12s 假守卫计数=%s\n" "$f" "$(grep -c "=== ZZZ-NOT-THERE " "$f.sh")"
done
echo "  ★ 全 0 —— 所以下面这条真计数必须非 0，否则同样不可信"
  retcode      假守卫计数=0
  outcapture   假守卫计数=0
  errmix       假守卫计数=0
  trapreturn   假守卫计数=0
  localscope   假守卫计数=0
  recursion    假守卫计数=0
  functype     假守卫计数=0
  exportfun    假守卫计数=0
  argpass      假守卫计数=0
  ★ 全 0 —— 所以下面这条真计数必须非 0，否则同样不可信
[退出码 0]
```

九个脚本全是 0。这一步的目的就是让「数到 0」变得**可疑**：
如果下面那条真计数也数不出东西，那整套对账都是纸糊的。
（这个模式在脚本源码里是 `=== ZZZ-NOT-THERE`，带一个尾随空格，任何脚本都不可能含有它。）

```
$ total=0
for f in retcode outcapture errmix trapreturn localscope recursion functype exportfun argpass; do
  n=$(grep -c "=== " "$f.sh")
  printf "  %-12s %s 格\n" "$f" "$n"
  total=$((total + n))
done
printf "  ★ 九个脚本合计 %s 格\n" "$total"
  retcode      7 格
  outcapture   6 格
  errmix       7 格
  trapreturn   7 格
  localscope   8 格
  recursion    7 格
  functype     7 格
  exportfun    8 格
  argpass      7 格
  ★ 九个脚本合计 64 格
[退出码 0]
```

换成真的 `grep -c "=== "`，每格数出来了：
`retcode 7`、`outcapture 6`、`errmix 7`、`trapreturn 7`、`localscope 8`、`recursion 7`、
`functype 7`、`exportfun 8`、`argpass 7`，**合计 64 格**。
这 64 个「格」是脚本源码里的分格标题行，而每一格都在前面的第 3~19 节里真实出现过
（每一格的屏幕输出都被完整搬进了这份捕获）。

> 为什么数 `'=== '` 而不是数 `'echo "=== '`？
> 因为本章有脚本用单引号写那句 echo（`recursion.sh`、`argpass.sh`），
> 用 `'echo "=== '` 去数会**恒 0**，那正是上面那格故意演示的假守卫。
> 数的字符串要挑「运行时和源码里长得一样」的那一段，这里就是 `=== ` 这个前缀。

再对两份账，一份是结构、一份是体量：

```
$ printf "  demo 自己的节标题数（grep ^banner）：%s\n" "$(grep -c "^banner " demo.sh)"
printf "  章目录里除 demo 外的脚本数：%s\n" "$(ls *.sh | grep -vc "^demo.sh$")"
  demo 自己的节标题数（grep ^banner）：24
  章目录里除 demo 外的脚本数：9
[退出码 0]
```

`demo.sh` 里 `^banner ` 的行数 = **24**，也就是这份捕获的节数；
章目录里除 demo 外的 `.sh` = **9**，正是九个取证脚本。

```
$ printf "  源文件行数：demo=%s ｜ 九脚本=%s\n" "$(wc -l < demo.sh)" "$(cat retcode.sh outcapture.sh errmix.sh trapreturn.sh localscope.sh recursion.sh functype.sh exportfun.sh argpass.sh | wc -l)"
  源文件行数：demo=538 ｜ 九脚本=1249
[退出码 0]
```

源文件行数：demo=538、九脚本=1249。
这两个数**每次改脚本都会变**，所以它只在「当场数」的语境里有意义 —— 正文引用它，
是因为这一页就是这一趟跑出来的，而不是「听说有 1200 行」。

## 一张表：函数的三本账 —— 码、名字、字节

第 05 章给循环记了三本账（名单、进程、收尾）。这一章给函数记三本，形状很像，但每一项都换了一层皮：

| 这本账记在哪 | 谁写它 | 谁读它 | 什么时候失效 | 本章哪几节钉的 |
|---|---|---|---|---|
| **退出码**（一个字节） | 函数体最后一条命令，或 `return N` | 外面的 `$?`、`if f`、`&&`/`||` | 只要中间插进另一条命令就没了；超过 255 当场回绕 | 第 3、4、8 节 |
| **stdout 的字节** | 函数体里任何写到 1 号 fd 的东西 | `$( )` 的捕获方 | 尾部换行被全吃光；多值被挤成一行；诊断混进来就脏了 | 第 5、6、7、8 节 |
| **名字表**（当前进程） | `f(){ }`、`function f { }`、`declare -f` 抄回来的文本、`export -f` 塞进环境 | `type` / 命令查找 / 新起的 `bash -c` | 换进程就没了（除非导出）；被同名函数遮蔽后被 PATH 追不上；`unset -f` 一条就抹掉 | 第 14、15、16、17、18、22 节 |
| **作用域栈**（每次调用一格） | 函数体里的赋值；`local` 只在本层 | 本层和**所有被它调下去的下层**（动态作用域） | 函数返回那一层当场撤销并恢复外层旧值 | 第 11、12、13 节 |

四行合起来就是本章的一句话：**函数不「返回」东西。它交出一个码、吐出一串字节、在当前进程的名字表里占一格、
在调用栈上压一层作用域 —— 想要哪个就去看哪个地方，别的地方没有。**

## 一页纸（考前扫这半页）

- **判成败看码，拿数据看字节**，两套并行且互不解释：`f(){ echo hi; return 7; }; v=$(f)` 之后
  `v` 里只有 `hi`，`$?` 才是 7（第 8 节）。
- **`return` 只有 8 位**：256→0、257→1、512→0、-1→255。`return 256` 和 `return 0` **分不开**（第 4 节实测）。
- **不写 `return` 的函数**，码就是体里最后一条命令的码；`local v=$(f)` 会把码**吞成 0**（赋值带码，披上 local 就没了）。
- **命令替换把尾部换行全吃光**：`printf "x\n"` 与 `printf "x\n\n\n"` 捕获后一模一样；
  只打一个空行的函数，捕获结果是**空串**（第 6 节：长度 1、1、0、1）。
- **诊断一律 `>&2`**：`$( )` 只接管 1 号 fd，2 号接不着，所以库里的 `log()` 永远不污染捕获（第 21 节）。
- **`$( )` 是子 shell**：里面的 `cd`、赋值、`exit` 一个都带不出来；`exit` 只杀子 shell，外面拿到码但脚本继续跑（第 5 节）。
- **函数体里漏一个 `local`，改的就是调用者的变量** —— 动态作用域：被调用者读得到、也改得动上层的 `local`（第 11 节）。
- **递归里 `local` 不是风格问题**：漏掉的中间变量在回退时被内层改掉，4! 当场算成 1（第 13 节实测）。
- **bash 没有块作用域**：`if`/`for` 里写的 `local` 出了那对花括号照样活着，圈是「这次调用」；
  没写 `local` 的循环变量一路活到函数外面（第 12 节）。
- **函数是当前进程名字表里的一格**：定义顺序不重要（调用那一刻才查名）、同名重定义不报错也不通知（第 14 节）。
- **跨进程只认三种姿势**：`source`（只管当前进程）、`export -f`（能跨 bash，但弄脏每个子进程的环境，
  dash 直接不认）、`declare -f` 抄成文本再 source（最 portable）（第 22 节）。
- **被函数遮蔽了就用三条绕法**：`command ls`、`builtin true`、绝对路径（第 16 节）。
- **转发参数只有一个姿势**：`"$@"`。空串也占一格（`show "a b" "" c` → `$#=3`）；`"$*"` 会把格数压成 1（第 20 节）。
- **别指望 `set -e` 替你管函数**：它会在第一条失败就把对照组掐掉，而在 `||` 左边又完全不管制（第 10 节）。
- **`RETURN`/`DEBUG` trap 默认不触发**：不开 `set -o functrace`，函数返回一次都不进 trap（第 9 节）。

## 这章的坑（按代价从大到小）

1. **函数里漏 `local`。** 代价：调用者的同名变量被改，递归结果错、循环变量被偷。屏幕上最狠的一格是
   「漏 `local n` 的阶乘把 4! 算成 1」—— 值错，但不报任何错（第 11、13 节）。
2. **想用 `return` 传数据。** 代价：`return 256` 与 `return 0` 在 `$?` 里长得一模一样，
   一个「用返回码表示错误编号」的设计从 256 开始全线塌陷（第 3、4 节）。
3. **诊断信息 `echo` 到 stdout。** 代价：`v=$(f)` 里混进「正在处理…」，
   于是 `[ "$v" = "OK" ]` 永远不成立 —— 一个测试**永远失败**的守卫；反过来如果只打了一句又恰好被 `if` 当码用，就是**永远成功**的假守卫（第 5、7 节）。
4. **以为命令替换里的副作用会留在外面。** 代价：在 `$( )` 里 `cd`、赋值、`exit` 全部丢失，
   脚本状态和你想的不是一件事（第 5 节）。
5. **靠 `export -f` 做「跨机器复用函数库」。** 代价：只对 bash 系有效，dash/busybox sh 当场
   `export: Illegal option -f`；而且每一个子进程的环境里都多一个 `BASH_FUNC_xxx%%` 怪键（第 17、22 节）。
6. **函数名撞了内建或外部命令。** 代价：函数的优先级最高，`ls`/`true`/`printf` 被抢之后
   下游所有脚本的行为都变了，而且没有任何提示（第 15、16 节）。
7. **传参不加引号。** 代价：`f $var` 会把含空格的值切成多格，还会触发通配展开，
   一个模式顶掉两个参数（第 19 节）。
8. **包装函数里用 `"$*"` 转发。** 代价：三格变一格，含空格的参数与空串全部变形（第 20 节）。
9. **把 `set -e` 当安全网。** 代价：一半该继续的现场被掐死，另一半（`||`、`if`、`!` 左边）根本不管制（第 10 节）。
10. **拿别名当函数用。** 代价：别名不接 `$@`、不递归、不参与 `type -t` 的那格，也不会被 `export -f` 带走（第 15、17 节）。
11. **没开 `functrace` 就写 RETURN/DEBUG trap。** 代价：trap 一次都不触发，你以为在记的日志是空的；
    而 `source` 结束反倒会触发一次 —— 两个方向都会骗你（第 9 节）。
12. **写 `if f; then` 时以为判的是「有没有输出」。** 代价：判的只有码，`f` 打到 stdout 的东西一句都不参与（第 8 节）。

## 自检问题

1. 函数能「返回」一个字符串吗？—— 不能。它只能交出一个 0~255 的码；字符串是它写到 stdout 的字节，走的是另一条道（第 3、5 节）。
2. `return 258` 之后 `$?` 是多少？—— `2`。低 8 位之外的全丢（第 4 节一排数：256→0、257→1、511→255、512→0）。
3. `local v=$(f)` 和 `v=$(f)` 的差别是什么？—— 前者把退出码吞成 `local` 自己的 0，后者把 `f` 的码留在 `$?`（第 7 节）。
4. `f(){ printf "x\n\n"; }`，`v=$(f)` 的 `v` 是什么？—— `x`，长度 1：尾部换行是**全部**被吃，不是吃一个（第 6 节）。
5. 函数只打了一个空行，捕获结果是什么？—— 空串（长度 0），`[ -z "$v" ]` 判它是空的（第 6 节 c 那格）。
6. 怎么让诊断信息不污染 `$( )` 的捕获？—— 写到 stderr：`echo ... >&2`（第 7、21 节，库里 `log()` 就是这么写的）。
7. 在 `$( )` 里 `cd /tmp`，出来后当前目录变了吗？—— 没有。命令替换是子 shell，`cd`、赋值、`exit` 都带不出来（第 5 节）。
8. `$( )` 里写 `exit 3`，脚本会结束吗？—— 不会，只结束那个子 shell；外面 `$?` 变成 3，脚本继续跑（第 5、9 节）。
9. 函数体里 `x=1` 没加 `local`，谁会遭殃？—— 调用者（甚至全局）：这一层的赋值改的就是上层那个同名变量（第 11 节）。
10. 被调用函数**读得到**调用者的 `local` 吗？—— 读得到，也改得动 —— 这就是动态作用域，和「写在哪个文件里」无关（第 11 节第 3 格）。
11. 怎么把这条链断掉？—— 被调用者自己写一句 `local`，遮蔽立刻生效（第 11 节第 4 格）。
12. 递归里漏一个 `local` 会怎样？—— 回退时内层已经把外层的同名变量改了，结果错但不报错（第 13 节：4! 算成 1）。
13. `if` 块里写的 `local`，出了块还在吗？—— 在。bash 没有块作用域，圈是「这次函数调用」（第 12 节）。
14. `local` 写在函数外面会怎样？—— 报 `local: can only be used in a function`，但**不终止脚本**（第 12 节）。
15. 先 `first(){ second; }` 再定义 `second`，能跑吗？—— 能。名字是调用那一刻才查的（第 14 节）。
16. 同名函数定义两次会报错吗？—— 不报错，后一句直接盖掉前一句（第 14 节）。
17. 函数、内建、PATH 上的命令同名时谁赢？—— 函数。要夺回来用 `command` / `builtin` / 绝对路径（第 15、16 节）。
18. `bash -c` 里为什么看不见我刚定义的函数？—— 函数活在当前进程的名字表里，不在磁盘上；新进程没拿到（第 17、18 节：码 127）。
19. `export -f` 之后 `env` 里长什么样？—— 一个键名形如 `BASH_FUNC_名字%%` 的条目，值以 `() {` 开头（第 17 节）。
20. 想把函数库交给 dash 跑，最稳的办法是？—— `declare -f` 把定义抄成纯文本再 `source`；`export -f` 和 `declare` 在 dash 里直接报错（第 22 节）。
21. 包装脚本转发参数应该写什么？—— `inner "$@"`；空串也占一格，`"$*"` 会压成一行（第 20 节）。
22. 本章为什么不写 `set -e`？—— 它会在第一条失败就把对照组掐掉，而在 `||`/`if`/`!` 左边又完全不管制（第 10 节）。

## 本章没演 / 没验证（绝不编造，都在这）

- **`RETURN`/`DEBUG` trap 与 `set -e`、`ERR` trap 的组合**：第 9 节只单独演了它们各自的触发次数，
  三条一起开的交互没有实测，所以本章不给结论。
- **`exit` 在进程替换 `<(...)` 里的传播**：只演了命令替换 `$( )` 那一种。
- **trap 跨 `exec`、跨真实子进程的继承规则**：第 22 节只演了干净的 `bash -c` 起新进程。
- **`BASH_FUNC_xxx%%` 这个键在其他 shell（dash / busybox / zsh）里怎么被解析**：
  本章只演了 dash 拒绝 `export -f` 这件事，没有逐个 shell 验证「拿到函数定义之后行为如何」。
- **任何 Shellshock 类的注入与利用**：纪律禁止，也不属于一本讲 bash 语法的书。
  本章只写实测到的代价 —— 每个子进程的环境都被塞、`env` 输出变难读。
- **`FUNCNEST` 对「非递归的深调用链」是否同样拦**：只演了递归；
  `ulimit -s` 的具体值与爆栈深度之间的对应关系也没量（那个量每跑必变，只报了稳定的 `rc=139`）。
- **`local -a` / `local -A`（局部数组、关联数组）在递归多帧下的可见性**：没演。
- **`local -n`（nameref）稳定带回多个值**：第 11 节演了它的正用和两个坑，
  没有演「用它当函数出参的完整工程写法」。
- **交互式 shell 里的函数**（配合 readline、写在 `~/.bashrc` 里的函数、`bash -i`）：
  本章一律不碰家目录，所以完全没有证据。
- **多线程/并发下的名字表**（`coproc`、后台作业里改函数定义）：本章不起后台作业，没演。
- **别的 bash 版本、别的机器**：全部结论只在 bash 5.3.9(1)-release + uutils coreutils 0.8.0 +
  mawk 1.3.4 + `/bin/sh → dash` 这台机器上跑出来；换版本前先重跑 `demo.sh` 再信第 3、13、17、22 节。
- **第 21 节那个函数库不是从真实项目里搬来的**：它是本章自造的收敛件，
  没跑过任何真实工作负载 —— 它证明的是「四条规矩能拼成一段能用的代码」，不是「这段代码适合你的项目」。
- **`set -o pipefail` 开着时，函数里那条管道交回什么码**：第 9 节只演了默认（关着）的样子 ——
  那格的括号里写着「没开 pipefail，只看最后一段」，而第 1 节的环境体检表里点的是 `errexit`/`functrace`
  那几项，`pipefail` 开着的那半没实测，所以本章不下结论。
- **函数的 fork / 启动成本、耗时**：`retry` 故意不 `sleep`，本章没有一处掐表 ——
  耗时每跑必变，进了捕获就不可复现；「循环/子进程贵在哪」的账在第 05 章。
- **反引号 `` ` ` `` 与 `$( )` 的正面对照**：第 15 节里反引号只作为一次事故出场，
  嵌套可读性、报错位置的差别都没逐项实测，本章一律用 `$( )`。
- **`unset -f` 作为「夺回名字」的第四条路**：第 16 节只演了 `command` / `builtin` / 绝对路径三条绕法，
  把函数从名字表里**删掉**这条路没演（它改的是全局状态，放到第 08 章讲更合适）。
- **真实递归（遍历目录树）**：第 13 节用的是 `4!` 和 `fib(10)` 这类纯数值递归，
  因为进入次数是可数的稳定数字；文件树那类递归的规模每跑必变，没演。

## 怎么跑这一章

```
cd bash-handbook/06-functions-and-returns
bash demo.sh                 # 跑完整章 24 节，跑完自动删沙箱
bash demo.sh > out.txt       # 重定向时自动关颜色，README 引用的就是这份纯文本
bash demo.sh --keep          # 保留沙箱并打印路径，进去自己接着敲
```

- 本章一共 10 个文件：9 个取证脚本 + `demo.sh`。demo 把它们整份复制进 `mktemp -d` 的沙箱
  （前缀 `bash06-`）再跑，**章目录里不会留下任何产物**（第 24 节当场自证：开跑前后都是 10 个条目）。
- ★ demo 用**相对文件名**跑它们（`bash retcode.sh`）：bash 的报错原文会带上 `$0`，
  跑绝对路径就把家目录绝对路径印上屏了（实测：相对 0 处、绝对 16 处）。
- 每一节的形状：**完整跑**那几节（第 3、5、7、9、11、13、15、17、19 节）整份跑一个脚本，
  脚本自己按 `=== N. 中文标题 ===` 分格；**小证据**那几节是 `runc` 现场敲的最小片段，
  每条都在一个全新的非交互 `bash -c` 里开始，所以上一节开的 `set -e`、遮蔽函数都不会串下来。
- 九个脚本合计 64 格，demo 自己 24 节（第 23 节当场数过，而且每道守卫都先被**故意弄响一次**）。
- 想只看某一节：`bash demo.sh | less`，或 `bash demo.sh --keep` 之后进沙箱里单跑那一个脚本
  （`cd "$(mktemp -d)"` 再 `bash /那个脚本的绝对路径` 也行，只是报错里会带上路径）。
- 语言环境：demo 会把自己的 `LC_ALL`/`LANG` 钉成 `C.UTF-8`（第 1 节解释了为什么 —— 中文语言环境下
  bash 报错是中文、`wc -m` 的计数与 `declare -p` 的转义形状都会跟着变）。所以你在自己终端里手敲同一条命令，
  报错原文可能是中文，那一行和捕获对不上是**正常**的。
- 交付闸门（这本书的引文保真机制）：正文里每一段输出都由「标行号的占位符」从定稿捕获按行号搬出，
  展开与核对是两条命令 —— `~/.local/bin/expand_fences.py <README> <捕获>` 与
  `~/.local/bin/chapter_gate.sh <README> <捕获> 'bash06-[A-Za-z0-9]{6}'`。

## 术语小抄

| 术语 | 一句话 | 本章哪节 |
|---|---|---|
| `return N` | 函数交出的**一个字节**的码；N 超过 255 当场回绕，函数外才是 `$?` | 3、4 |
| 裸 `return` | 不带参数 = 交出「上一条命令」的码，不是 0 | 3、9 |
| `$?` | 最近一条**完整命令**的码；中间插一条 `printf` 就把它覆盖掉了 | 3、8 |
| 命令替换 `$( )` | 子 shell + 把 1 号 fd 的字节读成字符串 + **吃掉全部尾部换行** | 5、6 |
| 退出码 vs 输出 | 两条独立通道：码给 `if`/`&&`/`||` 看，字节给捕获方看，互不解释 | 8 |
| `>&2` | 把这句话改道到 stderr，从此不参与 `$( )` 的捕获 —— 库里的 `log()` | 7、21 |
| 动态作用域 | `local` 的可见范围由**调用栈**决定：上层能看见下层看不见的那格，下层能改上层 | 11 |
| `local` | 只在本层函数调用有效；返回时恢复外层旧值；写在函数外面是错的（但不终止） | 11、12 |
| 块作用域 | bash **没有**：`if`/`for`/`while` 里写的变量出了大括号照样活着 | 12 |
| `local -n` | nameref，把「回填给调用方」做成指针；自引用和指向已返回的局部是两个坑 | 11 |
| `FUNCNEST` | bash 独有的递归深度上限；不设就只受栈限制（撞真栈时 `rc=139`，崩的是子进程） | 13 |
| 名字表 | 当前进程里「名字 → 身份」那张表；函数、内建、别名、关键字、PATH 命中各占一格 | 15 |
| `type` / `type -t` / `type -a` | 问一个名字的身份 / 分类 / 列出全部来源 | 15 |
| `declare -f` | 把函数还原成**定义文本** —— 唯一能搬出当前进程的可移植姿势 | 22 |
| `export -f` | 把定义塞进环境，键名形如 `BASH_FUNC_名字%%`；只喂得饱 bash 系 | 17、22 |
| 别名 | 纯文本替换：不接 `$@`、不递归、不参与 `export -f` | 15、17 |
| `command` / `builtin` | 绕过函数与别名 / 只走内建 —— 被遮蔽后的两条急救通道 | 16 |
| 位置参数 | `$1..$n`、`$#`、`$@`、`$*`；函数一进来它们就是**这次调用**的，脚本级的那套在函数里看不见 | 19 |
| `"$@"` | 每个参数一格、空串也占格 —— 转发参数的唯一写法 | 20 |
| `"$*"` | 用 `${IFS}` 的首字符拼成**一格**；只有它受 IFS 影响 | 19 |
| `set -- a b c` | 在函数里换掉本层的位置参数；返回后外层自动还原 | 19 |
| trap 的 `EXIT`/`RETURN`/`DEBUG` | 三种钩子；后两者默认不触发，要开 `set -o functrace` | 9 |
| `source`（或 `.`） | 在**当前进程**里执行文件；文件里的 `exit` 会杀脚本，`return` 不会 | 9、22 |
| `bash -c` | 新进程：干净名字表，没导出的函数一律 127 | 17、18 |
| `rc=127` / `rc=139` | 「命令找不到」/「撞了栈被 SIGSEGV」—— 本章两种典型崩法的稳定码 | 18、13 |
