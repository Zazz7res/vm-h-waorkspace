# Top-K 问题 top-k

> 一句话定位：**从 n 个数里挑出"最大的 K 个"（K 远小于 n），根本不需要排序 —— 一个大小固定为 K 的最小堆就能搞定，时间 O(n log K)、空间 O(K)。**

---

## 一句话是什么

给定一堆数（比如 100 万条日志的耗时），只要**最大的 K 个**（比如最慢的 10 条）。
本目录把三种解法**全部实现、全部跑、全部量**：

| 编号 | 做法 | 一句话 |
|---|---|---|
| ① | **全排序 + 取尾巴 K 个** | 最直觉，但为了 1 瓢水把整缸水搅了 |
| ② | **大小固定为 K 的最小堆**（本节主角，标准答案） | 堆顶放"目前候选里最差的那个"当门槛，新来的比门槛强才准进 |
| ③ | **快速选择 Quickselect**（简版） | 只找"第 n-K 小"这个门槛值，其余不管；平均 O(n)，最坏 O(n²) |

三个函数接口一模一样：`topk_by_xxx(输入数组, n, K, 输出数组, &比较次数)`，
所以可以**同一份数据喂三家，再检查结果是否一致** —— 这正是本节最重要的自检手段。

⚠ 本节最大的反直觉点：**求"最大的 K 个"要用"最小堆"**。想不通就看下面「核心操作 2」，
那里用"守门员"这个比喻把它讲透，并且有程序逐步打印的现场证据。

---

## 为什么需要它

### 现实里全是 Top-K

- 热搜榜前 50、歌曲榜前 100；
- 一亿条订单里金额最大的 20 笔（风控要看）；
- 服务日志里最慢的 10 个请求（性能排查第一动作）；
- 推荐系统：从 10 万候选里挑分数最高的 200 个再送精排；
- 机器学习：模型输出的前 K 个类别（top-k accuracy）。

它们的共同形状是 **n 很大、K 很小**（K/n 常在 0.1% 以下）。

### 不用它时的痛

```
土办法①：全部排序，取前 K 个
   1 亿个数排序 → 约 1 亿 × 27 ≈ 27 亿次比较，几秒到几十秒；
   而且必须把 1 亿个数全放进内存。
   实际上我们只要 10 个答案，却让另外 99.99999% 的数据都参与了排序。

土办法②：扫 K 遍，每遍找当前的最大值
   每次扫描 O(n)，共 O(nK)。K=100 时比排序还慢，而且改一遍数据要重扫。

土办法③：维护一个"前 K 名"的普通数组
   每来一个新数，要在这 K 个里找最小值再决定踢谁 → O(K) 一次判断，
   总共 O(nK)。K 小的时候能用，K 一大就崩。
```

而 **② 号解法（大小为 K 的最小堆）**：

- 内存里**永远只住 K 个数**（1 亿条数据的 Top-10 只占 10 个 int）；
- 数据可以**流式**到来，来一条处理一条，处理完就能扔掉 —— 全排序做不到，因为它要先看到全部数据；
- 每个新元素**只和堆顶比一次**，判断 O(1)；进来了才付一次 O(log K) 的下沉；
- 所以总代价 **O(n log K)**。n = 20 万、K = 1000 时，实测比较次数从 639 万降到 29 万。

## 内存布局图解

### ② 法的核心：一个"大小永远是 K"的最小堆

以 `K = 3`、目前堆里是 `{12, 41, 78}` 为例（这就是运行日志里真实出现过的一刻）：

```
        树的样子（最小堆：父亲 <= 孩子）                 压扁成数组（只有 3 格，永远不扩容）
                     12 ← 堆顶 = 门槛 = 候选里最差的那个          下标:   0     1     2
                   /    \                                              内容:  12    41    78
                41       78
                ↑         ↑
              中间值     最好的那个（最大堆里才叫"堆顶"，这里它反而在最角上）

  关键：我们【永远只看下标 0】这一个数。
        它是"目前为止最大的 K 个"里最小的那个 → 只要新来的数 > 它，新来的就有资格替换它。
```

### 守门过程（K=3，数据 `12 5 78 3 41 67 9 55 23 88 14 92 31 7 60`）

```
 阶段 1：满员之前 —— 来者不拒（还没装满，谈不上"淘汰"）
   收 12 → [12]              收 5  → [5 12]         收 78 → [5 12 78] ← 满了，门槛=5

 阶段 2：满员之后 —— 每个新数只和堆顶比【一次】
   来  3 → 3  <= 5 门槛 →  扔掉（1 次比较，什么也不做）
   来 41 → 41 >  5 门槛 →  踢掉 5，41 站上堆顶，下沉归位 → [12 41 78]，新门槛=12
   来 67 → 67 > 12       →  踢掉 12 → [41 67 78]，门槛=41
   来 55 → 55 > 41       →  踢掉 41 → [55 67 78]，门槛=55
   来 88 → 88 > 55       →  踢掉 55 → [67 88 78]，门槛=67
   来 92 → 92 > 67       →  踢掉 67 → [78 88 92]，门槛=78
   其余 23 14 31 7 60 全部 <= 78 → 各 1 次比较就打发掉

 最终答案 = 堆里的 3 个数 {78, 88, 92}（注意：数组顺序是 78 88 92，不是名次顺序！）
```

**为什么踢"门槛"是安全的？** 因为堆里另外 K-1 个候选全都 ≥ 门槛，
它们本来就比被踢的那个更配待在"前 K"里；而被踢掉的那个数从此再也不可能进前 K ——
后面就算来更大的，被踢的也只会是**更大的新门槛**。这是一条严格的"淘汰单调性"。

### ① 法（全排序）和 ③ 法（快选）的内存差别

```
① 全排序：   拷贝一份 n 个 int → 原地堆排序 → 取尾巴 K 个
              [? ? ? ? ? ? ? ? ? ? ? ? ? ? ?]  ← O(n) 额外空间，全体都要参与
               排完后： 3 5 7 9 12 14 23 31 41 55 60 67 78 88 92
                                                        └──── 最大的 3 个────┘

③ 快速选择： 拷贝一份 n 个 int → 反复 partition，只把【第 n-K 小】放到位
              [? ? ? ? ? ? ? ? ? ? ? ? ? ? ?]
               完成后：左边全都 <= 门槛，右边全都 >= 门槛，但【两边内部都是乱的】
                       └──── 随便(乱) ────┘门槛└──── 随便(乱) ────┘
              空间 O(n)（因为要拷贝），但工作量只有 O(n) 而不是 O(n log n)
```

## 核心操作逐个拆解

### 操作 1：`topk_by_sort(data, n, k, out, &cmp)` —— ① 全排序

**干什么**：把"最笨的办法"实现一遍当**基准线**，并给另外两种方法一个可比的对错参照物。

**一步步怎么做**

```
1) 参数检查：k<=0 或 n<=0 直接返回；k>n 就夹成 n（要 100 个但只有 30 个，那就给 30 个）
2) malloc 一份 n 个 int 的 work，把 data 抄进去
      ← 为什么必须抄？不抄就会把【调用者的数组】排成升序，这是不可接受的副作用
3) 对 work 做【堆排序】（升序）：
      阶段1 for (i = n/2-1; i >= 0; i--) 下沉 → 建成最大堆，O(n)
      阶段2 for (end = n-1; end >= 1; end--) { 堆顶和 end 交换; 在 [0..end-1] 里下沉 }
4) out[i] = work[n-1-i]，从尾巴倒着取 K 个 → out 天然就是【降序】（最大的在前）
```

**为什么这里用堆排序而不是快排**：堆排序**最坏也是 O(n log n)**，不会因为测试数据碰巧有序而退化，
这样和另外两个方法比"比较次数"才是干净的对比。（完整讲解在 `10-sorting/heap-sort`。）

**边界情况**：`k > n` 夹成 n；`n <= 1` 时堆排序的两个循环都不执行，直接返回。

**对应代码**：`topk.c:91`（`topk_by_sort`）、`topk.c:56`（`sift_down_max`）、`topk.c:80`（`heapsort_asc`）

### 操作 2：`topk_by_heap(data, n, k, out, &cmp)` —— ② K 最小堆守门（本节主角）

**干什么**：只维护"目前为止最大的 K 个"，用一个大小固定为 K 的最小堆。

**一步步怎么做**

```c
KHeap h;                       // 容量 cap 永远 = K，不需要 realloc，不会扩容
h.a = malloc(K 个 int);        // ★ 全部额外内存就这一坨：O(K)
for (i = 0; i < n; i++) {
    int x = data[i];
    if (h.size < h.cap) {
        kh_add(&h, x);         // 还没装满 → 无脑收下：放尾巴 + 上浮，O(log K)
    } else {
        if (x > h.a[0]) {      // ★ 满员后只和【堆顶】比【一次】：这就是门槛
            kh_replace_root(&h, x);   // 踢掉门槛：x 放到下标 0，然后【只下沉】，O(log K)
        }
        // 否则 x 连最差的候选都不如 → 扔掉，什么也不做（1 次比较就打发）
    }
}
out[0..K-1] = h.a[0..K-1];     // ⚠ 堆里的 K 个数【不是】有序的
```

**三个必须想通的点**

1. **为什么求"最大的 K 个"要用"最小堆"？**（本节最该背下来的推理）
   我们要做的判断是"新来的有没有资格挤掉一个"，需要的信息是**候选里最差的那个**。
   最小堆的堆顶恰好就是它 —— O(1) 白送。
   假如换成最大堆，堆顶是候选里**最好**的，跟新来的比不出任何结论；
   你想知道"该踢谁"，就得把整个堆扫一遍找最小值 → 每个元素 O(K)，总共 **O(nK)**，比全排序还慢。
   > 口诀：**留最大的 K 个 → 最小堆守门；留最小的 K 个 → 最大堆守门。
   > 堆顶永远放"你最想淘汰的那个"，淘汰决策才只需要一次比较。**

2. **为什么 `replace_root` 只需要下沉、不需要上浮？**
   能走到这一步说明 `x > 旧堆顶`，而旧堆顶是全堆最小的，所以 x 一定**不小于**它的两个孩子吗？不 ——
   x 只是比旧堆顶大，完全可能比孩子小，所以**要下沉**；
   但它不可能需要上浮，因为上浮的条件是"比父亲小"，而父亲是旧堆顶上层的元素，
   ≥ 旧堆顶……真正的原因是：**替换发生在堆顶，堆顶没有父亲**。省掉一半代码和一半比较。

3. **为什么 `kh_add`（未满员时）要上浮？**
   那时候新元素加在数组尾巴（最后一层最右），它有父亲，可能比父亲小 → 必须上浮。
   满员之后就再也不会走这条路了，所以 `replace_root` 里只有下沉。

**边界情况**：`k >= n`（等价于"全部都要"，退化成纯建堆，见下面第 6 幕实测里那个反直觉的行）；
`k == 1`（堆只有一个格子，`sift_down` 立刻返回，总比较次数正好 = n-1，即"扫一遍记住最大值"）；
输入全是同一个值（`x > 堆顶` 永远不成立 → 收满 K 个之后全部扔掉，答案正确）。

**对应代码**：`topk.c:244`（`topk_by_heap`）、`topk.c:235`（`kh_replace_root`）、
`topk.c:196`（`kh_sift_down`）、`topk.c:224`（`kh_add`）；
逐步打印版 `topk.c:293`（`topk_heap_trace`）。

### 操作 3：`topk_by_quickselect(data, n, k, out, &cmp)` —— ③ 快速选择

**干什么**：全排序是"把每个位置都排好"，而我们只想知道**门槛值**（第 n-K 小）落在谁身上。
快排每一轮的 partition 会把某个 pivot 放到它**最终应在的位置**，那我们就
反复 partition，直到 pivot 正好落在 `target = n-K` 上，然后**只走包含 target 的那一半**，另一半整个扔掉。

**一步步怎么做**

```
1) 拷贝一份 work（同样是 O(n) 空间，而且【会打乱】这份拷贝）
2) target = n - k，quickselect(work, 0, n-1, target)：
      while (lo < hi) {
          p = partition_lomuto(work, lo, hi);      // 把 pivot 放到最终位置 p
          if (p == target) break;                  // 门槛就位，收工
          target < p ? hi = p - 1 : lo = p + 1;    // ★ 只走一半，另一半不管
      }
   （用 while 循环代替递归：每轮只走一半，等价于尾递归，不会栈溢出）
3) threshold = work[target]
4) 收集：先把【严格大于】门槛的收进 out，再用【等于】门槛的补齐到 K 个
```

**两个工程细节**

- `partition_lomuto` 里做了**三数取中**（`lo / mid / hi` 三个位置的中位数当 pivot）：
  固定拿 `a[hi]` 当 pivot 遇到"几乎有序"的数据会退化到每轮只切掉一个元素 → O(n²)。
  三数取中是很便宜的防退化手段（**但不是保证**，第 7 幕就是它翻车的现场）。
- 第 4 步的"先 `>` 再 `==` 补齐"是有重复值时唯一正确的写法：
  所有 `>= threshold` 的元素个数可能**多于** K 个（比如 `{5,5,5,5}` 取前 2），
  只按 `>=` 收就会溢出 out 数组。

**平均 O(n) 从哪来**：`n + n/2 + n/4 + ... = 2n`。第 7 幕会拍到它在结构化数据上变成 40n 的样子。

**对应代码**：`topk.c:399`（`topk_by_quickselect`）、`topk.c:350`（`partition_lomuto`）、
`topk.c:384`（`quickselect`）、`topk.c:460`（`topk_quickselect_trace`，每轮切多少的取证工具）。

### 操作 4：`topk_normalize_desc(out, k)` —— 把 K 个结果排成降序（为了对比）

**干什么**：三种算法给出的**顺序**互不相同（① 天然降序、② 是堆数组顺序、③ 是原数组出现顺序），
所以"结果是否一致"必须先各自归一化再逐位比。

```
① 全排序 → [92 88 78]        ② 堆数组 → [78 88 92]        ③ 快选 → [92 88 78]（本次碰巧）
              ↓ 归一化（插入排序，K 很小所以够用）
           [92 88 78]                   [92 88 78]                   [92 88 78]   → 逐位相等 ✅
```

这里用的正是那句要命的实话：**Top-K ≠ 前 K 名排行榜**。
要名次就得再排一次 O(K log K)。因为 K 小，这个开销可以忽略 —— 但它**必须显式做一次**，
不能以为堆里出来的顺序就是排名（第 3 幕里 `K=5` 时堆原样输出是 `60 67 78 92 88`，
第一名 92 却在倒数第二位，就是活证据）。

**对应代码**：`topk.c:532`。

### 操作 5：实测 —— 为什么不能只写理论

**怎么测**：`clock()` 打真实耗时（每个方法跑 3 次取最快，减少调度噪声）＋
每个算法内置 `cmp` 计数器打**比较次数**（确定值，不受机器影响，可以手核）。

**数据必须硬编码固定**：本目录的大数组用 `a[i] = (i * 7919) % 1000003` 生成（1000003 是质数，
所以前 20 万个值互不相同），另外两幕用 LCG 和纯递减公式 —— **都不用 `rand()`**，
所以 README 里贴的每个数字你重跑一遍一定能复现。

**测出来什么**（详见下面「运行结果」）：

| 现象 | 数字 |
|---|---|
| n=20 万、K=1000 时 ① vs ② | 36.92ms/639 万次 vs 0.75ms/29 万次 —— **差约 50 倍** |
| K 从 100 涨到 10000（100 倍），② 的代价 | 只涨 4.4 倍 —— log K 名不虚传 |
| ② 在 K=n 时反而变便宜 | 367279 次：因为堆**从头到尾没满过**，一次门槛判断都没发生 |
| ③ 换一份输入 | 同一份数据不同目标：1.4n vs 40n；换 LCG 数据：全都回落到 ~2n |

## 复杂度表（横向对比）

| 方法 | 时间 | 额外空间 | 是否打乱原数组 | 对输入敏感吗 | 结果自带名次吗 | 适合流式吗 |
|---|---|---|---|---|---|---|
| ① 全排序取前 K | `O(n log n)` | `O(n)`（必须拷贝） | 不（内部拷贝） | 不敏感（堆排序最坏也 n log n） | ✅ 是 | ❌ 要看到全部数据 |
| ② **K 最小堆守门** | `O(n log K)` | **`O(K)`** | 不 | **完全不敏感**（次数只跟 K 有关） | ❌ 只保证堆顶最小 | ✅ 来一条处理一条 |
| ③ 快速选择 | 平均 `O(n)`，最坏 `O(n²)` | `O(n)`（要拷贝） | 不（但内部会打乱拷贝） | **极敏感**（pivot 位置决定一切） | ❌ 只给出门槛 | ❌ |
| 土办法：扫 K 遍 | `O(nK)` | `O(1)` | 不 | 不敏感 | ✅ 是 | ❌ |
| 土办法：无序数组当前 K 名 | `O(nK)` | `O(K)` | 不 | 不敏感 | ❌ | ✅ |
| （参考）完整排序算法本身 | `O(n log n)` | — | — | — | 全体名次 | — |

**K 和 n 谁主导？** 看这两个比值：

- ②：`O(n log K)`，K << n 时 log K 只有 log n 的几分之一 —— 这就是它赢的地方；
- ②：K 接近 n 时 `log K ≈ log n`，优势消失，而且**只有**它需要"预先知道 K"，此时不如直接排序。

## 常见的坑

### 坑 1：求"最大的 K 个"用**最大堆**（初学者第一反应，也是彻底错的）

堆顶是候选里**最好的**，新来的数跟它一比只能得出"新来的更差/更好"，
但你不知道该**踢谁** —— 想找出候选里最差的必须扫一遍整个堆：每个元素 O(K)，总共 O(nK)，
比全排序 O(n log n) 还慢，堆的意义全丢。
正确姿势：**堆顶放"你最想淘汰的那个"**。求最大 K 个 → 最小堆；求最小 K 个 → 最大堆。

### 坑 2：把堆里那 K 个数当成"排行榜"

第 3 幕实测：`K=5` 时堆数组原样是 `60 67 78 92 88`，最大值 92 在倒数第二位。
堆只保证 `a[0]` 是这 K 个里最小的，**兄弟之间无序**（这是 `06-heap/binary-heap` 讲过的性质，
在 Top-K 这里立刻变成坑）。
要名次必须再排一次 O(K log K)；本目录用 `topk_normalize_desc()` 显式做了这一步，
否则"三者结果一致"的比对根本没法做。

### 坑 3：忘了有重复值时会"超过 K 个"

快速选择法最后用"所有 `>= threshold` 的元素"收集答案看着很自然，
但 `{5,5,5,5}` 取前 2 时，`>= 5` 的有 4 个 —— 直接塞就把 out 数组写穿了（缓冲区溢出，真能崩进程）。
本实现写成两趟：先收**严格大于**门槛的，再用**等于**门槛的补齐到恰好 K 个（`topk.c:435` 起）。

### 坑 4：输出缓冲区按"常见的 K"分配，而不是按最坏情况

这个坑**我自己踩了，被 ASan 当场抓到**：第 6 幕想画"K 从 1 变到 n"的对比表，
复用了那块只有 `BIGK=1000` 个 int 的输出数组，但循环里 K 会取到 100000、200000 →
`heap-buffer-overflow ... WRITE of size 4`（普通 glibc 下表现为 `munmap_chunk(): invalid pointer`，
更难查）。教训：**缓冲区大小必须按最坏情况算**，那一幕后来专门 malloc 了一块 n 个 int 的 scratch
（`main.c` 里注释保留了这段事故记录）。写 C 就老老实实每次跑一遍 ASan，一次就能学会。

### 坑 5：不拷贝输入数组，把用户的数据改了

① 和 ③ 都必须原地重排；直接对 `data` 下手就等于给用户埋雷
（Top-K 的使用场景 —— 日志、榜单、推荐 —— 几乎都不能接受"数据被打乱"这个副作用）。
本目录三个函数一律**内部 malloc 一份拷贝**，② 只拷 K 个（它不需要动原数组）。
代价就是 ①③ 的 O(n) 额外空间，这是**明码标价**的，别以为免费。

### 坑 6：`k > n` / `k == 0` 没处理

`k > n`：要 100 个但只有 30 个 —— 应该给全部 30 个，而不是写穿 out。本实现统一 `if (k > n) k = n;`。
`k == 0`：立刻返回，不 malloc(0)（`malloc(0)` 的返回值是实现定义行为，别去赌）。

### 坑 7：拿 15 个数去"实测"，然后得出"堆没什么用"

小 n 时 ② 的 log K 和 ① 的 log n 差不了几倍，而 ② 的实现常数（分支、函数调用）更大，
实测甚至会**更慢**。要量出复杂度差异必须把 n 推到 10⁵、10⁶ 级别，
并且**同时打印比较次数**（次数是确定的，耗时会被系统调度污染）。
本项目第 6 幕用 n=20 万，才终于把 50 倍差距摊开。

### 坑 8：相信"快速选择是 O(n)"这句话而忽略输入

第 7 幕的实测：同一份等差取模数据，找最大的 1000 个用 1.4n 次比较（18 轮），
找最小值却要 40n 次（104 轮），因为三数取中在这份序列上把 pivot 稳定地放在了区间 99% 处。
"平均 O(n)"的前提是 pivot 大致居中。**换成 LCG 序列它立刻回到 ~2n。**
所以：要"最坏也有保证"用堆；上快选就老实随机化 pivot（或 BFPRT）。

### 坑 9：拿堆做流式 Top-K 时忘了"最终还要倒序输出"

② 结束时堆里是 K 个**候选**，门槛（最小的那个）在 `a[0]`。
直接 `for i in 0..K-1: print(a[i])` 打出来的是"从差到好乱序"，
而排行榜要求"从好到差"。真实工程做法：把这 K 个再排一次（O(K log K)），
或者反复 `pop` K 次（也 O(K log K)）。这一步在代码评审里经常被漏掉。

### 坑 10：`sift_down` 时跟"左孩子"比而不是跟"更好的孩子"比

`kh_sift_down` 里必须先比较两个孩子、挑更小的那个再和父亲比。
写成 `if (a[i] > a[2*i+1]) swap(i, 2*i+1)` 是新手最常见的实现错误：
堆序性会被破坏，门槛值不再是这 K 个里最小的，于是**踢错人**，Top-K 结果直接不对，
而且不一定每次都错（数据相关，最难查）。第 6 幕的三家交叉验证就是防这个的。

## 什么时候用它 / 什么时候别用

### 该用 ②（K 最小堆）

- **K 远小于 n**（K/n < 1% 是典型的甜点区），比如亿级日志取前 100；
- **内存受限**或**数据是流式来的**：只允许常驻 K 个元素；
- 要**稳定的最坏情况**：比较次数只跟 K 有关，不怕输入；
- 还要**动态**：边来数据边问"目前前 K 是谁"（这就是 `06-heap/priority-queue` 的形状）。

### 该用 ①（全排序）

- n 本来就小（几千以内），代码简单比省时间更重要；
- 你**反正需要全体有序**（Top-K 只是顺手的需求）；
- 需要名次，而且 K 接近 n。

### 该用 ③（快速选择）

- 只要**门槛值**本身（第 K 大是多少、中位数、分位数），不需要具体是哪 K 个；
- n 极大而 K ~ n/2（找中位数），堆在这里没有优势（log K ≈ log n），快选平均 2n；
- 允许随机化 pivot 且能接受"最坏 O(n²)"（或者用 BFPRT）。

### 别用 Top-K 这套东西的情况

- **要的是全体排名**：那是排序问题，去 `10-sorting`；
- **要的是"第 K 个是谁"以外的区间统计**（比如所有大于门槛的个数）：那是一次划分 + 计数，
  快选的 partition 顺手就能给，堆给不了；
- **数据能放进内存且 K 很大**：`std::sort` 一行搞定，比手写堆更快也更不容易错；
- **要"相似的那 K 个"**（向量检索 top-K nearest）：那是 KD-tree / HNSW 的活，线性扫 + 堆只是基线。

## 自检问题

**Q1：求"最大的 K 个"，为什么用最小堆而不是最大堆？**

因为要做的判断是"新来的够不够格挤掉一个"，需要的信息是**候选里最差的那个**，
最小堆的堆顶恰好就是它，一次比较就能决定。用最大堆的话堆顶是候选里最好的，
想知道该踢谁必须扫一遍整个堆 → O(K) 一次判断 → 总 O(nK)，比排序还慢。
记法：堆顶放"你最想淘汰的那个"。

**Q2：三种方法的结果顺序一样吗？为什么？**

不一样。① 从排好序的尾巴倒着取，天然降序；② 是堆数组的顺序，只保证 `a[0]` 最小，
兄弟之间完全无序；③ 是按元素在原数组里出现的先后被收集的。
所以比对"是否一致"前必须先归一化（本目录用 `topk_normalize_desc` 排成降序）。
这也说明 **Top-K ≠ 排行榜**，要名次得再排 O(K log K)。

**Q3：n = 20 万、K = 1000 时，实测比较次数各是多少？为什么差这么多？**

① 6,399,694（≈ 2n·log n 那一量级）；② 291,914；③ 281,405（≈ 1.4n）。
① 和 ② 差约 22 倍。注意 ② 的 291,914 **远小于**上界 `n log K ≈ 199 万`：
满员之后绝大多数元素只花 1 次比较就被门槛挡掉了，只有真正入选的那少数次才付 log K 的下沉。
所以 O(n log K) 是**上界**，实际数据上它常常表现得更接近 O(n) —— 这也是它实测能打的原因。
② 比 ① 便宜 22 倍的根源就在这里：① 让 20 万个数**全部**参与排序，② 只维护 1000 个候选。
② 便宜的根本原因是：满员后**每个新元素只和堆顶比一次**，绝大多数元素 1 次比较就被打发掉了。

**Q4：把 K 一路放大到 n，② 的比较次数是单调上升的吗？实测怎么说？**

不是。实测 K=100000（=n/2）时 2,400,352 次，K=200000（=n）时反而掉回 367,279 次。
因为 K = n 时堆**从头到尾没满过**，全程走"无脑收下 + 上浮"，一次门槛判断都没发生 —— 退化成纯建堆。
结论：② 的价值全在 K << n；K 接近 n 就别再谈 Top-K 了。

**Q5：快速选择的 O(n) 有什么前提？本节哪一幕打破了它？**

前提是每轮 partition 把区间**大致切成对半**。第 7 幕实测：同一份等差取模数据上，
三数取中选出的 pivot 从第 2 轮起稳定落在区间 99% 处，于是"找最小值"要 104 轮、40n 次比较；
换成 LCG 打散的序列立刻回落到 ~2n。所以"平均 O(n)、最坏 O(n²)"不是理论洁癖，是会被真实输入触发的。
