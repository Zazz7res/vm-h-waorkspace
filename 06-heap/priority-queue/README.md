# 优先队列 priority-queue

> 一句话定位：**优先队列 = 二叉堆 + 一层薄壳接口（enqueue / dequeue / peek / size），它只回答一件事——"下一个该服务谁"。**

---

## 一句话是什么

一个"不按到达顺序、而按**优先级顺序**出货"的队列：

- `enqueue(优先级, 任务)`：插进去，不管它多紧急；
- `dequeue(...)`：**永远弹出当前最优先的那个**（本项目约定：优先级数字越小越紧急）；
- `peek(...)`：只问"下一个是谁"，不真出队；
- `size / empty`：还有几个人排队。

底层就是那棵**被压扁成数组的完全二叉树**（小顶堆）。本目录按"叶子目录必须自包含"的约定，
在自己目录里重写了一份极简二叉堆（就 60 行左右的 `sift_up` / `sift_down`），
没有去 `#include` 隔壁 `binary-heap` 的头 —— 能再写一遍才算真会。

---

## 为什么需要它

普通队列（FIFO）的假设是"来的顺序 = 该服务的顺序"。可现实里到处都不成立：

```
到达顺序:  #101(p5) #102(p1) #103(p3) #104(p2) #105(p4) #106(p1) #107(p9) #108(p2)

普通队列这样服务:  #101 #102 #103 #104 #105 #106 #107 #108
                   ← 最不紧急的 #107(p9) 排在 #108(p2) 前面被服务了
                   ← 最紧急的 #102(p1) 却要干等 #101(p5) 做完

优先队列这样服务:  #102 #106 #104 #108 #103 #105 #101 #107
                   ← 优先级 p1 → p9 一路排开，最不紧急的最后才轮到
```

**不用它时的三种痛：**

| 土办法 | 痛在哪 |
|---|---|
| 每次服务前把整个队列线性扫一遍找最小 | 一次 O(n)，n 个任务 O(n²)。1 万个任务 = 亿次比较 |
| 保持队列数组始终有序（插入时找位置 + 整体后移） | 找位置能二分，**但搬移尾巴还是 O(n)**；插入慢得离谱 |
| 全部收完再排一次序 | 只能处理"一批批离线数据"。任务源源不断进来时完全用不上 |
| **优先队列（堆）** | 入队 O(log n)、出队 O(log n)、看最优先 O(1)，**在线场景唯一解** |

真实用途：操作系统进程调度、急诊分诊、Dijkstra 最短路、Huffman 编码建树、
事件驱动模拟（时间轴上下一个事件）、多路归并（合并 K 个有序文件）、
作业队列（K8s / Celery 的抢占调度）、限速与任务老化（aging）……

## 内存布局图解

```
  队列里存的是「一对小整数」，不是裸 int：

      typedef struct { int priority; int id; } Task;
                        ▲             ▲
              堆只拿它比大小    纯粹跟着搬，比较时【不看】

  入队 6 个任务之后（p = priority，#n = 任务号，方括号里是数组下标）：

          树形                                    数组（唯一真实存在的东西）
                                             ┌──────────┬──────────┬──────────┐
        p0(#6)[0]                            │ p5, id=1 │ p2, id=4 │ p1, id=2 │ …
       /        \                            └──────────┴──────────┴──────────┘
  p2(#4)[1]   p1(#2)[2]                        下标 0        1          2
  /    \        /      \
p5(#1)[3] p6(#5)[4]  p3(#3)[5]                每个格子 8 字节（两个 int），
                                              整块内存 = 一次 malloc 拿到的连续数组
```

要点：

1. **一块连续数组，零个指针。** 父子关系全靠下标算：父 `(i-1)/2`、左 `2i+1`、右 `2i+2`。
   所以"队列"占的内存就是 `capacity * sizeof(Task)`，扩容时整块 `realloc` 搬家。
2. **树里越靠上 = 越先被服务。** 下标 0 就是下一个出货的任务。
3. **唯一的不变量**：父亲优先级 `<=` 孩子优先级。
   兄弟之间谁紧急，树不管 —— 看图里 `[1]=p2` 和 `[2]=p1`，右孩子反而比左孩子紧急，完全合法。
4. `id` 字段在内存里只是"搭便车"：它跟着 `priority` 一起被交换搬运，
   但从来不参与任何比较。这正是下一节那个坑的根源。

## 核心操作逐个拆解

### 操作 1：`pq_enqueue(q, priority, id)` —— 入队

**干什么**：加一个任务进去，加完队列依然"父亲不比孩子更晚服务"。

**一步步**（`pqueue.c` 的 `pq_enqueue` + `sift_up`）：

```
① 容量满了先 realloc 翻倍（摊还 O(1)）
② 在栈上凑一个 Task{priority, id}，整个赋给 data[size]
③ size++（必须先加，否则 sift_up 的边界判断看不见它）
④ sift_up(size-1)：
     while (i > 0):
        p = (i-1)/2
        if data[i].priority < data[p].priority: 交换，i = p
        else: 停
```

**真实输出**（main.c 第 2 幕，入队 #4(p2) 时它一路爬到下标 1 就停了）：

```
  enqueue(优先级 2, 任务 #4) → 先站到队尾（下标 3）
        入队后: [ p5(#1) p5(#1)… ]         ← 实际打印见下面「运行结果」
      上浮: 下标 3 <-> 1（p5(#1) <-> p2(#4)）
      停：p2(#4) 不比父亲 p1(#2) 更紧急
```

**边界情况**
- 空队列入队：`size` 0→1，`i=0` 没有父亲，一次都不换。
- 优先级比父亲"更紧急"要一直爬到根：最后到的 #6(p0) 就爬了 2 层，直接当了队首。
- `realloc` 失败：返回 -1，队列内容不变。

**复杂度**：最坏 O(log n) 次交换；随机数据下平均接近 1~2 次（新任务往往和父亲比一次就停）。

---

### 操作 2：`pq_dequeue(q, &pr, &id)` —— 出队最优先

**干什么**：拿走队首（最紧急的那个），队列依然合法。

**一步步**（三步，顺序不能改）：

```
① top = data[0]                  // 先抄答案，② 会把它盖掉
② 交换 data[0] 和 data[size-1]，然后 size--
③ sift_down(0)                   // 只有队首这一格可能不紧急，修它
```

**为什么是"和最后一个交换"**：只有末尾那个元素一定是叶子，
搬走它不会有节点失去父亲，数组下标仍然连续（结构性不破），而且只花 1 次交换。
"删队首再整体前移"结构上其实没坏，但每次 O(n)，队列操作全线退化。
（详细推导见 `06-heap/binary-heap/README.md` 的操作 2。）

**`sift_down` 里最容易写错的一处**：必须跟"两个孩子里更紧急的那个"换。
反例：队首 p5、左 p1、右 p2。跟右孩子 p2 换 → 队首变 p2、左边还留着 p1 → p2 > p1 违规；
跟左孩子 p1 换 → 队首 p1、下面变成 p5/p2 → 这一层合法。**挑最小的那个自动满足"换上来的人 <= 另一个孩子"。**

**真实输出**（第 3 幕第 1 次出队）：

```
  dequeue → 队首 p0(#6) 被服务掉。它要和队尾下标 5 的 p3(#3) 交换
      出队第一步: 下标 0 <-> 5（p3(#3) <-> p0(#6)）
        缩容后: [ p3(#3) p2(#4) p1(#2) p5(#1) p6(#5) ]
      下沉: 下标 0 <-> 2（p1(#2) <-> p3(#3)）     ← 两个孩子 p2/p1，更紧急的是 p1(#2)
        下沉结束: [ p1(#2) p2(#4) p3(#3) p5(#1) p6(#5) ]
    >>> 被服务的是 #6，优先级 p0，剩余 5 人
```

**边界情况**
- 只剩 1 个元素：`last == 0`，自己和自己交换是白做的，代码跳过交换、直接 `size--`。
- 空队列：返回 -1，**不写** `priority_out / id_out`（调用方传进去的初值保持原样，main.c 第 7 幕专门验了这一点）。
- 两个 out 参数都可以传 `NULL`，表示"我只想要它出队，不关心是谁"。

**复杂度**：最坏 O(log n)。

---

### 操作 3：`pq_peek` / `pq_size` / `pq_empty`

- `peek`：只读 `data[0]`，**O(1) 且不改结构**。第 4 幕打印了"peek 前后长度一致 ✅"。
- 这是优先队列对外提供的**全部**信息量：它知道"下一个是谁"，**不知道"第二个是谁"**。
  想知道第二优先，只能先把第一优先 dequeue 掉。
- `size` 就是 `q->size` 这一个整数，O(1)。

---

### 操作 4：⚠⚠ 优先级相同怎么办？（本节最大看点，也是真实事故源）

直觉认为"一样紧急就先来的先服务"（FIFO / 稳定性）。**堆没有这个保证。**

main.c 第 5 幕把 4 个 `priority` 全等于 1 的任务按 101、102、103、104 顺序入队，然后全部出队：

```
  连续入队 4 个【优先级都是 1】的任务：#101 #102 #103 #104（按这个顺序到达）
  入队完，数组顺序: #101 #102 #103 #104   ← 看着是 FIFO 对吧？别急，那只是因为还没有任何元素需要搬动。

  期望（先来先服务 / FIFO 稳定）: 101 102 103 104
  实际（堆的真实行为）        : 101 104 103 102
  是否稳定：❌ 不稳定   ← 注意程序【没有报错】，优先级也照样全对，只是同优先级之间不公平
```

**为什么会这样？两个原因叠加：**

1. 比较函数 `wins()` **只看 priority，不看 id**。两个任务 p 相等时 `a<b` 和 `b<a` 都是假，
   堆认为"谁在上面都行"，入队阶段不会为了先后顺序做任何事 —— 所以入队完数组看着正好是 FIFO，
   这是个**假象**（只要队列里有别的优先级、或者做过一次出队，顺序立刻乱）。
2. 出队时把**最后一个**元素搬到队首再下沉。这个搬运规则和到达顺序毫无关系，
   于是最后到的 #104（原本在 `data[3]`）被直接提到队首，插到了 #102、#103 前面。
   你可以心算复核：`[101,102,103,104]` → 出队 101 → `data[3]` 的 104 换到 `data[0]` →
   剩下 `[104,102,103]`，三者 p 全等、谁也不换 → 出队顺序就是 104、103、102。

**危害长什么样**：不是崩溃、不是报错，而是"某个任务被同优先级的后来者无限插队"。
在真实调度系统里这叫**饥饿（starvation）**，排查起来极其难受，因为一切"看起来都正常"。

**工程解法（本项目刻意【不】实现，只给写法）**：给每个任务发一个入队时的**自增序号 `seq`**，
比较时按双键 —— 只改 2 行：

```c
typedef struct { int priority; int id; int seq; } Task;   /* 多一个字段 */

static int wins(const Task *a, const Task *b)
{
    if (a->priority != b->priority) return a->priority < b->priority;
    return a->seq < b->seq;          /* p 相同 → 序号小的（先来的）赢，稳定性立刻到手 */
}
/* enqueue 里写：t.seq = (int)q->enqueued++;  复杂度完全不变，仍是 O(log n) */
```

**为什么不顺手实现掉？** 因为"堆本身不稳定"这个事实值得你亲自踩一次；
而且加了 seq 之后每个元素多 4 字节、比较逻辑多一层，工程上是有代价的取舍。
顺带记住这条结论：**堆排序不稳定、`std::priority_queue` 也不稳定**，是同一个原因。

## 复杂度表（横向对比）

| 操作 | **优先队列（堆）** | 普通队列（FIFO，链表/循环数组） | 始终保持有序的数组 | "先攒着，最后排一次序" |
|---|---|---|---|---|
| 入队 enqueue | **O(log n)** | **O(1)** | O(n)（要找位置 + 搬移） | O(1) |
| 出队（要最优先） | **O(log n)** | O(1)，但拿到的是**最早到的** | **O(1)** | — 还没排完序 |
| peek 最优先 | **O(1)** | O(1)，但那是"最早到"不是"最优先" | O(1) | O(n)（要先排序） |
| 查某任务在不在 | O(n) | O(n) | O(log n)（可二分） | O(n) |
| 删除/修改队列中间的任务 | O(n)（得先线性找到它） | O(n) | O(n) | O(n) |
| 服务完全部 n 个 | **O(n log n)** | O(n) | O(n) | O(n log n)（排序）+O(n) |
| 相同优先级先来先服务 | ❌ **不保证**（见上文） | ✅ 天然 | 取决于实现 | 取决于排序稳定性 |
| 额外空间 | O(n)，一块连续数组 | O(n)（链表另加指针） | O(n) | O(n) |
| 能否在线（边进边出） | ✅ | ✅ | ✅（但插入慢） | ❌ 必须等全部到齐 |

定位一句话：**要"该先做的先做"且任务是流进来的，优先队列是唯一合理选择；
只要顺序无关紧要（或顺序就是到达顺序），普通队列 O(1) 更划算。**

5. 关键坑：优先级相同的任务，先来【不】先服务
----------------------------------------
  连续入队 4 个【优先级都是 1】的任务：#101 #102 #103 #104（按这个顺序到达）
  入队完，数组顺序: #101 #102 #103 #104   ← 看着是 FIFO 对吧？别急，那只是因为还没有任何元素需要搬动。

  开始按顺序出队：
    出队 #101（p1）
    出队 #104（p1）
    出队 #103（p1）
    出队 #102（p1）

  期望（先来先服务 / FIFO 稳定）: 101 102 103 104
  实际（堆的真实行为）        : 101 104 103 102 
  是否稳定：❌ 不稳定   ← 注意程序【没有报错】，优先级也照样全对，只是同优先级之间不公平

  为什么会这样？两个原因叠加：
    ① 比较函数只看 priority。两个任务 p 相同 → a<b 和 b<a 都是假，
       堆认为「谁在上面都行」，所以入队时【不会】为了先后顺序做任何事。
    ② 出队时把【最后一个】元素搬到队首，再下沉。这个搬运规则和到达顺序毫无关系，
       于是最后到的 #104 被直接提到队首附近，插到了 #102、#103 前面。
       （你可以自己心算一遍：4 个元素出队第 1 次后，data[3] 的 #104 被换到 data[0]。）

  工程上怎么破？—— 给每个任务发一个【自增序号】，比较按双键：
       typedef struct { int priority; int id; int seq; } Task;
       wins(a,b):  if (a->priority != b->priority) return a->priority < b->priority;
                    return a->seq < b->seq;      // 优先级相同 → 序号小的先走
       enqueue 时写 seq = q->enqueued++;
  只改比较那 2 行 + 入队记 1 个字段，稳定性立刻就有，复杂度一点没变（O(log n)）。
  本项目【不实现】它：因为「堆本身不保证稳定」这个事实值得你踩一次坑记住。
  顺带：这也是为什么 C++ 的 priority_queue、甚至很多排序实现都标榜「堆排序不稳定」。

## 常见的坑

1. **以为同优先级会先来先服务。** 本节主演：入队 101/102/103/104（p 全为 1），
   出队拿到的是 `101 → 104 → 103 → 102`。不报错、不崩溃，只是后来的插了队。
   修法：加自增序号做 `(priority, seq)` 双键比较。

2. **优先级数字的方向没约定清楚。** "1 是最高优先级"还是"9 是最高优先级"？两种约定都有人用。
   本实现是**越小越紧急**（小顶堆）。如果业务是"分数越高越该先做"，
   要么存 `-score`，要么把堆改成最大堆。**接口上写清楚，别靠猜。**

3. **以为 dequeue 两次就能拿到"第二优先"，而且很快。** 第一次 O(log n)，之后第二优先才是新队首；
   想要"前 3 个最优先"就必须真出队 3 次再入队回去（或用额外数组暂存）。
   堆没有"按名次随机访问"的能力。

4. **不判断返回值就用 out 参数。** 空队列时 `pq_dequeue` 返回 -1 且**不写** `priority_out/id_out`，
   里面的值还是你传进去前的旧值。第 7 幕专门演示了"初值 123/456 保持不动"。
   `if (pq_dequeue(q, &pr, &id) != 0) { /* 空，走另一条路 */ }` 是必须的写法。

5. **反复 `peek` 却不 `dequeue`，死循环。** peek 不删任何东西（这是它的优点也是坑）：
   `while (pq_peek(q,&pr,&id)==0) { ... }` 会永远拿到同一个任务。循环体里必须有 dequeue。

6. **想"修改已入队任务的优先级"或"取消某个任务"。** 堆不能按 id 定位，只能 O(n) 找到它、
   改完再既可能上浮又可能下沉。工程上的常规做法是**惰性删除**：
   不真删，只打个 `cancelled` 标记，dequeue 时遇到标记就丢掉继续弹下一个
   （Dijkstra 的堆实现就是这么干的）。别硬改堆。

7. **忘了 `pq_free` 之后要把指针置 NULL。** 堆内存还回去了，但 `q` 里存的地址数值不变 → 悬空指针。
   main.c 里每个 `pq_free(q); q = NULL;` 都是连着写的。

8. **在不需要"优先级"的场景硬用优先队列。** 如果服务顺序就是到达顺序（消息队列、BFS），
   普通队列 O(1) 更简单更快；引入堆只会让代码变长、常数变大。

## 什么时候用它 / 什么时候别用

**该用：**
- 任务/请求带紧急程度，且任务**源源不断到达**（在线调度、消息优先级、抢占式调度器）。
- 图算法：Dijkstra、Prim、A*（见 `07-graph/dijkstra`）。
- 合并 K 个有序序列 / K 路归并 / "永远知道当前最小那一堆的首元素"。
- Huffman 编码建树：反复"取两个最小的权重合并回去"。
- 事件驱动模拟：按虚拟时间弹出下一个事件。
- Top-K（见 `06-heap/top-k`，那里用的是"固定大小的 K 堆"这个变体）。

**不该用：**
- 顺序就是到达顺序 → 普通队列（`04-queue/*`），O(1) 且没有稳定性问题。
- 所有数据一次性到齐、只要最后有序 → 排一次序（`10-sorting/*`），O(n log n) 但常数小得多。
- 要频繁查"某个任务在不在队列里"、要删任意任务 → 哈希表 + 链表（LRU 那种组合，见 `09-others/lru-cache`）。
- 要"第 K 优先"这种名次随机访问、或者要前缀/区间统计 → BST（带 size 域）/ 树状数组 / 线段树。
- 只有 3~5 个候选 → 直接线性扫，代码短一半，实际更快。

## 自检问题

1. **入队 4 个优先级都是 1 的任务，数组顺序看着就是 FIFO，为什么说出队会乱？**
   **答：** 入队阶段相等不交换，所以顺序"碰巧"保住了。但第一次出队会把 `data[size-1]`
   （最后到的那个）搬到队首，从此顺序和到达时间无关。实测出队顺序 `101 104 103 102`。
   堆的比较只看 priority，它对"谁先来"这件事**没有任何信息**。

2. **想让优先队列稳定，最小改动是什么？代价？**
   **答：** `Task` 加一个入队时发的自增 `seq`，比较函数改成双键：
   先比 `priority`，相同再比 `seq`。复杂度还是 O(log n)，代价是每元素多 4 字节 + 比较多一层分支。

3. **`pq_peek` 和 `pq_dequeue` 的区别，除了"删不删"还有什么？**
   **答：** 时间复杂度不同：peek 是 O(1)（只读 `data[0]`），dequeue 是 O(log n)
   （交换 + 下沉，会改变整棵树）。另外 peek **不写**任何东西、不改 `size`，
   所以适合"先看一眼要不要处理"的判断；dequeue 才真正出货。

4. **`pq_dequeue(q, NULL, &id)` 合法吗？返回 -1 时 `id` 是什么值？**
   **答：** 合法，`NULL` 表示"优先级我不要"。返回 -1（队列空）时函数**完全不写** out 参数，
   `id` 保持调用前的旧值 —— 所以必须判返回值，不能拿 out 参数当"有没有取到"的依据。

5. **为什么本目录要自己重写一份堆，而不 `#include "../binary-heap/heap.h"`？**
   **答：** 两条原因。① 工程约定：Makefile 按叶子目录独立编译，跨目录 include 会直接编译失败，
   所以每个目录必须自包含；② 教学考虑：堆的骨架就 `sift_up` + `sift_down` 两件事，
   换一种元素类型（这里从 `int` 换成 `Task`）再写一遍，才知道哪些部分是"和类型无关的骨架"。
