# 二叉堆 binary-heap

> 一句话定位：**堆是一棵被压扁成数组的完全二叉树，专职用 O(1) 告诉你"现在最小（或最大）的是谁"。**

---

## 一句话是什么

堆（heap）就是一个数组，但我们**用下标把它当成一棵树来读**：

- 下标 0 是树根，永远是全局最小（最小堆）或最大（最大堆）的那个值；
- 任意下标 `i` 的父亲是 `(i-1)/2`，左孩子 `2i+1`，右孩子 `2i+2`；
- 于是"取最值"只要看 `data[0]`，"塞一个新值"只要沿下标往上爬，**全程 O(log n)，一个指针都不用**。

它不是排序，不是二叉搜索树，不是优先队列本身 —— 它是**这些工具的发动机**。

---

## 为什么需要它

先想想不用堆会怎样。你手上有一堆任务，需要随时知道"最紧急的那个是谁"，并且不断取走它：

| 做法 | 插入 | 取最值 | 取完 n 个的总代价 | 痛在哪 |
|---|---|---|---|---|
| 无序数组，取最值时全扫一遍 | O(1) | O(n) | O(n²) | 每次都要从头比一遍，100 万个任务就是 10^12 次比较 |
| 保持数组有序（插入时二分找位置 + 整体后移） | O(n) | O(1) | O(n²) | 找位置快了，**但搬移尾巴还是要 O(n)** |
| 每次插入后重新排序 | O(n log n) | O(1) | O(n² log n) | 荒唐，但真的有人这么写 |
| **二叉堆** | **O(log n)** | **O(1)** | **O(n log n)** | —— |

关键洞察：**我们其实不需要"整体有序"，只不需要知道"谁最突出"。**
把一个 n 个元素的集合维护成完全有序，代价很高；但只维护"父亲不差于孩子"这一条**局部**约束，
就能免费拿到全局最值 —— 因为沿着"最值一定在根上"这条推理链，局部约束会层层传递到顶部。

**这就是堆的哲学：用尽可能弱的有序性，换尽可能快的最值查询。**

真实场景：操作系统的任务调度、Dijkstra 最短路、Prim 最小生成树、Top-K（热搜前 10）、
合并 K 个有序链表、事件模拟的时间轴、中位数流（对顶堆）…… 全部是"只要最值"的场景。

## 内存布局图解

### 1. 同一个东西的两种画法

```
        树形（我们脑子里的样子）                    数组（内存里真实的一块连续空间）

                 1(0)                          下标:   0    1    2    3    4    5    6
             /       \                         值  :   1    3    2    7    9    5    6
          3(1)       2(2)
        /     \     /    \                     ┌────┬────┬────┬────┬────┬────┬────┐
     7(3)  9(4)  5(5)  6(6)                    │  1 │  3 │  2 │  7 │  9 │  5 │  6 │
                                               └────┴────┴────┴────┴────┴────┴────┘
                                                ▲    ▲         ▲
                                               根    根的左孩子  根的右孩子
```

**数组里没有任何指针。** 父子关系完全由下标算出来。这就带来三个好处：
1. 省内存（BST 每个节点要额外存 2 个指针 = 16 字节，堆每个元素只多 0 字节）；
2. 内存连续，CPU 缓存友好（访问孩子就是往前跳 2i 格，很可能还在同一缓存行了）；
3. 建堆、销毁都是"一块 malloc / 一块 free"，没有逐节点释放的麻烦。

代价是：**下标一旦和树的形状绑定，形状就不能随便变**。所以堆只能删堆顶（见下文），
删中间的元素是 O(n) 的苦力活。

### 2. 为什么这三条公式一定对（本节最该看懂的一段）

先看实测（main.c 第 2 幕会把这张表打出来）：

```
  下标 i | 二进制 |   父 (i-1)/2  |   左 2i+1   |   右 2i+2
       0 | 00000 |      无(根)   |           1 |           2
       1 | 00001 |             0 |           3 |           4
       2 | 00010 |             0 |           5 |           6
       3 | 00011 |             1 |           7 |           8
       4 | 00100 |             1 |           9 |          10
```

**"左 = 2i+1、右 = 2i+2"的来源**：完全二叉树第 d 层有 2^d 个节点，
第 0 层到第 d-1 层一共占掉 `2^d - 1` 个格子，所以第 d 层的下标从 `2^d - 1` 开始连续排。
把第 d 层第 k 个节点（`i = 2^d - 1 + k`）的孩子放到第 d+1 层的第 2k、2k+1 位上，代进去化简就是 `2i+1` 和 `2i+2`。
更直觉的记法：看上面的二进制列 —— **父亲就是把下标的二进制砍掉最后一位，孩子就是末尾添一位再挪 1 格**
（添 0 → 左，添 1 → 右；`+1/-1` 那个偏移是因为我们从 0 起下标，而不是 1 起下标）。

**"父 = (i-1)/2"为什么天然成立**（这是最容易含糊过去的地方，值得单独证）：
把孩子的下标代回父亲公式，看能不能算回原来的父亲 `p`。

```
  情况 A：i 是左孩子，即 i = 2p + 1
          (i - 1) / 2 = (2p + 1 - 1) / 2 = 2p / 2 = p                       ✅ 整除，干净

  情况 B：i 是右孩子，即 i = 2p + 2
          (i - 1) / 2 = (2p + 2 - 1) / 2 = (2p + 1) / 2 = p 余 1 → 砍掉 = p   ✅ 靠"砍掉小数"
```

情况 B 是关键：`(2p+1)/2` 的真值是 `p.5`，必须**向下取整**才落到 p。
而 C 语言的整数除法是**向零截断**：

- 正数时：向零截断 == 向下取整（`5/2 = 2`）✅
- 负数时：向零截断 != 向下取整（`-3/2` 在 C 里是 `-1`，向下取整应该是 `-2`）❌

而孩子的下标 `i >= 1`，所以分子 `i-1 >= 0`，**永远不会碰到负数那一支**。
于是公式安全落地。一句话总结：

> `(i-1)/2` 不是随手写的，它能成立**依赖于"下标非负"这个前提**。
> 你要是把它写成 `i/2 - 1`，`i=1` 时会算出 `-1`（正确答案是 0）—— 这就是初学者最常见的下标 bug。

（顺带：如果改用 1 起下标，公式变成更漂亮的"父 = i/2、左 = 2i、右 = 2i+1"，纯位移无偏移。
网上教程 0 起和 1 起两种写法混着出现，是看不懂父子关系的头号原因。**看清对方用的是哪种，本项目全程 0 起。**）

### 3. 两个不变量（任何操作前后都必须成立）

```
① 结构性 —— 必须是【完全二叉树】：
   除了最后一层每层塞满，最后一层从左往右【连续】，中间不许有洞。

   合法的形状（数组长度 6）：            非法的形状（下标 2 是洞）：
        X                                  X
       / \                                / \
      X   X                             X   X    ← 左孩子空着，右孩子却有值
     / \    \                                   数组写成 [0,1,_,3,4]，
    X   X    X                            这时 data[3] 到底是谁的孩子？说不清，树就散了

② 堆序性 —— 最小堆：任何父亲 <= 它的孩子（最大堆反过来）
   data[(i-1)/2] <= data[i]   对所有 i >= 1 成立
```

结构性是被**数组这个载体免费保证**的：数组下标天生连续 0..size-1，不可能有洞，
除非你自己搬移元素去破坏它。所以堆的所有操作都遵循同一套打法：

> **只在数组的开头或末尾动一刀（保住结构性），然后修复唯一的那一处堆序违例。**

由 ① + ② 可以推出第 ③ 条：**堆顶 `data[0]` 一定是全局最小值**
（任何一个元素都比不过它自己这条链上的父亲，一路传到顶，就都比不过堆顶）。

### 4. ⚠ 堆【不是】排序：最重要的一个认知纠偏

堆序性只约束"父亲和孩子"，对**兄弟之间**、对**跨层的两个不相关节点**、
对**下标的先后**没有任何承诺。main.c 第 5 幕会打出这个活例子：

```
   下标:   0   1   2   3   4   5   6
   值  :   1   3   2   5   4   9   8      ← 这是一个完全合法的最小堆
```

- `data[1] = 3`，`data[2] = 2`：**数组不是升序**（2 排在 3 后面，而 2 比 3 小）。
- 但它们是兄弟，堆根本不管兄弟之间谁大。
- `data[0] = 1` 确实是全场最小 —— 这才是堆唯一保证的东西。

所以：

| 你想要 | 该怎么做 | 代价 |
|---|---|---|
| 现在最值是谁 | `data[0]`（peek） | O(1) |
| 第 2 小 | 只能 pop 掉最小的，再看新的堆顶 | O(log n) |
| 第 K 小 | pop K 次 | O(K log n) |
| 全体有序 | pop 光（= 堆排序）或去 `10-sorting/heap-sort` | O(n log n) |
| 查某个值在不在 | 堆**不擅长**，要 O(n) 全扫。请去哈希表或 BST | O(n) |

再补一刀常见误解：**堆也不是二叉搜索树**。BST 要求"左 < 根 < 右"，堆只要求"父 <= 子"；
对堆做中序遍历得到的**不是**升序（本项目 `05-tree/bst` 讲 BST，别把两者混了）。

## 核心操作逐个拆解

### 操作 1：`heap_push(h, value)` —— 插入（上浮）

**干什么**：往堆里加一个数，加完堆必须依然合法。

**一步步怎么做**（对应 `heap.c` 的 `heap_push` + `sift_up`）：

```
第 1 步  把 value 写到 data[size]，然后 size++
         ↓ 为什么放末尾？数组末尾 = 完全二叉树"最后一层最右边"的空位。
           在那里挂一个新节点，形状依然完全合法（结构性不破）。
           放中间就得整体搬移 → O(n)，白学。
         ↓ 为什么必须先 size++ 再 sift？因为 sift_up 里用 l/size 做边界判断，
           不加上去它根本"看不见"这个新元素。

第 2 步  sift_up(新下标)：
           while (i > 0):                      // i > 0 就是"还有父亲"
               p = (i-1)/2
               if 孩子比父亲更该在上面:  交换，i = p
               else:                 停
         每一轮 i 至少砍一半（(i-1)/2 <= i/2），所以最多走 log2(n) 步。

第 3 步  停下的条件只有两个：不比父亲更优（堆序性已恢复）/ 撞到根（没有父亲了）。
```

**跑起来什么样**（main.c 第 3 幕真实片段，push 1 到已有堆 `[3 5 8]` 里）：

```
    push(1)：先挂到下标 3（完全二叉树只能从尾巴往后长）
      挂上后数组: [ 3 5 8 1 ]
      上浮：交换下标 3 <-> 1，值 5 <-> 1        ← 父亲是 data[(3-1)/2]=data[1]=5，1 < 5 所以换
      交换后数组: [ 3 1 8 5 ]
      上浮：交换下标 1 <-> 0，值 3 <-> 1        ← 再比一次：父亲 data[0]=3，1 < 3 再换
      交换后数组: [ 1 3 8 5 ]
        停：已经到堆顶（下标 0），没有父亲了    ← 爬到顶了，收工
```

**边界情况**
- 空堆插入：`size` 从 0 变 1，`i = 0` 没有父亲，循环一次都不进 —— 正确。
- 容量满：先 `realloc` 翻倍（摊还 O(1)），失败返回 -1 且堆保持原样。
- 值**等于**父亲：不换（比较用严格 `<`）。这既避免无意义的来回搬，也让输出可预测。

**复杂度**：最坏 O(log n) 次交换；平均（随机数据）只有约 1~2 次，非常便宜。

### 操作 2：`heap_pop(h, &out)` —— 取走堆顶（下沉）

**干什么**：拿走 `data[0]`（最小值），堆依然合法。

**本节最需要讲透的一段：为什么必须和最后一个元素交换，而不能直接删掉堆顶再把后面搬上来？**

我们同时受两条约束支配：

```
(a) 数组下标必须连续（0..size-1），中间不能有洞 —— 否则"压扁的树"当场散架。
(b) 堆顶那一格删掉之后，必须有值把它填上（树不能没有根）。
```

逐一检查候选：

| 候选填补者 | 满足 (a) 吗 | 满足 (b) 吗 | 代价 |
|---|---|---|---|
| **最后一个元素**（`data[size-1]`） | ✅ 末尾剪掉一格，其余下标一个都不用动 | ✅ | **1 次交换** |
| 中间某个元素（比如 `data[3]`） | ❌ 下标 3 留下一个洞，`data[k]` 是谁的孩子就说不清了 | ✅ | 要补洞就得整体搬移 |
| 后面的元素整体往前挪一格（"直接删堆顶"） | ✅ 形状碰巧还是完全二叉树 | ✅ | **搬 size-1 个元素 = O(n)** |
| 孩子的值一路"下拉"，空位往下传 | ✅ | ✅ | O(log n) 次搬移 + 最后仍需一个叶子填空 |

结论：
- **只有末尾元素一定同时满足 (a)(b)，而且只花 O(1)**。末尾元素必然是叶子（它不可能是任何节点的孩子之后还有孩子），
  搬走一个叶子不会让任何节点失去父亲 —— 这正是它被选中的深层原因。
- "直接删堆顶 + 整体前移"其实**结构不会坏**（很多人以为是结构坏了，不是），
  真正的致命点是复杂度：每次 pop 变成 O(n)，n 次 pop 就是 O(n²)，比冒泡排序还难看，堆彻底白学。
- "孩子下拉"（hole punching）思路是对的，工业实现偶尔用（少写一次交换），
  但它一路向下同样要挑孩子、最后仍要剪掉一个叶子，收益不抵代码复杂度的增加。教材实现一律用**交换法**。

**一步步怎么做**：

```
第 1 步  top_value = data[0]                       // ⚠ 先抄下来！下一步就把它覆盖了
第 2 步  交换 data[0] 和 data[size-1]               // 把要删的最小值挤到尾巴上
第 3 步  size--                                    // 剪掉尾巴：那个最小值就不属于堆了
第 4 步  sift_down(0)                              // 只有堆顶这一格可能违例，修它
```

`sift_down` 的关键细节：**要跟"两个孩子中更优的那个"比，不能只跟左孩子比。**

```
      5                            反例：父 5，左 1，右 2
    /   \
   1     2                        ① 若跟右孩子(2)换 → 父 2，左 1 → 2 > 1 仍然违规 ❌
                                   ② 跟左孩子(1)换 → 父 1，左 5，右 2 → 这一层合法 ✅
   为什么？因为换完之后，爬上来的那个孩子要接替父亲的位置，
   它必须 <= 另一个孩子（否则新的父子对立刻违规）。
   挑"两个孩子里更小的那个"就自动满足这一点：min(l,r) <= max(l,r)。
```

**跑起来什么样**（main.c 第 4 幕真实片段）：

```
    pop 堆顶：答案=1（下标 0）。它要和末尾 data[6]=8 交换
      pop 第一步：交换下标 0 <-> 6，值 8 <-> 1
      交换后数组: [ 8 3 2 5 4 9 1 ]
        size-- => 6（尾巴上那个 1 已经不属于堆了）
      缩容后数组: [ 8 3 2 5 4 9 ]
      下沉：交换下标 0 <-> 2，值 2 <-> 8        ← 两个孩子 3 和 2，更小的是 2（下标 2）
      交换后数组: [ 2 3 8 5 4 9 ]
        停：2 已经是自己和孩子里最该在上面的，这一带合法
```

**边界情况**
- `size == 1`：`last == 0`，自己和自己交换是白做的，代码里直接跳过交换、只做 `size--`（main 会打一行提示）。
- `size == 0`：返回 -1，不写 `out`，不崩。
- `out == NULL`：合法，表示"我只想丢掉堆顶，值不关心"。
- 下沉时**只有一个左孩子**：完全二叉树的性质保证"有右孩子必有左孩子"，
  所以只需处理"左孩子存在、右孩子越界"这一种半边情况 —— 代码体现为
  `先假设 best=左；只有当右孩子存在且更优时才改成右`。

**复杂度**：最坏 O(log n)（一路沉到底）。

### 操作 3：`heap_peek` —— 只看不动

**干什么**：读 `data[0]`，不删除。**O(1)**，这是堆唯一的全局信息。
**边界**：空堆返回 -1。

### 操作 4：`heap_build(h, arr, n)` —— 把一整批数据堆化，O(n)

**干什么**：给定 `n` 个现成数字，造出一个合法堆。

**一步步怎么做**：

```
第 1 步  把 arr 原样 memcpy 进 data，size = n
         ↓ 此刻"结构性"已经成立（数组连续 = 形状正确），"堆序性"还没成立。
第 2 步  for (i = n/2 - 1; i >= 0; i--)  sift_down(i)
         ↓ 从"最后一个有孩子的节点"开始，一路往前，逐个下沉。
```

**为什么起点是 `n/2 - 1`？**
`i` 是叶子 ⟺ 它的左孩子越界 ⟺ `2i+1 >= n` ⟺ `i >= (n-1)/2`。
也就是说数组**后半段大约 n/2 个全是叶子**，叶子没有孩子、堆序性自动成立，
对它们 sift_down 一步就返回（纯浪费），所以只处理 `0 .. n/2-1`。

**为什么必须"从后往前"？**
`sift_down(i)` 的正确性前提是：**i 的两个孩子为根的子树已经是合法堆**。
下标越大在树里越深，先修深的，等修到浅的时候它的子树刚好已经就绪。
反过来从 `i=0` 开始，前提不成立，修了也白修（下面又被上面弄乱）。

**为什么总代价是 O(n) 而不是 O(n log n)？（必考点）**

表面上看：`n/2` 个节点 × 每个最多下沉 `log n` 层 = O(n log n)。
错在"每个都下沉 log n 层"这个假设。真相是**下沉距离的分布极度倾斜**：

```
  层 d      本层节点数     最多下沉步数      该层总功上界
  第 0 层        1              log n             1 × log n
  第 1 层        2            log n - 1             2 × (log n - 1)
  ...
  倒数第 2 层   n/4               2                  n/4 × 2
  最后一层     n/2               0                  0        ← 一半的人白拿，一步不动
```

一半节点动 0 步、四分之一节点最多 1 步、八分之一最多 2 步……
总功 `= n × (0/2 + 1/4 + 2/8 + 3/16 + …) = n × 1 = O(n)`。
（那个级数 `Σ d/2^(d+1)` 收敛到 1，差比级数，记结论就行。）

**大白话版**：树是个金字塔。**砖头最多的那几层，离地面（叶子）最近。**
所以从底往上修，每块砖只挪一点点，总量当然是线性的。

对比 `逐个 push` 建堆为什么是 O(n log n)：
push 是**上浮**，而新元素**永远被放在最深的地方**（末尾），它要往上爬，
爬的距离平均就是 log n 级别 —— 数据最坏（降序进来）时每次都要爬满，跑不掉。

**本仓库把这两个数字真的量出来了**（main.c 第 7 幕，用 `cmp_count` 统计比较次数）：

```
        n  | heapify比较 | 增长倍数 | 逐个push比较 | 增长倍数 | n·log2n参考线
    1000 |        1982 |      -- |         7987 |      -- |     10000
    2000 |        3980 |   2.01 x |        17964 |   2.25 x |     22000
    4000 |        7978 |   2.00 x |        39917 |   2.22 x |     48000
    8000 |       15976 |   2.00 x |        87822 |   2.20 x |    104000
```

n 翻倍：heapify 的比较次数几乎**正好**翻倍（一次函数的特征），
push 翻得比 2 倍多一点 —— 多出来的那一点就是 `log n`，正是 O(n log n) 与 O(n) 的分界线。

⚠ 还要提醒一件实测里的陷阱（main.c 第 7.3 幕故意演示了它）：
把输入换成近似随机的数据，push 就只比 heapify 慢 1.04~1.11 倍，**几乎看不出差距**。
因为随机数据下新元素往往和父亲比一次就停了，平均上浮距离接近常数。
所以"渐进复杂度"讲的是**最坏趋势**，做实测必须挑对输入，否则会得到"两者一样快"的错误结论。
（我第一版还把 push 测在了一个**已经装满**的堆上，测出来两者一样快 —— 那是假的，
 实验设置错了比代码 bug 更难发现，所以这段留着当反面教材。）

**边界**：`n == 0` → 空堆；`n > capacity` → 先扩容；`arr` 本身不被修改（我们拷了一份）。

### 操作 5：最大堆 = 把比较号反过来

整份 `heap.c` 里"比大小"这件事**只出现在一个函数**：

```c
static int better_than(Heap *h, int a, int b)
{
    if (h->kind == HEAP_MAX) {
        return a > b;      /* 最大堆：大的往上走 */
    }
    return a < b;          /* 最小堆：小的往上走 */
}
```

所以上浮、下沉、建堆、pop 的代码**一行都不用改**，翻转 `kind` 就是另一个堆。
main.c 第 8 幕同一批数据跑两个堆：

```
      最小堆数组: [ 1 3 2 5 4 9 8 ]
      最大堆数组: [ 9 4 8 1 3 5 2 ]
      最小堆堆顶 = 1   最大堆堆顶 = 9
```

（这里**没有**用 `void *`，也**没有**用函数指针比较器 —— 一个枚举字段就够，
 符合本项目"元素永远是 int、比较逻辑不许复杂化"的约定。）

⚠ **一个反直觉的事实，必须记住**：

| 库 | 默认是 | 想要另一种 |
|---|---|---|
| C++ `std::priority_queue` | **最大堆**（默认 `less`，堆顶最大） | 得写 `priority_queue<int, vector<int>, greater<int>>` |
| Python `heapq` | **最小堆** | 想要最大堆就存负数 |
| Java `PriorityQueue` | **最小堆** | 传 `Collections.reverseOrder()` |
| 本项目的 `heap_new(cap, kind)` | 显式传 `HEAP_MIN` / `HEAP_MAX` | —— |

C++ 默认最大堆是因为它的设计目标是"排序语义下的 less = 升序"，结果坑了无数人：
写着"取最小值"的题，pop 出来全是最大值。**别背，去验证一行。**

## 复杂度表（和同类结构横向对比）

| 操作 | **二叉堆** | 无序数组 | 有序数组 | 平衡 BST(AVL/红黑) | 哈希表 |
|---|---|---|---|---|---|
| 取全局最小/最大 | **O(1)** | O(n) | **O(1)** | O(log n) | — 不保证 |
| 插入 | **O(log n)** | **O(1)** | O(n)（要搬移找位置） | O(log n) | O(1) |
| 删除最值 | **O(log n)** | O(n) | O(1)~O(n) | O(log n) | — 不保证 |
| 查找任意值在不在 | O(n) | O(n) | O(log n) | O(log n) | **O(1)** |
| 全体有序输出 | O(n log n)（pop 光） | O(n log n)（排序） | **O(n)** | O(n)（中序） | O(n log n) |
| 删除任意元素 | O(n)（要先找到它） | O(n) | O(n) | O(log n) | O(1) |
| 额外空间 | **O(1) 原地**（就那块数组） | O(n) | O(n) | O(n)（每节点 2 指针） | O(n) + 桶 |
| 建好 n 个元素 | **O(n)**（heapify） | O(n) | O(n log n) | O(n log n) | O(n) |
| 缓存友好度 | 很高（连续内存） | 很高 | 高 | 差（节点散落堆上） | 中 |

一眼能读出堆的定位：

- 只要业务是**"反复要最值"**，堆在"取最值 + 插入 + 删最值"这三件事上没有对手。
- 只要业务是**"查某个值在不在"**，堆很差（O(n)），换哈希表。
- 只要业务是**"删任意位置的元素"**，堆也很差（要线性找），换 BST 或哈希表 + 延迟删除。
- 需要**"有序 + 动态插入"**？堆给不了整体有序，用 BST / 跳表 / 或者干脆排序一次。

7. 复杂度实测：heapify 是 O(n)，逐个 push 是 O(n log n)
----------------------------------------
  【7.1】n=1000 时树有 10 层。第 d 层最多 2^d 个节点，最多下沉 (层数-1-d) 步：
    层 d | 本层节点数 | 最多下沉 | 该层步数上界
        0 |          1 |        9 |           9
        1 |          2 |        8 |          16
    ...（中间层省略）
        7 |        128 |        2 |         256
        8 |        256 |        1 |         256
        9 |        489 |        0 |           0
    合计下沉步数上界 = 1013 步（每步最多 2 次比较）→ 1.01 倍 n，线性！
    看清楚了吗：1000 个节点里，光最后一层就有 489 人，他们下沉 0 步；
    倒数第二层最多 256 人，每人最多挪 1 步。真正要挪很多步的只有顶上几层，
    而那里总共才几个人。**人多的地方离地面近** —— 这就是 O(n) 的全部秘密。

  【7.2】实测（输入用【降序】，这是 push 的最坏情况）：
        n  | heapify比较 | 增长倍数 | 逐个push比较 | 增长倍数 | n·log2n参考线
    1000 |        1982 |      -- |         7987 |      -- |     10000
    2000 |        3980 |   2.01 x |        17964 |   2.25 x |     22000
    4000 |        7978 |   2.00 x |        39917 |   2.22 x |     48000
    8000 |       15976 |   2.00 x |        87822 |   2.20 x |    104000
    解读：n 翻倍时 heapify 的次数几乎正好翻倍（=一次函数），
          而 push 翻的比 2 倍还多一点 —— 多出来的那一点就是 log n，
          它就是 O(n log n) 和 O(n) 的分界线。n 越大这个差距越夸张。

  【7.3】同一批规模，把输入换成【确定性打乱】（近似随机）：
  n=  1000  heapify=    1776  逐个 push=    1979  （push 只慢 1.11 倍）
  n=  2000  heapify=    3480  逐个 push=    3697  （push 只慢 1.06 倍）
  n=  4000  heapify=    6874  逐个 push=    7122  （push 只慢 1.04 倍）
    随机数据时新元素往往和父亲比一次就停了，平均上浮距离接近常数，
    所以 7.2 和 7.3 的差距能看出：**渐进复杂度讲的是最坏趋势，
    实测必须挑对输入，否则会得到【两者一样快】的错误结论。**

  为什么差这么多（结论背下来）：
    · heapify 从【最深的一层】往上处理：一半节点（n/2）是叶子，下沉 0 步；
      四分之一节点最多 1 步……总功 = n x (0/2 + 1/4 + 2/8 + 3/16 + ...) = n x 1 = O(n)。
      一句话：金字塔底层的砖头最多，但它们离地面最近，每人挪一点点。
    · push 正好相反：新元素【永远被放在最深的地方】，降序输入时每次都要爬满
      log n 层，n 次就是 O(n log n) —— 这个 log n 在最坏情况跑不掉。
    · 所以标准库和教材都说：手里已经有一整批数据时用 heapify，
      数据是源源不断流进来的才只能逐个 push。

## 常见的坑

1. **以为堆是排序** —— 看到 `data[1]=3, data[2]=2` 就觉得"堆写错了"。
   堆只保证父 <= 子，兄弟之间、跨层之间完全无序。想有序请反复 pop 或去 `10-sorting/heap-sort`。

2. **pop 时把堆顶删掉然后整体前移**。结构其实没坏，但每次 O(n)、n 次 pop 变 O(n²)，
   堆的意义全丢。**必须**"和末尾交换 → size-- → 下沉"。

3. **下沉时只跟左孩子比**。见操作 2 的反例（父 5、左 1、右 2）：跟右孩子换完仍然违规。
   **必须先比较两个孩子，挑更优的那个。**

4. **建堆方向写反**：`for (i = 0; i < n/2; i++) sift_down(i)`。
   sift_down 的前提是"子树已合法"，从根开始往下修，上面修好下面又坏。
   必须 `for (i = n/2 - 1; i >= 0; i--)`，**从后往前**。

5. **0 起下标和 1 起下标混用**。0 起：父 `(i-1)/2`、左 `2i+1`、右 `2i+2`；
   1 起：父 `i/2`、左 `2i`、右 `2i+1`。抄代码时对着错的那套，结果是下标永远差一格。
   把 `(i-1)/2` 写成 `i/2 - 1` 也是同一个错误（`i=1` 时算出 -1）。

6. **`push` 里忘了先 `size++` 再 `sift_up`**，或者 `pop` 里忘了先 `top = data[0]` 再交换
   —— 后者会让你返回一个"被末尾元素覆盖掉之后"的错值。这两个顺序错误都不会崩，
   只会**悄悄给出错误答案**，最难查。

7. **以为堆能高效删除任意元素**。堆没有任何"按值定位"能力，删 `data[17]` 得先线性找到它，
   再把它和末尾交换、然后既可能上浮又可能下沉 —— 整体 O(n)。
   工程上叫"需要索引堆（indexed heap）或延迟删除"，Dijkstra 用堆时就是靠"允许堆里有陈旧条目"绕开这一点。

8. **最小堆 / 最大堆记反了默认值**。C++ `priority_queue` 默认**最大堆**，Python `heapq` 默认最小堆。
   不要背，写完第一件事是 `push 三个数看一眼 pop 出来的是最大还是最小`。

9. **数组满了没扩容，或者 `realloc` 的返回值没接**。
   `realloc(h->data, ...)` 可能把内存搬到别处；写 `h->data = realloc(...)` 才安全，
   直接丢弃返回值 = 一旦搬家就悬空/泄漏（见 `heap_grow`）。

10. **拿堆当"第 K 小查询"用**。堆里查第 K 小只能 pop K 次（O(K log n)），
    想 O(log n) 查第 K 小得用平衡 BST（带 size 域）或树状数组 —— 见 `11-searching/kth-smallest`。

## 什么时候用它 / 什么时候别用

**该用堆：**
- 反复"取最值"，而且中间不断插入/删除：任务调度、事件模拟、合并 K 个有序序列。
- **Top-K / 第 K 大**（本项目 `06-heap/top-k`）：大小为 K 的小顶堆，O(n log K) 时间 + O(K) 空间。
- 图算法：Dijkstra（优先队列版）、Prim 最小生成树（见 `07-graph/*`）。
- 堆排序：原地、O(n log n) 时间、O(1) 额外空间，且**最坏情况也是 O(n log n)**（快排最坏会退化）。
- 数据流的中位数 / 分位数：对顶堆（一个大顶堆 + 一个小顶堆）。
- 你只在乎"谁最突出"，不在乎其余人的顺序 —— 这正是堆的设计初衷。

**不该用堆：**
- 要按值查找 / 判断存在性 → 哈希表（`08-hash/*`）或 BST。
- 要整体有序 / 要按序遍历 → 排序一次（`10-sorting/*`）或有序结构（BST、跳表）。
- 频繁删除任意位置的元素 → BST / 哈希 + 链表。
- 要区间和、前缀和、第 K 小这类"带查询的聚合" → 树状数组 / 线段树（`09-others/*`）。
- 数据量很小（比如 n < 20）且逻辑简单 → 直接线性扫或插排，代码量小一半，常数也更低。
- 要求**稳定**（相等元素保持先来后到）→ 堆天生不稳定，需要额外加序号字段（见 `06-heap/priority-queue` 那一幕）。

## 自检问题

1. **一个合法的最小堆数组是 `[1 3 2 5 4 9 8]`。`data[1]` 和 `data[2]` 谁大？这算 bug 吗？**
   **答：** `data[1]=3 > data[2]=2`，完全正常，不是 bug。它们都是 `data[0]=1` 的孩子，
   是兄弟关系；堆序性只管"父亲 <= 孩子"，从不规定兄弟之间的大小。
   这条也正好解释了"堆不是排序"。

2. **`heap_pop` 为什么必须和**最后一个**元素交换？和 `data[3]` 交换行不行？和"直接删堆顶后前移"呢？**
   **答：** 和 `data[3]` 交换后，下标 3 变成一个洞，数组下标不再连续，`data[4]` 是谁的孩子就说不清了
   —— 结构性被破坏，父子公式当场失效。
   "直接删堆顶后整体前移"结构上其实没坏，但每次 pop 要搬 n-1 个元素 = O(n)，n 次 pop 退化成 O(n²)。
   只有末尾元素是叶子，搬走它不影响任何节点的父子映射，而且只需要 1 次交换。

3. **自底向上 heapify 为什么是 O(n)，不是 O(n log n)？**
   **答：** 因为下沉距离的分布严重倾斜：一半节点是叶子（0 步），四分之一最多 1 步，八分之一最多 2 步……
   总功 `n × (0/2 + 1/4 + 2/8 + …) = O(n)`。直观说法：金字塔最底下几层砖头最多，但它们离地面最近。
   本仓库实测：n 从 1000 翻到 8000（8 倍），heapify 比较次数从 1982 涨到 15976，正好 8 倍；
   而逐个 push 同期涨到 11 倍 —— 那个多出来的 1.x 倍就是 `log n`。

4. **`heap_push` 用 O(log n)，`heap_build` 用 O(n)。手里已经有一整批数据，该怎么建堆？什么时候只能 push？**
   **答：** 一整批都在手上就用 `heap_build`（heapify），省掉一个 log 因子。
   数据是源源不断流进来的（在线场景，比如实时日志里维护"当前最热的话题"）只能逐个 push。
   这也是为什么"n 个元素 push 完再 pop 完"是 O(n log n) 的堆排序，而"heapify 再 pop 完"也是 O(n log n)
   —— 排序那一步的 log 是 pop 提供的，不是插入提供的。

5. **把最小堆改成最大堆，要动几行代码？C++ 的 `std::priority_queue` 默认是哪一个？**
   **答：** 本实现里**0 行**逻辑代码要改 —— 只有 `better_than()` 里比较号的那一句，
   由 `h->kind` 决定，其余（上浮/下沉/建堆/pop）完全不动。
   `std::priority_queue` 默认是**最大堆**（Python `heapq`、Java `PriorityQueue` 默认最小堆）。
   这是纯历史决定、背不住的，写完先跑一行验证。
