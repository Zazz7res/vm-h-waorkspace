# 开放寻址哈希表（线性探测 + 墓碑）hash-table-open-addressing

> 这一节和隔壁 `hash-table-chaining/` 是**同一件事的两种做法**：`put / get / delete`
> 三个动作一个都不少，键值对也一模一样是 `int → int`。改的只有一件事 ——
> **冲突的元素不再挂链，而是直接躺进桶数组的下一个格子。**
> 就这一改，删除从"摘个节点"变成了本节唯一真正的技术决定。

---

## 一句话是什么

**把所有元素塞进一个连续的槽数组里**：`h(key) % capacity` 算出首选格子，
撞了就 `+1、+1、+1` 往后找第一个空位（这就是**线性探测**）；
删除时那一格不能清空，只能立一块**墓碑**（tombstone），
因为"空槽"是查找唯一的停止信号。

对照记忆：

```
拉链法   = 数组 + 链。数组只放指针，元素在堆上散落。冲突「竖直」长（链变长）。
开放寻址 = 只有一个数组。元素本体躺在格子里。冲突「水平」摊（往后挪一格）。
```

---

## 为什么需要它

1. **少一堆 malloc，也少一堆指针。** 拉链法每插一个元素就 `malloc` 一个节点，
   节点里还必须自带一个 `next` 指针（8 字节，纯粹为了"挂链"）。
   开放寻址整张表只有**两次分配**（结构体 1 次 + 数组 1 次），
   第 1 幕末尾把这笔账打印了出来：5 个键，开放寻址 2 次分配，拉链法 7 次。

2. **缓存友好 —— 这是它真正的立身之本。** 查找沿着 `idx, idx+1, idx+2` 走，
   这些格子在内存里就是**相邻的字节**，一条 64 字节的缓存线能装下 5 格
   （`sizeof(Slot) = 12`）。硬件预取器顺手把后面几格一起搬进 L1。
   拉链法每比一个节点就是**一次随机跳转**到堆上散落的地址。
   第 7 幕把"探测格数"换算成了"缓存线条数"，数字在那儿。

3. **它是真实世界多数哈希表的写法。** Python 的 `dict`、Java 的 `HashMap`（JDK 8 之后
   桶内退化为红黑树但桶间仍是数组）、Rust 标准库 `HashMap`（SwissTable）、
   Go 的 `map`、LevelDB / RocksDB 的 block index —— 主流实现几乎都走开放寻址
   或它的变体（Robin Hood / SwissTable），原因就是上面两条：分配少、局部性好。

4. **代价必须先知道**：格子会**互相拖累**（primary clustering），
   所以装载率上限必须比拉链法保守得多（本节用 **0.5**，拉链法用 **0.75**），
   而且删除必须付"墓碑"这笔债。这一节 90% 的篇幅在处理这两件事。

## 图解

### 1. 全部家当就是一个格子数组

`capacity=8`，三个键 12 / 20 / 28，`h(key) = key`（故意用最傻的哈希，
这样**每个格号你都能手算**，跑完再对答案）。三个键的 home 全是 `4`：

```
拉链法（隔壁那一节）：数组只放指针，元素在堆上
   buckets[8]
   ┌────┬────┬────┬────┬─────┬────┬────┬────┐
 0 │ ∅  │ ∅  │ ∅  │ ∅  │  ●  │ ∅  │ ∅  │ ∅  │
   └────┴────┴────┴────┴──┬──┴────┴────┴────┘
                          └─►[28]─►[20]─►[12]─►NULL     ← 3 次 malloc，地址互不相邻

开放寻址（本节）：就一个数组，元素本体住在里面
   slots[8]
   ┌────┬────┬────┬────┬─────────┬─────────┬─────────┬────┐
   │  0 │  1 │  2 │  3 │    4    │    5    │    6    │  7 │
   ├────┼────┼────┼────┼─────────┼─────────┼─────────┼────┤
   │ ·  │ ·  │ ·  │ ·  │ U 12=120│ U 20=200│ U 28=280│ ·  │
   └────┴────┴────┴────┴─────────┴─────────┴─────────┴────┘
     EMPTY 全是 EMPTY          ▲ 首个空位接住第二个   ▲ 再接第三个
   home(12)=12%8=4 撞槽4 → 落 5；home(20)=4 撞槽4、5 → 落 6；home(28)=4 → 落 7
```

程序里这张表长什么样，第 1 幕原样打印过（`·` 空槽、`†` 墓碑、`U key=value` 占用）。

### 2. 冲突是"水平摊开"，不是"竖直挂链"

```
                槽 4        槽 5        槽 6        槽 7        槽 0
home 都是 4  →  U 12        U 20        U 28        U 4         ·
                ▲           ▲           ▲
                └─ 12 住家里 └─ 20 让一格 └─ 28 让两格

   拉链法在这里：buckets[4] ─►[28]─►[20]─►[12]─►NULL   （桶 5/6/7 仍然空着）
   开放寻址在这里：数组不会"装满"，只会"不好插" —— 格子被连成一串
```

⚠ 注意最后一格：如果串顶到了数组尾巴，`idx+1` 会**折回 0**（环形数组）。
第 2 幕里键 53 就住在槽 0，它的探测路径是 `5 → 6 → 7 → 0`。

### 3. 一次查找经过哪些格子（探测序列 = "开放寻址"这四个字的实体）

这是本节最重要的一张图。查找**只有两种停法**：

```
get(45)：home = 5
  槽 5        槽 6        槽 7
  U 29   ──►  U 37   ──►  U 45
  29≠45       37≠45       45=45 ★停！命中
  不停        不停                      → 3 步

get(61)：home 也是 5，但这个键从来没插过
  槽 5        槽 6        槽 7        槽 0        槽 1
  U 29   ──►  U 37   ──►  U 45   ──►  U 53   ──►  EMPTY
  不停        不停        不停        不停        ★停！判定【不存在】 → 5 步

  唯一的「没有」证据 = 撞到一个真·空槽 EMPTY。
  「USED 但键不对」不停，「墓碑」也不停。
```

为什么要绕到槽 0 才敢说没有？因为 53 自己就是这么找到的位置：
`5 → 6 → 7 → 0`。查找如果只看槽 5 就说"没有"，那 53 也永远找不出来。

### 4. 删除：EMPTY 会剪断链，墓碑不会（本节唯一真正的技术决定）

删掉住在**槽 4** 的 12。要命的地方在于：20 和 28 的 home **也是 4**，
它们俩的探测路径**都要路过槽 4**。

```
删除前                  ✅ 写成墓碑 TOMB            ❌ 写成 EMPTY
槽4  U 12               槽4  †   （挡路但不存数据）   槽4  ·   ←「这里从来没东西」
槽5  U 20               槽5  U 20                     槽5  U 20   （数据一分没少！）
槽6  U 28               槽6  U 28                     槽6  U 28

get(20)：               槽4(†→继续) → 槽5(命中)  ✅     槽4(·EMPTY→停) → 「不存在」 ❌
get(28)：               槽4(†→继续) → 槽5 → 槽6  ✅     槽4(·EMPTY→停) → 「不存在」 ❌
                        装载率 used/cap 没降（0.375）    装载率还变好看了（0.250）← 最阴的地方
```

**❌ 那一列不崩溃、不报错、内存也不越界，只是"数据还在数组里、程序却说没有"。**
`--bug` 开关会把它真的跑出来（见运行结果第 3 幕那段），三个连锁事故一起看。

墓碑的代价也在这儿写着：它不存数据，**但它照样挡路** —— 所以装载率的分子必须含墓碑。

### 5. 两本账：`used = size + tombs`

```
             槽 4     槽 5     槽 6     槽 7
插 12/20/28   U        U        U        ·        size=3 tombs=0 used=3  α=0.375
删掉 12       †        U        U        ·        size=2 tombs=1 used=3  α=0.375 ← 没降！
put(4) 回收   U        U        U        ·        size=3 tombs=0 used=3  α=0.375 ← 也没涨

被删掉的那一格：真元素少一个（size--），挡路的格子一个没少（used 不变）
→ 「删了东西，装载率却没下降」不是记账洁癖，是它【真的】还在拖慢查找。
→ 分子写成 size 会得到 α=0.250，程序以为表很空，于是再也不搬家，步数一路涨。
```

### 6. 一格 12 字节，一条缓存线 5 格

```
Slot = { int key; int value; int state; } = 4+4+4 = 12 字节（无指针、无 padding）
一条缓存线 = 64 字节 → 装 5 整格（5 × 12 = 60），剩下 4 字节凑不满第 6 格

  line 0 │ slot0 │ slot1 │ slot2 │ slot3 │ slot4 │ 5a  │
         │ 12 B  │ 12 B  │ 12 B  │ 12 B  │ 12 B  │ 4 B │   ← 合计正好 64 字节
  line 1 │ 5b  │ slot6 │ slot7 │ slot8 │ slot9 │ slot10│
         │ 8 B │ 12 B  │ 12 B  │ 12 B  │ 12 B  │ 12 B  │   ← slot5 被线切成两半

       ◄── 探测 0→1→2→3→4：五格全在同一条线里，1 次访存，硬件预取还白送 ──►
       ◄── 换算「格数 ÷ 5」因此只是下界：起点很少正好落在线首，头尾各多算一条
           （第 7 幕实测 64.50 格 ÷ 5 ≈ 12.90 条，真实数字 13.30 条）──►

对比拉链法：比一个节点 = 先读 next 指针 = 跳到堆上某个不相邻的地址 = 换一条线
```

### 7. primary clustering：串会被**别人**加长

```
step=1（顺序插 512 个键，capacity=1024）      step=33（互质铺开 512 个键，同样 capacity）
▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░...▒          ▓░▓░▓░▓░▓░▓░▓░▓░▓░▓░▓░▓░...
└──── 一条 512 格的长串 ────┘                 摊成 32 段，最长 17 格

新键落进串里 → 串自动延长一格 → 下一个路过这里的键更慢 → 越聚越大
实测（第 8 幕）：失败查找平均 257.50 格 vs 9.77 格 —— 差 26.4 倍，
                 而装载率两边都是 0.500、键数都是 512，只有分布不同。
```

这就是"线性探测慢"的真正原因：**不是因为格子分散在内存里**（那是第 7 幕的维度），
**是因为串会被别人加长**。治它的路子是换探测序列（`+1` → `+i²` 或 `+h2(key)`），
不是换数组。

## 逐操作拆解

### 1. `oa_create(capacity)` —— 建表（oa.c:106）

```
 malloc(OATable)                        → 40 字节：数组指针 + 5 个计数器 + del_mode
 calloc(capacity, sizeof(Slot))         → capacity 格 × 12 字节，全 0 位模式
```

- **为什么 `calloc`**：`oa.h` 里定死了 `SLOT_EMPTY = 0`。全 0 位模式天然就是"每格 EMPTY"，
  一步消灭"漏初始化某格 → state 是垃圾值 → 被当成 USED"这类 bug。那种 bug 的症状是
  "偶尔查不到明明存过的键"，最难查。
- **两处分配就要两处回滚**：数组申请失败时先 `free(t)` 再返回 `NULL`。
- **capacity 不必是 2 的幂**：代码用 `% capacity` 而不是 `& (capacity-1)`。
  本节全程用 2 的幂，只是为了让"翻倍后 home 怎么变"那条规律好算好核对（第 6 幕）。

### 2. 探测引擎 `oa_probe_core()` —— 全文件唯一的一份规则（oa.c:177，`static`）

`get / contains / delete / put / probe_path` **共用**这一个函数。为什么只许有一份：
规则一旦抄成第二份，两份就会开始各说各话（`put` 忘了墓碑能回收、`delete` 多认一次 EMPTY
就少删一个键）。差异全部用**可选输出参数**表达，传 `NULL` 就是不要那个信息：

```c
for (steps = 0; steps < cap; steps++) {        /* ★ 一圈最多 cap 步，绝不越界 */
    if (s->state == SLOT_EMPTY)  { *slot_out = idx; return steps + 1; }  /* 唯一合法判负 */
    if (s->state == SLOT_USED && s->key == key) { *found_out = 1; ... return steps + 1; }
    /* SLOT_TOMB：只记【第一个】墓碑 —— 越靠前离 home 越近，回收它最划算 */
    idx = oa_next_idx(idx, cap);               /* +1，到尾巴折回 0 */
}
return cap;   /* 绕一整圈没撞到 EMPTY：表里没有空格，让调用方自己决定搬家 */
```

三个易错点：
1. 循环上界是 `capacity`，不是"直到找到"。表满时后者会**无限循环**。
2. 步数 `return steps + 1`：撞到的那个 EMPTY **也要算一步**，我们确实看了它。
3. `oa_next_idx` 写"加法 + 判断"而不是 `(idx+1) % capacity`：`%` 是除法指令，
   探测循环里每步一次，值得省掉；顺便把"环形"这件事集中到一处。

### 3. `oa_get` / `oa_contains`（oa.c:254 / oa.c:272）

```c
int steps = oa_probe_core(t, key, NULL, 0, &found, &slot, NULL);
t->probes += steps;                    /* ★ 计的是真正走过的格数，别自己瞎写 +1 */
```

- `oa_contains` 就是 `oa_get(t, key, NULL)`：值不要，只要"在不在"。
- **为什么 `oa_get` 不是 `const`** 而 `oa_probe_path` 是：看探测序列是**观测**，
  看别人的表不该改别人；"这张表累计探测多少格"是**使用**行为，只有真在用的
  get/put/delete 才该记账。两个职责分成两个函数，`main.c` 就能既打印又统计、互不污染。
- `value_out` 传 `NULL` 表示只判存；**返回值 1/0 表示成不成**，值走输出参数
  （0 是合法的 `int` 值，不能当哨兵 —— 和第 08 章拉链法那条坑同源）。

### 4. `oa_probe_path`（oa.c:240）—— 把探测序列抄出来给打印用

`oa.h` 专门解释了为什么要把它单独拆出来：**数据与呈现分开**。
`oa_probe_path` 只负责"经过哪些下标 + 在不在"，把数组交给调用方；
`oa_print_probe_path`（oa.c:593）负责翻译成"槽 4(† 墓碑→不停，继续) → 槽 5(U 命中→停)"。
这样以后加二次探测 / 双重哈希时，**只需要换打印，不用换逻辑**。

### 5. `oa_delete`（oa.c:298）—— 本节唯一真正的技术决定

```c
if (t->del_mode == OA_DEL_ZERO) {              /* ❌ 只在 --bug 下打开 */
    s->state = SLOT_EMPTY; s->key = 0; s->value = 0;
} else {                                       /* ✅ 默认 */
    s->state = SLOT_TOMB; t->tombs++;
}
t->size--;
t->used = t->size + t->tombs;                  /* ★ used 是【派生值】，改完立刻重算 */
```

- 默认**必须是墓碑**。`OA_DEL_ZERO` 挂在 `del_mode` 字段上，只有命令行 `--bug` 才打开。
- `EMPTY` 那一路连 `key/value` 都清零 —— 这是故意的，它让"数据明明还在那儿"这件事
  从打印里也看不出来，这才是真实世界这类 bug 最难查的地方。
- 墓碑那一格**故意留着旧 key/value**：墓碑不需要身份，留着方便你盯着数组看历史。
  真实实现会清掉（键若是指针，留着就是悬空引用）；本节键是 `int`，留着无害。
- ⚠ 线性探测下删除**只能原地写状态**，绝不能"把后面的元素往前挪一格"。
  拉链法可以顺手重排链内顺序（桶内顺序无所谓），线性探测不行：要挪槽 5 的键到槽 4，
  必须先确认它的 home 就是 4；不满足就得连锁往后挪，一路传到那个 EMPTY 为止 ——
  那是 Robin Hood 表干的事。
- 删除**幂等**：本来就没有的键，`probe_core` 报 `found=0`，直接 `return 0`，
  绝不会二次修改状态（否则 `tombs` 会凭空涨）。

### 6. `oa_put`（oa.c:346）—— 回收墓碑 + 两本账 + 搬家决策

比拉链法的 `put` 多出三个开放寻址特有的难点，全在这个循环里：

```
(1) 探测 → found ? 覆盖 value、size 不动、return          ← 漏了会把表撑爆
(2) target = (路上有墓碑) ? 第一个墓碑 : 撞到的 EMPTY
(3) 只有【target 是 EMPTY】才增加 used → 才检查阈值 (used+1)*2 > capacity
       有墓碑且真元素塞得下 → [整理] 同容量重排，蒸发墓碑
       否则                  → [扩容] 翻倍
       两个分支之后都 continue —— ★ 搬家后 home、墓碑位、空槽位全部作废，从头重跑
(4) 落子：TOMB→USED 则 tombs--；size++；used = size + tombs 立刻重算
```

三个"只有在这儿才成立"的点：
- **为什么回收墓碑不用看装载率，占新空槽才要看**：回收是 `† → USED`，
  挡路格子数守恒 → `used` 不变；占空槽是 `EMPTY → USED` → `used + 1`。
  这一条区别就是"分子是 used 而不是 size"最直接的用处。
- **为什么用整数乘法** `(used+1)*2 > cap` 而不是 `> 0.5`：`double` 有舍入，
  "恰好一半"这种边界值今天相等、明天换个 capacity 就判错。
  而且是**严格大于**，所以装载率能升到正好 `0.500`（第 1 幕让你亲眼看到 4/8 = 0.500）。
- **`target < 0` 那条 `[兜底]`**：既没墓碑也没空槽（`used == capacity`），
  0.5 阈值下正常走不到这里，但**绝不留死循环** —— 强制翻倍。
  写死它是"最坏情况也要有一条出路"，而不是给三个月后的自己留一个静默卡死的现场。

### 7. `oa_rehash(t, new_capacity)`（oa.c:722）—— 扩容 vs 同容量重排

```
把 old 数组里【state == USED】的格，按【新 capacity】算 home、在新数组里探测到空位、复制本体
→ 释放旧数组 → 返回搬走的元素数（= 被重放的 USED 格子数）
```

- **只重放 USED**，`SLOT_TOMB` 被留在旧数组里，`free` 那一刻**彻底蒸发**（`tombs` 归 0）。
  这就是"同容量重排"那招的实现：`oa_rehash(t, t->capacity)`，格子数不变，
  只把墓碑清干净 —— 开放寻址特有的招式，拉链法没有"挡路"这回事，用不着。
- ⚠ 同容量重排**也会新分配一个数组**（`calloc` 一块新的、再 `free` 旧的），
  所以搬家瞬间内存峰值是 2 倍。真实库会原地清扫，本节选"新建 + 复制"是因为它
  绝不可能把某个键留在原地没重算 —— 简单比省内存重要。
- **失败就维持原样**：新数组 `calloc` 失败时打印 `[错误]` 并原样返回 0，
  装载率高一点只是**慢**，不是**错**（"宁可慢也不要崩"，Redis 增量 rehash 同动机）。
- **搬家必须用新 capacity 重算 home**（旧 home 一律作废）。
  忘了重算或者只搬一半 → 和拉链法那条"rehash 后忘记重算下标"一模一样：静默丢数据。
  第 6 幕用它做摊还统计：4+8+16+32 = 60 次复制 ÷ 64 次插入 ≈ 0.94 次/插入。

### 8. `oa_rehash_plan(t, new_capacity)`（oa.c:789）—— 搬家前先看一眼

打印每个键的「旧槽号 / 旧 home / 新 home / `h ÷ 旧capacity` 的商 q / q 的奇偶 /
按规律推出来的新 home / 是否吻合」。规律：capacity 翻倍时，
`key = q·C + r`，`q` 偶 → 新 home 还是 `r`，`q` 奇 → 新 home 变成 `r + C`
（一个旧桶最多裂成两个新桶，Redis 增量 rehash 就靠它）。

⚠ 这里打印的是 **home，不是真实落点**。真搬家时同一个 home 的元素要互相让位往后挪
（第 6 幕实测：预测 4 个 home 全对，实际落点 2 个被同 home 的键挤走）。
**落点是"全表占用状态"的函数，不是"键"的函数。**

### 9. 打印三件套：`oa_print`（oa.c:555）/ `oa_print_probe_path`（oa.c:593）/ `oa_stats`（oa.c:638）

- `oa_print`：每行 8 格，格子内容 `·` / `†` / `U key=value`，超过 24 格只画前 24 格并

### 12. `oa_free(t)`（oa.c:142）

两级释放，**顺序固定**：`free(t->slots)` → 把 `t->slots` 置 `NULL`（防止有人接着遍历
这张已拆的表）→ `free(t)`。
整张表就这两块内存，没有第三种分配 —— 这正是开放寻址的优点之一，
也意味着 `free` 的责任比拉链法**少一层**（那边还得逐个节点 `free(node->key)` 之类）。
`main.c` 每一幕结尾都自己 free 自己那张表，ASan 在退出时来查岗。

## 复杂度

`n` = 元素数，`m` = capacity，`α = used / m`（含墓碑！）。

| 操作 | 平均（摊还） | 最坏 | 为什么 |
|---|---|---|---|
| `oa_put` 插入 | O(1) | O(m) | 要走完"路过的那串"；摊还靠翻倍扩容（第 6 幕：60 次复制 ÷ 64 次插入 ≈ 0.94） |
| `oa_get` / `oa_contains` 命中 | O(½(1+1/(1−α))) | O(m) | α=0.5 → 1.5 格；α=0.9 → 5.5 格；α=0.95 → 10.5 格 |
| `oa_get` 不命中 | O(½(1+1/(1−α)²)) | O(m) | **必须一路走到串尾后面的 EMPTY**。α=0.5 → 2.5 格；α=0.9 → 50.5 格 |
| `oa_delete` | O(½(1+1/(1−α))) | O(m) | 一次查找 + 写一个 `state`，本身 O(1) |
| `oa_rehash` | — | O(m) | 每次搬家全表重扫；摊到 n 次操作上是 O(1) |
| 空间 | O(m) | — | `m×12` 字节，一次 calloc。α 上限 0.5 ⇒ 至少准备 2n 格 |

**"期望 O(1)"的前提是 α 被按住。** 线性探测的曲线不是"慢慢变陡"，是**墙**：
α 从 0.100 → 0.500，不命中查找实测 1.11 → 2.60 格（第 8 幕表格）；
公式再往外推，0.75 → 8.5 格，0.90 → 50.5 格。
这就是阈值取 0.5 而拉链法取 0.75 的全部原因：

```
拉链法看「平均链长 = α」：α=0.75 → 平均比 1.375 个节点，很温和；
        桶不够时链还能继续长（α 可以 > 1），表永远不会「无路可走」。
开放寻址看「连跑长度」：挡路格子连成一片，新键落进串里就把串延长一格，
        于是所有路过这里的键【一起】变长；α=1 时连 EMPTY 都没有，
        查找连【停止条件】都失去意义。
```

顺带两条：`α` 用 `used`（不是 `size`）才算得上"挡路程度"；
`Knuth` 那两条公式的前提是**简单均匀哈希**，线性探测实际会**略高于**它们
（第 8 幕实测 2.60 vs 理论 2.50，差的就是聚集税，不是 bug）。

### 第 7 幕：把"探测格数"换算成"缓存线条数"

```text
  一格 = 12 字节（三个 int：key 4 + value 4 + state 4，没有指针，没有 padding）
  一条缓存线 = 64 字节 → 装 5 格（还余 4 字节，凑不满第 6 格）
  线性探测的下一步是 idx+1 → 连续几格往往就在同一条线上，
  硬件预取器顺手把后面几格一起搬进 L1，等于免费。

  批 1【塌缩：一条 128 长的串】灌 128 个键（键 = 0, 1024, 2048, …）：
  格子数组 capacity=1024 │ USED=128 │ 墓碑=0 │ 空槽=896
  used = size + tombs = 128 + 0 = 128
  装载率 used/capacity = 0.125  ← 触发搬家的判据（本节阈值 0.5）
  真实密度 size/capacity = 0.125  ← 两个数的差 0.000 就是白白挡路的墓碑
  挡路区间（连跑）1 段，最长 128 格 ← primary clustering 的度量
  把现存 128 个键逐个查一遍：平均 64.50 步，最长 128 步
  累计探测格数 t->probes = 8256（put/get/contains/delete 都往里加）
  形态：▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ …（只画前 64 格）  （▓=占用 ▒=墓碑 ░=空）
  批 1【塌缩：一条 128 长的串】实测：平均探测 64.50 格（最长 128 格），平均踩 13.30 条缓存线
  批 2【铺开：一人一格】实测：平均探测 1.00 格（最长 1 格），平均踩 1.00 条缓存线

  换算的算术：64.50 格 ÷ 每线 5 格 ≈ 12.90 条，实测 13.30 条略高一点 ——
  因为探测的起点很少正好落在一条线的开头，头尾各多算一条。

  同一批键、同一种分布，放进拉链法要踩几条线（比较次数按头插规则精确算，
  见 chain_avg_comparisons 的注释；⚠ 那是【模型复算】，不是那边代码的实测）：
    批 1：128 个键摊进 1 个桶 → 平均比较 64.50 个节点；节点各一次 malloc、地址不相邻 →
      模型：桶数组 1 条线 + 每比一次 1 条线 = 平均 65.50 条线（开放寻址同批 13.30 条，差 4.9 倍）
    批 2：128 个键摊进 1024 个桶 → 平均比较 1.00 个节点；节点各一次 malloc、地址不相邻 →
      模型：桶数组 1 条线 + 每比一次 1 条线 = 平均 2.00 条线（开放寻址同批 1.00 条，差 2.0 倍）

  并排看（【访问次数两边几乎一样，差的是每次访问要不要换线】）：
    批次                  方案            平均访问次数    平均缓存线    线差    
    ------------------------------------------------------------------
    塌缩：一条 128 长的串 开放寻址        64.50           13.30         -       
                          拉链法(模型)    64.50           65.50         4.9x    
    铺开：一人一格        开放寻址        1.00            1.00          -       
                          拉链法(模型)    1.00            2.00          2.0x    

  内存账也顺便看一眼（两批用的都是 capacity=1024，一张表就是一个数组）：
    开放寻址：一格 12 字节，全是有效数据；整张表 1024 格 = 12288 字节，一次 calloc。
    拉链法：节点 = int key + int value + 指针 next = 16 字节，其中 8 字节纯粹是为了「挂链」；
           外加堆管理器给每次 malloc 记的账（glibc 最少 8 字节头 + 16 字节对齐），
           128 个元素就是 128 次 malloc。
    元素紧凑 = 缓存和分配器两头都省，这是开放寻址的立身之本。

  ⚠ 诚实边界（这三条别忘）：
    1) 「平均 13.30 条线」是【格号 → 缓存线】的算术换算，不是 perf 的 L1 miss 计数器
       实测。要量真未命中得用 `perf stat -e L1-dcache-load-misses` 或 valgrind --tool=cachegrind。
    2) 拉链法的「一跳一线」是最坏假设：刚 malloc 出来的相邻节点地址常常很近，
       实际差距会比 4.9x 小 —— 但方向不会反过来，而且表跑久了（堆碎片化）就回到这个量级。
    3) 批 1 是【最坏聚集】那一头：平均 64.50 格里只有 1 格真是你要的，
       其余 63.50 格读的都是别人的键 —— 「连续探测」在这里就变成
       「一整条线全读完、一个都不是」。它仍然赢在换线少，
       可这赢面是「数组连续」给的，不是「步数少」给的（第 8 幕量步数）。
```

```text
  装载率与探测步数的关系（capacity=1024；键 = 随机 home + 同 home 时加 capacity 的倍数，

  ⚠ 两个诚实的补充：
    1) 本演示的表最多只跑到 α=0.500 —— 一旦越线程序就搬家了，所以 0.75/0.90 那几档
       只能看公式。这恰好就是答案本身：开放寻址【不该】让 α 到 0.75。
    2) 最后一档失败实测 2.60 格、理论 2.50 格，实测【高于】理论 —— 不是 bug：
       那条公式的前提是「简单均匀哈希」（每次探测换个全新位置），而线性探测会聚集，
       本档实测最长连跑 19 格（512 个键抢 1024 个 home，串与串会互相并起来）。
       所以正确的读法是：公式给出【下限形状】，线性探测在它上面再加一层聚集税；
       α=0.400 那档实测 1.80 vs 理论 1.89 差得小，是因为那时候串还短、税还轻。
```

### 第 9 幕：把这一节的形状总结成一张图

```text
  同样存 12、20、28 三个键（capacity=8，home 全是 4）：

  拉链法：桶数组里【只放指针】，元素住在堆上散落的节点里
    ┌────┬────┬────┬────┬────┬────┬────┬────┐
    │    │    │    │    │  ▲ │    │    │    │
    └────┴────┴────┴────┴──┬─┴────┴────┴────┘
                            └─►[28]─►[20]─►[12]─►NULL
      3 次 malloc、3 个互不相邻的地址；删除 = 摘节点，干净利落

  开放寻址：【就一个数组】，元素本体躺在格子里
    ┌────┬────┬────┬────┬──────────┬──────────┬──────────┬────┐
    │  0 │  1 │  2 │  3 │    4     │    5     │    6     │  7 │
    ├────┼────┼────┼────┼──────────┼──────────┼──────────┼────┤
    │ ·  │ ·  │ ·  │ ·  │ U 12=120 │ U 20=200 │ U 28=280 │ ·  │
    └────┴────┴────┴────┴──────────┴──────────┴──────────┴────┘
      1 次 calloc；冲突水平摊开；删除必须留 †，否则剪断后面那些键的路

  删掉 12 之后两张表各自长什么样 —— 这就是两节的全部差别：

    拉链法   buckets[4] ─►[28]─►[20]─►NULL   ← 20 还在原位，一跳就到，摘掉节点就完事
    开放寻址 槽4=† 槽5=U 20 槽6=U 28          ← 20 还在原位，但找它【必须能跨过 †】

  三个必须带走的结论：
    1) EMPTY 是查找唯一的「停止标志」。删除写成 EMPTY = 剪断别人的探测链，
       症状是「数据还在、程序说没有」，不崩不报错。所以默认必须是墓碑。
    2) 装载率的分子是 used = USED + 墓碑，不是 size —— 墓碑挡路，所以它贵。
       于是阈值比拉链法保守（0.5 vs 0.75），并且多一招「同容量重排蒸发墓碑」。
    3) 元素在数组里 = 缓存友好 + 只分配两次；代价是冲突会传染（primary clustering），
       α 一高步数就沿 ½(1+1/(1-α)) 起飞。想要不聚集得换探测策略：
       二次探测 / 双重哈希把「+1」换成「+i²」或「+h2(key)」，聚集小得多，
       但删除的墓碑问题一模一样 —— 墓碑是开放寻址的债，不是线性探测的债。
  本幕不建表（纯图）。前八幕的表都在各自幕结尾 free 掉了，ASan 会来核对。

记住三句话：
  1) 只有【真·空槽 EMPTY】能让查找判负；USED 不匹配和墓碑都必须继续走。
  2) 删除写墓碑，装载率分子含墓碑；墓碑躲在路径外不肯消失时，做一次同容量重排。
  3) 元素在数组里 → 缓存友好、只分配两次；但冲突会传染，所以阈值只能到 0.5。
```

## 常见的坑

1. **删除把格子清成 EMPTY —— 剪断别人的探测链。**
   症状最毒：不崩溃、不报错、内存不越界，只是"数据还在数组里、程序说没有"。
   而且 `size` 和 `used` 双双减了，装载率还挺好看，没有任何警报。
   `--bug` 现场里连后续都演了一遍：你以为丢了于是重新 `put(20,999)` →
   表里出现**两个键 20**，槽 5 那个 200 成了永远读不到的幽灵；再 `delete(20)`
   只干掉路径上第一个，幽灵又冒出来。**修法：默认墓碑。**

2. **查找在墓碑处停下 —— 把墓碑当"空"。**
   `†` 既不是命中也不是空槽，**不许停**。只有 `SLOT_EMPTY` 能让查找判负。
   写成 `if (state != SLOT_USED) return 0;` 就等于把坑 1 又挖回来了，
   而且这次连"数据还在"都查不出来（因为你的查找提前退出了）。

3. **装载率的分子写成 `size`。**
   第 5 幕实测：8 块墓碑、`size = 0`，`size/capacity = 0.000` —— 程序以为表空着，
   再也不搬家；而查一个不存在的键实际要走 **9 格**。分子必须是 `used = size + tombs`。

4. **`key % capacity` 裸用，不管负数。**
   C 的 `%` 是截断除法的余数，符号跟被除数：`-1 % 8` 是 `-1`，拿去当格号就是
   `slots[-1]` —— 堆越界读写，编译器一声不吭，ASan 立刻打死。
   修法**只许**同余平移 `r += m`，**不许** `abs()`：`-3` 和 `3` 在模 8 下是不同的格子
   （`-3 ≡ 5`），取绝对值会让同一个键两次算出两个 home，探测链当场乱掉。

5. **插入路径上没记住墓碑，或者记住了却不用。**
   `put` 探测时要记**第一个**墓碑（越靠前离 home 越近）。不用的话墓碑只增不减，
   装载率一路涨到被迫搬家；用得太狠（比如"看见墓碑就落"）也不对 ——
   必须先确认键真的不存在，否则你会把已存在的键写成两个。
   第 5 幕 A 展示的另一半：**回收并不彻底**，躲在探测路径之外的墓碑谁也碰不到，
   所以要留"同容量重排"这一招。

6. **搬家后继续用旧的 home / 旧的落点结论。**
   `capacity` 一变，home、墓碑位置、空槽位置**全部作废**。`oa_put` 的做法是
   重排之后 `continue`，从头再探测一遍。留着旧结论 = 元素进错格子 = 静默丢数据。

7. **探测循环没有上界。**
   写 `while (1) { ... }` 靠"总能撞到 EMPTY"退出 —— 表一旦真填满（或外部把
   `used` 改坏）就是**死循环**，而且是在生产环境、压测里、或者某个凌晨。
   `for (steps = 0; steps < cap; steps++)` + 一圈后返回 `cap` 才叫有出路。

8. **拿 `0` 当"查不到"的哨兵。**
   接口必须是"返回值表成败、值走输出参数"（`oa_get(t, key, int *value_out)`）。
   0 是合法的 `int` 值，混用就会把"存过 0"读成"没存过"。

9. **以为线性探测 = 恒定 O(1)。**
   第 8 幕：同样 512 个键、同样 α=0.500，只是分布不同，
   失败查找平均 **257.50 格 vs 9.77 格**（差 26.4 倍）。
   聚集是线性探测的结构性问题，不是"运气不好"。要治就得换探测序列
   （二次探测 `+i²` / 双重哈希 `+h2(key)` / Robin Hood），
   但**删除的墓碑问题一模一样** —— 墓碑是开放寻址的债，不是线性探测的债。

10. **阈值抄拉链法的 0.75。**
    开放寻址 α→1 时数组里一个 EMPTY 都没有，查找连停止条件都失去意义，
    曲线右端是墙。本节 0.5 的代价是"至少准备 2n 格"，
    换来的是一串长度停在个位数。

## 什么时候用它 / 什么时候别用

**该用：**
- 键值都是**定长小对象**（`int`、小结构体、指针索引），在乎分配次数和缓存局部性。
- 读多写多但要**低常数**：符号表、去重、计数、缓存索引、编译器 intern 表。
- 元素数量级已知（可以先建够格子）；或者能接受翻倍扩容的摊还。
- 想要"一次分配就装下整张表"，序列化 / 内存布局可控。

**别用：**
- **删除极频繁**且来不及做重排：墓碑会长期顶高装载率（第 5 幕那两个数字）。
  这种场景要么用"同容量重排"，要么干脆用拉链法（摘节点零负担）。
- 要**有序遍历 / 范围查询**：哈希表做不到，用 BST / AVL（第 05 章）。
- 元素很大或大小可变：内联到数组会让每格都按最大者计费，此时"数组放指针 + 堆放数据"
  （拉链法那味道）更划算。
- 需要**最坏情况保证**：哈希只给期望保证；对抗性输入能把表打成第 8 幕第 1 行那条长串。
- 装载率必须很高（内存极紧）：0.5 意味着一半格子空着，这时候拉链法更省。

## 自检问题

1. 为什么"删除那一格不能写 EMPTY"？用 12 / 20 / 28 三个键说清楚断在哪。
   **答**：三者的 home 都是 4，20 住槽 5、28 住槽 6，它们的探测路径都要路过槽 4。
   槽 4 写成 EMPTY 后，`get(20)` 在第一步就撞上"停止条件"→ 回答不存在，
   而 20 就躺在槽 5、值一分没少。墓碑 `†` 的语义是"这里曾有东西，**别在这里停**"。

2. 查找的三种格子状态各该怎么处理？
   **答**：`USED` 且 key 相等 → 命中停；`USED` 但不等 → 继续；`TOMB` → 继续
   （但插入要记住第一个当回收位）；`EMPTY` → 判负停。**只有 EMPTY 能给出"没有"这个结论。**

3. 删掉一个键之后装载率为什么不变？
   **答**：`used = size + tombs`。删除是 `size--` + `tombs++`，`used` 守恒。
   格子还是那一格挡路，探测步数一格没少 —— 第 4 幕实测：删除前 5 次查找平均 3.00 格，
   删除后**反而涨到** 3.80 格。涨的那 0.80 格来自被删的那个键自己：
   它的 `get` 现在要走 6 格（槽 7 不匹配 → 槽 8 是 `†` 不许停 → 9、10、11 别人的键 →
   槽 12 才是 EMPTY），而删除前它 2 格就命中了。墓碑没有让查找变**快**，
   它只是让查找还**正确**。

4. `put` 什么时候**不**检查阈值？为什么？
   **答**：回收墓碑时不检查。`† → USED` 挡路格子数守恒，`used` 不变；
   只有 `EMPTY → USED` 才让 `used + 1`，才需要看 `(used+1)*2 > capacity`。

5. `[扩容]` 和 `[整理]` 的判据分别是什么？哪一招是开放寻址独有的？
   **答**：越过阈值后，若 `tombs > 0 && (size+1)*2 <= capacity`（真元素塞得下、
   挡路的净是墓碑）→ 同容量重排，只蒸发墓碑；否则 → 翻倍。
   同容量重排是开放寻址独有的：拉链法没有"挡路"这回事。
   第 5 幕 B 实测：`size=0 / tombs=8 / used=8`，一次 `capacity=16 → 16` 的重排把 8 块墓碑
   清光，同一种查找的步数从 9 格降到 1 格。

6. `capacity` 从 8 扩到 16，槽 6 的键 28 会搬到哪？预测的和实际的一样吗？
   **答**：`28 = 3*8 + 4`，商 3 是奇数 → 新 home = `4 + 8 = 12`（验算 `28 % 16 = 12` ✅）。
   但第 6 幕实测它的**落点是 13**，因为键 12 的新 home 也是 12 且先被重放，
   28 只能往后挪一格。结论：**home 只取决于键和 capacity，落点取决于全表占用状态。**

7. 为什么开放寻址"对缓存友好"，但第 8 幕第 1 行（一条 512 格长串）看起来很可怕？
   **答**：这是两个维度。第 8 幕第 3 行说得很清楚：同样 256.50 次比较，两边**次数一模一样**，
   差的全是"跳一次要不要换地址"。数组里的长串仍然是一条条连续的缓存线
   （64.50 格 ≈ 13.30 条线，实测值），拉链法那 256.50 次比较落在散落的 512 个节点上，
   按第 7 幕那个显式标注的模型是 ≈ 257.50 条线。
   聚集影响**步数**，内联存储影响**每步多贵** —— 两件事别混着说。

8. 为什么阈值取 0.5 而不是 0.75？
   **答**：拉链法看平均链长（α=0.75 → 比 1.375 个节点），链可以无限长；
   开放寻址看连跑长度，串会被别人加长，且 α→1 时连 EMPTY 都没有、停止条件失效。
   第 8 幕实测 α=0.500 时失败查找已到 2.60 格，公式外推 0.75 → 8.5 格、0.90 → 50.5 格。

9. 本节 `Slot` 是 12 字节，一条 64 字节缓存线装 5 格还余 4 字节。
   要是把 `state` 从 `int` 改成 `char`，会省成 9 字节吗？
   **答**：不会。`int` 对齐要求 4 字节，`{int key; int value; char state;}` 的
   `sizeof` 是 12（尾部 padding 3 字节）。想真省得用**并行的状态数组**
   （`int8_t states[m]`），那才是真实库的做法（SwissTable 用一个 metadata 向量）。
   本节为了"结构体自解释、能盯着看"选了三条 `int`，第 1 幕把 `sizeof` 打印出来核对过。

10. 为什么 `oa_probe_path` 是 `const OATable *`，而 `oa_get` 不是？
    **答**：观测 vs 使用。抄探测序列不该改别人的表（所以 `const`、不污染 `probes`）；
    `get` 要记账 `t->probes += steps`，所以只能拿可变指针。
    代价写在 `oa.c` 注释里：为了可观测性牺牲接口纯度。
