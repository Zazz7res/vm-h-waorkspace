# 拉链法哈希表 hash-table-chaining

> 前面所有章节里，"找东西"只有一条路：从头走到尾。这一节开始，找东西变成
> **"直接跳到一个格子上"** —— 这是你在工程里用得最多的数据结构，没有之一。
> 语言内置的 dict / map / HashMap，底下就是这个东西（外加一堆优化）。

---

## 一句话是什么

**一个数组 + 一堆链表**：哈希函数把任意键算成一个数组下标，桶数组负责"跳到哪一格"，
每格后面挂一条链表负责"算到同一格的键怎么办"。

```
   key ──► h(key) ──► h(key) % capacity ──► buckets[i] ──► 一条链 ──► 逐个比 key
          揉成大整数      压进下标范围         O(1) 跳转      冲突都在这儿
```

三件事缺一不可。少了哈希函数就没有下标；少了桶数组就没有 O(1)；
少了冲突处理，两个键撞在一起就只能二选一（数据会丢）。

---

## 为什么需要它

你已经见过两个极端：

| 结构 | 知道下标时 | 知道"值/键"要找它时 | 键的范围 |
|---|---|---|---|
| 数组 | **O(1)** | O(n)：一格一格扫 | 只能是 0..n-1 的连号整数 |
| 单链表 | O(n) | O(n) | 什么都能当键 |

现实需求偏偏是"**我只有一个不像下标的键**"：
- 学号 `2021305011` 找学生 → 数组要开 20 亿格；
- 用户名 `"alice"` 找余额 → 字符串根本没法当下标；
- 一段英文里每个单词出现几次 → 键是任意词，数量事先不知道。

哈希表的办法是**合谋**：再造一个函数，专门把"随便什么键"翻译成"连号下标"，
然后就退回数组那种一次跳转的快感。这个函数叫哈希函数，代价是
**不同键可能翻出同一个下标**（冲突），所以必须准备一套处理冲突的规矩。

一句话：**哈希表 = 用"算"代替"找"。算不出唯一格子时，用链表兜住。**

## 图解

### 1. 哈希函数到底干了什么

```
     键 key          h(key)           h(key) % 8        落到哪个桶
   ┌────────┐      ┌──────────┐      ┌────────┐      ┌──────────────────────────┐
   │   3    │ ───► │     3    │ ───► │    3   │ ───► │ buckets[3] ─►[k=3]─►NULL  │
   │  11    │ ───► │    11    │ ───► │    3   │ ───► │ （同一个格子 → 冲突！）    │
   │  27    │ ───► │    27    │ ───► │    3   │ ───► │ （又撞了）                 │
   │   8    │ ───► │     8    │ ───► │    0   │ ───► │ buckets[0] ─►[k=8]─►NULL  │
   │  20    │ ───► │    20    │ ───► │    4   │ ───► │ buckets[4] ─►[k=20]─►NULL │
   │ 100    │ ───► │   100    │ ───► │    4   │ ───► │ （撞在桶 4）               │
   └────────┘      └──────────┘      └────────┘      └──────────────────────────┘
       任意整数       还是整数         0..capacity-1       数组下标，一次跳转
```

本节故意让 `h(key) = key`（identity 哈希），因为**上面这张表的每一个数字你都能自己手算**。
真实项目会做乘法/移位混合（否则键带公共因子时一半桶会空着），但流程完全一样。

### 2. 桶数组 + 链：内存里的两级结构

```
    t->buckets ──►┌────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
                  │  [0]   │  [1]   │  [2]   │  [3]   │  [4]   │  [5]   │  [6]   │  [7]   │
                  └───┬────┴───┬────┴───┬────┴───┬────┴───┬────┴───┬────┴───┬────┴───┬────┘
                      │        │        │        │        │        │        │        │
            第一级：一次 calloc，8 个指针 = 64 字节连续内存，每格就是一个 Node*
                      ▼        ▼        ▼        ▼        ▼        ▼        ▼        ▼
                    [k=8]    NULL     NULL    [k=27]   [k=100]   NULL     NULL     NULL
                      │                          │        │
                      ▼                        [k=11]    [k=20]
                    NULL                           │        │
                    空桶：只花一个指针              ▼        ▼
                                                [k=3]     NULL
                                                      │
                                                      ▼
                                                    NULL
            第二级：每个方框各是一次 malloc 的 HTNode（16 字节），散落在堆上，靠 next 串
```

⚠ **这个图和 `07-graph/adjacency-list` 的图是同一个形状**：
`Node **buckets` / `Node **adj` —— 都是"指针数组，每格拉出一条链"。
你已经写过一遍了，这次只是每条链里装的东西从"邻居编号"换成"键+值"。

关键认知：
- **桶数组里从不装元素，只装指针。** 所以桶数组永远不会"装满"，
  负载因子超过 1 也不会写越界 —— 链会变长而已。这是拉链法和开放寻址最大的区别。
- **节点里必须再存一份 key。** 撞进同一个桶的键，哈希值一样，
  到底是不是你要的那个，只能靠逐个比 `p->key == key`。只存 value 就无法确认命中。

### 3. 负数取余：本节最阴的坑（main.c 第 1 幕实测）

数学里的"模"结果一定在 `[0, m)`；**C 语言的 `%` 是截断除法的余数，符号跟着被除数**：

```
   C 必须满足：(a / b) * b + (a % b) == a
   a = -7, b = 4：
        -7 / 4  = -1          ← 向 0 截断（不是 -2，那是 floor）
        所以 -7 % 4 = -7 - (-1)*4 = -3      ← 负数！
```

**网上常说"`-7 % 4` 在 C 里是 -1"，那是记错了：-1 是商，余数是 -3。**
真实运行输出（第 1 幕，节选）：

```text
  桶数 capacity = 8，合法下标只能是 0..7

         键 key      key%8     ht_mod  能用吗
  ------------------------------------------------------
              -1         -1          7   ❌ 越界
              -7         -7          1   ❌ 越界
            -100         -4          4   ❌ 越界
     -1000000007         -7          1   ❌ 越界
     -2147483648          0          0   ✅
               0          0          0   ✅
               7          7          7   ✅
             100          4          4   ✅

  逐条验算 C 的截断除法等式 (a/b)*b + a%b == a：
    -7 / 4 = -1,  -7 % 4 = -3,  验算 -1*4 + (-3) = -7  ← 余数是负的
     7 / -4 = -1,  7 % -4 = 3  ← 余数符号只跟【被除数】，跟除数无关
```

于是天真写法直接埋雷：

```c
int idx = h(key) % capacity;   // h(key) = -7、capacity = 8 → idx = -7
buckets[idx]                   // 读写数组前面的内存：编译器不拦，ASan 拦
```

修法只有一种，**并且要修成"平移"而不是"取绝对值"**（`chaining.c:88`）：

```c
int ht_mod(long value, int m) {
    long r = value % m;
    if (r < 0) r += m;   /* -3 + 8 = 5，和 -3 同余；取绝对值就变成 3，是另一个桶 */
    return (int)r;
}
```

为什么不能 `abs(h) % m`？
1. `-3` 和 `3` 在模 8 下是**不同的桶**（-3 ≡ 5）。取绝对值会让同一个键两次落到不同格子，
   哈希表的正确性直接被毁掉。
2. `h == INT_MIN` 时 `-h` 溢出，是**未定义行为**。`ht_mod` 先在 `long` 域里算就没事。

字符串哈希（djb2，`unsigned long`）另有一条同族坑：把无符号大数塞回 `long/int`
字符串哈希（djb2，`unsigned long`）另有一条同族坑：把无符号大数塞回 `long/int`
是 implementation-defined 的收窄转换，长键实测会变负。第 7 幕的真实输出
（列依次是：键 / 长度 / h 无符号 / 同一串位存进 long / 裸 %8 / ht_mod / ht_mod_u）：

```text
  cat                       3              193488125              193488125       5        5        5
  electrocardiograph       18   16188182617897271319   -2258561455812280297      -1        7        7   ← 最高位是 1，存进 long 变负：裸 %8 就是越界下标
  photomechanically        17   17821016536054216153    -625727537655335463      -7        1        1   ← 最高位是 1，存进 long 变负：裸 %8 就是越界下标
```

所以字符串表的下标换算走 `ht_mod_u`（无符号取余，全程没有符号问题，`chaining.c:112`）。
### 4. 负载因子与 rehash：整张表最重要的一根弦

```
负载因子 load factor = size / capacity  ← 平均每条链挂几个元素（键均匀时）

  0.25 ▓░░░░░░░░░  链很短，一半以上桶空着      → 查找平均 1 步多
  0.50 ▓▓▓░░░░░░░  工程舒适区（本节阈值 0.75）  → 查找 ~1.5 步
  0.75 ▓▓▓▓▓▓▓░░░  阈值边界，再装就触发扩容
  4.00 ▓▓▓▓▓▓▓▓▓▓… 每条链 4 个节点             → 查找退化，接近链表
```

`ht_put` 里那条判据（`chaining.c:421`）：

```c
if ((t->size + 1) * 4 > t->capacity * 3) {   /* ⟺ 装入后 size/capacity > 0.75 */
    ht_rehash(t, t->capacity * 2);
    ...
}
```

- 为什么写整数乘法不写 `> 0.75` 浮点比较：`double` 有舍入，边界值今天恰好相等、
  明天换个 capacity 就判错。整数比较没有"差一点点"。
- 为什么严格大于：装到正好 0.75 不动，第 4 个键会让负载因子变成 1.000 才扩 —— 少抖一次。

**rehash = 全部重新投桶，一个都不许漏。** 因为下标 = `h(key) % capacity`，
capacity 一变，**每个键的下标都变了**；老键留在老下标，下次 get 去新下标找 → 找不到 →
数据凭空消失。第 4 幕会先把"预言"打出来，再触发真扩容逐行对照：

```text
  预测：capacity 4 → 8 之后，每个键会落到哪个桶（只看非负键，规律才成立）
      key   旧桶   新桶   h/C 的商 q   q 奇偶   按规律推   吻合?
  ------------------------------------------------------------------
       9      1      1        2    偶          1   ✅
       5      1      5        1    奇          5   ✅
       1      1      1        0    偶          1   ✅
  结论：新下标只有两种 —— 旧下标，或旧下标 + 旧容量(4)。一个桶最多裂成两个桶。
```

翻倍扩容有个**免费的规律**（Java HashMap 的 split、Redis 增量 rehash 的立足点）：
`h = q*C + r`，`r` 就是旧下标；`q` 偶 → 新下标 `r`（原地），`q` 奇 → 新下标 `r + C`（搬家）。
证明就两行：`q` 偶时 `h = (q/2)*(2C) + r`；`q` 奇时 `h = ((q-1)/2)*(2C) + (r + C)`。
所以**一个旧桶最多裂成两个新桶**，`ht_rehash_plan()` 把这条打印出来并现场验算 ✅。

## 逐操作拆解

### 1. `ht_create(capacity)` —— 建表（chaining.c:242）

```
 malloc(IntHT)   →  结构体 24 字节（buckets 指针 + capacity + size + probes）
 calloc(cap, sizeof(HTNode*))  →  8 个指针全置 0
```

为什么 `calloc` 而不是 `malloc` + 手写循环置 NULL：
指针的全 0 位模式在 C 里就是 `NULL`，一步到位，顺便消灭"漏初始化某一格"
这类 bug（空桶必须是 `NULL`，是垃圾地址就是野指针）。

两处 malloc 就要两处回滚：新数组申请失败时必须先 `free(t)` 再返回 `NULL`，
否则就是"内存紧张路径上的泄漏"——偏偏内存紧张时最需要不泄漏。

### 2. `ht_put(t, key, value)` —— 插入或覆盖（chaining.c:421）

严格三步，顺序有讲究：

```
(1) idx = ht_mod(h(key), cap) → 走这条链找 key
        找到 → 改 value，return（★ size 不变）
(2) 没找到 → (size+1)*4 > capacity*3 ? 先扩容翻倍
(3) ★ 重新算一次 idx → 头插新节点 → size++
```

- 第 (1) 步不做，反复 `put` 同一个键会把表撑爆（`size` 一路涨、链一路长）。
- 第 (3) 步是初学者最容易漏的一行：**扩容后 capacity 变了，旧 idx 已经作废。**
  拿旧 idx 往新数组挂 = 元素进错桶 = 之后 `get` 永远找不到它。
  这种 bug 不崩溃、不报错，只是"数据静默丢失"，最难查。
- 用**头插**而不是尾插：头插 O(1)，尾插要走到尾巴（链越长越贵）。
  副作用是同桶内顺序 = 插入顺序的倒序，第 2 幕的输出里能直接看到。

### 3. `ht_get` / `ht_contains`（chaining.c:467 / 485）

```c
int idx = ht_bucket_of(t, key);
for (HTNode *p = t->buckets[idx]; p != NULL; p = p->next) {
    t->probes++;                  /* ★ 每看一个节点记一次数 */
    if (p->key == key) { ...命中; }
}
return 0;                         /* 整条链走完都没有 → 不存在 */
```

两条要点：
1. **桶非空 ≠ 键存在。** 判定"不存在"必须走完那条链（第 2 幕 `get(4)`：桶 4 挂了 2 个
   节点，都不是 4，比较 2 次之后才敢说没有）。
2. `ht_contains` 就是 `ht_get(t, key, NULL)` —— 输出参数传 `NULL` 表示"值我不要"。

`probes` 计数器是本节的**测量仪器**：`get` 里写进了这个字段，所以 `ht_get`
不能声明成 `const IntHT *t`（这是"为了可观测性牺牲接口纯度"的典型取舍，
真实库里会把它换成独立计数器或宏开关）。

### 4. `ht_delete` —— 拉链法的删除有多干净（chaining.c:490 → node_remove_key:201）

```
   dummy ─►[k=17]─►[k=9]─►[k=1]─►NULL
     ▲        ▲
     └─ prev ─┘        ← prev 永远站在"要删的那个"前面一格
```

删中间 / 删头 / 删尾**走同一套代码**：`prev->next = victim->next; free(victim);`
最后 `*head = dummy.next` 统一写回。这就是第 02 章哨兵写法的实战复现。

两个纪律：
- **先接链，再 free**。写成 `free(victim); prev->next = victim->next;`
  就是 use-after-free（ASan 会当场打死你）。
- `dummy` 是**栈上的**假节点，不 malloc 所以不 free；`victim` 必须 free，
  否则每删一个键漏 16 字节。
- 删除只减 `size`，**不减 `capacity`**（不缩容）：删一半再插满会来回搬家（thrash）。
  绝大多数库（含 Java HashMap）都不主动缩容。

### 5. `ht_rehash(t, new_capacity)` —— 心脏手术（chaining.c:320）

```
  老数组每个桶：p = 链头
      while (p != NULL) {
          nxt = p->next;              ← ★ 先抄 next，因为马上要改 p->next
          idx = ht_mod(h(p->key), new_capacity);   ← ★ 用【新 capacity】重算下标
          node_push_front(&fresh[idx], p);         ← 挂到新桶
          p = nxt;
      }
  free(老数组); t->buckets = fresh; t->capacity = new_capacity;
```

- 节点对象**一个都不重新 malloc**，只重接 `next`。所以 rehash 不产生新的分配责任，
  也不会有"搬家路上漏 free"。
- `先抄 next` 是链表遍历的老规矩：`node_push_front` 会覆盖 `p->next`，
  不抄下来老链就断了，后半条链失联 = 泄漏。
- **扩容失败可降级**：`calloc` 拿不到新数组时打印错误、保持原表不动、返回 0。
  负载因子高一点只是慢，不是错。这个"宁可慢也不要崩"的设计让哈希表能长期跑。

### 6. `ht_free(t)` —— 从里往外剥三层（chaining.c:276）

```
  for 每个桶: while (p) { nxt = p->next; free(p); p = nxt; }   ← 第 1 层：size 个节点
  free(t->buckets);   t->buckets = NULL;                        ← 第 2 层：指针数组
  free(t);                                                      ← 第 3 层：结构体
```

只 free 第 2、3 层是最典型的泄漏。ASan 会报 `xxx bytes in N objects`，
那个 **N 正好等于节点个数**，报告里的对象数就是线索。

### 7. 字符串键版本：djb2 + strcmp（chaining.c:654 / 796 / 920）

和 int 表比只有三处不同，其余全是重复 —— 这就是"C 没有泛型"的样子：

| | IntHT | StrHT |
|---|---|---|
| 哈希 | `h = (long)key`（identity） | `h = 5381; h = h*33 + c`（djb2） |
| 比较 | `p->key == key` | `strcmp(p->key, key) == 0` |
| 所有权 | key 是 int，不用管 | key 是 `char *`，**表自己复制一份**，free 时单独 free |

三个必须记住的点：
1. **为什么 `h * 33`？** `33 = 2^5 + 1`，可以写成 `(h << 5) + h`，一条移位一条加法；
   乘法还不断把低位信息搅到高位，实测散列质量好。初值 5381 是作者实测值。
   （Java 的 `String.hashCode` 用 `h * 31 + c`，思路完全一样。）
2. **为什么必须用 `unsigned long`？** 长字符串必然让这个乘法溢出。
   **无符号溢出 = 对 2^64 取模，标准明确定义**；有符号溢出 = 未定义行为。
   另外遍历时要先转 `unsigned char` 再进表达式，否则带符号的 `char`
   在扩展 ASCII 字节上是负数，会被符号扩展污染。
3. **为什么必须复制键？** 调用者的字符串可能是栈数组，函数一返回就成了悬空指针。
   第 7 幕现场演示：把调用者的缓冲区从 `"cat"` 改成 `"xat"`，
   表里 `contains("cat")` 仍然是 1 —— 因为表存的是自己那份副本。
   顺带一条 C 规矩：`strdup` 是 POSIX 的，`-std=c11` 下**没有声明**，
   隐式声明被当成返回 `int` → 指针截断，64 位机上必崩，所以本节手写 `dup_str`。

`sh_delete` 里 free 的顺序也是考点：`free(victim->key)` 必须在 `free(victim)` **之前**，
反了就再也读不到 `victim->key`。

### 8. 词频统计（chaining.c:920）—— 哈希表最常见的真实用途

切词规则（故意简单，但必须显式说清楚，工程里切词比哈希函数更容易出错）：
字母进当前词，非字母（空格、`, . ; !`、数字、下划线）一律当分隔符，
大写字母 `tolower` 归一化。于是原文里的 `The` 和 `the` 并进同一个键，`dog.` 记成 `dog`。

计数就三行：`get` 到 → `put(word, old+1)`；`get` 不到 → `put(word, 1)`。

最后**必须排序才能看榜单**：哈希表的遍历顺序 = 桶顺序 = `h(key) % capacity` 的顺序，
既不是插入顺序也不是字典序。想按词频看 Top N，就得把节点指针收集进数组显式排一次
（本节就地写插入排序，规则硬编码在函数里，因为仓库禁用函数指针比较器）。

## 复杂度

`n` = 元素个数，`m` = 桶数（capacity），`α = n/m` = 负载因子，`L` = 链长。

| 操作 | 平均（哈希均匀 + α 有界） | 最坏 | 为什么 |
|---|---|---|---|
| `ht_put` | **O(1)** | O(n) | 1 次数组跳转 + 走链；扩容摊还 O(1) |
| `ht_get` / `ht_contains` | **O(1)** | O(n) | 同上，代价就是那条链的长度 |
| `ht_delete` | **O(1)** | O(n) | 走链找前驱 + 一次 free |
| `ht_len` | **O(1)** | O(1) | 因为一路维护了 `size` 字段（不维护就退化成 O(n) 全扫） |
| `ht_rehash` | O(n) 一次 | O(n) | 全部重投；翻倍保证"每个元素平均只被搬常数几次" |
| 空间 | O(n + m) | — | 结构体 + m 个指针 + n 个节点（每节点 `sizeof(HTNode)=16`） |

**"O(1)" 是怎么来的**：查找代价 = `1 + 链长`。
在简单均匀哈希假设下，链长期望 = `α = n/m`。只要 `α` 被 0.75 卡住（常数），
代价就是常数 → 这就是那句"O(1)"的全部前提。前提塌了，O(1) 就是假的。

本节把前提塌掉的样子跑出来了（第 6 幕真实数字，n = 1000）：

| | 桶数 | 最长链 | 1000 次 get 比较节点总数 | 平均 |
|---|---|---|---|---|
| 健康表（键 0..999） | 2048 | 1 | **1000** | **1.00** |
| 病表（键全是 4096 的倍数） | 2048 | **1000** | **500500** | **500.50** |

`500500` 正好等于 `1+2+...+1000 = n(n+1)/2`，相差 **500 倍**。
链头到链尾的距离就是比较次数 —— 这就是"退化成了链表"的字面意思。

拉链法独有的一个特权：**α 可以超过 1**（桶数不够时全部键也能存，只是链变长）。
下一节开放寻址做不到 —— 它 `size > capacity` 就直接死循环。

## 常见的坑

1. **`h(key) % capacity` 裸写，负键直接越界。** 真实数字：`-7 % 8 = -7`、`-100 % 8 = -4`。
   必须走 `ht_mod`（或全程无符号 + `ht_mod_u`）。这一条在第 1 幕有实测表。
2. **修负数用 `abs(h) % m`。** 双重错：`-3` 和 `3` 是不同的桶（-3 ≡ 5），取绝对值毁掉正确性；
   而且 `h == INT_MIN` 时是未定义行为。平移 `r += m` 才是同余的。
3. **节点里只存 value 不存 key。** 撞进同一个桶之后你无法判断"这一格是不是我要的键"。
   哈希值相同 ≠ 键相同。
4. **`put` 不先查已存在 → 同一个键插了两条。** 表越撑越大，`get` 只返回链上第一个，
   读到的值"看起来随机"。正确顺序永远是：先找 → 有则改值 return → 无则插入。
5. **rehash 之后忘记重算下标。**（本节最阴的 bug）拿扩容前算好的 `idx` 去挂新数组，
   元素进了错误的桶，之后 `get` 永远找不到 —— **不崩溃、不报错，只是数据静默丢失。**
   见 `ht_put` 里那个标了 ★ 的第 (3) 步。
6. **`free(victim)` 之后才读 `victim->next` / `victim->key`。** 顺序永远是
   抄 next → 接链 → free 内层（字符串节点要 `free(key)` 再 `free(node)`）。
7. **只 `free(buckets)` 和 `free(t)`，漏了链上节点。** 本节最典型的泄漏，
   ASan 报的 `... bytes in N objects`，N 就是节点个数。三层所有权要从里往外剥。
8. **字符串键存了调用者的指针。** 调用者的数组/栈帧一销毁就是悬空指针。
   必须复制（本节手写 `dup_str`；`strdup` 在 `-std=c11` 下没有声明，别直接用）。
9. **把"遍历哈希表"当成有顺序。** 桶顺序 = `h(key) % m` 的顺序，和插入顺序、字典序都无关，
   rehash 之后还会整个变一遍。想要榜单必须**显式排序**（第 8 幕就是这么干的）。
10. **以为 capacity 是 2 的幂是"规定"。** 不是。2 的幂让 `h % m` 能换成 `h & (m-1)`（更快），
    并且让"翻倍扩容只搬一位"这条规律成立；但如果哈希函数低位质量差
    （比如键全是偶数、又用 identity 哈希），2 的幂反而让一半桶永远空 ——
    第 6 幕的病表就是这么造出来的。用乘法哈希就是在治这个病。
11. **负载因子阈值当教条。** 0.75 是"链长期望 0.75、空间利用尚可"的经验折中
    （Java HashMap 就用它）。字符串键比较贵（要 `strcmp`），有时会调得更低；
    内存极敏感的场景会调得更高。数字可调，"平均链长 = 负载因子"这个关系不可调。

## 什么时候用它 / 什么时候别用

**该用：**
- 只按**键**访问，不关心顺序、范围、前后邻居：缓存、索引、去重、计数（词频）、集合判存。
- 键是字符串 / 结构体首字段等"不像下标"的东西。
- 数据量事先不知道、还会一直长：桶数组翻倍即可，不需要预先知道上界。

**别用：**
- 要**有序遍历**或**范围查询**（"找出 18~30 岁的所有人"）→ 用二叉搜索树 / AVL（第 05 章），
  哈希表在这些事上是"能力缺失"，不是"慢"，而是**根本做不到**。
- 要**最坏情况保证** O(log n)：哈希表只给期望保证。对抗性输入（哈希碰撞攻击）
  能把你的表打成第 6 幕那个 500 倍慢的病表 —— 安全场景要么用树，要么用带随机种子的哈希函数。
- 元素极少（十几个）：一个数组线性扫可能更快也更省（没有 malloc 开销、缓存友好）。
- 极度在意内存：拉链法每个元素多一个 `next` 指针 + 一次 malloc 的管理开销。

## 自检问题

1. `capacity = 4` 时插入键 `-1`，为什么 `ht_mod(-1, 4)` 要给 3 而不是 1？
   **答**：`-1 % 4` 在 C 里是 `-1`，`-1` 不是合法下标。同余地加 4 得 3，
   且 3 与 -1 相差一个 4 的整数倍，落在 `[0,4)` 里 —— 下次查 `-1` 还算到 3，一致才对。
   若"修"成 `abs(-1) % 4 = 1`，那键 1 和键 -1 会争同一个桶而且都能插进去，
   但查 -1 时又会去桶 3 找 → 找不到 → 数据丢了。

2. 为什么"桶非空"不等于"键存在"？举第 2 幕的例子。
   **答**：桶 4 挂了 `100` 和 `20`，问 `get(4)`：下标算出来正好是 4，链也不空，
   但两个节点都不是 4 → 必须走完链才敢说"不存在"。第 2 幕打印它比较了 2 个节点。

3. `ht_put` 里为什么 rehash 之后要再算一遍 `idx`？不算会怎样？
   **答**：`idx = h(key) % capacity`，capacity 变了 idx 就是旧的。
   拿旧 idx 挂到新数组 = 元素进了错桶；之后所有按新 capacity 算下标的查询都找不到它。
   现象是"插入成功、size 也在涨、但 get 返回 0"，且不报错。

4. 为什么负载因子超过 0.75 才扩容，而不是 1.0（装不下再说）？
   **答**：`size/capacity = 1.0` 时**平均每条链 1 个节点**，已经有大量桶是 2、3 个节点，
   查找常数明显变差；桶数组还有"空桶只花一个指针"的优势，翻倍一次的代价
   （O(n) 摊还成常数）远比让链长涨起来便宜。0.75 是空间与链长的折中点。

5. capacity 从 8 扩到 16，键 9（旧桶 1）会搬到哪个桶？怎么不重算 h 就知道？
   **答**：`9 = 1*8 + 1`，商 1 是奇数 → 新下标 = 旧下标 + 旧容量 = `1 + 8 = 9`。
   验算 `9 % 16 = 9` ✅。这就是第 4 幕打印的"一个旧桶最多裂成两个新桶"，
   Redis 的增量 rehash 靠它把搬家分摊到多次操作里。

6. 词频统计里 `get("owl")` 为什么打印 -1 而不是 0？
   **答**：0 是**合法计数值**（一个词出现 0 次虽然不插表，但值域里 0 是可用的），
   拿 0 当"查不到"的哨兵就和真实数据混淆。C 里的标准做法是**返回值表示成不成的，
   值走输出参数**：`sh_get` 返回 1/0，`value_out` 才是数据；main 里 `? v : -1`
   是为了打印好看，接口本身从没依赖 0 当哨兵。

7. 字符串表比 int 表多几层 free 责任？漏哪一层最常见？
   **答**：多一层 `node->key`（每个键一次 `dup_str`）。最容易漏的也是这一层：
   `free(node)` 时忘了先 `free(node->key)`，ASan 会报一堆几十到几百字节的
   "definitely lost"，而且泄漏的对象数量 = 键的个数，正好是线索。

8. 为什么本节把 `capacity` 固定选成 2 的幂？这是必需的吗？
   **答**：为了演示"翻倍扩容 → 只有最高一位变"这条规律，也为了让 `%` 可换成 `&`。
   数学上不是必需（任何正整数都能当 capacity，`ht_mod` 照样给出合法下标），
   但真实库几乎都选 2 的幂，就是因为这条规律让 rehash 和分裂变得极便宜。
