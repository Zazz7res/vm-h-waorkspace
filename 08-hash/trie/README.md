# 前缀树 Trie

> 哈希表那一节你学到的是"把键**揉成**一个下标"。这一节正相反：
> **不揉，把键拆成一位一位，一位占一层。**
> 于是"找东西"变成了"走路"——从根出发，按字符一步一步往下踩。
> 搜索框一打字就跳出来的补全候选，背后就是这个结构。

---

## 一句话是什么

**一个"每个节点带 26 个岔路口"的树：键不是存在节点里的字符串，而是"从根走到这个节点的路径本身"。**

再加两个 int 计数器，所有前缀问题就都能 O(串长) 回答：

```
pass_count  几个串【经过】这个节点   ← 读它就知道"以它为前缀的串有几个"
end_count   几个串【在这里结束】     ← 读它就知道"这个前缀本身是不是一个完整的词"
```

| 想问什么 | 拉链法哈希表 | Trie |
|---|---|---|
| `card` 在不在？ | O(1) ✅ | O(L) ✅ |
| 以 `ca` 开头的有几个？ | O(n)，每个键比一遍 ❌ | **O(2)**：读 `ca` 的 `pass_count` |
| 输入 `do`，列出所有补全 | 做不到（要扫全表） | O(结果规模) DFS |
| 把所有键按字典序输出 | 要显式排序 | 遍历顺序天然就是字典序 |
| 每个元素占多少内存 | ~24 字节 + 键副本 | **216 字节/节点**（本节实测） |

一句话：**哈希表省内存但只会"问等于"，Trie 会"问开头"但内存花得狠。**

---

## 为什么需要它

真实需求：输入框里打了 `do`，要立刻列出 `door`、`donate`、`dough`。

- **哈希表**：`h("door")` 用 `h = h*33 + c` 把四个字符搅成一个 4 万亿的大整数。
  "d 在 o 前面""o 后面还有一个 o"这些**顺序信息在搅的过程中被销毁了**，拼不回来。
  所以它只能问"等于 `door` 的在哪"。要问"以 `do` 开头"，唯一的办法是把**每个键都拿出来
  `strncmp` 一遍**——本节第 7 幕实测：676 个键，比了 **676 次**。
- **数组 / 链表**：同样要全扫，而且连"精确查 O(1)"都做不到。
- **二叉搜索树**：能做范围查询，但比较的是整串的字典序大小，问"以 `do` 开头"
  也要在区间里扫一段，而且完全用不上"前缀共用"这件事。
- **Trie**：路径本身就是前缀。走到 `do` 那个节点只要 **2 步**，
  读它身上的 `pass_count` 就得到答案，和词表里有 676 个还是 676 万个词**无关**。

工程里它在跑的东西：搜索框/命令行 Tab 的自动补全、输入法候选词、拼写检查、
敏感词过滤（Aho-Corasick = Trie + fail 指针）、IP 路由的"最长前缀匹配"、
DNA 的 k-mer 计数、编译器的关键字/符号表。

代价也要当场说清：本节 676 个两字母的词，Trie 花了 **148 KB**，
拉链法哈希表大概 **16 KB**。见"图解"第 7 小张和运行输出第 7 幕。

> 本节的"值"就是那两个 `int` 计数器（仓库规矩：值一律 int，禁止 `void *`）。
> 想给每个词挂一个 int（词频、文档号），加个 `int value` 字段就行；
> 想挂变长对象就要 `void *` —— 那是本节明令禁止的东西，理由见 `chaining.h` 开头第四段。

## 图解

### 1. 键不是"存在节点里"，键就是"走过去的这条路"

插入 `cat` `car` `card` `do` `door` 之后的形状（第 3 幕会把它带计数器打印出来）：

```
        (root)        ""                 ← 空前缀，所有串都从它身上过
          ├── c           "c"
          │    └── a      "ca"            ← 3 个串经过它，但 "ca" 不是词
          │         ├── r "car"        ★ 是个词，同时 card 还从它继续往下
          │         │    └── d "card"  ★
          │         └── t "cat"        ★
          └── d           "d"
               └── o      "do"         ★ 是个词，同时 door 还从它继续往下
                    └── o "doo"           （不是词，只是半截路）
                         └── r "door"  ★

★ = end_count > 0（有单词在这里结束）
```

关键观察：**`"car"` 和 `"card"` 共用 c-a-r 三个节点。**
插 `card` 只新建 1 个节点（第 2 幕实测），不是 4 个。
"共用前缀"不是优化技巧，它就是 Trie 的定义 —— 也正是它能回答前缀问题的原因：
所有以 `ca` 开头的词，都在 `ca` 这个节点的**子树里**，一个都没跑掉。

### 2. 两个计数器：pass 是"流量"，end 是"站点"

这是本节最重要的一张图。把第 3 幕打印出来的数字摘出来：

```
  节点（这个前缀）    pass   end    怎么读
  ─────────────────────────────────────────────────────────
  (root)               5      0    5 个串都从根出发；根不是词
  c                    3      0    car/card/cat 经过；"c" 不是词
  ca                   3      0    同上 3 个；"ca" 不是词
  car                  2      1    card 穿过(1) + car 自己(1)；car 是词 ★
  card                 1      1    只有 card 经过，并且在这结束 ★
  cat                  1      1    只有 cat ★
  d                    2      0    do/door 经过
  do                   2      1    door 穿过(1) + do 自己(1) ★
  doo                  1      0    只有 door 穿过；"doo" 不是词
  door                 1      1    ★
```

两条铁律，看图就会明白：

```
  ① end_count > 0  ⟺ 这个前缀本身是一个完整单词
     ⚠ 千万不要用"它有没有孩子"来判断！
       car 有孩子 d，它照样是个词；doo 有孩子 r，它不是词。孩子和"是不是词"两回事。

  ② pass_count = 以这个前缀开头的串有几个（包含在它这里结束的那些）
     所以永远有 end_count <= pass_count。
     "以 ca 开头的词有几个" = ca.pass_count = 3  ← 直接读，不下子树。
```

重复插入（第 4 幕把 `cat` 插了两遍）之后：

```
  cat 节点：pass=2  end=2     ← 两个一模一样的串，共用同一个节点
  ca  节点：pass=4  end=0     ← 4 个串经过（car/card/cat/cat）
  节点总数：10 → 10           ← 一个新节点都没建！只是计数器 +1
  不同单词数：5 → 5           ← trie_count_words 认的是 end_count>0 的节点
```

于是 `end_count` 为什么必须是 `int` 而不是 `bool`，也一眼看穿了：
插两遍、删一遍，`end` 从 2 变 1，词**还在**；用 bool 的话删第一次就会把词误删。

### 3. 插入 `card`：每经过一个节点就 `pass+1`，只有最后那个 `end+1`

```
  走 'c' → child['c'-'a'] = child[2] 已有节点 → pass 3→4，不新建
  走 'a' → 已有                                    → pass 3→4，不新建
  走 'r' → 已有                                    → pass 2→3，不新建
  走 'd' → child[3] == NULL → calloc 一个，pass 0→1，end 0→1 ★
                                    （只有终点才动 end）
  实测（第 2 幕）：节点 5 → 6，新建 1 个字符节点，复用 3 个已有格子
```

### 4. 删除：一路把 `pass_count` 减 1，并且把归零的节点**真的 free 掉**

以第 6 幕的真实序列为例（此时树里是 cat×2、car、card、do、door）：

```
  删 "card"：card.pass 1→0 且 end 1→0  → free 掉 d 那一格
             car.pass  2→1（还有 car 自己是词）→ 留
             ca .pass  4→3、c  .pass 4→3        → 留
             节点 10 → 9   ✅ search("car") 仍然是 1 —— 删 card 不该动 car

  删 "cat"（第一遍）：cat.pass 2→1、cat.end 2→1 → 两个都不为 0 → 节点全留
             节点 9 → 9，search("cat") 还是 1（还剩一遍）  ★ 多重集合的味道

  删 "cat"（第二遍）：cat.pass 1→0 且 end 1→0 → free 掉 t
             ca.pass 2→1、c.pass 2→1（car 还在经过）→ 留
             节点 9 → 8

  删 "car"：        car.pass 1→0 且 end 1→0 → free 掉 r
             然后 ca.pass 1→0 且 end 0 → free 掉 a   ★ 连带收缩
             然后 c .pass 1→0 且 end 0 → free 掉 c   ★ 连带收缩
             节点 8 → 5（一删掉了 3 个节点）
```

**为什么 free 的判据是 `pass_count == 0 && end_count == 0`，不是只看 `end_count`？**

```
  'a' 这个节点的 end_count 从建好到销毁【一直是 0】（因为 "ca" 不是词）。
  如果只看 end_count 决定去留，它永远"还没资格被删"→ 整棵树只涨不缩，
  反复增删的词表几个月后把内存吃光，而且程序一点错误都不报。
  真正说明"这个节点没用了"的是【流量归零】：没有任何串再经过它。
```

**反例：删 `do` 时节点必须留下**（第 6 幕实测）：

```
  删 "do"：do.end 1→0（词没了）  do.pass 2→1（door 还从它身上过）
  → search("do")=0 ❌ 词没了
    starts_with("do")=1 ✅ 前缀还在
    count_prefix("do")=1 ✅ 还有 1 个串以它开头（door）
    节点数不变 ✅
  这就是双计数器的分工：end 管"词还在不在"，pass 管"节点还在不在"，互相独立。
```

### 5. 自动补全 = 从前缀节点出发做一次 DFS，靠一个"就地写"的路径缓冲区

给前缀 `do`，把子树里所有 `end_count > 0` 的节点的"路径"收集起来：

```
  递归进来时缓冲区状态            这一步做什么                     found
  ──────────────────────────────────────────────────────────────────
  path="do"            len=2   end=1 → 先抄走 "do"                +1
  path="do"→填[2]='o'  len=3   钻进 doo（end=0，什么都不抄）
  path="doo"→填[3]='r' len=4   end=1 → 抄走 "door"                +1
  返回 len=3 → 返回 len=2      ★ 回溯：不 memset、不清零，
                               下一条岔路填 path[2] 时【覆盖】掉旧的 'o'
```

真实输出（第 5 幕）：

```
  补全 "do"   → "do" "door"          （pass_count=2，补出 2 条）
  补全 "ca"   → "car" "card" "cat"   （pass_count=4，补出 3 条 ← cat 插了两遍）
  补全 "z"    → 空                   （walk 第一步就撞空格子，前缀本身不存在）
```

两个"为什么"：

- **为什么用递归**：树的深度事先不知道（1 到 31 层）。用循环就得自己造一个栈存
  "待处理节点 + 当前路径长度"，等于把函数调用栈重写一遍。递归把"回到上一层"交给栈帧。
- **为什么缓冲区必须就地写死、不许全局**：`path[]` 是 `trie_autocomplete`
  **自己栈帧里的 `char path[TRIE_WORD_MAX]`**，递归各层共用这一块内存（靠参数传地址）。
  如果它是全局变量：两次调用互相踩数据（不可重入）、并发直接错、
  而且"谁负责清零"变成隐形约定 —— 这是 C 里最经典的 bug 温床。函数一返回，
  栈帧消失，缓冲区自动没了，一次 malloc 也没有。

### 6. 遍历顺序：免费的字典序

```
  trie_dump_words() 出来的顺序：  car card cat do door
  为什么不用排序：child[] 的下标就是字母序号，i 从 0 扫到 25 天然等于 'a'→'z'；
                  且每层"先报自己的 end_count，再往下钻"，所以 do 排在 door 前面。
  对比拉链法：桶顺序 = h(key) % m 的顺序，想输出字典序必须把键全捞出来再显式排序。
```

### 7. 内存账：`sizeof(TrieNode) = 216`，而 26 个格子里绝大部分是 NULL

```
  一个节点的 216 字节怎么来的（第 1 幕用 sizeof + offsetof 实测，不是嘴上说的）：

  字节号  0                                                            215
        ┌──────────────────────────────────────────────────┬────────┬────────┐
        │ child[0] child[1] ...... child[25]  26 个指针    │end_count│pass_cnt│
        └──────────────────────────────────────────────────┴────────┴────────┘
          └────────── 26 × 8 = 208 字节（96% 的钱）──────────┘  └─ 4 ─┘ └─ 4 ─┘

  offsetof(TrieNode, end_count) = 208   ← 证实 child[] 正好占 0..207
  208 + 4 + 4 = 216 = sizeof(TrieNode)  ← 证实【没有补齐空洞】
```

第 7 幕把 676 个两字母的词（`aa`…`zz`）灌进去，账单是：

| 指标 | 实测值 |
|---|---|
| 节点数 | 703（= 1 根 + 26 首字母 + 676 末端） |
| 总字节 | 703 × 216 = **151848 字节（148.3 KB）** |
| child 槽位 | 703 × 26 = 18278 格，只用掉 702 格 → **空 96.2%** |
| 光空格子占掉 | 140608 字节（137.3 KB） |
| 摊到每个字符 | 112 字节 |
| 同样 676 个键用拉链法 | 约 676 × 24 字节 + 键副本 ≈ 16 KB 量级 |

```
   费在哪，一句话：Trie 把"这个节点有哪几个孩子"这件事，
   用一整张 26 格的【查找表】存了下来 —— 换掉了"到孩子里比一比"的开销，
   代价是 24 个格子中枪躺平。
```

### 8. 三兄弟结构对照（同一张图记住三种取舍）

```
   数组     键 = 下标 0..n-1        → O(1)，但键必须是连号整数
   哈希表   键 = 揉成一个大整数      → O(1) 精确查；顺序信息全丢，问不了前缀
   Trie     键 = 拆成一位一位       → O(L) 精确查 + 前缀 + 补全 + 字典序；每节点 216 字节
   二叉树   键 = 比大小分左右        → O(log n) 精确查 + 范围查；前缀能力远不如 Trie
```

## 逐操作拆解

本目录三个文件，**完全自包含**（只 include `<stdio.h> <stdlib.h> <string.h> <stddef.h>`
和自己的 `trie.h`，跨目录 include 一个都没有）：

| 文件 | 行数 | 作用 |
|---|---|---|
| `trie.h` | 250 | 只有声明 + 顶部大注释：Trie 解决什么问题、两个计数器、内存代价、本节三条规矩 |
| `trie.c` | 652 | 实现，11 个小节按顺序讲"这行为什么存在" |
| `main.c` | 580 | 九幕演示，每幕自己建树自己收摊 |

| 操作 | 位置 | 一句话 |
|---|---|---|
| `trie_node_new` | `trie.c:37` | 用 **calloc** 不用 malloc：26 个格子必须是 NULL，残留随机地址＝插入时钻空子走进别人的内存 |
| `word_is_valid` | `trie.c:61` | 唯一的"防越界写"的墙：只收小写字母、长度 ≤ 31、非空 |
| `trie_insert` | `trie.c:109` | 边走边 `pass+1`，终点 `end+1`；`TrieNode **root` 是因为空树时根要由它创建 |
| `walk` | `trie.c:166` | 三个查询共用的内部函数：走完才返回节点，走不通一律返回 NULL（不返回"走了一半"） |
| `trie_search` | `trie.c:196` | 走完 word 读 `end_count`；返回 int 而不是 bool，因为"插了几遍"是有效信息 |
| `trie_starts_with` | `trie.c:206` | 走完 prefix 就算赢，一个计数器都不读 |
| `trie_count_prefix` | `trie.c:217` | 走完 prefix 读 `pass_count` —— **本节最漂亮的一行**：O(L)，与子树大小无关 |
| `node_delete` / `trie_delete` | `trie.c:258` / `283` | 递归：`pass-1` → 递归孩子 → `pass==0&&end==0` 就 free 并 `return NULL` |
| `collect_words` / `trie_autocomplete` | `trie.c:338` / `374` | DFS + 回溯 + 栈上定长路径缓冲区，字典序输出 |
| `print_subtree` / `trie_print_tree` | `trie.c:420` / `469` | 缩进打印整棵树：`'*'` + `pass=` + `end=` + 行尾完整前缀 + 每层节点数 |
| `gather_stat` / `trie_print_stats` | `trie.c:503` / `518` | 一次遍历算出节点数/边数/词数/字符数，把"费内存"打成字节数 |
| `trie_count_nodes` / `trie_count_words` | `trie.c:554` / `567` | 都是 O(节点数) 全树遍历 —— 本节的"大小"类问题天生要遍历 |
| `trie_free` | `trie.c:615` | **后序**递归释放：先拔 26 棵子树，再 free 自己 |

三个接口设计上刻意留下的痕迹（值得注意）：

1. `trie_insert` / `trie_delete` 收 `TrieNode **root`，`trie_search` 等只收 `const TrieNode *`。
   区别就是"要不要动调用者手里那根指针"：插入可能创建根、删除可能把根删没（第 7 幕实测：
   676 个词全删光后 `root == NULL`）。这正是 `00-c-foundation/pointer-basics` 第 2 课的实战版。
2. 输出参数 `int *steps_out`（`trie_walk_counted`）允许传 `NULL` = "我不要这个结果"。
3. `trie_autocomplete` 要调用者提供缓冲区 + 容量，函数只保证不写爆 ——
   和 `fgets` / `snprintf` 是同一套 C 规矩，不是本节发明的。

## 复杂度

记号：`L` = 串长，`n` = 串个数，`M` = 节点总数（`M ≤ 1 + 所有串的字符总数`），
`σ` = 字符集大小（本节 26），`k` = 补全结果条数。

| 操作 | 时间 | 为什么是这一格 |
|---|---|---|
| `trie_insert` | **O(L)** | 走 L 步；新建 ≤ L 个节点，每节点一次 calloc。字符串比较一次都没做 |
| `trie_search` | **O(L)** | 走 L 步读 `end_count`。注意是 O(L) 不是 O(1)：要付"串长"这笔钱 |
| `trie_starts_with` | **O(L)** | 同上，读到路径能不能走完 |
| `trie_count_prefix` | **O(L)** ★ | 走 L 步读 `pass_count`。没有这个计数器就得 O(子树大小) |
| `trie_delete` | **O(L)** | 走 L 步 + 沿途 free ≤ L 个节点（先 search 确认存在，共两趟 O(L)） |
| `trie_autocomplete` | `O(P + 子树节点数)` | 前缀 P 步定位，然后必须走遍子树 —— 因为**结果本身就有那么多条**，这不是浪费 |
| `trie_dump_words`（字典序遍历） | `O(M)` | 遍历全部节点；对比哈希表：`O(n log n)`（要显式排序） |
| `trie_count_nodes/_words/_stats` | `O(M)` | 没在插入/删除里维护这些字段，天生要遍历（见下面的"取舍"） |
| 空间 | `O(M × σ)` 指针字节 = `O(M × 216)` | 第 7 幕实测 148.3 KB / 676 个两字母词 |

**核心一句：Trie 的耗时只看串长 `L`，不看词数 `n`。** 第 7 幕把它跑成了两个可复现的数字：

| 问的问题 | 朴素扫描 / 哈希表 | Trie |
|---|---|---|
| 以 `c` 开头的词有几个（词表 676 个） | 比较 **676** 个键 | 走 **1** 步 → 26 |
| 以 `ca` 开头的词有几个 | 比较 **676** 个键 | 走 **2** 步 → 1 |
| `zz` 在不在（精确查） | **676** 次 `strcmp`（它排最后） | **2** 步 |
| 前缀 `zzz` 存在吗（查不到） | **676** 次比较才敢说 0 | **2** 步撞空格子 |

为什么用"比较次数"而不是秒表衡量？计时有噪声（频率、缓存、别的进程都在抖），
比较次数是可复现的整数 —— 上一节拉链法用 `probes` 字段干的是同一件事。

两个必须说清的"不公平之处"（否则就是把 Trie 吹成万能）：

- **精确查这一格，哈希表赢**：`get("door")` 哈希表 O(1)（一次跳转 + 比一次键），
  Trie O(L)。只要精确查的需求，就别上 Trie，那笔内存白花了。
- **Trie 的 O(L) 里藏着一个大常数**：每步是一次 `child[idx]` 数组寻址（快，但也意味着
  跳指针、缓存不友好），而且每个节点一次 `calloc`。真实高并发词库会因为这两个原因
  改成"扁平数组存整棵树 + 二分找孩子"（`trie.c` 末尾第 11 节讨论）。

    → 0 个节点、root 是 NULL：最后一个串删掉时，根的 pass 也归零，被 node_delete free。
      这就是 trie_delete 为什么收 TrieNode **root —— 它要把调用者的根改成 NULL。
      此刻再调 trie_free(trie) 就是对 NULL 的空操作（合法），不会 double free。

----------------------------------------
第 8 幕：这棵树到底值多少钱 / 什么输入会被拒
----------------------------------------
      [新建根] 空树的第一次插入要先把根造出来，并写回调用者的指针
      cat/car/card/do/door：节点 10 个 × sizeof(TrieNode)=216 字节 = 2160 字节（2.1 KB）
        其中每个节点：child[26] = 26 × 8 = 208 字节，end_count+pass_count = 8 字节，合计 216 字节
        child 槽位：共 260 格，只用掉 9 格（边数 = 节点数 - 1 = 9），空 251 格 = 96.5%
        光那些 NULL 格子就占着 2008 字节（2.0 KB）—— 这就是"费"的字面意思
        存了几个词：5 个不同单词，字符总数 16 → 摊下来每个字符 135 字节

  对照上一节的拉链法哈希表（同样存这 5 个串）：
    哈希表：5 个链表节点（各 ~24 字节）+ 桶数组 + 键副本 ≈ 几百字节量级，会做的只有【整串精确查】。
    Trie  ：10 个节点 × 216 字节 = 2160 字节，贵好几倍，换来前缀查询 / 补全 / 字典序遍历。
    → 值不值，取决于你到底要不要问「以 … 开头」。只要精确查就用哈希表；
      要问前缀，哈希表唯一的办法是把每个键都拿出来比一遍（第 7 幕实测 676 次比较）。

  现在故意喂非法输入（每一次都试图算出越界的 child 下标，被 word_is_valid 拦下）：
      [警告] 键是 NULL 指针，已拒绝
      [警告] 空串 "" 不插：它对应的节点是根本身，语义会混乱
      [警告] 第 0 个字符 'C' 不是小写字母：idx = 'C' - 'a' = -30，child[] 只有 26 格，会越界 → 整个串已拒绝
      [警告] 第 3 个字符 '!' 不是小写字母：idx = '!' - 'a' = -64，child[] 只有 26 格，会越界 → 整个串已拒绝
      [警告] 第 3 个字符 '7' 不是小写字母：idx = '7' - 'a' = -42，child[] 只有 26 格，会越界 → 整个串已拒绝
      [警告] 第 0 个字符 '{' 不是小写字母：idx = '{' - 'a' = 26，child[] 只有 26 格，会越界 → 整个串已拒绝
  拒绝之后树里的词数还是 5 个 —— 墙有效：写操作一个字节都没漏进去。
  只读接口同样安全（走不通就说没有，不会去解引用非法格子）：
    search("Cat")=0  starts_with("ca!")=0  count_prefix("do7")=0

  一个「看着合法但其实很伤」的输入：超长串。合法上限是 31 个字符，我造 39 个：
      [警告] 串长 39 ≥ 上限 31，已拒绝（路径缓冲区只有 32 格）
  为什么连它也要拒：路径缓冲区是栈上的 char path[32]，
  没有长度上限，DFS 往下钻就会写到缓冲区外面 —— 栈溢出/覆盖返回地址，比越界写数组更致命。
  本幕的树已 trie_free 并把指针置 NULL（ASan 会来查岗）。

第 9 幕：形状总结 + trie_free（后序递归）
----------------------------------------
  三种结构解决同一个「按键找」问题，差别就在键被怎么处理：

    数组     键 = 下标 0..n-1        → O(1)，但键必须是连号整数
    哈希表   键 = 揉成一个大整数      → O(1) 精确查；顺序信息全丢，问不了前缀
    Trie     键 = 拆成一位一位       → O(L) 精确查 + 前缀 + 补全 + 字典序；每节点 216 字节

    二叉树   键 = 比较大小一步步分左右 → O(log n) 精确查 + 范围查，前缀查不如 Trie

  主树还剩这些节点（第 6 幕删到只剩 door）：
       (root)    pass=1    end=0   
         'd'       pass=1    end=0   
           'o'       pass=1    end=0   
             'o'       pass=1    end=0   
              *'r'       pass=1    end=1     ← 完整单词 "door"
      ── 每层节点数：第0层=1 第1层=1 第2层=1 第3层=1 第4层=1 （一共 5 层：第 0 层是根，最深层 4 = 最长单词 4 个字符）

  收摊：trie_free(root) 要 free 5 个节点。
  顺序必须是【后序】—— 每层的动作是「先把 26 棵子树递归拔掉，再 free 自己」。
  为什么不能先 free 自己：孩子的地址就存在我自己的 child[] 数组里，
  free(node) 之后那块内存已经还给系统，再读 node->child[i] 就是 use-after-free；
  更糟的是它「经常看起来没事」—— glibc 只是把这块地登记成空闲，老数据还躺在原地，
  于是错误版本能跑一百次都对，某一次 malloc 复用了它，树就长出随机分支。
  已 trie_free 并置 NULL：free 次数 = 节点数 = 5，ASan 应该报 0 字节泄漏。

=== 本节结束 ===
记住三句话：
  1) pass_count 是「几个串经过我」，end_count 是「几个串在我这结束」；
     前者答「以…开头的有几个」，后者答「它本身是不是一个词」。
  2) 复杂度只看串长 L：插入/查询/删除/前缀计数都是 O(L)，和词表里有多少词无关；
     代价是每个节点 26 个指针（216 字节），绝大多数格子是 NULL —— 空间换时间。
  3) 删除要一路把 pass_count 减 1，并把 pass 归零的节点真的 free 掉；
     销毁整棵树必须后序递归 free —— 先删孩子，再删自己。

## 常见的坑

1. **用"有没有孩子"判断"是不是单词"。** 错得最普遍的一条。`car` 有孩子 `d`（card），
   它照样是词；`doo` 有孩子 `r`，它不是词。**唯一判据是 `end_count > 0`。**
2. **删除只减 `end_count`，不减 `pass_count`。** 于是 `pass` 永远归不了零，
   节点永远删不掉：词表反复增删之后**只涨不缩**，不报错、不崩溃，只是某天内存吃满。
3. **`pass_count` 减成负数。** 删一个不存在的词还硬减。
   本节的防法：`trie_delete` 动手前先 `trie_search` 确认存在（`trie.c:283`）。
   负数计数器不会立刻出事，但它让"归零判据"永远为假 —— 又是个潜伏 bug。
4. **判据写成 `end_count == 0` 就 free。** 删 `car` 时把 `ca`、`c` 一起 free 掉，
   结果 `card`、`cat` 的地址被父亲攥着 —— 直接 use-after-free。
   正确判据是 **`pass_count == 0 && end_count == 0`**（见图解第 4 小张）。
5. **free 完忘记 `return NULL` 让父亲置空格子。** 父亲的 `child[idx]` 还留着那个地址，
   下一次插入走到这一格会"以为孩子还在"直接钻进去 → use-after-free。
6. **`trie_free` 写成先序（先 `free(node)` 再递归 `child[i]`）。**
   `free` 之后 `node->child[]` 这块内存已经不属于你，再读它就是读已释放内存。
   glibc 只把地块登记成空闲、数据还躺在原地，所以**它经常"看起来没事"**，
   直到某次 `malloc` 复用那块地，你就得到一棵会随机长分支的树。
   实测：直白写法 gcc `-Wall` 就会报 `pointer used after 'free'`；藏在递归里 ASan 报
   `heap-use-after-free`。**顺序永远是：先删孩子，再删自己。**
7. **不校验字符集就 `child[*p - 'a']`。** `'C' - 'a' = -30`、`'{' - 'a' = 26`：
   越界读写 `TrieNode` 结构体外面的内存。第 8 幕把这些输入真喂进去，看 `word_is_valid` 拦下。
8. **不设串长上限，路径缓冲区就会被写爆。** 补全和打印树的缓冲区是栈上的
   `char path[TRIE_WORD_MAX]`；一个 39 字符的串能让 DFS 写到栈外 ——
   覆盖返回地址，比越界写数组更致命。所以"上限"必须在插入时就拒（第 8 幕实测）。
9. **`trie_free(root)` 之后不把 `root` 置 NULL。** 再 `trie_free` 一次 = double free，
   ASan 直接 abort（00-c-foundation 第 5 课的老朋友）。
10. **把补全结果条数和 `pass_count` 当成一个数。** 第 5 幕实测：
    `count_prefix("ca") = 4` 但只补出 3 条 —— `pass` 数的是**串**（`cat` 插了两遍算 2 个），
    补全吐的是**不同的词**（节点只有一个）。两个都对，问的是两个问题。
11. **用 Trie 当 KV 存储。** 精确查它 O(L) 比哈希表的 O(1) 慢，内存还贵 10 倍。
    Trie 的价值 100% 在"前缀"这一侧；没有前缀需求就别用它。
12. **给补全函数用全局缓冲区。** 两次调用互相踩数据（不可重入）、线程一并发就错、
    清零责任变隐形。本节把缓冲区放在函数自己的栈帧里，靠参数把地址传下去。

## 自检问题

1. `cat`、`car`、`card` 都在树里时，`c` 节点的 `pass_count` 和 `end_count` 各是多少？
   **答**：`pass=3, end=0`。三个串都从 `c` 经过；`"c"` 本身不是词所以 `end=0`。
   推论：`"c"` 是"只当过路、自己不成词"的节点，判据是 `end_count == 0`，跟它有几个孩子无关。

2. 为什么 `trie_count_prefix("ca")` 是 O(2)，而不用把 `ca` 子树走一遍？
   **答**：因为插入时每个经过的节点都被 `+1` 记过了，`ca.pass_count` 就是答案。
   这正是"用一次插入时的小代价，换掉查询时的整棵子树"。没有 `pass_count` 就得 DFS 数星号。

3. 删 `car` 之后 `card` 会受影响吗？删 `card` 之后 `car` 呢？为什么？
   **答**：都不受影响，但**要分情况**。`card` 和 `car` 共用 `c-a-r` 三格。
   删 `card`：只有末尾 `d` 那格 `pass` 归零被 free，`car` 的 `end_count` 纹丝不动。
   删 `car`：`r` 的 `pass` 从 2 变 1（`card` 还经过它）→ **节点留下**，只是 `end` 变 0。
   判据永远看 `pass_count`，不看 `end_count`。

4. `end_count` 用 `bool is_word` 不行吗？
   **答**：不行。同一个词插两遍（第 4 幕实测 `search("cat")=2`），
   删一遍后 `bool` 只能变 `false` → 词被误删；`int` 变 1 → 词还在。
   另外第 5 幕还暴露了 `pass` 与"不同词数"的差别（4 vs 3），也是 `int` 才看得见。

5. 为什么 `trie_insert` 和 `trie_delete` 要 `TrieNode **root`，而 `trie_search` 只要 `const TrieNode *`？
   **答**：因为这两个函数可能改**调用者手里那根指针**：第一次插入要创建根；
   删掉最后一个串时根自己 `pass` 归零被 free，`*root` 必须变成 NULL（第 7 幕 676 个词全删光就是这一现象）。
   只读的查询不会改结构，`const` 是承诺，编译器帮你守住。

6. `trie_free` 为什么必须后序？先序会怎样？
   **答**：孩子的地址存在**我自己**的 `child[]` 里。先 `free(node)`，那块内存就还给系统了，
   接着读 `node->child[i]` 拿孙子地址 = use-after-free。它常常"看起来没事"（glibc 只是登记空闲，
   数据还在原地），直到某次 `malloc` 复用这块地，bug 会以"树长了随机分支"的形式爆发。

7. 本节 676 个两字母词花了 148 KB，而拉链法大概 16 KB。多花的钱买到了什么？
   **答**：买到 `child[]` 的"分支查找表"，于是：前缀查询 O(L)（不用扫全表）、
   自动补全 O(结果规模)、字典序遍历免费、公共前缀自动共享内存。
   什么时候这钱白花了：你只会问"等于"，从不问"开头"。

8. 把 `child[26]` 换成"孩子链表"或"压缩 Trie"，好处和代价各是什么？
   **答**：好处是内存随**实际分支数**走（本节实测 96.2% 的格子是 NULL，能省 5~20 倍）；
   代价是取一个孩子不再是 O(1)，得在这几个孩子里线性找（或排序后二分），
   复杂度从 `O(L)` 变成 `O(L × 平均分支数)`，代码量翻倍（见 `trie.c` 第 11 节四种方案对比）。
   什么场景必须换：字符集很大（Unicode、URL 路径）、或者树很浅很稀疏。
