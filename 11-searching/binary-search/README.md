# 二分查找（binary search）

## 一句话是什么

在**已排序**的数组上，每次拿中间元素和目标比，一刀砍掉一半候选，
用 O(log n) 次比较定位一个值 —— 或者更准确地说，定位一个**边界位置**。

## 为什么必须懂它

100 万个元素，最多 20 次比较就找到（2^20 = 1048576 > 10^6）。10 亿个元素，30 次。
顺序查找要 100 万次。这不是"快一点"，是数量级。

但真正的原因比性能更重要：**二分是"单调性"这个概念的第一个载体**。
后面 AVL 树、堆、Trie、树状数组、二分答案、第 K 小，全都建立在
「有一个可以二分的单调判据」上。把二分的边界写对，本质上是在训练
「我能把不变式说清楚吗」这件事。

而这件事的 notorious 难度是有史可查的：1946 年就有论文，1962 年业界仍在传"大多数人写不对二分"，
Google 2006 年的 bug 追踪里 Java `Arrays.binarySearch` 的溢出 bug 潜伏了 9 年才被发现。
写不对的原因只有一个，就是本节要反复讲的那一条：

> **区间开闭、循环条件、`mid ± 1` 三件事必须自洽。三者不匹配就必挂。**

## 图解：两种区间，两套自洽的写法

本节只教两种写法。它们的区别**仅在区间怎么定义**，其余全是推导。

```
【写法 A：闭区间 [left, right]】—— 用来「精确找一个值」
   初始化：left = 0,       right = n - 1     ← 两端都在区间【里面】
   循环：  while (left <= right)             ← [2,2] 还有一个元素没查，必须 <=
   收缩：  left = mid + 1  /  right = mid - 1 ← mid 已经比过，可以排掉
   退出：  left > right，区间空 → 返回 -1

【写法 B：半开区间 [left, right)】—— 用来「找第一个 >= target 的位置」
   初始化：left = 0,       right = n         ← 注意是 n，不是 n-1
   循环：  while (left <  right)             ← [2,2) 是【空】区间，必须 <
   收缩：  left = mid + 1  /  right = mid    ← ★ right 不减 1！
   退出：  left == right，区间空 → left 就是答案（可能 == n）
```

盯住那处星号差异：

- A 的 `right` 住在区间**里面**。`mid` 已经比较过且不符合，可以彻底排掉 → `mid - 1`。
- B 的 `right` 住在区间**外面**。`a[mid] >= target` 时 **mid 自己就是候选答案**
  （它可能就是第一个 >= target 的位置），排掉它就丢了答案 → 只能写 `right = mid`。

混用就得到两个经典事故，第 7 幕（`--show-bug`）把它们当场跑出来：

| 混法 | 后果 |
|---|---|
| A 的 `<=` 写成 `<` | **漏查最后一个候选**：元素明明在，程序报"不存在" |
| B 的 `<` 写成 `<=`（配合 `right = mid`） | **死循环**：`left == right` 时区间本该为空，循环条件认为非空，而三个变量一个都不变 |

## 核心概念逐个拆

### 1. `bs_exact`：闭区间精确查找

找到返回下标，找不到返回 `BS_NOT_FOUND`（-1）。
有重复元素时**返回哪一个不保证**（取决于中途怎么劈的）—— 想要最左或最右，请用下面的 lower/upper。

一个值得看一眼的副产品：退出时 `left == right + 1`，
而且 `left` 正好是 upper_bound 的答案、`right` 正好是最后一个 < target 的位置。
精确查找失败时的 `left` 不是垃圾值。

### 2. `bs_lower_bound` / `bs_upper_bound`：本节真正的主角

```
lower_bound(t) = 第一个【>= t】的下标（全都 < t 时返回 n）
upper_bound(t) = 第一个【>  t】的下标（全都 <= t 时返回 n）
```

两个函数**只差一个字符**：判据从 `a[mid] < target` 变成 `a[mid] <= target`。
含义是把"等于 target"也算成"太小，往右走"，于是留下的是第一个严格大于的位置。

为什么它们比"返回 -1"高明：**永远有一个合法返回值（0..n），没有失败分支**。
于是"忘记判 -1 就直接用下标"这类 bug 从源头消失。

### 3. 有了两个边界，其他全是减法

```
x 存在吗        → lower(x) < n 且 a[lower(x)] == x
x 出现几次      → upper(x) - lower(x)          （不存在时两者相等，自然得 0）
< x 的有几个    → lower(x)                     （下标本身就是个数！）
<= x 的有几个   → upper(x)
> x 的有几个    → n - upper(x)
在 x 左边插哪   → lower(x)（插在相同元素之前，保持稳定）
```

这就是 C++ 标准库**只给 lower_bound/upper_bound、不给"二分查找"**的原因：
边界位置比"在不在"有用得多，而且顺手推出计数和插入位置。

第 4 幕把这张表用真实的 12 元素数组整个跑了一遍：

```
  target | lower_bound | upper_bound | 存在? | 出现次数 | <target | <=target | >target
      0 |           0 |           0 |   否 |        0 |       0 |        0 |      12
      3 |           1 |           4 |   是 |        3 |       1 |        4 |       8
      4 |           4 |           4 |   否 |        0 |       4 |        4 |       8
      7 |           5 |           7 |   是 |        2 |       5 |        7 |       5
     11 |           8 |          11 |   是 |        3 |       8 |       11 |       1
     13 |          11 |          12 |   是 |        1 |      11 |       12 |       0
     14 |          12 |          12 |   否 |        0 |      12 |       12 |       0
```

（示例数组是 `1 3 3 3 5 7 7 9 11 11 11 13`，**故意做成有重复**：
无重复时 lower 和 upper 只差 1，看不出"下界相同、上界不同"这件事。）

看 target=4 那行：不存在，lower == upper == 4，而这个 4 正是"把 4 插进去还能保持有序、
最靠左的插槽"。**找不到时它给的是一个有用的位置，而不是一个需要你特判的失败码。**

### 4. `mid` 的写法：加法会溢出

`int mid = (left + right) / 2;` 是**错的**，虽然平时看不出问题。
第 6 幕用 `left = INT_MAX-3, right = INT_MAX` 实测：

```
  (left + right)             = 溢出后的值 -5   ← 已经是垃圾
  错误写法 (left+right)/2    = -2
  正确写法 left+(right-left)/2 = 2147483645   ← 落在区间里，这才是对的
```

**永远写 `left + (right - left) / 2`：先减后加，不可能溢出。**
（严格说有符号溢出是 UB，编译器可能给你任何结果，包括看起来正确的那个 ——
所以"偶尔能用"绝不是理由。）

### 5. 二分不只是"在数组里找数"：二分答案

二分的本质是：**答案落在一个可枚举的取值区间 `[lo, hi]` 上，且存在一个单调的「可行/不可行」判据**。
这时"找数"就变成"找第一个可行的取值"。

第 5 幕的例子是不开数学库求 `floor(sqrt(x))`，判据换成 `mid*mid <= x`：

```
          40 |           6 | 36 <= 40 < 49  ✓
         100 |          10 | 100 <= 100 < 121  ✓
  2147395600 |       46340 | 2147395600 <= 2147395600 < 2147488281  ✓
```

把 `bs_sqrt_floor` 和 `bs_lower_bound` 的代码并排看，结构完全相同：
区间 + 中点 + 单调判据 + 收缩。区别只有判据从 `a[mid] < target` 换成了 `mid*mid <= x`。
**"二分答案"这个套路的全部秘密就在这里**，`kth-smallest` 那节的解法三用的正是它。

⚠ 这一节里还藏着一个溢出：`mid*mid` 在 mid 接近 x 时必然爆 int，
所以判据必须写成 `long long`。它和 `(left+right)` 溢出是同一族 bug。

## 复杂度

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `bs_exact` | O(log n) | 第 1 幕实测：1024 个元素最多 11 次比较 |
| `bs_lower_bound` / `bs_upper_bound` | O(log n) | 同上 |
| `bs_count` | O(log n) | 两次二分 |
| `bs_count_less` 等 | O(log n) | 一次二分 |
| 空间 | **O(1)** | 只用 left/right/mid 三个变量 |

对照表（1024 个元素，`big[i] = i*3`）：

```
  target   存在?   顺序查找比较次数   二分比较次数
    1500   是                501             10
    3069   是               1024             11
    3072   否               1024             11
```

★ 查**不存在**的值时顺序查找必须走完全程 1024 次，二分照样只花十来次 ——
二分的优势在"找不到"的时候最明显。

```
       掐断时 left=0 right=0（区间 [0,0) 其实是【空】的，循环条件却不肯停）

```

真把程序挂住的话，你只能靠 Ctrl-C 收拾，而且 ASan 也帮不了你。

## 常见的坑

1. **三个条件不自洽。** 见上面的对照表，这是二分唯一真正的难点。
   对策：动手前先写下"我用闭区间还是半开区间"，其余三行照抄推导，不要凭手感。
2. **拿无序数组跑二分。** 结果**错误但不崩溃** —— 最难查的那种 bug（程序照常跑完，只是答案是错的）。
   本节给了 `bs_check_sorted` 专门自检。
3. **`mid = (left + right) / 2` 溢出。** 第 6 幕实测。永远写 `left + (right - left) / 2`。
4. **`right` 初始值写错。** 闭区间是 `n - 1`，半开区间是 `n`。抄混了整张表全错。
5. **`bs_contains` 里先读 `a[i]` 再判 `i < n`。** 当 target 比所有元素都大时 `i == n`，
   `a[n]` 直接越界。顺序必须是"先判范围再取下标"。
6. **重复元素用精确查找取"第一个"。** `bs_exact` 命中就立刻返回，返回哪个不保证。
   要最左用 lower_bound，要最右用 `upper_bound - 1`。
7. **以为 lower 和 upper 差 1。** 只有元素唯一时才是。有重复时差的是重复个数。
8. **`while (left <= right)` + `right = mid`。** 看着只是差一个减 1，实际是死循环 —— 第 7 幕现场。
9. **判据里漏了 `long long`。** 二分答案（如 `mid*mid <= x`）的算术比下标更容易溢出。

2. 半开区间版本为什么 `right = mid` 不能写成 `right = mid - 1`？举一个会丢答案的例子。
3. `lower_bound(4) == upper_bound(4)` 说明什么？这个相等的值有什么用途？
4. 「小于 target 的元素个数」为什么不等于 `bs_exact` 的结果加一？它等于什么？
