# 动态数组 dynamic-array —— 把上一节那堵墙拆掉

> 上一节静态数组装满 8 个就只能失败。这一节用 `malloc` / `realloc` 在堆上租格子，
> 容量可以一路长大，代价是多了两个必须自己管的东西：**账面（size / capacity）**和**归还（free）**。
> 本节最硬的两个结论 —— 翻倍为什么摊还是 O(1)、1/2 阈值为什么会抖动 —— 都是**真跑出来的数字**，不是口号。

---

## 一句话是什么

动态数组 = **堆上一排可以换大小的连续格子** + **两个分开记的数字**：

```
capacity = 现在【租了】几格（房子有几间）
size     = 现在【住了】几个人（有几个真实元素）
永远满足 size <= capacity
```

尾部追加时，有空位就只写一个值（O(1)）；空位用完就 `realloc` 一块更大的（新容量 = 旧容量 × 2），把老元素
整排抄过去。多租的那些空位就是「下次插入不用再搬家」的预付定金 —— 整个 vector 的性能秘密全在
`capacity - size` 这个差值里。静态数组里两个数字被迫相等，所以只要 `length` 一个字段；这里必须分成两个。

---

## 为什么需要它（不用它会怎样）

**不用它会怎样：长度只能靠猜或靠改代码。** 上一节的天花板是三行代码：
`[失败] 已满（8/8），静态数组不会自己变大`。数据量是运行时才知道的（读文件、读用户输入、长度不确定），
静态数组只有两条路：把 `#define` 改成「够大就行」→ 99% 的时间在浪费内存、剩下 1% 的时间溢出；或者每次
装不下就自己写一遍换内存的代码 —— 后者正是本节要帮你封装掉的东西。

**它换来的三件事，每件都有对应的代价：**

| 换来 | 代价（本节全部实测过） |
|---|---|
| 容量能长大 | 每次扩可能要 `realloc` 搬家，老指针当场作废 |
| 空表零成本（`init(0)` 懒启动） | 堆内存必须自己 `free`，忘一次漏一次 |
| 随机访问仍是 O(1)（格子照样连续） | 中间插入/删除照样要挪格子，O(n) 一点没变 |

最后一行最容易被骗：**动态数组只解决「装不下」，没解决「挪格子」。** 第 4 幕往 `index=1`
插一个元素照样挪了 4 格；要「不挪格子的增删」得去看 `02-linked-list/`。

## 图解（ASCII 图 + 内存/结构布局）

### 1. 两本账：结构体在栈上，仓库在堆上

```
  DynArray v   ← main 的局部变量，72 字节的「账本」住在栈上
  ┌──────────────┬───────┬──────────┬─────────────────────────────┬────────┬──────────┐
  │ int *data(8) │ size  │ capacity │ base/grow/shrink/policy …40B │ 2×u64  │ 抄动账本 │
  └──────┬───────┴───────┴──────────┴─────────────────────────────┴────────┴──────────┘
         │ 只存一个地址
         ↓ 堆上那排连续格子（malloc/realloc 租来的，容量可变）
   下标  0      1      2      3      4      5     …    15
        ┌──────┬──────┬──────┬──────┬──────┬──────┬───┬──────┐
        │  10  │  20  │  30  │-2003 │      │      │ … │      │
        └──────┴──────┴──────┴──────┴──────┴──────┴───┴──────┘
         └── size=3：元素区 ──┘└──────── capacity=4 起全是空位（残留垃圾值）────┘
                                     ↑ 第 3 格 -2003 是涂过的垃圾：格子是真的，值不是元素
```

第 1 幕那句「**size=3 是分界线，不是 capacity**」就是本节的核心图景：`pop` 之后格子里的值**还在**，
只是不再被算作元素 —— 所以元素个数必须单独记账，不能靠格子内容猜。越界事故几乎都出在这两个数字被搞混。

### 2. `realloc` 的三种结局（第 2 幕两种都真发生了）

```
A 原地扩大：后面正好有空地              B 整块搬家：后面被占了                C 失败：找不齐
 [10 20 30 40 ▢ ▢]                      [10 20 30 40] ← 旧块当场 free          返回 NULL
 ↑ 地址不变，一个字节都不抄              [10 20 30 40 50 60 70 80] ← 新地址     ↓
                                       realloc 已帮你把老数据抄过去            原内存原封不动、仍然有效
 本文那趟实测：扩容第 2 次 8→16 是 A        旧指针再读 = 悬空指针                 → 账面一个字都不改
 扩容第 1 次 4→8 就是 B（0x…020→0x…340）
```

三种结局**哪一种发生不由你选**，所以只有一条写法站得住：`moved = realloc(a->data, n)` 用临时指针接住、
判空之后才写回、**失败时保持原状**。

### 3. 为什么翻倍：贵动作被后面的空位摊掉

```
翻倍 4→8→16→32→64：  每次扩容后要再 push 2^(k-1) 步才撞上下一次扩容
   抄动总量 = 4+8+16+32 = 60 < 2×40        → 摊到每次 push 是常数 → 摊还 O(1)
+1   4→5→6→…→40：     每 push 一个都扩一次
   抄动总量 = 4+5+…+39 = 774 ≈ 40²/2       → 整体退化 O(n²)
第 3 幕两组数字都是真跑的：扩容 4 次 vs 36 次，抄动 60 个 vs 774 个。
```

### 4. 为什么缩容要等到 1/4：两条线必须隔开

```
阈值画在 1/2（坏）                       阈值画在 1/4（默认）
capacity 16 ──┬ 扩容线（size=16 满）     capacity 16 ┬── 扩容线（size=16）
              ┬ 缩容线（size<=8 砍）                │
   → 砍成 8，size=8 = 正好满                        缩容线 ┴ size<=4 才砍
   → push 1 个：立刻扩容回 16                       中间隔着 12 格缓冲带
   → pop  1 个：立刻缩容回 8                        pop 到 4 砍成 8，size=4 只占一半
   ⇒ pop/push 一来一回 = 每步搬家一次               要连 push 8 个才碰到扩容线
   第 6 幕实测：20 轮 = 40 次 realloc、抄 320 个     ⇒ 20 轮 realloc = 0 次
```

一句话：**扩容线和缩容线必须隔开一段缓冲带**。这条规矩不只属于 vector —— git 的 pack、JVM 的堆、
内存分配器全都一样（`.c` 注释里也是这么写的）。

## 逐个操作拆解（对应 dynamic-array.c 里每个函数）

### `dynarray_grow_one_step(a)` / `dynarray_reserve(a, extra)` —— 本节的心脏

新容量 = 旧容量 × `grow_multiplier` + `grow_increment`（默认 2/0 就是翻倍；旧容量为 0 时直接给
`DYNARRAY_MIN_CAPACITY` 格）。`reserve` 就是一句 `while (capacity < size + extra) grow_one_step()`：
**空位够用就一个字节都不碰**，这就是「空位」存在的全部理由；循环次数本身就是策略的差距 —— 翻倍通常
一次就够，+1 要转很多圈。`grow_one_step` 里四个防御动作，每一个都在挡真实的事故：

- **先把旧地址存成 `uintptr_t`**（纯整数）再和返回值比 —— 搬家后旧块已被 `free`，拿旧 `int *` 去打印或
  比较会吃「使用已释放内存」的警告；存成整数只比数值，从不解引用。
- **`int *moved = realloc(...)`，判空之后才写回 `a->data`**。裸写 `a->data = realloc(a->data, n)`，结局 C
  时 NULL 覆盖了 `a->data`，**原来那块内存还活着，但再也没人能找到它** —— 泄漏 + 悬垂一步到位。所以失败
  时本函数一行账面都不改，返回 false，调用者继续用旧数据。
- **防呆 `if (new_capacity <= old_capacity) new_capacity = old_capacity + 1;`** —— 策略字段万一被写成
  `0 * capacity + 0` 这种退化组合，`reserve` 的 while 会原地打转、程序卡死。防御要防的就是自己的公式。
- **新扩的格子立刻由私有 `poison_spare_cells` 涂成 `-(2000+i)`** —— 未初始化内存读它是未定义行为；工程
  代码不需要涂（真 vector 要么不管、要么默认构造 0），这里涂是为了让「元素区 / 空位区」的边界肉眼可辨。

两本账同时记：`copy_total` 按「每次都搬家」算（摊还分析的**上界**，与平台 realloc 聪不聪明无关），
`copy_moved_total` 只在地址真变了才累加（**实测**）—— 第 2 幕的 `最坏12/实测4` 就是这个差值。

### `should_shrink` / `dynarray_maybe_shrink` —— 1/4 阈值 + 三道地板

判定式写成不带除法、不带小数的整数比较：`size * shrink_denominator <= capacity * shrink_numerator`
（默认 1/4 即 `size*4 <= capacity*1`）。不写 `size <= capacity / 4` 是因为整数除法向下取整，边界差一格
就抖一次；用 `<=` 而不是 `<` 是让「正好压线」也算数，讲缓冲带时不必反复解释那一格。砍之前有三道地板：
不低于 `base_capacity`（否则空表在 0 格和 4 格之间反复 malloc/free）、必须装得下现有元素（砍完放不下
就是把数据挤没了）、`new >= old` 就干脆不砍。缩容失败（NULL）也什么都不改 —— 多占点内存而已。

### `dynarray_init(a, init_capacity)` / `dynarray_destroy(a)`

`init` 传 0 或负数 = **懒启动**：`data=NULL, capacity=0`，一块内存都不占，第一次 `push_back` 再现场租
`MIN_CAPACITY` 格（第 7 幕实测 `realloc` 旧地址就是 `0x0`，因为 `realloc(NULL, n)` 等价于 `malloc(n)`）；
`malloc` 失败时结构体保持「全 0 + data=NULL」的安全状态，照常能 `destroy`。
`destroy` 是三件事，顺序不能反：**`free(data)` → `data = NULL` → `size = capacity = 0`**。不置空就留着
「一个作废地址 + 两个看起来很正常的数字」，下次误用就是「合法的调用 + 悬空指针」（ASan 报
`heap-use-after-free`）；置零后任何操作都先撞上「空表」判断，当场暴露，而且 destroy 变幂等。
`.c` 里还有句诚实的话：destroy 之后再 `push_back`，表会因为 `realloc(NULL, n)` 「复活」成新表 ——
语法合法，但几乎一定是逻辑错误。

### 只读三档：`at` / `get` / `find`

`at` 是检查版：越界返回 false，`*value_out` 保持原值；先判 `data == NULL` 再判 index，因为 `capacity == 0` 的
懒启动空表哪怕 index=0 也绝不能解引用。`get` 是**不设防**版，函数体里一个 `if` 都没有，就是 `a->data[index]`
包一层皮 —— 留它是为了让你亲手摸到「语言层不检查」和「接口层检查」这两档的界线（C++ vector 的
`operator[]` 与 `at()` 正是这个分工）。`find` 线性扫 O(n)，找不到返回 -1。另注意 `dynarray_capacity(&v)`
**要传结构体**，而上一节 `static_array_capacity(void)` 不收参数 —— 每个表容量可以不一样，这就是「动态」的照面。

### 增删四个：`push_back` / `pop_back` / `insert_at` / `remove_at`

`push_back` 两条路径：A（绝大多数）写一个值 + `size++`，O(1)，一个字节都不搬；B（偶尔）先 `reserve` 扩容，
可能搬家 O(n)，再走 A；B 的成本摊到 A 上就是「摊还 O(1)」。写值必须在 `size++` 之前，反了会让 `size`
指着个没赋值的格子。`pop_back` 是 O(1)：`size--` 之后格子里的值**还在**，顺手做一次缩容检查（缩容只在删除类
操作后考虑，插入后再缩毫无意义）。`insert_at` / `remove_at` = 可能的扩容 O(n) + 后半排 `memmove` O(n) = **O(n)**。

### 教学专用：`set_growth_policy` / `set_shrink_policy` + 三个打印函数

两个 `set_*_policy` 在正式代码里绝对不需要，唯一理由是让 `main` **真的跑一遍**「+1 扩容」和「1/2 就缩」两种坏
策略，把 realloc 次数打印出来对比。参数都是普通 `int`，没有函数指针、没有泛型 —— 本项目一律如此。
`dynarray_print` 那一行就是体检报告：`size / capacity / data 地址 / 扩容次数(搬家次数) / 缩容次数 / 两本抄动账`。
`print_memory_map` 只画前 `max_cells` 格（容量会涨到几百几千，全画没法看），但账面报真数 —— **省的是打印，不省
事实**；`print_grow_report` 把「这一路搬了几回家」总结成「平均每个元素分摊 N 次抄动」，摊还 O(1) 就是这么变成账单的。

## 复杂度一览

| 操作 | 时间 | 为什么 |
|---|---|---|
| 按下标读（`at` / `get`）、`size` / `capacity` / `is_empty` | O(1) | 格子照样连续 `data + i*sizeof(int)`；后三个只读字段 |
| `find` 按值 | O(n) | 不排序只能线性扫 |
| `push_back` | **摊还 O(1)**，单次最坏 O(n) | 有空位只赋值；撞线才 realloc + 抄 |
| `pop_back` | O(1) | `size--`，不挪格子；偶尔触发缩容 |
| `insert_at` / `remove_at` | **O(n)** | 可能扩容 + 后半排 memmove，动态化救不了 |
| `grow_one_step` / `maybe_shrink` | O(n)（搬家）/ O(1)（原地） | 哪种结局**不由你选** |
| `init` / `destroy` | O(1) | 一次 malloc / 一次 free + 账面归零；懒启动则 O(0) |
| 连续 n 次 push 总抄动 | < 2n（翻倍）/ ≈ n²/2（+1） | 第 3 幕实测 60 vs 774 |
| 空间 | capacity 个格子，最坏约 2×size | 空位是定金，不是浪费 |

★ 上面这一 fence 里凡带「搬家」二字的读数（`扩容4次(搬家2)`、表里「真搬家」那一列、末尾「搬家实况：22 次里真搬家 1 次」那行）
**由堆当时的状态决定，换一趟跑就会变**——本机今天重跑给的是「搬家 4 / 真搬家 22 / 20」，一个字节都没错，只是运气不同。
本节真正的判据只由公式决定、重跑必得同一个数：扩容次数 **4 vs 36**、抄动总量 **60 vs 774**、平均 **1.50 vs 19.35**。

逐段读：**第一段**（第 1、2 幕）把两本账画在同一行 `size=3 / capacity=4`，那句 `边界: 第 3 格起就是空位`
是本节最该形成的直觉；两次扩容的对照更有价值：`0x…020 → 0x…340` 是**真搬家**（`data=` 跟着变），
`340 → 340` 是**原地扩大**，于是账面出现 `最坏12/实测4` —— 公式按「每次都搬家」记 4+8，实际只抄过一次。
**第二段**（第 3 幕）是摊还的实弹：同样 push 40 个，翻倍组扩 4 次抄 60 个（60 < 2×40 就是 `< 2n` 那本账），
+1 组扩 36 次抄 774 个，1.50 对 19.35；两句「这就是摊还 O(1)」是同一个函数打的，+1 组那句套话不成立。
**第三段**（第 5 幕）是边界证据：`17*4=68 > 64` 所以**不砍**，`16*4=64 <= 64` 压线才砍 —— 有空位不等于该
缩容；缩容日志地址全是 `2640 → 2640`（缩小几乎总能原地完成），最后停在 `capacity=4 = base_capacity`，
不会砍到 0，否则「清空再填满」又是一轮抖动。**第四段**（第 6 幕）是抖动实测：同样的动作，1/4 组 realloc
**0 次**，1/2 组 **40 次**、抄 320 个；40 次里真搬家只 1 次 —— 搬家少不代表没事，40 次系统调用已经把
O(1) 换成了 O(n) 的账。**最后四行**：懒启动空表 `data=(nil)`，第一次扩容旧地址就是 `0x0`；destroy 打完
置空三连，还提醒「之后再 push 会让表复活」。其余输出见第 4、8 幕：插入挪 4 格、`at(100)` 被拦、
`[size, capacity)` 读到垃圾不报错而 `>= capacity` 才 ASan `heap-buffer-overflow`；默认运行必须 0 泄漏。

## 常见的坑

1. **裸写 `a->data = realloc(a->data, n)`，不接失败分支。**
   错法：`realloc` 失败返回 NULL 覆盖掉 `a->data`，原来那块**还活着却再也找不到** —— 泄漏，
   后续操作全在 NULL 上解引用。对法：`int *moved = realloc(...)`，判空之后才写回；失败时账面
   一行不改（`00-c-foundation/dynamic-memory` 讲过同一件事，这里变成结构体内部的规矩）。
2. **搬家之后继续用旧指针。**
   错法：扩容前存了 `int *p = v.data;` 或 `&v.data[3]`，扩容后继续 `*p` —— 结局 B 时旧块已被
   `realloc` 当场 free，读它是 `heap-use-after-free`。对法：只认现取的 `v.data`；想留旧地址做事后
   对比就存成 `uintptr_t` 纯数值，只看不碰。
3. **把 `capacity` 当元素上界用。**
   错法：`for (i = 0; i < dynarray_capacity(&v); i++) sum += dynarray_get(&v, i);` → 把 `-2003`
   这类空位垃圾当数据算进去；或 `i > capacity` 越出堆块，ASan 报 `heap-buffer-overflow`。
   对法：循环上界一律 `size`；要读空位就明说自己在读空位 —— 否则就是在读运气。
4. **`free` 完不置 NULL、不归零账面。**
   错法：`free(a->data);` 之后结构体留着 `data=旧地址, size=9, capacity=16`，「数字看着一切正常」，
   下次调用照样通过检查。对法：`free` → `data = NULL` → `size = capacity = 0` 三件套；置 NULL 还顺带
   挡掉 double free（`free(NULL)` 是合法空操作），destroy 也因此幂等。
5. **缩容阈值画在 1/2。**
   错法：`size <= capacity/2` 就砍一半 → 砍完正好满，pop/push 一来一回每步都 realloc（第 6 幕 40 次）。
   对法：默认 1/4 才砍，且绝不砍到 `base_capacity` 以下；砍完 size 只占新容量一半，缓冲带摊平成本。
6. **阈值判定用整数除法。**
   错法：`size <= capacity / 4` —— 向下取整，边界差一格就抖一次，`capacity=6` 之类行为反直觉。
   对法：写成乘法 `size * 4 <= capacity * 1`（`.c` 里还用 `long long` 乘，防大容量时溢出）。
7. **以为动态化解决了插入删除。**
   错法：拿动态数组在头部反复 `insert_at`，性能比静态数组还差（多一次扩容）。
   对法：`insert_at` 就是 O(n)，要频繁中间/头部增删就换 `02-linked-list/` 或别的结构。
8. **忘了 destroy，或者把「pop 到空」当成归还内存。**
   错法：函数退出前不 destroy → 漏一整块 capacity（第 3 幕那张翻倍表漏掉就是 256 字节）。
   对法：谁 `init` 谁 `destroy`，写在同一个作用域里；`size` 弹成 0 时 `capacity` 仍是 4，
   真要彻底归还只能 destroy。

## 自检问题

1. 为什么必须两个字段 `size` 和 `capacity`？静态数组为什么一个 `length` 就够？
   **答：** 静态数组里两者被迫相等；动态数组故意让 capacity 更大，差值是「下次插入不用搬家」的定金，而 pop 之后格子里的值还在，只能靠 size 划界。
2. `push_back` 单次最坏是 O(n)，为什么说它是 O(1)？本节哪两个数字证明的？
   **答：** 摊还 —— 贵动作（realloc + 整排抄）被后面一大串免费空位摊掉。翻倍组 push 40 个：扩容 4 次、抄 60 个 < 2×40，平均 1.50 次；+1 组扩容 36 次、抄 774 个，平均 19.35 次 → O(n²)。
3. `realloc` 失败时原内存还在吗？本节代码怎么处理？
   **答：** 在，且完全有效（容量还是老值）。`grow_one_step` 判空后返回 false 并且账面一个字都不改，调用者继续用旧数据 —— 这就是不能用返回值直接覆盖自己的原因。
4. 扩容后 `data` 地址变了，谁会受害？
   **答：** 任何提前抄走旧地址的东西：`int *p = v.data`、`&v.data[i]`、迭代器、别的结构体里的备份指针。第 2 幕第一次扩容 0x…020→0x…340 之后旧地址一律作废。
5. 为什么缩容要等 1/4 而不是 1/2？为什么不能砍到 0？
   **答：** 1/2 时砍完正好满，pop/push 每步都 realloc（实测 20 轮 40 次）；1/4 留出一条缓冲带。砍到 0 会让「清空再填满」在 0 格和 MIN 格之间反复 malloc/free，所以 `base_capacity` 是地板。
6. `at` 和 `get` 为什么要同时存在？
   **答：** 两档：`at` 安全检查、越界返回 false（默认走它）；`get` 不设防、用于下标已由程序保证的内层循环，省掉每次比较。C++ vector 的 `at()` 与 `operator[]` 就是这个分工。
7. `init(0)` 的表在第一次 `push_back` 之前占多少堆内存？`destroy` 之后再 `push_back` 会怎样？
   **答：** 0 字节（`data=NULL, capacity=0`，第 7 幕实测）。之后再 push 会因为 `realloc(NULL,n)` 等价 `malloc(n)` 而让表「复活」成新表 —— 语法合法，但几乎一定是逻辑错误。
