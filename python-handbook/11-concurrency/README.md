## 第 00 节 · 本章在讲什么：四种写法换的不是并行度，是谁在什么时候让出

「Python 有 GIL，所以不能并发」——这句话本章要当场拆成两半。
前半句是真的：这台机器上，同一时刻只有一个线程在执行 Python 字节码。
后半句是错的：本章会量出「等待时 GIL 当场撒手」「一个线程死循环时别的线程照样推进」
「四个线程真能同时挂在等待里」三件事，全部是屏幕上跑出来的布尔值。

一句话版本，四条主线（屏上每节末尾那句 `主线①/②/③/④` 指的是同一套编号）：

> **主线① GIL 是「一次只让一个线程跑字节码」的锁，不是「不能并发」：等待时它放手，算死时它收税。**
> 它锁的对象是**一张执行票**，颗粒度细到单条字节码（第 02 节第 2 格数出来了：一行 `box["n"] += 1`
> 翻成 13 条字节码）。所以「睡觉、等管道、等 socket」这些**不在执行字节码**的时刻，票当场交出去；
> 而「对几百万个整数求和」这种一路都在执行字节码的活，四个线程只是排四个队。
>
> **主线② `threading` / `multiprocessing` / `asyncio` / `concurrent.futures` 换的不是并行度，
> 是谁在什么时候让出。** 线程：被抢占 + 在 IO 等待时主动让；协程：**只在 `await` 处让**，
> 不让就整段霸住循环；进程：压根没有「让」这件事，代价是每份活得 pickle 进出、还得付一笔启动税
> （第 09、10、13 节）。选型的判据只有一句：**你的时间花在等，还是花在算**。
>
> **主线③ 本机 3.14 的默认 start method 是 `forkserver`，而它会重新 import 你的主模块。**
> 没有 `if __name__ == "__main__":` 守卫的脚本被**整份重跑**一遍 —— 这一格不是警告文案，
> 是当场炸出来的 `RuntimeError` 原文 + 退出码 1（第 06 节第 2 格）。
> 更反直觉的是它的兄弟格：只是**问了一句** `get_start_method()`，默认就再也 `set` 不动了（第 07 节第 5 格）。
>
> **主线④ 「有 GIL」不等于「线程安全」，「`await` 了」不等于「并发」。**
> 丢更新三联（纯 `+=` 本机一条不丢 / 读→让出→写结构性必丢 / 加锁又不丢，第 03 节第 5~7 格）
> 证明前者；`time.sleep` 把整个事件循环冻住、那一刻 ticker 一拍都没跳（第 09 节第 4 格）证明后者。

## 第 01 节 · 地板：这台机器的解释器到底是怎么并发它的

这一节不引任何外部资料，只把本章后面每一个判定都站在上面的那五行打印出来。
屏幕上第一条命令就是一句 `python3 -c`，五个 `print`，五行读数 —— 它是本章唯一一次
「先把尺亮出来，再谈结论」。

```
$ python3 -c "

print(\"sys._is_gil_enabled() →\", sys._is_gil_enabled(), \"｜ 编译期 Py_GIL_DISABLED →\", sysconfig.get_config_var(\"Py_GIL_DISABLED\"))

print(\"multiprocessing 全部 start method →\", mp.get_all_start_methods(), \"｜ 默认 →\", mp.get_start_method())
```

第三行是整章的地基：**`True` 和 `0` 是两个不同的问题**。
`sys._is_gil_enabled()` 问的是「此刻这把锁开着吗」，答案是 `True`；
`sysconfig.get_config_var("Py_GIL_DISABLED")` 问的是「编译这版解释器时有没有把 GIL 编掉」，
答案本机当场印的是 **`0`**（不是 `None`，也不是缺项）。
`0` 的意思是「这个开关存在，并且关着」——也就是**带着 GIL 编的**。
凡是见过「`None` 就表示带着 GIL」那种写法的读者，请以本机这一行为准：
本章只说「非 1（本机这个值是 0）」，不说它印 `None`。

第四行给了本章的算术底色：`os.cpu_count()` 是 4，`sched_getaffinity` 也是 4，
两者当场相等 —— 所以本章能说「账面核数和进程能问到的核数这一致」，
但**不能说**「4 颗核就等于 4 倍速」，那是第 07 节第 8 格和第 13 节要各自否掉的东西。
第五行是主线③ 的起点：本机可选的三种 start method 排成
`['forkserver', 'fork', 'spawn']`，`forkserver` 排在**第一位**，默认值也当场是 `forkserver`。
这一句和 `sys.getswitchinterval() → 0.005` 一起，是后面「换手节拍」与「孩子进程怎么生出来」两格的尺。

地板的第二块，是把「退路」一条条堵死。这一步必须做，否则本章后面每格都会被读成

## 第 02 节 · a 篇完整跑：GIL 到底是什么 —— 身份、粒度、什么时候放手

这一篇是主线① 的正文。屏幕上在跑 `a_gil_identity.py` 之前，先把「这一节要盯哪三格」写在屏上：

```
══════ 第 2 节 a 篇：GIL 到底是什么 —— 身份、粒度、什么时候放手 ═══════════════════════════════
主线① 的现场。屏幕上要盯三格：第 2 格「GIL 的粒度比你的语句细得多」（字节码条数）、
第 4 格「等待时它放手」（主线程睡在自己的 Lock 上，旁观线程一路推进）、
第 6 格「GIL 管执行权，Lock 管你的临界区」—— 有 GIL ≠ 互斥，这是主线④的前半。
```

三格分别对应主线① 的三句话：**粒度**（比你的语句细）、**放手**（等待时交票）、**边界**（GIL 管执行权，
不管你的临界区）。下面逐格看。

这一格十条判据全 `[成立]`，但它真正值钱的是**把退路堵死**这件事：


**二、`list.append` 和 `+=` 不是同一族。**

**三、跨进程也是同一套纪律，但本机给不出稳定证据。**

这段是本格最该记住的东西：**共享内存段的无锁 `+=` 在本机时好时坏**，
所以它靠机器忙不忙，写不成一条能复现的判据 —— 屏幕上只留下「加锁之后 `.value == 8` → `True`」这一条。

## 第 08 节 · 矩阵格：父进程此刻的内存，孩子到底拿不拿得到

这一节合并 `c` 篇（第 4、6 格）与 `e` 篇（第 3 格）三处读数，回答的是同一句常被写错的话：
「模块顶层的变量，子进程当然看得见」。三处的措辞不同、工具不同，但屏幕上给的是同一族结构量。

下面三块并排是屏幕上原样摘出的三处读数（出处：c 篇第 4 格 282-284 行、c 篇第 6 格 317-319 行、
e 篇第 3 格 472-476 行），本章一字没改，措辞不同是因为三格问的不是同一件东西：

```
  │ fork → FORK name=__main__ mem=3 argv=guarded_child.py
  │ spawn → SPAWN name=__mp_main__ mem=0 argv=guarded_child.py
  │ forkserver → FORKSERVER name=__mp_main__ mem=0 argv=guarded_child.py
```

```
  [尺子能响] 「每个孩子各自数到的长度」这条判据会不会恒真（先故意按 [1,2,3,4] 去对）：故意按 [1, 2, 3, 4] 去对，实测 [1, 1, 1, 1] 对不上
  [成立] 4 个任务各自 append 一次，孩子数到的都是 1（每个都是新副本）：实测 [1, 1, 1, 1] ｜ 预期 [1, 1, 1, 1]
  [成立] 父进程这份模块级列表的长度：孩子改了 4 次，这边还是：实测 0 ｜ 预期 0
```

```
  [成立] 冷池跑一份「立刻返回」的空活，比主进程自己跑贵 10 倍以上吗：实测 True ｜ 预期 True
  [成立] 池热了之后，同一份空活还是比主进程自己跑贵吗：实测 True ｜ 预期 True
  [成立] worker 里的 __name__ 是什么（它把主模块当 __mp_main__ 重新 import 了一份）：实测 '__mp_main__' ｜ 预期 '__mp_main__'
  [成立] worker 看得见主进程后来设的那个模块级标记吗：实测 False ｜ 预期 False
  [成立] 同一个函数在主进程里调用看得见吗（对照）：实测 True ｜ 预期 True
```

三块合起来的读法：

**一、方法决定「有没有复印件」。** 第 07 节第 4 格那三行里，`fork` 报 `mem=3`、
`spawn` 与 `forkserver` 报 `mem=0` —— 同一个 `argv`、同一份脚本，唯一的差别就是继承不继承此刻内存。
而本机默认是那一路 `mem=0` 的。
**二、不共享不是「看不见」，是「各拿一份复印件」。** c 第 6 格那组 `[1, 1, 1, 1]` / `0` 是最容易被读错的：
孩子**看得见**那个列表（能 append、能数到长度 1），只是它改的是自己那份；
父进程这份长度仍是 `0`。所以「看不见」和「看见了但不共享」是两件事，
屏幕上量的是后者（长度这个结构量），措辞却是「每个都是新副本」。
**三、进程池里那条 `__mp_main__` 是同一件事的另一面。** e 第 3 格的三条判据
（`worker 里的 __name__ 是什么` → `'__mp_main__'`、
`worker 看得见主进程后来设的那个模块级标记吗` → `False`、
`同一个函数在主进程里调用看得见吗（对照）` → `True`）
把「重新 import 一份」这个动作的**后果**量了出来：worker 的模块里只有 import 那一刻就存在的东西，
主进程后来设的标记它没有。这正是 c 第 3 格那条 `AttributeError`（藏在守卫里的函数找不到）的同一族事故。
**四、这条边界的代价是「启动税」。** e 第 3 格前两条判据（冷池一份立刻返回的空活比主进程自己跑
贵 10 倍以上 → `True`、池热了之后同一份空活还是比主进程自己跑贵 → `True`）
说的都是「每个 worker 都要重跑一遍主模块的 import」这件事 —— 活拆得太细，进程池是倒亏的。

★ 本章**没**在这三处给任何时长读数：「贵 10 倍以上」是比值布尔，
「mem=3 / mem=0」是列表长度，`'__mp_main__'` 是名字。
判据形状只有这三种，是因为它们在本机可复现；「冷池比热池慢多少」那种数在本机每跑必变，
所以连屏幕都不许上（见第 14 节那道扫描器）。

## 第 09 节 · d 篇完整跑：协程不是自动并发 —— 不 await 就不跑，不让出就全冻

`d_asyncio_scheduling.py` 是主线② 与主线④ 的后半。屏幕在这一支之前先把量法写清楚了：

```
══════ 第 5 节 d 篇：协程不是自动并发 —— 不 await 就不跑，不让出就全冻 ═══════════════════════════════
主线② 与主线④ 的后半。第 1 格：调用协程函数只生产一个协程对象，屏幕上就有那条
RuntimeWarning: coroutine ... was never awaited 的原文。第 4 格是本章的量法：
主协程里放一句同步 sleep，那一刻 ticker 一拍都没跳（await 版已经跳过了拍）——
总拍数两种写法都满，所以「任务没死，只是全部迟到」。
```

「第 4 格是本章的量法」这句是重点：**循环冻没冻住，只能数结构（跳了几拍），数秒就废了**。

```
$ timeout 600 python3 d_asyncio_scheduling.py

  刚写完 `co = do_nothing(log)`：log = [] ｜ inspect.iscoroutine(co) → True ｜ 类型 → coroutine
  co 的 repr 带内存地址，按本章规矩折掉：<coroutine object do_nothing at <地址>>
  [成立] await 过一次之后 log 里才有东西：实测 ['协程体真的跑了'] ｜ 预期 ['协程体真的跑了']
  [成立] await 拿到的返回值：实测 1 ｜ 预期 1
  [成立] 同一个协程对象 await 第二次（报错原文）：实测 'RuntimeError: cannot reuse already awaited coroutine' ｜ 预期 'RuntimeError: cannot reuse already awaited coroutine'
  [成立] 只创建不 await，GC 之后漂出来的原文：实测 ["RuntimeWarning: coroutine 'do_nothing' was never awaited"] ｜ 预期 ["RuntimeWarning: coroutine 'do_nothing' was never awaited"]
  → 断言：协程函数调用只生产一个协程对象；执行它的那一下叫 await，没人替你做 ｜ 本格判据 4/4 条成立（少一条上面就有 [不成立！]）
```

`co = do_nothing(log)` 这一行过去之后：`log = []`（一个副作用都没发生）、
`inspect.iscoroutine(co)` → `True`、类型 → `coroutine`，
而 repr 里那个内存地址按本章规矩折成了 `<地址>`（屏幕上明写「co 的 repr 带内存地址，按本章规矩折掉」）。
`await` 过一次之后 `log` 里才有东西 → `['协程体真的跑了']`，返回值 → `1`。
两条原文是这一格的重点：同一个协程对象 `await` 第二次 →
`RuntimeError: cannot reuse already awaited coroutine`；
只创建不 `await`、GC 之后漂出来的是 → `RuntimeWarning: coroutine 'do_nothing' was never awaited`。
★ 这就是主线② 的协程版本：**执行它的那一下叫 `await`，没人替你做**。
写 `f()` 只是生产了一个待执行对象，和「调一个普通函数」在这一点上完全不同 ——
这条差异是本章后面所有「我明明 await 了」事故的源头。

```
=== 2. create_task 是排班，await 是干等：主协程不让出，任务一个都不动 ===
  [成立] create_task 之后立刻：已经跑起来的任务个数（主协程还没让出）：实测 0 ｜ 预期 0
  [成立] 同上：已经做完的任务个数：实测 0 ｜ 预期 0

  [成立] 同一时刻做完的个数（任务里放了 sleep，所以稳稳是 0）：实测 0 ｜ 预期 0
  [成立] 两个直接 await：完成的先后 == 发出的先后：实测 ['慢', '快'] ｜ 预期 ['慢', '快']
  [成立] 两个 create_task：完成的先后变成「谁先干完谁在前」：实测 ['快', '慢'] ｜ 预期 ['快', '慢']
  → 断言：await 一个任务只是等它；create_task 才是交给循环，而它也得等主协程让出 ｜ 本格判据 6/6 条成立（少一条上面就有 [不成立！]）
```

四条计数判据把「排班」和「开跑」切开：`create_task` 之后**立刻**，
已经跑起来的任务个数 → `0`、已经做完的个数 → `0`；
主协程 `await` **让出一次**之后，已经跑起来的 → `3`、做完的仍是 `0`（任务里放了等待）。
★ 「让出一次才变 3」是主线② 最硬的一句：`create_task` 只是把任务交给循环排队，
**轮到它的前提是当前协程主动离开**。
最后两条把「谁先做完」这件事做成了可核对的顺序：
两个直接 `await` → 完成先后 `['慢', '快']`（就是发出的先后）；
两个 `create_task` → `['快', '慢']`（变成谁先干完谁在前）。
屏幕上印的是这两个字面标签，没有「快了多少」——因为「快慢」在这里是任务里预先写死的档位名。

```
=== 3. gather 保的是「你交出去的顺序」，不是「谁先做完」 ===
  [成立] gather 返回值的顺序 == 交出去的顺序：实测 ['c', 'a', 'b'] ｜ 预期 ['c', 'a', 'b']
  [成立] 实际做完的先后（另一本账）：实测 ['a', 'b', 'c'] ｜ 预期 ['a', 'b', 'c']
  [成立] 两本账一模一样吗：实测 False ｜ 预期 False
  [成立] gather 直接吃协程对象（不用你先 create_task）收到的份数：实测 3 ｜ 预期 3
  → 断言：gather 给你「按参数顺序对齐」的结果表；想知道谁先做完得自己另外记账 ｜ 本格判据 4/4 条成立（少一条上面就有 [不成立！]）
```

三本账摆在一起：`gather` 返回值的顺序 == 交出去的顺序 → `['c', 'a', 'b']`，
实际做完的先后（另一本账）→ `['a', 'b', 'c']`，两本账一模一样吗 → `False`。
第四条补了个易用性判据：`gather` 直接吃协程对象（不用你先 `create_task`）收到的份数 → `3`。
★ 断言行那句「想知道谁先做完得自己另外记账」就是本格的用途边界：
`gather` 给你一张**对齐的结果表**，它不是完成顺序的记录仪。
这条和第 10 节第 5 格（`map` 保序 / `as_completed` 按完成先后）是同一件事在两个库里的形状。


## 第 11 节 · 矩阵格：三件「千万别统一」的事 —— 阈值、冻住、并行度

### 11.1 加速判定：四套阈值并存，谁也不比谁严

### 11.2 「循环被冻住」这件事本机怎么量

`d` 篇第 4 格（第 09 节）与 `g` 篇第 4 格量的是同一件事，两处的量法**必须一致**才叫证据：

```
=== 4. 附：asyncio 里做重活会把整个循环冻住（量的是拍数，不是秒）===
      重活留在循环里：那一刻一拍都没跳吗 → True （结构上必是 0：算死期间循环一次都没被让出来）
      重活挪进 to_thread：那一刻已经跳过拍了吗 → True （跳了几拍每跑必变，所以这里只问有没有）
      两种写法最后总拍数都满了 20 拍吗 → True （任务没死，只是全部迟到）
  → 判据：「循环被冻住」只能数拍子（那一刻是 0 拍还是已跳过拍），拿秒表量就废了 ——
     冻住多久每跑必变，而「一拍都没跳」是结构上跑不掉的。
```

对照 `d` 篇那格的读数（393-403 行）：`time.sleep` 版「已跳拍数 == 0 吗 → `True`」，
`await asyncio.sleep` 版「已跳 >= 2 拍吗 → `True`、== 0 吗 → `False`」，
两种写法**最后总拍数都是 20**。两处合起来给的是同一句：
**冻住 = 那一刻一拍都没跳；不是 = 总拍数变少**。
`g` 篇那两行括号里的话把为什么写得很直白：「跳了几拍每跑必变，所以这里只问有没有」、
「拿秒表量就废了 —— 冻住多久每跑必变，而『一拍都没跳』是结构上跑不掉的」。
★ 由此也否掉一条常见误写：「asyncio 里阻塞会让总拍数变少」——屏上两个 `20` 就是反证。

### 11.3 并行度：上限是你声明的那个数，实到几个每跑必变

这是本章处理得最小心的一处。屏幕上的证据有三处，方向一致：

- **f 篇第 5 格**（575-582 行）：100 份活 / `max_workers=2`，「真干过活的进程个数 == 2 吗 → `2`」，
  而「== 任务数 100 吗 → `False`」——这一处活远多于人，所以每个声明的 worker 都被派到。
- **g 篇第 3 格**（659-660 行）：进程版算死，屏幕上写的是
  「并行度的天花板是**声明的 4 个 worker**，不是 6 份活」→ 这批活落在多于一个进程里吗 `True`。
- **g 篇第 2 格**（637-652 行）：写法 A 线程池声明 `max_workers=6`，屏幕上问的是

## 自检问题

1. 「Python 有 GIL，所以不能并发」这句话错在哪半句上？
   —— 错在把「一次只让一个线程跑字节码」读成「一次只能有一个线程在做事」。
   第 02 节第 4 格当场量：主线程睡觉、主线程堵在空管道上时，另一条线程都在推进（两条 `True`）。
2. `box["n"] += 1` 为什么**可能**被插队？本机量到的粒度是什么？
   —— 一行语句翻成 13 条字节码，读（`BINARY_OP`）和写（`STORE_SUBSCR`）之间隔着好几条（第 02 节第 2 格，85-91 行）。
3. 那本机 `+=` 到底丢不丢？能不能写「GIL 下 `+=` 一定丢」？
   —— 不能。4 线程 × 20 万次在默认与 `1e-6` 两种口径下都**不丢**（第 03 节第 5 格，185-190 行），
   a 篇收口自己写了这条禁区（135 行）。
4. 那本章能写成结论的是哪句？
   —— 「读 → 主动让出一次 → 写」结构性必丢，加锁才治得住（第 03 节第 6、7 格，192-207 行）。
5. `setswitchinterval` 调到 1e-6 有什么后果？
   —— 改得动、调得回，但两条加速判定全 `False`，且不丢这件事也不变（第 03 节第 4 格 + 第 5 格，176-190 行）。
   它是公平性旋钮，不是并行度旋钮。
6. 8 个线程比 4 个线程能多干多少纯计算？

   第 12 节第 4 格再量一遍（8 条比 2 条、8 条比主线程一个人，都 `False`）。
7. 没有 `if __name__ == "__main__":` 守卫，本机 forkserver 会怎么样？

  e 第 2 格「加速到 4 倍（= 核数）了吗 → False」（468 行）、f 第 5 格（579-580 行）、
  g 第 3 格「快到 3 倍了吗 → False」（662 行）。
- **「`submit` 之后 `f.done()` 是 False」不成立为通则。**
  判据：屏幕上那条判据自己带着条件括号「（任务里放了 sleep，所以这条量的是形状）」（494 行）。
- **「`asyncio.to_thread` 的线程名以 `ThreadPool` 开头」被本机否掉。**
  判据：g 第 5 格当场印前缀 `asyncio`、并判「是事件循环自己开的默认线程池吗 → True」（670-673 行）。
- **「asyncio 里阻塞会让总拍数变少」被本机否掉。**
  判据：d 第 4 格两种写法最后总拍数都是 `20`、g 第 4 格「总拍数都满了 20 拍吗 → True」（400-402、667 行）。
- **跨进程无锁 `+=` 是否一定丢：没演（不给稳定复现）。**
  判据：c 第 6 格那句 `✗ 本机演不出来（稳定版）` —— 无锁 bump 三遍跑下来 `.value == 8` 有时成立有时不成立（323 行）。
- **池实际派出几个 worker：本机每跑必变，所以那个数被从屏幕上撤了。**
  判据：g 篇开头两行 ★ 明写撤数原因（625-626 行）。本章凡涉及并行度只写「上限是声明的那个数」。
- **「同一个池第二批更便宜」没演。**
  判据：c 第 7 格 `✗`（334 行）：两批谁快谁慢会翻面，只留「第二批序号接着涨」这条结构判据。
- **「`as_completed` 比 `map` 快」没演**；判据：e 第 8 格④ 列进「本机给不出结论」（529 行）。
  同理「一次 `select` 就同时看到 N 路都有话」也没演（每轮给到几路取决于对方何时吐字，本机不稳，所以不印轮数）。
- **free-threading（去掉 GIL）下的任何行为没演。**
  判据：`Py_GIL_DISABLED` 当场印 `0`、`/usr/bin/python3.14t` 不在盘上（31-32、73-74 行）。
  「换一台不带 GIL 的机器结果会不同」= **未验证**，本章只字不预测。
- **第三方事件循环 / 装包这条路没演。**
  判据：`uvloop` / `trio` / `curio` 全 `False`、`pip` 不在场（31-36 行）。
  所以 `asyncio.to_thread` 是**本机唯一在场**的解法（d 第 5 格 + 第 8 格⑤，439 行）。
- **多核真并行（线程版）没演。**
  判据：a 篇收口 `✗ 本篇没演` 明写「多核真并行（那得用进程，见 c 篇）」（135 行）；
  g 第 3 格线程版「快过 1.3 倍 → False」（656 行）。
- **契约里预告的那句 `AttributeError: Can't get local object ...` 本机没出现。**
  判据：f 第 3 格 ★ —— 本机对闭包、局部函数、`lambda`、局部类实例印的**全是** `PicklingError`（565 行）。
- **信号在子线程里的「转交链」只给了出路、没演实现。**
  判据：f 第 1 格断言行写「得用 `queue`/`Event` 转交」（548 行），但本章没有一格把那条转交跑起来。
- **一切时长、pid、对象地址、丢更新后的具体计数：屏幕上就没有，所以书里也没有。**
  判据：第 14 节那道扫描器的两条链（弄响版全 > 0 / 正式版全 = 0 / `fold` 折掉行数 > 0，828-833 行）。
  唯一印了计数的两格是 `==` 得住的确定值（`80000`、`8000`，583-589 行），不是「还剩多少」。
- **别的机器、别的 Python 版本、别的平台默认 start method：未验证。**
  判据：g 第 0 格与第 7 格两次当场写着「换一台机器（核数不同、有没有 GIL）请整张重跑，别引用本表」（633、679 行）；
  本机只探到 `['forkserver', 'fork', 'spawn']` 这一组（17 行、246 行）。
- **静态检查工具与本章无关，而且本章没重测它们在场性。**
  本章七支脚本没一格调用过 `mypy` 之类；本机对它们的实测在第 10 章做过（10 §「环境体检」），
  本章不重复引用那一章的屏幕输出当证据。

## 怎么跑这一章

```
cd python-handbook/11-concurrency
bash demo.sh                  # 十节全跑，跑完自动删沙箱（默认）
bash demo.sh --keep           # 跑完保留沙箱并打印路径，进去自己接着敲
bash demo.sh > out.txt 2>&1   # 重定向时自动关颜色，得到纯文本（本章引用的就是这一份）
```

十节的分工照第 00 节那张表找：第 1 节是地板，第 2~8 节是七支取证脚本各一节
（`a` 身份 → `b` 线程 → `c` 进程 → `d` 协程 → `e` 池与 select → `f` 误区 → `g` 收口），
第 9 节是章级互相对账，第 10 节是红线自证。屏幕上只有两种行：`$ 命令` 底下到 `[退出码 N]` 为止
都是当场跑出来的原文；以 `#` 开头的是写给下一格的说明，不是屏幕产物。

想单点复现某一格，就把那一支拷进临时目录再跑：

```
SB=$(mktemp -d /tmp/py11-chk-XXXXXX)
cp python-handbook/11-concurrency/b_threads_two_faces.py "$SB"/
cd "$SB" && timeout 600 python3 b_threads_two_faces.py
```

★ 别在章目录里直接 `python3 某支.py`：每支脚本都在**当前目录**自建一个 `*-demo/` 子目录，
正常收尾会自己删掉（b 篇 `232 行`、c 篇 `358 行` 那两行「还在吗 → False」就是这件事的判据），
但中途 `Ctrl-C` 会把残骸留在章目录里。demo 自己则全程只读章目录（第 14 节那份「跑前 = 现在」清单）。
★ 每支脚本外面都套 `timeout 600`：并发代码最坏的失败模式是**卡住**，而卡住不会打印任何东西 ——
`rc=124` 就是当场把「卡住」这件事印出来（第 14 节的负样本里假 rc=124 被认出来了）。
★ 本章**不许**用 `Ctrl-C` 之外的方式中断脚本后接着复用那个目录；`__pycache__` 只在 import 时产生，
第 14 节那格已经当场演示过（`763-771 行`）。

三件事先记住，否则读数会跟本章对不上：
① 必须在 CPython `3.14.4` 且默认 start method 为 `forkserver` 的机器上跑（第 01 节那五行地板）；
② 屏幕上没有秒、没有 pid、没有地址，任何一格都不许被改写成带秒数的版本 —— 那是本章的红线，
第 14 节的扫描器会为这两类禁串把关；
③ 报错原文跟版本绑定：本章逐字引用的 `ValueError` / `RuntimeError` / `PicklingError` /
`ConnectionResetError` 那几句只在本机 `3.14.4` 验过。

本章正文里引屏幕原文的地方一律只写行号占位符（形如 `@@R 629-632@@`），
由 `expand_fences.py` 从定稿捕获 `py11.txt` 按行号原地换成逐字围栏 —— 所以本书里没有任何一行引文是手打的。

|---|---|---|

| `sys._is_gil_enabled()` / `Py_GIL_DISABLED` | 前者问「此刻开着吗」（`True`），后者问「编译时编掉过吗」（本机印 `0`，非 1 就是带着 GIL） | 第 01 节、第 02 节第 1 格 |

| 结构量 | 能复现的非时长读数：拍数、个数、份数、顺序是否一致、`==` 得住的确定值 | 全章；例：第 03 节第 3 格（峰值 4/1）、第 09 节第 4 格（总拍数 20） |
| 让出 | 交出执行票的动作。线程靠抢占 + IO 等待；协程**只在 `await` 处** | 第 02 节第 4 格、第 09 节第 2 格 |

| `__mp_main__` | 子进程重新 import 主模块时用的模块名；`fork` 那一路才是 `__main__` | 第 07 节第 4 格、第 10 节第 3 格 |
| `mem=3` / `mem=0` | 本格用来量「继不继承此刻内存」的结构量（模块级列表的长度） | 第 07 节第 4 格、第 08 节 |

| `map` / `as_completed` | 前者保你发出的顺序，后者按谁先做完给谁（不是快慢承诺） | 第 10 节第 5 格 |

## 本章回指

- **05 §「字节码视角」**：那章量过「局部变量是数组下标、全局是查名字」；
  本章第 02 节第 2 格把同一条流水线用在 `box["n"] += 1` 上，读出 13 条字节码、
  读写之间隔着好几条 —— 丢更新的机械原因就接在那里。
- **05 §「闭包」**：那章讲内层函数出门时带的那几个 `cell`；
  本章第 12 节第 3 格给出它的进程池反面：住进局部命名空间的东西**没有名字可查**，
  所以 `pickle` 只能报 `PicklingError: Can't pickle local object ...`。
- **02 §「+= 对 list 和 str 是两种命运」**：那章的 `+=` 讲的是原地与新建；
  本章第 03 节第 5~7 格和第 05 节把同一个符号读成「几条字节码、中间让没让出」，
  两处不冲突：那章管语义，本章管**调度时机**。
- **04 §「复制的六级梯子」**：第 08 节那句「模块级变量不共享，孩子拿的是复印件」
  用的正是那章 `copy.copy` / 贴标签的分界语言 —— 而 `fork` 给的是**进程级**的那一份复印件。
- **07 §「异常也是一棵树」**：那章钉过 `except Exception` 接不住的那一支；
  本章第 09 节第 7 格给出这一支在并发里的具体名字 —— `CancelledError` 不是 `Exception` 的儿子。
- **07 §「异常链」**：那章分清了 `__cause__` 是你写的、`__context__` 是解释器记的；
  本章第 10 节第 6 格给它的跨进程版本：线程池 `__cause__` 是 `None`，进程池挂 `_RemoteTraceback`。
- **07 §「异常走到程序边界」**：那章讲退出码与线程里的静默；
  本章第 04 节第 8 格（daemon 被硬切但退出码仍 0）和第 12 节第 7 格（卡住不会打印任何东西）
  是同一条边界的两个并发形状。
- **09 §「f 篇完整跑」**：那章把 `if __name__ == "__main__"` 讲成「按名字去模块上找」的规矩；
  本章第 06 节第 2、3 格是它的进程版兑现：没有守卫 → 整份重跑，有守卫但函数不在顶层 → `AttributeError`。
- **09 §「e 篇完整跑」**：那章钉过「只有 import 会写 `__pycache__`、直跑脚本不产缓存」；
  本章第 14 节那格（763-771 行）把它当判据复用了一次 —— 五项计数里只有 import 那一样会跳。
- **08 §「临时文件的四种粒度」**：本章每支脚本自建的 `*-demo/` 沙箱、daemon 那格的 marker 文件，
  用的都是那一章的规矩（自建、自己 `rmtree`、判据用「在不在」而不是「多久」）。
- **10 §「环境体检」**：那章实测了本机静态检查工具与 `pip` 的缺席；本章只借用「没有 `pip`」这一条
  解释「为什么装不了东西」，其余一律以本章第 01 节当场探出的那块地板为准。
- **bash 手册 09 §「先把这台机器的发言权确认一遍」**：本章第 14 节那套
  「先造负样本让守卫响、再报 0」的纪律，和那一章「先确认脚本有没有发言权」是同一件事。
