# 堆排序 heap-sort

> 唯一一个「O(1) 额外空间 + 最坏也是 O(n log n)」的通用排序。代价是**实测比快排慢一倍左右** —— 本节把两阶段全过程、每步的数组快照和树形都打出来，并且**用真实毫秒数把"为什么慢"和"那它还有什么用"两件事都说清楚**（答案是 introsort 的兜底）。

---

## 一句话是什么

把数组**原地看成一颗完全二叉树**（父子上标靠公式算，不建任何节点结构），先把它整理成「每个爹都 ≥ 两个孩子」的**最大堆**，然后反复做三件事：**堆顶和末尾交换 → 堆的有效长度减 1 → 新堆顶往下沉**。每做完一轮，数组末尾就多一个"永久正确"的元素，做 n-1 轮就排完了。

---

## 为什么需要它

先看你手上的牌：

| 你要的东西 | 谁给得起 |
|---|---|
| 最坏情况也有 O(n log n) | 归并、堆 |
| 而且【不额外要内存】 | **只有堆**（归并要 O(n) 临时数组） |
| 而且要能处理"数据一条条来、随时要最大值" | 堆（这是快排/归并根本不给的能力） |

三个条件同时满足的只有堆排序。它是嵌入式、内核、OOM 敏感场景的默认排序；也是**快排的保险丝**（见第 6 幕 introsort 实测）。

不用它时的痛：
- 只用快排：遇到"输入已经有序 / 大量重复 / 被对手专门构造"就是 O(n²)，10 万个数从 0.3 毫秒变 200 毫秒（第 6 幕实测 203.88 ms vs 1.46 ms）。
- 只用归并：要额外 n 个 int。排 1000 万个整数就是多 40MB —— 在 MCU、内核、移动端后台这种场景里，这 40MB 就是要命的那部分。
- 想随时知道"当前最大/最小是谁"：数组、快排、归并都给不了，堆给的是 O(1) 看一眼堆顶。

## 核心思路图解

### ① 数组怎么变成一棵树（本节全部技巧的地基）

约定**根在下标 0**：

```
     下标公式： parent(i) = (i-1)/2      left(i) = 2i+1      right(i) = 2i+2

                        a[0]                        ← 堆顶：整段最大值一定在这
                     /        \
                 a[1]          a[2]
                /     \        /     \
            a[3]    a[4]    a[5]    a[6]
             /  \
          a[7]  a[8]

     把它按【层序】抄成一排，正好就是 a[0] a[1] a[2] ... ⇒ 数组下标 = 树的节点编号
```

为什么合法：这是**完全二叉树**（除最后一层全满，最后一层从左往右连续）。这样的树按层写出来就是连续下标，所以父子关系**不用存，当场算**。
⇒ 这就是堆排序能 O(1) 空间的根本原因：**没有第二份结构，只有同一个数组的两种看法。**

最大堆只承诺 `a[i] ≥ a[2i+1]` 且 `a[i] ≥ a[2i+2]`，**不承诺兄弟之间有序**。所以"是堆"比"是有序数组"弱得多，但也正因为弱，它能用 O(n) 就建好。

### ② 阶段 1：建堆（从 a[(n-2)/2] 开始，倒着下沉）

拿本节的固定数组 `[4 10 3 5 1 8 7 2]`（n=8 ⇒ 从下标 3 开始，倒着做到 0）：

```
   i=3  a[3]=5 vs a[7]=2      ⇒ 不用动（叶子那层本来就是合法堆）
   i=2  a[2]=3 孩子 8、7       ⇒ 8 最大 ⇒ 换：[4 10 8 5 1 3 7 2]
   i=1  a[1]=10 孩子 5、1      ⇒ 不用动
   i=0  a[0]=4  孩子 10、8     ⇒ 10 最大 ⇒ 换 → 4 落到下标 1，它的孩子 5、1 里 5 更大 ⇒ 再换
                                     一路下来：[10 5 8 4 1 3 7 2]
   阶段 1 结束（实测：建堆只花了 10 次比较，n=8 ⇒ 比 2n 还少）
```

### ③ 阶段 2：反复取堆顶（每轮一个快照，`|` 右边是已锁死区）

```
   取走 10： [ 2 5 8 4 1 3 7 | 10 ]   ← 堆顶↔末尾换，然后 2 从根沉到底（走了 2 层）
   取走  8： [ 2 5 7 4 1 3 | 8 10 ]
   取走  7： [ 2 5 3 4 1 | 7 8 10 ]
   取走  5： [ 1 4 3 2 | 5 7 8 10 ]   ← 堆只剩 4 个了，树矮了一层，下沉最多 2 步
   取走  4： [ 1 2 3 | 4 5 7 8 10 ]
   取走  3： [ 1 2 | 3 4 5 7 8 10 ]
   取走  2： [ 1 | 2 3 4 5 7 8 10 ]
   堆里只剩 1 个 ⇒ 它必然是最小值 ⇒ 不用动 ⇒ [ 1 2 3 4 5 7 8 10 ]
   阶段 2 实测：比较 17 次、节点累计下沉 13 层
```

注意顺序：**每次拿走的是"当前剩下的最大值"，从后往前填 ⇒ 排完是升序**。（想要降序就建最小堆。）

### ④ 为什么建堆是 O(n)，不是 O(n log n)

```
   高度 h 的节点最多 ceil(n / 2^(h+1)) 个，每个最多沉 h 层：
       总层数 = n/2*0 + n/4*1 + n/8*2 + n/16*3 + … = n * Σ h/2^(h+1) = 2n = O(n)
   直觉：越靠下的层节点越多，而它们要沉的层数越少（最底层干脆沉 0 层）⇒ 两头一乘就收敛了。

   本节实测（比较次数除以 n，不随 n 增长 ⇒ 线性）：
       n=  256 │ 建堆 476 次（= 1.86 n）│ 取数 2816 次（= 1.38 n·log2n）
       n= 1024 │ 建堆 1836 次（= 1.79 n）│ 取数 15412 次（= 1.51 n·log2n）
       n= 4096 │ 建堆 7084 次（= 1.73 n）│ 取数 77933 次（= 1.59 n·log2n）
   ⇒ 两阶段的代价差了一个 log n 量级：【建堆不是瓶颈，取数才是】。
```

### ⑤ 为什么 O(1) 空间 + 稳定的 O(n log n)，实测却比快排慢

复杂度表上两者同为 O(n log n)，但**表里没写常数**。三件隐形代价：

```
   ① 访问模式：下沉是 0 → 2 → 6 → 14 → … 指数级往下跳，缓存行了
      快排/插入是下标单调往前扫，一行缓存一次带走十几个数，命中率接近 100%。
   ② 每沉一层要做【2 次比较 + 1 次交换】，而一次交换 = 3 次写内存。
   ③ 每次"取最大值"都要走完整的一条 log n 路径；快排一趟分区是"n 个数各看一眼"，
      总长度差不多，但快排的"看一眼"是一次顺序比较，堆的"走一层"是一次随机写。

   本节实测（固定种子 LCG 生成的乱序排列，n=16384）：
       heap-sort      2.89 ms   比较 408136 交换 214627
       quick+median3  1.61 ms   比较 263635
       quick-naive    1.46 ms   比较 279301
   ⇒ 堆排序比较次数多约四成，耗时约 1.8~2 倍。慢不是慢在渐进复杂度，慢在常数。
```

### ⑥ 那它到底值在哪：introsort（第 6 幕实测）

```
   同一批数据换成【已经升序】（裸快排的毒药）：
       heap-sort      2.27 ms   比较 421566    ← 完全不看输入长相，代价和乱序时几乎一样
       quick+median3  0.38 ms   比较 221197    ← 三数取中把有序数据救回来了
       quick-naive  203.88 ms   比较 134209536 ← O(n²)！1.34 亿次比较正好等于 n(n-1)/2

   introsort = 三数取中快排 + 小段(≤12)切插入 + 【递归深度超过 2·log2(n) 就把那一段交给堆排】
   ⇒ 平时享受快排的速度（默认阈值下真实数据一次都不会切，保险静静躺着），
     一旦分区连续失衡（被构造、全相同、极端偏斜）立刻退回 O(n log n) 兜底。
     本节还故意把阈值压到 4，逼兜底分支真的跑起来：n=8192 时切出 16 段给堆排，
     结果与 0..8191 完全一致 —— 没被走过的分支等于没测过的代码。
```

## 核心操作逐个拆解

### 1. `sink_range(a, lo, hi, root, verbose, st)` —— 唯一的发动机（`heap_sort.c:221`）

**干什么**：`a[root]` 太小了（它的两棵子树却都已经是合法堆），把它一层层往下换，换到"比两个孩子都大"为止。术语叫 heapify-down / 下沉 / sift-down。

**一步步**：
1. `left = lo + 2*(root-lo) + 1`，`right = left + 1`（子区间口径，`lo` 当成新的 0）。
2. 在**存在的**孩子里挑较大的那个：`largest = root`，`a[left] > a[largest]` 则改成 left，`a[right] > a[largest]` 则改成 right。两次比较各计数一次。
3. `largest == root` ⇒ 已经 ≥ 两个孩子 ⇒ 直接返回（**这就是叶子节点"沉 0 层"的来源**）。
4. 否则 `swap(a[root], a[largest])`，`root = largest`，回到第 1 步。

**为什么只跟较大的孩子换**：目标状态是"爹 ≥ 左 且 爹 ≥ 右"。跟较小的换，换完爹在新位置上仍可能小于另一边；跟最大的换，换下来的那个位置上的值正是"上一代的爹"，它只需要继续跟新孩子的最大者比 —— 一路下去，除了正在沉的这条路，其它子树始终保持合法。

**为什么写成 `for(;;)` 而不是递归**：`sink(child)` 是尾递归，编译器可能优化但不保证。写成 `root = largest` 回到循环顶部是**手动尾递归消除**，栈上永远只有一层 —— 这也是堆排序空间严格 O(1) 的原因之一（快排平均要 O(log n) 的栈）。

**边界**：`root` 是叶子（`left > hi`）⇒ 两次比较都被 if 跳过、立刻返回；只有左孩子（`left == hi`）⇒ 右孩子分支必须被挡住，**绝不能读 `a[left+1]`**；区间为空（`lo > hi`）⇒ 函数第一行直接返回。

**左右孩子相等时选谁**：代码用严格 `>`，所以选左孩子 —— 行为确定，README 里的过程才可复核。

### 2. `build_max_heap(a, lo, hi, verbose, st)` —— 阶段 1（`heap_sort.c:280`）

**干什么**：原地把 `a[lo..hi]` 变成最大堆。

**一步步**：
1. 算起点：最后一个有孩子的节点是 `lo + (size-2)/2`（`size = hi-lo+1`）。`n=8 → 3`，`n=7 → 2`。
2. `for (i = 起点; i >= lo; i--)` 逐个 `sink_range(a, lo, hi, i, ...)`。

**为什么必须从大到小倒着来**：`sink` 的前提是"它的两棵子树已经是合法堆"。倒着走时，处理到某个节点，它下面所有节点都已处理完 ⇒ 前提天然成立。顺着走等于白做。

**边界的坑**：`size == 1` 时 `(size-2)/2` 在 C 里是 `(-1)/2 = 0`（整除向零截断），会多跑一次无意义的 sink。代码用 `if (size < 2) return;` 挡住了 —— 这类"负数除法向零截断"是 C 里最容易咬人的地方之一。

**代价**：O(n)，实测 1.73~1.86 n 次比较（见上文 ④）。

### 3. `heap_sort_range(a, lo, hi, verbose, st)` —— 阶段 2 全流程（`heap_sort.c:312`）

```c
    build_max_heap(a, lo, hi, verbose, st);
    for (int end = hi; end > lo; end--) {
        swap_int(&a[lo], &a[end]);           /* 当前最大值归位到 end */
        sink_range(a, lo, end - 1, lo, verbose, st);  /* 注意 hi 变成 end-1：堆缩小了 */
    }
```
**三个要点**：
- **交换不能省成"把 a[0] 搬到别处"**：不交换就得真的删除元素、往前搬一整段，那是 O(n)。用"堆的有效大小"划开已排区，一个字节额外内存都不花。
- **`end - 1` 是关键**：传给 sink 的区间右端必须缩小，否则刚归位的最大值又被沉回堆里，结果全错。
- **循环到 `end > lo` 为止**：`end == lo` 时堆里只剩 1 个元素，它必然是最小值，不用动。

### 4. `heap_sort_trace(a, n, verbose, st)` —— 教学版（`heap_sort.c:339`）

和 `heap_sort_range` 做的事完全一样，只是把两阶段分开走，并在建堆之后、每次取数之后各打印一次数组快照 + 树形（`|` 右边标出已锁死区），还分别报出阶段 1 / 阶段 2 的比较次数。**分开打印的价值**：让你亲眼看到"建堆很便宜、取数才是大头"。

### 5. `Heap` + `heap_push` / `heap_pop_max` —— 对照用的动态堆（`heap_sort.c:397~471`）

**为什么排序不需要它，但本节还是写了**：
- push = 值塞到数组末尾（保持"完全"这个前提）→ `swim` 往上冒：只要比爹大就换上去（`heap_sort.c:425`）。
- pop = 记下 `a[0]` → 把**最后一个**元素补到顶上 → `size--` → `sink_range` 沉下去。**这正好就是堆排序阶段 2 的动作**，只不过堆排序把"拿走"实现成了"和数组末尾交换"，从而省掉了一个堆结构。
- 什么时候真需要它：数据一条条来、要随时取极值、Top-K、Dijkstra、事件调度（联系 `06-heap/` 和第 11 章的 `kth-smallest/`）。
- 别忘了 `heap_free`：本目录里 `data` 是 malloc 出来的，ASan 会盯着它。

### 6. `heap_sort_tagged(key, tag, n)` —— 稳定性实验（`heap_sort.c:514`）

两条平行数组：`key[]` 分数、`tag[]` 身份证；key 换到哪，tag 同步换到哪，打印成 `88a/88b`。实测：

```
   [88a 88b 70c 88d 60e] → [60e 70c 88d 88b 88a]   ← 三个 88 的顺序整段反转
   [5a 5b 2c 5d 1e 5f]   → [1e 2c 5f 5d 5b 5a]     ← 同上，第一处翻车在下标 3
```
凶手就是阶段 2 每一次 `swap(a[0], a[end])` —— **首尾远距离对调**，一个同分元素被瞬移到另一端，中间同分兄弟整段反转。这不是"实现得不好"，是堆排序的结构决定的，换任何写法都逃不掉。

### 7. `mini_quick_sort` / `mini_quick_sort3` / `intro_sort`（`heap_sort.c:595` / `650` / `699`）

**为什么本目录要自带快排**：Makefile 按目录独立编译，不能 `#include ../quick-sort/quick_sort.h`，但"堆排比快排慢多少""堆排当兜底值多少钱"这两个结论不实测就只是道听途说。于是重写了几十行的对照实现。

**踩过的一个真实的坑（第 6 幕的备注里也写了）**：`mini_median3` 第一版只把 `a[lo]/a[mid]/a[hi]` 排成升序就结束了 —— 那时中位数在 `a[mid]`，而 Lomuto 取的枢轴仍然是 `a[hi]`（三者里的最大值），等于什么都没做。现场证据：升序数据上 median3 版比较 8398842 次、裸快排 8386560 次，**几乎一模一样**。补上 `swap(a[mid], a[hi])` 之后，同一份数据的比较次数从 839 万掉到 47115 次（n=4096）。**"看起来对"和"实测有效"是两回事，这就是要跑数字的原因。**

### 8. 验货工具（`heap_sort.c:64~114`）

`print_arr / is_sorted_ascending / same_elements / is_permutation`（目录自包含，各自一份）。另外本节的 main.c 里还有一个 `verify_max_heap`：**每次建堆结束都单独验一遍"每个爹 ≥ 两个孩子"**。这条比"最后排好了"更根本 —— 它是阶段 2 能正确工作的前提，也是本节实测里唯一能证明"堆确实是堆"的检查。

## 复杂度表

| 情况 | 时间 | 空间 | 本节实测依据 |
|---|---|---|---|
| 最好 | O(n log n)（取 n 次堆顶省不掉） | O(1) | 升序数据 n=16384：2.27 ms，和乱序时同量级 |
| 平均 | O(n log n) | **O(1)**（原地，sink 是尾递归消除） | 比较 = 建堆 ~1.8n + 取数 ~1.6 n log2 n |
| 最坏 | **O(n log n)** ← 这是它最值钱的一行 | O(1) | 建堆/下沉的路径只由下标决定，**与输入无关** |
| 是否稳定 | **不稳定** | — | `[88a 88b 70c 88d 60e] → [60e 70c 88d 88b 88a]` |
| 缓存友好度 | 差（跳跃访问） | — | 同为 O(n log n)，实测耗时约为快排 1.8~2 倍 |
| 建堆单独的代价 | **O(n)** | O(1) | 1.86n / 1.79n / 1.73n 次比较（n=256/1024/4096） |

----------------------------------------
  规则：根 = a[0]；a[i] 的父 = a[(i-1)/2]；左孩子 = a[2i+1]；右孩子 = a[2i+2]
  所以数组按【层序】读就是一棵树：a[0] / a[1] a[2] / a[3] a[4] a[5] a[6] / a[7] ...

  现在这个数组: [ 4 10 3 5 1 8 7 2 ]

4. 实测钉死「建堆是 O(n) 而不是 O(n log n)」
----------------------------------------
  直觉：一半节点在最底层 ⇒ 沉 0 层；四分之一在倒数第二层 ⇒ 最多沉 1 层……
        总下沉层数 = n/4*1 + n/8*2 + n/16*3 + … = 2n（收敛的级数）⇒ O(n)。
  看数据（比较次数除以 n，应该基本是个常数，不随 n 增长）：
      n=  256 │ 建堆比较     461（= 1.80 n）│ 取数比较    2840（= 1.39 n·log2n）│ 下沉   1565 层
      n= 1024 │ 建堆比较    1886（= 1.84 n）│ 取数比较   15386（= 1.50 n·log2n）│ 下沉   8269 层
      n= 4096 │ 建堆比较    7688（= 1.88 n）│ 取数比较   77941（= 1.59 n·log2n）│ 下沉  41379 层
  ⇒ 建堆那一列稳定在 ~2n 附近（n 越大越接近），取数那一列稳定在 ~n log n：
    两阶段的比例差得离谱，所以【建堆不是瓶颈】，瓶颈永远在「取 n 次堆顶」。

## 常见的坑

1. **父子公式记成 1 起步。** `left = 2i+1 / right = 2i+2 / parent = (i-1)/2` 是**根在下标 0** 的版本；根在下标 1 的版本是 `2i / 2i+1 / i/2`。两套混着用，第一个孩子就会指错，症状是"排序结果时对时错、n 是 2 的幂时特别容易翻车"。本节从头到尾只用 0 起步那套。

2. **`last_parent` 算错。** 正确是 `(size - 2) / 2`（等价于 `size/2 - 1`），不是 `size/2`。写 `size/2` 会多做一次无意义的 sink（不致错，但计数全歪）；写成 `size/2 + 1` 就可能从 `i = size/2` 起算导致 `2i+1 >= size` ⇒ 越界读。**边界 `n=1` 时 `(size-2)/2 = 0`（C 的整除向零截断），必须先用 `size < 2` 返回。**

3. **sink 时忘记把区间右端缩小。** 阶段 2 的正确调用是 `sink_range(a, lo, end - 1, lo)`。传成 `end` 的话，刚归位的最大值还在堆里，下一轮又被捞出来 —— 结果是"前一半正确、后一半乱套"，而且**不报错**，只是答案不对。

4. **用 `while (a[i] < a[child]) i = child;` 之类"顺手"的非严格比较。** 兄弟相等、或爹和孩子相等时，如果不严格 `<`（这里是最堆取 max 时的 `>`），可能在相等值之间反复换、或者选了不该选的孩子。全相同数组（`[7 7 7 7]`）是最常见的翻车现场；本节的边界表里专门放了它。

5. **把"堆"当成"有序数组"。** 堆只保证爹 ≥ 孩子，**同一层之间完全无序**。所以"堆排完直接从左往右读是降序"是错的（升序是"从后往前被填出来的"），"取走堆顶之后剩下的还是堆"也是错的（必须再 sink 一次）。

6. **`heap_pop_max` 里先 `size--` 还是先补堆顶，顺序反了会读到自己刚扔掉的格子。** 正确顺序：记下 `data[0]` → `size--` → `data[0] = data[size]` → `if (size > 0) sink(..., size-1, ...)`。忘记最后那个 `size > 0` 判断，会在 pop 最后一个元素时用 `hi < lo` 的区间去 sink（本节的 sink 第一行有防护，但别依赖别人的防护）。

7. **指望堆排序稳定。** 见第 6 幕，两个同分的人顺序必然可能被整段反转。要稳定用归并。

8. **只背"O(1) 空间、最坏 O(n log n)"就上场用它。** 实测它比快排慢近一倍；而且建堆那 `~2n` 次比较是**固定成本**，n 很小（比如 n=8）时"建堆+取数"的总比较 27 次，比插入排序最坏情况的 28 次没便宜多少，常数却大得多。小数组请回插入排序（`../comparison-basic/`）。

## 什么时候用它 / 什么时候别用

**用它：**
- **额外内存是硬约束**（嵌入式、内核、大数组 + 内存吃紧），又要 O(n log n) 保证 —— 这是它的唯一无替代场景。
- **最坏情况必须有上界**（在线服务、实时系统、可能被恶意输入打） —— introsort 的兜底就是它。
- **只要"前 K 个最大/最小"或"随时看极值"** —— 建一次堆 O(n)，每次取极值 O(log K)。比"完整排序 O(n log n)"省，见 `../../11-searching/kth-smallest/`（那边用**大顶堆维护 K 个**做流式 Top-K，是同一套下标公式）。
- 数据流式到来、边进边要极值（第 2 幕的 push/pop 就是这个形状）。

**别用：**
- 追求平均速度 ⇒ 快排 / introsort（`../quick-sort/`）。
- 要求稳定 ⇒ 归并（`../merge-sort/`）。
- n 很小 ⇒ 插入排序（`../comparison-basic/`）。
- 值是范围有限的整数 ⇒ 计数 / 基数（`../non-comparison/`），快得多还不比较。
- 只需要"整段最大值"一次 ⇒ 别建堆，一个 `for` 扫一遍 O(n) 就完了，建堆是白花的。

## 自检问题

**Q1：为什么建堆是 O(n)，而"逐个 push n 次"是 O(n log n)？**
A：建堆时绝大多数节点在最底层、下沉 0 层，需要长距离下沉的节点极少（总层数 = `Σ n/2^(h+1)·h = 2n`）；而逐个 push 时每个新元素都是往最底层塞、然后往上冒，冒泡距离的期望是常数但**每个元素都要付一次**，加上树逐渐长高，总计 O(n log n)。实测：n=4096 建堆 7084 次比较（1.73n）。

**Q2：阶段 2 里 `sink_range(a, 0, end - 1, 0)` 为什么是 `end - 1`？**
A：`a[end]` 刚被放上"当前剩下的最大值"，它已经在最终位置上、**必须退出堆**。区间右端写 `end` 就等于还把它算在堆里，下一轮它又会浮到堆顶被取一次。

**Q3：堆排序排完为什么是升序而不是降序？**
A：因为每次取的是**当前最大值**，而且填的位置是**从右往左**。最大值最终落在 `a[n-1]`，次大落在 `a[n-2]`……所以整个数组是升序。想要降序就建最小堆，或者反过来从左边开始填。

**Q4：为什么堆排序必然不稳定？给出本节的实测证据。**
A：阶段 2 每轮 `swap(a[0], a[end])` 是把堆顶和数组**末尾**对调，距离可以高达 n-1。同分的元素会被这样瞬移到另一端，中间同分兄弟的相对顺序整段反转。实测：`[88a 88b 70c 88d 60e] → [60e 70c 88d 88b 88a]`，三个 88 变成 d、b、a。

**Q5：它 O(1) 空间、最坏 O(n log n)，为什么实测比快排慢一倍？**
A：慢在常数，不在渐进：① 下沉按 `i → 2i+1` 指数跳，缓存行；② 每层要 2 次比较 + 1 次交换（3 次写）；③ 每取一个极值要走完 log n 层。实测 n=16384 乱序：heap 2.89 ms / 408136 次比较 vs quick 1.46 ms / 279301 次。

**Q6：`introsort` 里那个"深度超过 2·log2(n) 就切堆排"为什么用 2 倍而不是 1 倍？**
A：健康的分区即使不太均匀，深度也大约只到 log2(n) 的常数倍；阈值设 1 倍会把正常情况误伤（本来快排继续劈两下就好了），设 2 倍是"确实明显失衡了才干预"的经验值。本节实测：默认阈值下真实数据切堆排 0 次（保险不触发），人为压到 4 就切出 15~16 段且结果完全正确。
