# 快速排序 quick-sort

> 全场平均最快的那个：**挑一个数当参照物，一趟把数组劈成「左边都 ≤ 它 ≤ 右边都」，劈完它就已经站在最终位置上了**，然后只对两半边各再来一遍。本节把 Lomuto 和 Hoare 两种分区都写了一遍，并且**现场跑出最坏情况**（有序数组 + 固定末位枢轴 ⇒ O(n²)），再现场跑出两种救法。

---

## 一句话是什么

从数组里**随便挑一个数**（叫它 pivot / 枢轴），然后做一件事：把比它小的都挪到左边、比它大的都挪到右边。这件事做完，这个数就永远不用再管了 —— 它已经在最终排好的位置上。剩下两半各自是"小一号的原问题"，递归地再来一遍。

跟归并排序是**同一种分治、但把力气花在了不同的地方**：

```
归并：拆的时候不看内容（对半砍就完事），全部力气花在【合并】上。
快排：全部力气花在【劈】上，劈完就啥也不用干了 —— 合并那一步是空的。
```

这也是为什么快排的 merge 步骤是"没有步骤"：枢轴落位之后，左半边、右半边内部排好序，整体自然就排好了，不需要任何"把两段并起来"的动作。

---

## 为什么需要它

不用快排的话，你手上的选择是这样的：

| 你用的 | 痛点 |
|---|---|
| 冒泡 / 选择 / 插入 | 稳稳的 O(n²)。10 万个数就是 100 亿次操作，等到天荒地老。 |
| 归并排序 | O(n log n) 是稳的，但**必须再准备一个和原数组一样大的临时数组**。要在手机上给 100 万个数排序，你就得多申请 4MB。而且它的写内存是"到处乱写"，缓存不友好。 |
| 堆排序 | O(1) 额外空间 + 最坏 O(n log n)，但常数大、缓存命中率极差，实测比快排慢一截。 |
| **快排** | **原地排（只 O(log n) 的栈），平均最快，缓存友好（顺序扫数组），工程默认选择。** |

真实世界里快排就是默认答案：C 库的 `qsort`、Linux 内核的 `sort()`、大多数标准库的数组排序（或它的一个变体 introsort）都是快排家族。原因不是"理论最优"（它最坏能退化成 O(n²)），而是**平均情况下它的内层循环短到只有"一次比较 + 可能一次交换"，而且比较的地址是连续往前的，CPU 缓存和分支预测都站在它这边**。

代价有两条，本节都会实测给你看：
1. **不稳定**（3 个数就能翻车，见第 6 幕输出）。
2. **最坏 O(n²)**，而且触发条件极其日常 —— "输入已经排好序"就是最常见的触发方式。

## 核心思路图解

### 一趟分区在干什么（这是快排唯一需要理解的概念）

```
      选枢轴（这里选最后一个 6）              分区之后
   [ 9 5 7 1 3 8 2 «6» ]                 [ 5 1 3 2 «6» 8 9 7 ]
                                          └─────┘  ↑  └─────┘
   承诺：跑完之后                          全都≤6   6   全都≥6
                                            ↑
     ① 枢轴 6 站在下标 4 —— 这就是它【最终】位置，这辈子只动这一次
     ② 左边 [0..3] 全都 ≤ 6，右边 [5..7] 全都 ≥ 6
     ③ 左边内部什么顺序？不管。右边呢？也不管。
        两半边跟枢轴再无任何关系 ⇒ 可以完全独立地递归
```

**②③ 是快排能递归的全部理由**：分区之后，任何左边的数都不会跑到右边去，也不需要跟右边比较。所以"排好整个数组"就等价于"排好左半边 + 排好右半边"。

### Lomuto：只往右走的一根指针 i（`quick_sort.c:132`）

约定四段区间，`pivot = a[hi]`（固定取最后一个）：

```
  [  ≤ pivot  |  > pivot  |  还没看  |  pivot ]
  lo        i  i+1        j        hi-1    hi
   └─已确认─┘  └─已确认─┘  └─待处理─┘        └─暂存─┘

  j 从 lo 一路扫到 hi-1，每看一个数只做一件事：
     a[j] <= pivot ⇒ i++，然后把 a[i] 和 a[j] 换一下（把"小的"收进左区）
     a[j] >  pivot ⇒ 什么都不做，它 naturally 留在"未确认区"

  扫描结束 ⇒ 收尾 swap(a[i+1], a[hi])：把枢轴从暂存位挪进它该站的坑
```

8 个乱序数 `[9 5 7 1 3 8 2 6]` 第 1 趟的真实过程（程序打印的是结果，中间态手算如下）：

```
   j=0 a[0]=9 > 6 ⇒ 不收           i=-1
   j=1 a[1]=5 ≤ 6 ⇒ i=0，swap(5,9) [ 5 9 7 1 3 8 2 «6» ]
   j=2 a[2]=7 > 6 ⇒ 不收           [ 5 9 7 1 3 8 2 «6» ]
   j=3 a[3]=1 ≤ 6 ⇒ i=1，swap(9,1) [ 5 1 7 9 3 8 2 «6» ]
   j=4 a[4]=3 ≤ 6 ⇒ i=2，swap(7,3) [ 5 1 3 9 7 8 2 «6» ]
   j=5 a[5]=8 > 6 ⇒ 不收
   j=6 a[6]=2 ≤ 6 ⇒ i=3，swap(9,2) [ 5 1 3 2 7 8 9 «6» ]
   收尾 swap(a[4], a[7])            [ 5 1 3 2 «6» 8 9 7 ]   ⇒ 枢轴落 4
```

和文末真实输出第 1 幕的 `分区后： [ 5 1 3 2 «6» 8 9 7 ]` 一致。

### Hoare：两头各一根指针对向走（`quick_sort.c:190`）

```
   i →→→               ←←← j
  [ 9 5 7 1 3 8 2 6 ]，参照值 pivot = a[中点] = 1（只是参照值，不站岗！）

   i 从 lo 往右找【第一个 ≥ pivot】   （a[0]=9 ≥ 1，立刻停下）
   j 从 hi 往左找【第一个 ≤ pivot】   （6,2,8,3 都 > 1，一路走到 a[3]=1 停）
   i < j ⇒ 交换：错位的两个一起归位
   两边指针继续走，直到 i ≥ j ⇒ 返回 j 当【分界点】
```

和 Lomuto 最要命的三个不同：

```
   ① 返回值不是枢轴位置，只是"左段的最大值 ≤ 右段的最小值"这个缝。
      ⇒ 递归必须写 (lo, p) 和 (p+1, hi)；写成 (lo, p-1) 会把 a[p] 这个元素漏掉。
   ② 两个子区间永远非空（各至少 1 个元素）⇒ 分区趟数恰好 n-1，
      而 Lomuto 经常把某一侧劈成 0 个，趟数比 n-1 少（实测 42 vs 63，见第 4 幕）。
   ③ 内层必须用严格 < 和 >。写成 <= / >= 的话，遇到【全相同的数组】两根指针
      都会停在原地不动 ⇒ 每趟分界点都跟上次一样 ⇒ 死循环。
```

### 最坏情况：塌成一根链条（第 3 幕真实输出）

固定取最后一个当枢轴 + 喂进已升序数组 ⇒ 每趟枢轴都是这一段的最大值 ⇒ 右半永远是 0 个：

```
   正常情况（好的分区）                最坏情况（末位枢轴 + 升序数据）
        [1..8]                             [1..8]
       /     \                               \
  [1..4]   [5..8]                            [1..7]     ← 只劈掉 1 个
   / \      / \                                \
[1,2][3,4][5,6][7,8]                           [1..6]
 深度 log2(8) = 3                             / \  ... 根本没有另一半
 每层总工作量 n ⇒ O(n log n)                 [1..5]
                                            [1..4]   ← 递归树变成一根【链条】
                                            深度 n-1 = 7
                                            比较 7+6+5+4+3+2+1 = 28 = n(n-1)/2
                                            ⇒ O(n²)
```

真实数字（8 个升序数）：`比较 28 | 交换 7 | 分区 7 趟 | 最大递归深度 6`。
换到 64 个升序数：`比较 2016 | 分区 63 趟 | 最大递归深度 62` —— 2016 = 64×63/2，标准的三角形数。

### 两种救法（同一个有序数组喂进去对比）

```
  救法一 三数取中：用 a[lo]、a[mid]、a[hi] 三个数的【中位数】当枢轴
        升序数组里 lo=最小、hi=最大 ⇒ 中位数正好是中间那个值 ⇒ 一刀劈成两半
        实测 64 个升序数：比较 2016 → 360，深度 62 → 5

  救法二 随机化 pivot：每次在本段里随机抽一个下标，换到末尾再走 Lomuto
        价值不在于"平均更省"，而在于【没有任何一份输入能稳定坑到它】——
        三数取中是确定的，对手可以专门构造数据去坑它（Ninomiya–Takahashi 攻击
        就是针对 median-of-three 构造的），随机化没有固定弱点。
        实测 64 个升序数：比较 2016 → 378，深度 62 → 10
```

### 为什么平均是 O(n log n)（一个够用的直觉）

```
  每个元素被比较的次数 = 它"被劈出去"那一层的层数。
  只要枢轴大致落在本段的中位附近（哪怕是 1/4 ~ 3/4 的位置），
  一个元素到"落定"最多被劈 log2(n) 次；n 个元素 ⇒ n log n。
  严格推导要算"两个元素 i、j 何时还会互相比较"：只有当它们第一次被同一个
  枢轴劈散之前才会比一次，概率是 2/(j-i+1)，加起来是 2n ln n ≈ 1.39 n ln n = O(n log n)。
  本节实测：n=1024 的乱序数据，比较 19128 ≈ 1.32 × 1024 × log2(1024) × ... 同一个量级，
  而最坏情况要 1024×1023/2 = 523776 次 —— 差 27 倍。
```

### 顺手点一句：快排是"求第 K 小"的地基

一趟分区之后枢轴在最终位置 `p`：如果 `p+1 == k`，答案就是它；否则**只需要递归包含第 k 个的那半边**，另一边看都不看。把"递归两半"变成"只走一半"，总工作量从 O(n log n) 掉到 **平均 O(n)**。这就是 11 章 `../../11-searching/kth-smallest/` 里快速选择的全部原理，这里只需记住"只走一半"这个改法。

## 核心操作逐个拆解

### 1. `partition_lomuto(a, lo, hi, st)` —— 最省脑子的分区（`quick_sort.c:132`）

**干什么**：把 `a[lo..hi]` 劈成"左 ≤ 枢轴 ≤ 右"，枢轴落在返回值上。

**一步步**：
1. `pivot = a[hi]` —— 固定取最后一个。
2. `i = lo - 1`。用 -1 表示"目前还没有一个数被确认进左区"，这样第一条语句 `i++` 之后 i 就正好是 0，逻辑统一（如果写成 `i = lo`，就要额外处理"第一个元素 ≤ 枢轴时不该交换"的情况，非常容易错）。
3. `j` 从 `lo` 扫到 `hi - 1`（**注意不是 hi**，枢轴自己不能参加扫描）。
4. `a[j] <= pivot` ⇒ `i++`，然后 `swap(a[i], a[j])`。`i == j` 时是自己跟自己换 —— 代码里用 `if (i != j)` 跳过，纯粹为了交换计数好看，不跳过也不影响正确性。
5. 循环结束，`swap(a[i+1], a[hi])` 把枢轴放进它的坑，返回 `i+1`。

**边界**：`lo == hi`（一个元素）时第 4 步一次都不执行，第 5 步是自己换自己，返回 `lo` —— 无害但没意义，所以递归层用 `lo < hi` 拦住了，不会调进来。

**不稳定在哪一步**：就是第 5 步那次"远距离交换"。枢轴（末尾）跟 `a[i+1]`（可能在最前面）换，中间那一批相等元素的相对顺序被一脚踢翻。第 6 幕 `[88a 88b 70c] → [70c 88b 88a]` 就是这个案例。

### 2. `partition_hoare(a, lo, hi, st)` —— 交换最省的分区（`quick_sort.c:190`）

**干什么**：同样劈成"左 ≤ 参照值 ≤ 参照值一侧 ≤ 右"，返回**分界点**。

**一步步**：
1. `pivot = a[lo + (hi-lo)/2]` —— 取中点的**值**（不是下标；它会被换走，所以只能记住值）。
2. `i = lo - 1; j = hi + 1;` —— 两根指针都站在数组**外面**。
3. `do { i++; } while (a[i] < pivot);` —— **先走一步再看值**（do-while）。这是 Hoare 的命门：写成 `while (a[i] < pivot) i++;` 时，如果 `a[lo] == pivot` 那 `i` 一步不动；另一边同理；两指针停在原地 ⇒ 交换的还是那两个 ⇒ 死循环。
4. `do { j--; } while (a[j] > pivot);` —— 同理。
5. `if (i >= j) return j;` —— 两指针 crossed，缝就在 j。
6. 否则 `swap(a[i], a[j])`，回到第 3 步。

**为什么内层必须是严格 `<` 和 `>`**：全相同数组（例子里的 `[7 7 7 7]`），用 `<`/`>` 时两根指针都会立刻停下然后交换、继续前进，区间能正常缩小；写成 `<=`/`>=` 就"谁都走不动"。**这就是第 7 幕边界表里放 `[7 7 7 7]` 的原因，实测通过。**

**为什么返回值一定在 `[lo, hi-1]`**（保证两个子区间都非空、递归一定终止）：第 1 步的 `i++` 至少走到 `lo`，`j--` 至少走到 `hi`；参照值本身既不会被 i 越左、也不会被 j 越右 ⇒ 停在 `i <= j` 时交换、crossed 时 `j >= lo` 且 `j < hi`。所以递归写 `(lo, j)` + `(j+1, hi)` 一定是把区间劈小了。

### 3. 递归骨架 `qs_lomuto_range` / `qs_hoare_range`（`quick_sort.c:224` / `quick_sort.c:270`）

```c
    int p = partition_lomuto(a, lo, hi, st);   /* p 是枢轴的最终下标 */
    qs_lomuto_range(a, lo, p - 1, ...);        /* 枢轴已经落定，跳过它 */
    qs_lomuto_range(a, p + 1, hi, ...);
```
```c
    int p = partition_hoare(a, lo, hi, st);    /* p 只是分界点 */
    qs_hoare_range(a, lo, p, ...);             /* 必须包含 p！ */
    qs_hoare_range(a, p + 1, hi, ...);
```

教学版在每次分区前后各打印一行，并且**当场程序化验证分区的承诺**：扫左半取最大值、扫右半取最小值，比较"左半最大 ≤ 右半最小"是否成立（输出里每趟都有 `校验：… ⇒ 成立`）。这一条比"最后排好了"更有说服力 —— 它证明分区函数本身是对的，排错只会错在递归边界上。

### 4. `median_of_three` + `quick_sort_median3`（`quick_sort.c:383` / `425`）

**干什么**：把 `a[lo]、a[mid]、a[hi]` 三个位置的数**就地排成升序**，然后返回 `mid` 作为中位数下标。

**为什么顺手把三个位置排好**：排完之后 `a[lo] ≤ a[mid] ≤ a[hi]`，于是
- `a[lo]` 是本段最小 ⇒ 内层扫描 j 时天然成了哨兵，少一次越界判断；
- `a[hi]` 是本段最大 ⇒ 正好把它当枢轴，`hi - 1` 是天然右边界。
这就是工程实现里"三数取中 + 把中位数换到 hi + 走 Lomuto"三件套的由来（本节的 `qs_med3_range` 就是这么写的，见 `quick_sort.c:389`）。

**边界**：`hi - lo < 2`（两个或更少元素）时三数取中没有意义，代码直接退回"取最后一个"。

### 5. `quick_sort_randomized`（`quick_sort.c:491`）

随机取一个下标 `k ∈ [lo, hi]`，`swap(a[k], a[hi])`，然后走标准 Lomuto。
随机数发生器是本目录自带的 **固定种子 LCG**（`seed = seed*1103515245 + 12345`，种子 `20261003`，每次进入排序函数前 `lcg_reset()`）。**为什么不用 `rand()`**：`rand()` 的实现随 libc 变化，README 里贴的输出就对不上、也没法复核了。固定种子 ⇒ "看起来随机、实际每次一样"，这是教学项目里唯一正确的做法。

### 6. `quick_sort_tail_opt`（`quick_sort.c:545` / `517`）

```c
    while (lo < hi) {
        int p = partition_lomuto(a, lo, hi, st);
        if (p - lo < hi - p) { qs_tail_range(a, lo, p - 1, ...); lo = p + 1; }  /* 递归短的，长的继续循环 */
        else                  { qs_tail_range(a, p + 1, hi, ...); hi = p - 1; }
    }
```
**为什么栈就锁死 O(log n)**：每次真正进入递归的那个子问题，规模最多是当前的一半 ⇒ 嵌套层数最多 log2(n)。剩下的大半边变成同一层的循环，栈上不累积。
**实测**：64 个升序数，`plain-Lomuto 深度 62` → `tail-opt 深度 0`，而**比较次数 2016 一模一样** —— 这个优化只救栈、不救时间，最坏情况仍是 O(n²)。

### 7. `quick_sort_tagged` —— 稳定性实验（`quick_sort.c:602`）

int 类型没法带"原始序号"，所以用**两条平行数组**：`key[]` 存分数、`tag[]` 存身份证（a/b/c）。所有 `swap(key[i], key[j])` 的地方同步 `swap(tag[i], tag[j])`，打印时输出 `88a` 这样的串。这是"只有 int 也能演示稳定性"的通用技巧，`../comparison-basic/` 和 `../merge-sort/` 用的是同一招，三个目录各自带一份实现（目录自包含）。

### 8. 验货三件套（`quick_sort.c:25` / `35` / `45`）

`is_sorted_ascending`（逐对检查 `a[i] <= a[i+1]`）、`same_elements`（跟手写的标准答案数组逐个比）、`is_permutation`（O(n²) 数值计数，确认没丢数、没凭空造数、没改数）。**为什么不能用 `qsort` 排一遍再比**：`qsort` 需要函数指针比较器，本节明令禁止；而且拿被测算法的兄弟当标准答案，本身就不干净。这三个函数每个目录自带一份，就是为了能独立验货。

## 复杂度表

| 情况 | 时间 | 本节实测依据 |
|---|---|---|
| 最好 | O(n log n)（枢轴每次都正正中中） | `median3/8-asc`：比较 25、深度 2 |
| 平均 | **O(n log n)**，约 1.39 n log2 n 次比较 | n=1024 乱序：比较 19128；n=64 乱序：311 |
| 最坏 | **O(n²)** | 64 个升序 + 末位枢轴：比较 2016 = 64×63/2，深度 62 |
| 空间 | 原地，只有递归栈：平均 O(log n)，**最坏 O(n)** | 链条形状 ⇒ 深度 n-1 |
| 是否稳定 | **不稳定** | `[88a 88b 70c] → [70c 88b 88a]` |
| 缓存友好度 | 好（顺序扫描，比较地址单调前进） | — |

补充：Hoare 分区**交换次数明显少**（64 乱序：82 vs 146），但**比较次数明显多**（646 vs 311）、分区趟数恒定 n-1。所以"Hoare 更快"这个说法要限定：它省的是**写内存**，在元素很大、交换很贵的场景更划算。

5. 尾递归优化：只递归短的那半边，长半边用 while 循环吃掉（救栈，不救时间）

  朴素写法在最坏数据下，栈上要同时挂 n 层「等左半边返回」。

  为什么栈就锁死 O(log n)：每次进递归，那个子问题规模最多是当前的一半 ⇒ 嵌套不会超过 log2(n)。

## 常见的坑

1. **把 Hoare 的递归写成 `(lo, p-1)`。** Hoare 返回的是"缝"，不是枢轴位置。写 `(lo, p-1)` 会把 `a[p]` 这个元素永远排除在外 ⇒ 排序结果少一个元素、或者局部没排好，而且**不报错、不崩溃，悄悄给你错的顺序**。判定口诀：看分区函数最后有没有把枢轴放到某个确定下标；放了才敢 `-1` 跳过。

2. **Hoare 的两个指针没写成 do-while（或没有"先走一步"）。** `while (a[i] < pivot) i++;` 在 `a[lo] == pivot` 时一步都不走；右边对称地停住；交换两个"已经停住"的元素 ⇒ 状态回到上一轮 ⇒ **死循环**。这类 bug 的现场是"程序卡住但数组看起来没动"。

3. **Hoare 内层用了 `<=` / `>=`。** 全相同元素（`[7 7 7 7]`）会让两根指针都停在原地 ⇒ 分界点永远和上次一样 ⇒ 死循环。**必须严格 `<` 和 `>`**。反过来说 Lomuto 必须写 `<=`（等号归左区），否则相等元素全被推到右区，分区不收敛 —— 两个函数的等号取向是相反的，这是最容易记混的一条。

4. **固定取第一个 / 最后一个当 pivot，而且不加防护。** 已排序、近乎已排序、大量重复 —— 这三类输入在生产环境里是**常态而不是例外**（比如"把去年的有序导出文件再排一次"）。一踩就是 O(n²)。至少做三数取中，要么随机化。

5. **`mid = (lo + hi) / 2` 溢出。** 二分查找、三数取中都会算中点。`lo = 1<<30`、`hi = 1<<30 + 10` 时 `lo + hi` 在 int 里溢出成负数，`(lo+hi)/2` 变成负下标 ⇒ 越界/UB。正确写法 `lo + (hi - lo) / 2`（本节 `quick_sort.c:190` 里 Hoare 的参照值就是这么取的）。

6. **靠递归消灭最坏情况的栈。** 链条形状下递归深度是 n，n = 10 万时直接爆栈段错误。解法不是"改分治"，是**先递归短的那半边、长半边用 while 吃掉**（第 5 幕）；再加"小段切回插入排序"（见 `../comparison-basic/`）和"递归过深切换堆排序"（见 `../heap-sort/`），就是 introsort。

7. **指望快排稳定。** 收尾那次远距离交换是结构性的，不是可以调参数修掉的。同分要保序就用 `../merge-sort/`，或者把"原始下标"塞进比较键（本节的 tag 数组思路）。

8. **用 `rand()` 当随机化 pivot 的种子还嫌不够，又忘了复位。** 教学代码要输出可复核 ⇒ 必须自带固定种子发生器，并且**每次进入排序函数都 reset**，否则同一份 main 里两次调用结果不同，README 里的数字就骗人了。

## 什么时候用它 / 什么时候别用

**用它：**
- 通用内存数组排序，尤其是**元素是 int/小结构体、比较很便宜**的场合 —— 平均最快，这是工程默认答案。
- 需要**原地**（额外空间只有栈）。
- 只需要"前 k 个大概排好"的场合，用它的分区变形（快速选择，`../../11-searching/kth-smallest/`）。
- 数据规模小：配合"切回插入排序"（小数组上快排的递归开销反而比 O(n²) 的插入便宜）。

**别用：**
- 要求**稳定** ⇒ 归并（`../merge-sort/`）。
- 最坏情况不能容忍（在线系统、硬实时、可能被恶意输入攻击）⇒ 堆排序（`../heap-sort/`）或 introsort。
- 数据在链表上 ⇒ 归并（指针拼接，不需要额外空间）。
- 值是整数而且值域不大 ⇒ 计数 / 基数（`../non-comparison/`），能直接绕过 O(n log n) 下界。

## 自检问题

**Q1：一趟分区跑完，你能对数组做出哪两个断言？**
A：① 枢轴站在它的最终位置；② 左边全都 ≤ 枢轴 ≤ 右边全都。第 3 个断言"左右两边内部有序"是**错的** —— 那还要递归。这两个断言就是本节每次分区后打印"校验：左半最大 X ≤ 枢轴 ≤ 右半最小 Y"的内容。

**Q2：为什么 Lomuto 的 i 要从 `lo - 1` 开始，而不是 `lo`？**
A：`lo - 1` 表示"左区目前是空的"，于是"发现一个该进左区的数"这个动作永远统一成 `i++; swap(a[i], a[j])`。如果从 `lo` 起步，第一次就撞上"a[lo] 该不该进左区"的特例，得额外判断，代码一长就容易错。

**Q3：Hoare 分区在 64 个乱序数上交换 82 次、Lomuto 交换 146 次，但 Hoare 比较 646 次、Lomuto 只有 311 次。为什么？**
A：Hoare 一次交换同时把两个错位元素送回家（Lomuto 每确认一个只归位一个，还要为枢轴多搬一次），所以交换省。代价是两根指针各自要走完"越过对方"的全程，对每个元素都多做几次比较；而且两个子区间永远非空 ⇒ 分区趟数固定 n-1，比 Lomuto 的 42 趟多。结论：**Hoare 省写内存，Lomuto 省比较和递归**。

**Q4：为什么"先递归短的那半边"能把栈压到 O(log n)？它有没有让排序变快？**
A：因为每次真正递归进去的子问题规模 ≤ 当前的一半，嵌套次数最多 log2(n)。没有变快 —— 第 5 幕实测 64 个升序数比较次数 2016 → 2016 完全不变，只有深度从 62 → 0。**它救的是栈，不是时间**。

**Q5：三数取中和随机化都能破掉"有序数据"这个最坏情况，为什么工业实现常常两个都要？**
A：三数取中对有序/近有序特别有效且零开销（只是两次比较），所以默认用它；但它是**确定性**的，存在专门构造的输入（Ninomiya–Takahashi 攻击）能让 median-of-three 快排退化。随机化把"输入决定命运"变成"骰子决定命运"，没有任何一份输入能稳定坑到它，适合面对不可信输入的场景。

**Q6：`quick_sort(a, n)` 对 n = 0、n = 1 会怎样？**
A：入口第一行 `if (a == NULL || n < 2) return;` —— 不碰任何下标。第 7 幕实测：五个入口（Lomuto/Hoare/三数取中/随机化/短边递归）用 `n = 0` 调用都安全返回，数组内容没被写坏。
