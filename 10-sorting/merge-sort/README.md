# 归并排序 merge-sort

> 分治的第一个样板：**拆到只剩一个元素（天然有序）→ 两两合并**。发动机只有 merge 那十几行，本节把它逐行拆开、每层合并结果全部打印出来。

---

## 一句话是什么

把数组**对半砍到只剩 1 个元素**（一个元素不用排），然后**把两个已排好的段合成一个已排好的段**，一层层往上合，合完就是有序的。

---

## 为什么需要它

不用归并会怎样？

| 痛处 | 归并怎么解决 |
|---|---|
| 快排最坏 O(n²)，你写的项目偏偏喂进来一份"已经有序"的数据 | 归并**最好 = 平均 = 最坏 = O(n log n)**，永远不塌方。实测：已有序比较 11 次、完全逆序比较 9 次，抄写量一样 |
| 要**稳定**排序，同时 n 很大（插入排序 O(n²) 扛不住） | 归并是"又稳定又 O(n log n)"的唯一常用解，这是它存在的最大理由 |
| 链表排序怎么办？链表没有下标，随机访问是 O(n)，快排/堆排直接废 | **链表归并是教科书级搭配**：合并两条链表只要改指针，**零额外空间**（详见下面"和 02 章的联系"） |
| 想求"逆序对数量"、"数组有多乱"、"翻转对"这类题 | 归并的 merge 那一刻顺手就能统计，见第 6 幕，O(n log n) |
| 外部排序（文件比内存大，要分块读写磁盘） | 归并是唯一能改成"流式两两合并"的主流算法（多路归并、Timsort 的 run 合并都源自它） |

代价就一条：**要 O(n) 的额外内存**。这一点本节专门讲清楚为什么省不掉。

## 核心思路图解

### 拆 —— 到只剩一个元素为止

```
      [38 27 43 3 | 9 82 10]          ← 谁都不服
        /                 \
   [38 27 43 3]      [9 82 10]        ← 各拆一半（mid = lo + (hi-lo)/2）
     /      \         /     \
  [38 27]  [43 3]  [9 82]  [10]
   / \      / \     / \
 [38][27] [43][3] [9][82]             ← 全是 1 个元素：天然有序，递归出口 lo >= hi
```

### 合 —— 两个指针各看自己那半边，谁小取谁（发动机）

```
第 1 层合并（宽度 1 + 1 → 2）
   [38] + [27]     i=0↑  j=1↑   比 38 vs 27 → 27 小 → 写 27
     结果 [27 38]
   [43] + [3]        → [3 43]
   [9]  + [82]       → [9 82]        （9 小，直接取左）

第 2 层合并（宽度 2 + 2 → 4）      左段 [27 38]  右段 [3 43]
   tmp:  [ 27 38 ]      [  3 43 ]
            ↑i              ↑j
   a :  [ __ __ __ __ ]
            ↑k
   比 27 vs 3  → 3 小   → a=[ 3 __ __ __ ]        i=0 j=2 k=1
   比 27 vs 43 → 27 小  → a=[ 3 27 __ __ ]        i=1 j=2 k=2
   比 38 vs 43 → 38 小  → a=[ 3 27 38 __ ]        i=2(越界) j=2 k=3
   左段空了 → 右段剩下的 [43] 直接抄 → a=[ 3 27 38 43 ]
   ★ 只比了 3 次就合完 4 个数 —— "敢只比两个指针所指的值"，靠的是两段【各自已有序】

第 3 层合并（宽度 4 + 3 → 7）      左段 [3 27 38 43] 右段 [9 10 82]
   → [ 3 9 10 27 38 43 82 ]
```

### 每一层之后的数组快照（程序真实打印，见文末输出第 4 幕）

```
原始:                [ 38 27 43 3 9 82 10 ]
第 1 层（宽 1）合完:  [ 27 38 3 43 9 82 10 ]    ← 两两合，3 次合并（最后那个 10 没人配，原地不动）
第 2 层（宽 2）合完:  [ 3 27 38 43 9 10 82 ]    ← 2 次合并
第 3 层（宽 4）合完:  [ 3 9 10 27 38 43 82 ]    ← 1 次合并，收工
```

### 为什么复杂度是 O(n log n)、而且最坏也是

```
层数：段宽 1 → 2 → 4 → 8 … 到 n，一共 log2(n) 层（n=7 时 3 层，实测正好 3 层）
每层：所有合并加起来，每个元素被"读一次、写一次" ⇒ 每层严格 O(n)
⇒ 总 O(n log n)。
关键点：这个推导【和数据无关】。不管来的是乱序、有序还是逆序，
        拆的形状一样、每层要搬的格子数一样 —— 所以归并没有"最坏情况"这一说。
实测（第 7 幕）：n=256 时抄写 4096 格 = 256 × 8 = n·log2(n)，一模一样。
```

### 为什么一定要 O(n) 额外空间（省不掉的那部分）

```
往 a[lo..hi] 里写回时，读指针也在这段里。不抄走就覆盖：
   a: [ 5  8  12 | 3  6  20 ]      假设不抄 tmp，直接边比边写
   写 a[0] = 3（右段的最小值）→ 可是 a[3] 就是 3，它后面还有 6、20 等着被读
   下一次要写 a[1]，取左段的 5 —— 好，5 还在 a[0]？不，a[0] 已经被 3 覆盖了！
⇒ 数据被自己踩掉。所以必须先把原料【整体搬到别处】，才敢往原数组里覆盖。
```

**"只需要一份"**：在入口 `malloc` 一个长度 n 的 tmp，所有递归层共用它的不同区间（每个 merge 只用 `tmp[lo..hi]`），这就避免了每次合并都申请/释放。归并的"空间 O(n)"是一次性的，不是每层叠加。

### 和 02 章链表的联系：为什么链表排序特别适合归并

```
数组归并要 tmp，是因为"读和写在同一片内存"。
链表不是：节点是散在堆上的，合并时我们【只改 next 指针】，从不覆盖别人的数据。

  L1: 3 → 7 → 9          L2: 1 → 5 → 8
      ↑p1                    ↑p2
  比 3 vs 1 → 1 小 → 结果尾指针接上 1，p2 前进（没有任何数组拷贝）
  比 3 vs 5 → 3 小 → 接上 3，p1 前进
  ...
  结果: 1 → 3 → 5 → 7 → 8 → 9

  额外空间 = O(1)（只用几个指针变量；递归版栈上 O(log n)，自底向上版连栈都省了）
  切一半用快慢指针（02-linked-list/singly 里写过 slist_middle），找中点也是 O(n)。
⇒ 所以"给链表排序"标准答案就是归并：LeetCode 148 的官方解法，也是 Java 里
   Collections.sort(LinkedList) 的做法。数组才需要 tmp，链表改指针即可。
```

## 核心操作逐个拆解

代码位置指 `merge_sort.c`。

### 1. `merge_ranges(a, tmp, lo, mid, hi, st, verbose)` —— 发动机（`merge_sort.c:92`）

**干什么**：把 `a[lo..mid]` 和 `a[mid+1..hi]` 两个**各自已有序**的段合成一段有序，写回 `a[lo..hi]`。

**一步步**：
1. `for (p = lo; p <= hi; p++) tmp[p] = a[p];` —— 把原料整段抄进 tmp（不抄就会自我覆盖）。
2. `i = lo`（左段指针）、`j = mid + 1`（右段指针）、`k = lo`（写回位置）。
3. `while (i <= mid && j <= hi)`：比 `tmp[i]` 和 `tmp[j]`，小的抄到 `a[k]`，对应的指针 +1，`k+1`。
4. 有一个指针越界就退出循环；**剩下的那半段整段抄回**（两个 `while (i <= mid)` / `while (j <= hi)`），这一步一次比较都不做。

**边界情况**：
- 第 3 步的循环条件是 `&&`：任意一段空了就停。如果写成 `||` 会去读越界的 `tmp`。
- 第 4 步**只可能是其中一段还有剩**（因为写回格子数 = 两段长度和），所以两个 `while` 只有一个会真的执行，不用 if 区分。
- `tmp` 必须由调用者准备到长度 ≥ `hi+1`。本节的三个入口都在最外层一次性 `malloc(n)`，所以永远够用。
- 前置条件是**两段各自有序**。直接喂两个乱段进去，出来的一定不是有序的 —— 这就是为什么必须先递归排好再合。

**对应代码**：`merge_sort.c:92`；决定稳定性的那一行是 `merge_sort.c:119` 的 `if (tmp[i] <= tmp[j])`。

### 2. `merge_sort_range(...)` —— 三行递归骨架（`merge_sort.c:168`）

**干什么**：拆 → 递归排左 → 递归排右 → 合。

**一步步**：
1. `if (lo >= hi) return;` —— 递归出口，段里 0 或 1 个元素。
2. `mid = lo + (hi - lo) / 2;` —— 不用 `(lo + hi) / 2`，避免下标相加溢出（`11-searching/binary-search` 有一整幕讲这个坑）。
3. 递归左半边、递归右半边、`merge_ranges` 合起来。

**边界情况**：`lo == hi`（单元素）必须先返回；如果写成 `lo > hi` 才返回，单元素会算出 `mid == lo == hi`，右递归区间 `[lo+1..hi]` 变空段、然后 `merge_ranges` 拿到 `mid == hi` 的"空右段"，虽然结果碰巧对，但白跑一层递归，且当 `lo == 0, hi == 0` 时 `merge_ranges(0, 0, 0)` 里 `hi` 段越界读。判空要判在最早的地方。

### 3. `merge_sort(a, n)` —— 工程版入口（`merge_sort.c:198`）

**干什么**：`malloc` 一份 tmp → 递归 → `free`。

**边界情况**：
- `n <= 1` 直接 return，**连 malloc 都不做**（第 7 幕实测 n=0 安全返回）。
- malloc 失败：本节打印错误并放弃排序，返回 void。为什么不返回错误码？为了教学时不被错误处理淹没；正式代码应该往上传 `int`。

**内存责任**：tmp 在本函数申请、在本函数释放，调用者拿不到它 ⇒ 不可能泄漏。这是"谁申请谁释放"最干净的形态。

### 4. `merge_sort_trace(a, n, verbose, st)` —— 教学版入口（`merge_sort.c:216`）

**干什么**：和工程版完全同构，只是把 `verbose` 和统计指针传进递归。

**输出说明**（看懂第 3 幕的关键）：`| 拆 [...] → ...` 和 `| 合并完 [...]` 这类行由**递归骨架**打印，缩进随递归深度增加；`合并 左段 [...] + 右段 [...] → 取右3 取左27 ...` 这类行由**发动机**打印，用固定缩进（它不知道自己在第几层）。两种缩进混在一起是刻意的：**树形靠递归行体现，逐格决策靠发动机行体现**。

### 5. `merge_sort_bottom_up(a, n, verbose, st)` —— 不递归的按层版（`merge_sort.c:250`）

**干什么**：外层 `width = 1, 2, 4, …`，内层 `lo += 2*width`，每轮把宽度为 width 的相邻段两两合并。

**边界情况（这段最容易错）**：
```
mid = lo + width - 1;          左段最后一个下标
hi  = mid + width;             右段"理论"最后一个下标
if (hi > n - 1) hi = n - 1;    ← 尾巴不够长就截断
内层循环条件 lo < n - width    ← 保证左段至少存在，且【只剩一个孤段时不用处理】
```
少了截断那行 → `hi` 越界，ASan 直接报 stack/heap-buffer-overflow。
少了 `lo < n - width` 这个条件 → 会出现"只有左段、右段是空的"，虽然 `merge_ranges` 里空右段等于原地抄一遍，但完全浪费。
n=7、width=4 时只合一次（`[0..3] + [4..6]`，右段实际宽度只有 3），第 4 幕输出正好体现了"奇数段/尾巴短"。

### 6. `merge_sort_tagged(key, tag, n)` —— 稳定性实测（`merge_sort.c:356`）

**干什么**：按 `key`（分数）排序，`tag`（原始下标）跟着搬；排完看同分组的 tag 顺序有没有变。

**结论（第 5 幕真实输出）**：`88a 95b 88c 70d 95e 88f` → `70d 88a 88c 88f 95b 95e`，88 组还是 a→c→f ⇒ **稳定**。
秘密在 `merge_sort.c:321` 的 `tmp_key[i] <= tmp_key[j]`：相等时**优先放左边**，而左边就是原数组里靠前的那段 ⇒ 先来的人一定先出站。

### 7. `count_inversions(a, n, verbose)` —— 归并思想的应用（`merge_sort.c:435`）

**干什么**：数逆序对（`i < j` 但 `a[i] > a[j]`），O(n log n)。

**一步步**：递归同归并；唯一的区别是在"右段先出队"的那一刻加一个数。

```
合并  左段 [ 2 3 5 8 ]     右段 [ 1 4 ]
          ↑i                   ↑j
右段的 1 要比 → tmp[i]=2 > 1 → 1 先出队！
左段有序 ⇒ 从 i 到 mid 全部 ≥ 2 > 1，他们【每个人】都和 1 构成逆序对，
而且他们在原数组里都在 1 前面 ⇒ 一次加 (mid - i + 1) = 3 对：(2,1) (3,1) (5,1)
```

**为什么这样不重不漏**：每个逆序对的两个元素**恰好第一次在某次合并时分属左右两段**（就是它们共同的最低层祖先），那一刻被数一次，之后它们已在同一段里不会再跨段 ⇒ 不重不漏。

**边界**：相等（`tmp[i] <= tmp[j]`）**不算**逆序对，所以严格 `>` 的定义由 `<=` 分支保证 —— 和稳定性用的是同一个等号。

**验货**：`count_inversions_bruteforce`（`merge_sort.c:464`）用 O(n²) 双循环再数一遍，第 6 幕两者输出都是 9 ⇒ 一致。

## 复杂度表

| 算法 | 最好 | 平均 | 最坏 | 空间 | 是否稳定 |
|---|---|---|---|---|---|
| 归并（数组版） | **O(n log n)** | **O(n log n)** | **O(n log n)** | **O(n)** 额外 + 递归栈 O(log n) | **稳定** |
| 归并（链表版，只改 next） | O(n log n) | O(n log n) | O(n log n) | **O(1)**（迭代版；递归版栈 O(log n)） | 稳定 |

本节实测数字（真实输出）：

| 数据 | n | 比较 | 抄写格数 | 合并次数 |
|---|---|---|---|---|
| `[38 27 43 3 9 82 10]` | 7 | 14 | 40 | 6 |
| 同上，已有序版 | 7 | 11 | 40 | 6 |
| 同上，完全逆序版 | 7 | 9 | 40 | 6 |
| `(i*37)%n` 排列 | 256 | 1698 | 4096 | 255 |
| `(i*37)%n` 排列 | 1024 | 8161 | 20480 | 1023 |
| `(i*37)%n` 排列 | 4096 | 37177 | 98304 | 4095 |

注意抄写格数 **恒等于 n·log2(n)×2 的一半**，也就是"每层把每个元素搬两遍（抄进 tmp + 抄回 a），共 log2(n) 层"：`256 × 8 × 2 = 4096`。比较次数则稳定在 `n·log2(n)` 的 0.75~0.85 倍。

## 常见的坑

1. **忘了把原料抄进 tmp，直接边比边写 a** —— 写回的数据把还没读的覆盖掉，结果"看起来排好了但少了几个数"。这是归并最经典的错。
2. **每次合并都 `malloc` 一个新 tmp**：复杂度没变，常数爆炸，而且极易漏 free 造成泄漏。正确做法是入口申请一份、全程复用（本节的 `merge_sort` 就是这个形状）。
3. **`<=` 写成 `<`**：结果仍然有序，稳定性消失。多条件排序（先按分数排、再按班级排）才会暴露这类 bug，最难查。
4. **mid 用 `(lo + hi) / 2`**：`lo`、`hi` 都很大时相加溢出（32 位 int 变负数），拿负数当下标直接崩。统一写 `lo + (hi - lo) / 2`。
5. **自底向上版忘了截断 `hi > n-1`**：尾巴那段右半不存在，`hi` 越界；ASan 会报 `stack-buffer-overflow`。同理内层条件要写 `lo < n - width`。
6. **递归出口写成 `if (lo > hi) return;`**：单元素段会继续拆成"空右段"，多跑一层还容易算出 `merge_ranges(lo, mid=lo, hi=lo)` 这种畸形区间。出口要判在 `lo >= hi`。
7. **`merge_sort_range` 里先合再拆**（把 `merge_ranges` 提到两个递归前面）：合的时候两段还没排好，等于用未排序数据做合并 —— 输出的数组看着"像排过"但顺序错。递归的顺序就是正确性。
8. **tmp 的下标用 0 基准**：本节的 tmp 用的是**和 a 一样的全局下标**（`tmp[lo..hi]`），不是从 0 开始的局部下标。自己改写时两套基准混用必错。

## 什么时候用它 / 什么时候别用

**用**：
- 要求**稳定**且 n 大：唯一常用的稳定 O(n log n)。
- 要求**最坏也有保证**（实时系统、答辩现场演示、不能塌方的服务）：归并最好=平均=最坏。
- **链表**排序：只改指针，O(1) 额外空间。
- 外部排序 / 数据在磁盘或网络上分块来：两两归并天然适配。
- 要用到"逆序对""合并 K 个有序数组""K 路归并"这类衍生题：思路直接复用。

**别用**：
- 内存吃紧、n 巨大（比如 1 亿个数）：O(n) 的额外 tmp 就是硬伤 → 用堆排（`../heap-sort/`，O(1) 空间）或快排（`../quick-sort/`，栈 O(log n)）。
- 数据很小（≤ 16）：递归 + 抄写的固定开销比插入排序那 5 行代码贵 → `../comparison-basic/`。
- 值域很小的整数：`../non-comparison/` 的计数排序直接 O(n+k)。
- 只要"前 K 个"而不是全排序：归并会把后半程全排完，浪费；应该用堆（见 `../../11-searching/kth-smallest/` 的大顶堆维护 K 个）。

## 自检问题

1. **为什么归并排序最坏也是 O(n log n)？**
   答：拆的形状只由 n 决定（跟数据内容无关），固定 log2(n) 层；每层所有合并加起来恰好把每个元素搬两遍，是 O(n)。两者相乘 O(n log n)，没有任何一步依赖"数据碰巧有序"。实测 n=7 时有序/逆序的抄写量都是 40 格、都是 6 次合并。
2. **归并的 O(n) 额外空间能省掉吗？数组和链表的区别在哪？**
   答：数组省不掉 —— merge 要往 `a[lo..hi]` 覆盖写，不先把原料抄走就会踩掉还没读的数据。链表省得掉：节点散落在堆上，合并只是**重新接 next 指针**，不覆盖任何数据，所以只要几个指针变量（O(1)）；切中点用快慢指针。这就是"链表排序首选归并"的原因。
3. **稳定性是靠哪一行代码保证的？为什么？**
   答：`if (tmp[i] <= tmp[j])`（`merge_sort.c:119` / tagged 版 `merge_sort.c:321`）。相等时优先取左段那个，而左段在原数组里整体靠前 ⇒ 相等元素的原始先后被原样保留。
4. **合并 n 个数最多比较几次？最少呢？**
   答：最多 `n-1`（两段各剩最后一个时那一次比较定生死），最少 `min(len左, len右)`（一边整体先出完）。实测 `[38 27 43 3 9 82 10]` 全程比较 14 次，n log n 的下界意义上已经接近最优。
5. **逆序对为什么"右段先出队 ⇒ 加左段剩余个数"？会不会重复计数？**
   答：左段有序，`tmp[i] > tmp[j]` 时 `tmp[i..mid]` 全都 `≥ tmp[i] > tmp[j]`，且它们在原数组中位置都在 `j` 前面 ⇒ 正好 `mid - i + 1` 对。不会重复：任意一对元素只在它们的"最低层共同祖先"那次合并里第一次跨左右两段，之后就在同一段里了。
6. **自底向上版为什么要 `if (hi > n - 1) hi = n - 1;`？**
   答：n=7、width=4 时理论右段是 `[4..7]`，但下标 7 不存在。不截断就越界。截断后右段实际宽度 3，正是"最后一层左边 4 个、右边 3 个"的真实形状。
