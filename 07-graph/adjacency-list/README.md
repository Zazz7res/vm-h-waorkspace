# 邻接表 adjacency-list

> 一个数组当"目录"，每个格子里挂一条链表当"邻居清单"。
> 它不是"省空间的矩阵"，它是**唯一能让你以 O(V+E) 走完整张图**的表示法。

---

## 一句话是什么

**开一个长度 V 的指针数组 `adj`，`adj[i]` 是第 i 条链表的头；链表上每个节点存一个邻居编号。**
于是"i 的邻居都有谁"= 顺 `adj[i]` 往下走一遍；链上有几个节点，i 的度就是几。

一句话记忆：**邻接矩阵是"摊平的表"，邻接表是"一串小方块"。**

这一节的节点就是第 02 章的单链表节点，只是字段名从 `val` 换成了 `dest`
（存的不是"值"，是"邻居的编号"）。本节把用到的链表操作**在自己的目录里重写了一份极简版**
（造节点 / 数长度 / 头插 / 尾插 / 按值删，每个 10~20 行），因为叶子目录必须自包含，
不能 `#include "../../02-linked-list/singly/slist.h"`。

---

## 为什么需要它

先看**只用邻接矩阵**会有多痛。我们的示例图 V=8、E=7，很可爱；
把它放大到现实规模：**V=10 万，E=20 万**（社交网络里"人均 2 个好友"级别的稀疏图）。

| 你要干的事 | 邻接矩阵 | 邻接表 |
|---|---|---|
| 存下这张图 | 100 亿格 × 4B = **40 GB**（还没开始算就死了） | **6.87 MB** |
| 遍历某个点的全部邻居 | 扫一整行 10 万格，其中 2 格有用 → O(V) | 走 2 个节点 → **O(度)** |
| BFS/DFS 走完全图 | O(V²) = 100 亿步 | **O(V+E) = 30 万步** |
| 问"i 和 j 连了吗" | **O(1)** ✅ | O(度) |

**结论：矩阵的问题不是"浪费"这么温和，而是"根本装不下"。**
而 40 GB 里 99.996% 的格子都是 0 —— 我们在为"不存在的关系"付内存。
邻接表的态度很干脆：**只记录存在的东西**。有边才挂节点，没边就是一个 NULL。

顺带说清一件大多数人条件反射搞错的事（本文「运行结果」第 6 幕会算给你看）：
**在 V=8、E=7 这种小图上，邻接表比矩阵更费内存**（288 字节 vs 256 字节），
因为每个链表节点要多背一个 8 字节的 `next` 指针。
邻接表真正赢的是**大图/稀疏图的规模弹性**和**遍历速度**，不是"绝对省内存"。

## 内存布局图解

### 示例图 G（全章共用，和邻接矩阵那节是**同一张图**）

```
  无向图 G：8 个顶点 0..7，7 条边，故意不连通
  分量一：0-1, 1-2, 2-0, 2-3      分量二：4-5, 5-6, 6-4      孤立点：7

        0 ───── 1                     4 ───── 5
         \     / \                     \     /
          \   /   \                     \   /
           2 ──────                     6          7 ← 孤零零
            \
             3
```

### 它建成邻接表，在内存里长这样

```
  第一级：adj 指针数组（一次 calloc 分配的 V 个 Node*，连续内存）

   adj[0] ──►┌────────┬────┐   ┌────────┬────┐
             │ dest 1 │next┼──►│ dest 2 │next┼─►NULL
             └────────┴────┘   └────────┴────┘
   adj[1] ──►┌────────┬────┐   ┌────────┬────┐
             │ dest 0 │next┼──►│ dest 2 │next┼─►NULL
             └────────┴────┘   └────────┴────┘
   adj[2] ──►┌────────┬────┐   ┌────────┬────┐   ┌────────┬────┐
             │ dest 0 │next┼──►│ dest 1 │next┼──►│ dest 3 │next┼─►NULL
             └────────┴────┘   └────────┴────┘   └────────┴────┘
   adj[3] ──►┌────────┬────┐
             │ dest 2 │next┼─►NULL                            ← 度 1 的叶子
             └────────┴────┘
   adj[4] ──►┌────────┬────┐   ┌────────┬────┐
             │ dest 5 │next┼──►│ dest 6 │next┼─►NULL
             └────────┴────┘   └────────┴────┘
   adj[5] ──►┌────────┬────┐   ┌────────┬────┐
             │ dest 4 │next┼──►│ dest 6 │next┼─►NULL
             └────────┴────┘   └────────┴────┘
   adj[6] ──►┌────────┬────┐   ┌────────┬────┐
             │ dest 4 │next┼──►│ dest 5 │next┼─►NULL
             └────────┴────┘   └────────┴────┘
   adj[7] ──►NULL                                              ← 孤立点：一个指针都不占
   ┌──────┐
   │  v=8 │  ┌─────┐
   │  e=7 │  │ ... │  GList 结构体本身，另一次 malloc
   └──────┘  └─────┘

  ★ 三层内存：GList(16B) → adj 数组(8×8=64B) → 14 个链表节点(14×16=224B)
     加起来 304 字节（本机的真实 sizeof，见运行结果第 1 幕）。
     对照矩阵：64 格 × 4B = 256 字节。**小图上邻接表反而更大**，就是这个 16B/节点 的锅。

  ★ 节点是"一次 malloc 一个"，散落在堆上，彼此不连续 → 遍历邻居要指针跳转，
     CPU 缓存友好度远不如矩阵那种一整块的连续内存。这也是"链表更省就更快"这个
     直觉错掉的第二个地方。
```

### 同一张图、两种表示，摆在一起看

```
  邻接矩阵 第 0 行  ： 0 1 1 0 0 0 0 0        ← 8 格，6 个是"废 0"
  邻接表   第 0 条链： [1] -> [2] -> NULL     ← 2 个节点，一个废格子都没有

  邻接矩阵 第 7 行  ： 0 0 0 0 0 0 0 0        ← 8 格全 0
  邻接表   第 7 条链： NULL                   ← 1 个指针
```

**"稀疏图省空间"的秘密就这么一句话：矩阵把 0 也存了，链表只存 1。**

### 无向图：一条边必须挂两个节点

```
  加边 (0,1) 实际做了两件事：
      adj[0] 的链尾挂上 dest=1 的节点   ┐
      adj[1] 的链尾挂上 dest=0 的节点   ┘  ← 两个不同的堆节点，不是一块内存共享

  所以：  节点总数 = 2 × 边数 = 2E，度之和 = 节点总数 = 2E
  这条等式是免费的自检器：跑出来不等，就说明某条边只挂了一边（对称性被破坏）。
  运行结果里每次 glist_print 都会顺手把这四个数字打出来核对。

  ⚠ 有向图才只挂一个节点（adj[a] 挂 dest=b，表示 a→b）。
    代价是：有向邻接表**很好算出度、很难算入度** —— 入度得把所有链扫一遍看谁挂着 u，
    O(V+E)。要常查入度就得再建一张"逆邻接表"（把所有边反向再存一份），
    或者像拓扑排序那节一样额外维护一个 indegree[] 数组。
```

### 节点内部：16 字节而不是 12 字节

```
  typedef struct Node { int dest; struct Node *next; } Node;

  手算：int 4 字节 + 指针 8 字节 = 12 字节
  实测：sizeof(Node) = 16 字节       ← 见运行结果第 6 幕

       ┌──────────┬────────┬──────────────────┐
       │ dest 4B  │ 空 4B  │   next 8B        │
       └──────────┴────────┴──────────────────┘
                    ▲
                    └── padding：64 位机上指针必须 8 字节对齐，
                        编译器在 int 后面塞 4 字节把它推到 8 的倍数

  教训：算内存一律按 sizeof 算，别按字段手加。少算这 4 字节，
       在 40 万条边的图上就少算 1.6 MB；在真实大图上是几个数量级的偏差。
```

## 核心操作逐个拆解

### 1. `glist_create(v)` —— 建一张空图（glist.c:179）

**干什么**：malloc 一个 `GList`，calloc 一个 V 个 `Node*` 的数组，返回图指针。

**一步步**：
1. 检查 `0 < v <= GL_MAX_V`，不合法直接返回 NULL。
2. `malloc(sizeof(GList))`，判空。
3. `calloc((size_t)v, sizeof(Node*))`，判空 —— **失败时先 `free(g)` 再返回 NULL**。
4. 填 `g->v = v; g->e = 0;`。此刻 V 个表头全是 NULL，也就是"所有点都是孤立点"。

**边界情况 / 为什么这么写**：
- **为什么用 calloc 不用 malloc？** calloc 会把分配的内存**全部填 0**，
  而"指针的全 0 位模式"在 C 里就是 NULL。省一个循环，也少一个"漏初始化某格"的 bug。
  对照邻接矩阵那节：那边结构体在栈上、里面是垃圾，必须手动双层循环清 0；
  这边是堆上指针数组，calloc 一步到位。**同一个"必须初始化"的问题，两种解法。**
- **为什么第二次 malloc 失败时要回滚第一次？**
  只分配一处时不会出事；一旦有两处分配，忘了回滚就是**失败路径上的泄漏** ——
  平时不触发，内存紧张时才触发，而内存紧张时正是你最不该再漏的时候。
  这个习惯比"记住哪行代码漏了 free"更值钱。
- **`(size_t)v` 这个强转不是装饰**：写 `calloc(v * sizeof(Node*), 1)` 这种形式时，
  `v * sizeof(...)` 里 sizeof 是无符号的，会自动提升，不容易炸；
  但 `malloc(v * v * sizeof(int))` 里 `v * v` 两个都是 int，**在乘完就溢出了**，
  sizeof 救不回来。养成"参与乘法的整数先转 size_t"的肌肉记忆。

**对应代码**：`glist.c:179`。

### 2. `glist_add_edge(g, a, b)` —— 加一条无向边（glist.c:285）

**干什么**：往 a 的链尾挂 `dest=b` 的节点，往 b 的链尾挂 `dest=a` 的节点，`e++`。

**一步步**：
1. 判空、判越界、判自环。
2. 用 `glist_has_edge` 顺链查一遍这条边是否已存在（O(度)）。
3. `node_push_back(&g->adj[a], b)`。
4. `node_push_back(&g->adj[b], a)` —— **万一这步失败，把第 3 步挂上的节点摘掉（回滚）**。
5. 两步都成功才 `g->e++`。

**边界情况 / 为什么这么写**：
- **为什么传 `&g->adj[a]` 而不是 `g->adj[a]`？**
  因为头插、或者插到空链时，要改的是**表头指针这个变量本身**。
  传 `g->adj[a]`（一个 `Node*` 值）进去，函数里 `head = 新节点` 改的只是拷贝，
  出来一看表头还是 NULL —— 节点挂在堆上没人认领，直接泄漏。
  这就是 00-c-foundation 那条铁律的第三次出场：**想改外面的指针，就传指针的地址。**
  `adj` 是"指针数组"，`&adj[i]` 是"指向指针的指针"，所以函数签名写 `Node **head` 是**必然**，
  不是风格问题。
- **为什么第 4 步失败要回滚？** 不回滚的话图会变成"a 的链里有 b，b 的链里没有 a"。
  这种**不对称状态**比崩溃可怕：从 a 做 BFS 能到 b，从 b 做 BFS 到不了 a，
  连通分量个数取决于你从哪个点开始遍历 —— 一个"结果随输入顺序变化"的 bug 极难定位。
- **平行边（重边）**：本实现**主动拒绝**。注意这和矩阵不同 ——
  邻接表**技术上完全能**表达重边（一条链上挂两个 `dest` 相同的节点），
  矩阵不行（一格只能有一个数）。我们把重边拦掉只是因为示例图是简单无向图。
  真要支持（比如两城之间多班航班），删掉第 2 步即可，但那时"边数 e"和
  "节点数/2"的等式关系要重新定义。

### 3. `glist_has_edge(g, a, b)` —— 判边：本节最该记住的短板（glist.c:380）

**干什么**：顺 `adj[a]` 这条链一格一格走，看有没有哪个节点 `dest == b`。

**一步步**：判空 → 判越界 → `for (p = adj[a]; p; p = p->next) if (p->dest == b) return 1;` → `return 0`。

**边界情况 / 为什么这么写**：
- 复杂度 **O(度(a))**，最坏 O(V)。矩阵是 O(1)。
  这一行的差距决定算法选型：Floyd 那种三重循环，内层核心就是判边，
  用邻接表会把 O(V³) 活活拖成 O(V⁴)。
- `a` 是孤立点时 `adj[a] == NULL`，循环体一次都不执行，直接返回 0 ——
  这就是"空链"在链表写法里的天然优雅之处，不需要特判。
- 参数 `const GList *g` 加上 `const Node *p`：承诺只读。
  查询函数一律写 const，误改时编译器立刻报错。

### 4. `glist_degree(g, u)` / `glist_node_count(g)` —— 查度与自检（glist.c:412 / 426）

**干什么**：`degree` 数 `adj[u]` 那条链多长；`node_count` 数全图一共几个节点。

**边界情况 / 为什么这么写**：
- 度 = 链长，O(度)。比矩阵的 O(V) 快 —— 因为链上**只有真邻居**，没有一堆 0 要跳过。
- 有向图这里数出来的是**出度**；入度要 O(V+E) 全表扫。
- `node_count` 存在的唯一理由是验证等式 **节点总数 == 度之和 == 2×边数**。
  每次 `glist_print` 都顺手打这四个数字，等于给每次改图做完就自检一遍。
  写数据结构时，**能白送的断言一定要白送**。

### 5. `glist_remove_edge(g, a, b)` —— 删边，第 02 章按值删的实战（glist.c:455）

**干什么**：在 a 的链里摘掉 `dest==b` 那个节点并 free，在 b 的链里摘掉 `dest==a` 那个，两个都成功才 `e--`。

**一步步（核心在 `node_remove_val`，glist.c:118）**：
1. 栈上造一个假节点 `dummy`，让 `dummy.next = *head`。它不 malloc，所以不需要 free。
2. `prev = &dummy`，然后**永远只看 `prev->next`**：
   - 命中 → `victim = prev->next; prev->next = victim->next; free(victim);`
   - 未命中 → `prev = prev->next`
3. 结束（或命中后）统一 `*head = dummy.next;` 写回头指针。

**为什么这么绕？—— dummy 哨兵的价值**：
删头节点要改的是 `*head` 本身，删中间节点要改的是"前驱的 next"。两种情况写法不同，
很容易漏一种。塞一个假前驱 dummy 进去，头节点就变成了"dummy 的后继"，
于是**删头 / 删中 / 删尾三种情况被同一个循环同一套逻辑吃掉了**：

```
   dummy ─►[5]─►[3]─►[7]─►NULL        要删 5（就是头）
      ▲      ▲
      └ prev ┘        ← prev 永远站在"要删的那个"前面一格
   执行 prev->next = victim->next  →  dummy ─►[3]─►[7]
   再 *head = dummy.next           →  头指针换成 3 ✅
```

运行结果第 5 幕末尾把这段手工执行了一遍，并且打印了 `list` 的前后地址 ——
你会看到头指针真的变了，这就是"为什么必须传 `Node **`"的现场证据。

**边界情况 / 为什么这么写**：
- **顺序：先跨接，再 free。** 反过来写成 `free(victim); prev->next = victim->next;`
  就是 **use-after-free**，ASan 会当场打死你。
- **找不到**：`node_remove_val` 返回 0。`glist_remove_edge` 里若只摘成功一边
  （`ok1 != ok2`），会打印 `[警告]` 并且**不动 `e`** —— 图已经是半截状态，
  宁可大声报告，也不要悄悄给出一个错的边数。
- 对比矩阵：矩阵删边是"涂两格"O(1) 且不涉及内存；这里 O(度) 且要 free。
  这就是"省空间"的代价。

### 6. `glist_free(g)` —— 逐顶点逐节点剥干净（glist.c:239）

**干什么**：把三层内存倒着全部还给系统，要求 ASan 报 0 泄漏。

**一步步**：
1. `g == NULL` 直接返回（`free(NULL)` 本来就合法）。
2. 外层 `for i in 0..v-1`：逐个顶点。
3. 内层遍历该链，**三步走**：
   `nxt = cur->next;` → `free(cur);` → `cur = nxt;`
4. `g->adj[i] = NULL;` 表头置空。
5. `free(g->adj); g->adj = NULL;` 再 `g->v = 0; g->e = 0;` 最后 `free(g);`

**边界情况 / 为什么这么写**：
- **为什么必须先剥节点再剥数组？** free 掉 `adj` 数组之后，
  你就再也拿不到那些节点的地址了 —— 拿不到地址的堆内存 = **永久泄漏**。
  多级结构的释放顺序永远是"**从最里层往外剥**"。
- **为什么内层要先把 `cur->next` 抄进 `nxt`？**
  因为 `free(cur)` 之后 `cur->next` 已经是别人的内存了，读它就是 use-after-free。
  写成 `free(cur); cur = cur->next;` 是最自然的错法，ASan 一抓一个准。
- **为什么 free 完要置 NULL？** 函数里的 `g` 是拷贝，置 NULL 只能保护本函数内
  后续几行；真正的保护要靠调用方也置 NULL（运行结果第 4 幕的
  `build_front_version_demo` 里就演示了 `glist_free(gf); gf = NULL;`）。
  置 NULL 的价值在于：误用会**立刻崩**，而不是悄悄读到已归还的内存给出诡异答案。

### 7. `glist_sample()` —— 造出共用示例图 G（glist.c:549）

**干什么**：把 G 那 7 条边原样建出来，返回 malloc 的图（**调用者负责 free**）。

**这里藏着一个关于"顺序"的坑，值得单独讲**：
尾插保住的是**加边顺序**，不是**编号升序**。
如果照邻接矩阵那节的加边顺序 `(0,1)(1,2)(0,2)(2,3)` 来建，2 号点的链会变成

```
   [1] -> [0] -> [3]      ← 1 先挂（来自 (1,2)），0 后挂（来自 (0,2)）：不是升序！
```

而矩阵那一节里 2 的邻居清单天生是 `0 1 3`（因为后面 bfs/dfs 是按 `j = 0..V-1` 扫行，
顺序必然是升序）。两边对不上，就没法并排核对。
所以本节把**同一批边**重排成：

```
   (0,1) (0,2) (1,2) (2,3) (4,5) (4,6) (5,6)
```

排完每个顶点的链表自动全部升序：`0:[1,2] 1:[0,2] 2:[0,1,3] 3:[2] 4:[5,6] 5:[4,6] 6:[4,5] 7:[]`。
规律是"对顶点 u，那些'邻居比 u 小'的边要最早加"。
真实工程里没人这么排（要么不在乎顺序，要么建完再对每条链排序），
我们做这一步**只为了让输出可复现、可逐行核对**。教学场景里，顺序本身就是价值。

V = 顶点数，E = 边数。加粗的是这一列的赢家。

| 操作 | 邻接表 | 邻接矩阵 | 边集数组 |
|---|---|---|---|
| 建图（初始化） | **O(V)** | O(V²) 要清 V² 格 | **O(V)** |
| 加边 | **O(1)**（头插）/ O(度)（尾插） | O(1) | **O(1)** |
| 删边 | O(度)：找前驱 + free | **O(1)** | O(E) |
| **判两点有没有边** | O(度)，最坏 O(V) | **O(1)** ✅ | O(E) |
| **枚举一个点的全部邻居** | **O(度)** ✅ | O(V)：整行扫，多数是 0 | O(E) |
| **遍历全图所有边** | **O(V+E)** ✅ | O(V²) | O(E) |
| BFS / DFS 总复杂度 | **O(V+E)** | O(V²) | 不适用 |
| 空间 | **O(V+E)** ✅ | O(V²) | O(E) |
| 支持平行边（重边） | **✅** 链上挂两个节点 | ❌ 一格只能存一个值 | ✅ |
| 查入度（有向图） | O(V+E) ❌ 要逆邻接表 | **O(V)** 数一列 | O(E) |
| 缓存友好度 | 差（节点散落堆上，指针跳转） | **好（一整块连续内存）** | 中 |
| 内存确定性 | 每节点一次 malloc，碎片 + 泄漏风险 | **一次分配，没有 free 责任** | 少 |

看这张表最容易被忽略的两行：
- **缓存友好度**：矩阵虽然要扫更多格子，但格子是连续内存，CPU 预取很有效率；
  链表每走一格一次指针跳转。所以小规模图上"链表更快"经常是错觉。
- **内存确定性**：矩阵那一节整个 main 没有一次 malloc，ASan 天然 0 泄漏；
  本节三层分配 + 逐节点 free，是本章第一次真正考验你的内存管理纪律。

## 常见的坑

1. **`free(cur)` 之后才去读 `cur->next`**（链表第一大坑）。
   正确顺序永远是三步：**抄下 next → free 当前 → 跳到抄下来的地址**。
   写反就是 use-after-free。ASan 会直接报 `heap-use-after-free` 并打死程序。

2. **只传 `Node *head`，删头节点后外面看不见**。
   `head = head->next;` 改的是函数自己的拷贝。所有会"换头"的操作必须传 `Node **head`，
   调用时写 `&g->adj[i]`。运行结果第 5 幕打印了头指针的前后地址，就是这个道理的证据。

3. **新节点忘了 `next = NULL`**。
   malloc 不初始化，next 里是垃圾地址。建表时看起来正常（你可能恰好没遍历到它），
   一旦遍历到那格就是野指针。`node_new` 里把 `next = NULL` 和赋值绑在一起做掉，
   比"每个调用点记得检查"可靠得多。

4. **无向图只挂了一边**。
   只在 `adj[a]` 挂了 `dest=b`，忘了 `adj[b]` 挂 `dest=a`。
   现象：`has_edge(b,a)` 返回 0、从 b 出发 BFS 漏掉 a、度不对称。
   **自检法**：`节点总数 == 度之和 == 2×边数`，`glist_print` 每次都顺手验了。

5. **free 了 `adj` 数组却没 free 链表节点**（本节最容易的泄漏）。
   两级结构必须**从最里层往外剥**。只 `free(g->adj)` 的话，
   ASan 会报 `224 bytes in 14 objects` 之类的 definite loss —— 泄漏报告里
   的对象数量就是线索，14 正好是节点个数。

6. **忘了 free 就 return，或者 `glist_sample()` 的返回值不接住**。
   `GList *g = glist_sample();` 之后每条出口路径（包括出错提前 return）都要先 free。
   C 没有析构函数，没有智能指针，"谁 malloc 谁 free"是纪律不是建议。

7. **把"尾插"当成"升序插入"**。
   尾插只保住加边顺序。想要邻居清单升序，要么把加边顺序排好
   （见 `glist_sample` 注释里的推导），要么建完再对每条链排序，
   要么改成"按序插入"（O(度) 但结果天生有序）。

8. **有向图想用邻接表查入度，结果每问一次就 O(V+E) 全扫**。
   要么额外维护 `indegree[]` 数组（拓扑排序那节就这么干），
   要么再建一张所有边反向的"逆邻接表"。数据结构的短板不会因为选了"更好的表示法"消失，
   只能靠**补一份冗余数据**来换。

## 什么时候用它 / 什么时候别用

**该用邻接表：**
- **稀疏图**（现实里绝大多数图：社交网络、网页链接、路网、依赖关系、调用图）。
  E 和 V 同量级，矩阵会炸，邻接表毫发无伤。
- **算法的核心动作是"走邻居"**：BFS、DFS、连通分量、拓扑排序、
  Dijkstra / Prim / Kruskal 的松弛过程 —— 全都是"枚举当前点的所有邻居"，
  邻接表是 O(度)，矩阵是 O(V)。**总复杂度直接差一个 V/E 的因子。**
- **顶点数会动态增长**：来一个点加一条链，不用整体搬家。
- **顶点编号稀疏**：ID 是 10 亿级的用户 ID，只需要 100 个表头 + 一张映射表，
  不像矩阵要开 10 亿 × 10 亿。
- **需要平行边**：两城之间多班航班，矩阵一格存不下，链表爱挂几个挂几个。

**别用邻接表：**
- **要海量判边**：Floyd 三重循环、判断"是不是完全图"。
  O(度) 的判边会把复杂度整体抬一个档次 —— 这类场景该用矩阵。
- **稠密图**：E 接近 V²/2 时，邻接表的 `next` 指针开始反噬
  （每个节点 16 字节只为记一个 int），矩阵 4 字节一格更省，还白送 O(1) 判边。
- **怕内存管理**：本节这种三层 malloc 的结构，泄漏/use-after-free/双重 free
  三种事故都可能。而矩阵那节一次 malloc 都没有。
- **在意常数**：链表节点散落在堆上，缓存命中差；矩阵是一整块连续内存。

**决策一句话**：**算法要"问一对点"就用矩阵，要"走一圈邻居"就用邻接表。**
两个都要？很多竞赛和工程代码的做法是**同时建两份**（矩阵 + 邻接表），
空间换时间，用得起就换。

## 自检问题

1. 为什么 `node_push_back` 的参数是 `Node **head` 而不是 `Node *head`？
   **答**：因为"插入到空链"和"头插"都要改**表头指针变量本身**。
   传 `Node *head` 时函数拿到的是一份拷贝，改它改不到 `g->adj[i]`，
   新节点挂在堆上没有任何指针指向它 —— 既看不见（功能上等于没插），
   又 free 不掉（内存泄漏）。C 语言铁律：**想改外面的变量，就传它的地址。**

2. 一张 V=8、E=7 的无向图，邻接表里一共有几个链表节点？多少字节？
   **答**：14 个节点（一条边两端各挂一个），`14 × sizeof(Node) = 14 × 16 = 224` 字节，
   加 8 个头指针 64 字节 = 288 字节（再加 GList 结构体 16 字节 = 304 字节）。
   注意比邻接矩阵的 256 字节**还大** —— 所以"邻接表更省空间"这句话
   只在**大图/稀疏图**上成立，别无条件背下来。

3. 用邻接表做 BFS，总复杂度为什么是 O(V+E) 而不是 O(V×度)？
   **答**：每个顶点最多入队一次（因为有 visited 标记），共 V 次；
   每次出队时扫它那条链，**每条边最多被扫两次**（无向图两端各一次）→ 2E。
   合计 O(V+E)。关键在于"扫链"的代价是**按边数摊的**，不是按 V 摊的 ——
   这正是邻接表相对矩阵（每点都要扫 V 格 → O(V²)）的根本优势。

4. `free(victim); prev->next = victim->next;` 这两行写反顺序会怎样？
   **答**：use-after-free。`victim` 已经还给堆管理器，读 `victim->next`
   是访问不属于自己的内存。ASan 会报 `heap-use-after-free` 并终止程序；
   没有 ASan 时可能"看起来正常"很久，直到某次 malloc 把那块复用掉、
   你读到一个全新的值，链表凭空接错地方 —— 这类 bug 几乎不可能靠看代码找到。

5. 有向图的邻接表，出度和入度哪个好用哪个难用？为什么拓扑排序那一节要额外维护一个 `indegree[]` 数组？
   **答**：邻接表的链是"我指向谁"，所以**出度 = 链长（O(度)）**；
   入度是"谁指向我"，链上根本没记，只能把所有顶点的链全扫一遍数挂着 u 的节点，
   O(V+E)，问一次就这么贵。拓扑排序要反复查、反复减入度，所以
   **一次性预计算一个 `indegree[V]` 数组**，把每次查询降到 O(1)。
   代价是"冗余数据要维护" —— 加边删边都得同步更新它，漏一处就和真实图不一致了。
