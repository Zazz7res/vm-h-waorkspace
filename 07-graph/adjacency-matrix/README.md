# 邻接矩阵 adjacency-matrix

> 用一张 V×V 的二维数组把整张图摊平，判断两点有没有边只要**看一眼格子**。
> 它不是"最简单的图表示"，它是"唯一能让你 O(1) 判边的图表示"。

---

## 一句话是什么

**给每个顶点一个编号 0..V-1，然后开一张 V 行 V 列的表：`edge[i][j] = 1` 就表示"i 和 j 之间有一条边"，`0` 表示"没有"。**

图这件事到此就变成了一道查表题。没有指针、没有链表、没有"顺着找"，
所有信息都躺在一段连续内存里，位置由编号直接算出来。

一句话记忆：**邻接矩阵 = 图的乘法表。**

---

## 为什么需要它

先看**不用它**会有多痛。假设你手上只有"边集数组"（把每条边存成一对对 `{a, b}`）：

| 你想干的事 | 只有边集数组时 | 有邻接矩阵时 |
|---|---|---|
| 问"3 号和 7 号之间有没有边" | 从头扫到尾，一条一条比 → **O(E)**，E=20 万就要比 20 万次 | 取 `edge[3][7]` → **O(1)**，一次访存 |
| 问"删掉边 (3,7) 之后呢" | 还是全扫一遍找它 | 直接把两格涂 0 → **O(1)** |
| Floyd 三重循环里问"i 经过 k 能不能到 j" | 内层每次 O(E) → 总复杂度 O(V³·E) 直接爆炸 | 每次 O(1) → 干净地留在 O(V³) |
| 看"i 的所有邻居" | 全扫一遍 | 扫第 i 行 → O(V) |

第三行就是邻接矩阵存在的理由：**当你需要海量地、反复地问"这两点连没连"，
只有查表能救你。**后面 `floyd/` 那一节整个算法就是建立在这个 O(1) 上的，
换成链表表示那个三重循环会慢到不能用。

代价也很实在：**表的面积只跟顶点数有关，跟边数一点关系都没有。**
8 个顶点要 64 格，10 万个顶点要 100 亿格 —— 哪怕这 10 万个点之间只有 20 万条边。
这笔账在本文末尾「运行结果」里会算给你看（40 GB vs 6.87 MB，差 5555 倍），
**看完那笔账你才知道自己什么时候不该用它**。

## 内存布局图解

### 示例图 G（本章所有目录共用同一张图）

```
  无向图 G：8 个顶点 0..7，7 条边，故意不连通

  分量一：0-1, 1-2, 2-0, 2-3       （0、1、2 成环 + 挂着 3）
  分量二：4-5, 5-6, 6-4            （另一个环）
  孤立点：7                         （谁也不连）

        0 ───── 1                     4 ───── 5
         \     / \                     \     /
          \   /   \                     \   /
           2 ──────                     6          7 ← 孤零零
            \
             3
```

### 它在内存里长这样：一张表，横竖都是顶点编号

```
            j（终点）→
          0   1   2   3   4   5   6   7
        ┌───┬───┬───┬───┬───┬───┬───┬───┐
   i    │ 0 │ 1 │ 1 │ 0 │ 0 │ 0 │ 0 │ 0 │  0 ← 行：0 的邻居清单 = {1, 2}
   （   ├───┼───┼───┼───┼───┼───┼───┼───┤
   起    │ 1 │ 0 │ 1 │ 0 │ 0 │ 0 │ 0 │ 0 │  1 ← {0, 2}
   点   ├───┼───┼───┼───┼───┼───┼───┼───┤
   ）    │ 1 │ 1 │ 0 │ 1 │ 0 │ 0 │ 0 │ 0 │  2 ← {0, 1, 3}  本图度最大
        ├───┼───┼───┼───┼───┼───┼───┼───┤
        │ 0 │ 0 │ 1 │ 0 │ 0 │ 0 │ 0 │ 0 │  3 ← {2}  叶子
        ├───┼───┼───┼───┼───┼───┼───┼───┤
        │ 0 │ 0 │ 0 │ 0 │ 0 │ 1 │ 1 │ 0 │  4 ← {5, 6}
        ├───┼───┼───┼───┼───┼───┼───┼───┤
        │ 0 │ 0 │ 0 │ 0 │ 1 │ 0 │ 1 │ 0 │  5 ← {4, 6}
        ├───┼───┼───┼───┼───┼───┼───┼───┤
        │ 0 │ 0 │ 0 │ 0 │ 1 │ 1 │ 0 │ 0 │  6 ← {4, 5}
        ├───┼───┼───┼───┼───┼───┼───┼───┤
        │ 0 │ 0 │ 0 │ 0 │ 0 │ 0 │ 0 │ 0 │  7 ← 整行全 0 = 孤立点
        └───┴───┴───┴───┴───┴───┴───┴───┘
              ▲                        ▲
              └── 沿这条对角线镜像对称 ──┘
                  （因为无向边 (i,j) 和 (j,i) 是同一条）
```

读法只有两句：
- **看一行** = 看"这个点的邻居清单" → 数一数这一行有几个 1，就是**度**。
- **看一格** = 问"这两点连没连" → `edge[i][j]`，直接有答案，**不用找**。

### 物理视角：它真的只是一段连续的 64 个 int

```
  地址低 ────────────────────────────────────────────────────► 地址高
  ┌──────────────────┬──────────────────┬──────────────────┬─────┐
  │ 第 0 行 8 个 int │ 第 1 行 8 个 int │ 第 2 行 8 个 int │ ... │
  └──────────────────┴──────────────────┴──────────────────┴─────┘
   共 64 格 × 4 字节 = 256 字节，一次 malloc/一个栈上结构体就搞定

  edge[i][j] 的地址 = 基址 + (i * V + j) * sizeof(int)
                    = 一次乘法 + 一次加法 + 一次访存
```

这就是 O(1) 判边的**物理来源**：答案所在位置可以**算**出来，所以不需要**找**。
邻接表做不到这点，因为它的位置得靠指针一跳一跳走。

### 带权版：形状不变，只是"读法"变了

```
  无权： edge[i][j] =  0 / 1        →  0 表示无边
  带权：   w[i][j]  = -1 / 权值     → -1 表示无边，权值可以是 0！

  带权矩阵（0 到 4 号点，(1,2) 这条边权值是 0，代表"免费/零距离"）：
          j=    0   1   2   3   4
      i=0    [   -1   7  -1  -1  -1 ]
      i=1    [    7  -1   0  -1 999 ]      ← 这个 0 是"真边"，不是"无边"
      i=2    [   -1   0  -1  15  -1 ]
      i=3    [   -1  -1  15  -1 120 ]
      i=4    [   -1 999  -1 120  -1 ]

  ★ 为什么"无边"不能用 0 表示？
     因为 0 是一个完全合法的权值：两点距离 0、票价 0 元、任务耗时 0。
     一旦让 0 兼任"无边"，程序读到 0 时无法区分是"没有这条路"还是
     "有一条免费的路"。把免费的路当成不存在，最短路就会舍近求远绕过去，
     而且逻辑没错、数据没错 —— 纯粹是**标记选错**，这类 bug 极难查。
     所以标准做法：拿一个"业务上永远不会出现的值"专门当哨兵。
     你已经见过很多次了：字符串结尾的 '\0'、EOF = -1、
     查找失败返回 -1。思想是一模一样的。
```

## 核心操作逐个拆解

### 1. `gmatrix_init(g, v)` —— 建一张空图（gmatrix.c:64）

**干什么**：把 64 个格子全部清零，记下顶点数 `v`，边数 `e` 归 0。

**一步步怎么做**：
1. 判空指针。
2. 检查 `0 <= v <= GM_MAX_V`；超了就把 `v` 设成 0（宁可建一张空图，也绝不越界写内存）。
3. 双层循环把 `edge[i][j]` 全写 0。
4. `g->v = v; g->e = 0;`

**边界情况 / 为什么这么写**：
- **为什么必须手动清零？** 因为 `GMatrix g;` 是 main 里的**栈上局部变量**，
  C 语言不保证栈内存初值是 0 —— 里面是上一次函数调用留下的垃圾。
  不清零的话，某些格子随机为 1，程序会认为"这里有条边"，于是你查一条
  从没加过的边它说有，度和边数全乱；换台机器、换个调用顺序，结果还不一样。
  （如果写成全局变量，C 保证静态区初始全 0，就不会有这问题。
  但"靠语言保证"不如自己清零直观，教材代码一律自己清。）
- `v` 传 8 是上限，因为数组尺寸编译期就写死成 `GM_MAX_V = 8`。

**对应代码行**：`gmatrix.c:64` 函数开头，清零的双层循环在 `gmatrix.c:85` 附近。

---

### 2. `gmatrix_add_edge(g, a, b)` —— 加一条无向边（gmatrix.c:121）

**干什么**：`edge[a][b] = 1` **并且** `edge[b][a] = 1`，边数 +1。返回 1 表示真加上了。

**一步步怎么做**：
1. 判空。
2. 检查 `a`、`b` 都在 `[0, v)` 内。
3. 检查 `a != b`（本节禁止自环）。
4. 检查这条边是否已存在（存在就返回 0，什么都不改）。
5. **两格同时置 1**，`g->e++`。

**边界情况 / 为什么这么写**：
- **只写一格会怎样？这是邻接矩阵的头号 bug。**
  第 i 行的含义是"i 的邻居清单"。只写 `edge[a][b]=1` 而不写 `edge[b][a]=1`，
  那么"从 a 能找到 b，从 b 找不到 a"。后果是：从 b 出发的 BFS/DFS 会漏掉 a
  那一整片、连通分量个数算错、度也算错。
  有向图才只写一格（因为 i→j 不代表 j→i）。
- **重复加同一条边**：返回 0 且不改 `e`（幂等）。否则你加两次，
  边数就虚报成 2，而矩阵里其实只有一个 1。
- **自环**：返回 0。真实场景里自环有时合法，那时去掉这条检查即可；
  这里禁掉是为了让对角线保持全 0，一眼看得清。
- **越界**：打印错误并返回 0。绝不能让 `edge[8][0]` 真的被执行 ——
  越界写是未定义行为，比逻辑错误可怕得多。

---

### 3. `gmatrix_has_edge(g, a, b)` —— 判边，本节的主角（gmatrix.c:201）

**干什么**：回答"顶点 a 和 b 之间有没有边"。

**一步步怎么做**：判空 → 判越界 → `return g->edge[a][b];` 就完了。

**边界情况 / 为什么这么写**：
- 越界时**返回 0 而不是去读内存**。这一步不是形式主义：`v=4` 的图被误问 `(7,0)`，
  不检查就会去读 `edge[7][0]`；因为我们数组固定 8×8，这次恰好没越界，但读到的是
  语义上无意义的垃圾。"固定数组的巧合"会让 bug 悄悄活很久 —— 检查要按
  "真实顶点范围"来做，而不是按"数组开多大"来做。
- 参数是 `const GMatrix *g`：承诺只读不改。写错了（比如误写 `g->edge[a][b]=1`）
  编译器立刻报错，这是 `const` 唯一真正值钱的地方。

---

### 4. `gmatrix_degree(g, u)` —— 查度（gmatrix.c:232）

**干什么**：数第 `u` 行里有几个 1。

**一步步怎么做**：判越界 → `for j in 0..v-1: if (edge[u][j]) cnt++;`

**边界情况 / 为什么这么写**：
- 为什么是 **O(V)** 而不是 O(1)？因为一行有 V 个格子，我们老老实实数。
  （进阶：加边时顺手维护一个 `deg[]` 数组就能降到 O(1)，代价是加/删都要多改一格。
  这就是"用空间换时间"—— 拓扑排序那一节我们真的会维护一个 `indegree[]`。）
- 无向图行和列一样，数行数列数结果相同。**有向图必须分清**：
  出度 = 数第 u 行，入度 = 数第 u 列。
- u 越界返回 0。

`gmatrix_print_degrees()`（gmatrix.c:260）顺便做一次**免费的自检**：
把度之和跟 2×边数 对比。这就是**握手定理**：每条边有两个端点，
所以度之和必然等于 2E。本图 14 == 2×7 ✅。
**算出来不等，就说明你加边时漏了对称那一格** —— 用它当测试断言非常划算。

---

### 5. `gmatrix_remove_edge(g, a, b)` —— 删边（gmatrix.c:160）

**干什么**：把 `edge[a][b]` 和 `edge[b][a]` 都涂回 0，`e--`。

**一步步怎么做**：判空 → 判越界 → 若本来就是 0 就返回 0（**不减 e**）→ 涂两格 → `e--`。

**边界情况 / 为什么这么写**：
- 删不存在的边如果不拦住，`e` 会被减成**负数**，之后所有"边数"统计一起废掉。
- 删边在矩阵里是"两笔涂改"，**O(1)**；换成邻接表就得顺着链表找前驱、改 `next`
  （第 02 章那套指针手术）。对比着看才知道矩阵有多省心。

---

### 6. `gmatrix_print(g)` —— 把表打出来（gmatrix.c:302）

**干什么**：带行号列号打印整张表。没有算法含量，但它是本节最有价值的函数 ——
初学者对"图"最缺的就是"它在内存里长什么样"的画面。

**几个排版细节**（写 demo 的基本功）：
- 用 `%3d` 固定列宽：值虽然是 1 位数，但 V 一大列号就变 2 位，
  不定宽表格立刻错位。
- 行号用 `%-4d`（`-` 是左对齐），让所有 `[` 竖着排成一列。
- 对角线打成 `.`，主动提醒"这里必须是 0"。
- ⚠ 踩过的坑：**别用中文符号当表格占位符**。`·`、`（` 这类字符终端显示占 2 列、
  但 UTF-8 编码占 3 字节，而 `printf` 的 `%3s` 是按**字节**补空格的，
  所以混着用必然错位（第一版就翻车成了 `·999` 挤成一坨）。
  表格里的占位符一律用 ASCII；本节最后干脆把带权矩阵的 `-1` 原样打印，
  让"屏幕上的表"和"内存里的表"逐格一致，你才核对得起来。

### 7. `gmatrix_sample(g)` —— 造出共用示例图 G（gmatrix.c:344）

**干什么**：硬编码那 7 条边，把 G 原样建出来。

**为什么全是固定数据、不搞随机**：
图算法的 bug 往往只在特定结构上出现（成环、不连通、孤立点）。
随机图每次跑都不一样，你既没法复现现场，README 里也没法贴确定输出。
所以这张图被刻意设计成"每处都有讲究"：
- `0-1-2` 成环 → 用来演示判环、演示 BFS 里"邻居已经访问过"的情况
- `3` 只挂在 `2` 上 → 度 1 的叶子，用来演示 DFS"走到底再回头"
- `4-5-6` 另一个环 → 用来演示"必须对每个未访问点再起一次遍历"
- `7` 孤立 → 用来演示"BFS 从 0 出发访问不到它"，引出连通分量

后面 `bfs/`、`dfs/`、`connected-components/` 用的都是**同一张图**，
你可以横向对照：同一张图，换个容器、换个遍历，看到的东西不一样。

### 8. `gmatrix_space_report(v, e)` —— 算账（gmatrix.c:397）

**干什么**：把"浪费"变成三个能核实的数字：矩阵格子数、真正非 0 的格子数、浪费率；
再算同一张图用邻接表要多少字节。

**为什么强调"必须算账"**：
「邻接矩阵浪费空间」这句话谁都会背，**不写数字的结论不算结论**。
跑出来（完整见文末「运行结果」）：

| 场景 | 矩阵格子 | 矩阵内存 | 非 0 格 | 浪费率 | 邻接表 | 倍率 |
|---|---|---|---|---|---|---|
| V=8, E=7（我们的图） | 64 | 256 B | 14 | 78.125% | **288 B** | 0.9× |
| V=8, E=28（满图） | 64 | 256 B | 56 | 12.500% | 960 B | 0.3× |
| V=10万, E=20万 | 100 亿 | **40.00 GB** | 40 万 | 99.996% | **6.87 MB** | **5555.6×** |

三行数字给出三个结论，而且第二行大多数人没意识到：
1. 第三行是"稀疏图别用矩阵"的全部理由：40 GB vs 6.87 MB。
2. **第一行反过来**：8 个点 7 条边的小图，邻接表（288 B）比矩阵（256 B）**还大**，
   因为每个链表节点都要多背一个 8 字节的 `next` 指针。**别条件反射地以为链表更省。**
3. 第二行是稠密图：浪费率只剩 12.5%，而且那 12.5% 全是对角线（自己到自己，
   天生存不了信息），其余格子格格有用 → 这时候矩阵又省又快。

**代码里的两个 C 语言要点**：
- 全程用 `unsigned long long` 算。`1e10` 远超 `INT_MAX`（约 2.1×10⁹），
  用 `int` 存会**溢出成负数**，你会得出"矩阵占 -2 GB"这种荒唐结论 ——
  这是 C 里最典型的**静默 bug**，编译器不会警告你。
- 邻接表节点按 `sizeof(DemoNode)` 算，**不是**按"4 + 8 = 12"算：64 位机上
  指针要 8 字节对齐，编译器在 `int` 后塞了 4 字节 padding，真实是 **16 字节**。
  算内存必须按 `sizeof` 算，别按手加的字节数算。

## 复杂度表

横向对比三种图的表示法（V = 顶点数，E = 边数）。
注意"加边"和"判边"这两个优势项全在矩阵这边，"遍历邻居"和"空间"这两项全输。

| 操作 | 邻接矩阵 | 邻接表 | 边集数组 |
|---|---|---|---|
| 建图（初始化） | O(V²) 要清 V² 格 | O(V) | O(E) |
| **判两点有没有边** | **O(1)** ✅ | O(度) ，最坏 O(V) | O(E) |
| 加边 | O(1) | O(1)（头插）/ O(度)（尾插） | O(1) |
| 删边 | **O(1)**（已知是哪两点） | O(度) 要顺着链表找 | O(E) |
| **枚举一个点的全部邻居** | O(V)（整行扫，多数是 0） | **O(度)** ✅ | O(E) |
| **遍历全图所有边** | **O(V²)** | **O(V + E)** ✅ | O(E) |
| BFS / DFS 总复杂度 | O(V²) | O(V + E) | 不适用 |
| 空间 | **O(V²)** | **O(V + E)** ✅ | O(E) |
| 支持平行边（重边） | ❌ 一格只能存一个值 | ✅ 链上挂两个节点 | ✅ |
| 支持自环 | ✅（对角线） | ✅ | ✅ |
| 判图是否连通 | O(V²) | O(V + E) | — |

一句话总结这张表：
- **矩阵赢在"随机问一对点"**（判边/删边 O(1)）和**稠密图**。
- **邻接表赢在"批量走邻居"**（遍历 O(V+E)）和**稀疏图**。
- V² 项什么时候致命？看上面那笔 40 GB 的账。

## 常见的坑

1. **无向图只写了一格**（头号坑）。
   只写 `edge[a][b]=1` 忘了 `edge[b][a]=1`。现象很隐蔽：图"看起来"建好了，
   但从 b 出发找不到 a，BFS 少一片、连通分量多算几个、度不对称。
   **自检法**：打印度之和，看它是否等于 2×边数（握手定理），一测就穿。

2. **把顶点编号和顶点"内容"搞混**。
   矩阵里只有编号，`edge[3][6]` 是"3 号和 6 号之间"。如果外面传进来的
   3 其实是"名字为 3 的人"，而内部编号是 0..V-1，就需要一张
   `名字 → 编号` 的映射表。忘记映射，就会出现"最大编号 1000 却只有 5 个点"
   —— 于是你为了存 5 个点开了 1001×1001 的表。**稀疏编号是邻接矩阵炸掉的常见方式。**

3. **`V*V` 用 `int` 存，静默溢出**。
   `100000 * 100000 = 1e10` 超过 `INT_MAX`（约 2.1e9），结果变成负数，
   你会算出"矩阵占 -2 GB"或者 `malloc` 了一个小得离谱的空间然后越界。
   要写 `(long long)v * v` 或 `size_t`。**注意还要先乘再 sizeof**：
   `v * v * sizeof(int)` 里前两项都是 int，乘法在溢出之后才轮到 `sizeof`，
   救不回来。正确写法是 `(size_t)v * v * sizeof(int)`。

4. **带权图拿 0 当"无边"**。
   见正文：权值为 0 的合法边会被当成不存在。选哨兵要选业务上不会出现的值（-1），
   或者用 `INT_MAX` 表示无穷大 —— 但用 `INT_MAX` 时**两条边相加会溢出**，
   `dijkstra/bellman-ford` 那一节会专门讲这个坑（要先判断"是不是无穷大"再加）。

5. **memset/清零漏了，直接用栈上的结构体**。
   栈内存不保证是 0，随机垃圾会被读成"有边"。要么自己双层循环清零，
   要么用 `calloc`，要么声明成全局/`static`（静态区保证初始为 0）。

6. **忘了 `v` 上限检查，下标越界**。
   `GM_MAX_V = 8` 的数组，`add_edge(1, 100)` 一旦不拦就写飞了。
   更阴的是：因为数组固定 8×8，`edge[7][0]` 这种"超出语义但没超出物理"的访问
   **不会崩**，只会安静地给出错误答案。检查要按语义（`v`）做，不是按数组大小做。

7. **误以为"邻接表一定比矩阵省"**。
   算账那一节第一行就是反例：V=8、E=7 时邻接表 288 字节 > 矩阵 256 字节，
   因为每个链表节点要多背 8 字节 `next`。省不省，要看 **密度**，不是看名字。

## 什么时候用它 / 什么时候别用

**该用邻接矩阵：**
- **需要海量判边**：Floyd、判断"完全图"、检查某条约束边在不在 —— 只要核心操作是
  "i 和 j 连了吗"，矩阵是唯一 O(1) 的答案。
- **稠密图**：E 接近 V²/2，浪费率只剩对角线，矩阵还比链表省掉 `next` 指针。
- **V 很小且固定**：棋盘、城市交通图（V 几十到几百）、状态机的转移表。
- **要用矩阵运算本身**：邻接矩阵的幂有图论含义（A^k 的 (i,j) 元 = i 到 j 长度 k 的
  路径条数），邻接表没法这么算。
- **顶点编号密集连续**（0..V-1 一个不漏）。

**别用邻接矩阵：**
- **稀疏大图**：社交网络、网页链接图、路网。V=10 万就 40 GB，直接出局。
- **顶点编号稀疏**：ID 是 1e9 级别的雪花 ID，却只有 100 个活跃点。
- **要频繁枚举邻居**：BFS/DFS 在矩阵上是 O(V²)，邻接表是 O(V+E)。
- **可能有平行边**：一格存不下两条边，矩阵天生表达不了重边（只能存最小权值那条）。
- **顶点数会动态增减**：固定数组加一个顶点就得整体搬家。

**决策一句话**：先问"我要判边还是要走邻居"，再问"这图稠不稠"。
两问之后答案自动出来，不用凭感觉。

## 自检问题

1. 无向图的邻接矩阵里，`edge[2][5] = 1`，那么 `edge[5][2]` 是多少？为什么？
   **答：一定是 1。** 无向边 (2,5) 没有方向，"2 的邻居清单里有 5" 和
   "5 的邻居清单里有 2" 是同一条边的两次记录。所以无向矩阵沿对角线镜像对称。
   有向图就不一定：`edge[2][5]=1` 只说明 2→5，5→2 可以是 0。

2. 为什么"查度"是 O(V)，能不能做到 O(1)？代价是什么？
   **答：因为要数完一整行。** 可以额外维护一个 `deg[V]` 数组，
   加边时 `deg[a]++; deg[b]++;`，删边时减回来，查度就变 O(1)。
   代价：① 多 O(V) 空间；② 加删边都必须同时维护，漏一处 `deg` 就和真实矩阵不一致了
   —— **冗余数据必然带来同步负担**，这是所有"用空间换时间"的共同代价。

3. 带权矩阵里，如果某条边权值真的就是 -1（比如"亏损 1 元"），怎么办？
   **答：-1 这个哨兵方案失效**，因为出现了歧义。三种出路：
   ① 换成更极端的哨兵，比如 `INT_MIN`；② 多加一个平行数组 `bool has_edge[V][V]`
   显式记录"有没有边"（用 O(V²) 额外空间换确定性）；③ 改用邻接表/边集数组，
   节点里带一个 `exists` 字段。选哪个取决于你更怕歧义还是更怕空间。

4. V=1000 的图，矩阵要多少内存？该用矩阵还是邻接表？
   **答：1000² × 4 字节 = 400 万 B ≈ 3.8 MB。** 这个内存完全不在乎。
   所以关键不是"V=1000 算大还是算小"，而是：如果 E 只有 2000（稀疏），
   遍历一遍要 O(V²)=100 万次访存 vs O(V+E)=3000 次 —— 该用邻接表；
   如果 E 有 40 万（稠密）或者你需要大量判边，用矩阵。**空间不痛不代表时间不痛。**

5. 这一节的结构体是 `int edge[8][8]` 定长数组，不用 malloc。有什么好处和坏处？
   **答：好处** —— 没有内存泄漏（ASan 直接 0 泄漏），不用判 malloc 失败，
   数组在栈上连续、访问快，代码全部注意力都在"图"上。
   **坏处** —— 顶点数编译期写死成 8，超过就装不下；而且不管实际几个点都占 256 字节。
   这正是"最小可跑实现"刻意做的取舍：**先用定长把概念讲清，再考虑动态化**。
   （动态版就是把 `int edge[8][8]` 换成 `int **edge` + 两次 malloc，
   你会额外得到"释放要按行 free 再 free 指针数组"这一整套内存管理负担。）
