# 哈夫曼树与哈夫曼编码（huffman-tree）

> 一句话定位：把"出现多的字符给短码、出现少的给长码"这件事做得又省又不歧义 —— 用一棵树自动造出一张前缀码表，压缩完还能一个不差地解压回来。

---

## 一句话是什么

**哈夫曼树是一棵"带权叶子尽可能靠近根"的二叉树**；它的用途是把字符放到叶子上，
从根到叶子走过的 0/1 路径当成这个字符的编码，于是得到：

1. 频次高的字符码短，频次低的字符码长 → 总比特数最少；
2. 所有字符都在叶子上 → 谁的编码都不是别人的开头（前缀码）→ 不需要分隔符也能唯一解码。

建树的方法只有一句话，但要记牢：

> **统计频次 → 全部丢进最小堆 → 每次取出权重最小的两个、合并成一个新节点放回堆 → 堆里只剩一个节点时，它就是根。**

本目录真的把整条链路跑完了：统计、建树、打印树、生成编码表、编码成比特流、
再解码回原文并用 `strcmp` 证明一字不差。示例文本 34 个字符，
ASCII 要 272 比特，哈夫曼只要 126 比特。

---

## 为什么需要它

### 不用它：定长编码，肉眼可见的浪费

最土的存法是每个字符同样多比特。ASCII 就是定长 8 位。

我们的示例文本 `"that is the test of huffman coding"`：

```
   空格 ×6      t ×5      h ×3   f ×3      a ×2  e ×2  i ×2  n ×2  o ×2  s ×2
   c ×1   d ×1   g ×1   m ×1   u ×1
```

用 ASCII：34 × 8 = **272 比特**。其中 `u` 只出现 1 次，也老老实实付 8 比特；
`空格` 出现 6 次，同样付 8 比特。频次差了 6 倍，代价一模一样 —— 这就是浪费。

"那我按这段文本里实际出现的 15 种字符算，`ceil(log2 15) = 4` 位不就够了？"
对，136 比特，确实省了一大半。但**仍然是定长**：`空格`（6 次）和 `u`（1 次）还是付一样多。

### 用了它，但如果"随便变长"：信息直接丢了

省下来的动机很正当：让常见的短、少见的长。可是乱着给会出事，这是**整个第 05 章最重要的一段**，
值得慢慢看。

假设只有 3 个字符，我给了这张表：

```
   A = 0
   B = 01
   C = 10
```

看起来挺合理：A 最常见，给它 1 位。现在解码器收到比特流 `010`，请你自己切一刀：

```
   切法一： 0 | 10   → A  C
   切法二： 01 | 0   → B  A
```

**同一段比特能解出两句不同的话**。demo 的第 1 幕不是嘴上说说，它把两种切法真的穷举打印出来了：

```
        解法 1：AC     ← 切法：0|10
        解法 2：BA     ← 切法：01|0
```

病根在哪？在读到第一个 `0` 的那一刻，解码器**不知道该不该停**：
`0` 既是一个完整的编码（A），又是 `01`（B）的开头。
要修也行 —— 每个字符后面加个分隔符，或者在编码表里存码长，但分隔符自己也要比特，
大概率越加越亏，完全背离了压缩的初衷。

### 前缀码：把"不用分隔也能切开"变成结构保证

定义（背下来）：**任何一个字符的编码，都不是另一个字符编码的前缀**，这样的表叫**前缀码（prefix code）**。

换一张前缀码表：`A=0, B=10, C=11`。再读 `010`：`0`→A，剩下 `10`→B，**唯一解 = "AB"**。
为什么唯一？因为 A 的编码 `0` 不可能是别的编码的开头，所以"读到 0 就停"永远是对的，
不需要往后看一个比特做判断（这叫**无需前瞻 / 即时解码**）。

那怎么"自动"造出一张又短又是前缀码的表？—— **把每个字符都放在二叉树的叶子上，编码 = 从根到叶子的路径**：

```
                根
               /  \
            A(叶)  \          ← A 的路径就是 "0"，它下面没有孩子了
                 /  \          ← B、C 要再往下走一层才能得到，所以一定是 "0?"/"1?" 这种更长的串
              B(叶) C(叶)
```

理由特别直白：**从根到某个叶子的路径，中途不可能经过另一个叶子**（叶子没有孩子）。
所以任何一条编码都不可能是另一条的前缀 —— 前缀冲突在**结构上**就不可能存在。
反过来，如果把某个字符放在内部节点上，它的路径立刻变成它所有子孙路径的前缀 → 冲突。
这就是"所有字符必须放叶子"这条规矩的真正理由（对应代码：`huff_build` 里只给叶子造节点，
`assign_codes` 里只在 `node->is_leaf` 时登记编码）。

### 还顺手拿到了"最少比特"

在**所有**前缀码里，哈夫曼树给出的**带权路径长度 WPL 最小**，也就是这段文本编码后的总比特数最少
（在"每个字符必须用整数位比特编码"这个约束下）。所以它同时满足两个要求：
**合法（前缀码）+ 最省（WPL 最小）**。这就是为什么它出现在教材里、也出现在真实的 `DEFLATE`/`gzip` 里。

| 方案 | 本例总比特 | 说明 |
|---|---|---|
| ASCII 定长 8 位 | 272 | 谁都不偏袒，最费 |
| 按字符集定长 `ceil(log2 15)` = 4 位 | 136 | 省了，但罕见字符仍白付 |
| **哈夫曼变长前缀码** | **126** | 平均 3.71 位/字符 |
| 香农熵理论下限（手算：H ≈ 3.657 位/字符） | ≈ 124.3 | 哈夫曼只差它 1.4%，而且是整数位宽的硬约束下 |

最后一行是"天花板"：任何无损编码都不可能比熵更短。哈夫曼 126 vs 124.3，已经很贴了。
（差距来源：`空格` 想用 3.657 位，但比特不能劈开，只能给 2 位；`c/d/g/m/u` 想要
`log2 34 ≈ 5.09` 位，只能给 5~6 位。算术编码能把这个缝隙再压小，见"什么时候别用"。）

## 内存布局图解

本节有**三块内存**，分工很清楚：堆（临时工具）、树（最终产物）、编码表（对外使用的快捷入口）。

### ① 最小堆：一个指针数组，它本身就是"一棵完全二叉树的扁平化"

`HuffMinHeap` = `HuffNode *item[512]` + `int size`。数组下标当成树的位置来看：

```
    数组:  [ 0 ] [ 1 ] [ 2 ] [ 3 ] [ 4 ] [ 5 ] [ 6 ] [ 7 ] ...
            ↓     ↓             ↓      ↓     ↓
    看成树:        ①                    ← item[0]，全局最小，pop 就拿它
                  / \
                 ②   ③                 ← item[1], item[2]
                /\   /\
               ④ ⑤ ⑥ ⑦                 ← item[3..6]
              /│\ ...                   ← item[7..14]

    下标算术（不用任何指针字段）：
       父亲(i) = (i-1) / 2
       左孩子(i) = 2i + 1
       右孩子(i) = 2i + 2
    性质只有一条：parent->weight <= child->weight
```

⚠ 看图时的第一个误区：**数组不是排好序的**。demo 第 2 幕真的打出来了：

```
        堆里 15 个节点（按层看，父 ≤ 子；同层之间【不保证】有序）：
          第 1 层: [0:权重1]
          第 2 层: [1:权重1][2:权重1]
          第 3 层: [3:权重2][4:权重1][5:权重2][6:权重1]
          第 4 层: [7:权重6][8:权重3][9:权重2][10:权重2][11:权重3][12:权重2][13:权重5][14:权重2]
          堆顶 item[0] = 权重 1 ← 这就是当前全局最小，pop 就是拿它
```

第 4 层里 `权重6` 排在 `权重3` 前面 —— 没错，堆只保证父子关系。
哈夫曼只反复问一件事"最小的在哪"，而堆顶永远是答案，所以这个"半排序"结构刚好够用。

### ② 哈夫曼树：`HuffNode` 三个字段 + 两个指针

```
   struct HuffNode { int weight; unsigned char ch; int is_leaf; HuffNode *left, *right; }

                    [内部 w=34]                 ← 根：权重 = 全文字符数 34
                    /        \                     ch/is_leaf 对内部节点没有意义（is_leaf=0）
          [内部 w=14]        [内部 w=20]
          /       \          /        \
   [叶 空格 w=6] [内部 w=8] [内部 w=9] [内部 w=11]
                                ...       /    \
                                     [叶 t w=5] ...
                                            ↑
   叶子里 ch=' '(0x20), weight=6, left=right=NULL
   任何一个字符都在叶子上；内部节点只是"路标"，不存字符
```

内存分布（15 个字符 → 15 个叶子 + 14 个内部节点 = 29 次 `calloc`，全部挂在 root 下面）：

```
   malloc 出来的 29 块 HuffNode，互相用 left/right 串成一棵无环树，root 是唯一入口。
   → 所以销毁只要一次 huff_free_tree(root) 的后序遍历，一块都不能漏；
     ASan 报 leak 就说明有节点"失联"了（比如 pop 出来忘了挂回去）。
```

### ③ 编码表：`HuffCodeEntry[256]`，下标就是字符的 ASCII 码

```
   下标 0x20(' ') 0x61('a') 0x63('c') ... 0x74('t') 0x75('u')   0xFF
   ┌───────┬───────┬───────┬─────┬───────┬───────┬─────┐
   │f 6    │f 2    │f 1    │ ... │f 5    │f 1    │f 0  │   f=freq
   │len 2  │len 4  │len 5  │     │len 3  │len 5  │len 0│
   │"00"   │"0101" │"10100"│     │"110"  │"11100"│""   │
   └───────┴───────┴───────┴─────┴───────┴───────┴─────┘

   为什么用 256 格数组而不是哈希表 / 二叉查找树？
     编码要逐字符查（"这个字符的码是什么"），数组下标查是 O(1)，一行代码；
     而且 256 是 unsigned char 的全部取值，任何字节都能装下，永远不会有"查不到"的分支要处理。
     代价：256 × (4+4+64) ≈ 18KB 的栈/静态区，换来的是彻底简单。
   ⚠ 下标必须写 (unsigned char)c：如果 char 是 signed 的，
     一个 0x80 以上的字节会变成负数 → freq[-100] = 越界。这是本节最阴的坑之一。
```

三块内存的关系（一次完整流程）：

```
   原文 text ──huff_count_chars──► freq[256] ──► 15 个 HuffNode* ──► 最小堆 item[]
                                                                     │
                                                       循环 pop 两个、合并、push 回去
                                                                     │
                                                                     ▼
                                                        根节点 root（1 个 HuffNode*）
                                                                     │
                                                       assign_codes 走树（DFS）
                                                                     ▼
                                            编码表 table[256]（每个字符的 0/1 串）
                                                                     │
                          huff_encode 用 table 把 text 变成 bits[]；huff_decode 用 root 把 bits[] 变回 text
```

## 核心操作逐个拆解

下面每一条都是"**干什么 → 一步步怎么做 → 边界情况 → 对应代码行**"。

### 1. 统计频次 `huff_count_chars`（`huffman.c:241`）

**干什么**：把原文扫一遍，得到每个字符出现几次，同时返回"有几种不同字符"。

**一步步**：
1. `freq_out[256]` 先全部清 0（`huffman.c:243-245`）；
2. `for (const char *p = text; *p != '\0'; p++)` 逐字符 `freq_out[(unsigned char)*p]++`；
3. 再扫一遍数组数出 `> 0` 的格子数 = `distinct`。

**边界情况**：
- `text == NULL` → 返回 0，`freq_out` 保持全 0，调用方拿到空表（`huffman.c:246`）；
- 空串 `""` → 同样 `distinct = 0`，`huff_build` 会返回 `NULL`，main 里必须判空；
- 文本里出现 0x80 以上的字节（比如中文 UTF-8、或者 `\xff`）：靠 `(unsigned char)` 转换，
  它落在 128~255 这一格，不会写疯。**这个强制转换不是洁癖，是必需的。**

**对应代码行**：`huffman.c:241-260`；demo 里的第 1 步打印在 `huffman.c:346-358`：
```
    第 1 步 统计频次：文本共 34 个字符，出现了 15 种不同字符
      字符 → 频次： 空格:6  a:2  c:1  d:1  e:2  f:3  g:1  h:3  i:2  m:1  n:2  o:2  s:2  t:5  u:1
```

### 2. 最小堆 `push`：放进去然后"上浮"（`huffman.c:60`）

**干什么**：把一个节点插进堆，保持"父 ≤ 子"。

**一步步**：
1. 检查满没满（`huffman.c:65-68`），检查 `node == NULL`（62）；
2. 放到数组末尾 `item[size]`，然后 `size++` —— 末尾正是完全二叉树"最左下"的空位，
   所以**形状**天然还是合法的，只有**顺序**可能要修（70-72）；
3. 上浮：`while (pos > 0)`，算父亲 `(pos-1)/2`；
   - `父->weight <= 子->weight` → 性质已恢复，`break`（76-78）；
   - 否则**交换两个指针**（不是交换节点内容），`pos = parent` 继续往上（80-83）。

**边界情况**：
- 堆空（`size == 0`）：`pos = 0`，`while` 条件不成立，直接返回，不会算出 `parent = -1`；
- 权重相同：**不交换**（用的是 `<=`），所以相同权重的相对次序稳定 —— 这也是为什么
  demo 里 `c` 和 `d` 合并、`m` 和 `g` 合并看起来"顺理成章"；
- 只上浮一层就停是常态：新来的节点大多只比父亲大一点点。

**为什么交换指针而不是搬节点？** 节点是 `calloc` 出来的，可能被别的地方（比如已经建好的子树）
用 `left/right` 指着；搬"内容"会让外面的指针指向错的字符。搬"数组格子里的地址"则节点本身
在内存里一动没动。**这一点和 `05-tree/b-tree` 里"移动的是指针/键值，不是节点"的思路一致。**

**对应代码行**：`huffman.c:60-86`。

### 3. 最小堆 `pop`：拿走堆顶然后"下沉"（`huffman.c:103`）

**干什么**：返回当前最小节点，并让剩下的仍然是堆。

**一步步**：
1. `min = item[0]`；`size--`；
2. **把原来的最后一个元素搬到堆顶**（`huffman.c:111`）—— 只有搬"最后一个"才能保证数组仍是
   一棵完全二叉树；搬别的会留下空洞；
3. `item[h->size] = NULL;`（`huffman.c:112`）擦掉腾出来的格子：地址已经在堆顶了，
   留着两份就是"鬼指针"，将来调试时会误以为它还在堆里；
4. 下沉：和**两个孩子里较小的那个**比；比它大就交换，然后到那一格继续；
   - 先判断 `left >= size` → 我已经是叶子位置，收工（120-122）；
   - 右孩子只有在**存在且更小**时才选（123-125）；
   - `item[pos]->weight <= item[small]->weight` → 性质恢复，收工（126-128）。
5. 返回 `min`。

**边界情况**：
- 空堆返回 `NULL`（105-107）。调用方**必须判空**。本文件里安全的原因是
  `huff_build` 只在 `while (heap.size > 1)` 里 pop（`huffman.c:383`），
  以及最后"只剩 1 个"时 pop 一次（414）—— 那时数组里确实有 1 个元素。
- `size == 1` 时：`size--` 变 0，`item[0] = item[0]`（自赋值，无害），`left = 1 >= 0` 立即 break。
- 为什么下沉比上浮"多一步思考"？上浮只需和**唯一的父亲**比；下沉要和**两个孩子**比并挑较小的，
  否则可能换完仍然违反另一边的性质。

**对应代码行**：`huffman.c:103-135`。

### 4. 打印堆状态 `huff_heap_dump`（`huffman.c:142`）

**干什么**：把堆"按层"打印出来，让人看清它是一棵树而不是一排数字。

**一步步**：第 `k` 层的下标范围正好是 `[2^k - 1, 2^(k+1) - 2]`，所以循环里维护
`level_start`（本层第一个下标）和 `level_count`（本层最多几个格子），每轮 `level_count *= 2`；
最后一层没填满就用 `if (level_end > h->size) level_end = h->size;` 截一下（`huffman.c:154-156`）。
最后单独强调一行"堆顶 item[0] 才是全局最小"。

**边界情况**：空堆打一行"堆：空"就返回（144-147），不碰 `item[0]`（那是 NULL）。

**对应代码行**：`huffman.c:142-169`。

### 5. 建树主循环 `huff_build`（`huffman.c:328`）

**干什么**：一步到位 —— 统计、造叶子入堆、反复合并到只剩一个、走树填编码表。

**一步步**：
1. **第 1 步**：`huff_count_chars` 得到 `freq[256]` 和 `distinct`；空文本直接返回 `NULL`；
2. **第 2 步**：`huff_heap_init`，然后把每个 `freq[i] > 0` 的字符造一个叶子 `push` 进堆
   （`huffman.c:364-376`）。打印堆初始状态；
3. **合并循环**：`while (heap.size > 1)`（`huffman.c:383`）
   - `a = pop()`，`b = pop()` —— 两次 pop 就拿到"最小两个"，这就是堆存在的理由；
   - `merged = make_inner(a, b)`：`weight = a->weight + b->weight`，`left = a`，`right = b`，`is_leaf = 0`；
   - `merge_sum += merged->weight`（留着跟 WPL 对账）；
   - `push(merged)` 放回堆，`huff_heap_dump` 打印本轮之后的堆；
4. **收尾**：`root = pop()`，堆里只剩它，就是根；
5. **第 3 步**：`table[i].freq = freq[i]` 先把频次填进表（打印表格要用），然后 `assign_codes(root, path, 0, table)` 走树登记编码。

**边界情况**：
- 只有一种字符（`"aaaa"`）：循环一次都不进，堆里本来就只有 1 个节点 → **它既是根又是叶子**；
  `merge_sum = 0`。demo 第 8 幕专门跑这个，并指出"合并法 == WPL"这个经典结论在这个极端下不成立
  （WPL = 4 而 merge_sum = 0），因为合并法依赖至少发生一次合并。**这是本节最容易被忽略的角落。**
- 恰好两种字符：循环进 1 次，根有一个左叶子一个右叶子，两个字符的编码都是 1 位（`0` 和 `1`）。
- `push(merged)` 失败（堆满）时：`free(merged)` 再返回 `NULL` —— **谁申请谁负责回收**，
  `a`、`b` 已经挂在 `merged` 上，但 `merged` 还没进堆，所以整棵 `merged` 子树（含 a、b）
  会被 `free(merged)` 漏掉吗？不会：`free` 只释放 `merged` 自己，a/b 仍在 `heap.item` 里被
  `huff_build` 的失败路径……（这里诚实说明）本 demo 的 `HUFF_HEAP_CAP = 512`，
  而堆里元素只会从 `distinct ≤ 256` 开始只减不增（每轮 -2 +1），所以**这条分支在 demo 里不可达**，
  写成防御性代码。真要支持更大字符集，就得改成"失败时把堆里剩下的节点逐个 free"。

**打印出来的样子**（demo 第 2 幕，15 种字符 → 14 轮合并）：
```
      ── 第 12 轮：堆里还有 4 个节点，取走最小的两个 ──
        取出 权重6(空格) 和 权重8(子树) → 合并成新内部节点 权重14
        堆里 3 个节点（按层看，父 ≤ 子；同层之间【不保证】有序）：
          第 1 层: [0:权重9]
          第 2 层: [1:权重11][2:权重14]
          堆顶 item[0] = 权重 9 ← 这就是当前全局最小，pop 就是拿它
      ── 第 13 轮：堆里还有 3 个节点，取走最小的两个 ──
        ...
      堆里只剩 1 个节点 → 它就是根，权重 34（= 文本总字符数）
      各轮合并权重之和 = 126（下面会和 WPL 对一下，两者必须相等）
```
注意 `权重6(空格)`：频次第二高的 `空格` 直到第 12 轮才被取用 —— 因为它一直躺在堆里等着，
而**它被合并的次数**（1 次）就是它最后的深度（1 + 上层给它加的量）。最终它拿到 2 位编码 `00`。

**对应代码行**：`huffman.c:328-431`（`make_leaf` 在 180，`make_inner` 在 196）。

### 6. 走树登记编码 `assign_codes`（`huffman.c:279`）

**干什么**：从根往下 DFS，左拐写 `'0'`、右拐写 `'1'`，走到叶子把整条路径存进表。

**一步步**：
1. 传一个 `char path[HUFF_MAX_CODE_LEN]` 缓冲区复用（不是每条分支都 `malloc` 一份）；
2. 到叶子（`node->is_leaf`）：`path[depth] = '\0'` 把路径当字符串截断，
   `table[node->ch].code_len = depth`，`snprintf` 抄进表；返回；
3. 到内部节点：先 `path[depth] = '0'` 递归左，再 `path[depth] = '1'` 递归右 ——
   **同一个格子被覆盖两次**，这就是"回溯"不用额外空间的写法（`huffman.c:301-304`）。

**边界情况**：
- `depth == 0` 且节点是叶子（单字符文本）→ 会得到长度 0 的空编码，"这个字符不占任何比特"，
  解码时没法知道它出现了几次。所以**特判成 1 位的 `"0"`**（`huffman.c:285-288`）。
- `depth >= HUFF_MAX_CODE_LEN - 1` → 打警告并放弃这条子树（296-300）。
  256 种字符时树最深可能到 255 层，所以 64 这个上限对 demo 够用但**不是普适的**，README 坑 #7 提了。

**这一小节顺手证明了前缀码**：登记只发生在叶子处；内部节点从不登记。
所以表里的每条编码都是"根 → 叶子"的完整路径，谁也不会是别人的开头。
`huff_check_prefix_free`（`huffman.c:547`）再把这件事用两两 `strncmp` 实测一遍，输出：
```
    => 全部互不为前缀，是合法前缀码 ✓ 所以不需要分隔符就能唯一解码
```

**对应代码行**：`huffman.c:279-305`。

### 7. WPL：带权路径长度（`huffman.c:531`）

**干什么**：一个数衡量这棵树好不好 —— 也是"这段文本编码后到底多少比特"。

**定义**：`WPL = Σ(每个叶子的权重 × 它到根的路径长度)`。

**两种算法（都要会，而且必须相等）**：
1. **定义法**：递归遍历，叶子就累加 `weight * depth`，内部节点往下传 `depth + 1`
   （`wpl_rec`，`huffman.c:520-529`）。
2. **合并法**：把每一轮"合并产生的新节点权重"全加起来。
   直觉：合并一次 = 这个子树里所有叶子的深度都 +1 = WPL 增加了它们的权重和 = 新节点权重。

demo 第 5 幕把两种算法和逐叶子的账一起打出来，三方互相验证：
```
  ① 定义法（递归遍历叶子累加 weight×depth）算出 WPL = 126 比特
  ② 合并法（每次合并产生的新节点权重全部加起来）= 126 比特
     两者相等 ✓  ← 这是哈夫曼 coding 的经典结论，两种算法必须相等

        空格 频次  6 × 码长 2 =  12 比特
        t      频次  5 × 码长 3 =  15 比特
        ...
     合计 126 比特（应当 == WPL）
```
**考试怎么写**：给一串权重（比如 `7 2 5 10 4 1`），让你建树、算 WPL。
手工做法：排序 → 拿最小两个合并 → 插回有序序列 → 重复。
校验捷径：**WPL = 所有内部节点权重之和**。两种算出的数不一样就是画错了。

**边界情况**：单节点树（`"aaaa"`）：定义法 `4 × 1 = 4`（因为我们特判码长为 1），合并法 `0`。
所以这个结论的适用前提是"至少合并过一次"。demo 明说了这点，不含糊。

**对应代码行**：`wpl_rec` 在 `huffman.c:520-529`，`huff_wpl` 在 `531-545`。

### 8. 编码 `huff_encode`（`huffman.c:591`）

**干什么**：逐字符查表，把编码串首尾相接成一整条比特流。**中间不加任何分隔符。**

**一步步**：
1. `for (const char *p = text; *p != '\0'; p++)`；
2. `const HuffCodeEntry *e = &table[(unsigned char)*p]` —— O(1) 查表；
3. 逐位 `bits_out[used++] = e->code[i]`。

**边界情况**：
- `e->freq <= 0`：这个字符不在表里 → 报错返回 0，说明"建树用的文本和要编码的文本不是同一份"。
  这是哈夫曼最典型的使用错误：**码表和文本必须配套**（真实压缩文件头就存着码表）。
- 缓冲区不够：判断写成 `if (used + 1 >= cap)`，因为最后还要留一格放 `'\0'`（`huffman.c:607`）。
- `bits_out` 里存的是**字符 `'0'` 和 `'1'`**，不是真的比特位 —— 为了让打印出来给人看。
  真工程一定用位操作（`byte |= 1 << k`），1 字节能存 8 倍内容。坑 #6 详述。

**对应代码行**：`huffman.c:591-622`。

### 9. 解码 `huff_decode`（`huffman.c:641`）

**干什么**：拿比特流 + 哈夫曼树（**注意：解码要的是树，不是表**），从根开始走，
`0` 往左、`1` 往右，落到叶子就吐字符然后回根。

**一步步**：
1. `cur = root`；
2. 每读一个比特：`'0'` → `cur = cur->left`，`'1'` → `cur = cur->right`，别的字符 → 报错返回 -1；
3. `cur == NULL` → 比特流比树长，输入被写坏了，返回 -1（`huffman.c:671-674`）；
4. `cur->is_leaf` → 写 `out[n++] = cur->ch`，然后 **`cur = root`**（`huffman.c:681`）——
   这一行是整个解码的灵魂：吐完立刻回根，剩下的比特属于新字符；
5. 全部读完：`if (cur != root)` 说明末尾剩半截（停在内部节点），打警告但把已解出的字符返回。

**为什么"走到叶子就一定能停"？** 因为前缀码保证下一条路径的含义只由"当前在哪个节点"决定，
不需要偷看后面的比特。对照第 1 幕的坏表：读到 `0` 时无法决定停不停。

**为什么解码要传整棵树，编码却只要表？** 因为"哪个字符对应哪串比特"要沿树问；
反过来"哪串比特对应哪个字符"只有树能给（把表建成 Trie 也行，但那就等于重建了树）。
**这也是哈夫曼文件必须带码表/树的原因**：丢了树，126 比特就是一堆噪声。

**边界情况**：
- 根就是叶子（单字符）：`if (root->is_leaf)` 特判成"每 1 比特 = 1 个该字符"（`huffman.c:649-660`）；
- `out` 缓冲区不够：`if (n + 1 >= cap)` 提前报错返回 -1，不写越界；
- 截断：见 demo 第 8 幕情况二，`126 → 124` 比特，只解出 33 个字符，函数给出警告。
  真实格式靠文件头里的"原文长度"决定该在哪一比特停。

**对应代码行**：`huffman.c:641-689`。

### 10. 打印：编码表 / 树形（`huffman.c:438`、`huffman.c:499`）

`huff_print_table` 扫 256 格，只打 `freq > 0` 的行，画成方框表。
`huff_print_tree` 用和 `05-tree/b-tree` 一样的"缩进 + `├─ └─`"递归（`print_tree_rec`，
`huffman.c:467`），只多了一件事：**每条边标上 `0 →` / `1 →`**，
于是"某个字符的编码"就是从上往下把它头顶的标签念一遍。

递归签名是 `print_tree_rec(node, line_prefix, label, i_am_last)`：
`line_prefix` 是"我这一行前面要照抄的祖先竖线"，`label` 是"我和父亲之间那个连接符 + 边标签"。
少传一个 `i_am_last` 就会画出错位（本仓库的树形视图踩过这个坑，两处都修好了）。

**边界情况**：`root == NULL` 打"（没有树：空文本）"而不是段错误（`huffman.c:501-503`）。

### 11. 销毁 `huff_free_tree`（`huffman.c:703`）

**干什么**：把 29 次 `calloc` 还回去。

**一步步**：后序 —— 先 `huff_free_tree(root->left)`，再 `right`，最后 `free(root)`（708-710）。

**为什么必须后序**：一旦 `free(node)`，`node->left` / `node->right` 就变成被回收的纸条，
再去读就是 use-after-free。自顶向下先放自己是**经典错误写法**。

**边界情况**：`root == NULL` 直接返回。单节点树也能正确释放（左右都是 NULL，放自己）。

**验证手段**：ASan 的 leak 检查。所有节点都挂在 root 下面，所以"没报 leak"
就等于"没有节点失联" —— 比如 pop 出来忘了 push/挂回去，就会在这里暴露。

## 复杂度表

设 `n` = 文本字符总数，`k` = 不同字符的种类数（`k ≤ 256`，本例 `n = 34, k = 15`）。

### 建与用：本节实际做的

| 操作 | 复杂度 | 说明 |
|---|---|---|
| 统计频次 | `O(n + 256)` = `O(n)` | 扫一遍文本；数组下标查，没有哈希 |
| 造 k 个叶子 + 全部入堆 | `O(k log k)` | 逐个 push，每个上浮最多 log k |
| 合并循环 | `O(k log k)` | 恰好 `k-1` 轮，每轮 2 次 pop + 1 次 push = `O(log k)` |
| 走树填编码表 | `O(k × 平均码长)` | 每个叶子抄一条路径 |
| **建树总计** | **`O(k log k)`** | 与文本长度 `n` 无关（统计除外） |
| 编码整段文本 | `O(n × 平均码长)` = `O(n)` 级 | 逐字符 O(1) 查表 + 逐位写入 |
| 解码整段文本 | `O(n × 平均码长)` | 逐比特走树，总步数 = 比特总数 |
| 查一个字符的编码 | `O(1)` | 数组下标，不是二分不是哈希 |
| 算 WPL | `O(k)` | 遍历一次叶子 |
| 前缀码自检 | `O(k² × 码长)` | 两两比，纯演示用，不是必需步骤 |
| 释放 | `O(k)` | 后序遍历 |
| 空间 | `O(k × 码长)` | 29 个树节点 + 256 格表 + 堆数组 |

### 横向对比：建树这件事的三种实现

| 做法 | 每轮取"最小两个"的代价 | 总代价 | 好不好写 |
|---|---|---|---|
| **最小堆（本节）** | `O(log k)` | **`O(k log k)`** | 要自己写 push/pop，但写一次就通用 |
| 每次都全表扫描找最小 | `O(k)` | `O(k²)` | 最省事，k=256 时约 6.5 万次比较，demo 也无所谓 |
| 先排序 + 两个队列 | `O(1)` 摊还 | `O(k log k)`（全花在排序） | 工程里最优雅：**合并产生的权重天然单调递增**，所以一个"原始队列" + 一个"合并队列"就能代替堆，不用堆也能到 `O(k log k)`。面试加分项。 |

（"双队列"为什么成立？因为每轮新合并出的权重 `a+b` 一定不小于上一轮的，
所以第二个队列自身天然有序。这是哈夫曼 coding 里的一个经典小技巧。）

### 横向对比：三种编码方案

| 方案 | 每字符比特 | 需要额外存码表吗 | 需要分隔符吗 | 本例总比特 |
|---|---|---|---|---|
| ASCII 定长 | 固定 8 | 不需要 | 不需要 | 272 |
| 字符集定长（`ceil(log2 k)`） | 固定 4 | 需要存 k 种字符的映射 | 不需要 | 136 |
| **哈夫曼前缀码** | **变长 2~6，平均 3.71** | **需要（存树或表）** | **不需要** | **126** |
| 香农熵下限（理论） | 平均 3.657 | — | — | ≈124.3 |
| 乱给的变长码 | 变长 | 需要 | **需要**（否则歧义） | 无法解码 |

### 和别的树放在一起看（本节 vs 05 章其他结构）

| | 哈夫曼树 | 二叉搜索树 / AVL | B 树 |
|---|---|---|---|
| 关心的事 | 让"权重×深度"最小 | 让查找路径短（平衡） | 让"一次磁盘页能带的分支"最多 |
| 有大小顺序吗 | **没有**，`left/right` 只表示编码 0/1，不能按权重二分查找 | 有 | 有 |
| 能在上面查 key 吗 | 不能（只能从根按 0/1 走，那是解码，不是查找） | 能 | 能 |
| 树高由什么决定 | 由权重的分布决定，可能很不平衡（本例最深 6 层） | 由节点数 + 旋转保证 | 由阶 m 和节点数 |
| 主要用途 | 压缩、最优合并顺序、编码 | 有序集合、字典 | 数据库索引、文件系统 |

⚠ 特别注意第一行和第二行：**哈夫曼树不是搜索树**。
在哈夫曼树上"查一个字符"要靠编码表数组（`O(1)`），不是靠往下比大小 —— 比不了，
内部节点的 `left` 只是"编码下一位是 0"，和权重大小没有方向关系。
（顺带一提：本例树就很不平衡，`空格` 深度 2、`g/m` 深度 6，这不是 bug，
是"按频次分配深度"的必然结果。）

----------------------------------------

  ① 定义法（递归遍历叶子累加 weight×depth）算出 WPL = 126 比特

## 常见的坑

### 坑 1：把变长编码当成"随便给长短" —— 忘了前缀条件

最致命的概念坑。`A=0, B=01, C=10` 语法上完全合法、每个字符都有编码，
但 `010` 能解成 `AC` 也能解成 `BA`（第 1 幕穷举出来了）。
判断口诀：**任何一条编码都不能是另一条的开头**。工程上还有"后缀码"（从后往前读）等变种，
但初学者只要记住"叶子 + 从根到叶子的路径"就永远错不了。

### 坑 2：以为"编码表就够了解码用" —— 解码必须有树

`huff_decode` 的入参是 `HuffNode *root`，不是 `HuffCodeEntry table[]`。
编码是"字符 → 比特"，查表就行；解码是"比特串 → 字符"，必须**逐比特沿树走**，
因为"当前这个比特属于哪个字符"这个状态只有树能给。
所以真实压缩文件要**在文件头存码表（或树的形状）**；丢了它，那段比特流就是一堆随机噪声。

### 坑 3：`char` 是 signed 的时候，`freq[c]` 直接越界

```c
char c = 0xC3;              /* 有符号 char 里它是 -61 */
freq[c]++;                  /* 写 freq[-61]：栈被踩，编译器还不一定报警 */
freq[(unsigned char)c]++;   /* 正确：195 */
```
只要用字符当数组下标（本节的 `freq[256]`、`table[256]` 全都是），就必须先转
`unsigned char`。本文件里每一次下标都加了转换（`huffman.c:596`、`huffman.c:246-254` 等）。
ASCII-only 的 demo 不会暴露这个 bug，但一旦喂进 UTF-8 中文就会 —— 这也是"教学代码
也要写对"的理由。

### 坑 4：节点忘置 NULL，或 `free` 顺序写反

- 造节点要用 `calloc`（`make_leaf`/`make_inner`，`huffman.c:180/196`）。如果用 `malloc`
  又忘了手写 `left = right = NULL`，`huff_print_tree` 一路往 `left` 递归就会撞垃圾指针段错误。
- 释放必须**后序**：`free(left)` → `free(right)` → `free(self)`。
  先放自己再去读 `root->left` 就是 use-after-free。
- `huff_heap_pop` 里 `h->item[h->size] = NULL`（`huffman.c:112`）同理：
  腾出来的格子要擦干净，否则数组里留着一份"已经出堆"的地址，调试时会被误导。

### 坑 5：单字符文本 → 编码长度 0

`"aaaa"` 只有一种字符，堆里一上来就 1 个节点，循环一次不跑，**根就是叶子**。
按"根深度 0"给编码的话，编码就是空串 —— 编码后 0 比特，解码时怎么知道有几个 `a`？
所以本节特判成 1 位 `"0"`（`huffman.c:285-288`，`huff_decode` 对应 `huffman.c:649-660`）。
副作用：这种极端情况下"合并法 == WPL"不成立（WPL=4，合并权重和=0），第 8 幕把它打印出来对照了。
**写代码时容易 entirely 忘了这条路，然后被一个 `"a"` 的输入搞崩 —— 空文本和单字符文本都是
"边界输入"，每个数据结构都值得单测它们一次。**

### 坑 6：比特流到底用"字符 0/1"还是"真比特位"

本节 `bits[]` 存的是 `'0'`/`'1'` 这两个**字符**（1 比特占 1 字节），纯粹为了 `printf` 出来给人看。
真实实现必须是位操作：
```c
unsigned char byte = 0; int nb = 0;
for (每条编码的每一位) { byte = (byte << 1) | bit; if (++nb == 8) { 写出 byte; nb = 0; } }
/* 别忘了最后把不满 8 位的那一半补齐并记录有效位数 */
```
"最后不满 8 位怎么补、补几位"又是一个经典细节 —— 这就是坑 7 的另一种表现。

### 坑 7：解码的"停在哪里"必须靠外部信息

`huff_decode` 只知道给了多少比特，不知道"原文有多少个字符"。
如果编码结束时还差几位没凑满一个字节，补 0 之后解码器可能多解出半截（停在内部节点）。
本节用 `bit_count` 精确控制，并在末尾判断 `if (cur != root)` 发警告（`huffman.c:684-686`）；
真实格式的做法是在文件头存**原文字符数**。第 8 幕情况二演示了截断的表现。

### 坑 8：以为哈夫曼一定"压得动"

对**已经压缩过**的数据（zip 后的文件、jpg、mp3）再上哈夫曼，收益≈0 甚至膨胀
（因为频次接近均匀，熵就是 `log2 k`，变长没有优势；而码表本身还要占空间）。
极端例子：文本 1 个字符、256 种字符合法 —— 光存树就比原文长。
哈夫曼适合"频次分布很不均匀"的数据（自然语言、DNA、日志），这也正是 demo 用它的原因。

### 坑 9：权重相同时的"任意性"

`huff_push` 用 `<=`（相等不上浮），所以相同权重的顺序稳定；
但**哈夫曼树本身不唯一**：权重 `1 1 1 1` 可以有多种合法合并顺序，WPL 相同、
每个字符的码长集合相同，但具体编码串不同。
所以"我的哈夫曼实现和参考答案的编码不一样"是**正常的** ——
判断对错看 WPL，不看编码字符串。

## 什么时候用它 / 什么时候别用

### 适合

- **字符/符号频次差异大的文本类数据**：日志、源代码、自然语言、DNA 序列（A/C/G/T 只有 4 种，
  哈夫曼能做到接近 2 位/碱基的极限）。
- **需要"最优合并顺序"** 的问题：把若干堆文件两两合并，每次代价 = 两堆之和，问总代价最小 ——
  这就是哈夫曼算法本身（LeetCode 1134 / 经典"最优归并"）。
- **作为更大方案的最后一环**：`DEFLATE`/`gzip`/`bzip2`/`MP3`/`JPEG` 都在
  熵编码阶段用哈夫曼（`gzip` 的 `DEFLATE` = LZ77 + 哈夫曼）。
  面试问"gzip 用了什么"，答"哈夫曼"没错，但要说清它只负责最后一步。
- **资源受限、要求解码极简**的场景：解码就是"走树 + 回根"，没有乘法、没有窗口，
  老式调制解调器/传真机（CCITT Group 3 编码）就是这么干的。
- **教学/面试**：唯一"手写就能实现、又能立刻看到压缩效果"的最优编码。

### 别用 / 换成别的

| 场景 | 为什么不用哈夫曼 | 换什么 |
|---|---|---|
| 数据已压缩（jpg/mp3/zip） | 频次近乎均匀，收益≈0，码表还占空间 | 直接别压；或换更上层的封装 |
| 码表必须极小 / 符号数巨大 | 每符号都要存变长码，表本身可能比数据长 | 定长编码；或"自适应/有限长度哈夫曼"（如 `Canonical Huffman`） |
| 要更贴近熵极限 | 整数位宽是硬约束，单项偏差最多 1 比特，累计能差几个百分点 | **算术编码 / 区间编码**（JPEG、H.264、WebP） |
| 边流边压、频次未知 | 哈夫曼要**先扫一遍统计**才能建树（两遍） | **自适应哈夫曼**（FGK/Vitter，LZSH）或 **ANS**（zstd） |
| 需要随机访问某条记录 | 编码是全局耦合的比特流，改一个字符要重编后面全部 | 定长记录 / 普通索引结构 |
| 只想要"有序 + 查找" | 哈夫曼树**不是搜索树**，不能二分 | 回到 BST / AVL / B 树 |

### 一句话记住取舍

> **哈夫曼 = 用"两遍数据 + 存一张码表"换"整数位宽下最少的比特"。**
> 频次越不均匀越划算；频次越均匀越接近白费。

## 自检问题

**Q1：为什么"把所有字符都放在叶子上的二叉树"一定给出前缀码？**

A：因为前缀码的定义是"任何一条编码不是另一条编码的开头"，而"编码 = 根到某叶子的完整路径"。
若 A 的编码是 B 的前缀，就意味着"根 → B 的路径"中途经过了 A 所在的那个节点，
即 A 是 B 的祖先 —— 但 A 是叶子，叶子没有孩子，不可能当祖先。矛盾，所以不可能发生。
代码里的体现就是 `assign_codes` **只在 `node->is_leaf` 时往表里登记**（`huffman.c:284`）。

**Q2：哈夫曼建树为什么必须用堆？不用堆行不行？**

A：需求是"每轮取权重最小的两个"，一轮要问一次。
用堆：`O(log k)` 一轮，总共 `O(k log k)`。
全表扫描：`O(k)` 一轮，总共 `O(k²)` —— 行得通，k=256 时约 6.5 万次比较，demo 级别也够用。
更好的是**先排序 + 两个队列**：因为合并产生的权重天然单调递增，
一个"原始叶子队列" + 一个"合并结果队列"就能在 `O(1)` 摊还取到最小，总 `O(k log k)`（全花在初始排序）。
所以答案：堆不是必需，只是"标准答案的形状"；本目录用堆是因为它顺便演示了 `06-heap` 的用法。

**Q3：WPL 和"编码后的总比特数"是一个东西吗？和"所有内部节点的权重之和"呢？**

A：三个都等价（在至少合并过一次的前提下）。
- WPL = Σ(叶子权重 × 深度)。叶子深度 = 码长，叶子权重 = 频次 → 每一项就是"这个字符花掉的总比特" → 和就是总比特数。
- 合并法：每次合并让那个子树里所有叶子深度 +1，贡献 = 它们的权重和 = 新节点（内部节点）权重，
  所以 WPL = Σ 所有内部节点权重。
demo 第 5 幕三种算出来的都是 126。
例外：单字符文本（`"aaaa"`），WPL(定义法)=4、合并法=0 —— 因为一次都没合并过。这是结论的适用边界。

**Q4：解码时为什么"每读一个比特就决定下一步"就够，不用往后多看一位？**

A：这叫**即时解码**，靠的正是前缀码性质。当前所在节点是完全确定的状态：
在内部节点 → 下一个比特必须再读一位（往左/往右）；在叶子 → 已经完整，立刻吐字符回根。
两种情况下都不会出现"必须看后面才能判断"。
反例就是第 1 幕那张坏表：读到 `0` 时，它是完整编码（A）**同时**又是 `01` 的开头（B 的一半），
状态不够，必须前瞻或者加分隔符 —— 而这正是前缀码帮我们省掉的东西。

**Q5：把本节改成"真压缩文件"，还差哪几件事？**

A：至少五件：
1. 比特打包成字节（现在 `bits[]` 一个字符存一个比特，白浪费 8 倍）；
2. 把编码表/树的形状序列化进文件头（否则解压方拿不到码表），并且要尽量省 ——
   常用**规范哈夫曼（Canonical Huffman）**：只存每个码的**长度**，编码可由长度重新推出来；
3. 存原文字符数（或原始字节数）用来判断末尾停在哪儿（坑 7）；
4. 分块压缩，让码表能复用且能并行/随机访问（`gzip` 的多 block、`zstd` 的 frame）；
5. 频次未知时的自适应策略（FGK/Vitter）或先做 LZ 类重复消除再上哈夫曼（`DEFLATE`）。
本节刻意只做 1~5 之外的"核心原理"，这是教学的取舍，README 上面几个坑就是它和工程之间的距离。
