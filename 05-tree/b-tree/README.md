# B 树 b-tree

> 一句话定位：**把"一个节点"撑成一页磁盘大小**，于是树高只剩 3 层 —— 数据库和文件系统查一条记录，只需要读 3 次磁盘。

---

## 一句话是什么

B 树就是一棵**每个节点能装好几个键、能挂好几个孩子**的二叉搜索树。

二叉搜索树（BST）的一个节点是"1 个键 + 2 个孩子"；B 树把它变宽成
"最多 m-1 个键 + 最多 m 个孩子"（m 叫**阶**，order）。搜索规矩完全一样：
比大小、往左或往右的孩子钻，只不过一个节点里要连着比好几把才能决定钻哪条缝。

本节的 demo 用 **m=3**：一个节点最多 **2 个键**、最多 **3 个孩子**、最少 **1 个键**。

```
       m=3 的一个节点（2 个键，3 个"孩子空隙"）

              空隙0          空隙1          空隙2
                │              │              │
                ▼              ▼              ▼
            ┌────────┬────────┐
     ...  ◄─┤  10    │   20   ├─►  ...
            └────────┴────────┘
             全都 < 10    10 与 20 之间    全都 > 20

     铁律：空隙数 = 键数 + 1。
     有 k 个键的节点，一定挂着 k+1 棵子树，第 i 棵子树管的是
     "key[i-1] < x < key[i]" 这段区间（边界用 -∞ / +∞）。
```

它同时满足这四条（少一条就不是 B 树）：

1. 节点内键从小到大排；整棵树中序读出来全局有序。
2. 键数范围 `MIN_KEYS ≤ num_keys ≤ MAX_KEYS`（**根例外**：根最少 1 个键就行，甚至可以 0 个）。
3. **所有叶子都在同一层**（这一条是它"矮"的全部原因）。
4. 本节实现不支持重复键（真数据库靠"键 + 行号"来消歧，见「常见的坑」#4）。

## 为什么需要它

### 先看不用它有多痛

假设你有 100 万条用户记录放在硬盘上，想按 user_id 查一个人。

**方案 A：什么都不建，顺序扫。**
100 万次比较，而且为了找到一条记录把整个文件读一遍（几 GB）。查一次几秒，
每秒查一万次就是做梦。

**方案 B：拿内存里的二叉搜索树/红黑树搬过去。**
逻辑没错，但树高 ~20 层，**每层都要去硬盘上取一个不同位置的节点**。
硬盘的"随机读一次"要付 0.1~10 毫秒（机械盘约 10ms，SSD 约 0.1ms，
就算 SSD 也比内存访问慢几万倍）。20 次随机 IO = 机械盘上 200ms，
一次查询两亿分之一秒变成了 0.2 秒 —— 慢到不能用。

**方案 C：B 树。**
树高 3 层，**读 3 次磁盘**。而且这 3 次是"顺着父指针往下"的，第一次读根
（根往往常驻内存），实际可能只读 2 次。

### 关键洞察：硬盘不接受"只读一点点"

| | 内存 | 磁盘 |
|---|---|---|
| 最小读写单位 | 1 字节（缓存行 64B） | **一整页/扇区，通常 4KB** |
| 随机访问一次 | ~100 纳秒 | ~100 微秒（SSD）到 10 毫秒（HDD） |
| 读 1 字节 vs 读 4096 字节 | 差不多 | **几乎一样贵**（寻道/映射的钱照付） |

既然读 4096 字节和读 32 字节一个价，那**读回来的 4096 字节一定要装满有用的键**。
"装满一页的键"这件事，就是 B 树存在的全部理由。

**不用它时的痛，一句话总结**：
把内存结构（红黑树）直接搬到磁盘上，等于"花 4096 字节的运费，运 32 字节的货，
还要运 20 趟"。B 树把货塞满车厢，2 趟运完。

## 为什么数据库/文件系统用 B 树而不用红黑树（把账算死）

这是本节最重要的一小节。数据都用 **100 万个键**（1e6），int 键 4 字节，指针 8 字节，页 4096 字节。

### 第一步：红黑树的节点有多大、装不满一页有多亏

红黑树一个节点：`key(4) + 左指针(8) + 右指针(8) + 父指针(8) + 颜色(1) + 对齐 ≈ 32 字节`。

一个 4096 字节的页能装 **128 个节点**，但一次查找只会碰到其中 **1 个**：
因为树的每一层只需要 1 个节点，而相邻两层的节点在磁盘上位置完全随机，
**不可能一起读回来**。

```
红黑树查一个键（100 万节点，树高 ~20 层）：

  第 1 层 根节点 ──► 读页 #7734  ← 用掉 32B，剩下 4064B 白读
  第 2 层        ──► 读页 #118   ← 又一次随机 IO
  第 3 层        ──► 读页 #5521
  ...
  第 20 层       ──► 读页 #903
  ──────────────────────────────
  合计 20 次随机 IO，读回 20 × 4KB = 80KB，真正用到的只有 20 × 32B = 640B
  利用率 640 / 81920 ≈ 0.8%
```

### 第二步：B 树把一页装满键，扇出直接起飞

B 树一个节点 = 一页 = 4096 字节。设阶为 m，节点占的字节：

```
  键区 (m-1) 个 int   = 4m - 4 字节
  孩子区 m 个指针      = 8m 字节
  头部（键数、is_leaf 等）≈ 12 字节
  合计 ≈ 12m + 8   ≤ 4096   →   m ≤ 340 左右
```

于是 **m ≈ 340**：一个节点装 339 个键、340 个孩子。这个数字叫**扇出（fan-out）**，
它是 B 树杀招的来源：

```
  1 层（根）    最多 339 个键
  2 层          最多 340 × 339        ≈ 11.5 万个键
  3 层          最多 340² × 339       ≈ 3900 万个键   ← 100 万键绰绰有余
```

**所以 100 万个键只要 3 层，一次查找最多读 3 个页 = 12KB，利用率接近 100%。**

| 100 万个键 | 节点多大 | 树高 | 查找要几次磁盘随机读 | 为此读回多少字节 |
|---|---|---|---|---|
| 红黑树 / AVL / BST | ~32 字节 | ~20 层（最坏 40） | **~20 次** | 80KB（只用 640B） |
| B 树（4KB 页，m≈340） | 4096 字节（正好一页） | **3 层** | **3 次** | 12KB（基本全用上） |
| B 树（本节 demo，m=3） | 56 字节（故意做小） | 13 层才装 1e6 | 13 次 | —— 说明"阶太小=白搭" |

`make one DIR=05-tree/b-tree` 的第 5 幕就是现场把这几行算给你看，不是抄来的数字。

### 第三步：三个容易被追问的点

**① 为什么红黑树不能"把一页里 128 个节点都用上"？**
能，但要用"缓存友好的布局"重写一遍（内存数据库如 Redis 的 skiplist 就是这么干的）。
标准红黑树的父子在堆上是随机散落的，一次 IO 拿不回一条路径。
而 B 树从定义上就是"一条路径 = 一个页"，天生对齐磁盘。

**② 扇出大为什么等于 IO 少？**
树高 h ≈ log_m(n)。n=1e6 时：
- m=2（二叉树）→ log₂(1e6) = 20 层
- m=340 → log₃₄₀(1e6) = 3.97 → 取整 3~4 层

m 从 2 变成 340，层数从 20 降到 3。**层数就是 IO 次数**，这是一道纯对数换底的题。

**③ 那为什么不干脆把节点搞得越大越好（比如 1MB 一个节点）？**
页太大 → 一次 IO 读进大量用不上的键，且内存/磁盘带宽浪费、写入放大严重。
工程上就是"跟随操作系统的页大小"：文件系统 4KB，InnoDB 默认 16KB。

### 顺带一提：谁在用 B 树家族

| 东西 | 用的是 |
|---|---|
| MySQL InnoDB 主键/二级索引 | **B+ 树**（16KB 页） |
| PostgreSQL 默认索引 | **B 树**（变体，8KB 页） |
| MongoDB / SQLite / RocksDB | B 树家族 / LSM 树 |
| NTFS、ext4、APFS、HFS+ 目录与元数据 | **B 树 / B+ 树** |
| Java HashMap、Redis zset | 不是 B 树（哈希表 / 跳表），因为它们在内存里 |

## B+ 树和 B 树的差别（为什么 MySQL 索引用 B+ 树）

**一句话：B 树的每个节点都存数据；B+ 树只有叶子存数据，内部节点纯粹是"路牌"，
并且所有叶子被一条链表串起来了。**

```
B 树（内部节点也挂数据）        B+ 树（内部节点只是路牌）
      [10|20]                        [10 | 20]        ← 只有键+孩子指针，没数据
      /  |  \                        /      \
  [5] [12] [30]                [10|20]  [20|30]      ← 内部层更小 → 扇出更大
   ↑ 每个节点都可能带记录        [5] ⇄ [10] ⇄ [12] ⇄ [20] ⇄ [30]   ← 叶子串成链表！
```

三个实质区别：

| 差别 | 带来什么好处 |
|---|---|
| 内部节点**不存数据**，只存"键 + 页号" | 同样一页能塞下的路牌数量暴增（InnoDB 16KB 页里约 1170 个），扇出更大 → 树更矮。经典结论：**3 层 B+ 树大约能索引 2000 万行**（1170 × 1170 × 每叶约 16 行 ≈ 2190 万） |
| 叶子用指针**串成有序链表** | `WHERE age BETWEEN 20 AND 30`、`ORDER BY id LIMIT 1000` 这种范围查询，定位到起点之后**沿着链表横着走**就行，不用回到上层再钻。B 树做范围查询要"中序回溯"，代价高得多 |
| 所有查询都**一定走到叶子**才拿到数据 | 耗时稳定（每次都是"树高"次 IO），红黑树/B 树里"命中内部节点就提前返回"反而让成本忽快忽慢 |

顺带一句"聚簇索引"：InnoDB 的叶子直接存整行数据，所以主键索引的叶子=数据本身，
二级索引的叶子存的是主键值（所以要"回表"再走一次 B+ 树）。
这一串推理的起点，就是本节写的这颗 B 树。

## 内存布局图解

### 一个节点在 C 里到底是怎么摆的

```c
typedef struct BTreeNode {
    int key[BTREE_MAX_KEYS + 1];              /* 2 + 1 = 3 格 */
    struct BTreeNode *child[BTREE_MAX_KEYS + 2]; /* 2 + 2 = 4 格 */
    int num_keys;
    int is_leaf;
} BTreeNode;
```

堆上 `[10 | 20]` 这个节点长这样（地址从 0x3000 开始，64 位平台）：

```
        0x3000 ┌───────────────────────────┐
               │ key[0] = 10               │  4B
               │ key[1] = 20               │  4B
               │ key[2] = 0   ← 超载缓冲格  │  4B（只有分裂那一瞬间用得上）
               │ (对齐填充 4B)              │
        0x3010 ├───────────────────────────┤
               │ child[0] = 0x2A00  ──────────► 子树：全都 < 10
               │ child[1] = 0x2B40  ──────────► 子树：10 < x < 20
               │ child[2] = 0x2C80  ──────────► 子树：全都 > 20
               │ child[3] = NULL    ← 超载缓冲格
        0x3038 ├───────────────────────────┤
               │ num_keys = 2              │  4B
               │ is_leaf  = 0              │  4B
        0x3040 └───────────────────────────┘   共 56 字节

  ⚠ 两个数组为什么都多开一格？（这一格是本节最容易看错的 4 个字节）
     本实现的插入是"先塞满再分裂"：塞完第 3 个键的一瞬间，节点里就是
     MAX_KEYS + 1 = 3 个键、4 个空隙。没有这两格缓冲，就得临时再 malloc
     一个数组、搬完、释放 —— 白折腾一趟还可能失败。
     所以数组直接开大一格，超载的那一格用完就在分裂里搬走，恢复 ≤ MAX_KEYS。
```

### child[] 的"空隙"到底是什么（这张图必须看懂，否则代码全看不懂）

```
       内部节点 [10 | 20] 有 3 个孩子，孩子编号永远和"键的缝隙"对齐：

                     key[0]=10        key[1]=20
       ┌───────────────┬──────────────────┬──────────────┐
       │               │                  │              │
       │   child[0]    │    child[1]      │   child[2]   │
       │  x < 10       │  10 < x < 20     │  x > 20      │
       └───────────────┴──────────────────┴──────────────┘

       规律：child[i] 管的区间是 ( key[i-1] , key[i] )，两端不存在就用 ±∞。
             有 num_keys 个键 → 有 num_keys+1 个孩子，最大下标就是 num_keys。
```

### 整棵 demo 树在内存里的连线（第 2 幕最后那棵树）

```
   root ──► [5 | 9]
              ├─ child[0] ──► [2]
              │                 ├─ child[0] ──► [1]
              │                 └─ child[1] ──► [3 | 4]
              ├─ child[1] ──► [7]
              │                 ├─ child[0] ──► [6]
              │                 └─ child[1] ──► [8]
              └─ child[2] ──► [11 | 20]
                                ├─ child[0] ──► [10]
                                ├─ child[1] ──► [12]
                                └─ child[2] ──► [30 | 40]

   堆上这些节点的地址完全可能乱序（[8] 的地址比 [1] 小也照样跑得通），
   顺序全靠上面这些指针。这就是"树 = 指针连起来的盒子堆"，
   跟"内存里挨着放"的数组正好相反（对比 01-array/dynamic-array）。
```

## 核心操作逐个拆解

### 1. `btree_new()` —— 建一棵空树

**干什么**：给一个能用的树根。

**一步步怎么做**
1. `calloc(1, sizeof(BTreeNode))` 租一个节点。
2. `num_keys = 0`，`is_leaf = 1`。
3. 返回它当根。

**边界情况**
- **空树不是 NULL**，而是一个 0 键的叶子。这样插入永远只有"钻到叶子塞键"一条路，
  不用在第一次插入时特判"要不要造根"。
- 用 `calloc` 而不是 `malloc`：把所有 `child[]` 一次性清成 NULL。
  忘清 child 是这个结构最致命的 bug（垃圾指针一解引用就段错误，而且几层之后才炸）。

**对应代码**：`btree.c:163`（`btree_new`）、`btree.c:47`（`btree_make_node`，含内存图注释）

---

### 2. `btree_search(root, key, &probes)` —— 查找

**干什么**：判断键在不在，顺便数出"读了几次页"（`probes`，磁盘语境下就是 IO 次数）。

**一步步怎么做**
1. 从根开始，`probes++`（进一个节点 = 读一页）。
2. 在本节点的键里线性找 `key`：找到 → 命中，收工。
3. 节点是叶子 → 树里没有这个键，收工。
4. 否则用 `btree_gap_pos` 找"第一个严格大于 key 的键的下标 i"，钻 `child[i]`，回第 1 步。

**为什么是"第一个严格大于"**：键小于 key 的都留在左边，只有"第一个比你大"的键
才是你右边那道缝的左边界。举例：`[10|20]` 里查 15 → 20 是第一个 > 15 的，下标 1 → 钻 child[1]（管 10<x<20）。

**边界情况**
- `root == NULL`：直接返回没找到，probes = 0（防御性，正常不该出现）。
- 查不存在的键也照样走到叶子 —— 因为**所有叶子同层**，所以"查有"和"查无"成本一样，
  都是 ≤ 树高 次。这一点 demo 第 3 幕打印给你对比了。
- `probe_out` 可以传 `NULL`，表示"我不关心读盘次数"（`_out` 参数的老约定）。

**对应代码**：`btree.c:212`（`btree_search`）、`btree.c:139`（`btree_gap_pos`，全节最核心的下标函数）

---

### 3. `btree_insert(&root, key)` —— 插入（本节最大考点）

**干什么**：塞进一个键，并保持 B 树的四条规矩不破。

**一步步怎么做（"先塞满再分裂"流派）**
1. 从根往下钻，一直钻到一个**叶子**（走法同查找）。
2. 在叶子数组里找插入位置：`pos` = 第一个比 key 大的键的下标。
3. 把 `[pos, num_keys)` 整体**从后往前**右移一格，在 `pos` 写入 key，`num_keys++`。
4. 检查 `num_keys > MAX_KEYS`？
   - 没超 → 完事。
   - 超了 → **分裂**：
     - `mid = num_keys / 2`；中键 `key[mid]` 单独拿出来；
     - `key[mid+1..]` 和 `child[mid+1..]` 搬进一个**新申请的右兄弟**；
     - 本节点收缩成"左半"（`num_keys = mid`）。
5. 中键 + 右兄弟**上推给父亲**：父亲在对应下标插入中键，右兄弟挂成 `child[gap+1]`。
6. 父亲被塞了键之后可能又超载 → 回到第 4 步，**分裂一层层往上冒**。
7. 如果冒到**根**还是超载 → 现造一个新根（1 个键、2 个孩子），树高 +1。

图解（demo 第 1 幕插 30 的真实过程）：

```
   插之前:  root ──► [10 | 20]
   第③步:          [10 | 20 | 30]   ← 超载一格（key[2] 缓冲格正在用）
   第④步分裂:      左半 [10]     中键 20     右半 [30]（新建节点）
   第⑦步没人接中键 → 造新根：

                    [20]              ← 新根（1 键 2 孩子）
                   /    \
              [10]        [30]

   插 40 时（第⑤步有父亲接）：
                    [20]                    [20 | 40]
                   /    \      中键 40 上推  /    \    ← 父亲没超载，到此为止
              [10]     [30 | 40]        [10]   [30]  [50]...
```

**边界情况**
- **重复键**：本实现直接忽略并打印一句提示（返回值 0）。真数据库要允许重复，
  得把"行号/主键"拼进键里，见坑 #4。
- **根分裂**：没人接中键，所以必须造新根 —— 这是 B 树**唯一**长高的方式（红黑树靠旋转"局部加深"，B 树只在根加层，所以叶子永远同层）。
- **内存不够**：分裂所需的右兄弟、新根都是**先申请好再动手改状态**。
  任何一次申请失败，函数原样退回，树一个字节都没改，也不漏内存（这是本节刻意保住的性质，见 `btree_split` 上方注释）。
- **`key` 数组比 `MAX_KEYS` 大一格**：写循环边界时特别容易数错，所有涉及"空隙"的循环上界都是 `num_keys + 1`。

**对应代码**：`btree.c:469`（`btree_insert`：处理根分裂 + 备用根）、`btree.c:342`（`insert_one`：递归主体）、`btree.c:289`（`btree_split`：劈三块，带完整内存图）

### 4. `btree_remove(&root, key)` —— 删除（本节实现了完整版）

> 说明：这一节**不是留空、也不是假代码**。借键、合并、连锁合并、根退化四种情况
> demo 第 4 幕全都真跑出来了，输出在下面「运行结果」里可以逐行对照。

**干什么**：删掉一个键，并保持"所有非根节点键数 ≥ MIN_KEYS"。

**一步步怎么做**
1. 递归下钻到目标键所在的位置（走法同查找）。
2. 分三种情况：
   - **在叶子上** → 直接删（数组左移一格，`num_keys--`）。
   - **在内部节点上** → **绝不真删**：取左子树最大键（**前驱**）顶替它，
     然后去左子树里删掉那个前驱。前驱一定在叶子最右下角，于是"真删"永远发生在叶子。
   - **没找到** → 什么都不做，返回 0。
3. 如果删完某个节点键数 < MIN_KEYS（**欠键 underflow**）→ 向上汇报，让父亲救：
   - **① 左兄弟有富余**（`> MIN_KEYS`）→ **借**：父亲的 `key[i-1]` 下移给我当最小键，
     左兄弟的最大键上移进父亲，左兄弟最右边的孩子指针转给我当最左孩子（右旋）。
   - **② 右兄弟有富余** → 镜像操作（左旋）。
   - **③ 都没富余** → **合并**：父亲的 `key[j]` 下移当"桥"，把 `child[j+1]` 整个搬进
     `child[j]`，空壳节点 `free` 掉；父亲少一个键、少一个孩子。
4. 父亲因为合并少了一个键，可能自己也欠键 → 继续往上救 → **连锁合并**。
5. **根被掏空（0 键）** → 让它唯一的孩子当新根，老根 free → **树矮一层**。

图解一（借键，demo 第 4 幕"删 1"的真实一步）：

```
   父亲 [2]，孩子 child[0] = []（欠键 0 个），child[1] = [3 | 4]（有富余，2 > MIN_KEYS=1）

   借之前:              借之后:
        [2]                  [3]                       ← 父亲的键换了
       /   \                /   \
     []    [3|4]          [2]   [4]                    ← 父亲的 2 下移给我，我的 3 上移给父亲

   序关系检查：左子树 [2] < 父亲键 3 < 右子树 [4] ✓ 一点没破
```

图解二（合并 + 连锁，demo 第 4 幕"删 10"，三层一起塌）：

```
            [40 | 80]                 [40 | 80]                [40]
            /   |   \                /   |   \                 /  \
        [20]  [60]  [100|120]  →  [20] [60] [100|120]   →   []  [60]  [100|120]  →  ...
        /  \                       /  \                       []
     [10]  [30]                 [ ]  [30]                     ↑
   删 10 → 叶子变空          没得借 → 用 20 当桥合并          合并后 [20|30]
   父 [20] 少键 → 空 → 再往上一层合并 → 根 [40|80] 也少键 → 根剩 0 个键 → 树矮一层
```

**边界情况**
- **删内部节点**必须换前驱/后继，否则那两道空隙代表的两棵子树会断掉。
- **合并的键数账**（m=3）：欠键孩子 0 个键 + 桥 1 个 + 兄弟 ≤ MIN_KEYS=1 个 = 2 = MAX_KEYS，
  **绝不会超载**。一般情形 `2·ceil(m/2)-1 ≤ m-1` 恒成立 —— 这就是 MIN_KEYS 定义成
  `ceil(m/2)-1` 的原因，它不是随手拍的数字，是为了让"合并刚好不超载"。
- **`i == 0` 且没左兄弟**：只能往右看；若右边也帮不上，就把右兄弟并进自己
  （实现里统一成"把 j+1 并进 j"，所以取 j=0）。
- **删到根剩 0 键**：根是内部节点 → 退化；根是叶子 → 变成空树（保留 0 键叶子当根，
  所以空树还能继续插，demo 里最后 5/6/7 就是插进"删空的树"的）。
- **删不存在的键**：全程不改一个字节，返回 0（demo 里删 666 演示）。

**对应代码**：`btree.c:901`（`btree_remove`）、`btree.c:825`（`remove_one`）、`btree.c:788`（`fix_child`：借/合并的决策树）、
`btree.c:608`（`borrow_from_left`）、`btree.c:659`（`borrow_from_right`）、`btree.c:723`（`merge_children`）、`btree.c:580`（`subtree_max_key` 找前驱）

## 复杂度表

本节 m=3；真实场景 m≈300~1200，"树高"那一列差别就在 m 上。n = 键的个数。

| 操作 | B 树（阶 m） | 红黑树 / AVL | 二叉搜索树（退化成链） | 有序数组 | 哈希表 |
|---|---|---|---|---|---|
| 查找 | O(log_m n) | O(log₂ n) | O(n) 最坏 | O(log₂ n) 二分 | O(1) 平均 |
| 查找的**磁盘 IO 次数** | **≈ log_m n**（3~4 次） | ≈ log₂ n（20 次） | 不可用 | 二分只需 log 次，但要连续读 | 哈希冲突后不可控 |
| 插入 | O(log_m n)，节点内数组移动 O(m) | O(log₂ n) + 旋转 | O(n) 最坏 | **O(n)**（要整体搬） | O(1) 平均 |
| 删除 | O(log_m n) + 借/合并链式上推 | O(log₂ n) + 旋转 | O(n) | **O(n)** | O(1) 平均 |
| 范围查询 `[a,b]` | B+ 树 O(log n + k)（叶子链表横着走） | 中序回溯 O(log n + k)，常数大 | O(n) | O(log n + k) 顺序扫，很友好 | 做不到，只能全表 |
| 最坏高度 | ⌈log_m n⌉，很矮 | 2·log₂(n+1) | n（有序输入直接成链） | 1 | —— |
| 额外空间 | O(n) | O(n) | O(n) | O(n) | O(n)~O(1.5n) |
| 无序数据的等值查询 | 不如哈希 | 不如哈希 | 不如哈希 | 不如哈希 | **最强** |
| 是否有序保存 | 是 | 是 | 是 | 是 | **否** |

三个要点：
- B 树的优势**全部来自"扇出大 → 层数少"**，而层数只在"一次 IO 一页"的场合才是硬成本。
  纯内存环境下 log₂ 和 log₃₄₀ 的差别只是指针追逐次数，红黑树常更省内存、更简单。
- B 树节点内是"数组"，所以插入/删除要 O(m) 的数组搬移；但 m 再大也就几百，比一次磁盘 IO 便宜得多。
- 哈希表 O(1) 但**不保序**，所以范围查询、排序、前缀匹配都干不了 —— 这正是索引必须用 B+ 树的原因。

----------------------------------------

     节点字节 = (m-1)×4 + m×8 + 16 = 12m + 12 ≤ 4096  →  m ≤ 340

  ② m=340 时装下 1000000 个键要几层？（每层最多键数 = (m-1)×m^(h-1)）
     第 1 层最多装 339 个键
     第 2 层最多装 115260 个键
     第 3 层最多装 39188400 个键  ← 够了！

  ③ 本节 demo 的 m=3 呢？（对比就知道「阶」有多重要）
     m=3：一个节点最多 2 个键，装下 1000000 个键要 13 层（对照 demo：现在树里 3 个键就已经 2 层了）
     结论：阶越小 → 树越高 → 读盘越多次。教学用 m=3 是为了看清分裂，
           工程上 m 是由『一页装几个键』定出来的几百到几千。

  ④ 红黑树（BST 家族）同样 100 万个键：
     节点 = 键 4B + 左右父 3×8B + 颜色 1B + 对齐 ≈ 32B
     树高 ≈ log2(1000000) = 20 层（最坏 2×log2(n) = 40 层）
     一次查找 = 从上到下 = 20 次随机 IO，虽然 32B 塞不满一页，
     但每次 IO 都得付一遍寻道/映射的钱 → 20 × 4KB = 80KB 读进来，只用 640B。

## 常见的坑

### 1. `child[i]` 的下标算错一格 —— 整棵子树凭空消失
键的下标是 `0..num_keys-1`，孩子的下标是 `0..num_keys`（多一个）。
插入时两个数组都要右移，**循环起点差 1**：

```c
for (int i = node->num_keys;     i > gap;     i--) node->key[i]   = node->key[i-1];   /* 键 */
for (int i = node->num_keys + 1; i > gap + 1; i--) node->child[i] = node->child[i-1];  /* 空隙 */
```
写成一样的边界，表现是"某些键找不到了"或"中序打印少一个数"。
**每次改完数组操作，第一件事是打中序看还剩几个键**（本节每个函数都顺手打了）。

### 2. 分裂/借键之后忘了把搬走的格子擦成 0 / NULL
`num_keys` 变小了，但数组尾格还留着老键、老指针。老指针尤其危险 ——
左右两个节点都存着同一个子节点地址，将来 `btree_free` 会把它释放两次（double free，堆管理器直接 abort）。
本节的规矩是"用完擦干净"，`btree_split`、`borrow_*`、`merge_children` 里每一条都做了。

### 3. "先塞满再分裂" vs "边下钻边预分裂"，两种写法不能混
- 本节用的：钻到叶子塞键 → 超载再往上劈。所以需要 `key[MAX_KEYS+1]` 缓冲格。
- CLRS 那套：下钻之前先看孩子满不满，满就先劈，于是任何节点都不会超载，
  数组正好 `key[MAX_KEYS]` 就够。
两种都对，**混用就炸**：比如拿 CLRS 的数组大小去跑本节的代码，插入时直接数组越界
（写 `key[MAX_KEYS+1]` 那一格，ASan 会报 heap-buffer-overflow）。

### 4. 重复键
本实现遇到重复键直接忽略。真数据库不能这么办 —— 主键可以拒，索引键（比如"年龄"）必须允许重复。
标准做法是把键做成 `(age, 主键id)` 这种复合键，靠主键把两个相同 age 分出大小，
于是"重复"在 B 树眼里根本不存在。另一个做法是每个键挂一个"行号链表"。
考试如果问"B 树能存重复键吗"，准确回答是"键本身不重复，但可以让值重复或用复合键"。

### 5. 删除时先递归再顶替，键就"删了个寂寞"
`remove_one` 处理内部节点命中时，顺序必须是
`node->key[pos] = pred;` → `remove_one(child[pos], pred)` → 需要时 `fix_child(node, pos)`。
如果把顶替放到递归之后，递归里的借键/合并会搬动本节点键数组，旧值又被搬回来了。

### 6. 用二分查找去节点里找键 —— 对，但别在 demo 里这么写
真实 B 树一页有几百个键，节点内确实是二分（或插值查找）。
本节 m=3 只有 2 个键，二分反而更慢更绕。**"用哪种查找取决于 m 的大小"**，
写代码前先问自己：这里一个节点装几个键？

### 7. 把 B 树和 B+ 树混为一谈
B+ 树叶子才存数据、叶子还串成链表；B 树每层都可能带数据。
面试写"B 树索引支持高效范围查询"会被追问 —— 严格说是 **B+ 树**的叶子链表在支撑。

### 8. 认为"B 树高度是固定的"
所有叶子同层（这是真的），但**同一层数能装的键数有个范围**，
删除引发合并后，很多节点会只剩 MIN_KEYS 个键，树会明显变矮变空。
本节 demo 第 4 幕最后从 3 层塌到 1 层就是这个现象。

## 什么时候用它 / 什么时候别用

**该用 B 树家族：**
- 数据放不进内存（数据库表、文件系统、消息持久化）—— 只要目标是"少几次磁盘 IO"，就是它。
- 需要**有序**访问 + **范围查询**（`>``<``BETWEEN``ORDER BY`、前缀匹配）。
- 需要主键/唯一约束这种"要么找到要么断定没有"的语义（叶子同层 → 查无和查有一样快）。

**别用：**
- 纯内存 + 只有等值查询 → **哈希表**（O(1)，B 树的 log 是白付的）。
- 纯内存 + 只要有序/前驱后继 → **红黑树 / AVL**（节点小、代码比 B 树好写、内存省得多）。
- 写多读少、要求顺序写磁盘（LSM-Tree：RocksDB / HBase / Cassandra）——
  B 树随机写会触发分裂和页级写放大，这类场景 LSM 更合适。
- 数据量小到"一次读一整块进内存也无所谓"（比如几千条配置）→ **有序数组 + 二分**最省事，
  还自带最好的缓存局部性。
- 需要"并发插入不锁整棵树" → 工程上得配合 latch coupling / B-link tree，本节实现完全没考虑并发。

## 自检问题

**Q1：一页 4KB，int 键 4B，指针 8B，阶 m ≈ 340。为什么 100 万个键只要 3 层？**
A：第 h 层最多能装 `(m-1) × m^(h-1)` 个键。h=2 → 340×339 ≈ 11.5 万（不够），
h=3 → 340²×339 ≈ 3900 万（够了）。树高就是 IO 次数，所以 3 次。

**Q2：为什么 B 树的叶子一定同层？这个性质是靠什么操作维持的？**
A：因为 B 树**只在根那一层长高**（根分裂才造新根），删除塌下去也是从根塌
（根剩 0 个键才退化）。中途的分裂、借键、合并全都发生在"同一层内部"，
不会让某一条路径单独变长。红黑树没这个约束，叶子可以深浅不一。

**Q3：`[10 | 20]` 这个节点里查 20 应该怎么办？插入 20 呢？**
A：查 20：`btree_key_pos` 直接命中 `key[1]`，不用往下钻。
插入 20：本实现视为重复键忽略。真索引里 20 会作为"另一个 (20, id)"往下走到叶子。

**Q4：删除时为什么"不能真的把内部节点的键摘掉"？两种补救叫什么事？**
A：那个键是左右两棵子树的**分界标签**，摘掉之后两棵子树的区间就没界了。
所以要拿前驱（左子树最大）或后继（右子树最小）来顶替，再去子树里删那个顶替者 ——
它保证在叶子上。补救手段的两个名词：兄弟有富余叫 **借/旋转（rotate）**，
都没富余叫 **合并（merge）**，合并会让父亲少一个键，所以可能一路往上连锁。

**Q5：本节 `key[]` 开的是 `MAX_KEYS + 1` 格，为什么？**
A：因为插入用的是"先塞满再分裂"，塞完第 MAX_KEYS+1 个键的一瞬间必须有个地方放它。
如果换成 CLRS 的"下钻前先预分裂"，就永远不会有超载瞬间，`MAX_KEYS` 格足够 ——
但数组大小和写法必须配套，混用会越界。

**Q6：B+ 树为什么比 B 树更适合做范围查询？**
A：两个原因：① 叶子存数据且用指针串成有序链表，定位到起点后横向走就行，不用回溯；
② 内部节点不存数据，一页装的路牌更多 → 扇出更大 → 树更矮。
