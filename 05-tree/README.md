# 05 · 树 tree

> 前面四章（数组 / 链表 / 栈 / 队列）都是"一条线"，从这里开始是"分叉"。
> 树是本仓库最重要的一章：数据库索引、`map`/`set`、堆、文件系统、编译器语法分析、压缩编码，全在这里。

## 一句话是什么

**树 = 一个根 + 若干棵子树，每棵子树本身又是一棵树。**

这个"自己定义自己"的性质叫**递归定义**，它带来两个直接后果，贯穿本章全部六种结构：

1. 处理树几乎总是在写递归：`先处理自己 + 递归处理每个孩子`，出口永远是"这个指针是 NULL"。
2. 于是"遍历"就是树唯一的读法，而**性能只取决于树有多高**（高度 = 从根走到最深叶子要几步）。

```
        树的样子                         为什么"高"决定一切
       root ─── 1                        查找/插入/删除都是"往下走一层"
        / \                             走得越深越慢
       2   3       ← 高度 3             平衡树高 ≈ log2(n) → 100 万个数据只要 20 层
      / \   \                           退化树高 = n        → 100 万个数据要 100 万层
     4   5   6    ← 叶子
```

## 本章解决的唯一核心矛盾

**"用指针分叉"让我们摆脱了数组的挪动成本，但代价是树形会被数据的顺序带偏。**

| 这条链条就是本章的主线 | 它干了什么 | 还剩什么问题 |
|---|---|---|
| **binary-tree** 普通二叉树 | 先不管顺序，把"节点 + 两个指针 + 四种遍历"练熟 | 查找只能 O(n)，压根没有顺序 |
| **bst** 二叉搜索树 | 加一条铁律「左 < 根 < 右」→ 中序天然有序，查找平均 O(log n) | **会退化**：数据按序进来就变成链表，退化成 O(n) |
| **avl-tree** | 每个节点记高度，一歪就**旋转**拽回来 → 严格平衡，最坏也 O(log n) | 旋转太积极，插入删除时调整频繁 |
| **red-black-tree** | 改用"红/黑颜色 + 5 条性质"做**懒平衡**（近似平衡），旋转次数更省 | 代码最复杂，仍然只有"近似"平衡 |
| **b-tree** | 一个节点存很多 key、有很多孩子（又矮又胖）→ 一次磁盘 IO 拿回一大把 | 实现复杂，内存场景反而不如二叉 |
| **huffman-tree** | 不再为了"查得快"，而是按**出现频率**造树：常见字符离根近 → 变长前缀码压缩 | 只能用于编码/压缩这个专门场景 |

> **一句话讲透全章：从 BST 到 AVL 到红黑树，全都是在解决同一个「退化」问题 ——
> 插入删除之后想办法把树拽回平衡，让高度永远稳在 O(log n)。**
> B 树解决的是同一问题的存储版（别让树长高，一高就要多读几次磁盘）；
> 哈夫曼树是唯一的"反派"：它**故意**把树造得不平衡，因为它的目的不是查找快，是编码短。

## 六种结构对比表

| 结构 | 目录 | 是否按值有序 | 是否自动平衡 | 平衡手段 | 查找最坏 | 典型应用场景 | 实现难度 |
|---|---|---|---|---|---|---|---|
| 普通二叉树 | `binary-tree/` | ❌ 无序 | ❌ 谈不上 | 无 | O(n)（本来就不靠顺序） | 表达式树、DOM/目录层级、递归与遍历教学 | ★★ |
| 二叉搜索树 | `bst/` | ✅ 左<根<右 | ❌ **会退化** | 无 | **O(n)** | 有序集合入门、`map`/`set` 的原理、区间查询 | ★★★ |
| AVL 树 | `avl-tree/` | ✅ | ✅ **严格平衡**（高度差 ≤ 1） | 四种**旋转**（LL/RR/LR/RL） | O(log n) | 读多写少的有序索引（数据库内存索引、字典） | ★★★★ |
| 红黑树 | `red-black-tree/` | ✅ | ✅ **近似平衡**（最长路 ≤ 2× 最短路） | 变色 + 旋转，性质保证 | O(log n) | `std::map`、Java `TreeMap`、Linux 内核调度/epoll、Nginx | ★★★★★ |
| B 树 | `b-tree/` | ✅ 节点内多 key 有序 | ✅ 靠"所有叶子同层 + 度数下限" | 节点**分裂/合并**（不是旋转） | O(log_m n)，m = 阶 | 数据库索引（MySQL InnoDB）、文件系统（ext4/NTFS） | ★★★★★ |
| 哈夫曼树 | `huffman-tree/` | ❌ 只按频率，不比大小 | ❌ 不但不平衡，还故意歪 | 每次取两个最小的合并（配**堆**） | 不适用（是编码不是检索） | 压缩（DEFLATE/ZIP、JPEG 熵编码）、前缀码设计 | ★★★ |

补充几点，避免背错：

- **"有序"和"平衡"是两件正交的事**：AVL/红黑/B 树都既有序又平衡；
  堆（`06-heap/`）平衡但**只有偏序**（父亲 ≤ 孩子），中序遍历毫无意义；
  哈夫曼树连偏序都没有。
- **AVL vs 红黑树怎么选**：AVL 更平衡 → 查得更快；红黑调整次数更少 → 写得更快，
  而且删除时最多 3 次旋转，所以标准库和内核几乎都选红黑。
- **B 树为什么"又矮又胖"**：磁盘一次读 4KB，一个节点塞满一页 → 读一次比较几十个 key，
  树高 3~4 层就能索引上亿行。二叉树太瘦，读一层只拿到 1 个 key，IO 次数直接爆炸。

## 建议学习顺序（就是本章目录顺序）

| 顺序 | 目录 | 必须先想通的事 |
|---|---|---|
| 1 | `binary-tree/` | 节点 = 数据 + 两个指针；前/中/后 = "访问自己"的时机；层序要队列；递归就是在用系统的栈；销毁必须后序 |
| 2 | `bst/` | 一条铁律换来"中序有序 + 每步砍一半"；插入必落在空位；删除三种情况（尤其后继顶替）；**亲手把它退化成链表** |
| 3 | `avl-tree/` | 四种旋转到底把哪根指针改了；为什么旋转后铁律还成立；平衡因子怎么维护、什么时候才需要往上回溯调整 |
| 4 | `red-black-tree/` | 五条性质；为什么"红红不能相连"就够保证不退化；插入修复的三种情况（叔父红 / 叔父黑）；为什么工程上宁要"懒平衡" |
| 5 | `b-tree/` | 一个节点放 m-1 个 key、m 个孩子；插入满了就分裂并向父亲"顶"一个 key；所有叶子同层 |
| 6 | `huffman-tree/` | 频率决定树形；从根到叶的 0/1 路径 = 编码；为什么"前缀码"保证解码无歧义；为什么这棵树**故意**不平衡 |

学完 2 之后先拐去 `06-heap/binary-heap/` 看一眼也很划算：堆是"用数组存树"，
和前面"用指针连树"形成对照，会立刻让你明白"指针不是树的必需品"。

## 内存布局：六种结构的节点到底长什么样

```
① 普通二叉树 / BST / AVL / 红黑树：一个节点两个指针（AVL 多个高度，红黑多 1 个颜色）

   ┌────────┬────────┬────────┐        ┌────────┬────────┬────────┬────────┐
   │ val 40 │ left   │ right  │        │ val 40 │ left   │ right  │ h=2 或 红│
   └────────┴───┬────┴───┬────┘        └────────┴───┬────┴───┬────┴────────┘
                ▼        ▼                          多出来的字段就是"怎么保持平衡"的代价

② B 树（阶 3）：一个节点好几个 key、孩子比 key 多一个，又矮又胖

   ┌───────────────────────────────┐
   │ n=2 │ key[10] │ key[30] │     │
   │     │   ▲     │    ▲    │  ▲ │   ← 3 个孩子指针
   └─────┼───┼─────┼────┼────┼────┘
        <10  10~30   >30        一次 IO 读回一整页，顺手比较几十个 key

③ 二叉堆：根本没有指针，父子和下标算出来

   数组：[ 1 │ 3 │ 5 │ 8 │ 7 │ 6 ]     i 的孩子 = 2i+1 和 2i+2
                                          → 省掉一半内存（指针），代价是不能按 key 找
④ 哈夫曼树：权值 + 两个指针；真正的信息藏在"从根到叶的 0/1 路径"里
   (5) ── 频率小的往深处走 → 编码长；(9) 靠近根 → 编码短
```

## 各结构怎么"看"——遍历的横向对比

| 遍历/看法 | 在干什么 | 谁在用 |
|---|---|---|
| 前序 根→左→右 | 先拿到框架再填细节：复制一棵树、表达式转前缀（波兰式）、XML 开始标签 | binary-tree、BST 打印 |
| 中序 左→根→右 | **BST 的"体检报告"和"排序输出"**；也用来判合法（严格升序？） | BST / AVL / 红黑 |
| 后序 左→右→根 | 孩子的结果都齐了才轮到算自己：求高度、删整棵树、表达式求值（`a b c * +`） | 所有结构的 `free_tree`、AVL 重算高度 |
| 层序（BFS） | 一层一层看：完全二叉树/堆的下标编号、最短路径、按深度统计 | 堆的下标关系、B 树看层数 |
| 从根到叶的路径 | 路径本身就是答案：查找走了哪几岔、哈夫曼编码 0/1 | bst 查找、huffman 编码 |

## 本章共同的坑

1. **以为"树 = 查找快"** —— 只有**平衡的有序树**才快。裸 BST 会退化，堆和哈夫曼树根本不面向查找。
2. **递归没写 NULL 出口**：树函数第一句永远是 `if (node == NULL) ...`，少了它就段错误。
3. **销毁没走后序**：孩子的地址写在父亲身体里，先 free 父亲 = use-after-free。
4. **改了指针忘了"谁来指它"**：删除/旋转时如果不把新根交回父亲（返回值或二级指针），
   那一支子树就凭空消失 —— 表现为内存泄漏 + 数据不见了。
5. **把 `left/right` 当成"小/大"**：普通二叉树里 left 只是"第一个孩子"，和大小无关；
   只有 BST 里 left 才等价于"更小的那边"。
6. **背错"前中后"**：三者左右顺序永远不换，换的只是"访问自己"这一句写在第几个位置。
7. **拿树当数组用**：树不支持 O(1) 随机访问，"给我第 5 个"在树里是 O(n)（或需要子树计数）。
8. **忽略真实成本**：树每个节点两个指针（本机 24 字节存 4 字节 int），
   还有随机跳转带来的缓存不友好；小数据集上数组 + 二分经常实测更快。

## 自检问题

1. **本章六种结构，哪几种是"为了查找快"，哪几种不是？依据是什么？**
   **答：** binary-tree 不是（无序，查找 O(n)，它是教学载体）；bst / avl / red-black / b-tree 是
   （都按值有序，差别只在"怎么防退化"：bst 不管、avl 旋转、红黑懒平衡、b-tree 靠"节点变胖"）；
   huffman-tree 也不是（按频率建树，目标是编码长度最短，压根不做按值查找）。

2. **"一棵 7 个节点的 BST，最坏多高？什么数据会造成最坏？"**
   **答：** 7 层（就是链表）。按 1,2,3,4,5,6,7 或 7,6,...,1 这种有序序列插入就会造成。
   `05-tree/bst/` 第 7 幕现场打印了这棵树，屏幕上看就是一条链。

3. **AVL 和红黑树都保证 O(log n)，为什么标准库的 `map` 选红黑树？**
   **答：** 红黑是"近似平衡"，插入/删除时的旋转和变色次数更少（删除最多 3 次旋转），
   写场景代价低；AVL 太平衡，一次写入可能沿路回溯调整很多层。
   读远多于写才选 AVL；通用容器选红黑。

4. **为什么 B 树不追求"平衡到左右子树高度差 ≤ 1"，而是追求"所有叶子在同一层"？**
   **答：** 它真正的敌人是磁盘 IO 次数，而 IO 次数 = 树高（每层读一页）。
   只要保证同层 + 度数下限，树高就被钉在 log_m n；节点内一次比较多个 key 是免费的，
   所以"胖"比"平衡得精细"更有价值。

5. **"递归其实就是系统在帮你用栈"，这句话在本章体现为什么？**
   **答：** 每个树函数都在"记住我欠哪个孩子还没走"，这件事是栈帧自动做的。
   所以前/中/后序都能改写成显式栈的迭代版（`binary-tree` 三个都写了并逐位对拍）；
   而层序遍历不是深度优先，它的"欠账表"必须是队列 —— 这也是为什么本节自带一个队列。

6. **本章为什么每个目录都自带一份 `free_tree` / `print_tree`，不共享代码？**
   **答：** 叶子目录独立编译（Makefile 只把同一目录下的 `.c` 编到一起），
   跨目录 include 会直接编译失败。教学仓库里"重复但自包含"优于"精简但互相牵连"。
