# 红黑树 red-black-tree

> 同样是二叉搜索树的自救，但红黑树换了个思路：不量高度，改**给节点染色**，然后死守五条规则。
> 规则一守住，"最长路径不超过最短路径两倍"就自动成立 —— 用一点点"没那么平衡"，换回旋转次数大幅下降。

## 一句话是什么

**红黑树 = BST + 每个节点一个颜色位 + 五条永远不许破的规则。**

五条性质（先背下来，后面逐条解释它们各自"管什么"）：

```
性质 1  每个节点不是红的就是黑的，没有第三种颜色。
性质 2  根节点必须是黑的。
性质 3  所有"叶子"（空位）都是黑的 —— 本实现里它们不是 NULL，而是同一个共享哨兵 t->nil。
性质 4  红节点的两个孩子必须都是黑的 ⇔ 不许有两个红节点父子相连。
性质 5  从任意节点出发走到它所有后代叶子，路上数到的黑节点个数相同。
```

真正在"保证平衡"的只有 **性质 4 + 性质 5**，其余三条是为了让这两条能干净地成立。
推导只有三行，但它是整章的枢纽：

```
① 由性质 5：同一个节点的所有叶子路径黑节点数相同，记这个数为 bh（黑色高度）。
② 由性质 4：红节点不能相连 ⇒ 一条路上最短可能是"全黑"（长度 = bh），
   最长只能"黑红黑红"交错（长度 <= 2·bh）。
   ⇒ 最长路径 <= 2 × 最短路径          ← 红黑树的"平衡"就是这个意思
③ 最短路径至少 bh 个黑 ⇒ n >= 2^bh - 1 ⇒ bh <= log2(n+1)
   树高 h <= 2·bh <= 2·log2(n+1)       ← 于是查找/插入/删除都是 O(log n)
```

对照 AVL：AVL 要求 `|左高 - 右高| <= 1`（严格平衡，树高 `1.44·log2(n+2)`）；
红黑只要求"不超过两倍"（大致平衡，树高 `2·log2(n+1)`）。
**红黑树故意接受"没那么平衡"**，因为它要买的东西是：**修复时旋转次数少**。

同一批数据（顺序插入 1..7）三种树的形状：

```
  裸 BST          AVL                红黑树（本实现第 4 幕实测）
  1               4                   2[B]
   └─R 2         ┌┴┐                ┌──┴──┐
      └─R 3     2   6              1[B]   4[R]
         └─R 4  ┌┴┐ ┌┐             ┌┴┐   ┌┴┐
            └─R 5 1 3 5 7          3   6  ...
               └─R 6
                  └─R 7            7 个节点，高 4 层
  高 7（链）      高 3               上限 2·log2(7+1) = 6，只用 4 层
```

## 为什么需要它（AVL 已经把平衡解决了，还要红黑干嘛）

AVL 用严格平衡换来最矮的树，代价写在删除上：

| | AVL | 红黑树 |
|---|---|---|
| 一次**插入**最多旋转 | 2 次 | **2 次** |
| 一次**删除**最多旋转 | **O(log n) 次** | **3 次** |
| 修复的手段 | 只能靠旋转（旋转要改指针、改 parent） | **大量靠变色**（改 1 个字节），旋转只在必要时 |
| 树高（查找代价） | **更矮** | 稍高，最多 2·log2(n+1) |

红黑树的核心技巧是"**把冲突往上推**"：插入时叔叔是红的，就只是三个节点变色，
黑高一个字没动，然后把"红红相连"这个问题搬到爷爷那一层继续处理 —— 零旋转。
AVL 没有这种"变色上移"的余地，因为它盯的是高度，高度只能靠旋转压。
所以：**读多写少 → AVL；写多（尤其删除多）→ 红黑。**
`std::map` / `std::set`（libstdc++）、Java `TreeMap` / `TreeSet`、Linux 内核 `rb_tree`（调度器 CFS、`epoll`、
模块地址映射）用的都是红黑树，就是这个取舍的结果。

本目录把这个取舍做成可验证的实验：第 2 幕**故意只旋转不变色**，让校验器当场报"性质 5 被破坏"；
第 3 幕把插入修复三种情况连同左右镜像各演一遍；第 6 幕把删除的四段账（红/黑叶/双孩子/不存在）拆开；
第 7 幕随机增删 **300 次、每一步都跑一遍五条性质校验**，实测 **0 次破环**。

## 内存布局图解

### 1. 节点：比 AVL 多了 `parent` 和 `color`，但没有 `height`

```
   ┌────────┬───────┬──────────┬────────┬────────┐
p ─▶│ value  │ color │ parent   │ left   │ right  │
   └────────┴───────┴────┬─────┴───┬────┴───┬────┘
                         │         │        │
                    回指爸爸    左孩子   右孩子
                    ↑ 删除/修复要往上走，必须有它；AVL 不需要（AVL 是自顶向下递归的）
                                      （没有孩子时指向 nil 哨兵，绝不是裸 NULL）
```

```c
typedef struct RBNode {
    int            value;
    RBColor        color;    /* RB_RED = 0 / RB_BLACK = 1，故意不靠 0/1 猜，判黑写 == RB_BLACK */
    struct RBNode *parent;
    struct RBNode *left;
    struct RBNode *right;
} RBNode;
```

**注意没有 `height`** —— 红黑树不测高度，测的是"黑高"，而黑高只在打印和校验时现算（`rb_subtree_bh`）。

### 2. 树本体：`root` + 那个唯一的哨兵

```c
typedef struct RBTree {
    RBNode *root;    /* 真正的根（永远黑）。空树时它 == nil，而不是 NULL */
    RBNode *nil;     /* 全世界只有一个的"空叶子"哨兵：黑色，所有空位都指它 */
    int     verbose; /* 1 = 把修复每一步打印出来 */
} RBTree;
```

内存里 40/20/60 三个节点是这样连的（第 1 幕真实输出的地址关系，地址每次运行会变）：

```
   t.root ──► ┌────────────────────────┐
              │ 40 │ B │ nil │ 20 │ 60 │
              └──┬─────────┬───────┬───┘
                20         60      ↑
                 │          │      └── parent 指向哨兵（不是 NULL）
                 ▼          ▼
   ┌────────────────────┐ ┌────────────────────┐
   │ 20 │ R │ 40 │ nil │ │ 60 │ R │ 40 │ nil │ │   ← 20 和 60 的四条腿
   │      左/右都 = nil  │ │      左/右都 = nil  │ │      全部指向【同一个】地址
   └────────────────────┘ └────────────────────┘
                    ▲ ▲
                    │ └────────┘
   t.nil  ──────────┘  ┌──────────────────────┐
                       │ 0  │ B │ ? │ ? │ ?  │  ← 唯一的哨兵，天生黑色
                       └──────────────────────┘    它的 value/parent/left/right
                                                    三个字段【故意】留空，谁也不许读
```

### 3. 为什么要共享哨兵，而不是到处判 NULL

不用哨兵时代码长这样：

```c
if (z->parent != NULL && z->parent->color == RB_RED) { ... }
if (uncle == NULL) { /* 视为黑 */ } else { if (uncle->color == RB_RED) ... }
```

有哨兵时，"空孩子"是一个**真实的黑节点**，于是：

```c
if (u->color == RB_RED) { ... }     /* u 是哨兵也照样能读，读出来就是"黑" —— 正好等于
                                        "NULL 视为黑"这条约定，性质 3 由这一个节点天然保证 */
```

三个好处：
1. **判空少一半**：每个颜色判断少一个 `if`，少一个 `if` 就少一个漏写分支的 bug。
2. **性质 3 由结构保证**：所有空位都是同一个黑节点，不需要每次"把 NULL 当黑"。
3. **删除的双黑冒泡有了边界**：`x = x->parent` 往上走时，`x` 可以是哨兵而不用特判；
   循环条件 `x != t->root` 也永远可读。

代价：哨兵是"全树共享的一个堆节点"，销毁时必须**最后只 free 一次**（`rbtree_destroy` 就是这么写的）。

## 核心操作逐个拆解

`rbtree.c` 分 9 组，按"先静后动"排：

| 组 | 内容 |
|---|---|
| 第 1 组 | 内部小工具：`rb_transplant` / `rb_minimum` / `rb_destroy_rec` |
| 第 2 组 | `rbtree_init` / `rbtree_destroy` / `rbtree_set_verbose` |
| 第 3 组 | `rbtree_rotate_left` / `rbtree_rotate_right` |
| 第 4 组 | `rbtree_insert` + 插入修复（情况 1/2/3 + 镜像） |
| 第 5 组 | `rbtree_remove` + `rb_delete_fixup`（双黑 CASE 1~4 + 镜像） |
| 第 6 组 | `rbtree_search` / `rbtree_print_inorder` |
| 第 7 组 | `rbtree_print_tree`（颜色 + 黑高） |
| 第 8 组 | **`rbtree_check` / `rbtree_check_quiet`**：五条性质全验 |
| 第 9 组 | `rbtree_count` / `rbtree_height` / `rb_color_name_of` |

### 1. `rbtree_init` / `rbtree_destroy`

```c
void rbtree_init(RBTree *t);      /* malloc 出哨兵 → 染黑 → t->root = t->nil = 哨兵 */
void rbtree_destroy(RBTree *t);   /* 后序 free 所有真实节点 → 最后 free 唯一的哨兵 → 两个指针置 NULL */
```

空树的判断从 `root == NULL` 变成 `t->root == t->nil`，一旦接受这个设定，
"这棵树空不空"就只有一种写法，而且任何节点读孩子颜色时永远不会解引用 NULL。

### 2. 左旋 / 右旋：6 个指针，一个颜色都不动

```
   左旋 x：右孩子 y 上位                     右旋 y：左孩子 x 上位（镜像）
        x                                            y
       / \        左旋 x                    →        / \     右旋 y    →
      A   y                                       x   C
         / \                                     / \
        B   C                                   A   B
```

```c
void rbtree_rotate_left(RBTree *t, RBNode *x);
void rbtree_rotate_right(RBTree *t, RBNode *y);
```

和 AVL 旋转的两点差别：

| | AVL 旋转 | 红黑旋转 |
|---|---|---|
| 要不要更新高度 | 要（先下后上 `avl_update_height`） | **不要**（没存高度） |
| 要不要维护 parent | 不要（没有 parent 字段） | **要**，一共 6 个指针 |
| 怎么交回新根 | 返回新根，调用者 `root = ...` | **不返回**：`t->root` 或 `parent->left/right` 当场改掉 |

"6 个指针"漏哪个都会出事，尤其 `parent`：删除修复要 `x = x->parent` 往上冒泡，
`parent` 指错就走到别人家去了，而且性质 4/5 看起来还都是好的（只有 `rbtree_check` 的附加检查能抓到）。

**★ 第 2 幕的重要实验：旋转本身不保平衡。**
对一棵合法红黑树的根做一次纯左旋（只搬指针、不改颜色），校验器立刻报：

```
✗ 性质5被破坏：节点 10[B] 的左子树黑高 1，右子树黑高 0，不相等
✗ 性质5被破坏：节点 20[B] 的左子树黑高 2，右子树黑高 0，不相等
```

旋转只搬形状，黑高靠配套的**变色**。所以第 3 幕里每一次旋转都紧跟一句"谁染黑谁染红"，两者成对出现。

### 3. 插入 = BST 插入 + `rb_insert_fixup`

**阶段 A：完全按 BST 找位置**（迭代，不用递归 —— 因为有 `parent` 可以往上走），
走到哨兵就是找到空位；`value` 已存在则**忽略**（本教学版本不收重复值）。
新节点一律：`color = RB_RED`，两条腿 = `t->nil`，`parent` = 找位置时的最后一个真节点。

**为什么新节点必须染红？** 两条路对比一下就知道：

```
插成【黑】 → 经过它的每条路径黑数 +1 → 性质 5 立刻破。
            性质 5 是"全局"约束（牵涉到它下面所有叶子），基本只能大动干戈。
插成【红】 → 黑高一点没动，性质 5 完好；最坏只是和红的爸爸"红红相连"（性质 4）。
            性质 4 是【局部】约束（只看父子两代），改 2~3 个颜色 + 最多 2 次旋转就能修好。
```

一句话：**把破坏限制在最小范围**，这是红黑树所有设计选择的出发点。

**阶段 B：修复（循环条件 `while (z->parent->color == RB_RED)`）**

设 `p` = 爸爸，`g` = 爷爷，`u` = 叔叔。爸爸红 ⇒ 根必黑 ⇒ 爷爷一定存在，可以放心读 `g`。

```
情况 1：叔叔是红的 → 只变色，零旋转
   爸 p 染黑、叔 u 染黑、爷 g 染红；z = g，冲突【上移一层】继续循环。
   （黑高没变：这条路上原来有 1 个黑，现在还是 1 个黑 —— 只是把问题搬到爷爷身上）

情况 2：叔叔黑 + 我在【内侧】（爸左我右 / 爸右我左）→ 先把形状掰成外侧
   z = p; 对爸爸旋转一次（这一步【不动颜色】）；重新取 p / g，紧接情况 3。

情况 3：叔叔黑 + 我在【外侧】（爸左我也左 / 爸右我也右）→ 变色 + 旋转，当场终结
   爸 p 染黑、爷 g 染红、对爷爷旋转一次（外侧方向决定左旋还是右旋）。
   红红相连消除，且这条路黑数不变 ⇒ 祖先不用再动，循环必然退出。
```

情况 1/2/3 在"爸是左孩子"和"爸是右孩子"两种情形下完全镜像，代码写了两套（`情况2·镜像` 等），
逻辑一一对应。**每个情况都必须有镜像**，这是红黑树最难背但对齐最整齐的部分。

循环外最后一行：`t->root->color = RB_BLACK;` —— 强制根黑（性质 2）。
为什么染黑根不破坏性质 5？根是所有路径的公共起点，它变黑等于**每条路径同时 +1 个黑**，相等关系仍然成立。

旋转次数：插入全程**最多 2 次**（只走情况 3 ⇒ 1 次；走情况 2+3 ⇒ 2 次；纯情况 1 ⇒ 0 次）。
变色次数却可能到 `O(log n)`（情况 1 一路往上推）。

### 4. 删除 = BST 三种情况 + 双黑修复

骨架三步：

```
第一步：按 BST 规矩决定"真正腾出原位置的是哪个节点" y
        - z 没有左孩子 → 右腿（可能是哨兵）顶上来
        - z 没有右孩子 → 左腿顶上来
        - 两条腿都有   → 摘后继 y（右子树最小），把 y 整个搬到 z 的位置，并【继承 z 的颜色】
                         后继一定没有左腿 ⇒ 搬动绝对安全
第二步：记账 —— 记住 y【离开前】的颜色 y_color_before。
        红色离场：每条路黑数没动 ⇒ 直接结束（很多删除就是这么便宜）。
        黑色离场：经过它的那条路少了一个黑 ⇒ 进入第三步。
第三步：把这笔亏空记在顶替者 x 头上，叫【双重黑】，交给 rb_delete_fixup 去"借黑"。
```

`y->color = z->color` 这一行很关键：**换人站岗不换颜色**，那个位置的黑数才不会因为"换了个人"而变。
（第 6 幕 (c) 现场：删双孩子根 50（黑），后继 55（红）顶上来并染成黑；
记账的是 55 原来站的位置 —— 那里原来是红的，所以不用修复。）

**双重黑（double black）是什么**：不是一个"黑黑"的节点，而是一种**记账状态**：
"这条路径还欠一个黑"。它必须被注销才能回到合法红黑树。注销的手段是让**兄弟那棵子树借一个黑过来**。

设 `x` = 背着亏空的那个（左孩子情形），`w` = `x` 的兄弟：

```
CASE 1  兄弟 w 是【红】
        → w 染黑、爸爸染红、对爸爸【左旋】。
          目的只有一个：给自己换一个【黑】兄弟，好继续往下走 CASE 2/3/4。
          （红兄弟不可能带黑侄子以外的结构，所以转完必然落到下面三种之一）

CASE 2  兄弟黑 + 兄弟的两个孩子都黑
        → 没处借黑：把兄弟染红。它那边各条路黑数 -1，跟 x 这边一样浅了；
          亏空【推给爸爸】，x = x->parent 继续冒泡。
          （这就是删除最坏要走 O(log n) 层的原因，和插入的情况 1 是同一个套路）

CASE 3  兄弟黑 + 远侄子黑（近侄子红）
        → 近侄子染黑、兄弟染红、对兄弟【右旋】⇒ 掰成 CASE 4。只掰形状，不结清账。

CASE 4  兄弟黑 + 远侄子红
        → 兄弟继承爸爸的颜色、爸爸染黑、远侄子染黑、对爸爸【左旋】。
          x 这边正好补回一个黑 ⇒ 账平了，x = root 直接退出循环。

退出循环后 x->color = RB_BLACK：注销双黑标记。
```

`x` 是右孩子时完全镜像（兄弟在左边、远侄子在左），代码同样写了两套。
**旋转次数：删除全程最多 3 次**（CASE 1 一次 + CASE 3 一次 + CASE 4 一次），
比 AVL 删除的最坏 O(log n) 次少得多，这就是红黑树"没那么平衡"买回来的东西。

一个能一眼看懂的捷径：**顶替者本来就是红的**，直接把它染黑就补上了这个黑，一步都不冒泡
（第 6 幕 (b) 就是这个情况，输出里能看到 `[双黑·当场销账]`）。

### 5. `rbtree_check`：本章最重要的教学设施

```c
int rbtree_check(const RBTree *t);        /* 通过时也打一份"体检报告" */
int rbtree_check_quiet(const RBTree *t);  /* 通过时一个字都不打，破了才打详情（压力测试用） */
```

返回 `0` = 全部成立；返回 `n` = 发现 `n` 处破坏，并把**破的是第几条、坏在哪个节点、当时颜色**打出来。
检查项：

```
性质 1  color 只能是 RB_RED / RB_BLACK（防写脏）
性质 2  根是黑的
性质 3  所有空位都指向【那一个】共享哨兵，且哨兵是黑的；树里不许出现裸 NULL 的腿
性质 4  红节点两个孩子必须都是黑的
性质 5  每个节点左右子树的黑色高度必须相等（递归返回 bh，左右不等就报）
附加    child->parent 必须指回父亲 —— 不属于五条性质，但带 parent 的实现最容易在这写错
        ⚠ 哨兵例外：它的 parent 字段是故意留空的，跳过不查
```

压力测试（第 7 幕）把它当单元测试用：**随机增删 300 次，每步都查**。
本项目实测：成功插入 176 / 成功删除 124 / **校验失败 0 次** / 全程最大树高 7（理论上限 `2·log2(53) = 12`）。

### 6. 打印格式：`42[B] bh=4`

```
42[B] bh=4
   ├─L 26[B] bh=3
   │  ├─L 16[R] bh=2
```

- `[R]` / `[B]` = 红 / 黑（固定宽度，排版整齐）；
- `bh` = 该子树的黑色高度（从该节点往下走到哨兵路上数到的黑节点数，**不含哨兵本身**）；
- **读图自检法**：同一个节点的左右孩子标的 `bh` 应当相等 —— 那就是性质 5。

## AVL vs 红黑：三分钟决策指南

**先把两者的"平衡哲学"摆在一起**

```
AVL ：我保证每个节点左右高度差 <= 1        → 树很矮（1.44·log2(n+2)），但一失衡就必须旋转
红黑：我保证每条路黑数相同 + 红不相邻      → 树稍高（2·log2(n+1)），但很多失衡靠【变色】就能推走
```

**决策表**

| 你的场景 | 选谁 | 为什么 |
|---|---|---|
| 查询远多于增删，且要最坏保证（内存里的只读字典、符号表、路由表） | **AVL** | 树更矮 ⇒ 每次查找少比较几层；写少，O(log n) 次旋转的痛用不到 |
| 增删频繁、写入型负载（LRU、任务队列、时间轮、实时插入的排行榜） | **红黑** | 插入 ≤2 次、**删除 ≤3 次**旋转；AVL 删除最坏 O(log n) 次 |
| 实现"有序 map/set"这类标准库容器 | **红黑** | libstdc++ 的 `map`、Java `TreeMap` 都是它，生态与经验都在这一边 |
| 数据要落硬盘、一页能装几十个键 | **都不选，上 B 树/B+ 树** | 指针树一次 I/O 只读一个节点太亏（见 `05-tree/b-tree/`） |
| 纯按 key 取值、完全不在乎顺序 | **都不选，上哈希表** | 平均 O(1)，代码还简单一个数量级 |
| 只关心最大/最小（Top-K、优先队列） | **都不选，上堆** | 数组存储、零指针开销（见 `06-heap/`） |
| 不敢手写旋转、能接受随机化 | **都不选，上跳表** | `02-linked-list/skip-list/`，期望 O(log n)，代码量小很多 |
| 内存极敏感、节点数以千万计 | **红黑略优** | 颜色 1 bit 可塞进指针低位；AVL 要一个 `int height` |
| 递归栈深必须可控 | 都行 | 两者树深都是 O(log n)，裸 BST 才有栈溢出风险 |

**一句话记忆**：**读多写少用 AVL，写多读少用红黑；要落盘用 B 树，不要顺序用哈希。**

**本项目里的实测对照**（都是运行结果原话）

```
AVL ：32 个顺序数据 → 高 6；理论上限 1.44·log2(34) ≈ 7.7
红黑：52 个节点      → 高 7；理论上限 2·log2(53) = 12
红黑第 7 幕：300 次随机增删，每步校验，破环 0 次
```

## 复杂度表

| 操作 | 平均 | 最坏 | 备注 |
|---|---|---|---|
| 查找 `rbtree_search` | O(log n) | **O(log n)** | 树高 <= 2·log2(n+1) |
| 插入 `rbtree_insert` | O(log n) | O(log n) | 查找位 O(log n) + 修复：**变色可 O(log n)，旋转 <= 2 次** |
| 删除 `rbtree_remove` | O(log n) | O(log n) | 修复：冒泡 O(log n) 层，但**旋转 <= 3 次** |
| 求最小/最大 | O(log n) | O(log n) | `rb_minimum` 一路向左 |
| 中序遍历 | O(n) | O(n) | 颜色不影响顺序 |
| `rbtree_count` / `rbtree_height` | O(n) | O(n) | 全树扫（没存 size/height，教学版直说） |
| `rbtree_check` | O(n) | O(n) | 五条性质 + parent 互指全查 |
| 空间 | O(n) | O(n) | 每节点比 AVL 少 `int height`、多 `parent` + `color` |
| 递归深度（遍历/校验/销毁） | O(log n) | O(log n) | 增删本身是**迭代**的，不吃栈 |

> 想要 O(1) 拿到"第 k 小"或"节点总数"，得在节点里再存 size（顺序统计树），本教学版没做。

## 常见的坑

1. **只旋转、不变色**
   形状转对了，性质 5 立刻破（黑高左 2 右 0）。本目录第 2 幕就是专门演示这个死法。
   记忆点：**旋转管形状，变色管黑高，两者成对出现。**

2. **6 个 parent 指针漏写一个**
   `rotate` 时忘了 `y->parent = x->parent`，或者 `x->parent->left/right` 没改到 `y`。
   五条性质可能全看不出来（它们不查 parent！），只有往上走的那段代码（删除、修复）会走到别的子树里。
   所以 `rbtree_check` 额外加了"父子互相指认"这一项，专抓这个。

3. **旋转后没有重取兄弟 `w`**
   CASE 1 / CASE 3 之后必须 `w = x->parent->right;`（镜像则取 `left`）。
   兄弟换人了还攥着老地址，接下来 `w->left->color` 读的是完全无关的子树。

4. **忘记性质 3 的约定："NULL 视为黑"必须真的用哨兵兑现**
   代码里任何地方出现 `if (x == NULL)`，就说明你的哨兵铺漏了。
   新节点两条腿必须显式写成 `z->left = z->right = t->nil;`，否则 `rbtree_check` 报
   "节点 X 有一条腿是裸 NULL"。

5. **新节点染成黑色**
   看着"更稳妥"，其实把破坏从局部的性质 4 升级到全局的性质 5，修复难度陡增。
   一律染红，别自作主张。

6. **删除时记账记错对象**
   双孩子情况里，`free` 掉的是 `z`，但**颜色账记在"腾出原位置的那个节点"头上**（`y_color_before`）——
   也就是后继原来的颜色。而 `y` 站到新位置后继承的是 `z` 的颜色。
   混了这两件事，就会出现"该修复的没修复"或"不该修复的乱修复"。
   （第 6 幕 (c) 专门把这条打印出来：55 顶到 50 的位置、继承黑色；记账的是 55 原本是红色 ⇒ 不用修。）

7. **`y->parent == z` 的特判漏掉**
   后继恰好就是 `z` 的右孩子时，不能直接 `rb_transplant(t, y, x)` —— 那样 `y` 会被搬两次、指针全乱。
   只需保证 `x->parent = y`。这是删除里最隐蔽的一个分支。

8. **哨兵被 free 多次 / 或者被当成真节点遍历**
   哨兵全树只有一个，`rb_destroy_rec` 遇到 `t->nil` 必须立刻 `return`，
   最后由 `rbtree_destroy` 单独 free 一次。遍历/打印同理：`node == t->nil` 就是递归终点，
   别打印它的 value（它是 0，会在输出里冒出一个莫名其妙的 0）。

9. **`while (z->parent->color == RB_RED)` 之外忘了收尾**
   循环结束后必须 `t->root->color = RB_BLACK;`，否则情况 1 一路推到根时会留下红根（违反性质 2）。

10. **以为"红黑树是最平衡的二叉树"**
    它不是，AVL 才更矮。红黑树只保证"最长 <= 2 × 最短"。
    拿红黑树当"高度最优"用（比如每层都要一次 I/O 的场景）是选型错误。

1. **五条性质里，哪几条是真的在"保证 O(log n)"？其余的呢？**
   **答：** 真正干活的是**性质 4 + 性质 5**：红不相邻 + 每条路黑数相同 ⇒ 最长 ≤ 2×最短 ⇒
   `h ≤ 2·log2(n+1)`。性质 1 只是定义颜色域，性质 2（根黑）和性质 3（空位是黑）
   是为了让 4、5 在边界上成立并且让代码少判空。

2. **为什么新节点一律染红？插成黑色会怎样？**
   **答：** 插成黑 ⇒ 经过它的每条路径黑数 +1 ⇒ 全局性质 5 立刻破，几乎只能大动干戈。
   插成红 ⇒ 黑数不动，最坏只是和红的爸爸相连（性质 4，只看父子两代的局部问题），
   改 2~3 个颜色 + 最多 2 次旋转就能修。核心思想：把破坏限制在最小范围。

3. **情况 1（叔叔红）只变色不旋转，为什么黑高没变？**
   **答：** 变色的三个是"爸黑、叔黑、爷红"。看任意一条穿过这片的路：
   原来经过爸（黑）和爷（黑）= 2 个黑；现在爸还是黑、爷变红，但爸上面多算的爸的爸爸是黑 ⇒
   同一条路上黑数守恒。性质 5 不受影响，所以只是把"红红相连"这个性质 4 的问题推到爷爷那一层。

4. **情况 2 为什么必须紧跟情况 3？只做情况 2 会怎样？**
   **答：** 情况 2 在**内侧**（爸左我右）：直接对爷爷旋转会把"我"旋到错误的一侧，形状不合法。
   所以先对爸爸转一次，把"我"挪到外侧（这一步不动颜色），此时"我"成了新的外侧孙子，
   就正好是情况 3 的适用形状。情况 2 本身不结清账，它只是"掰直"。

5. **`rbtree_check` 能查出"parent 写歪"吗？五条性质里有没有管 parent 的？**
   **答：** 五条性质**完全不管 parent**（它们只看颜色和黑高），所以 parent 写歪时性质可以全过。
   本实现的校验器额外加了一项"孩子必须认父亲"（哨兵例外，它的 parent 字段故意留空不查），
   这是唯一能自动抓出该问题的地方。

6. **删除时"双黑"是个真节点吗？它怎么被注销？**
   **答：** 不是节点，是**记账状态**："这条路径还欠一个黑"。亏空挂在顶替者 `x` 头上（`x` 常常就是哨兵）。
   注销方式：让兄弟那棵子树借一个黑过来 —— CASE 2 兄弟染红（亏空上移，把账推给爸爸），
   CASE 4 兄弟继承爸爸颜色 + 爸爸染黑 + 远侄子染黑 + 旋转（一次结清）。
   退出循环后统一 `x->color = RB_BLACK` 销账。

7. **捷径：什么时候删除一步都不用冒泡？**
   **答：** 顶替者本来就是**红**的。把它染黑，那条路径正好补回一个黑（第 6 幕 (b)：
   删黑的 10，顶上来的是红的 15 ⇒ `[双黑·当场销账]`）。
   另一个常见捷径是"离场的是红节点"（性质 5 根本没动，连 fixup 都不进）。

8. **红黑树比 AVL 慢在哪、快在哪？给出各自的最坏旋转次数。**
   **答：** 慢在查找：树更高（`2·log2(n+1)` vs `1.44·log2(n+2)`），多走几层、多几次比较。
   快在写入：插入两者都 ≤2 次旋转，但**删除 AVL 最坏 O(log n) 次，红黑 ≤3 次**
   （CASE 1 + CASE 3 + CASE 4 各一次）。红黑靠"变色上移"把很多失衡在颜色层面就化解了。

9. **为什么本实现的插入/删除是迭代的，而 AVL 那边是递归的？**
   **答：** 因为有 `parent` 指针。红黑树可以"先 BST 挂上去，再顺着 parent 往上修"，
   不需要递归的回溯栈。AVL 没有 parent，只能靠递归返回时那一路做"更新高度 + rebalance"。
   附带好处：增删不吃栈空间（AVL 是 O(log n) 栈，退化树才有栈溢出风险）。

10. **`2·log2(n+1)` 这个上界在 n = 52 时是多少？实测多少？**
    **答：** `2·log2(53) ≈ 2·5.73 = 11.46`，取整上界 12 层；第 7 幕压力测试全程最大树高只有 **7**。
    说明这个界是"最坏情况护栏"而不是实际形状 —— 红黑树通常比上界矮得多，
    但**再矮也不可能低于 AVL 的界**，这就是两种哲学的分工。
