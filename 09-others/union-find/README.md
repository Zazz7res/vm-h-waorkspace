# 并查集 union-find

> 两个 `int` 数组，就能把"谁和谁是一伙的"这类问题从 O(n) 降到近乎 O(1)。

---

## 一句话是什么

并查集是一种**只用来管"分组"这件事**的结构：它把每个集合存成**一棵树**，用**树根的下标**当这个集合的编号。

于是两个操作变得极快：

- `find(x)`：从 x 沿 `parent[]` 往上爬，爬到根 —— 根就是 x 所属集合的名字。
- `union(a, b)`：把 a 那棵树的根和 b 那棵树的根连起来，两个集合就合成一个了。

判断 a、b 是不是同一伙的，只需要比一下"它们的根相等吗"。

---

## 为什么需要它

**痛点场景**：一张图上不断加边，中途不停地问"点 u 和点 v 现在连通吗"。

| 做法 | 每次问连通要干什么 | 10000 次询问的代价 |
|---|---|---|
| 不用并查集：每次现跑 BFS/DFS | 从 u 出发遍历整块连通区域 | O(n + m) 一次 ⇒ 上亿次操作 |
| 提前跑一遍连通分量 | 但边还在加，答案随时会变，预处理好作废 | 加一条边就要全图重算 |
| 用并查集 | 两个点各爬几步到根，比一下 | 实际就当 O(1) ⇒ 微秒级 |

**再举个生活化的例子**：微信群里"你和谁是好友的好友链"。你想知道你和小明算不算"认识"（有共同好友链），
朴素办法是把整条朋友圈关系图搜一遍；并查集只要提前把每段好友关系 union 好，之后每次问都是常数。

还有一类题只有并查集能干：**边一条条进来，要立刻知道"加上这条会不会出现环"**（第 8 幕演示），
或者 **Kruskal 最小生成树里"选这条边会不会成环"** —— 判断依据都是 `union` 返回 0。

## 内存布局图解

整个结构就两块连续内存，没有链表、没有节点 malloc：

```
   UF
  ┌────────────┬────────────────────────────────────┐
  │ parent ────┼──→ ┌────┬────┬────┬────┬────┬────┐ │
  ├────────────┤    │  0 │  0 │  0 │  2 │  4 │  4 │ │  ← 每个格子存"我爹的下标"
  │ rank ──────┼──→ │  2 │  0 │  1 │  0 │  1 │  0 │ │  ← 只有格子的下标是根时，它的 rank 才有意义
  ├────────────┤    └────┴────┴────┴────┴────┴────┘ │
  │ n = 6      │                                     │
  │ components │                                     │
  └────────────┴────────────────────────────────────┘

  对应的森林（把 parent 反过来看就是树）：

        0                4               5
       /|\                \
      1 2 3               ...
          \
           ...
```

把 `parent[] = [0, 0, 0, 2, 4, 4]` 翻译成人话：

```
  下标 0：parent[0]=0  ⇒ 0 就是根，它这个集合叫"0 集合"，成员 {0,1,2,3}
  下标 1：parent[1]=0  ⇒ 1 的爹是 0
  下标 2：parent[2]=0  ⇒ 2 的爹是 0
  下标 3：parent[3]=2  ⇒ 3 的爹是 2，2 的爹是 0 ⇒ 3 也属于"0 集合"
  下标 4：parent[4]=4  ⇒ 4 是另一棵树的根
  下标 5：parent[5]=4  ⇒ 5 属于"4 集合"
```

**关键认知**：`parent[i]` 里存的永远只是"父亲"，不是集合编号。集合编号 = 爬到顶那个点的下标。
所以根会因为合并而改变，任何时候要判断都得现爬一次，不能把根记死。

`find(3)` 走的路径：`3 → 2 → 0`，撞到 `parent[0]==0`，返回根 0。

## 核心操作逐个拆解

### 1. `uf_init(uf, n)` —— 初始化成"最碎"状态

**干什么**：造 n 个各自独立的集合。

**一步步怎么做**：
1. `calloc` 两条 int 数组（calloc 自带清零，省一个循环也少一个坑）。
2. `parent[i] = i` —— 每个人都把自己当爹，于是 n 个点就是 n 棵树。
3. `rank[i] = 0` —— 孤点高度记 0。
4. `components = n` —— 集合数记账。
5. 任何一块申请失败，另一块**必须立刻 free**，然后返回 -1。

**边界情况**：`n <= 0`、`n > UF_MAX_N`、`uf` 传 NULL 都会打印错误并返回 -1，不会写坏内存。

**对应代码**：`uf.c` 的 `uf_init()`。

### 2. `uf_find_naive(uf, x, path_out, path_cap, path_len_out)` —— 朴素 find（不压缩）

**干什么**：老老实实往上爬，同时把爬过的整条路径抄进 `path_out`，只为教学演示"路径长什么样"。

**一步步怎么做**：
1. 把起点 x 抄进路径数组。
2. `while (parent[cur] != cur) { cur = parent[cur]; hops++; }` —— 一句话：**不是我爹是我自己的时候就继续往上**。
3. 循环结束时 `cur` 就是根。
4. `hops` 存到 `uf->walks`，让外面能读到"这次爬了几条边"。

**边界情况**：
- x 本身就是根：循环一次都不进，路径只有 `[x]`，走 0 条边。
- `path_out` 传 NULL：只要根不要路径，照样能跑。
- 路径比数组长：只抄前 `path_cap` 个，绝不越界写。
- ⚠ 如果 `union` 写错，把**非根节点**挂成了别人的爹，就可能形成"爬不到顶"的环 ⇒ 这个 while 死循环。
  本文件的 union 只改根的 parent，所以不会出现。

**对应代码**：`uf.c` 的 `uf_find_naive()`。

### 3. `uf_find(uf, x)` —— 带**路径压缩**的 find（正式代码用它）

**干什么**：找到根的同时，把这一路爬过的点**全部直接挂到根上**。

**一步步怎么做（递归版）**：
```
      压缩前                        递归回程逐个改写                压缩后
        0                                                       0
        ├─ 1                                                    ├─ 1 ─┐
        │    └─ 3                                                ├─ 3 ─┤  ← 全挂到 0
        │         └─ 7                                           └─ 7
        └─ 2                                                     └─ 2
   find(7)：下去时走 7→3→1→0；回来时依次执行 parent[3]=0、parent[1]=0（7 自己也是）
```
1. `if (parent[x] == x) return x;` —— 我是根，递归到底。
2. 否则让爹去爬，拿到根。
3. `parent[x] = root;` —— ★就这一行：把我自己直接挂到根上。
4. 返回根。

**为什么改写树是合法的**：`parent` 只是"快速找根"的辅助工具，只要改完之后**所有点还能爬到同一个根**，
"谁和谁同集合"这个事实就没变。压缩只是把工具摆顺，不动语义。

**边界情况**：递归深度 = 树高。本演示 n ≤ 12 绝对安全；真实工程 n=1e6 时建议写成
"先爬到根、再倒序回写"的迭代版，避免爆栈（这里为了代码最短用了递归版，已在注释里说明）。

**对应代码**：`uf.c` 的 `find_compress()`（static 内部函数）+ `uf_find()`（入口，负责把 walks 清零/写回）。

### 4. `uf_union(uf, a, b)` —— **按秩合并**

**干什么**：把两个集合合成一个，并且**让矮树挂到高树下面**，这样树就长不高。

**一步步怎么做**：
1. 各爬到根 `ra`、`rb`（顺手压缩）。
2. `ra == rb` ⇒ 本来就是一家人，**返回 0，什么都不改**（这个返回值是判环的关键，见第 8 幕）。
3. 谁 rank 小谁当儿子：代码里统一把 `ra` 换成较高的那个，然后 `parent[rb] = ra`。
4. **只有两个 rank 相等时**才 `rank[ra]++`：
   - 矮挂高 ⇒ 高树高度没变，rank 不动
   - 等高相挂 ⇒ 新树高度 +1，必须记上，否则以后判断会低估
5. `components--`，返回 1。

**为什么按秩合并能保证树矮**：某棵树的 rank 每涨 1，就必须撞上一棵一样高的树；
"凑齐两棵高 h 的树"至少要有 `2^h` 个元素 ⇒ `h ≤ log2(n)`。n=1e6 时树高最多 20。

**边界情况**：下标越界返回 -1；a==b 时 `ra==rb`，走"返回 0"分支（自环也算成环）。

**对应代码**：`uf.c` 的 `uf_union()`。

### 5. `uf_union_naive(uf, a, b)` —— 故意不优化（反面教材）

无条件 `parent[ra] = rb`，不看高度也不压缩。按 (0,1)(1,2)(2,3)… 的顺序做，就会得到一根**晾衣杆**：

```
  0 → 1 → 2 → 3 → 4 → 5 → 6 → 7        find(0) 要爬 7 条边
```

复杂度退回 O(n)。留着它是为了让第 6 幕的对比有说服力。

### 6. `uf_connected` / `uf_component_count`

- `uf_connected(a,b)`：`uf_find(a) == uf_find(b)`。这就是并查集 90% 的实际用法。
- `uf_component_count()`：直接读 `components`，O(1)。因为每次真的合并都 `-1` 记着账。

### 7. 打印三件套

- `uf_print_parent_array(uf, tag)`：把 `parent`、`rank` 整排打出来，附带集合数和"根分别是谁"。
  **本节 demo 每次 union/find 之后都会调它**，森林的每一点变化都在你眼皮底下。
- `uf_print_forest(uf)`：从每个根出发递归缩进打印，把树形画出来。
- `uf_tree_height(uf, root)`：递归算真实树高，用来量化"优化前 7 层 / 优化后 1 层"。

> 注意 `uf_print_forest` 和 `uf_tree_height` 都在**全表扫描找儿子**。
> 因为 `parent[]` 只有"往上的指针"，没有"往下的指针"，这是并查集的一个真实短板：
> 它不能高效地"列出某个集合的所有成员"（要列就得 O(n) 全扫，或者自己再挂一条链表）。

### 8. 两个优化合起来的复杂度

- 只用按秩：`find` 最坏 O(log n)
- 只用路径压缩：均摊也很好，但单次最坏仍可能 O(log n) 级别
- **两个都用：n 次操作总代价 O(n·α(n))**，α 是反阿克曼函数。

**不用去啃 α 的数学**，只需要记住：它增长慢到离谱 —— n 取"宇宙里所有原子的数量"（约 10^80），
α(n) 依然 ≤ 5。所以**工程上直接把它当常数用**，写文档、估复杂度的时候就写"近似 O(1)"。

## 复杂度表

| 操作 | 并查集（两个优化全上） | 并查集（不优化，退化成链） | 每次现跑 BFS/DFS | 位图/布尔数组标记 |
|---|---|---|---|---|
| `find` / 判连通 | **均摊 ≈ O(α(n))，实际当 O(1)** | O(n) 最坏 | O(n + m) | O(1)（但只能问"是不是同一组已知的"，边一变就全废） |
| `union` | **≈ O(1)** | O(n)（先要爬到根） | — | O(n)（要把一组的标记全改一遍） |
| 判图有无环 | O(m·α(n)) 扫一遍边即可 | O(m·n) | O(n + m)，但只能一次性问完 | 不适合 |
| 数连通分量 | O(m·α(n))，且能**边加边答** | O(m·n) | O(n + m)，加一条边就得重算 | — |
| 列出某集合全部成员 | O(n) 全表扫（本体不支持） | O(n) | O(n) | O(n) |
| 额外空间 | O(n)，两个 int 数组 | O(n) | O(n) 队列/栈 | O(n) |

**和同类的取舍**：
- 只加边、只问连通 ⇒ **并查集**（最短代码、最快答案）
- 边会**删掉**、还要最短路 ⇒ 并查集干不了，得用 BFS/DFS 或动态图算法
- 要"某个集合的成员列表" ⇒ 并查集本体不行，需要邻接表 + BFS

## 常见的坑

1. **`union` 里把非根节点挂上去**。写成 `parent[b] = ra`（b 而不是 `rb`）就把树搞出了环，
   之后 `find` 死循环或答案错乱。**规矩只有一条：只改"某个根"的 parent。**
2. **忘了等高才 `rank++`**。等高相挂时不加 1，下一次按秩判断就会挑错方向，树慢慢变高；
   反过来"每次合并都 +1"，rank 会虚高，虽然结果还是对的，但打印出来会让人误判树高。
3. **把根记死当常量**。`int my_root = uf_find(x);` 存下来，之后再 union，`my_root` 可能已经不再是根了。
   每次要用都得现爬，或者用 `parent[r] == r` 再验一次。
4. **忘了 `find` 有副作用**（它会把沿途节点直接挂到根上，还会重写 `uf->walks`）。
   所以"先 find 一遍再按原树形统计深度"这类代码，结果会被自己刚刚的压缩改掉 ——
   本节第 6 幕特意用**不压缩的 `uf_find_naive`** 去量树高，就是为了绕开这个坑。
5. **元素不是 0..n-1 的下标就直接拿去用**。并查集只认 int 下标；题目给 1..n 就要么开 n+1 的数组、
   要么全减去 1。下标越界在本实现里会被挡住并打印错误，但线上代码往往会直接段错误。
6. **以为路径压缩让单次真的 O(1)**。它是"均摊"近乎常数：第 4 幕那根晾衣杆，第一次 `find(0)` 花了 7 步，
   压缩完才变便宜。做复杂度分析时要说"均摊"。
7. **想用并查集做删除 / 求路径长度 / 列举成员**。它只支持"合并 + 找代表元"，
   要带权（比如"两点距离差"）得学扩展版"带权并查集"，要删除就得换结构。

## 什么时候用它 / 什么时候别用

**适合**：
- 动态加边、动态问连通（离线处理最小生成树 Kruskal、图片连通块、社交网络"是否同群"）
- 判无向图是否有环（本节第 8 幕）
- 数连通分量个数、把若干"等价关系"合并成组（如账户合并、朋友圈问题）
- 只关心"是不是同一伙"，不关心"这伙里都有谁"

**别用**：
- 边会被**删除**（并查集不支持拆开，只能整体重建或用"可撤销并查集"离线处理）
- 要**最短路径 / 具体路径 / 两点间距离**（那是 BFS/Dijkstra 的活）
- 要频繁**列出集合成员**或"取集合中最大值"这类（得自己在根上挂额外信息，或者直接上平衡树）
- 图很小、只问一次 ⇒ 直接 DFS 更省事，没必要建结构

## 自检问题

1. `parent[] = [1, 2, 2, 4, 4]`，请问 `find(0)` 返回什么？0 和 3 是同一集合吗？
   **答**：0→1→2，`parent[2]==2` 所以根是 2；3→4，`parent[4]==4` 根是 4。根不同 ⇒ 不是同一集合。
2. 为什么"路径压缩"改写树形不会破坏正确性？
   **答**：因为并查集唯一的语义是"所有同集合的点能爬到同一个根"。压缩只是把沿途节点的爹换成根，
   它们仍然爬到同一个根，等价关系没变。
3. 按秩合并时，为什么 `rank` 只在两棵树一样的高的时候才 +1？
   **答**：矮树挂到高树下面，高树的高度一点没变，rank 当然不动；
   两棵一样高的树对接，新树才会高出 1 层，必须记下来，否则下次判断方向会低估。
4. `uf_union(a, b)` 返回 0 意味着什么？举两个它能直接解决的问题。
   **答**：意味着 a、b 早就在同一集合（本次什么都没合并）。
   ①无向图加边时返回 0 ⇒ 这条边造成环；②Kruskal 里返回 0 ⇒ 这条边不能选（会成环）。
5. 为什么说"α(n) 可以直接当常数"？
   **答**：反阿克曼函数增长慢到离谱，n 取宇宙原子总数时 α(n) 才 5，实际数据规模里它 ≤ 4。
   所以工程和做题时都写"近似 O(1)"，不需要理解它的定义。
6. 并查集能回答"集合 0 里有哪些成员"吗？
   **答**：本体不能高效回答 —— `parent[]` 只有向上的指针。要列举就得 O(n) 全表扫（本 demo 第 9 幕就是这么打的），
   或者额外挂链表。
