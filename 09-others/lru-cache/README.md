# LRU 缓存 lru-cache

> 一句话是什么：**一个「装满了就扔最久没被用过的那个」的定长缓存**。
> 它是全仓库唯一**必须同时用两种结构**的章节 —— 哈希表 + 双向链表，一份数据、两个视图，为的是让 `get`
> 和 `put` 都稳定在 O(1)。（LeetCode 146 就是让你手写它，第 3 幕用的正是它的官方序列。）

## 为什么需要它

缓存的现实是**内存有限**：能放快的数据永远比全量少，于是必须回答「装不下了，扔谁？」。LRU 的答案是扔「最久
没被访问过」的那条，依据是访问的**局部性** —— 刚被碰过的大概率还会被碰。

**真实场景：手机 App 的图片内存缓存。** 列表里 5000 张商品图，内存只给 64 MB，装得下约 200 张。用户滑到第 400
张后**往回滑**想看第 320 张：还在内存里就 1 毫秒显示完，被扔了就得重走磁盘解码甚至网络，列表当场掉帧。所以满了该扔
**「最久没被看过」的那张，而不是「最早存进来」的那张** —— 最早进来的那张，可能正是用户当前这一屏反复回看的。这就是
LRU ≠ FIFO 的现实意义。同一套道理还在 OS 页面置换、CPU 缓存行、InnoDB buffer pool、Redis `allkeys-lru`、反向代理
连接池（最久没被借用的连接先关）里跑。

**为什么一种结构不够？** `main.c` 第 1 幕把两种痛各测了一遍，这是真实输出：

```text
      · 只有哈希表（没有链表）：只能把所有桶全扫一遍比 stamp ⇒ 扫了 6 个条目，答案是 key=101
        这就是 O(n)：缓存越大越慢，而缓存恰恰就是为了大而存在的
      · 有双向链表：直接看 tail.prev ⇒ 0 次比较，答案是 key=101
      · 两个答案 一致 ✔ ⇒ 链表维护的顺序是真的「按新旧排」的，没写错
```

只用哈希表：查 key 是 O(1)，但「谁最旧」答不了，只能扫全表比时间戳 ⇒ O(n)，而且每次 get 都在改写新旧关系，这个扫描
连「提前算好」都做不到。只用双向链表：尾巴就是最旧（O(1) 知道该扔谁），但 `get(k)` 要**找** k 在哪个节点 ⇒ O(n)。合
起来才是两个 O(1) 各管一半，而且**桶里存的就是链表节点的指针** ⇒ 没有第二份数据要同步；还必须**双向** —— 从中间摘走
节点要改前驱的 `next`，单链表找前驱又得 O(n)。

## 图解

### 1. 全景：一份数据、两个视图（哈希槽指向链表节点）

```
   以第 2 幕 capacity=6（⇒ 13 个桶）真实状态为例，槽位与 lru_print_buckets 打印的表格一致
   哈希表 buckets[13]（只存指针）              双向链表（head / tail 是哨兵，不存数据）
   ┌────┬────┬────┬────┬  …  ┬────┐
   │  0 │  2 │  5 │  6 │     │ 12 │   head ⇄ [106] ⇄ [105] ⇄ … ⇄ [101] ⇄ tail
   ├────┼────┼────┼────┼  …  ┼────┤     ↑哨兵   ↑最新                ↑最旧
   │  · │103 │101 │106 │     │105 │──► 102      tail.prev = [101]
   └────┴──┬─┴──┬─┴──┬─┘     └──┬─┘             = 下一个被淘汰的就是它
          ▼    ▼    ▼          ▼   ← 每格指向的都是链表里**同一个 LRUNode**；桶 12 上 105 → 102 是撞桶
   每个节点三根线：prev / next 管「新旧顺序」，hnext 管「同桶冲突」⇒ 哈希只是索引，不是仓库
```

### 2. 核心图：链表顺序 = 最近使用顺序，一次 `get(1)` 把节点搬到头部

```
  第 3 幕 capacity=2 的真实状态：put(1,1)、put(2,2) 之后，get(1) 前 / 后
  get(1) 之前                                     get(1) 之后
  ┌────────┐ ┌─────────┐ ┌────────┐               ┌────────┐ ┌─────────┐ ┌────────┐
  │ head   │◄│ key=2   │◄│ tail   │               │ head   │◄│ key=1   │◄│ tail   │
  │ 哨兵   │►│ val=2   │►│ 哨兵   │               │ 哨兵   │►│ val=1   │►│ 哨兵   │
  └────────┘ └─────────┘ └────────┘               └────────┘ └─────────┘ └────────┘
    tail.prev = 节点[2] ⇒ 下一个淘汰 key=2           tail.prev = 节点[1] ⇒ 下一个淘汰 key=1
  摘：改 p->prev->next、p->next->prev 两处 ⇒ head ⇄ [2] ⇄ tail，中间的洞当场焊上
  插：p->prev=&head; p->next=head.next; head.next->prev=p; head.next=p;
      ⇒ head ⇄ [1] ⇄ [2] ⇄ tail      ← 「被用过一次」= 节点在链表里挪了个位置
  哈希表左右一模一样、一个指针都没动：buckets[h(1)]、buckets[h(2)] 指的还是同一批节点
```

这就是 LRU 的全部语义：**「最近使用」不靠时间戳数组维护，靠位置**，尾巴永远是该扔的那个。两个**哨兵**永远站着 ⇒
`p->prev`、`p->next` 永远非 NULL ⇒ 摘和插里一个 `if` 都不用写，也不用管链表空不空、是不是只剩一个节点。哨兵不省内
存（反而多两个节点），省的是**分支和 bug** —— LRU 写错九成错在边界特判。

## 逐操作拆解

**输出怎么读**（否则会看反）：第 3 幕每一步是「打印当前状态 → 执行 → 打印 `⇒` 结果 → 打印『这一步做完』」，所以
紧跟「第 N 步 …」下面的链表是**操作之前**的样子。以下代码逐字符照抄 `lru.c`，`…` 表示省略中间几行。

### 1. `lru_create` + `lru_pick_buckets`：容量、桶数、两个哨兵

```c
    c->bucket_count = lru_pick_buckets(capacity);
    c->promote_on_get = 1;          /* 默认是真 LRU */
    …
    int b = capacity * 2 + 1;
    …
        b++;                        /* 奇数：和乘法散列的 2 的幂因子不共因子，散得更开 */
```
桶数组是一次 `calloc((size_t)c->bucket_count, sizeof(LRUNode *))` ⇒ `capacity=2` 是 7 桶、`6` 是 13 桶、`8` 是 17
桶（真实输出都对得上），下限 7；**桶数必须明显大于容量**（负载因子 ≤ 0.5），桶越满、拉链越长，O(1) 越接近 O(n)。
`head`/`tail` 是**结构体成员**而非 `malloc` 来的 ⇒ 不用申请、也**永远不该被 free**（`lru_destroy` 的循环就靠这条停
在 `p != &c->tail`），空表 = `head.next == &tail`。`capacity <= 0` 当场被拒并返回 -1，源码为此写了
`printf("      [错误] lru_create：capacity=%d 必须是正整数\n", capacity);`，但 `main.c` 没跑这条路，输出里看不到。

### 2. 哈希那一半：`lru_hash_bucket` / `lru_find_node` / `lru_hash_remove`

```c
    unsigned int k = (unsigned int)key;
    k *= 2654435761u;
    return (int)(k % (unsigned int)bucket_count);
    …
    LRUNode **pp = &c->buckets[b];
    while (*pp != NULL) {
        if ((*pp)->key == key) {
            *pp = (*pp)->hnext;
    …
        pp = &(*pp)->hnext;
```
两个细节：**先转 `unsigned` 再取模**（否则负 key 得负桶号 ⇒ 数组越界）；再乘 `2654435761u`（= 2³²/黄金比例，Knuth 乘法散列）
把高位打散 —— 连续 key 直接取模时桶号等于 key 号，碰上「步长恰好等于桶数」的数据会全挤进同一格。查找（`lru_find_node`）沿
`hnext` 走链，且**必须**逐个比 `p->key == key`：撞进同一桶的不同 key 哈希值一样，不比对就确认不了命中；比了几个记进
`c->bucket_steps` 好把代价打印出来。删除用**二级指针**：`pp` 永远指向「存着这个节点的那只格子」（桶头 `buckets[b]` 或前一个
节点的 `hnext`）⇒ **删链头和删链中是同一行代码**，不用 `prev`、不用特判（和 `pointer-basics` 的二级指针是同一招）。

### 3. 链表那一半：`lru_unlink` / `lru_push_front` / `lru_move_front`

```c
    p->prev->next = p->next;
    p->next->prev = p->prev;
    …
    p->prev = &c->head;
    p->next = c->head.next;
    c->head.next->prev = p;
    c->head.next = p;
```
`lru_move_front` = `unlink` + `push_front`（开头一句 `if (c->head.next == p)` 挡掉「已经最新」的白忙）就是这个结构的心
脏：**「最近使用」实现上就是挪到链表头**。`unlink` 里紧跟两行 `p->prev = NULL; p->next = NULL;` —— 不是洁癖：哪条路径
摘下来忘了插回去，NULL 解引用**当场崩**，比「悄悄挂在旧链上被遍历」好抓一百倍。`push_front` 四行顺序不能乱（源码注释
原话：「先接自己的两边，再改邻居」）：反过来会先把 `head.next` 覆盖掉、丢掉后继节点。

### 4. `lru_get`：查 + 提升，必须连着做

```c
    if (p == NULL) {
        c->misses++;
        return -1;                  /* 题目规定的未命中记号 */
    …
    p->stamp = ++c->clock_ticks;    /* 记时刻：给 lru_check_order / lru_naive_find_oldest 用 */
    if (c->promote_on_get) {
        lru_move_front(c, p);       /* ★LRU 的全部灵魂就在这一行 */
    }
```
未命中时 `size`、链表、哈希表**全部不变**（不存在的东西没法提），第 6 幕末尾专门验了这点。命中就顺手记一个全局递增的
「第几刻」（`clock_ticks` 自增，`accesses` 也加一），于是「链表从头到尾 = stamp 从大到小」这条不变式能被机器查出来，
而不是靠人相信它。

### 5. `lru_put` + `lru_evict_node`：三条路，顺序极其要紧

```c
    if (p != NULL) {
        /* 老 key：只改值 + 提到最新，**不新增条目、不淘汰任何人** */
        p->value = value;
        p->stamp = ++c->clock_ticks;
        lru_move_front(c, p);
    …
    if (c->size >= c->capacity) {
        lru_evict_node(c, c->tail.prev);   /* tail.prev 恒等于最旧节点，哨兵保证它永远存在 */
    …
    lru_hash_remove(c, victim->key);
    lru_unlink(victim);
    free(victim);
    …
    c->size--;
```
路 A 老 key：改值 + 搬头，`size` 不变、谁也不被淘汰。路 B 新 key 且已满：**先淘汰后插入** —— 源码注释自己写了后果：
`顺序反了会怎样？capacity=1 时：先插入的话它自己就是最旧的，紧接着被淘汰的是它自己` ⇒ 缓存恒空、恒 miss。路 C 未满：
`malloc` → 插头 → 插桶头 → `size++`。最后几行是 `lru_evict_node` 的核心：**淘汰要连着做完四件事 —— 1) 哈希表摘掉
2) 链表摘掉 3) `free` 4) `size--`**（`free` 与 `size--` 之间还有一句 `g_nodes_freed++;` 自记账），少一件都是 bug，症状
见坑 4。`last_evicted_key`/`last_evicted` 必须在 `free` **之前**记下，否则就是读已释放内存。

### 6. `lru_destroy` + 观察对拍函数（不属于 LRU 本体）

```c
    /* 只 free 真节点：从 head.next 走到 tail 为止，tail 本身不能 free（它是栈上的成员） */
    while (p != &c->tail) {
        LRUNode *next = p->next;
        free(p);
        …
    free(c->buckets);
    c->buckets = NULL;              /* 置空：再调一次 destroy 也安全，用了它则是干净的段错误 */
```
**先存 `next` 再 `free(p)`**，否则 `p->next` 就是读已释放内存；只走链表是因为节点在链表里只一份 ⇒ 天然不会重复
`free`；`free(c->buckets)` 也不能忘（桶数组是独立一次 `calloc`，只清链表照样整块泄漏）。置 NULL 让 destroy **幂等**，
所以 `main.c` 结尾故意对 `cache` 连调两次证明不会二次释放；另有全局计数自己记账，收尾「申请几个 / 释放几个」必须配平
—— 这是第一道闸。

| 观察 / 对拍函数 | 为什么存在 |
|---|---|
| `lru_peek` | 只查**不提升**：对拍时「看一眼」不该改变新旧顺序，否则观察者污染被观察的系统 |
| `lru_check_order` | 沿链表验「stamp 严格递减」+「链表长度 == size」，一个函数盯住两条不变式 |
| `lru_naive_find_oldest` | 故意**不走链表**、扫全部桶找最小 stamp ⇒ 就是「只有哈希表」的平行世界，和 `tail.prev` 必须永远同答案 ⇒ 两个实现互相盯着 |
| `lru_print_buckets` | 打印每格链长与最长链，让「哈希退化」肉眼可见 |
| `lru_set_promote_on_get` | 关掉提升 ⇒ 现场退化成 FIFO，证明第 4 节那一行值多少 |

**实现到什么程度（诚实清单）**：① key/value 都是 `int`，不做泛型；② 桶数 `lru_create` 一次定死，**没有扩容 / rehash**，
也没有线程安全；③ `lru.h` 末尾把 `lru_alloc_stats` 声明了两遍（143 与 147 行），C 允许重复声明、不影响编译，属文档冗余；
④ `lru.h` 说 `lru_peek` 会把步数记进 `bucket_steps`，实际做不到（参数是 `const LRUCache *` 写不回去），见坑 7；⑤ `main.c`
第 4、5 幕有几处**讲解文字比实测输出讲得满**，一切以 stdout 为准。

## 复杂度

| 操作 | 时间 | 为什么 |
|---|---|---|
| `lru_get`（命中 / 未命中）| **O(1)** 平均 | 一次乘法 + 一次取模定到桶，拉链平均 1~2 个节点；提升 = `unlink` 改 2 处邻居 + `push_front` 改 4 处 = 6 次指针写，**与链表长度无关**；未命中只是不搬、不分配 |
| `lru_put`（老 key / 未满新 key）| **O(1)** | 定位 + 改值 + 搬头；或 定位 + `malloc` + 插头 + 插桶头 |
| `lru_put`（已满新 key）| **O(1)** | 淘汰对象是 `tail.prev`，**看一眼就知道扔谁**，不用扫；`lru_evict_node` 四件事全 O(1) |
| `lru_destroy` | O(n + B) | n 个真节点 + 一次 `free` 桶数组，只在收尾跑 |
| 五个观察 / 对拍函数 | O(n)，两个还 +B | 教学用的遍历与全表扫描，**不在热路径**；`naive` 故意 O(n)，它就是「没有链表」的下场 |
| 空间 | O(capacity + B)，B = 2×capacity+1 | 每节点 4 个 int + 3 个指针（x86-64 上 40 字节），另加每桶一个指针 |

O(1) 是**两块 O(1) 拼起来的**：哈希表管「定位到节点」，双向链表 + 哨兵管「从任意位置摘走 / 插到头部」，任何一环退化整体
就是 O(n)；而且是「平均」不是「最坏」—— 桶开太小时拉链长度就是最坏比较次数，第 4 幕演的正是这件事。

## 常见的坑

1. **`get` 命中后忘了 `lru_move_front` —— 你就不是 LRU，是 FIFO。** 症状很隐性：程序照跑、命中率照算，只是策略悄悄换了。
   **但要说实话：第 5 幕这次没把差异演出来**，因为它 get 的顺序 `1→2→3` 正好和插入顺序同向，两边尾巴都停在 `key=1`（见上面
   第 5 幕那两行原文），对照行自己也承认「居然一致（说明这串操作碰巧同序）」。要看出差异得让访问顺序 ≠ 插入顺序（例如依次
   `get(3) get(1) get(2)` 再 `put(4)`；按代码推演 LRU 扔 3、FIFO 扔 1 —— 这一串本仓库没跑过，所以这里**不贴它的输出**）。
   同理 `main.c` 写着「看 FIFO 那行的自洽检查为什么跳过」，可那段根本没调 `lru_check_order` ⇒ **一切以 stdout 为准**。
2. **`put` 已存在的 key 只改 `value`、忘了搬到头部。** 正确分支必须连着 `p->value` + `p->stamp` + `lru_move_front` 三件事。
   漏第三行 ⇒ 刚被写过的 key 还挂在尾巴上、下次淘汰先扔它，对外表现是「我明明刚存的东西怎么又 miss」。反方向的手误是在这个
   分支里**又 `malloc` 一个节点**：同 key 在桶里两份、链表上两个节点存同一个 key，而 `lru_hash_remove` 只摘得掉一个。
3. **满了时「先插入再淘汰」。** `capacity=1` 时新节点自己就是 `tail.prev`，马上被淘汰 ⇒ 缓存恒空、恒 miss；大容量下几乎看不
   出来，偏偏小容量压测才炸。`if (c->size >= c->capacity)` 必须在 `malloc` 前。
4. **淘汰只做一半。** 只 `free` 不摘哈希 ⇒ 桶里留野指针，下次 `get` 撞上就是 use-after-free（读到垃圾 key/value，还可能「恰
   好正常」而一路潜伏）；只摘哈希不摘链表 ⇒ 链表上挂着已释放内存，`lru_print` 一遍历就崩；忘 `size--` ⇒ `size` 永远 ≥
   `capacity`，从此每次 put 白扔一个条目。它难查，正因为**症状崩在与错误完全不同的地方**。
5. **`free` 的时机和对象。** 必须先 `next = p->next` 再 `free(p)`；`free(c->buckets)` 也不能忘。反过来**哨兵绝不能 free**：
   `head`/`tail` 是结构体成员（活在调用者的栈上），free 它们等于 `free` 栈地址，ASan 会直接点名。
6. **负数 / 0 当 key：必须先转 `unsigned` 再取模。** C 的 `%` 符号跟着左操作数，`-1 % 桶数` 是负下标，越界写常崩在八竿子打不
   着的地方。第 6 幕把 `0, -1, -7, 7, 2147483647` 五个 key 全打在合法区间（`一定在 0..16 内`），而且 `key=0` 是**合法 key**。
   所以「这次没淘汰任何人」不能靠 `last_evicted_key` 的特殊值表示，代码用的是独立标志位（`last_evicted=0`）。
7. **桶数开成容量那么大 ⇒ 拉链把 O(1) 吃回去。** 第 4 幕把 `bad.bucket_count` 改成 3（`main.c` 自己注释「⚠ 教学用：正常代码
   别硬改字段」），6 个 key 挤成 `最长链 3（在桶 0）`，负载因子 2.0。两处数字要打折看：① 桶数虽被改成 3，但 `calloc` 当初按
   13 格申请，所以 destroy 打印的 `+ 3 个桶`只是**当前 `bucket_count` 的数值**，真实释放的是整块 13 格数组；② `lru_peek` 参数
   是 `const LRUCache *`、**写不回** `bucket_steps`，于是第 4 幕那两行「最坏的一次比了几个节点」读到的是**上一次 `lru_put`
   留下的值**（13 桶那次 key=42 独占一格 `5 : 42` ⇒ 0；3 桶那次 42 排在 35、28 前面 `2 : 42 35 28` ⇒ 2）。结论方向没错，但别
   把这两个数当 peek 的实测步数。
8. **未命中返回 `-1` 是约定不是语义。** `value` 本身也能被存成 -1，这时外面区分不了「没这个 key」和「这个 key 的值就是 -1」。
   真实工程要么返回 `bool` + 传出参数，要么用一个不可能当值的哨兵：`lru_get(999) = -1（未命中），misses = 1`。

## 自检问题

1. 为什么桶里存**链表节点的指针**而不是 `(key,value)` 的拷贝？→ 「为什么需要它」+ 图解 1（存拷贝要两处各自维护，淘汰还得放两次内存）。
2. `get` 命中为什么必须用**双向**链表，只有 `next` 会怎样？→ 图解 2 + 拆解 3（要改前驱的 `next` 才摘得掉中间节点，单链表找前驱 ⇒ O(n)）。
3. `capacity=1` 时「先插后淘汰」的症状是什么？为什么大容量看不出来？→ 拆解 5 + 坑 3 + 第 6 幕输出。
4. 一次淘汰必须做完哪四件事？漏掉分别什么症状？→ 拆解 5 + 坑 4。
5. `lru_naive_find_oldest` 明明 O(n)，为什么还要写它？→ 拆解 6 的表格（它就是「只有哈希表」的平行世界，和 `tail.prev` 对拍；不一致就说明链表顺序已不是按新旧排的）。
6. `promote_on_get = 0` 时 `lru_check_order` 为什么跳过而不是报错？→ 拆解 6 + 坑 1（FIFO 下「位置」等价于插入顺序而非使用顺序，前提已不成立，报错反而是撒谎）。
