# 线段树 segment-tree（带懒标记 lazy propagation）

> 一句话定位：**区间查询 O(log n)、区间修改也 O(log n)** 的全能选手，代价是代码量和一层"欠账"心智负担。

---

## 一句话是什么

把**区间**当成二叉树的节点：叶子管 1 个数，父亲管两个孩子合起来的那一段，所以 **父亲的和 = 左 + 右**。
任意一段区间都能被拆成树上**不超过 2·log n 个"整块"节点**，查询时只加这几块，不整块的就一次比较踢掉。

再在外面套一层**懒标记 `lazy[]`**：区间修改时只改"被整段盖住"的那几个节点，
把"欠孩子的那一笔"记在 `lazy[node]` 里，**等真的要用到孩子时（往下钻）才还** —— 这叫 pushdown。

本节的数据是固定的 `a[1..8] = 5 3 8 1 4 2 7 6`，全程可以手算复核。

---

## 为什么需要它

需求：一个数组，**改区间**（`a[2..5] 每个 +3`）和**查区间和**（`a[2..5] 等于几`）大量交替出现。

| 做法 | 查区间和 | 改区间 | 痛在哪 |
|---|---|---|---|
| 只存原数组，现场 for 循环 | O(n) | O(区间长度) | 两个都是线性的：1e5 次操作 × 1e5 长度 = 10^10，直接超时 |
| 前缀和数组 `pref[]` | O(1) | **O(n)** | 改一个数，它右边所有 `pref` 全废；"改区间"更是灾难 |
| 树状数组 BIT | **O(log n)** | 单点 O(log n)；**改区间要一格一格改 ⇒ O(长度·log n)** | BIT 天生只擅长"单点改 + 前缀查"。硬做区间改得上"差分 BIT"，两层套娃极易写错 |
| **线段树 + 懒标记** | **O(log n)** | **O(log n)** | 代码长（递归 + pushdown）、常数比 BIT 大、空间 4n |

**上一节（`09-others/binary-indexed-tree/`）留了个坑没填**：BIT 做 `a[2..5] += 3` 只能拆成
4 次单点 `update`，区间越长越慢 —— 也就是"根本没优化"。线段树就是为这类需求生的。

第 1 幕把这个痛**实测**出来：`a[2..5] += 3` 在线段树里只访问 11 个节点（其中真正写值的 8 个），
朴素循环要写 4 格；n=10 万、区间长 5 万时，朴素是 5 万次写、线段树还是十几个节点。

**生活化比喻**：老师要算全班 8 大组的总分。
- 笨办法：每次从第 1 组数到第 8 组（O(n)）。
- 线段树：组长只报"我们组 4 人共 32 分"，班长报"我这 4 个组共 130 分"。问"第 3~6 组多少分"时，
  能整块拿的组长就整块拿，不用下去数人头。
- 懒标记："今天临时通知 3~5 组每人加 3 分" —— 这话只说给管着 3~4 组的组长（他点头记在小本本上），
  他底下两个人**暂时不知道**。等哪天要单问第 3 组，组长才把小本本上的话往下传达（pushdown）。
  没人问就永远不传达 —— 白省一堆力气，这就是"懒"。

## 内存布局图解

### 1. 逻辑上是一棵二叉树，物理上是三条 int 数组

```
                          1  [1,8]              ← sum[1] = 36（全部之和）
                 ┌─────────┴─────────┐
              2  [1,4]               3  [5,8]   ← sum[2] = 17，sum[3] = 19
          ┌──────┴──────┐      ┌─────┴──────┐
       4  [1,2]     5  [3,4]  6  [5,6]   7  [7,8]
       ┌──┴──┐      ┌──┴──┐   ┌──┴──┐     ┌──┴──┐
    8 [1,1] 9 [2,2] 10[3,3] 11[4,4] 12[5,5] 13[6,6] 14[7,7] 15[8,8]   ← 叶子 = 单个元素
```

**节点编号规则（整个结构就靠这一条撑着）**：节点 `i` 的左孩子是 `2i`、右孩子是 `2i+1`，
所以**不用一个指针**，`node*2` 就是孩子 —— 这就是"数组当树"。

```
   SegTree
  ┌───────────┬──────────────────────────────────────────────────────────────┐
  │ sum  ─────┼─→ [空][1号][2号][3号][4号][5号][6号][7号][8号] … [36号]        │  共 4n+5 = 37 格
  ├───────────┤      36    17   19    8    9    6   13    5    3   ← n=8 时只用到 1..15
  │ lazy ─────┼─→ 同样 37 格：某格非 0 = "这个节点管的区间里每人还欠 lazy 这么多，孩子不知道"
  ├───────────┤
  │ a   ──────┼─→ [空][5][3][8][1][4][2][7][6]  ← 原值副本，**只给朴素对拍用**，线段树不碰它
  ├───────────┤
  │ n = 8     │   trace = 0/1（要不要打印递归走向）   visits = 本次访问了几个节点
  └───────────┘
   手算核对：sum[2] = 5+3+8+1 = 17 ✔   sum[3] = 4+2+7+6 = 19 ✔   sum[1] = 36 ✔
```

### 2. 为什么是 4n 而不是 2n（第 3 幕实测表，眼见为实）

只有 n 正好是 2 的幂时树才**满**，此时最后一层从 `n+1` 排到 `2n`，`2n` 刚好。
n 不是 2 的幂时树不满，但编号仍照 `2i`/`2i+1` 往两边推，**最靠右那条分支每次乘 2 再加 1，编号窜得比元素数快**：

```
     n    实际最大编号    2n    4n     结论
      5            9      10     20   2n 够用
      6           13      12     24   ★2n 不够（差 1 格就是越界写）
     10           25      20     40   ★2n 不够，差 5 格
     12           29      24     48   ★2n 不够，差 5 格
   n = 1040       3969    —    4160   占 4n 的 95.4%  ⇒ 4n 是"几乎卡着上界"的安全值
```
（最后那行是第 3 幕扫 n=1..2000 找出来的最凶例子：**4n 不多不少刚好够用**，而 2n 会越界踩坏别人的内存。）

### 3. 懒标记挂在哪 —— 三格快照（第 6 幕真实输出，n=8）

`a[2..5] += 3` 之后，树长这样（节选）：

```
   改之前：                            改之后（★只有 3 格被整段盖住，[3,4] 挂了欠账）：
   节点1   [1,8]  和=36                节点1   [1,8]  和=48        ← 汇总上来的，对
     节点2   [1,4]  和=17                节点2   [1,4]  和=26      ← 汇总，对
       节点4   [1,2] 和=8                  节点4   [1,2] 和=11     ← 汇总，对
         节点8  [1,1] 和=5                  节点8  [1,1] 和=5      ← 不在区间里，没动
         节点9  [2,2] 和=3                  节点9  [2,2] 和=6      ← 整段盖住 ⇒ 直接 +3
       节点5   [3,4] 和=9                  节点5   [3,4] 和=15  lazy=+3 ★  ← 整段盖住：+3×2 人
         节点10 [3,3] 和=8                  节点10 [3,3] 和=8      ← ⚠ 脏！真值已是 11
         节点11 [4,4] 和=1                  节点11 [4,4] 和=1      ← ⚠ 脏！真值已是 4
```

**全树始终成立的不变式**（背下来，pushdown 的必要性就从这里推出来）：

```
   sum[父]  =  sum[左] + sum[右] + lazy[父] × 父区间长度
   还账前：15 = 8 + 1 + 3×2 = 15 ✔        还账后：15 = 11 + 4 + 0×2 = 15 ✔
```

于是有两条**必须记住**的推论：

1. **任何一个节点自己的 `sum` 永远是正确的**（含挂在自己身上的账）。
   ⇒ 查询只要能"整块取走"这个节点，就**完全不用往下走、不用还账** —— 省时间就是这么来的（第 6 幕第 3 步实测：
   查 `[1,4]` 只访问 3 个节点就返回 26）。
2. **孩子的值可能是脏的**（`sum[10]=8` 而真值是 11）。
   ⇒ 只要打算往孩子走，就必须先把父亲的账还下去（pushdown），否则读到的就是脏值 ——
   **查询路径和修改路径都适用**，没有例外。

为什么修改路径也非还账不可？因为部分相交的节点在改完孩子后要执行
`sum[父] = sum[左] + sum[右]`（`st_add_rec` 最后一行）。若父亲还挂着 lazy 没还，
`左+右` 就少算了那笔账，把父亲的**正确值覆盖成错的** —— 这类 bug 不会当场崩，只在很久之后给你一个莫名其妙的数字。

## 核心操作逐个拆解

### 1. `st_init(t, src, n)` / `st_free(t)` —— 建树与拆树

**干什么**：用 `src[0..n-1]`（C 的 0 起点）建一棵管 `[1..n]` 的树。

**一步步怎么做**（`st_build_rec`，后序遍历，一趟 O(n)）：
1. `calloc(4n+5)` 两条数组 `sum[]`、`lazy[]`，再 `calloc(n+1)` 一条朴素副本 `a[]`；
   `src` 存进 `a[1..n]`（下标 +1，因为节点编号从 1 起）。
2. 到节点 `(node, [l,r])`：若 `l == r` ⇒ 叶子，`sum[node] = a[l]`、`lazy[node] = 0`，返回。
3. 否则 `mid = l + (r-l)/2`（**不要写 `(l+r)/2`**：n 很大时 `l+r` 会溢出），
   先递归建 `2i`（管 `[l,mid]`）和 `2i+1`（管 `[mid+1,r]`），回来 `sum[node] = sum[2i] + sum[2i+1]`。

**边界情况**：`n <= 0` 或 `t == NULL` ⇒ 打印错误返回 -1；malloc 失败时把已申请的全部 free 并置 NULL。
`src == NULL` ⇒ 全 0 起步（合法，不是错误）。
`st_free` 三个指针都要 free + 置 NULL，漏一个 ASan 就点名。

**对应代码**：`segtree.c` 的 `st_init()`、`st_build_rec()`、`st_free()`。

### 2. `st_range_add(t, L, R, v)` —— 区间加（懒标记的灵魂）

**干什么**：`a[L..R]` 每个数 `+v`，只碰 O(log n) 个节点。

**一步步怎么做**（`st_add_rec`，第 1 幕把每一步都打印出来了）。三种情况，**顺序绝对不能颠倒**：
1. `[l,r]` 与 `[L,R]` **完全不相交**（`R < l || r < L`）⇒ 转身就走。这一步只花一次比较，是线段树快的另一半原因。
2. `[l,r]` **被 `[L,R]` 整个盖住**（`L <= l && r <= R`）⇒ ★调用 `st_apply` 后 `return`，**不再往下**：
   ```
      sum[node] += v × (r - l + 1)     ← 区间和 = 每人加 v × 有几个人
      if (l != r) lazy[node] += v      ← 只有"有孩子"的节点才记账；叶子没孩子，欠给谁？
   ```
3. **只有一部分相交** ⇒ 先 `st_pushdown(node)` 把旧账还给孩子，再钻进两个孩子递归，
   回来 `sum[node] = sum[2i] + sum[2i+1]`（此时 `lazy[node]` 必为 0，所以这个式子成立）。

**实测**（第 1 幕）：`a[2..5] += 3` 访问 11 个节点 = 3 个整段盖住的（[2,2]、[3,4]、[5,5]）
+ 5 个祖先重算汇总 + 3 个路过发现不相交立刻返回。

**边界情况**：
- `L > R`、`L < 1`、`R > n` ⇒ 打印错误直接返回，绝不越界。
- `v == 0` ⇒ 白跑一趟，无害。
- "把 `a[i]` **改成** v"（赋值，不是加）：线段树只认加法，先问再算差：
  `int cur = st_range_sum(t,i,i); st_point_add(t, i, v - cur);`（`segtree.h` 里有这段提示）。
  ⚠ 别把"区间赋值"直接写成 `lazy[node] = v` 混在加法标记里 —— 那是另一种标记（要记"覆盖"而不是"加"，
  还得处理"覆盖后又加"的顺序），本节不碰这个坑。

**对应代码**：`segtree.c` 的 `st_range_add()`、`st_add_rec()`、`st_apply()`。

### 3. `st_range_sum(t, L, R)` —— 区间和查询

**干什么**：返回 `a[L..R]` 的和。

**一步步怎么做**（`st_sum_rec`，结构和修改一模一样，只是"整段盖住"时返回而不修改）：
1. 不相交 ⇒ **返回 0**。0 是加法的单位元（"什么也没加"），所以能直接和别的结果相加。
   ⚠ 换成区间最大值，这里必须返回"负无穷"，返回 0 会把答案污染成 0 —— 这是最常见的移植事故。
2. 整段被盖住 ⇒ 直接返回 `sum[node]`，**不往下**（这才是省时间的地方；见不变式推论 1）。
3. 部分相交 ⇒ **`st_pushdown(node)`** 后分别问左右，回来相加。

**为什么是 O(log n)**：树高 log n；每一层最多有 2 个节点"卡在区间边界上"必须继续往下，
其余要么整块取走、要么一次比较踢掉 ⇒ 取走的整块 ≤ 2·log n 个。
第 7 幕的实测：n=8 时每次操作只访问 **1~11 个节点**（`visits` 字段），朴素要加 1~8 格；
n=100 万时上界约 40 个节点，而朴素是 100 万次。

**边界情况**：非法区间同样打印错误并返回 0；单点查询写 `st_range_sum(t,i,i)`
（**别去读叶子格 `sum[]`**，更别读 `a[]`，见"常见的坑"第 4 条）。

**对应代码**：`segtree.c` 的 `st_range_sum()`、`st_sum_rec()`。

### 4. `st_pushdown(t, node, l, r)` —— 还账（内部函数）

**干什么**：把挂在自己身上的欠账转给两个孩子，然后把自己清零。

**一步步怎么做**：
1. `z = lazy[node]`；`z == 0` ⇒ **立刻返回**（最常见的分支，所以没欠账时它的开销只有一次读）。
2. `l == r`（叶子）⇒ 就地清零返回。实际上 `st_apply` 从不给叶子记 `lazy`，这条是防御性写法。
3. `st_apply(2i, l, mid, z)` + `st_apply(2i+1, mid+1, r, z)` ⇒ 两个孩子各记到自己头上
   （孩子有孩子的话，`lazy` 会继续往上累加，可以好几层都不还 —— 懒到底）。
4. `lazy[node] = 0`。父亲的 `sum` **一个字都不用改**（早在 `st_apply` 时就加好了）。

**对应代码**：`segtree.c` 的 `st_pushdown()`（函数上方有"还账前 / 还账后"的对比图 + 不变式）。

### 5. `st_point_add(t, i, delta)` —— 单点加

就是"把区间缩成一个点"：`st_range_add(t, i, i, delta)`。
第 5 幕实测：访问 7 个节点，真正被改的只有 `[3,3]→[3,4]→[1,4]→[1,8]` 这一条链（树高+1 = 4 格）。

### 6. 朴素版 `st_naive_range_sum` / `st_naive_range_add` —— 专门用来打脸

`st_naive_range_sum` 就是一个 for 循环加 `a[L..R]`，`adds_out` 带回"加了几次"（用来和线段树比工作量）；
`st_naive_range_add` 就是 for 循环把 `a[L..R]` 每个 `+v`。
**关键设计**：`sum[]/lazy[]` 和 `a[]` 是**两套互不知情的实现** —— 线段树函数只动前者，朴素函数只动后者。
同一串操作喂给两边，结果必须永远相等，不相等就说明有一份写错了（第 7 幕）。

### 7. `st_print_tree` / `st_print_lazy` / `st_max_node_index`

- `st_print_tree(t)`：缩进打印整棵树，每个节点显示"编号 / 管的区间 / 当前和 / 欠账"，
  叶子额外标注对应哪个 `a[i]`。懒标记挂在哪、孩子有多脏，全靠它看见。
- `st_print_lazy(t)`：只把 `lazy != 0` 的节点挑出来打印，并给一句提醒
  （"它们自己的 sum 是对的，但子树里的值还是旧的"）。树很大时用它在所不辞。
- `st_max_node_index(n)`：纯算下标递推（`node*2` / `node*2+1`），不申请任何内存，
  返回"建 n 个元素的树实际用到的最大下标"。第 3 幕拿它把 `2n` vs `4n` 做成了一张实测表。

## 复杂度表

| 项目 | 朴素 for 循环 | 前缀和数组 | 树状数组 BIT | **线段树（懒标记）** |
|---|---|---|---|---|
| 区间查询（和） | O(n) | O(1) | O(log n) | **O(log n)**，实测 n=8 时 1~11 个节点 |
| 区间修改（加） | O(长度) | O(n) | O(长度·log n)（只能拆成单点） | **O(log n)** ★这就是它存在的理由 |
| 单点修改 | O(1) | O(n) | O(log n) | O(log n)，实测 4~7 个节点 |
| 区间最大值 / 最小值 / GCD | O(n) | ✖ 做不了 | ✖ 做不了 | **O(log n)**（同一套模板，改合并方式） |
| 建树 | — | O(n) | O(n log n) | O(n) |
| 额外空间 | O(1) | O(n) | O(n) | **O(4n)** 两条数组 = 8n 个 int |
| 常数 / 代码量 | 最小 | 最小 | 3 行，常数小 | 递归 + pushdown，比 BIT 慢几倍、长十倍 |
| 会不会算错（难度） | 不会 | 容易漏同步 | 下标从 1 开始这一个坑 | **pushdown 漏一次就悄悄错**，最难 |

横向结论：**能 BIT 就 BIT**（短、快、不容易错）；只有在"区间修改 + 区间查询"，
或者"查询的东西不能拆成前缀相减"（区间最大值、最小值、GCD、第一段满足条件的位置……）时才上限段树。
而"区间最大值 + 区间修改"这种，线段树是**唯一**顺手的 O(log n) 工具。

## 编译与运行

在项目根目录：

```bash
make one DIR=09-others/segment-tree
# 内存安全检查（越界写是这一节的主题，必须跑）：
gcc -Wall -Wextra -Wshadow -std=c11 -g -fsanitize=address -static-libasan \
```

## 常见的坑

1. **数组只开 2n ⇒ 越界写**。n=6 就要 13 格（比 2n=12 多 1 格），n=10 要 25 格（2n 只给 20）。
   最阴的地方：n 正好是 2 的幂时**测试全过**，一改到 n=6、n=10 就崩，而且崩在别的地方。
   解法：`4*n + 5`，第 3 幕那张表就是它的证据。
2. **忘记 pushdown 就去读孩子**（全节第一大坑）。症状：单个查询结果偏小，而且**改的区间越多越频繁就越错**，
   自己单步看还以为"逻辑没问题"。铁律：**只要打算往孩子走（查询、修改都一样），必须先 pushdown**。
3. **pushdown 了，但修改完孩子没汇总父亲**。`st_add_rec` 第 3 种情况最后一行
   `sum[node] = sum[node*2] + sum[node*2+1];` 少写它，父亲的旧和留着不动 ⇒ 之后所有"整块取走父亲"
   的查询全错。反过来，"整段被盖住"时**不能**再汇总（孩子压根没改，汇总会把刚加上的账冲掉）。
4. **把树里的某个格子当 `a[i]` 用**。两个原因都会翻车：
   (a) `sum[]` 是按节点编号排的，叶子 `a[3]` 在 n=8 时住在 `sum[10]` —— 编号会随 n 变；
   (b) 祖先可能挂着 lazy，叶子里还是**脏值**（第 6 幕实测：`sum[10]` 写着 8，真值 11）。
   要单点值请用 `st_range_sum(t, i, i)`，它保证沿途还账。
5. **`mid = (l + r) / 2` 写成加法**。`l + r` 在 n 上到 1e9 级别时 int 溢出 ⇒ 数组下标变负数。
   统一写 `mid = l + (r - l) / 2`，本文件里三处 mid 全是这个写法。
6. **不相交时返回 0，却把模板抄去求最大值**。求和的单位元是 0（加不加都一样），
   求 max 的单位元是"负无穷"。照抄 `return 0;` ⇒ 全负数组的最大值查询会神秘地返回 0。
7. **在"整段被盖住"的分支里还往下递归**。那就退化成了 O(n) 暴力，线段树的全部意义就是那一行 `return`。
8. **`st_free` 漏一个指针**。三条数组 `sum`/`lazy`/`a` 全要 free 并置 NULL；
   本 demo 跑 ASan 就是为了这条（漏了会直接点名 "LeakSanitizer"）。
9. **递归深度担心爆栈**：不用怕，深度只有 `log2(n)+1`（n=8 时 4 层，n=1e9 时 30 层）。
   真正会爆栈的是拿线段树去"逐层打印"或者写成 n 层递归，别把 `st_print_tree` 用到超大 n 上
   （它本来也只是教学用，n=8 才印得下）。

## 什么时候用它 / 什么时候别用

**适合**：
- **区间修改 + 区间查询**（本节的主题，BIT 干不动的活）
- 查询不能拆成"前缀相减"的：区间最大值 / 最小值 / GCD / 第一个 ≥ x 的位置 / 最长连续满足段
- 扫描线、线段树合并、可持久化线段树等一切进阶玩法的地基（先有这棵树，才谈得上那些）
- 需要按区间做决策的问题：`O(log n)` 的稳定性比"数据量小所以暴力"更可靠

**别用**：
- 只有"单点改 + 前缀查" ⇒ 用 BIT（`09-others/binary-indexed-tree/`）：代码短 10 倍、常数小、几乎不会写错
- 数据一次建好、后面**绝不修改** ⇒ 排序数组 + 二分 / ST 表（稀疏表）更简单更快
- 需要"区间赋值 + 区间加 + 区间查询"混合 ⇒ 得上更复杂的标记设计（或平衡树 / 树链剖分），门槛高一大截
- 数据量很小（n ≤ 1e3）且操作数很少 ⇒ 朴素 for 循环更好，写起来 3 分钟，还不会错

## 自检问题

1. 为什么数组要开 `4n+5`？`2n` 到底差在哪？
   **答**：节点 `i` 的孩子是 `2i`、`2i+1`，只有 n 是 2 的幂时树才满（最大编号 `2n-1`）。
   树不满时编号仍按 `2i/2i+1` 往两边推，最右分支每次"乘 2 加 1"，窜得比元素数快：
   实测 n=6 要 13 格（>12）、n=10 要 25 格（>20），而最坏情况（n=1040）用到 4n 的 95.4% ⇒ `4n` 是几乎卡着上界的保险值。
2. `lazy[node] = 3` 到底是什么状态？此时谁的数是对的、谁是脏的？
   **答**：意思是"本节点管的这段区间里，每个孩子身上还欠 +3 没传下去"。
   `sum[node]` **是对的**（记账时就 `+= 3×区间长度` 了）；它的**整棵子树都是脏的**，
   叶子值偏小。不变式：`sum[父] = sum[左] + sum[右] + lazy[父] × 父区间长度`。
3. 为什么"整段被盖住"时查询可以直接返回、不往下钻，但"部分相交"时必须 pushdown？
   **答**：整段被盖住时答案就是这个节点自己的 `sum`，而它永远是对的（见第 2 题）⇒ 不往下走，就永远不碰脏数据。
   部分相交时必须去问孩子，孩子可能脏 ⇒ 先还账。这就是"能整块拿就不拆"既省时间又保安全的由来。
4. 修改路径上也要 pushdown，为什么？明明改完还要 `sum[父] = sum[左] + sum[右]` 汇总。
   **答**：正因为要汇总。如果父亲身上还挂着没还的账，孩子身上就**缺那笔账**，
   `左 + 右` 算出来比真实值少 ⇒ 把父亲本来正确的 `sum` **覆盖成错的**。
   先 pushdown 才能保证"孩子的和"与"父亲的账"是同一套口径。
5. 用这套结构（只有 `lazy` 加法标记）能做"把 `a[2..5]` 全部**赋值**成 7"吗？
   **答**：不能直接做。`lazy` 记的是"每人再加多少"，赋值是"每人变成多少"，两者混合要额外记
   "覆盖标记 + 覆盖的时间顺序"（经典做法：再加一个 `set_tag`，遇到赋值就清掉该节点的加法账并置覆盖标记）。
   单点赋值可以做：`st_point_add(t, i, 新值 - st_range_sum(t, i, i))`。
6. 有了上一节的 BIT，为什么还要学线段树？
   **答**：BIT 的两个短板线段树都能补：① 区间修改只能拆成单点改（O(长度·log n)）；
   ② 查询必须能表达成"前缀相减"，区间最大值这种可重叠子问题它干不了（要上稀疏表）。
   线段树把这两件事都变成 O(log n)，代价是代码量、常数、以及 pushdown 这个心智负担。
