## 一句话是什么

**一条位数组 + k 个哈希下标**，用来回答"这个键**肯定没来过**，还是**也许来过**？"

- 它说"**肯定没有**" ⇒ **百分之百可信**，可以直接拒绝，后面的数据库一次都不用碰。
- 它说"**可能存在**" ⇒ **有一定概率是假的**，这个概率在设计时就定死了（本节的 p = 1%），只能再去真表确认。

一句话记忆：**布隆过滤器是"宁可错杀、不可放过"的门神 —— 它只会误报，绝不会漏报。**

它跟哈希表最本质的区别：**布隆过滤器不存键本身**。
`user_42` 加进去之后，内存里没有一个字节写着 `user_42`，只有 7 个位被按成了 1。

```c
Bloom *bf = bloom_new(5000, 0.01);   /* 预计 5000 个键，容忍 1% 误判 */
bloom_add(bf, "user_42");            /* 登记：把它那 7 个位按亮 */
bloom_maybe_contains(bf, "user_42"); /* ⇒ 1（可能存在） */
bloom_maybe_contains(bf, "x_42");    /* ⇒ 0（肯定没有）—— 这个 0 是硬保证 */
bloom_free(bf);                      /* 谁 malloc 谁 free */
```

**关于"存的值"**：本仓库铁律是"值一律 `int`、不许 `void *` 泛型、不许函数指针比较器"。
布隆过滤器天生就没有"值"这个槽位 —— 它的"值"就是那 k 个位（0 或 1）。
所以本节 `int` 出现在两处：**键**（`bloom_add_int(bf, 1001)`）和**返回值**（0/1/-1），全程零个 `void *`。

## 为什么需要它

想象你在做一个短链服务，每来一个短码就要问数据库"这个码存在吗"。
99% 的请求是乱码（爬虫瞎猜），每次都打到数据库就是白打。
你手里有两种选择：

| 方案 | 判"在不在"需要什么 | 5000 个键要占多少内存 |
|---|---|---|
| 哈希表 / Set | 必须把**每个键本身**存下来，还要能比较（strcmp） | 每元素约 60 字节 ⇒ **300000 字节** |
| 布隆过滤器 | 只需要 k 个**位**被按亮 | m = 47926 **位** ⇒ **5991 字节** |

差 **50 倍**，而且这个差距会随着键变长继续拉大（键是 URL 的话哈希表更惨，布隆完全无感）。
本节程序实测出来的比例是 **50.1 倍**（见第 6 幕输出）。

**为什么能这么省？** 因为它放弃了三件事：

1. **放弃精确**：可能误判（"也许来过"里混着 p 比例的假消息）。
2. **放弃删除**：位是多个键共用的，你不敢关灯（第 8 幕实测：删 1 个键，误伤 2 个键）。
3. **放弃列举**：问不出"里面都有谁"，内存里根本没有键。

只要你能接受这三条放弃，它就能把"判在不在"的成本压到**每元素约 10 位**（p=1% 时），
这是任何精确结构都做不到的。真实场景：

- **缓存穿透防护**：不存在的 key 直接拒，不打后端（最常见的用法）。
- **爬虫 URL 去重**：几十亿 URL，判"这个网址我抓过吗"，不需要精确答案。
- **垃圾邮件/黑名单初筛**、**数据库 LSM-tree 判断"这个键可能在哪张 SSTable 里"**（RocksDB、Cassandra 都这么做）、
  **协同编辑里判"这个词是不是拼写错误"**（拼写词典布隆 + 少量假阳性完全可接受）。

> 反向清单：**别用它做权限判断、去重落库、唯一性约束**——那些场景"误判"就是事故。
> 它只能当"粗筛"，粗筛后面必须跟着一个精确结构来复核（或者假阳性本身无所谓）。

### 图 2：位数组寻址 —— 为什么是 `/8` 和 `%8`

一个 `unsigned char` 有 8 位，能当 8 个开关。"第 idx 个开关"必须拆成两个问题：

```
        idx = 11
          │
          ├── idx / 8 = 1   ⇒ 住在第 1 个字节里（每字节装 8 个 ⇒ 整除就是"第几行"）
          └── idx % 8 = 3   ⇒ 是这个字节的第 3 位（余数就是"行内第几列"）

   楼层类比：一栋楼每层 8 个房间，1005 号房 → 1005/8 = 125 层，1005%8 = 5 号房。

   bits[0]      bits[1]      bits[2]      bits[3]
   位号 76543210 76543210     ...
           全局  7 6 5 4 3 2 1 0
   下标映射 8→ 9  10  11  12  13  14  15     ← 字节内下标从【右】往【左】长
   bits[1] = 0 0 0 0 1 0 0 0
                    ↑ 第 3 位（1u<<3）就是全局下标 11 = 1*8 + 3

   代码就是这三步：
       bits[idx / 8]        ← ① 找到字节（行号）
       1u << (idx % 8)      ← ② 造出只有那一位是 1 的掩码（列号）
       |=                   ← ③ 按亮（灯已经亮着也没关系，|= 是幂等的）
```

**为什么写 `1u` 而不是 `1`**（本节最该背下来的一条）：

| 写法 | 语义 | 结论 |
|---|---|---|
| `1 << 7` | 有符号 int 左移，结果 128，还在 int 范围内 | 这一行恰好没事（位号最大 7） |
| `1 << 31` | 有符号 int 移进符号位 ⇒ 结果不是 int 能表示的值 ⇒ **有符号溢出 = 未定义行为** | ❌ 编译器有权假设它不发生 |
| `1u << 31` | 无符号左移，**对 2^32 取模，标准明确定义** = 2147483648 | ✔ 正确姿势 |
| `1 << 40` / `1u << 40` | 移位量 ≥ 类型位宽 ⇒ **未定义行为** | ❌ 要写 `1ULL << 40` |

位操作的通用形状是 `1u << 位号`，位号可能是 0..31、64 位域里还是 0..63。
**一律用无符号字面量**，就不用每次去查"这次有没有越过符号位"；而且 `unsigned char |= unsigned int`
两边都无符号，不会引入符号扩展。第 64 位域里（`bloom_hash_int`、`bloom_derive_slots`）同理一律 `ULL`。

### 图 3：两条性质的由来

```
【性质 A｜说没有 ⇒ 一定没有】为什么 100% 可信（反证一遍）

    键 K 真被 add 过
      ⇒ add 时把它的 k 个位全按成 1
      ⇒ 位数组只会 0→1，永远不会 1→0（标准版没有删除！这条是关键前提）
      ⇒ 现在再去看这 k 个位，必然【全是 1】 ⇒ 必然回答"可能存在"
    逆否命题：回答"肯定没有"（说明至少有一位是 0）⇒ K 一定没被 add 过 ✔


【性质 B｜说有 ⇒ 可能误判】假阳性是怎么"凑"出来的（本节探针 x_42 的示意）

    查询 x_42 的 7 个位： #3997 #9074 #14151 #19228 #24305 #41769 #46846
    x_42 从没被 add 过，可是这 7 位全是 1 —— 因为它们分别被【七个不同的键】点亮的：

      #3997 ← user_103 点亮      #9074  ← user_88  点亮
      #14151← user_4021 点亮     #19228 ← user_7    点亮
      #24305← user_999  点亮     #41769 ← user_42   点亮   ← 注意！user_42 就是图 1 那个键
      #46846← user_2733 点亮

    7 个位全亮的概率 ≈ (占比)^k = (0.517)^7 ≈ 1%  ⇒ 每 100 个不存在的键，约有 1 个被骗。
    ⇒ "误判率由 1 的占比决定" 这一句话就是整个布隆过滤器的全部物理学。
```

### 图 4：为什么不能删 / 计数布隆怎么救

```
   标准布隆（1 位/格）                        计数布隆（1 字节/格）
   ─────────────────                          ──────────────────
   共用位 #404： word_0 和 word_42 都要它      共用格 #404： 记的是"占用数" = 2

   add(word_0)  → bit#404 = 1                 add(word_0)  → cnt#404 = 1
   add(word_42) → bit#404 = 1（已经是 1 了）   add(word_42) → cnt#404 = 2
                  ↑ 位只有两个状态，             ↑ 计数器记住了"有 2 个人在用"
                    "有 2 个人在用"这件事丢了

   remove(word_0) 只能清位 ⇒ bit#404 = 0       remove(word_0) ⇒ cnt#404 = 1
   查 word_42 ⇒ 有一光是 0 ⇒ "肯定没有" ✘      查 word_42 ⇒ 7 格全 > 0 ⇒ "可能存在" ✔
        （假阴性：word_42 明明还在）                 （word_42 安然无恙）

   ⇒ 删除能力的价格：每格 1 位 → 1 字节，空间 ×8（4 bit/格则 ×4）。
```

## 逐操作拆解

### API 一览（本节全部对外接口）

### 拆解 1：`bloom_params` —— m 和 k 是解出来的

要求"放 n 个元素、误判率不超过 p"，两个公式：

```
   m = ceil( -n · ln p / (ln2)² )        位数
   k = round( (m/n) · ln2 )              哈希个数（至少 1）
   常数：ln2 = 0.69314718055994530942 ，(ln2)² = 0.48045301391820142467
```

**怎么来的**（三步就能推）：

1. 插 n 个键、每键点 k 位 ⇒ 某个特定位**从没被点过**的概率 ≈ `(1 - 1/m)^(kn) ≈ e^(-kn/m)`，
   所以 **1 的占比 `d ≈ 1 - e^(-kn/m)`**。
2. 一个不存在的键要被骗，它的 k 个位必须**全亮** ⇒ **误判率 `≈ d^k`**。
3. 给定 p 反解"最省的 m"：把 `d^k = p` 对 k 求极值，最优发生在 **`d = 1/2`**
   （位数组恰好一半亮一半灭最划算）⇒ 由 `d=1/2` 解出 `kn/m = ln2`，即 `k = (m/n)·ln2`；
   再代回 `d^k = p` 就得到 `m = -n·ln p/(ln2)²`。

推论两条很好记：**最优 k = log₂(1/p)**；**每元素位数 = m/n ≈ 1.4427 · log₂(1/p)**。
p=1% ⇒ k = 6.64 → 取整 **7**，每元素 **9.585 位**（本节第 2 幕的表把这两列并排打印，可以直接对账）。

**为什么不用 `<math.h>`**：本仓库的编译命令固定不带 `-lm`。
浮点的 `+ - * /` 是编译器直接出指令的，**不需要库**；但 `log/exp/sqrt/pow/ceil/round/fabs` 这些
**函数**是 libm 的符号，不加 `-lm` 就 `undefined reference`。所以：

| 需要的东西 | 本节的替代写法 |
|---|---|
| `ln(p)` | `bloom_ln()`：先用 2 的幂把 x 缩到 [0.5,1)，再用 `ln(v)=2(y+y³/3+y⁵/5+…)`，`y=(v-1)/(v+1)`，`\|y\|≤1/3` 收敛极快。实测 `bloom_ln(0.01) = -4.605170185988091`，与真值差 `8.9e-16` |
| `ceil(x)` | 先 `(unsigned long long)x` 截断（非负数 = 向下取整），再 `if ((double)i < x) i++` |
| `round(x)` | `(int)(x + 0.5)` |
| `sqrt(...)` | `my_sqrt()`：牛顿迭代 `x ← (x + v/x)/2`，40 次（第 5 幕用来算随机波动） |
| `fabs(x)` | `if (x < 0) x = -x` |
| `pow(d, k)` | `pow_int()`：for 循环乘 k 次（k 是个位整数，比调库还快） |
| `log2(1/p)` | 换底：`-bloom_ln(p) / LN2` |

还有一个前提钉死：`_Static_assert(CHAR_BIT == 8, ...)` ——
`/8`、`%8`、`(m+7)/8` 全都建立在"一字节 8 位"上，C 标准只保证 `CHAR_BIT >= 8`。
搬到 9 位字节的机器上，这行会**直接编译报错**，而不是悄悄算错下标。

### 拆解 2：`bloom_add` —— 一遍哈希 + k 次按位

```c
bloom_derive_slots(bloom_hash_str(key), bf->m, bf->k, slots, 64);  /* 扫字符串一遍 */
for (int i = 0; i < bf->k; i++) {
    bits_set(bf->bits, slots[i]);          /* k=7 次 |= 一个字节里的某一位 */
}
```

`bloom_hash_str` 用 **64 位 FNV-1a**：初值 `14695981039346656037`，每字节 `h = (h ^ byte) * 1099511628211`。
三个必须注意的点（注释里都在）：

- 遍历指针写成 `const unsigned char *`：`char` 在 x86 默认**有符号**，中文字节是负数，
  直接进表达式会被**符号扩展**成 `0xFF..xx`，污染高位。
- 必须 `unsigned long long`：长键一定让这个乘法溢出；**无符号溢出 = 对 2^64 取模（标准定义）**，
  有符号溢出 = UB。顺带的福利：无符号 `% m` 永远非负，不需要 `08-hash` 里 `ht_mod` 的"加 m 再取余"补丁。
- 先异或再乘（1a）比先乘再异或（1）雪崩更快，短字符串不撞。

`bloom_hash_int` 是 **乘法 + 右移异或的搅散**（MurmurHash3 / splitmix64 的 finalizer）：

```c
x = (unsigned long long)(unsigned int)key + 0x9E3779B97F4A7C15ULL;
x ^= x >> 30; x *= 0xBF58476D1CE4E5B9ULL;
x ^= x >> 27; x *= 0x94D049BB133111EBULL;
x ^= x >> 31;
```

**为什么要搅散**（第 3 幕实测打印，两个理由一硬一常见）：

1. **硬伤**：不搅散时 `h1 = key`、`h2 = key 的另一半 = 0` ⇒ `slot_i = (h1 + i*0) % m` 对每个 i 都一样
   ⇒ **k 个下标全部重合**，一个键只占 1 位而不是 7 位。第 3 幕把 key=7/1000/1001/1024 的 7 个下标并排打出来，
   左半边是同一个数重复 7 遍；第 5 幕再实测后果：同样 5000 个键、同样 m，**误判率 8.88% vs 1.22%，贵 7.3 倍**。
2. **常见伤**：连续整数只差最低几位；当 m 是 2 的幂、或键是 1024 的倍数（自增主键、页号、内存地址）时，
   整批键会撞在同一个下标段上。乘法把低位信息顶到高位、`^= x >> n` 再把高位搬回低位，两边都混。

`1u`/`1ULL` 的位宽纪律在这里同样适用（`bloom_derive_slots` 里 `b |= 1ULL`）。

### 拆解 3：双重哈希 —— 一个 64 位哈希怎么顶替 k 个独立哈希

教科书写的是"k 个独立哈希函数 h₁…h_k"。**工程上没人真写 k 个**（Kirsch & Mitzenmacher, 2006）：

```
   slot_i = (a + i * b) mod m ,  i = 0 .. k-1
   a = h % m                       ← 唯一起点
   b = 1|搅散(h) % m               ← 步长，强制奇数、强制非 0
```

为什么够用：

1. **理论**：误判率的分析只需要这些下标**两两接近独立**（pairwise independence），一次线性组合恰好给得出；
   论文证明这样造出来的过滤器与"真 k 个独立哈希"的版本**渐近误判率相同**。
2. **省**：字符串只扫 **一遍**（真 k 个哈希要扫 k 遍，k=7 就是 7 倍指令数），剩下 k-1 个下标是加法和取模。
3. **可验证**：先把 a、b 都 `% m` 再等差，所以这 k 个下标是 **Z_m 上一条干净的等差数列**。
   第 3 幕专门打印"相邻差"那一行，7 个差全是 5077 ⇒ 一眼验证结构正确。
   （顺带：直接在 64 位大数上算 `h1 + i*h2` 也能跑，但每次 `i*h2` 都会在 64 位里回绕，
   而 `2^64 mod m ≠ 0`，等差性质在 mod m 之后就看不出来了 —— 能用，但不利教学。）
4. **b 为什么要奇数、为什么要防 0**：
   - `b = 0` ⇒ k 个点全重合（就是上面"硬伤 1"），所以绝不允许；
   - m 是 2 的幂而 b 是偶数 ⇒ `a + i*b` 只会落在 m 的**一半**位置上（另一半永远点不到，白白浪费空间），
     所以 `b |= 1ULL` 保证奇数，和任何 2 的次幂互质。m 是奇数时 `b |= 1` 可能把 b 顶到 m，代码里退 2 处理。

### 拆解 4：`bloom_maybe_contains` —— 短路返回

```c
for (int i = 0; i < bf->k; i++) {
    if (bits_test(bf->bits, slots[i]) == 0) {
        return 0;          /* 一个灭的就够了：肯定没有，剩下几个不用看 */
    }
}
return 1;                  /* 全亮：只能说"也许有" */
```

- 返回 **0 是硬保证**，返回 **1 是软结论** —— 这条不对称就是布隆的全部价值。
- 短路让"肯定没有"平均只看一半的位（占比 50% 时期望 2 次左右），热路径更快。
- **它不比较键、不 strcmp**：这就是它能省 50 倍的根因，也是它不能给出精确答案的根因。

### 拆解 5：删除 —— 标准版禁止，计数版收费

- 标准版：**没有 `bloom_remove`**。只有 `bloom_naive_remove()` 这个反面教材（第 8 幕用它现场制造假阴性）。
  实测：装满 200 个键（占比 52%）后删掉 1 个键 ⇒ 剩下 199 个键里 **2 个被误伤成"肯定没有"**；
  理论上也该如此：A 的 7 个位全部只属于 A 的概率 ≈ `(1-占比)^7 = 0.58%`。
- 计数版：`counting_bloom_add/remove/maybe_contains`，**实现了，也实测了**。
  第 9 幕：同一个共用格从 2 减到 1，B 依然报告"可能存在"，剩下 199 个键**误伤 0 个**；
  批量插 100 全删 100 ⇒ 计数版复查 0/100 "可能存在"，而标准版仍是 100/100（位关不掉）。
  代价：一格 1 字节 ⇒ **8 倍空间**（4 bit/格是 4 倍，但要处理半个字节的奇偶对齐，本节不写）。
  新增的坑：计数器撞到 255 就**停在 255 不再加**并永久置 `counter_overflowed = 1`，
  此后 remove 不再保证正确（本节代码挡住了回绕，但没实测饱和路径 —— 要往同一格塞 256 次才撞得到）。

## 复杂度

记 n = 已插入键数、m = 位数、k = 哈希个数、L = 键长（字符串字节数）。

| 操作 | 时间 | 说明 |
|---|---|---|
| `bloom_new(n,p)` | O(m/8) | calloc 一条清零的位数组（"位图初值 0 就是算法的一部分"，呼应 `00-c-foundation/dynamic-memory`） |
| `bloom_add` | **O(L + k)** | 扫键一遍 + k 次 `|=`（外加 k 次 `% m` 除法） |
| `bloom_maybe_contains` | **O(L + k)**（平均更短，见到 0 就短路） | k 次 `&` 测试 |
| `bloom_ones` / `bloom_density` | O(m) | 只为体检存在，**不在热路径上**，别在循环里调 |
| 空间 | **m bit = m/8 字节** | `m ≈ 1.4427 · n · log₂(1/p)` ⇒ p=1% 时每元素约 **9.6 位 = 1.2 字节** |
| 计数版空间 | m 字节（4 bit 版 2m 位） | 是标准版的 **8 倍**（4 倍） |
| 删除 | 标准版 **不支持**；计数版 O(k) | 见拆解 5 |

和精确结构对比（同一批 5000 个字符串，本节第 6 幕的实测）：

| | 布隆（p=1%） | 哈希表粗估 |
|---|---|---|
| 位数/字节 | 47926 位 | — |
| 字节 | **5991** | **300000**（60 字节/元素） |
| 会不会误判 | 会（实测 1.22%） | 不会 |
| 能不能删 | 不能 | 能 |
| 能不能列出全部元素 | 不能 | 能 |
| 键长影响内存 | **完全无关** | 线性相关 |

> k 的取舍直觉：k 变大 ⇒ 同一 m 下占比更低、误判更低，但每次 add/查询多几次位操作；
> 最优 k 就是 `log₂(1/p)`，跑偏一点也不致命，**n 估小才致命**（第 7 幕实测超售 1.6 倍 ⇒ 误判率 8.12%）。

        A 的 7 个位【全部只属于 A】（删掉一个人都伤不到）的概率 ≈ (1-占比)^k = 0.5842%
      ⇒ 性质对照：误判（假阳性）只是让人【多查一次】，能容忍；

        布隆唯一的卖点就是「不会假阴性」，所以标准布隆【禁止删除】——

## 常见的坑

1. **把"可能存在"当成"存在"用**。返回 1 只有 p 比例是假的，但你如果据此直接拒绝/放行，
   就把一个概率结构当成了精确结构。**唯一正确姿势**：0 直接处理，1 再去真表复核。
2. **n 估小了**。本节第 7 幕实测：按 5000 设计却插到 8000 ⇒ 误判率从 1.22% 涨到 8.12%。
   而且布隆**不能就地扩容**（m 一变，所有旧键的下标全错位），只能新建大的重灌一遍。
   **n 宁可多估一倍**。
3. **试图删除**。第 8 幕现场：删 1 个键误伤 2 个键。位只有 0/1 两个状态，
   它不知道这个位被几个键借用，所以清位 = 制造**假阴性** ——
   假阳性只是多查一次，假阴性是业务事故。要删就上计数布隆（第 9 幕），付 8 倍空间。
4. **int 键不搅散**。第 3/5 幕实测：`h2 = 0` 让 k 个下标全重合，误判率 1.22% → 8.88%。
   连续整数、1024 的倍数、内存地址这类"低位有规律"的键，必须先 `key += 常数; 乘-移位-异或` 搅散。
   顺带：`int` 转 64 位要先 `(unsigned int)key`，否则负数被符号扩展成 `0xFF...`，所有负数长得一模一样。
5. **以为能问出"里面都有哪些元素"，或者以为能反查**。位数组里没有键的任何副本
   （第 4 幕打印了前 8 个字节，全是 0 和 1）。也因此**键必须能被重新生成出来**：
   本节 main.c 一个字符串都没保存，每次都用 `snprintf` 现场造 `user_%d`。
6. **`inserts` 不是去重后的元素个数**。`bloom_add` 对同一个键调两次，`inserts` 就是 2
   （布隆无法知道这个键之前来过，`add` 里没有"查一下再加"这步 —— 加了也白加，位已经亮了）。
   它只是"add 被调用了几次"的记账，别拿它当 cardinality 用。
7. **`/8`、`%8` 写成 `/sizeof`、或者忘了向上取整**。字节数必须是 `(m + 7) / 8`
   （整数除法是向下取整，先加"除数-1"才是向上取整）；写 `m/8` 会少分配一个字节，
   最后一个字节的赠品位（`m` 不是 8 的倍数时多出来的那几位）访问就越界 —— ASan 第一个抓到它。
8. **位号用 `1 << n` 而不是 `1u << n`**。第 7 位侥幸没事，`1 << 31` 是 UB，
   `1u << 40` 也是 UB（移位量 ≥ 位宽）。64 位域一律 `1ULL`。
9. **多线程共享一个位数组**。`bits_set` 是 `字节 |= 掩码`，**读-改-写不是原子的**，
   两个线程改同一个字节的不同的位会丢改动 ⇒ 某个键的某个位没按亮 ⇒ **假阴性**（又是致命的）。
   正规做法：每线程一个分片、查询时 OR 起来；或者对整个 `unsigned long` 做原子 OR（要按字对齐）。
10. **用 p 来解释"精确率"**。p 是"**对不存在的元素**误判的概率"；对**存在**的元素它说"有"是 100% 正确的。
    想算"报'有'的可信度"要的是另一件事（取决于集合内/外键的比例），别把两者混起来。
11. **计数布隆的计数器回绕**。撞到 255 还继续 `+1` 会回到 0（无符号溢出是定义好的，但语义错了），
    之后 `remove` 就会把占用数减错，**假阴性又回来了**。本节的做法是撞到就停住 + 永久标记 `counter_overflowed`。

## 自检问题

1. `bloom_maybe_contains` 返回 0 和返回 1，可信度有什么不同？为什么？
   **答**：返回 0 是**硬保证**（一定没来过）：加过 ⇒ k 个位都被按亮，而位只有 0→1 单向变化，
   所以现在必然全亮；逆否命题就是"看到任何一个 0 ⇒ 没加过"。
   返回 1 只是**软结论**：这 k 位可能被别的键分别点亮，概率约 `占比^k`。

2. n = 10000、p = 1% 时，m 大约多少位？k 取几？（不许按计算器，用两个推论）
   **答**：`k = log₂(1/p) = log₂100 ≈ 6.64 → 7`；每元素 `m/n = k/ln2 ≈ 1.4427·k ≈ 9.6` 位
   ⇒ `m ≈ 96000` 位 = **12000 字节**。同样 p 下空间只随 n 线性增长，系数固定 ≈ 9.6 位/元素。

3. 为什么 `bytes = (m + 7) / 8`？多出来的几位会不会被误命中？
   **答**：整数除法向下取整，加 7 再除是标准的"向上取整除法"，因为 `m` 通常不是 8 的倍数，
   必须把最后那个"半空字节"也分配出来，否则 `bits[idx/8]` 越界。
   多出来的几位**永远不会被命中**，因为下标是 `% m` 得到的（范围 0..m-1），
   它们只会一直是 0 —— 所以数"1 的占比"时也只能数到 `m`，不能数整个字节的位（本节的 `bloom_ones` 就是按 m 循环的）。

4. 本节只用了一个哈希函数（FNV-1a），为什么敢说是"k 个哈希"？
   **答**：`slot_i = (a + i*b) mod m`。误判率分析只需要**两两接近独立**，线性组合给得出这个性质
   （Kirsch & Mitzenmacher 证明与真 k 个独立哈希渐近同误判率）。
   好处是字符串只扫一遍；`b` 强制奇数且非 0，否则 k 个点会重合或只覆盖 m 的一半位置。

5. 把 `bits_clear` 用在标准布隆过滤器上会出什么事？计数布隆为什么没这个问题？
   **答**：会造出**假阴性**（第 8 幕：删 word_0，word_42 一起消失，另外还误伤 1 个）。
   位只有 1 bit，"这一格被几个人用"的信息根本没记下来。计数布隆每格是个计数器，
   删除只减自己那一份（2 → 1），别人那份还在，所以查询依然报"可能存在"。

6. 第 7 幕：按 n=5000 设计的过滤器，插到 8000 个键时占比 68.9%、误判率 8.12%。
   为什么误判率涨得这么凶？
   **答**：误判率 = `占比^k`，k=7 是指数。占比从 0.517 到 0.689（×1.33），
   误判率就变成 `1.33^7 ≈ 7.5` 倍（实测 1.22% → 8.12%）。
   **指数结构对"超出设计容量"毫无容忍度** —— 这就是 n 必须给足余量的数学原因。
